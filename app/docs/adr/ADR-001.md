# ADR-001: Build a server-rendered Django application

## Status

Proposed, October 2026. Not yet reviewed or accepted.

## Context

Organizers and attendees need one current registration
record. Ownership and capacity rules must hold whatever a
browser sends. Main journeys must work with a keyboard and
on narrow screens. A small volunteer team must be able to
build and maintain the application, and the book's readers
are learning Django.

## Options

- A: a connected form and spreadsheet.
- B: a server-rendered Django application with a database.
- C: a Django API with a separate JavaScript client.

## Decision

Build the first release as one Django application that
renders HTML pages on the server, stores records in a
relational database, and applies Otahque's rules in its
views and models.

## Consequences

One application to build, test, and host. Rules run in one
place. Pages work with links and forms before any
JavaScript. Highly interactive screens need extra work, and
other software has no API until one is added.

## Revisit if

A mobile or partner application needs Otahque's data;
check-in or other work must continue offline; measurement
shows that server rendering cannot meet an agreed
performance target.
