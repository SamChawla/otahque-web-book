Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 and L2 check what you have just learned. L3 asks how it works underneath. L4 and L5 ask about the design and leadership decisions that later chapters build on: attempt them now, and return to them when you reach those chapters. Use the readiness checkpoint to decide whether to continue. If an answer is difficult, revisit its worked example and explain the result in your own words. L4 and L5 are extension questions, not a gate to the next chapter.

L1 (Junior): What is the difference between a list and a dictionary, and when would you use each?

What the interviewer is testing: Can you choose a collection by how its values will be found?

Flip to check your answerFold answer back

Perfect answer: A list is an ordered collection: you select an item by its position, counting from 0. A dictionary maps keys to values: you look a value up by its key. Use a list for a sequence of similar things, such as events in order, and a dictionary for the named facts about one thing, such as an event’s title and whether it is published. This chapter combines them as a list of dictionaries. When a key may be missing, get() returns a default instead of raising KeyError.

Behind the scenes:

how each lookup finds its item (summary)

# titles[1]       -> go straight to position 1
# event["title"]  -> hash("title") picks the slot to check,
#                    so lookup by key does not scan every item
# "title" in titles would scan the list item by item

Code proof: in a file run with Python 3.14:

Python

event = {"title": "Python Evening", "is_published": True}
titles = ["Python Evening", "Testing Clinic"]
print(titles[1])
print(event["title"])
print(event.get("venue", "Venue to be confirmed"))

Output

Testing Clinic
Python Evening
Venue to be confirmed

Common mistakes:

  • Expecting index 1 to be the first item.
  • Misspelling a key and then reading the KeyError as a broken dictionary.
  • Using a list where looking up by name would be clearer.

Follow-up the interviewer might ask:

  • “How would you count the published events in a list of dictionaries?”
  • “What does len() return for each collection?”

L2 (Mid-Level): What does a function return if it has no return statement, and why does that matter?

What the interviewer is testing: Can you tell output that is displayed from a value that is returned?

Flip to check your answerFold answer back

Perfect answer: It returns None. print() displays text but gives nothing back to the caller, so storing the result of a function that only prints stores None. That matters as soon as the result is used: a label function that prints instead of returning leaves the caller with None to display or compare, and the mistake shows up far from its cause. Return the value, and let the caller decide whether to print it.

Behind the scenes:

what every call evaluates to (summary)

# Every function call is an expression with a value.
# Reaching the end of the body is the same as `return None`.
# print() itself returns None after writing its text.

Code proof:

Python

def show_title(title):
    print(title)

result = show_title("Python Evening")
print(result)

Output

Python Evening
None

Common mistakes:

  • Confusing printed output with a return value.
  • Returning in one branch and forgetting the other.
  • Reading None as an error rather than as a value.

Follow-up the interviewer might ask:

  • “Change show_title so that the caller can use the title.”
  • “When is returning None the right design?”

L3 (Senior): Explain instance attributes, and why changing one object does not change another.

What the interviewer is testing: Do you understand what self refers to, and what the class and its instances each hold?

Flip to check your answerFold answer back

Perfect answer: Calling a class creates a new instance. Python runs __init__ with self referring to that new object, so self.title = title stores an attribute on that one instance. first and second each have their own title, so changing first.title leaves second.title alone (Figure 4.4). Methods are defined once, on the class, and shared: when you call first.label(), Python passes first as self. A value assigned on the class itself is different: it is shared by every instance until an instance assigns its own.

Behind the scenes:

first = EventCard("Python Evening") (summary)

# 1. Python creates a new, empty EventCard object
# 2. EventCard.__init__(that_object, "Python Evening") runs
# 3. self.title = ... stores into that object's own attributes
# first.label() is EventCard.label(first)

Code proof:

Python

class EventCard:
    def __init__(self, title):
        self.title = title

    def label(self):
        return "Event: " + self.title

first = EventCard("Python Evening")
second = EventCard("Testing Clinic")
first.title = "Python Afternoon"
print(first.label())
print(second.label())

Output

Event: Python Afternoon
Event: Testing Clinic

Common mistakes:

  • Thinking the class holds one title for all its instances.
  • Leaving out self.
  • Putting a list on the class and being surprised that every instance shares it.

Follow-up the interviewer might ask:

  • “What happens if the class defines titles = [] and each instance appends to it?”
  • “Why does label() need self?”

L4 (Staff): Why does every project need its own virtual environment, and how do you prove which Python and packages a project is using?

What the interviewer is testing: Can you explain isolation and verify an environment instead of assuming it?

Flip to check your answerFold answer back

Perfect answer: A virtual environment gives a project its own place to install packages, so versions do not collide with another project or with the system’s Python, and the environment can be rebuilt from recorded versions. uv records the Python version in .python-version and creates .venv, and we select it with --python .venv. To prove it, print sys.executable, which should point inside .venv, and compare sys.prefix with sys.base_prefix, which differ inside a virtual environment; uv pip list --python .venv shows its packages. Rebuild an environment on each machine rather than copying the folder: it contains machine-specific paths.

Behind the scenes:

how Python knows it is in an environment (summary)

# uv venv writes .venv/pyvenv.cfg, naming the base Python.
# At startup, Python finds pyvenv.cfg beside its executable
# and sets sys.prefix to .venv; sys.base_prefix still names
# the base installation, so the two differ.

Code proof: with a file run by uv run --no-project --python .venv:

Python

import sys

print(sys.executable)
print(sys.prefix != sys.base_prefix)

Output

[a path inside your project's .venv folder]
True

Common mistakes:

  • Installing packages into the system’s Python.
  • Running one environment’s interpreter while believing another is selected.
  • Copying or sharing .venv.

Follow-up the interviewer might ask:

  • “How would a teammate rebuild your environment?”
  • “What is the difference between pinning a package and locking every dependency?”

L5 (Lead): You are onboarding three new contributors to a Python project. What do you standardize before they write code, and why?

What the interviewer is testing: Can you make a team’s results reproducible and its problems quick to diagnose?

Flip to check your answerFold answer back

Perfect answer: Standardize what makes results the same everywhere and errors easy to report: one exact Python version, recorded in the project; one tool for environments, such as uv; a separate environment per project; commands written for each platform; and a readiness script that stops loudly when something is wrong, like this chapter’s readiness.py. Agree how to report a problem: the command, the working directory, the full traceback, and the versions. Leave personal choices, such as the editor, to each person. Onboarding is finished when each contributor’s readiness check gives the expected output, before their first change.

Behind the scenes:

what a readiness script should check (summary)

1. the Python version matches the pinned one
2. the interpreter is inside the project's environment
3. the project's own code imports
4. a few known inputs give known results
then print one clear success line, or fail at the first gap

Code proof: this chapter’s readiness program, run with the practice environment:

Terminal

uv run --no-project --python .venv readiness.py

Output

Readiness checks passed

Common mistakes:

  • Setup notes that say only “install Python”.
  • Standardizing personal preferences, such as the editor.
  • Onboarding without a verification step.

Follow-up the interviewer might ask:

  • “A contributor’s readiness check passes but the project still fails. What next?”
  • “What belongs in a README, and what in a script?”
