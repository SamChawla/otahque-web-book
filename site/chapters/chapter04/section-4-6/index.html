4.6 Virtual environments and readiness check

Sai can now run the two files. Later, one project may need a different package version from another. A virtual environment gives a project its own package installation area, so installing a dependency for one project need not change the other. It also gives us an explicit interpreter path to check.

Starting point: completed 4.5, with event_text.py and preview.py in otahque-python-practice, uv 0.13.5 available, and CPython 3.14.9 verified. Keep the shell in that directory. This section creates .venv beside your source files, records the Python pin, adds an identity-check file, and finishes with a small readiness program. No third-party packages or Django are required.

Create the environment with the selected Python

Use uv to record the Python version and create the environment. First inspect the directory: if .python-version already exists, read it before changing it; if .venv exists, use the recovery instructions below. For this new practice directory, run these commands in PowerShell or a macOS/Linux/WSL shell:

uv python pin 3.14.9
uv venv --python 3.14.9

The first command writes 3.14.9 into .python-version. uv can read that file when selecting Python; it is not a package list or a dependency lock. The second command creates .venv using the requested Python. Expect a creation message naming .venv and possibly an activation hint. Windows stores its Python executable under Scripts; macOS/Linux uses bin. Your source files stay beside the environment.

If .venv already exists, inspect it with the identity checks below instead of recreating it over unknown contents. If it is wrong or incomplete, preserve it and run uv venv --python 3.14.9 .venv-check in a fresh directory name; substitute .venv-check wherever later commands select .venv. For creation failures, read the error, check the selected Python and directory permissions, correct the cause, and retry into a new environment directory. No pip bootstrap is needed.

Use the environment without depending on activation

Run preview.py through the selected environment. This command is the same in PowerShell and macOS/Linux/WSL shells:

uv run --no-project --python .venv preview.py

The output must still be Python Evening, then Private draft. Here --python .venv selects the environment directory explicitly. Activation is an optional shell convenience that changes command lookup; it does not create the environment. These uv commands do not need activation. The expected no-project warning described in 4.5 may also appear.

Que. 20 Does an environment choose a different Python version merely because its directory is named .venv?

Show answerHide answer

Answer. No. uv venv --python 3.14.9 selects the base Python used to create it. The name .venv is a convention. Choosing the intended base interpreter and inspecting the resulting environment are separate from naming its folder.

Verify the interpreter, not just the prompt

Create check_environment.py beside preview.py with the following complete content:

import sys

print(sys.version.split()[0])
print(sys.executable)
print(sys.prefix)
print(sys.base_prefix)
print(sys.prefix != sys.base_prefix)

The standard library is the collection of modules included with Python. sys is one of those modules. sys.version contains interpreter version information; split() separates its whitespace-delimited parts and [0] selects the first, the version number. sys.executable identifies the running interpreter. sys.prefix identifies its environment prefix, while sys.base_prefix identifies the base installation. The != comparison asks whether the two prefixes differ.

All platforms:

uv run --no-project --python .venv check_environment.py

Read the five output lines in order. The first must be 3.14.9. The executable path should identify .venv/Scripts/python.exe on Windows or .venv/bin/python on macOS/Linux, with your machine’s path separators. The next line identifies .venv; the following line identifies the base Python installation. The final line must be True. Paths differ between computers, so compare their roles rather than copying a sample absolute path.

A False final line means the interpreter reports that it is outside a virtual environment. Check the exact executable used by the command, not just the prompt’s appearance. A different version means the environment was created with another base interpreter. Preserve the source files and create a new environment using the verified 3.14.9 installation.

Keep the package tool attached to the interpreter

uv has a pip-compatible interface for inspecting and managing packages. It does not invoke a separately installed pip program. Inspect this environment without installing anything:

All platforms:

uv pip list --python .venv

In this freshly created environment, the command succeeds with no package rows; output may be empty. Python’s standard-library modules are not third-party package rows. uv venv does not install pip by default, and uv pip does not need it in the environment. A missing pip module is therefore not an error to repair here. The --python .venv option identifies exactly which environment to inspect. Do not add packages for this exercise.

A virtual environment isolates package availability by default; it is not a security boundary against programs you run. It also depends on its base Python and contains machine-specific paths. Keep your source files as the durable work; recreate an environment on another machine rather than copying its directory. Chapter 8 will develop dependency records and reproducible project setup.

Official references: https://docs.astral.sh/uv/pip/environments/ and https://docs.python.org/3.14/library/sys.html. Once the selected Python is installed, these local, dependency-free runs and package inspections need no download. Chapter 8 will introduce uv project metadata, dependencies, and locking; we do not run uv init or create a lockfile here.

Que. 21 Can a successful import or a prefix comparison prove that the future Django application is correct?

Show answerHide answer

Answer. No. These checks establish which interpreter and package environment you are using. Application behaviour needs its own examples and tests. The files here still operate only on fictional in-memory values.

Bring the language pieces together

Save event_card.py using the complete class definition from 4.4. For convenience, its exact content is repeated here; keep it beside event_text.py, not inside .venv:

class EventCard:
    def __init__(self, title):
        self.title = title

    def label(self):
        return "Event: " + self.title

Create readiness.py with this complete content:

from event_card import EventCard
from event_text import event_label


def count_published(events):
    count = 0
    for event in events:
        if event["is_published"]:
            count = count + 1
    return count


events = [
    {"title": "Python Evening", "is_published": True},
    {"title": "Testing Clinic", "is_published": False},
]
assert count_published(events) == 1
assert count_published([]) == 0
assert event_label("Testing Clinic", False) == "Private draft"
assert event_label("Python Evening", True) == "Python Evening"
card = EventCard("Python Evening")
assert card.label() == "Event: Python Evening"
print("Readiness checks passed")

count starts at zero for each call. Each matching event adds one; the return is outside the loop, so all items are considered before the count is returned. An empty list skips the body and returns zero. The imports reuse the label function and the class, while card is one instance of that class.

assert evaluates a condition and raises AssertionError if it is false in these normal runs. The checks cover a mixed list, an empty list, both label branches, and an instance method. Only after they pass does the final message print. These are small learning checks; do not use assertions for application authorization or input validation, because optimized Python execution can disable them. Run the commands as written, without an optimization option.

All platforms:

uv run --no-project --python .venv readiness.py

Expected output:

Readiness checks passed

If you see AssertionError, identify the failed comparison and predict the actual value before editing. If an import fails, check that readiness.py, event_text.py, and event_card.py are saved together. Do not remove the failing assertion to obtain the success message. Keep a copy before changing a working example.

In practice: working on two Python projects

Situation. A developer maintains an older project while learning with a separate practice project.

Application. Give each project its own virtual environment and use uv to select the intended one. This separates their installed packages while keeping source files outside the environment.

Consideration. An environment is not a portable dependency record or a security boundary. Chapter 8 will develop dependency records and reproducible project setup.

Try it yourself

Save readiness.py as readiness_changed.py. Change the second event’s False to True and predict what happens before running it. Then adjust the expected count to match this changed input, leaving the empty-list and label checks intact. Finally, explain what goes wrong if return count is indented inside the for loop.

Que. 22 What should the changed run and diagnosis show?

Show answerHide answer

Answer. The first run raises AssertionError at the comparison with 1, because both events now match and count_published returns 2. Change that expected count to 2; the success message should return and the other checks still pass. Moving return count inside the loop would exit after the first item. With no items, that misplaced return would never run, so the function would return None instead of zero. The empty-list check helps expose that mistake.

To run the changed copy, use the same environment interpreter and substitute readiness_changed.py for readiness.py in the preceding command. You now have evidence from a prediction, an observed failure, and a reasoned correction. The unchanged readiness.py remains your reference.

Readiness checkpoint: explain, run, and diagnose

Before moving into Django setup, explain a branch and a loop including the empty case; distinguish return from print; follow a module import and an instance-method call; and locate a failing operation in a traceback. On your own machine, record the uv and Python versions, current practice-directory path, expected and actual preview output, environment identity result, uv package-list result, and readiness result. Keep those observations in a plain-text file named readiness-notes.txt in the practice directory. Use your actual paths and results; there is no pre-filled claim of success.

If a language prediction is uncertain, return to that section’s short exercise. If a command fails, preserve the error and use the directory/interpreter checks before changing code. Completing only the paper work is useful progress, but the tools checkpoint is complete only after you run and explain the results on your machine. This chapter has prepared Python practice files, not a Django application or a verified registration feature.
