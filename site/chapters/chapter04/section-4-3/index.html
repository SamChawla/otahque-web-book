How We Build It

Starting point: the paper examples in What You Need to Know; no existing application checkpoint. You need a plain-text editor, a terminal, and internet access for the initial tool downloads. These steps install uv 0.13.5, select CPython 3.14.9, create a folder named otahque-python-practice with a few small Python files and a .venv/ environment, and end with a readiness program that prints Readiness checks passed. No Django package is needed yet.

The Custom Way: whatever Python the shell finds

The most direct way to run a file is to type the name of a Python program and the file. Read this listing; you do not need to run it:

illustration_only (not a setup step)

python --version
python preview.py

It sometimes works, and that is the problem. python is not a fixed program: the shell searches the directories on its PATH and runs the first match. On one computer that is Python 3.14, on another an older 3.x, on a third nothing at all; on Windows, typing python without an installation can open the Microsoft Store instead. Installed packages then land in whichever Python ran, and two projects that need different versions of a package collide. Nothing in the command records which interpreter you meant. The two steps below replace that guesswork with uv, a pinned Python, and an environment we can name in every command.

Step 1: Run saved files from an editor and a terminal

Sai wants to check the predictions rather than trust them. She needs to know which file she saved, where her terminal is working, and which Python will run it. Those are three separate questions; a useful setup makes each answer visible.

This step installs uv 0.13.5 and uses it to select CPython 3.14.9. CPython is the standard implementation of Python. You will create two runnable files in a new folder named otahque-python-practice and compare their output with your predictions from What You Need to Know.

Identify the three tools

An editor lets you write and save plain text. A terminal is the window in which you interact with a command-line program. A shell interprets commands typed there: use PowerShell on Windows, or the usual shell in macOS Terminal or Linux/WSL. WSL is Windows Subsystem for Linux; its terminal follows the Linux instructions, not the PowerShell ones. The Python interpreter is the program that executes Python source code.

On Windows, Windows Terminal can open different shells in separate tabs. Choose a PowerShell tab for the Windows commands in this book. Command Prompt (cmd.exe) is another shell with different command syntax. Bash is a shell commonly used on Linux; a Bash tab inside WSL follows the Linux/WSL instructions. Check the tab’s shell before copying a command; the terminal window alone does not tell you which syntax to use.

Use an editor you already know that saves plain text and preserves indentation. Configure it to insert four spaces for each indentation level. A word processor is not suitable for .py files. On Windows, show filename extensions and check that the saved name is preview.py, not preview.py.txt. Keep ordinary straight quotation marks in source code.

Install uv and select the pinned Python

New Tool: uv

What problem exists? Each project needs a known Python version and its own installed packages, and the command that runs it should say which.

What did people do before? They installed Python versions by hand, created environments with the built-in venv module, and installed packages with pip, using separate tools and commands that differ between platforms.

What is uv? A tool from Astral that installs Python versions, creates virtual environments, and manages packages from one consistent command line.

Why uv? One tool and one command form on Windows, macOS, and Linux, with the exact version named in every command. The standard-library venv module remains valid; this book uses uv to keep Python selection and environment management in one workflow.

Now let’s install it.

A virtual environment is still the underlying isolation mechanism; we will inspect one in Step 2.

This book pins uv 0.13.5, the current stable release when this chapter was written (October 2026), and CPython 3.14.9. Python 3.14 is compatible with the planned Django 6.1 series. Pinning means naming the exact version used for the examples. Recheck versions at a future setup checkpoint rather than silently changing them halfway through the exercises.

If uv is not installed, use Astral’s versioned installer below. These commands download and execute its installation script, so use the official address as shown. No existing Python installation is required. On a managed computer, use your administrator’s approved installation route. Run commands at the shell prompt, not at Python’s >>> prompt; do not type a prompt symbol.

Windows PowerShell (the backtick continues the command on the next line):

PowerShell

$uvInstaller = 'https://astral.sh/uv/0.13.5/install.ps1'
powershell -ExecutionPolicy Bypass -Command `
    "Invoke-RestMethod '$uvInstaller' | Invoke-Expression"

The execution-policy option applies to that child PowerShell process. It does not change the machine’s permanent policy. Follow the installer’s completion message and open a new PowerShell window so it can find uv.

macOS Terminal or Linux/WSL Bash:

Terminal

curl -LsSf https://astral.sh/uv/0.13.5/install.sh | sh

Open a new terminal after installation. If curl is unavailable, follow Astral’s installation guide for an alternative supported method. Windows Subsystem for Linux uses the Linux installation inside WSL, separately from Windows.

All platforms: check uv before continuing. If you already have it, start here rather than rerunning the installer.

Terminal

uv --version

The version must begin with uv 0.13.5, the version used throughout this book; build information may follow. If uv is not found, reopen the terminal and follow the installer’s PATH guidance. PATH is the list of directories your shell searches for commands. If another version appears, inspect Get-Command uv in PowerShell or command -v uv on macOS/Linux, then select the intended installation. Do not overwrite a shared installation merely to match this exercise.

All platforms: install the selected Python and check it:

Terminal

uv python install 3.14.9
uv run --no-project --python 3.14.9 python --version

The install command downloads Python if needed. uv-managed CPython builds come from Astral’s python-build-standalone project; they are not the python.org graphical installer. The second command asks uv to run Python with the requested version. --no-project keeps these exercises independent of any enclosing uv project. uv may warn that no project was found; that warning is expected here and does not mean the Python command failed.

Expected Python output:

Output

Python 3.14.9

If the download fails, preserve the error and check connectivity, available disk space, and permission to write to the installation directory before retrying. Do not replace the operating-system Python. If the version differs, stop and inspect the command and selected installation before creating the environment.

Official guides: https://docs.astral.sh/uv/getting-started/installation/ and https://docs.astral.sh/uv/guides/install-python/. These steps have been tested on Windows. The macOS, Linux, and WSL commands follow Astral’s documentation but have not yet been tested for this book; if one behaves differently, follow the official guides and please report the difference.

Choose a directory you can identify

A directory is a folder. The current working directory is the folder the shell uses to resolve relative paths such as preview.py. Choose an existing parent folder where you keep learning work, open your terminal there, and inspect it before creating anything:

Windows PowerShell:

PowerShell

The first command prints your current path; the second lists its entries. Your path will differ from another reader’s. Create the practice directory only if that name is not already in use:

The final path must end in otahque-python-practice. If that folder already exists, inspect it; use it only if it is your intended practice folder. Otherwise choose a new name, such as otahque-python-practice-2, in both commands. Do not delete or overwrite an existing folder to follow the example. A path containing spaces needs quotation marks when used as a command argument.

Save the reusable module and runner

Open that same directory in your editor. Create event_text.py and save this complete content; it is the function from “Functions and imports”:

Python

def event_label(title, is_published):

        return title

Create preview.py beside it, with this complete content:

Python

from event_text import event_label

Save both files before running. In the shell, still inside the practice directory, check the filenames and execute the runner:

macOS Terminal or Linux/WSL Bash:

Terminal

Expected output:

Output

The command names the file to execute. Python can find event_text.py beside the runner; the import makes its function available. After the program ends, the shell prompt returns. Running the file again starts a fresh interpreter execution. You may also notice a __pycache__ directory containing cached imported code; it is not the source file you edit.

Recognize the interactive prompt

Running uv run --no-project --python 3.14.9 python without a script filename opens interactive Python and shows >>> after a version banner. At that prompt, enter Python statements such as print("Hello"). A directory-changing shell command does not belong there. To return to the shell, type exit() and press Enter. The >>> and continuation ... markers are prompts, not text to copy into a .py file.

Step 2: Create a virtual environment and run the readiness check

New Concept: virtual environment

What problem exists? Two projects can need different versions of the same package, and installing one would break the other.

What did people do before? Installing all packages into one shared Python is a simpler starting arrangement, but one project’s dependency changes can affect another.

What is a virtual environment? A Python environment with its own package installation area, built on a base Python. Packages installed into it do not change the base installation or other environments.

Why use one? Each project gets its own packages, and its interpreter path tells you exactly which environment ran.

Now let’s create one beside the practice files.

Sai can now run the two files. This step gives them an environment of their own, with an interpreter path we can check.

Starting point: completed Step 1, with event_text.py and preview.py in otahque-python-practice, uv 0.13.5 available, and CPython 3.14.9 verified. Keep the shell in that directory. This section creates .venv beside your source files, records the Python pin, adds an identity-check file, and finishes with a small readiness program. No third-party packages or Django are required.

Create the environment with the selected Python

Use uv to record the Python version and create the environment. First inspect the directory: if .python-version already exists, read it before changing it; if .venv exists, use the recovery instructions below. For this new practice directory, run these commands in PowerShell or a macOS/Linux/WSL shell:

PowerShell

uv python pin 3.14.9
uv venv --python 3.14.9

The first command writes 3.14.9 into .python-version. uv can read that file when selecting Python; it is not a package list or a dependency lock. The second command creates .venv using the requested Python. Expect a creation message naming .venv and possibly an activation hint. Windows stores its Python executable under Scripts; macOS/Linux uses bin. Your source files stay beside the environment.

If .venv already exists, inspect it with the identity checks below instead of recreating it over unknown contents. If it is wrong or incomplete, preserve it and run uv venv --python 3.14.9 .venv-check in a fresh directory name; substitute .venv-check wherever later commands select .venv. For creation failures, read the error, check the selected Python and directory permissions, correct the cause, and retry into a new environment directory. No pip bootstrap is needed.

Use the environment without depending on activation

Run preview.py through the selected environment. This command is the same in PowerShell and macOS/Linux/WSL shells:

PowerShell

uv run --no-project --python .venv preview.py

The output must still be Python Evening, then Private draft. Here --python .venv selects the environment directory explicitly. Activation is an optional shell convenience that changes command lookup; it does not create the environment. These uv commands do not need activation. The expected no-project warning described in Step 1 may also appear.

Que. 20 Does an environment choose a different Python version merely because its directory is named .venv?

Flip to check your answerFold answer back

Answer. No. uv venv --python 3.14.9 selects the base Python used to create it. The name .venv is a convention. Choosing the intended base interpreter and inspecting the resulting environment are separate from naming its folder.

Verify the interpreter, not just the prompt

Create check_environment.py beside preview.py with the following complete content:

Python

import sys

print(sys.version.split()[0])
print(sys.executable)
print(sys.prefix)
print(sys.base_prefix)
print(sys.prefix != sys.base_prefix)

The standard library is the collection of modules included with Python. sys is one of those modules. sys.version contains interpreter version information; split() separates its whitespace-delimited parts and [0] selects the first, the version number. sys.executable identifies the running interpreter. sys.prefix identifies its environment prefix, while sys.base_prefix identifies the base installation. The != comparison asks whether the two prefixes differ.

All platforms:

PowerShell

uv run --no-project --python .venv check_environment.py

Read the five output lines in order. The first must be 3.14.9. The executable path should identify .venv/Scripts/python.exe on Windows or .venv/bin/python on macOS/Linux, with your machine’s path separators. The next line identifies .venv; the following line identifies the base Python installation. The final line must be True. Paths differ between computers, so compare their roles rather than copying a sample absolute path.

A False final line means the interpreter reports that it is outside a virtual environment. Check the exact executable used by the command, not just the prompt’s appearance. A different version means the environment was created with another base interpreter. Preserve the source files and create a new environment using the verified 3.14.9 installation.

Keep the package tool attached to the interpreter

uv has a pip-compatible interface for inspecting and managing packages. It does not invoke a separately installed pip program. Inspect this environment without installing anything:

All platforms:

PowerShell

uv pip list --python .venv

In this freshly created environment, the command succeeds with no package rows; output may be empty. Python’s standard-library modules are not third-party package rows. uv venv does not install pip by default, and uv pip does not need it in the environment. A missing pip module is therefore not an error to repair here. The --python .venv option identifies exactly which environment to inspect. Do not add packages for this exercise.

A virtual environment isolates package availability by default; it is not a security boundary against programs you run. It also depends on its base Python and contains machine-specific paths. Keep your source files as the durable work; recreate an environment on another machine rather than copying its directory. Chapter 8 will develop dependency records and reproducible project setup.

Official references: https://docs.astral.sh/uv/pip/environments/ and https://docs.python.org/3.14/library/sys.html. Once the selected Python is installed, these local, dependency-free runs and package inspections need no download. Chapter 8 will introduce uv project metadata, dependencies, and locking; we do not run uv init or create a lockfile here.

Flip to check your answerFold answer back

Answer. No. These checks establish which interpreter and package environment you are using. Application behaviour needs its own examples and tests. The files here still operate only on fictional in-memory values.

Bring the language pieces together

Save event_card.py using the complete class definition from “Classes and reading errors”. For convenience, its exact content is repeated here; keep it beside event_text.py, not inside .venv:

Python

class EventCard:
    def __init__(self, title):
        self.title = title

    def label(self):
        return "Event: " + self.title

Create readiness.py with this complete content:

Python

from event_card import EventCard
from event_text import event_label


def count_published(events):
    count = 0
    for event in events:
        if event["is_published"]:
            count = count + 1
    return count


events = [
    {"title": "Python Evening", "is_published": True},
    {"title": "Testing Clinic", "is_published": False},
]
assert count_published(events) == 1
assert count_published([]) == 0
assert event_label("Testing Clinic", False) == "Private draft"
assert event_label("Python Evening", True) == "Python Evening"
card = EventCard("Python Evening")
assert card.label() == "Event: Python Evening"
print("Readiness checks passed")

count starts at zero for each call. Each matching event adds one; the return is outside the loop, so all items are considered before the count is returned. An empty list skips the body and returns zero. The imports reuse the label function and the class, while card is one instance of that class.

assert evaluates a condition and raises AssertionError if it is false in these normal runs. The checks cover a mixed list, an empty list, both label branches, and an instance method. Only after they pass does the final message print. These are small learning checks; do not use assertions for application authorization or input validation, because optimized Python execution can disable them. Run the commands as written, without an optimization option.

All platforms:

PowerShell

uv run --no-project --python .venv readiness.py

Expected output:

Output

Readiness checks passed

If you see AssertionError, identify the failed comparison and predict the actual value before editing. If an import fails, check that readiness.py, event_text.py, and event_card.py are saved together. Do not remove the failing assertion to obtain the success message. Keep a copy before changing a working example.

In practice: working on two Python projects

Situation. A developer maintains an older project while learning with a separate practice project.

Application. Give each project its own virtual environment and use uv to select the intended one. This separates their installed packages while keeping source files outside the environment.

Consideration. An environment is not a portable dependency record or a security boundary. Chapter 8 will develop dependency records and reproducible project setup.
