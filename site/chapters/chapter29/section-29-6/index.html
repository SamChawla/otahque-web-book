Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead: attempt them now, and return after Chapters 57 and 59. They are extension questions, not a gate to the next chapter.

L1 (Junior): What does a password reset prove, and why does its page look the same for every address?

What the interviewer is testing: Do you know what the email proves, and can you name account enumeration?

Flip to check your answerFold answer back

Perfect answer: A reset proves only that the person can read the account’s mailbox: the link reaches nobody else. So it is exactly as strong as the email account, which is why the link must work once and expire. The page must not say whether an address has an account, or anyone could learn who uses the site by trying addresses, which is called account enumeration. Otahque shows the same page for every address and sends an email only to a member’s address, and a test proves both.

Behind the scenes:

a reset for two addresses (summary)

member's address  -> 302 to done page; 1 email
unknown address   -> 302 to done page; 0 emails

Code proof: Step 5’s l1_reset.py:

Output

demo@example.org    302 /accounts/password/reset/done/ 1
nobody@example.org  302 /accounts/password/reset/done/ 0

Common mistakes:

  • Showing “no account with that address”, or a different page for it.
  • Sending a new password by email instead of a link.
  • Making the link work for days, or more than once.

Follow-up the interviewer might ask:

  • “How would you keep the answer time the same once real email is sent?”
  • “What should happen to the member’s other sessions after a reset?”

L2 (Mid-Level): Sai uses her reset link, then clicks it again. Predict what she sees.

What the interviewer is testing: Can you explain why a token stops working when nothing about it is stored?

Flip to check your answerFold answer back

Perfect answer: She sees “Bad Token: the password reset link was invalid, possibly because it has already been used”. The token is a time and a hash worked out, with the secret key, from her id, the time, her password hash, and her last sign-in. When she saves a new password, the hash changes, so checking the old token gives a different answer. Nothing was stored, so nothing needed deleting; and after an hour, the time inside the token fails it anyway.

Behind the scenes:

two clicks on one link (summary)

first click   -> redirect to .../set-password/
new password  -> saved; password hash changes
second click  -> token_fail: "Bad Token"

Code proof: the Mini-Challenge’s l2_link.py:

Folder structure

first click ends: 5-set-password
new password saved: /accounts/password/reset/key/done/
second click, token_fail: True
says "already been used": True

Common mistakes:

  • Storing tokens in a table and forgetting to delete them after use.
  • Believing a token is valid until its time runs out, however often it is used.
  • Leaving the token in the address of the page where the password is typed, where scripts and logs can see it.

Follow-up the interviewer might ask:

  • “Why does signing in also end an unused reset link?”
  • “What happens to every reset link if SECRET_KEY changes?”

L3 (Senior): A product manager asks for sign-in by magic link. Defend a code instead.

What the interviewer is testing: Can you compare two designs by what each proves and how each fails, and state a standard’s limit honestly?

Flip to check your answerFold answer back

Perfect answer: A link signs in whichever device opens it: the member asks on a laptop and opens the email on a phone, mail scanners open links to check them, and a forwarded email still works. A code is typed into the browser that asked, which remembers the request in its session, so the same code anywhere else is refused; Otahque’s lasts ten minutes and allows three tries. Neither is a second factor: NIST says email “SHALL NOT be used for out-of-band authentication”. But whoever reads the mailbox can already reset the password, so the code adds no new way in, and when two-factor sign-in is on, it is still asked for after the code.

Behind the scenes:

one code, two browsers (summary)

laptop asks for a code  -> code tied to its session
phone types the code    -> refused: no request there
laptop types the code   -> signed in

Code proof: Step 7’s l3_code.py:

Output

a link in the email: False
phone signed in: False
laptop signed in: True

Common mistakes:

  • Calling an emailed code a second factor.
  • A link or code that never expires, or allows unlimited guesses.
  • Telling an unknown address that it has no account, by email or on the page.

Follow-up the interviewer might ask:

  • “How would you rate-limit code requests for one address?”
  • “When would you turn code sign-in off for staff?”

L4 (Staff): A member says their authenticator code is always wrong. Diagnose it.

What the interviewer is testing: Can you reason from how TOTP works to the likely causes, and test a time-based rule without waiting?

Flip to check your answerFold answer back

Perfect answer: A TOTP code comes from the shared secret and the current 30-second step, so a code is wrong when the two sides disagree on either. The commonest cause is the phone’s clock: set by hand and off by more than 30 seconds, it shows the code for another step, and allauth accepts only the current one. The fix is to set the phone’s time automatically, not to widen the window for everyone; OWASP suggests recording one token’s drift instead. Next, a code typed twice within its 30 seconds is refused the second time on purpose. Last, a member who scanned an old QR code has an old secret: turning the app off and on again gives a new one, and the recovery codes cover the time in between.

Behind the scenes:

one secret, three clocks (summary)

phone in step with the server -> accepted
phone 40 seconds slow          -> a step behind: refused
phone 40 seconds fast          -> a step ahead: refused

Code proof: l4_totp.py, with the clock fixed by mock.patch:

l4_totp.py (practice file; delete it afterwards)

from unittest import mock

from allauth.mfa.totp.internal import auth

secret = auth.generate_totp_secret()
now = 1_800_000_000  # a fixed moment, in seconds


def code_at(moment):
    return auth.format_hotp_value(
        auth.hotp_value(secret, moment // 30))


with mock.patch('time.time', return_value=now):
    for label, moment in (('right now', now),
                          ('phone 40 s slow', now - 40),
                          ('phone 40 s fast', now + 40)):
        ok = auth.validate_totp_code(secret, code_at(moment))
        print(f'{label:16} accepted: {ok}')

Output

right now        accepted: True
phone 40 s slow  accepted: False
phone 40 s fast  accepted: False

Common mistakes:

  • Widening the accepted window for every member to hide one wrong clock.
  • Testing time-based rules with sleep() instead of a mocked clock.
  • Resetting a member’s two-factor sign-in on request without checking who is asking.

Follow-up the interviewer might ask:

  • “How would you prove the server’s own clock is right?”
  • “What should support check before removing a member’s authenticator?”

L5 (Lead): Where should Otahque require two-factor sign-in, and how should recovery work?

What the interviewer is testing: Can you weigh security against members’ effort, plan for lost devices, and name the risks that remain?

Flip to check your answerFold answer back

Perfect answer: Require it where a stolen account does the most harm: staff, who can change every event in the admin, from Chapter 59. Offer it to members, whose accounts reach only their own registrations, and make it easy: a QR code, re-authentication before the change, and ten single-use recovery codes. Every change to a factor sends a notice. Support must check who is asking before removing anyone’s authenticator, or recovery becomes the easiest attack. And the remaining risks are named with dates: the secrets are plain text until Chapter 59 encrypts them, used codes live in one process’s cache until Chapter 57, and passkeys, the strongest factor, follow HTTPS in Chapter 63.

Behind the scenes:

recovery codes for one member (summary)

turned on   -> 10 codes of 8 digits
one used    -> accepted once, then refused
stored      -> a seed, as plain text until Chapter 59

Code proof: l5_recovery.py makes a member’s recovery codes in a transaction it rolls back:

l5_recovery.py (practice file; delete it afterwards)

from allauth.mfa.models import Authenticator
from allauth.mfa.recovery_codes.internal.auth import (
    RecoveryCodes,
)
from django.db import transaction

from accounts.models import User

with transaction.atomic():
    demo = User.objects.create_user('demo@example.org',
                                    'a-long-safe-pass-123',
                                    display_name='Demo')
    codes = RecoveryCodes.activate(demo)
    unused = codes.get_unused_codes()
    print('codes:', len(unused), 'of', len(unused[0]),
          'digits')
    print('first use:', codes.validate_code(unused[0]))
    print('second use:', codes.validate_code(unused[0]))
    print('left:', len(codes.get_unused_codes()))
    row = Authenticator.objects.get(user=demo)
    print('stored:', sorted(row.data), '(no codes)')
    transaction.set_rollback(True)

Output

codes: 10 of 8 digits
first use: True
second use: False
left: 9
stored: ['seed', 'used_mask'] (no codes)

Common mistakes:

  • Requiring two factors for everyone at once, so that members are locked out of their own registrations.
  • No recovery path except support, with no check of who is asking.
  • Treating “two-factor is on” as finished while the secrets sit in plain text.

Follow-up the interviewer might ask:

  • “How would you move every existing staff member to two-factor sign-in without locking anyone out?”
  • “Would you allow ’trust this browser for 30 days’? What would it cost?”
