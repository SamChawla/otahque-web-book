How We Build It

Start from Chapter 28, in the folder containing manage.py, with your own .env, the locked environment, 224 passing tests, every migration applied, and Sam’s superuser password from Chapter 18. One package extra is added, in Step 8, with its migrations. The new files are four email templates in templates/account/email/, templates/allauth/elements/field.html, and docs/design/passwords-and-two-factor.md. The commands are written the same for Windows PowerShell, Git Bash, macOS, Linux, and WSL; the chapter’s checks ran in the first two. Each step with new behaviour writes its tests first and runs them to see them fail. Steps 2 and 10 hold behaviour allauth and Django already have, so their checks pass at once.

The tests use helpers that each later step shares: member() makes a member with Chapter 27’s test password, sign_in() signs a test browser in through allauth’s page, and subjects() lists the subjects of the emails sent. Every test class that signs in or asks for codes calls cache.clear() in setUp(), for a reason Step 4 explains.

The Custom Way

Django has its own password views, and many tutorials build the reset with them. This illustration is not part of the project:

illustration_only/urls.py (not part of the project)

from django.contrib.auth import views as auth_views
from django.urls import path

urlpatterns = [
    path('password/reset/',
         auth_views.PasswordResetView.as_view()),
    path('password/reset/done/',
         auth_views.PasswordResetDoneView.as_view()),
    path('reset/<uidb64>/<token>/',
         auth_views.PasswordResetConfirmView.as_view()),
    path('reset/done/',
         auth_views.PasswordResetCompleteView.as_view()),
]

Each view needs a template, the reset email needs two more, and the change pages need their own pair. Django’s views do the hard part well: the same page for every address, a token that stores nothing, and the token moved out of the address bar before the page is shown. But in Otahque they would be a second set of account pages beside allauth’s, with their own templates, emails, and rate limits, and they skip members with no usable password, so Raj could never reset. A hand-made magic link would need even more: a signed, expiring token from Chapter 28, a table to make it single-use, and a way to tie it to the browser that asked. The Django Way here is to use the pages allauth already serves, decide their settings, write their words, and prove each rule with a test.

Step 2: How a reset token works

Before using allauth’s reset, watch the token idea in Django’s own generator. Save this practice file as s2_token.py beside manage.py, run it with uv run python manage.py shell -c "exec(open('s2_token.py').read())", and delete it. It makes two demo members inside a transaction it rolls back, so your rows are unchanged:

s2_token.py (practice file; delete it afterwards)

from django.contrib.auth.tokens import (
    default_token_generator,
)
from django.db import transaction

from accounts.models import User

PASSWORD = 'a-long-safe-pass-123'
tokens = default_token_generator
with transaction.atomic():
    demo = User.objects.create_user(
        'demo@example.org', PASSWORD, display_name='Demo')
    other = User.objects.create_user(
        'other@example.org', PASSWORD, display_name='Other')
    token = tokens.make_token(demo)
    when, check = token.split('-')
    print('the token:', len(when), 'characters of time,',
          len(check), 'of hash')
    print('stored anywhere: no; it is worked out again')
    print('valid for demo:', tokens.check_token(demo, token))
    print('valid for other:',
          tokens.check_token(other, token))
    demo.set_password('violet kettle harbour')
    demo.save()
    print('after a new password:',
          tokens.check_token(demo, token))
    transaction.set_rollback(True)

Output

the token: 6 characters of time, 32 of hash
stored anywhere: no; it is worked out again
valid for demo: True
valid for other: False
after a new password: False

The token is a time and a hash, and nothing is saved anywhere. It is valid for the member it was made for, not for another, and a new password makes it fail, because the hash covers the password.

LINK = re.compile(
    r'http://testserver(/accounts/password/reset/key/\S+/)')


class ResetCase(TestCase):
    """A member, Sai, and helpers for password resets."""

    def setUp(self):
        cache.clear()
        self.sai = member()
        member('old@example.org', is_active=False)

    def ask(self, email='sai@example.org'):
        """Ask for a reset email for email."""
        mail.outbox.clear()
        return self.client.post(
            reverse('account_reset_password'),
            {'email': email})

    def link(self):
        """Return the reset link in the first email."""
        return LINK.search(mail.outbox[0].body).group(1)

    def set_new_password(self, client, link):
        """Follow link and set the new password."""
        # The key moves from the address into the session.
        page = client.get(link)
        return client.post(page.url, {
            'password1': NEW_PASSWORD,
            'password2': NEW_PASSWORD})


class ResetTests(ResetCase):
    """Resets: the same page for all, one-hour links."""

    def test_every_address_gets_the_same_page(self):
        done = reverse('account_reset_password_done')
        for email in ('sai@example.org',
                      'nobody@example.org',
                      'old@example.org'):
            self.assertRedirects(self.ask(email), done)

    def test_only_a_member_gets_an_email(self):
        self.ask()
        self.assertEqual(len(mail.outbox), 1)
        for email in ('nobody@example.org',
                      'old@example.org'):
            self.ask(email)
            self.assertEqual(mail.outbox, [])

    def test_the_link_works_once(self):
        self.ask()
        link = self.link()
        self.assertRedirects(
            self.set_new_password(self.client, link),
            reverse('account_reset_password_from_key_done'))
        response = Client().get(link, follow=True)
        self.assertTrue(response.context['token_fail'])

    def test_the_link_lasts_one_hour(self):
        self.ask()
        link = self.link()
        for minutes, fails in ((59, False), (61, True)):
            later = (datetime.now()
                     + timedelta(minutes=minutes))
            with mock.patch.object(
                    PasswordResetTokenGenerator, '_now',
                    return_value=later):
                response = Client().get(link, follow=True)
            failed = response.context.get('token_fail')
            self.assertEqual(bool(failed), fails)

    def test_a_reset_does_not_sign_in(self):
        self.ask()
        self.set_new_password(self.client, self.link())
        self.assertNotIn(
            '_auth_user_id', self.client.session)
        self.sai.refresh_from_db()
        self.assertFalse(self.sai.check_password(PASSWORD))
        sign_in(self.client, password=NEW_PASSWORD)
        self.assertIn('_auth_user_id', self.client.session)

Common Error: rate limits that leak between tests

allauth limits reset requests to five a minute for each address, and keeps the count in Django’s cache. The local cache lives in memory for the whole test run, and Django does not empty it between tests. A test class without cache.clear() in setUp() passes when run alone, then fails in the full run with “429 != 302”, because earlier tests already used the address’s five requests. Clear the cache in setUp() of every test class that signs in, resets, or asks for codes.

    def test_a_recovery_code_works_once(self):
        sai, secret = self.two_factor_on()
        codes = Authenticator.objects.get(
            user=sai, type=Authenticator.Type.RECOVERY_CODES,
        ).wrap().get_unused_codes()

    def test_a_used_code_waits_in_the_cache(self):
        sai, secret = self.two_factor_on()

Under the Hood: what the database holds

Each member’s authenticators are rows of allauth’s mfa_authenticator table. The totp row’s data holds the secret your phone was given, written out, and the recovery_codes row holds the seed the ten codes are made from; the interview’s L5 prints such a row. allauth’s adapter has two methods, encrypt() and decrypt(), that a project can replace; by default they change nothing. test_the_secret_is_stored_as_text in Step 9 records this, and Chapter 59 encrypts both with a key kept in .env, before Otahque is put online in Chapter 63. Until then, treat a copy of the database, or of a backup, as holding every member’s second factor.

# Passwords, sign-in codes, and two factors: design

Status: Drafted in Chapter 29, for review. Not approved.

## Passwords

- At least 15 characters (NIST SP 800-63B-4, 3.1.1.2,
  for a password used alone), not like the email or
  name, not a common password, not all digits. No
  other composition rules; no forced periodic change.
- Existing shorter passwords keep working; the rule
  applies whenever a password is chosen, changed,
  reset, or set.
- Change: the browser that changes it stays signed in;
  every other browser is signed out.
- A member with no password (a GitHub sign-up) may set
  one from the profile, or through a reset.

## Reset

- Every address gets the same page. Only a member's
  address gets an email (ACCOUNT_EMAIL_UNKNOWN_ACCOUNTS
  is False); inactive accounts get none.
- The link works once and for one hour
  (PASSWORD_RESET_TIMEOUT). A new password, a new
  address, or a sign-in ends it.
- A reset does not sign the member in (OWASP Forgot
  Password Cheat Sheet); the new password does.

## Notices

- Password changed, set, or reset; email changed;
  two-factor turned on or off: one email each, with
  the IP address, browser, and time.

## Sign-in by code

- An emailed code, eight characters, for ten minutes,
  three tries, only in the browser that asked.
- It proves control of the mailbox, as a reset email
  does: a convenience, not a second factor (NIST
  SP 800-63B-4, 3.1.3.1). Two-factor still applies
  after it.

## Two-factor sign-in

- Optional for members; required for staff from
  Chapter 59. An authenticator app (TOTP, 30-second
  codes) and ten single-use recovery codes. Passkeys
  later, after HTTPS (Chapter 63), as an optional
  extra.
- Turning it on asks for the password again and needs
  a confirmed email address.
- A code is accepted once. allauth remembers used
  codes in the cache; OneUseActivateTOTPForm also
  marks the activation code. It calls the private
  TOTP._mark_code_used(): a test fails if an upgrade
  changes it.

## Known risks

- The authenticator secret, and the seed the
  recovery codes are made from, are stored as plain
  text in mfa_authenticator. A copy of the database,
  a backup, or an export gives every member's codes.
  Exports leave the table out (Chapter 41); Chapter
  59 encrypts it before any deployment (Chapter 63).
- Used codes and rate limits live in the local-memory
  cache, one per process. Before more than one
  process, a shared cache (Chapter 57, Redis in 62).
- Until Chapter 43, a known address may answer more
  slowly than an unknown one, because only it sends
  an email.

## Admin

- The admin's sign-in page sends staff to allauth's,
  so limits and two-factor apply. Staff without
  two-factor still enter until Chapter 59.
