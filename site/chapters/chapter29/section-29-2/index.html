What You Need to Know

What a password proves, and the rules for one

A password proves that the person typing it knows a secret that only the member should know. Django never stores the password itself: Chapter 17 showed that it stores a hash, a value worked out from the password that cannot be turned back into it. At sign-in, Django hashes what was typed and compares.

Which passwords to accept is set by AUTH_PASSWORD_VALIDATORS, the list Django’s project template put in settings.py and Chapter 17 promised to review here. Its four checks refuse a password too like the member’s name or email, one shorter than eight characters, one in a list of 20,000 common passwords, and one made only of digits.

The rules in this chapter come from NIST SP 800-63B-4, the United States National Institute of Standards and Technology’s guidance on signing in, finalized in 2025. Otahque is not a government system, but the guidance is public, tested, and widely followed. Table 29.1 compares it with Django’s defaults.

Length wins because each extra character multiplies the guesses an attacker needs. “violet kettle harbour” is 21 characters, easy to remember, and far harder to guess than “P@ssw0rd!”, which follows the old symbol rules and appears in every attacker’s list. Fifteen characters applies to a password used alone; NIST allows eight when a second factor is always required. Two-factor sign-in is optional for Otahque’s members, so for most of them the password is the only factor, and 15 is the rule.

A new rule applies only when a password is chosen, changed, reset, or set. Existing passwords keep working: NIST says not to force a change without a reason to believe the password was stolen.

Changing, resetting, and setting a password

Three pages handle passwords, and allauth already provides all three at addresses Chapter 27 installed:

  • Change (/accounts/password/change/): a signed-in member types the current password and a new one.
  • Reset (/accounts/password/reset/): a member who forgot it receives an email with a link, and chooses a new one.
  • Set (/accounts/password/set/): a member with no password, such as Raj, chooses a first one.

Changing a password signs out every other browser where the member was signed in, and keeps the browser that made the change. Django does this by storing a value worked out from the password hash in each session; when the hash changes, every other session no longer matches, and Django treats it as signed out. If a thief had Sai’s password and was signed in on another computer, her change throws the thief out.

A reset that reveals nothing

Account enumeration means learning which addresses have accounts by watching how a site answers. A reset page that says “no account with that address” tells the stranger exactly that. So Otahque’s reset page shows the same “check your email” page for every address: a member’s, an unknown one, and that of an account an administrator has made inactive. Only a member’s address gets an email. Figure 29.1 follows Sai’s reset.

allauth can also email an unknown address to say “someone tried to use this address here; you have no account”. The decision for Otahque is that someone who never signed up should not receive Otahque’s emails, so that email is turned off. The OWASP Forgot Password Cheat Sheet, the Open Worldwide Application Security Project’s guidance, also asks for the same answer in the same time for every address. Locally, sending an email to the console takes no measurable time; Chapter 43 measures the difference once real email is sent.

Two more rules follow from the same guidance. A reset does not sign the member in: after choosing a new password, Sai signs in with it, the ordinary way. And every change to a password, by change, reset, or set, sends the member a notice, an email that says what changed, from which address and browser, and when. A notice is how Sai would learn of a change she did not make.

Tokens that end

The link in a reset email ends with a token, a value that proves the email was sent by Otahque for this member. Chapter 28 showed signed values, which work until they expire however many times they are used. A reset token must work once. Django’s token generator achieves that without storing anything: the token is worked out from the member’s id, a time, the current password hash, and the time of the last sign-in. Change the password, or sign in, and the same calculation gives a different answer, so the old token no longer matches. allauth’s generator adds the member’s email addresses, so changing an address ends the link too.

New Concept: a token that stores nothing

What problem exists? A reset link must work once, expire, and be impossible to make up. Saving each token in a table works, but then the table must be cleaned, and a copy of it would let anyone reset any password.

What did people do before? Early sites emailed a new password in plain text, or stored a random token that never expired.

What is it? A token worked out from data that changes when it is used: the password hash and the last sign-in, signed with SECRET_KEY through an HMAC, the same kind of keyed hash as Chapter 28’s signatures. Using the link changes the password, and the token stops matching.

Why use it? There is nothing to store, clean, or leak, and nobody without SECRET_KEY can make a valid one. Expiry comes from the time inside it, checked against PASSWORD_RESET_TIMEOUT.

Now let’s use it. Step 2 makes a token in the shell and watches it stop working.

PASSWORD_RESET_TIMEOUT is three days in Django. Otahque sets one hour: a link sitting in a mailbox is a key to the account, and an hour is long enough for slow mail. NIST allows emailed recovery codes for at most 24 hours; OWASP asks only for “an appropriate period”.

A code instead of a link

A magic link signs a person in from an email, with no password. allauth’s version sends a code instead: eight letters and digits such as DPFW-HDVB, typed into the browser window that asked for it. Figure 29.2 shows why a code is the safer form.

A link signs in whichever device opens it. Sai asks on her laptop, opens the email on her phone, and her phone is signed in, not her laptop. Some email services open links themselves to check them for danger. And anyone she forwards the email to can use it. The code is tied to the browser that asked for it: allauth remembers the request in that browser’s session, so the same code typed anywhere else is refused. Otahque’s code works for ten minutes, and three wrong tries throw it away.

Under the Hood: what an emailed code proves

NIST SP 800-63B-4 says that “email SHALL NOT be used for out-of-band authentication”: an emailed code is not a second factor, because anyone who can read the mailbox can read the code. That is true, and it is also true of the reset email. Whoever controls Sai’s mailbox can already reset her password, so a sign-in code opens no new way in; it only saves the step of choosing a new password. Otahque treats it as a convenience at the level of a reset. When two-factor sign-in is on, the second factor is still asked for after the code.

Something you know, something you have

Two-factor sign-in asks for two different kinds of proof. The password is something you know. The second is something you have: a phone with an authenticator app, such as Google Authenticator, Microsoft Authenticator, or any app that supports TOTP. Figure 29.3 shows a sign-in with both.

TOTP, a time-based one-time password, works like this. When Sam turns it on, Otahque makes a random secret and shows it as a QR code. His app reads it, and from then on, both the app and Otahque work out a six-digit code from the secret and the current time, cut into 30-second steps. The codes match only if both have the same secret and the same time. Nothing travels between the phone and Otahque, so the phone needs no network.

A phone can be lost. Recovery codes are ten single-use codes of eight digits, shown once two-factor sign-in is on. Sam prints them or keeps them in his password manager, and each one works once in place of the app’s code.

New Tool: allauth’s two-factor module

What problem exists? Two-factor sign-in needs secrets, QR codes, codes checked against time, recovery codes, pages to turn it on and off, and a second step in every sign-in path: password, code, provider, and the admin.

What did people do before? Separate packages bolted a second step onto Django’s sign-in, and every new sign-in path needed it added again.

What is it? allauth.mfa, the multi-factor part of the allauth package Otahque already uses, added with its mfa extra. It provides TOTP, recovery codes, and passkeys, and puts the second step after every way of signing in.

Why use it? One package for every sign-in path, kept up to date by the same maintainers, and decided for Otahque on 13 November 2026.

Now let’s use it. Step 8 adds it, Step 9 turns it on for a member, and Step 10 signs in with it.

Two rules protect the second factor. Turning it on asks for the password again, so that a browser left signed in cannot add an attacker’s phone. And a code is accepted only once, even inside its 30 seconds: someone who sees Sam type it cannot use it after him. allauth remembers each used code in Django’s cache, a fast store kept in the server’s memory. Otahque’s cache, like Django’s default, lives inside one server process; Chapter 57 lists every kind of cache Django offers and moves Otahque to one shared between processes.

Two-factor sign-in is optional for members and will be required for staff from Chapter 59. A passkey, which signs in with the phone’s fingerprint or face, is the strongest second factor, but browsers allow it only on HTTPS sites, so Otahque adds it, as an optional extra, after Chapter 63.

Where each check lives

Most of this chapter’s behaviour is allauth’s and Django’s; Otahque decides settings, words, and one form, and proves each rule with a test. Figure 29.4 shows the four places.

The database box names a risk. allauth stores the authenticator secret, and the seed from which the recovery codes are made, as plain text. Anyone with a copy of the database can work out every member’s codes. Locally the members are fictional and no site is public, and Chapter 59 encrypts these values before Chapter 63 puts Otahque online. This chapter shows the risk with a test rather than hiding it.
