How We Build It

Start from Chapter 18, in the folder containing manage.py, with your own .env, the locked environment, 29 passing tests, every migration applied, and a local superuser. The events_event table is empty. Steps 1 to 4 work in the Django shell and change only rows in db.sqlite3: you save three events and leave two of them published and one a draft. Steps 5 and 6 change files: the event tests, the views, and the two event templates in the events app, and the stylesheet source in static/otahque. They also delete the app’s templatetags folder and rebuild the stylesheet. At the end of Step 7, 30 tests pass, /events/ lists the two published events soonest first, the workshop’s page shows its start time in India, the draft’s address returns 404, and the work is committed.

The Custom Way

This illustration asks SQLite for published events by building the SQL out of a string, as hand-written database code often did; do not add it to the project. It uses a small table in memory, so it runs anywhere:

illustration_only/string_sql.py (not part of the project)

import sqlite3

db = sqlite3.connect(':memory:')
db.execute('CREATE TABLE event (title TEXT, status TEXT)')
db.executemany('INSERT INTO event VALUES (?, ?)', [
    ('Python meetup', 'published'),
    ('Spring planning', 'draft'),
])


def titles(sql, params=()):
    return [t for (t,) in db.execute(sql, params)]


status = "published' OR '1'='1"
built = f"SELECT title FROM event WHERE status = '{status}'"
print('built:', titles(built))
safe = 'SELECT title FROM event WHERE status = ?'
print('placeholder:', titles(safe, (status,)))
print('normal:', titles(safe, ('published',)))

Output

built: ['Python meetup', 'Spring planning']
placeholder: []
normal: ['Python meetup']

The status value stands for text that came from outside the program, such as part of a web address. Built into the SQL with an f-string, its quote mark ends the string early, and OR '1'='1' becomes part of the condition, which is true for every row: the draft leaks. This is SQL injection. The second query uses a ? placeholder and passes the value separately, so SQLite compares the status with the whole text, quote marks and all, and finds nothing; with a real status it works normally. Now list what the hand-written version still lacks even when it uses placeholders: each query names its columns by hand, each row comes back as a tuple to unpack by position, nothing checks that status is a real column, and the SQL would need rewriting for another database.

Under the Hood: how the ORM sends values

When the ORM turns filter(status=...) into SQL, the SQL holds a placeholder, and the value travels beside it as a parameter, exactly like the illustration’s ?. The database never reads the value as SQL. This is why ORM queries are protected from SQL injection by default. The protection ends where you build SQL text yourself: an f-string passed to a cursor, raw() with values joined into its text, or the old extra() method. Injection is category A05 in the OWASP Top 10 2025, a widely used list of the most serious web application risks, and SQL injection is one of its main forms. Chapter 55 uses raw() safely, with parameters, and Chapter 59 reviews injection across the whole application.

Step 2: Create events and fetch them

Start the shell again with uv run python manage.py shell, and import Python’s datetime and UTC, which the shell does not import for you. Then build Sam’s meetup as an object and look at it before saving:

Django shell

>>> from datetime import UTC, datetime
>>> meetup = Event(
...     title='Python meetup',
...     starts_at=datetime(2026, 11, 19, 18, 30, tzinfo=UTC),
...     ends_at=datetime(2026, 11, 19, 20, 30, tzinfo=UTC),
...     timezone='Europe/London',
...     location='Leeds Central Library',
...     capacity=40,
... )
>>> print(meetup.pk, meetup.status)
None draft
>>> meetup.save()
>>> print(meetup.pk, meetup.status)
1 draft

Calling the class, Event(...), creates an object in Python only. Its primary key, pk, the id column, is None, because the database has not seen it, and its status is the model’s default, draft. save() sends an INSERT, and the database chooses the id. starts_at is an aware datetime: tzinfo=UTC says which zone the 18:30 belongs to, and so is ends_at. Otahque stores every start and end time in UTC and the event’s own zone, here Europe/London, beside it.

Common Error: a naive datetime

Leave out tzinfo=UTC, and save() still works but prints RuntimeWarning: DateTimeField Event.starts_at received a naive datetime (2026-11-19 18:30:00) while time zone support is active. A naive datetime has no zone, so Django guesses that it means the default zone in settings.py, UTC. The guess happens to be right here and would be wrong for an event entered in Kolkata time. Delete the row with delete(), shown in Step 4, and create it again with tzinfo=UTC.

create() does both steps at once: it builds the object, saves it, and returns it. Create the online workshop, which Soni wants to attend, already published, and the spring plan as a draft:

Django shell

>>> workshop = Event.objects.create(
...     title='Django workshop',
...     starts_at=datetime(2026, 12, 3, 9, 0, tzinfo=UTC),
...     ends_at=datetime(2026, 12, 3, 12, 0, tzinfo=UTC),
...     timezone='Asia/Kolkata',
...     location='Virtual',
...     capacity=60,
...     status=Event.Status.PUBLISHED,
... )
>>> planning = Event.objects.create(
...     title='Spring planning',
...     starts_at=datetime(2027, 3, 10, 18, 0, tzinfo=UTC),
...     ends_at=datetime(2027, 3, 10, 20, 0, tzinfo=UTC),
...     timezone='Europe/London',
...     location='Leeds Central Library',
...     capacity=12,
... )

Event.Status.PUBLISHED is Chapter 16’s choice, which stores 'published'. The workshop runs from 09:00 to 12:00 UTC, which is 14:30 to 17:30 in India. Loop over every event to see what the table holds. Type the for line, then the indented print line, then press Enter on the empty ... line:

Django shell

>>> for event in Event.objects.all():
...     print(event.pk, event.title, event.status)
...
1 Python meetup draft
2 Django workshop published
3 Spring planning draft

The events come back soonest first without asking, because Chapter 16’s model sets ordering = ['starts_at']. Your ids should match these. If you created and deleted events along the way, yours are higher: SQLite does not reuse an id once it has been used. That is why the steps below refer to meetup.pk, never to a number you type.

Common Error: a misspelled field name

Event(titel='Python meetup') fails at once with TypeError: Event() got unexpected keyword arguments: 'titel', and nothing is saved. Check the spelling against events/models.py.

Now fetch one event with get(), then ask for one that does not exist, then for one that is not unique:

Django shell

>>> Event.objects.get(pk=meetup.pk)
<Event: Python meetup>
>>> Event.objects.get(title='Python Meetup')
Traceback (most recent call last):
...
events.models.Event.DoesNotExist: Event matching query ...
>>> Event.objects.get(status=Event.Status.DRAFT)
Traceback (most recent call last):
...
events.models.Event.MultipleObjectsReturned: get() ...

The shell prints an event using Chapter 16’s __str__(), its title. The second call asks for Python Meetup with a capital M; an equals condition compares letter case too, so no row matches, and the message ends does not exist. The third matches the two drafts, and the full message is get() returned more than one Event -- it returned 2!. Both errors stop the line, not the shell, which waits at the next >>>. Their full tracebacks name files inside Django; read the last line first. Leave the shell with exit().

Step 3: Ask questions with QuerySets

Start the shell again and import datetime and UTC. Build a QuerySet of the published events, print it, and then exclude the online events:

Django shell

>>> from datetime import UTC, datetime
>>> published = Event.objects.filter(
...     status=Event.Status.PUBLISHED
... )
>>> published
<QuerySet [<Event: Django workshop>]>
>>> Event.objects.exclude(location='Virtual')
<QuerySet [<Event: Python meetup>, <Event: Spring planning>]>
>>> Event.objects.filter(status="published' OR '1'='1")
<QuerySet []>

Only the workshop is published so far; the meetup is still a draft until Step 4. exclude() is the opposite of filter(): every row that does not match. The third line is the Custom Way’s attack, given to the ORM. No event has that text as its status, so nothing matches, and the draft stays hidden: the value was sent as a parameter, never as SQL.

Now try the lookups from Table 19.1:

Django shell

>>> Event.objects.filter(title__iexact='python MEETUP')
<QuerySet [<Event: Python meetup>]>
>>> Event.objects.filter(title__icontains='plan').count()
1
>>> december = datetime(2026, 12, 1, tzinfo=UTC)
>>> Event.objects.filter(starts_at__lt=december)
<QuerySet [<Event: Python meetup>]>
>>> Event.objects.filter(starts_at__gte=december).count()
2
>>> Event.objects.filter(starts_at__year=2027)
<QuerySet [<Event: Spring planning>]>
>>> hidden = [Event.Status.DRAFT, Event.Status.CANCELLED]
>>> Event.objects.filter(status__in=hidden).count()
2

iexact finds the meetup that Step 2’s exact get() missed. count() on a QuerySet that has not run asks the database for a number, not for rows, so it is the cheap way to ask “how many”. A datetime you compare with must be aware too, so december has tzinfo=UTC.

Order, slice, and pick one:

Django shell

>>> latest = Event.objects.order_by('-starts_at')
>>> [event.title for event in latest[:2]]
['Spring planning', 'Django workshop']
>>> latest.first()
<Event: Spring planning>
>>> Event.objects.filter(location='Leeds').exists()
False
>>> Event.objects.filter(location='Leeds').first()
>>> Event.objects.filter(location='Leeds')[0]
Traceback (most recent call last):
...
IndexError: list index out of range

order_by('-starts_at') replaces the model’s order; the minus sign means latest first. [:2] becomes SQL’s LIMIT 2, and the list comprehension prints just the titles, which keeps the output short. first() returns the first object, or None when there is none, which is why the shell prints nothing for the empty Leeds search: no location equals Leeds exactly, because the library’s location is Leeds Central Library. exists() answers “is there at least one?” without loading rows. Indexing an empty QuerySet with [0] raises IndexError; use first() when nothing may match.

Two mistakes come up often. Try them both:

Django shell

>>> Event.objects.filter(name='Python meetup')
Traceback (most recent call last):
...
django.core.exceptions.FieldError: Cannot resolve ...
>>> published.title
Traceback (most recent call last):
  File "<console>", line 1, in <module>
AttributeError: 'QuerySet' object has no attribute 'title'

The full first message goes on to list every valid field name after Choices are:. There is no name field; the event’s field is title. The second treats a QuerySet as one event. A QuerySet holds events but has no title of its own; loop over it, or use get() or first() to get one object.

To see roughly what SQL a QuerySet will run, print its query attribute:

Django shell

>>> print(published.query)
SELECT ... WHERE "events_event"."status" = published ...

The full line lists every column in the SELECT, then the WHERE condition, then ORDER BY the start time, from the model’s ordering. Read it as an approximation for people, not as the SQL that runs: published appears without quote marks because the real query sends it separately as a parameter. Django’s documentation does not treat query as part of its public interface, so use it for looking only.

Finally, count queries. CaptureQueriesContext, from Django’s test utilities, records every query run inside a with block; connection is one of the shell’s automatic imports. Type each block, then press Enter on the empty ... line:

Django shell

>>> from django.test.utils import CaptureQueriesContext
>>> with CaptureQueriesContext(connection) as queries:
...     in_person = Event.objects.exclude(location='Virtual')
...     print('built:', len(queries))
...     titles = [event.title for event in in_person]
...     print('listed:', len(queries))
...     print(in_person.count(), in_person.exists())
...     print('reused:', len(queries))
...
built: 0
listed: 1
2 True
reused: 1
>>> with CaptureQueriesContext(connection) as queries:
...     print(Event.objects.count(), Event.objects.count())
...     print('queries:', len(queries))
...
3 3
queries: 2

These are Figure 19.1’s numbers. Building in_person ran nothing. The list comprehension evaluated it: one query. After that, count() and exists() used its cache: still one. In the second block, Event.objects.count() builds a new QuerySet each time it is written, so writing it twice runs two queries. Leave the shell with exit().

Step 4: Change and remove rows

Sam has two changes. The meetup has moved to Room 2 of the library, and it is ready to publish. Start the shell again and import datetime and UTC. Fetch the meetup by its title, which is unique among your events, change one field, and save only that field:

Django shell

>>> from datetime import UTC, datetime
>>> meetup = Event.objects.get(title='Python meetup')
>>> meetup.location = 'Leeds Central Library, Room 2'
>>> meetup.save(update_fields=['location'])
>>> Event.objects.get(pk=meetup.pk).location
'Leeds Central Library, Room 2'

Changing the attribute changes the object in Python only; save() writes it. With update_fields, the UPDATE sets that one column, so it cannot overwrite a change someone else made to another column in the meantime. Fetching the row again shows what the database holds.

Publish it with update(). Before any update() or delete(), count what the QuerySet matches, so that you know how many rows will change:

Django shell

>>> to_publish = Event.objects.filter(pk=meetup.pk)
>>> to_publish.count()
1
>>> to_publish.update(status=Event.Status.PUBLISHED)
1
>>> meetup.status
'draft'
>>> meetup.refresh_from_db()
>>> meetup.status
'published'

update() returned 1, the number of rows it matched. The meetup object still said draft, because update() changed the database, not objects already in Python. refresh_from_db() reloads an object’s fields from its row.

Common Error: update() or delete() on every row

Calling update() on Event.objects itself, or delete() on Event.objects.all(), changes or deletes every event, and the shell has no undo. Build the QuerySet first, check its count(), then call update() or delete() on it, as in this step. If it happens to your practice rows, recreate them with Step 2’s create() calls; never delete db.sqlite3 or a migration to recover.

Now see that save() checks nothing. Save an event that breaks every rule the model describes, then find and delete it:

Django shell

>>> broken = Event(
...     title='',
...     starts_at=datetime(2026, 1, 1, tzinfo=UTC),
...     ends_at=datetime(2025, 12, 31, tzinfo=UTC),
...     timezone='Nowhere/Special',
...     location='',
...     capacity=0,
...     status='archived',
... )
>>> broken.save()
>>> print(broken.pk, repr(broken.title), broken.status)
4 '' archived
>>> invalid = Event.objects.filter(status='archived')
>>> invalid.count()
1
>>> invalid.delete()
(1, {'events.Event': 1})

An empty title, an unknown time zone, no places, and a status that is not one of the three choices: the database stored all of it, because the table’s only rule about these columns is that capacity is not negative. Chapter 16’s full_clean() would have refused the title, the location, and the status, but nothing called it. delete() returned the total number of rows deleted and the count for each model: here one Event. Its id, 4, will not be used again. Check what the table holds now:

Django shell

>>> for event in Event.objects.all():
...     print(event.pk, event.title, event.status)
...
1 Python meetup published
2 Django workshop published

Two published events and one draft: the data the pages will show. Leave the shell with exit(). These rows live in db.sqlite3, which Git ignores, so they are yours alone; a teammate’s copy of Otahque has its own.

Step 5: Write the page tests first

The pages still read the dictionary. Before changing them, change the tests to describe the pages you want. Tests that use the database must be TestCase classes, from Chapter 18, and each class creates its events once in setUpTestData(), a class method that TestCase runs before the class’s tests. Each test then sees those rows, and any change a test makes is rolled back before the next one.

def save_event(**changes):
    """Save a published event; keywords replace defaults."""
    fields = {
        'title': 'Python meetup',
        'starts_at': datetime(2026, 11, 19, 18, 30,
                              tzinfo=UTC),
        'timezone': 'Europe/London',
        'location': 'Leeds Central Library',
        'capacity': 40,
        'status': Event.Status.PUBLISHED,
    }
    fields.update(changes)
    fields.setdefault(
        'ends_at', fields['starts_at'] + timedelta(hours=2)
    )
    return Event.objects.create(**fields)


def layout_pages(event):
    return [
        ('/', 'events/home.html', 'Otahque'),
        ('/events/', 'events/list.html',
         'Events | Otahque'),
        (f'/events/{event.pk}/', 'events/detail.html',
         'Python meetup | Otahque'),
    ]

save_event() saves a published event with sensible values, and any keyword argument replaces one of them, so a test states only what matters to it, such as status=Event.Status.DRAFT. When a test gives no end time, setdefault() sets one two hours after the start, so a test that moves the start never leaves the end before it. layout_pages() lists the three pages with their templates and titles; the detail page’s address depends on the saved event’s id, so it is built from the event. class EventListTests(TestCase):
    @classmethod
    def setUpTestData(cls):
        save_event(
            title='Django workshop',
            starts_at=datetime(2026, 12, 3, 9,
                               tzinfo=UTC),
        )
        save_event(title='Python meetup')
        save_event(title='Spring planning',

        save_event(title='Autumn social',
                   status=Event.Status.CANCELLED)

    def test_published_events_soonest_first(self):
        with self.assertNumQueries(1):
            response = self.client.get('/events/')
        html = response.content.decode()
        self.assertLess(html.index('Python meetup'),
                        html.index('Django workshop'))
        self.assertNotContains(response, 'Spring planning')
        self.assertNotContains(response, 'Autumn social')

    def test_empty_list(self):
        Event.objects.all().delete()
        response = self.client.get('/events/')
        self.assertContains(response, 'No events yet.')

setUpTestData() saves four events: two published, the later one first, one draft, and one cancelled. class EventDetailTests(TestCase):

    def test_published_event(self):

            f'/events/{self.event.pk}/'

        self.assertContains(
            response, '<h1>Python meetup</h1>', html=True
        )
        self.assertContains(

        )
        self.assertContains(
            response, 'Thursday 19 November 2026, 20:30 GMT'
        )
        self.assertContains(
            response, 'Leeds Central Library'
        )
        self.assertTemplateUsed(
            response, 'events/detail.html'
        )

    def test_time_in_event_time_zone(self):
        event = save_event(
            starts_at=datetime(2026, 12, 3, 9,
                               tzinfo=UTC),
            timezone='Asia/Kolkata',
        )
        response = self.client.get(f'/events/{event.pk}/')
        self.assertContains(
            response, 'Thursday 3 December 2026, 14:30 IST'
        )

    def test_unpublished_events_are_hidden(self):
        response = self.client.get(
            f'/events/{self.event.pk}/'
        )
        self.assertContains(
            response, 'Leeds Central Library'

                       Event.Status.CANCELLED):

                event = save_event(status=status)

                    f'/events/{event.pk}/'

    def test_missing_event(self):

            resolve('/events/999/').func,
            views.event_detail,

        self.assertEqual(response.status_code, 404)

    def test_invalid_id(self):

        self.assertEqual(response.status_code, 404)

Step 6: Read events from the database

Replace events/views.py with this:

events/views.py

from django.shortcuts import get_object_or_404, render

from .models import Event


def home(request):
    return render(request, 'events/home.html')


def event_list(request):
    events = Event.objects.filter(
        status=Event.Status.PUBLISHED
    )
    return render(
        request, 'events/list.html', {'events': events}
    )


def event_detail(request, event_id):
    event = get_object_or_404(
        Event, pk=event_id, status=Event.Status.PUBLISHED
    )
    return render(
        request, 'events/detail.html', {'event': event}
    )

SAMPLE_EVENTS and the Http404 import are gone. event_list passes a QuerySet to the template without running it; the template’s {% for %} loop evaluates it, with one query, in the model’s order, soonest first. event_detail asks for the event with this id and the published status: a draft or a cancelled event matches nothing, so get_object_or_404() raises Http404, exactly as for an id that does not exist. A visitor cannot tell a hidden event from a missing one, which is what the rule intends. The address pattern from Chapter 10 accepts whole numbers only, so /events/abc/ never reaches the view.

{% load tz %} loads Django’s time zone tags. Inside {% timezone event.timezone %}, every datetime, the start and the end alike, is shown in the zone the event names, such as Asia/Kolkata, instead of the project’s TIME_ZONE, UTC. The date filter formats it: l is the weekday, j the day without a leading zero, F the month’s name, Y the year, H:i the 24-hour time, and T the zone’s abbreviation. The end shows its full date too, so an event that ends on another day still reads correctly. One fixed format is enough for now; Chapter 61 decides how Otahque formats dates and times for different languages and regions. The title in the title block is escaped like any other variable, which the escaping test proves.
