What You Need to Know

From rows to objects

Chapter 15 asked questions of a database in SQL, and Chapter 16 described the event table as a Python class. A program needs both at once: it thinks in objects, and the database stores rows.

New Concept: the ORM

What problem exists? Python code works with objects that have attributes, such as event.title. The database stores rows in tables and answers SQL. Every page that shows events has to turn a question into SQL, send it, and turn each row it receives back into something Python can use.

What did people do before? They wrote the SQL by hand in each view, often building it out of strings, and copied each column out of each row by position. Every query was a chance to misspell a column, forget a condition, or let a visitor’s text change the SQL itself.

What is an ORM? An object-relational mapper translates in both directions. You describe what you want in Python, such as “events whose status is published, soonest first”, and the ORM writes the SQL, sends the values separately from it, and builds one model object for each row. Django’s ORM uses the models you wrote in Chapter 16 to know the tables and columns.

Why use it? The query is written once, in Python, and checked against the model’s fields. The same code runs on SQLite now and PostgreSQL in Chapter 32. Values never become part of the SQL text, which closes the most common route to SQL injection.

Now let’s use it. Every query in this chapter starts from Event.objects.

The ORM does not stop you from writing SQL, and it does not make SQL knowledge useless. Chapter 15’s SELECT, WHERE, and ORDER BY are exactly what the ORM writes for you, and knowing them helps you read what it does. Step 3 shows you that SQL.

Managers and QuerySets

Two words describe almost everything in this chapter.

New Concept: managers and QuerySets

What problem exists? You need a starting point for every question about a table, and a way to refine a question step by step, such as “published events”, then “in Leeds”, then “soonest first”, without running a query at each step.

What did people do before? A query was one string, written all at once. Refining it meant editing the string, or writing a second one.

What are they? A manager is the object on a model class through which queries start. Django gives every model one called objects, so Event.objects is the event table’s manager. Chapter 17 wrote one of its own, UserManager, to add create_user(); most models use Django’s plain one. A QuerySet is a description of a query that has not necessarily run yet. Event.objects.all() returns a QuerySet of every event; filter(), exclude(), and order_by() each return a new QuerySet with one more condition or order, leaving the one they started from unchanged.

Why use them? A QuerySet can be built in steps, passed around, and refined, and it reaches the database only when something needs its rows. The view can build one, and the template can loop over it.

Now let’s use them. Step 3 builds QuerySets in the shell and counts when they run.

A QuerySet behaves like a list in a few ways: you can loop over it, ask its length, and slice it with [:2]. It is not a list, though, and the next topics show where the difference matters.

The Django shell

Saving rows needs Python with Django’s settings loaded. Chapter 16’s practice helper did that for one script at a time; the Django shell does it for a session you type into.

New Tool: the Django shell

What problem exists? You want to try a query and see its answer at once, then try the next one, without writing a file for each.

What did people do before? Chapter 16’s setup_django.py loaded the settings, and each experiment was a script you saved and ran again.

What is the Django shell? manage.py shell starts Python’s interactive prompt with Otahque’s settings loaded. It also imports every model from the installed apps automatically, and, since Django 6.0, a few common tools such as connection, so Event and User are ready without an import line. You type a line after the >>> prompt and press Enter; Python runs it and prints its value. A line that opens a block, such as a for loop, or leaves a bracket open, gets a ... prompt for the next line.

Why use it? It is the quickest way to learn the ORM: every call and its answer are in front of you. Rows you save are saved for real, in your db.sqlite3.

Now let’s use it. Steps 1 to 4 happen in the shell.

In this book, a shell session is printed as you would see it. Type what follows each >>> or ... prompt, and nothing else; the lines without a prompt are what Python prints back. A line that is only ..., after an indented block, means “press Enter on an empty line” to finish the block. Elsewhere, a ... line marks lines left out of a long message, such as the middle of an error’s traceback.

One object or many

Two methods answer questions, and they answer different kinds.

New Concept: get(), filter(), and field lookups

What problem exists? Sometimes you need exactly one event, such as the one whose address a visitor opened. Sometimes you need every event that matches a condition, and there may be none, one, or many.

What did people do before? With SQL, every query returned a list of rows, and each caller checked by hand whether the list had the one row it expected.

What are they? get() returns exactly one object. If no row matches, it raises the model’s DoesNotExist error, such as Event.DoesNotExist; if more than one matches, it raises MultipleObjectsReturned. filter() returns a QuerySet of every match, which may be empty, and never raises either error. Both take conditions as keyword arguments. A plain field name, such as status='published', means “equals”. A field name, two underscores, and a lookup name ask a different question: title__icontains='python' means “the title contains python, ignoring letter case”, and starts_at__gte=... means “starts at or after”.

Why the difference? A page about one event needs one event, or a clear “not found”. A list page needs a collection that may be empty. Choosing the method states what you expect, and the errors catch the cases you did not expect.

Now let’s use them. Steps 2 and 3 try both, including the errors.

Table 19.1 lists the lookups this chapter uses. Django has many more, listed in its QuerySet reference; these cover most everyday pages.

One difference between databases matters already. On SQLite, contains, the case-sensitive form of icontains, also ignores letter case for English letters, because SQLite’s LIKE does. Use icontains when you mean “ignoring case”, so that the query means the same thing on PostgreSQL in Chapter 32.

When a query runs

A QuerySet is lazy: building it costs nothing, and the database is asked only when something needs the rows.

Under the Hood: laziness and the result cache

Event.objects.filter(...) creates a QuerySet object holding a description of the query, Django’s own Query object, and returns at once; no SQL is sent. Each filter(), exclude(), or order_by() copies that description and adds to the copy. The query runs when the QuerySet is evaluated: when a for loop starts, when list(), len(), or bool() is called on it, when the shell prints it, or when a template’s {% for %} loops over it. At that moment Django turns the description into SQL for the database in use, sends it with the values as separate parameters, builds one model object per row, and stores the list of objects inside that QuerySet, its result cache. Looping over the same QuerySet again uses the cache. So do count() and exists() once the whole result is cached, because the answer is already known. A new QuerySet, even one built from the same code, starts with an empty cache and queries again. Two details are easy to miss. Slicing, such as [:2], and taking one item, such as [0], on a QuerySet that has not been evaluated return a new query each time instead of filling the cache. And calling count() or exists() on a QuerySet that has not been evaluated asks the database a smaller question, SELECT COUNT(*), without loading any rows.

One QuerySet’s path, from the manager to the reused cache, is drawn in Figure 19.1.

Laziness is why a view can build a QuerySet and hand it to a template without running anything, and why the list page can run exactly one query however many events it shows. It is also why a careless loop can run many: each time code builds a new QuerySet inside a loop, it asks the database again. Step 3 counts both cases, and the list page’s test pins the count at one.

Try it yourself

Que. 1 Raj builds a QuerySet of the published events and names it upcoming. On the next line, he calls order_by() on it to sort the events latest first, and gives the result the same name. How many queries have run after the two lines, and what did the second line do to the first QuerySet?

Flip to check your answerFold answer back

Answer. None. Both lines build QuerySets; nothing has asked for rows yet. The second line does not change the first QuerySet: order_by() returns a new QuerySet with the same condition and a new order, and the name upcoming now refers to that new one. The query runs when something evaluates it, such as a loop.

Changing and deleting rows

Reading is half the job. The ORM changes rows in two ways, and neither checks the values.

update() works in the database only. It does not call any model’s save(), it does not change objects you already hold in Python, and it returns the number of rows it matched. delete() returns how many rows it deleted, with a count per model.

Common Error: assuming save() checks the data

Chapter 16 called full_clean() and saw Django refuse a status of archived. That check does not run when you save: save() sends whatever the object holds, and the database stores it unless a database rule refuses it. Django’s documentation says full_clean() is not called automatically by save(). Forms call it for you, from Chapter 24, and Chapter 21 adds database constraints, which refuse bad values however they arrive. Step 4 saves a broken row on purpose, sees it stored, and deletes it.

Public pages and the published rule

The pages read the database from Step 6. What they read is a product decision: the PRD’s requirement that drafts stay hidden from visitors becomes a condition in a query.

Prefer get() with a try block in a view?

A detail view could call Event.objects.get(pk=event_id) inside try, catch Event.DoesNotExist, and raise Http404, as Chapter 10’s view did for the dictionary. get_object_or_404(), from django.shortcuts, does exactly that in one call: it takes a model, a manager, or a QuerySet, and the same conditions as get(), and raises Http404 when nothing matches. Use it in views, where “not found” should become a 404 page. Outside views, such as in the shell or a script, use get() and catch the named error, so that a missing row is not mistaken for a missing page. Never catch a bare Exception around get(): it would hide a typo in a field name as easily as a missing row.

The detail view needs the published rule too, not only the list. If it looked events up by id alone, anyone who guessed /events/3/ would see the spring plan. Figure 19.2 shows both pages’ path.

In practice: a page that must never show drafts

Situation. An organizer saves a half-written event to come back to later. Its title mentions a speaker who has not yet agreed. If it appears on a public page, even for an hour, the community sees it.

Application. The rule lives in the query, filter(status=Event.Status.PUBLISHED), in every view that serves visitors, and a test proves it for each page by saving a draft and asserting that it does not appear. A template that hides drafts with an {% if %} would still load them, and would forget the rule on the next page someone writes.

Consideration. Writing the same condition in two views is repetition that can drift: a third view may forget it. Chapter 22 moves the rule into one named method, published(), after you have seen the repetition it removes. Until then, the tests are the guard.
