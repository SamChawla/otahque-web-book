Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead to a larger application with a team: attempt them now, and return to them after Chapters 22 and 57. They are extension questions, not a gate to the next chapter. Each code proof except L5’s is a short file in the practice folder that starts by importing Chapter 16’s setup_django.py; run it from the folder that holds manage.py with uv run python ../practice/ followed by the file name. The proofs read your three events and leave them as they are.

L1 (Junior): What is the difference between get() and filter(), and what does each do when nothing matches?

What the interviewer is testing: Do you know which method promises one object, and how to handle the cases where that promise fails?

Flip to check your answerFold answer back

Perfect answer: get() returns exactly one model object. When no row matches, it raises the model’s DoesNotExist error; when more than one matches, it raises MultipleObjectsReturned. I use it when exactly one row must exist, usually by primary key or another unique field, and I catch the named error rather than a bare Exception. In a view, I use get_object_or_404(), which turns a missing row into a 404 page. filter() returns a QuerySet of every match, which may be empty, and raises neither error; it is also lazy, so it does not run until it is evaluated. I use it for lists, and with first() when I want one object or None.

Behind the scenes:

get and filter (summary)

get(pk=1)        -> one object, now, or an exception
filter(...)      -> a QuerySet, later, maybe empty
filter().first() -> one object or None
view             -> get_object_or_404() for a 404 page

Code proof: both methods, asked for a title no event has:

../practice/l1_get_filter.py

import setup_django
from events.models import Event

print(Event.objects.filter(title='Nope'))
try:
    Event.objects.get(title='Nope')
except Event.DoesNotExist as error:
    print('get():', error)
print(Event.objects.filter(title='Nope').first())

Output

<QuerySet []>
get(): Event matching query does not exist.
None

Common mistakes:

  • Using get() on a field that is not unique, so it fails once a second matching row appears.
  • Expecting filter() to return one object, then reading .title on the QuerySet.
  • Wrapping get() in except Exception, which also hides typos in field names.

Follow-up the interviewer might ask:

  • “How would you fetch one event by id in a view, and what should a visitor see if it is hidden?”
  • “When is filter(...).first() better than get()?”

L2 (Mid-Level): When does a QuerySet hit the database, and when does it reuse results?

What the interviewer is testing: Can you predict queries from code, which is the basis of every performance conversation about the ORM?

Flip to check your answerFold answer back

Perfect answer: Building and chaining a QuerySet never queries the database: filter(), exclude(), and order_by() return new, unevaluated QuerySets. The query runs when the QuerySet is evaluated: iterating over it, including in a template, calling list(), len(), or bool(), printing it, or slicing it with a step. Evaluation fills the QuerySet’s result cache, and iterating the same QuerySet again, or calling count() or exists() on it once fully evaluated, uses that cache. A new QuerySet, even from identical code, has an empty cache, so Event.objects.count() written twice runs two queries. Slicing or indexing an unevaluated QuerySet runs a limited query each time and does not fill the cache. So I keep one QuerySet in a variable when I need its rows more than once, I use count() or exists() on an unevaluated QuerySet when I need only a number or a yes, and I check the count in tests with assertNumQueries.

Behind the scenes:

laziness (summary)

filter(), order_by()     -> new QuerySet, 0 queries
for, list(), len(), bool -> 1 query, rows cached
same QuerySet again      -> cache, 0 queries
new QuerySet, same code  -> 1 more query

Code proof: one QuerySet used twice, then a new one built from the same code:

../practice/l2_laziness.py

import setup_django
from django.db import connection
from django.test.utils import CaptureQueriesContext

from events.models import Event

with CaptureQueriesContext(connection) as queries:
    published = Event.objects.filter(status='published')
    print('built:', len(queries))
    first_pass = list(published)
    second_pass = list(published)
    print('same QuerySet twice:', len(queries))
    again = list(Event.objects.filter(status='published'))
    print('new QuerySet:', len(queries))

Output

built: 0
same QuerySet twice: 1
new QuerySet: 2

Common mistakes:

  • Building a new QuerySet inside a loop, so each pass queries again.
  • Calling len() on a QuerySet only to count it, which loads every row; count() asks for a number.
  • Assuming that [0] on an unevaluated QuerySet uses a cache.

Follow-up the interviewer might ask:

  • “Why does if events: run a query, and when is exists() better?”
  • “How would you prove in a test that a page’s query count does not grow with its data?”

L3 (Senior): What do save(), save(update_fields=...), and QuerySet update() each send, and what does none of them do?

What the interviewer is testing: Do you know exactly what reaches the database when a row changes, and where validation actually happens?

Flip to check your answerFold answer back

Perfect answer: save() on an existing object sends one UPDATE that sets every column from the object’s attributes, so it can overwrite a change another process made to a column this code never touched. save(update_fields=[...]) sends an UPDATE of only the named columns, which avoids that and sends less. Both go through the model’s save() method and its signals. QuerySet update() sends one UPDATE ... WHERE for every matching row; it does not call save(), does not send the pre_save or post_save signals, does not change objects already loaded in Python, and returns the number of rows matched. None of the three calls full_clean(): Django’s model validation runs only when called, as forms do. So data rules belong in two places: validation in forms and other entry points, for helpful messages, and database constraints, which refuse bad data whichever code path writes it. In Otahque, Chapter 21 adds those constraints and Chapter 24 the forms.

Behind the scenes:

writes (summary)

obj.save()                -> UPDATE every column
obj.save(update_fields=x) -> UPDATE only x
qs.update(f=v)            -> one UPDATE, no save()
none of them              -> full_clean()

Code proof: how many columns each write sets, captured inside a transaction that is rolled back, so your events stay as they are:

../practice/l3_writes.py

import re

import setup_django
from django.db import connection, transaction
from django.test.utils import CaptureQueriesContext

from events.models import Event


def columns(queries):
    sql = queries[-1]['sql']
    return re.findall(r'SET (.*) WHERE', sql)[0].count('=')


with transaction.atomic():
    event = Event.objects.get(title='Python meetup')
    with CaptureQueriesContext(connection) as q:
        event.save()
    print('save():', columns(q), 'columns')
    with CaptureQueriesContext(connection) as q:
        event.save(update_fields=['location'])
    print('update_fields:', columns(q), 'column')
    rows = Event.objects.filter(pk=event.pk)
    print('update():', rows.update(status='archived'))
    print('stored:', rows.get().status)
    transaction.set_rollback(True)
event.refresh_from_db()
print('after rollback:', event.status)

Output

save(): 7 columns
update_fields: 1 column
update(): 1
stored: archived
after rollback: published

save() set all seven columns besides the id; update_fields set one. update() stored a status that is not one of the choices, without complaint. transaction.atomic() groups the writes, and set_rollback(True) undoes them all at the end of the block; refresh_from_db() then reads the row as the database holds it again.

Common mistakes:

  • Believing the model’s choices or required fields stop bad values on save().
  • Putting important logic in save() and then using update(), which skips it.
  • Reading an object after update() without refresh_from_db().

Follow-up the interviewer might ask:

  • “Two people edit different fields of the same event at once. What can go wrong with save()?”
  • “Where would you enforce that capacity is at least one?”

L4 (Staff): After organizer names were added to the events page, it went from 1 query to 41. How do you find and fix it?

What the interviewer is testing: Looking ahead: can you recognize a query per row, measure it, and fix it without guessing?

Flip to check your answerFold answer back

Perfect answer: Forty-one queries for forty events is the classic pattern called N+1: one query for the list, then one more for each row, because the template reads event.organizer.display_name and each access loads that related row on its own. I would confirm it first, with assertNumQueries in a test, CaptureQueriesContext, or a tool such as Django Debug Toolbar, and look at the repeated query. For a foreign key, select_related('organizer') fetches the organizer in the same query with a join; for many-to-many or reverse relations, prefetch_related() fetches them in one extra query. Then I would keep the list page’s test asserting a fixed number of queries with several events, so the problem cannot return quietly. Otahque has no relationships yet: Chapter 20 adds them, Chapter 22 composes such queries, and Chapter 57 measures them.

Behind the scenes:

N+1 (summary)

1 query        -> the list of events
+1 per event   -> event.organizer, loaded on access
select_related -> one query with a JOIN
test           -> assertNumQueries(1) with many rows

Code proof: relationships arrive in Chapter 20, so this proof shows the same shape with what exists now: a query written inside a loop, against the same answer worked out from one query:

../practice/l4_per_row.py

from collections import Counter

import setup_django
from django.db import connection
from django.test.utils import CaptureQueriesContext

from events.models import Event

with CaptureQueriesContext(connection) as q:
    for event in Event.objects.all():
        Event.objects.filter(location=event.location).count()
print('query per row:', len(q))
with CaptureQueriesContext(connection) as q:
    events = list(Event.objects.all())
    Counter(event.location for event in events)
print('one query:', len(q))

Output

query per row: 4
one query: 1

With three events, the loop ran 1 + 3 queries; with forty, it would run 41. The second version runs one, however many events there are.

Common mistakes:

  • Adding caching before measuring, which hides the queries instead of removing them.
  • Using prefetch_related() for a foreign key, where select_related() needs no extra query.
  • Testing the query count with one event only, where N+1 cannot show.

Follow-up the interviewer might ask:

  • “When is a second query from prefetch_related() better than a join?”
  • “How would you stop a template from triggering queries at all?”

L5 (Lead): How would you stop drafts leaking onto public pages as the number of views grows?

What the interviewer is testing: Looking ahead: can you turn a rule that lives in one query into a rule that holds across a team and a growing codebase?

Flip to check your answerFold answer back

Perfect answer: Today the rule is written twice, as a filter() in the list view and a condition in the detail view. That works for two pages, but each new public page, feed, sitemap, or search result is a new chance to forget it. I would make the rule explicit and hard to miss. First, write it down as a product rule: visitors see published events only. Second, give it one home in code, a named QuerySet method such as Event.objects.published(), which Chapter 22 adds, so that views ask for published events instead of repeating the condition. Third, test it per page: every public page gets a test that saves a draft and a cancelled event and proves they are absent or return 404, as this chapter’s tests do. Fourth, review public views for bare Event.objects queries, and make the safe method the easy default. Finally, run the tests on every change before it is merged, which Chapter 34 automates. I would not hide drafts in templates, because a template can only hide what the query already loaded.

Behind the scenes:

visibility rule (summary)

rule    -> written down: published only
code    -> one method: Event.objects.published()
tests   -> each public page: draft and cancelled hidden
process -> review, then tests before every merge

Code proof: the detail page’s tests, including the one that saves a draft and a cancelled event and expects 404 for both, after checking the published page. In PowerShell:

Common mistakes:

  • Hiding drafts with {% if %} in a template, after the query has loaded them.
  • Testing the list page and assuming the detail page follows.
  • Adding a new public page without a visibility test.

Follow-up the interviewer might ask:

  • “Should a cancelled event’s page return 404, or show a notice? Who decides?”
  • “How would you make the unsafe query harder to write than the safe one?”
