Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 and L2 check what you have just learned. L3 asks how it works underneath. L4 and L5 ask about the design and leadership decisions that later chapters build on: attempt them now, and return to them when you reach those chapters. Use the readiness checkpoint to decide whether to continue. If an answer is difficult, revisit its worked example and explain the result in your own words. L4 and L5 are extension questions, not a gate to the next chapter.

L1 (Junior): What is the difference between a Django project and a Django app?

What the interviewer is testing: Do you know which part configures the website and which parts supply its features?

Flip to check your answerFold answer back

Perfect answer: A project is the configuration and the apps brought together for one website: its settings, its root URL configuration, and the WSGI and ASGI entry points that servers use. startproject config . created the config package and manage.py. An app is a Python package that supplies one capability, such as the events app in Chapter 7. A project uses many apps, and an app can be reused across projects, as django.contrib.auth is.

Behind the scenes:

what startproject wrote (summary)

# manage.py          -> selects config.settings, runs commands
# config/settings.py -> INSTALLED_APPS, MIDDLEWARE, ROOT_URLCONF
# config/urls.py     -> urlpatterns: the root URL configuration
# config/wsgi.py     -> application object for WSGI servers
# config/asgi.py     -> application object for ASGI servers

Code proof: in PowerShell, a macOS shell, or Linux/WSL Bash, beside manage.py:

Terminal

uv run --no-project --python .venv python manage.py shell -c "
from django.conf import settings
print(settings.ROOT_URLCONF, settings.WSGI_APPLICATION)"

Output

12 objects imported automatically (use -v 2 for details).

config.urls config.wsgi.application

Common mistakes:

  • Creating a new project for each feature.
  • Giving the project package the same name as an app.
  • Treating the project folder as just another app.

Follow-up the interviewer might ask:

  • “Which apps does a new project already include?”
  • “Why did we name the project package config?”

L2 (Mid-Level): What does manage.py do, and how does Django know which settings to use?

What the interviewer is testing: Do you understand how a command finds the project’s configuration?

Flip to check your answerFold answer back

Perfect answer: manage.py is a small script that sets the DJANGO_SETTINGS_MODULE environment variable to config.settings, unless it is already set, and then runs Django’s command-line utility. Commands such as check and runserver therefore run with this project’s settings. The settings are an ordinary Python module, named by that variable; config/wsgi.py and config/asgi.py set the same default for servers. Because the default only applies when the variable is unset, a production server or a test run can select different settings without editing manage.py.

Behind the scenes:

manage.py (summary of main)

# os.environ.setdefault('DJANGO_SETTINGS_MODULE',
#                       'config.settings')
# from django.core.management import execute_from_command_line
# execute_from_command_line(sys.argv)
#   -> django.setup() with those settings, then the command

Code proof: from the folder that contains manage.py, in PowerShell, a macOS shell, or Linux/WSL Bash. The quoted text spans three lines; type it exactly, including the final double quote:

Terminal

uv run --no-project --python .venv python manage.py shell -c "
from django.conf import settings
print(settings.SETTINGS_MODULE)"

Output

12 objects imported automatically (use -v 2 for details).

config.settings

Common mistakes:

  • Running manage.py from another folder.
  • Editing manage.py instead of the settings.
  • Expecting settings in a separate configuration-file format.

Follow-up the interviewer might ask:

  • “What happens if you run a command outside the folder with manage.py?”
  • “How would a production server find the settings?”

L3 (Senior): What does manage.py check examine, and what does a pass not prove?

What the interviewer is testing: Do you know what system checks cover, and avoid treating them as tests?

Flip to check your answerFold answer back

Perfect answer: check runs Django’s system check framework. Registered checks inspect the configuration for common problems, such as settings, URL configuration, templates, and models, and report errors and warnings with identifiers such as security.W018. check --deploy adds checks for deployment settings. A pass means no known configuration problem was found. It does not prove that pages work, that Otahque’s rules are right, that the database is ready, or that the site is secure.

Behind the scenes:

django/core/checks/registry.py (summary)

# Check functions are registered with @register(tags...);
# deployment checks are registered with deploy=True.
# run_checks() calls every registered function and collects
# CheckMessage objects; ERROR and above stop the command.

Code proof: the new project’s development settings fail the deployment checks, as they should, and the command exits with an error status. PowerShell, in otahque/:

PowerShell

uv run --no-project --python .venv python manage.py `
  check --deploy

macOS shell or Linux/WSL Bash, in otahque/:

Terminal

uv run --no-project --python .venv python manage.py \
  check --deploy

Output

SystemCheckError: System check identified some issues:
[One error, mail.E001, for the development email backend,
and seven warnings, security.W004 to security.W020,
including DEBUG and an empty ALLOWED_HOSTS]
System check identified 8 issues (0 silenced).

Common mistakes:

  • Treating “no issues” as a test suite.
  • Ignoring warnings.
  • Changing settings only to silence a deployment warning without understanding it.

Follow-up the interviewer might ask:

  • “How would you add a check of your own?”
  • “Which deployment issue would you fix first, and why?”

L4 (Staff): runserver works on your computer. Why must it not serve the public site, and what replaces it?

What the interviewer is testing: Do you know the limits of the development server and what a production setup adds?

Flip to check your answerFold answer back

Perfect answer: Django’s documentation says the development server is for development only: it has not been through security audits or performance tests. It reloads code for convenience, and in this chapter it listens on the loopback address, so only your own computer can reach it. In production, a WSGI or ASGI server loads config.wsgi or config.asgi, usually behind a web server or proxy that handles HTTPS and static files, with DEBUG turned off, ALLOWED_HOSTS set, and the secret key kept out of the code. check --deploy lists what is still missing. Later chapters build that setup.

Behind the scenes:

django/core/servers/basehttp.py (summary)

# runserver serves the object named by WSGI_APPLICATION,
# here 'config.wsgi.application', through Python's simple
# wsgiref server: one process, for local development.

Code proof: the setting runserver follows, in PowerShell, a macOS shell, or Linux/WSL Bash:

Terminal

uv run --no-project --python .venv python manage.py shell -c "
from django.conf import settings
print(settings.WSGI_APPLICATION)"

Output

12 objects imported automatically (use -v 2 for details).

config.wsgi.application

Common mistakes:

  • Exposing runserver on a public address.
  • Running with DEBUG on in production.
  • Thinking that wsgi.py is itself a server.

Follow-up the interviewer might ask:

  • “WSGI or ASGI for Otahque, and why?”
  • “What does ALLOWED_HOSTS protect against?”

L5 (Lead): How would you make every contributor’s Django setup identical, and what is still missing from our Chapter 6 setup?

What the interviewer is testing: Can you tell a reproducible setup from one that only works today?

Flip to check your answerFold answer back

Perfect answer: Pin the Python version in .python-version, create a separate .venv for the project with uv, install an exact Django version, and give everyone the same readiness commands: check_environment.py, uv pip check, and manage.py check. Still missing: a pin on Django alone is not a complete lock, so its dependencies, such as asgiref and sqlparse, and tzdata on Windows, could differ between machines; Chapter 8 introduces that workflow. The project also needs version control, secrets kept out of the code, and automated checks that run the same commands for every change. A lead makes the verified path the easy one, and checks it: each new contributor’s readiness check passes before their first change.

Behind the scenes:

what is pinned today (summary)

# .python-version  -> 3.14.9            (pinned)
# Django==6.1.2    -> django            (pinned)
# asgiref, sqlparse, tzdata -> chosen by the installer on
# the day you install: not yet recorded anywhere.

Code proof: list what the environment actually contains:

Terminal

uv pip list --python .venv

Output

Package  Version
-------- -------
asgiref  3.13.0
django   6.1.2
sqlparse 0.6.0
tzdata   2026.5

This is the list on Windows. On macOS and Linux there is no tzdata row, because Django asks for that package only on Windows.

Common mistakes:

  • Sharing a .venv folder.
  • Assuming that the same Django version means the same environment.
  • Recording versions once by hand and never again.

Follow-up the interviewer might ask:

  • “Which files would you commit, and which never?”
  • “How would you upgrade Django safely across a team?”
