6.2 Create the project

Sam needs a working starting structure before he can add event behaviour. Django can generate that structure. Generating it once gives us a small set of files to understand instead of asking us to invent the wiring ourselves.

Starting point: Section 6.1’s verified environment. Work in the same otahque/ folder, beside .venv/ and check_environment.py. No project files should exist there yet. This section creates manage.py and a config/ package; its visible check is a successful Django system check. No browser server is running yet.

A project collects configuration; an app supplies a capability

A Django project brings together the configuration and apps for a website. Its configuration says which components to use and how they fit together. A Django app is a Python package that supplies a particular capability, such as working with events. A project can use several apps, and an app can sometimes be reused in another project. Chapter 7 develops that distinction and creates our first app.

The word application in Chapter 5 meant the whole running web application. Django app has this narrower meaning. Calling the generated configuration package config does not make it the events app or add event pages.

We will use otahque/ as the outer working folder and config as the inner Python package name. The outer folder also holds the environment and helper. The package name appears in Python imports such as config.settings, so keep it exactly as shown. Avoid django or a name that hides another installed Python module. The folder name is not a public domain name.

Que. 4 Why are the working folder and the configuration package named differently?

Show answerHide answer

Answer. They have different jobs. otahque/ holds our work; config/ is the Python package containing the site’s configuration. Using distinct names helps us tell a filesystem location from an import path. It does not create two websites or two independently running services.

Read the generation command before running it

Django’s startproject command writes the initial project files. config is the package name. The final dot means the current directory: put manage.py here and config/ inside this folder. Without an explicit destination, Django normally creates another outer directory named after the project, which would give us a different layout.

Check the folder before generation. If it already contains manage.py or config/, stop and inspect it rather than trying to repair it by running the command again. Existing .venv/, .python-version, and the helper from 6.1 should remain in place.

PowerShell, in otahque/. The backtick continues the command onto the next line; put no spaces after it:

uv run --no-project --python .venv python -m django `
  startproject config .

macOS shell or Linux/WSL Bash, in otahque/. The backslash continues the command; put no spaces after it:

uv run --no-project --python .venv python -m django \
  startproject config .

Choose the block for your shell and run it once. Both blocks represent the same Django operation. The uv options select the environment already verified in 6.1; python -m django runs Django’s management entry point without depending on a separately discovered command.

Successful generation normally returns to the prompt without a success message. Inspect the files in your editor. This is the expected layout at this point; the contents of .venv/ are deliberately omitted:

otahque/
    .python-version
    .venv/
    check_environment.py
    manage.py
    config/
        __init__.py
        settings.py
        urls.py
        asgi.py
        wsgi.py

The new files are manage.py and the five Python files inside config/. Opening or running Python can also produce __pycache__/ folders containing cached bytecode. Those are generated working files, not another Django app and not files to edit.

Check the generated configuration

manage.py is the new project’s command-line helper. Unlike the general Django entry point, it knows to select config.settings. Run the following in PowerShell, a macOS shell, or Linux/WSL Bash, still beside manage.py:

uv run --no-project --python .venv python manage.py check

Expected result:

System check identified no issues (0 silenced).

This check looks for common configuration problems. It does not open a browser, create account tables, or prove that future registration rules work. If Python cannot open manage.py, check the current directory. If Django cannot be imported, repeat the explicit environment check from 6.1. If generation reports a name conflict or existing file, preserve what exists and inspect it; Section 6.5 shows how to compare with a freshly generated copy.

In practice: making a repeatable starting structure

Situation. A second contributor wants the same project layout as Sam.

Application. Record the package name and destination as well as the framework version. The final dot explains why manage.py sits beside .venv/.

Consideration. Generation is a starting action, not a repair command. Repeating it over existing work can encounter conflicts; compare with a freshly generated copy instead (Section 6.5).

Try it yourself

On paper, remove the final dot from the generation command. Predict where manage.py would be placed and explain why our next command would then fail if you stayed in the original outer folder. Do not regenerate the working project for this exercise.

Que. 5 What changes when no destination is supplied?

Show answerHide answer

Answer. Django creates an outer config/ folder containing manage.py and another config/ package. The original otahque/ folder would not contain manage.py, so python manage.py check from there would fail to find that file. Our explicit dot keeps the layout shown above. If you accidentally made the nested layout, inspect it and compare it with the layout shown above; do not delete or move files blindly.
