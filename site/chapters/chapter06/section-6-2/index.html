What You Need to Know

Three versions, three jobs

We carry uv 0.13.5 and CPython 3.14.9 forward from Chapter 4 and install Django 6.1.2, checked against Django’s official download page on 26 October 2026. Django’s 6.1 installation FAQ lists Python 3.14 as supported. The planned upgrade to Django 6.2 LTS remains a separate later checkpoint.

New Tool: Django

What problem exists? Every web application needs the same machinery: matching addresses, reading requests, building responses, talking to a database, protecting forms, and signing people in. Writing it yourself for each project is slow and easy to get subtly wrong.

What did people do before? Developers assembled separate libraries or wrote the plumbing by hand, as the Custom Way in How We Build It shows in miniature.

What is Django? A Python web framework that supplies that machinery as one tested package, with conventions for where each piece lives.

Why Django? Chapter 5 compared the options: it fits a server-rendered first release, a small volunteer team, and the rules Otahque must enforce. Its documentation and long-term-support releases suit a book that will be read for years.

Now let’s install it into an environment we can name.

The double equals sign in Django==6.1.2 asks the package installer for that exact Django release. It is a package version requirement, not the Python comparison expression from Chapter 4. This pins Django itself. Django also needs supporting packages, called dependencies, and the installer selects compatible versions of those. A complete dependency lock records those choices too, which Chapter 8 will teach.

Installation and execution must select the same environment

Installing Django makes its Python package available to one interpreter. It does not create an Otahque project, start a server, or add a website to a browser. The commonest setup failure is installing into one environment and running with another, so every command in this chapter names the environment explicitly with --python .venv. Answer. No. We have shown that the selected environment can run Django 6.1.2. We still need project files and a running server before a browser can receive a page.

A project collects configuration; an app supplies a capability

A Django project brings together the configuration and apps for a website. Its configuration says which components to use and how they fit together. A Django app is a Python package that supplies a particular capability, such as working with events. A project can use several apps, and an app can sometimes be reused in another project. Chapter 7 develops that distinction and creates our first app.

The word application in Chapter 5 meant the whole running web application. Django app has this narrower meaning. We will use otahque/ as the outer working folder and config as the inner Python package name. The outer folder also holds the environment and a small helper. The package name appears in Python imports such as config.settings, so keep it exactly as shown, and avoid django or any name that hides another installed module. The folder name is not a public domain name.

Que. 2 Why are the working folder and the configuration package named differently?

Flip to check your answerFold answer back

Answer. They have different jobs. otahque/ holds our work; config/ is the Python package containing the site’s configuration. Using distinct names helps us tell a filesystem location from an import path. It does not create two websites or two independently running services.

Under the Hood: what manage.py does

The manage.py file that startproject generates is a few lines long. Its main() function calls os.environ.setdefault('DJANGO_SETTINGS_MODULE', 'config.settings'), which names our settings module unless the environment already names another, and then passes the terminal’s arguments to Django’s execute_from_command_line(). That function sets Django up with those settings and runs the requested management command, such as check or runserver. config/wsgi.py and config/asgi.py set the same default before building the application object a server calls.

A local server, a loopback address, and a port

Django’s development server, started with runserver, listens by default on 127.0.0.1 at port 8000. The address 127.0.0.1 is loopback: it refers to this computer, so nothing else on the network can reach it. A port distinguishes one listening service from another at an address. While the server runs, its terminal stays occupied; it has not frozen merely because the prompt does not return.

The server also reports unapplied migrations. A migration is a recorded database change, such as creating tables for an app. The warning is expected, because the generated project enables apps whose tables have not been created. We leave those migrations unapplied: Otahque’s custom user model must be chosen in Chapter 17 before the first migration is applied, and running the command the warning suggests would jump ahead of that decision. This deferral is specific to the fresh development page, which needs no tables. It is not advice to ignore migration warnings in an application that needs its database.

Prefer activating the environment?

Many guides activate a virtual environment so that plain python finds it. Activation works, but it changes your shell invisibly, and a new terminal or an editor may not inherit it. We name --python .venv in every command instead, so each command shows which environment it uses. Chapter 8 introduces uv’s project workflow, which selects the environment for us.
