6.1 Prepare an isolated Django environment

Installing Django makes its Python package available to an interpreter. It does not create an Otahque project, start a server, or add a website to a browser. We will first make sure we can identify exactly which interpreter has Django, so the next section starts from a known environment.

Starting point: Chapter 4’s readiness checks and Chapter 5’s proposed design; no Django project exists. Begin in a directory where you keep your own work, outside the Chapter 4 practice folder. You need uv 0.13.5, managed CPython 3.14.9, an editor, a terminal, and internet access to download packages. This section creates otahque/, .python-version, .venv/, and a small check_environment.py file. The visible result is a successful terminal verification, not a browser page yet.

Keep the versions and their jobs separate

We carry uv 0.13.5 and CPython 3.14.9 forward from Chapter 4 and install Django 6.1.2, checked against Django’s official download page on 26 October 2026. Django’s 6.1 installation FAQ lists Python 3.14 as supported. The planned upgrade to Django 6.2 LTS remains a separate later checkpoint.

The double equals sign in Django==6.1.2 asks the package installer for that exact Django release. It is a package version requirement, not the Python comparison expression from Chapter 4. This pins Django itself. Django also needs supporting packages, called dependencies; the installer selects compatible versions of those. A complete dependency lock records those choices too, which Chapter 8 will teach.

Create a fresh work folder

Open the terminal in your chosen work directory. On Windows, use PowerShell. On macOS, use your usual terminal shell; on Linux or WSL, use Bash. WSL is a separate Linux environment: follow the Linux commands there, with uv and Python installed inside WSL. These commands belong at a shell prompt, not at Python’s >>> prompt.

Check that no folder named otahque already exists here. If it does, inspect it before proceeding. Keep existing work and choose a fresh sibling folder such as otahque-learning instead; use that name in the next command. Do not nest this work inside an old project or reuse the Chapter 4 environment.

PowerShell, macOS shell, or Linux/WSL Bash:

mkdir otahque
cd otahque
uv --version
uv python pin 3.14.9
uv venv --python 3.14.9

The current directory is now otahque/. The version check should begin with uv 0.13.5; build details may follow. The pin command writes .python-version with 3.14.9. The venv command creates .venv/ using that Python and should report CPython 3.14.9. It may also suggest an activation command; you can ignore it, because every command in this chapter names .venv explicitly. If these do not match, return to Chapter 4’s version checks before installing anything. A dot at the start of a name often hides it in a file manager; your editor can still open it.

Install into the environment you name

In the same otahque/ directory, run the following in PowerShell, a macOS shell, or Linux/WSL Bash:

uv pip install --python .venv "Django==6.1.2"
uv run --no-project --python .venv python -m django --version

uv pip is uv’s package-installation interface; it does not require a pip program inside the environment. --python .venv selects the environment explicitly for installation and execution. uv run launches the command; --no-project keeps uv from looking for a uv project’s dependency metadata. The Django project we create next and a uv-managed project are different ideas. Chapter 8 introduces uv’s project workflow.

The installer reports Django and its supporting packages. Download messages, timings, and dependency versions may differ; the final version command must print 6.1.2. A warning that --no-project found no project is harmless here. python -m django asks the selected Python to run the django module, rather than trusting a standalone django-admin command found elsewhere on your computer. No environment activation is needed.

Que. 1 The version command prints 6.1.2. Have we created the Otahque website?

Show answerHide answer

Answer. No. We have shown that the selected environment can run Django 6.1.2. We still need project files and a running server before a browser can receive a page. Section 6.2 creates those project files.

Check the interpreter as well as the package

Create check_environment.py beside .venv/, not inside it. This is a small verification helper, not a Django project file. Type or save the complete file below; do not name it django.py, which would hide the package we want to import. It extends Chapter 4’s environment check with a Django import.

import sys

import django

print(sys.version.split()[0])
print(sys.executable)
print(sys.prefix != sys.base_prefix)
print(django.get_version())

sys.version gives Python’s version text; split()[0] selects its first space-separated part. sys.executable identifies the running interpreter. Different prefix and base_prefix values indicate a virtual environment. The django import and get_version() call then check the framework available to that same interpreter.

PowerShell, macOS shell, or Linux/WSL Bash, still in otahque/:

uv run --no-project --python .venv check_environment.py
uv pip check --python .venv

The helper should print the following four items. The path line is described here because your absolute path will differ:

3.14.9
[your otahque/.venv interpreter path]
True
6.1.2

The bracketed second line is a placeholder, not literal program output. On Windows, the path ends in .venv\Scripts\python.exe; on macOS/Linux it normally ends in .venv/bin/python. Check that it belongs to this otahque folder. uv pip check should report that installed packages are compatible. That check detects dependency problems; it does not verify Otahque’s product rules or security.

Que. 2 An editor runs the helper with a different Python. What should you do?

Show answerHide answer

Answer. Compare the executable path with the one printed by the explicit uv command. Select this work folder’s .venv interpreter in the editor, as in Chapter 4, and rerun. Installing Django into whichever other Python the editor happened to choose would leave the mismatch unexplained.

In practice: reproducing a setup report

Situation. A contributor says Django is installed, but an import fails when they run the project.

Application. Ask for the working directory, interpreter path, Python version, and Django version from the same execution. Those observations help distinguish a missing package from a different interpreter.

Consideration. A successful check on one computer does not establish that another shell or operating system uses the same environment. Keep the environment selection visible in commands.

If a setup check fails

These commands were tested on Windows with PowerShell. The macOS, Linux, and WSL forms follow official documentation but have not yet been tested on those systems. If a step fails, keep your folder as it is and work through the table above; never reset your own folder to recover from an error.

Try it yourself

A contributor has .venv/ and .venv-old/ in a work folder. They install Django into .venv/ but run the helper with --python .venv-old. Predict what could happen and write the corrected execution command. Do this on paper; you do not need to create another environment.

Que. 3 Why can the helper fail even after a successful installation?

Show answerHide answer

Answer. Installation and execution selected different environments. The old one may lack Django or contain a different version. From the work folder, run uv run --no-project --python .venv check_environment.py, then check all four output items. Changing a prompt’s appearance does not establish which interpreter ran.

Before continuing, confirm Python 3.14.9, an executable inside this folder’s .venv, True for isolation, Django 6.1.2, and a successful dependency check. Keep check_environment.py for comparison when setup changes. There is still no manage.py, event app, or database schema in this folder.
