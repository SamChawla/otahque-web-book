How We Build It

Starting point: Chapter 4’s readiness checks and Chapter 5’s proposed design; no Django project exists. Begin in a directory where you keep your own work, outside the Chapter 4 practice folder. You need uv 0.13.5, managed CPython 3.14.9, an editor, a terminal, a browser, and internet access to download packages. These steps create otahque/ with .python-version, .venv/, check_environment.py, manage.py, and config/. The visible results are a passing system check and Django’s welcome page in your browser.

The Custom Way: a web answer by hand

Before Django generates anything, it helps to see the smallest possible Python web application. Read this listing; you do not need to run it, and it must not go into your project. It uses wsgiref, from Python’s standard library, to answer exactly one request:

illustration_only/hello_wsgi.py

from wsgiref.simple_server import make_server


def application(environ, start_response):
    start_response('200 OK', [('Content-Type', 'text/plain')])
    return [b'Hello from a hand-written WSGI app']


with make_server('127.0.0.1', 8000, application) as server:
    server.handle_request()

Run in a scratch folder, it answers one browser visit to http://127.0.0.1:8000/ with that line of text, prints a request log such as "GET / HTTP/1.1" 200 34, and exits. The function named application follows WSGI, the agreement between Python web applications and servers. Everything a real site needs is missing: matching different addresses, templates, a database, forms, security protections, and an error page. That is the work Django’s project files and development server do for us, which is why we generate them rather than write them.

The Django Way: generate and run the project

Step 1: Create a fresh work folder and environment

Open the terminal in your chosen work directory. On Windows, use PowerShell. On macOS, use your usual terminal shell; on Linux or WSL, use Bash. WSL is a separate Linux environment: follow the Linux commands there, with uv and Python installed inside WSL. These commands belong at a shell prompt, not at Python’s >>> prompt.

Check that no folder named otahque already exists here. If it does, inspect it before proceeding. Keep existing work and choose a fresh sibling folder such as otahque-learning instead; use that name in the next command. Do not nest this work inside an old project or reuse the Chapter 4 environment. In PowerShell, a macOS shell, or Linux/WSL Bash:

Terminal

mkdir otahque
cd otahque
uv --version
uv python pin 3.14.9
uv venv --python 3.14.9

The current directory is now otahque/. The version check should begin with uv 0.13.5; build details may follow. The pin command writes .python-version with 3.14.9. The venv command creates .venv/ using that Python and should report CPython 3.14.9. It may also suggest an activation command; you can ignore it. If these do not match, return to Chapter 4’s version checks before installing anything. A dot at the start of a name often hides it in a file manager; your editor can still open it.

Step 2: Install Django into the environment you name

In the same otahque/ directory, in PowerShell, a macOS shell, or Linux/WSL Bash:

Terminal

uv pip install --python .venv "Django==6.1.2"
uv run --no-project --python .venv python -m django --version

uv pip is uv’s package-installation interface; it does not require a pip program inside the environment. --python .venv selects the environment for installation and execution. uv run launches the command, and --no-project keeps uv from looking for a uv project’s dependency metadata. The installer reports Django and its supporting packages; download messages, timings, and dependency versions may differ, but the final version command must print 6.1.2. A warning that --no-project found no project is harmless here. python -m django asks the selected Python to run the django module, rather than trusting a standalone django-admin command found elsewhere on your computer.

Step 3: Check the interpreter as well as the package

Create check_environment.py beside .venv/, not inside it. This is a small verification helper, not a Django project file. Do not name it django.py, which would hide the package we want to import. It extends Chapter 4’s environment check with a Django import:

check_environment.py

"""Show which Python, environment, and Django run here."""
import sys

import django

print(sys.version.split()[0])
print(sys.executable)
print(sys.prefix != sys.base_prefix)
print(django.get_version())

The first line, in triple quotes, is a docstring: a short description that Python keeps with the module, and that editors and help() show. Every module in Otahque starts with one, following PEP 257, Python’s convention for docstrings. sys.version gives Python’s version text, and split()[0] selects its first part. sys.executable identifies the running interpreter. Different prefix and base_prefix values indicate a virtual environment. The import and get_version() then check the framework available to that same interpreter. Still in otahque/, in PowerShell, a macOS shell, or Linux/WSL Bash:

Terminal

uv run --no-project --python .venv check_environment.py
uv pip check --python .venv

The helper should print four items. The path line is a placeholder, because your absolute path will differ:

Output

3.14.9
[your otahque/.venv interpreter path]
True
6.1.2

On Windows, the path ends in .venv\Scripts\python.exe; on macOS and Linux it normally ends in .venv/bin/python. Check that it belongs to this otahque folder. uv pip check should report that installed packages are compatible. That check detects dependency problems; it does not verify Otahque’s product rules or security.

Step 4: Generate the project

Django’s startproject command writes the initial project files. config is the package name. The final dot means the current directory: put manage.py here and config/ inside this folder. Without an explicit destination, Django creates another outer directory named after the project, which would give us a different layout.

Check the folder first. If it already contains manage.py or config/, stop and inspect it rather than running the command again. Existing .venv/, .python-version, and the helper should remain in place.

PowerShell, in otahque/. The backtick continues the command onto the next line; put no spaces after it:

PowerShell

uv run --no-project --python .venv python -m django `
  startproject config .

macOS shell or Linux/WSL Bash, in otahque/. The backslash continues the command; put no spaces after it:

Terminal

uv run --no-project --python .venv python -m django \
  startproject config .

Choose the block for your shell and run it once. Successful generation normally returns to the prompt without a message. Inspect the files in your editor. This is the expected layout; the contents of .venv/ are omitted:

Folder structure

otahque/
    .python-version
    .venv/
    check_environment.py
    manage.py
    config/
        __init__.py
        settings.py
        urls.py
        asgi.py
        wsgi.py

The new files are manage.py and the five Python files inside config/. Opening or running Python can also produce __pycache__/ folders containing cached bytecode. Those are generated working files, not another Django app and not files to edit.

Common Error: forgetting the final dot

Without the final dot, Django creates an outer config/ folder containing manage.py and another config/ package. The otahque/ folder then has no manage.py, so the next command fails with “can’t open file”. If that happened, inspect the nested layout and compare it with the listing above; do not delete or move files blindly, and do not run startproject again over it.

Step 5: Check the generated configuration

manage.py is the new project’s command-line helper; as the Under the Hood box explained, it selects config.settings for us. In PowerShell, a macOS shell, or Linux/WSL Bash, still beside manage.py:

Terminal

uv run --no-project --python .venv python manage.py check

Expected result:

Output

System check identified no issues (0 silenced).

This check looks for common configuration problems. It does not open a browser, create account tables, or prove that future registration rules work. If Python cannot open manage.py, check the current directory. If Django cannot be imported, repeat Step 3.

In practice: making a repeatable starting structure

Situation. A second contributor wants the same project layout as Sam.

Application. Record the package name and destination as well as the framework version. The final dot explains why manage.py sits beside .venv/.

Consideration. Generation is a starting action, not a repair command. Repeating it over existing work can encounter conflicts; compare with a freshly generated copy instead, as shown in “When something goes wrong”.

Step 6: Read the generated files

Soni asks which file will eventually connect an event address to Python code. The generated project is small enough to answer by reading it. Open manage.py and the config/ files in your editor; change nothing in this step. Figure 6.2 maps them.

The empty config/__init__.py marks config as a regular Python package. The dot in config.settings means the settings module inside that package; it is not a file extension and is different from the destination dot in startproject.

config/settings.py is a Python module of configuration values. Some are strings or Booleans; others are lists and dictionaries, which you practised in Chapter 4. Table 6.2 shows what to notice now.

The generated settings enable Django’s admin, account, session, and other supporting apps. That does not mean Otahque’s event behaviour or account pages exist. Do not paste your SECRET_KEY into a public question or screenshot. The generated value begins with django-insecure- as a reminder that it suits local development only; a deployed system needs a different secret, kept out of shared code.

config/urls.py holds the root URL configuration from Chapter 5. Its urlpatterns list currently contains a route for Django’s built-in admin site, but no event route or Otahque home page yet; Chapter 9 adds our own routing. Do not try to create a superuser or visit the admin as this chapter’s check: it needs database tables we have deliberately not created.

config/wsgi.py and config/asgi.py each expose an object named application that a compatible server can call, the same shape as the Custom Way’s function. WSGI means Web Server Gateway Interface; ASGI means Asynchronous Server Gateway Interface, which also supports asynchronous interactions. They are alternative entry points, not two applications to start together. Django’s runserver uses the WSGI application. Leave both files unchanged; deployment comes much later.

Step 7: Run the development server and visit the page

In PowerShell, a macOS shell, or Linux/WSL Bash, in otahque/:

Terminal

uv run --no-project --python .venv python manage.py runserver

The console includes a system check, the migration warning, the framework version, and the listening address. The following is an excerpt with variable and lengthy output omitted, not a complete transcript:

Folder structure

System check identified no issues (0 silenced).
[Migration warning and timestamp omitted]
Django version 6.1.2, using settings 'config.settings'
Starting WSGI development server at http://127.0.0.1:8000/
[Stop instruction and production-server warning omitted]

With the server still running, enter http://127.0.0.1:8000/ in the browser’s address bar. Use http, not https, for this local exercise; the default local server has no TLS certificate. You should see Django’s successful-installation page with a rocket illustration. The page appears because this is an unmodified development URL configuration with DEBUG enabled. It is Django’s fallback welcome page, not an event template that we wrote, and it will change when we add our own routes. Django may create an empty db.sqlite3 while checking migration status; that does not mean any tables exist.

Look back at the terminal. A line for GET / with status 200 records the successful page request. Refreshing the browser makes another request. The browser may request other resources as well, so count the root-page entries rather than assuming one console line means one entire visit.

Que. 6 Does the welcome page prove that Sai can register for an event?

Flip to check your answerFold answer back

Answer. No. It verifies this local startup and request path. There are no Otahque event routes, templates, models, or registration rules yet. Our first Otahque page starts in Chapter 9, and registration arrives after the database and account work.

Step 8: Stop, observe, and restart

Return to the terminal running the server and press Ctrl+C. On Windows, Django’s startup message says CTRL-BREAK instead; Ctrl+C also stops the server in PowerShell. Wait for the shell prompt to return. Refresh the same browser address: a new request should now fail to connect. An already displayed page can remain on screen, so its presence alone does not prove that the server is running.

Run the same runserver command again, wait for the startup address, and refresh the browser. The welcome page should return. Stop the server again when you finish. Stopping the process does not remove the project or its environment. Django’s development server normally reloads when existing Python code changes; adding some new files may need a manual restart.

Common Error: exposing the development server

If a browser cannot connect, do not open firewall access or bind runserver to all network interfaces to make it work. It is a development convenience, not a production server. Keep its default loopback address, and check the address, the port, and that the server is still running.

Try it yourself

Complete one start, visit, stop, refresh, and restart cycle. Write down the address, the root request’s status while running, and what changes after stopping. Keep the migration warning unresolved, and explain why that is intentional here.

Que. 7 What evidence should the cycle produce?

Flip to check your answerFold answer back

Answer. While the process runs, http://127.0.0.1:8000/ shows Django’s welcome page and the terminal records GET / with 200. After Ctrl+C returns the prompt, a fresh request cannot connect to that stopped server. Restarting restores the page. Unapplied migrations remain expected because we have not configured the custom user or created tables.

When something goes wrong

Raj follows the startup instructions but his browser cannot connect. Reinstalling everything would discard useful clues. Ask instead which step last worked: finding the files, importing Django, loading the configuration, listening on a port, or making the browser request. Table 6.3 covers setup, and Table 6.4 covers startup.

These commands were tested on Windows with PowerShell. The macOS, Linux, and WSL forms follow official documentation but have not yet been tested on those systems. If a step fails, keep your folder as it is and work through the tables; never reset your own folder to recover from an error.

Use another port without disturbing a listener

If you cannot identify an existing listener, leave it alone. Do not end an unknown process or relax security settings to clear the error. For a controlled alternative, start our project on port 8001 after ensuring your own earlier server is stopped. PowerShell:

PowerShell

uv run --no-project --python .venv python manage.py `
  runserver 8001

macOS shell or Linux/WSL Bash:

Terminal

uv run --no-project --python .venv python manage.py \
  runserver 8001

Visit http://127.0.0.1:8001/ and expect the same Django welcome page. If 8001 is also occupied, inspect your open terminals and choose a known free port. Stop the server you started when the check is complete. The port argument does not change project files or apply migrations.

Que. 8 You start on 8001 but refresh the page on 8000. What have you tested?

Flip to check your answerFold answer back

Compare with a fresh copy when needed

If you think a generated file was changed by accident and the error alone does not show what changed, generate a fresh copy and compare that one file. You need this only when something has gone wrong; from Chapter 8, Git will show such changes directly. The commands run startproject in a new, empty sibling folder, so they do not touch your project. If you named your work folder otahque-learning, use that name in place of otahque. PowerShell, starting in otahque/:

PowerShell

cd ..
mkdir otahque-compare
cd otahque-compare
uv run --no-project --python ../otahque/.venv `

In practice: asking for help with evidence

Situation. Raj reports that the project works in one terminal but not another.

Application. Compare a startup record from both: working directory, interpreter, Django version, check result, and listening URL. The earliest difference is a concrete lead.

Consideration. Exclude your secret key and unrelated private paths when sharing the record. A successful system check does not prove future features; from Chapter 9, each new page behaviour also gains an automated test.
