6.4 Open the development page

Sam can now ask the project to answer a real browser request. The result will be Django’s development welcome page. It is a small but useful result: Python can load the project, a local server can listen, and a browser can receive its response.

Starting point: Sections 6.1–6.3, with the environment and system check passing. Work in otahque/, beside manage.py. You need a browser and a free local port. No source files change. You will start, visit, stop, and restart the server; Django may create a local db.sqlite3 file while checking migration status, but we will not apply any migrations.

Run a server on your own computer

PowerShell, macOS shell, or Linux/WSL Bash, in otahque/:

uv run --no-project --python .venv python manage.py runserver

runserver starts Django’s development web server, which by default listens on 127.0.0.1 at port 8000. The address 127.0.0.1 is loopback: it refers to this computer. A port distinguishes one listening service from another at an address. The terminal stays occupied while the server runs; it has not frozen merely because the prompt does not return.

The console includes a system check, a warning about unapplied migrations, the framework version, and the listening address. The following is an excerpt with variable and lengthy output explicitly omitted, not a complete transcript:

System check identified no issues (0 silenced).
[Migration warning and timestamp omitted]
Django version 6.1.2, using settings 'config.settings'
Starting WSGI development server at http://127.0.0.1:8000/
[Stop instruction and production-server warning omitted]

A migration is a recorded database change, such as creating tables for an app. The warning is expected because the generated project enables apps whose tables have not been created. Leave those migrations unapplied in this chapter. We must choose and configure Otahque’s custom user model in Chapter 17 before the first migration is applied. Running a command suggested by the warning now would jump ahead of that decision.

This deferral is specific to the fresh development page, which does not need account tables. It is not advice to ignore migration warnings in an application that needs its database. The presence of db.sqlite3 alone does not establish that any tables or registrations exist. Do not delete a database as a generic way to silence the warning.

Visit the exact address

With the server still running, enter http://127.0.0.1:8000/ in the browser’s address bar. Use http, not https, for this local exercise. The proposed HTTPS connection in Chapter 5 describes the eventual secure site; the default local server has no TLS certificate configured. Secure public hosting is a later task.

You should see Django’s successful-installation page with a rocket illustration. Read its success message and confirm the address bar. The page appears because this is an unmodified development URL configuration with DEBUG enabled. It is Django’s fallback welcome page, not an event template that we wrote. It will change when we add our own routes.

Look back at the terminal. A line for GET / with status 200 records the successful page request. Refreshing the browser makes another request. The browser may request other resources as well, so count the root-page entries rather than assuming one console line means one entire visit.

Que. 8 Does the welcome page prove that Sai can register for an event?

Show answerHide answer

Answer. No. It verifies this local startup and request path. There are no Otahque event routes, templates, models, or registration rules yet. Our first Otahque page starts in Chapter 9, and registration arrives after the database and account work.

Stop, observe, and restart

Return to the terminal running the server and press Ctrl+C. On Windows, Django’s startup message says CTRL-BREAK instead; Ctrl+C also stops the server in PowerShell. Wait for the shell prompt to return. Refresh the same browser address: a new request should now fail to connect. An already displayed page can remain on screen, so its presence alone does not prove that the server is running. Browser error wording varies.

Run the same runserver command again, wait for the startup address, and refresh the browser. The welcome page should return. Stop the server again when you finish this exercise. Stopping the process does not remove the project or its environment. The next startup uses those same files.

Django’s development server normally reloads when existing Python code changes. Adding some new files may require a manual restart. We will not depend on reload behaviour to explain an error: first read the terminal and confirm which server and address you are using.

Que. 9 Should you use runserver to make Otahque available to the public?

Show answerHide answer

Answer. No. It is a development convenience, not a production server. Keep its default loopback address for this exercise. Do not open firewall access or bind it to all network interfaces to fix a local browser error. Production serving, certificates, and deployment checks come later.

In practice: separating a running process from saved files

Situation. Soni can still see a welcome page after Sam stops the server.

Application. Refresh the address and watch for a new request in the server terminal. Saved source files persist; the process that answers requests exists only while it is running.

Consideration. An old page or another server can mislead. Match the address and port to the startup message, especially when more than one local project is open.

Try it yourself

Complete one start–visit–stop–refresh–restart cycle. Write down the address, the root request’s status while running, and what changes after stopping. Keep the migration warning unresolved; explain why that is intentional here.

Que. 10 What evidence should the cycle produce?

Show answerHide answer

Answer. While the process runs, http://127.0.0.1:8000/ shows Django’s welcome page and the terminal records GET / with 200. After Ctrl+C returns the prompt, a fresh request cannot connect to that stopped server. Restarting restores the page. Unapplied migrations remain expected because we have not configured the custom user or created tables.
