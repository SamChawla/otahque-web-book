Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead to a larger application with a team: attempt them now, and return to them after Chapters 32 and 64. They are extension questions, not a gate to the next chapter. Each code proof is a short file in the practice folder that starts by importing Chapter 16’s setup_django.py; run it from the folder that holds manage.py with uv run python ../practice/ followed by the file name. The proofs read your rows and roll back anything they try, so your data stays as it is.

L1 (Junior): What is the difference between validation and a database constraint in Django?

What the interviewer is testing: Do you know where each kind of rule runs, and which one actually guarantees the data?

Flip to check your answerFold answer back

Perfect answer: Validation is Python code that checks an object and raises ValidationError with messages: field validators, choices and max_length, the model’s clean(), and, since Django 4.1, the model’s constraints, all run by full_clean(). It runs only when something calls it: forms and the admin do, but save(), update(), and bulk_create() do not. A database constraint, such as a CheckConstraint or UniqueConstraint in Meta.constraints, is part of the table, so the database refuses every write that breaks it, from any code, and Django raises IntegrityError. I use a constraint for every rule the database can express, because it is the only guarantee, and validation, including a violation_error_message on each constraint, to explain problems to people before saving. Rules the database cannot express, such as “a real time-zone name”, stay validators, and I remember that they protect only callers that validate.

Behind the scenes:

validation and constraints (summary)

full_clean() -> fields, clean(), unique, constraints
save()       -> no validation; database rules apply
update()     -> no save(), no validation; rules apply
constraint   -> refused write: IntegrityError

Code proof: the same broken rule, asked of both:

../practice/l1_layers.py

import setup_django
from django.core.exceptions import ValidationError
from django.db import IntegrityError, transaction

from events.models import Event

event = Event.objects.get(title='Spring planning')
event.capacity = 0
try:
    event.full_clean()
except ValidationError as error:
    print('validation:', error.messages)
try:
    with transaction.atomic():
        Event.objects.filter(pk=event.pk).update(capacity=0)
except IntegrityError as error:
    print('database:', error)

Output

validation: ['Capacity must be more than 0.']
database: CHECK constraint failed: event_capacity_gt_0

full_clean() explains the rule with the constraint’s message, before writing. update() skips validation, and the database refuses the write; the atomic() block keeps the failed statement from affecting anything else.

Common mistakes:

  • Believing that save() validates, or that choices restricts what the database stores.
  • Showing IntegrityError text to members instead of a message from validation.
  • Making a validator the only guard for a rule the database could hold.

Follow-up the interviewer might ask:

  • “Which of save(), update(), and bulk_create() call full_clean()?”
  • “Where would you catch IntegrityError in a view, and what would you show the member?”

L2 (Mid-Level): Why does save() not call full_clean(), and when should your code call it?

What the interviewer is testing: Do you understand the cost and the order of model validation, and who is responsible for calling it?

Flip to check your answerFold answer back

Perfect answer: Validation costs work: validate_unique() and validate_constraints() query the database, and validators can be slow. Django leaves the decision to the caller, so code that saves trusted data in bulk does not pay for it. full_clean() runs clean_fields(), then clean(), then validate_unique(), then validate_constraints(), and collects every error into one ValidationError whose message_dict maps each field, or __all__ for the whole row, to its messages. A field that already failed is excluded from the later checks that use it. Forms and the admin site call it for me. My own code should call it whenever data comes from a person or an outside source: an import, an API payload, a management command. Code that builds rows from values it controls can rely on the constraints. Because clean() may change values, such as lower-casing an email, I call full_clean() before save(), not after.

Behind the scenes:

full_clean() (summary)

clean_fields()         -> each value, validators
clean()                -> the row as a whole
validate_unique()      -> unique fields (query)
validate_constraints() -> Meta.constraints (query)
all errors             -> one ValidationError

Code proof: one unsaved event with three problems, and the same values saved without validation, then rolled back:

../practice/l2_full_clean.py

from datetime import UTC, datetime

import setup_django
from django.core.exceptions import ValidationError
from django.db import transaction

from events.models import Event

fields = dict(title='', location='Leeds', capacity=0,
              starts_at=datetime(2027, 2, 1, tzinfo=UTC),
              ends_at=datetime(2027, 2, 1, 2, tzinfo=UTC),
              timezone='Europe/Londn')
try:
    Event(**fields).full_clean()
except ValidationError as error:
    print(sorted(error.message_dict))
with transaction.atomic():
    unchecked = Event(**dict(fields, capacity=5))
    unchecked.save()
    print('saved without validation:', unchecked.pk > 0)
    transaction.set_rollback(True)
print(Event.objects.filter(location='Leeds').count())

Output

['__all__', 'timezone', 'title']
saved without validation: True
0

The blank title and the time zone are field errors, and the capacity rule is a constraint error under __all__, all in one exception. With a valid capacity, save() stores the blank title and the misspelt time zone without complaint, until the rollback removes the row.

Common mistakes:

  • Calling full_clean() after save(), so its corrections never reach the database.
  • Expecting full_clean() to stop at the first error.
  • Raising errors in clean() for a field a form does not show, which Django reports as a ValueError.

Follow-up the interviewer might ask:

  • “How would you validate ten thousand imported rows efficiently?”
  • “What does the exclude argument of full_clean() do, and who uses it?”

L3 (Senior): How do you enforce “one active registration per member and event” without forbidding a new registration after a cancellation?

What the interviewer is testing: Can you choose the right kind of uniqueness, and explain why application checks are not enough?

Flip to check your answerFold answer back

Perfect answer: A check in the view, “is there an active registration? if not, create one”, has a gap between the check and the insert, and two simultaneous requests both pass it. So the rule must live in the database. A plain unique constraint on event and member would also refuse re-registering, because cancelled rows keep the same pair. The answer is a conditional UniqueConstraint(fields=['event', 'member'], condition=Q(status='active'), name=...), which PostgreSQL and SQLite build as a partial unique index holding only active rows. I give it a violation_error_message, so validation explains the duplicate, and I still handle IntegrityError in the view for the race the check cannot see. Tests prove both halves: a second active registration raises IntegrityError, and a registration after a cancellation succeeds. MySQL and MariaDB do not support conditions on unique constraints, so on those databases I would need another design, such as a nullable column that is unique only while active.

Behind the scenes:

conditional uniqueness (summary)

UniqueConstraint(fields=['event', 'member'],
                 condition=Q(status='active'))
-> CREATE UNIQUE INDEX ... WHERE status = 'active'
cancelled rows -> outside the index
two active     -> IntegrityError

Code proof: the index as SQLite stores it, and a re-registration after a cancellation, rolled back:

../practice/l3_partial.py

import setup_django
from django.db import connection, transaction
from django.utils import timezone

from registrations.models import Registration

with connection.cursor() as cursor:
    cursor.execute(
        'SELECT sql FROM sqlite_master WHERE name = %s',
        ['registration_one_active'],
    )
    (sql,) = cursor.fetchone()
print('WHERE', sql.split(' WHERE ')[1])
place = Registration.objects.filter(status='active')[0]
with transaction.atomic():
    place.status = 'cancelled'
    place.cancelled_at = timezone.now()
    place.save()
    Registration.objects.create(event=place.event,
                                member=place.member)
    print('registered again:', place.event)
    transaction.set_rollback(True)

Output

WHERE "status" = 'active'
registered again: Python meetup

sqlite_master is SQLite’s own table of tables and indexes, and holds the CREATE UNIQUE INDEX statement with its WHERE clause. Cancelling a place and registering again succeeds, and the rollback restores the original row.

Common mistakes:

  • Using unique_together, which blocks re-registration after a cancellation.
  • Relying on an exists() check in the view.
  • Forgetting that the same pattern fits organizer assignments, with revoked_at__isnull=True.

Follow-up the interviewer might ask:

  • “What does the member see if two clicks race, and where is that handled?”
  • “How would you enforce the same rule on MySQL?”

L4 (Staff): You must add a constraint to a large production table that already holds rows breaking it. How do you roll it out?

What the interviewer is testing: Can you change a live schema without an outage, a failed deploy, or silently lost data? This looks ahead to Chapters 32 and 64.

Flip to check your answerFold answer back

Perfect answer: First I measure: a query that counts the rows breaking the rule, using the constraint’s own condition, tells me how big the problem is. Then I stop new bad rows at the source, by deploying validation and fixing the code paths that create them, so the count stops growing. Next comes the data fix, decided with the people who own the data: correct, cancel, or delete each kind of row, in a reviewed, reversible data migration or command, never by hand in production. Only then do I add the constraint. On SQLite, Django rebuilds the table, which is fine for a small database. On PostgreSQL, adding a CHECK scans the whole table while holding a lock; for a large table I add it as NOT VALID, which checks only new writes, and run VALIDATE CONSTRAINT afterwards, which checks old rows without blocking writes. A unique index can be built with CREATE INDEX CONCURRENTLY. Chapter 64 covers these zero-downtime patterns. After release, I watch for IntegrityError in the logs: it shows a path I missed.

Behind the scenes:

rollout (summary)

count  -> exclude(constraint.condition).count()
stop   -> validation and code fixes first
fix    -> reviewed data migration
add    -> PostgreSQL: NOT VALID, then VALIDATE
watch  -> IntegrityError in the logs

Code proof: every CheckConstraint on Event, used to count the rows that would break it:

../practice/l4_audit.py

import setup_django
from django.db.models import CheckConstraint

from events.models import Event

for constraint in Event._meta.constraints:
    if isinstance(constraint, CheckConstraint):
        broken = Event.objects.exclude(constraint.condition)
        print(constraint.name, broken.count())

Output

event_capacity_gt_0 0
event_ends_after_start 0
event_status_valid 0

_meta.constraints is the model’s list of constraints, and each CheckConstraint keeps its condition as a Q object, so exclude() finds the rows outside it. All three counts are 0 now; before Step 6’s fixes, the first would have been 1.

Common mistakes:

  • Adding the constraint first and discovering the bad rows when the deploy fails.
  • Fixing production rows by hand, with no record or review.
  • Locking a busy table for minutes with a plain ADD CONSTRAINT on PostgreSQL.

Follow-up the interviewer might ask:

  • “How would you make the data fix reversible?”
  • “What does NOT VALID guarantee before VALIDATE runs?”

L5 (Lead): Design email identity for an international product. What does “the same address” mean, and where do you enforce it?

What the interviewer is testing: Can you turn a vague identity question into a product decision, and know the limits of the tools that enforce it? This looks ahead to Chapters 27 and 32.

Flip to check your answerFold answer back

Perfect answer: “The same address” is a product decision, not a technical default. Domains are case-insensitive, and the local part before @ is case-sensitive in principle but treated as case-insensitive by nearly every provider, so most products treat addresses that differ only in case as one identity. I decide whether to store addresses as typed and compare them case-insensitively, or to store a normalized form; Otahque stores lower case. Then I enforce it everywhere: one normalization function in the user manager, used for creation and for the sign-in lookup; normalization in clean() for forms; and a database constraint for writes that skip both. International addresses need more care. Python’s lower() handles every alphabet, but SQLite’s LOWER() changes only A to Z, so a SQLite constraint misses É, while PostgreSQL’s lower() handles it. Some letters have no simple lower-case pair, such as German ß, where casefold() gives ss, and visually identical characters can have different Unicode codes, so I would also normalize to one Unicode form and decide whether such addresses may register at all. I record the decision, and test sign-up, sign-in, and imports against it.

Behind the scenes:

email identity (summary)

decide    -> same address = same member
normalize -> manager: create_user(), sign-in lookup
validate  -> clean() for forms
enforce   -> CHECK email = LOWER(email)
limits    -> SQLite LOWER(): A to Z only

Code proof: the same address lower-cased by SQLite and by Python:

../practice/l5_lower.py

import setup_django
from django.db import connection

address = 'ÉMILE@EXAMPLE.ORG'
with connection.cursor() as cursor:
    cursor.execute('SELECT LOWER(%s)', [address])
    print('SQLite:', cursor.fetchone()[0])
print('Python:', address.lower())
print('Straße:', 'Straße'.lower(), 'Straße'.casefold())

Output

SQLite: Émile@example.org
Python: émile@example.org
Straße: straße strasse

SQLite leaves É in capitals, so a direct write of Émile@example.org would pass Otahque’s constraint on SQLite; the manager’s Python lower() handles it. casefold() is Python’s stronger comparison form, which turns ß into ss.

Common mistakes:

  • Normalizing at sign-up but not at sign-in, so a member cannot sign in with capitals.
  • Assuming the database’s LOWER() matches Python’s lower().
  • Treating the decision as a technical detail instead of recording it.

Follow-up the interviewer might ask:

  • “Would you store the address as typed as well, for display?”
  • “How do you migrate existing accounts that collide after normalization?”
