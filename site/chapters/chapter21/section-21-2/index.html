What You Need to Know

Three places a rule can live

Chapter 16 met validation once: full_clean() refused the status 'archived' because it is not one of the field’s choices. Chapter 19 then saved exactly that row with save(), and the database stored it. Both results were correct, and the difference between them is the subject of this chapter.

New Concept: validation and database constraints

What problem exists? A rule such as “capacity is more than 0” must hold for every event, however the row is written. Rows reach the table through forms, the shell, the admin site, scripts, and bulk operations that never create a model object.

What did people do before? They checked values in each place that wrote rows, with if statements before saving. Each new way of writing data needed the same checks again, and the one that forgot let bad rows in.

What are they? Validation is Python code that inspects an object before it is saved and raises ValidationError with messages. Django has three kinds: a validator on a field checks one value; Model.clean() checks several fields of one row together; and full_clean() runs them all. A database constraint is a rule written into the table’s definition, such as CHECK ("capacity" > 0). The database refuses any INSERT or UPDATE that breaks it, and Django raises IntegrityError.

Why both? Validation runs only when code calls it, but it can explain a problem to a person. A constraint runs on every write, but its error is meant for programmers. Otahque uses constraints as the guarantee and validation as the explanation.

Now let’s use it. Step 2 shows a row that passes full_clean() and is saved anyway, and Steps 4 to 7 close each gap.

Table 21.1 compares the three places. The first two are Python; the third is the database.

What full_clean() runs, and what save() does not

full_clean() runs four stages, in this order, and collects every error before it raises one ValidationError:

  • clean_fields() checks each field: required values, max_length, choices, and the field’s validators;
  • clean() checks the row as a whole, and may also tidy values, such as lower-casing an email;
  • validate_unique() checks unique=True fields, such as the member’s email, by asking the database;
  • validate_constraints() checks the rules in the model’s Meta.constraints, also by asking the database.

save() runs none of them. Django’s documentation states it plainly: full_clean() is not called automatically when you call save(). Querysets go further: update() and bulk_create() write rows without calling save() at all. Forms, from Chapter 24, call full_clean() for you; most other code does not.

Under the Hood: why save() does not validate

Validation can be expensive. validate_unique() and validate_constraints() each run database queries, and a validator such as this chapter’s time-zone check reads a list of about six hundred names. Code that saves thousands of rows from a trusted source, or saves one field after changing it, would pay that cost on every call. So Django leaves the decision to the caller: forms and the admin site validate, because people type into them, and other code calls full_clean() when it needs to. A side effect is that a rule enforced only by validation is enforced only where someone remembered to call it. That is why each Otahque rule that the database can express also becomes a constraint. Constraints joined model validation in Django 4.1: since then, full_clean() asks the database whether a row would break any rule in Meta.constraints, so the same rule produces a friendly ValidationError before saving and a hard IntegrityError if someone saves without asking. Older articles that say constraints are never part of full_clean() describe Django before 4.1.

A model’s clean() method is where a rule about several fields goes when it cannot, or should not, be a constraint. This example is for reading only; Otahque does not need it yet. It raises an error attached to a field by passing a dictionary:

illustration only (not part of the project)

def clean(self):
    if self.status == 'published' and not self.location:
        raise ValidationError(
            {'location': 'A published event needs a place.'}
        )

Answer. Only the status. clean_fields() checks choices, so 'archived' fails, but a capacity of 0 is a valid PositiveIntegerField value, because that field allows zero. save() accepted both because it does not call full_clean(), and the table had no rule about either column yet.

Database constraints in Django

Django writes a constraint for you from a line in the model’s Meta class, and makemigrations turns it into SQL.

New Tool: CheckConstraint and UniqueConstraint

What problem exists? Rules must reach the table’s definition, and change with the models, through migrations like everything else in the schema.

What did people do before? They wrote ALTER TABLE ... ADD CONSTRAINT in SQL by hand, outside the project’s migrations, so the rules and the models could drift apart.

What are they? Two classes listed in Meta.constraints. models.CheckConstraint(condition=..., name=...) becomes a CHECK: every row must satisfy the condition. models.UniqueConstraint(fields=[...], name=...) makes a combination of columns unique. Given a condition= as well, it is conditional: the uniqueness applies only to rows that match the condition, which is exactly “at most one active registration per member and event”. Each constraint needs a name, unique in the database, and may have a violation_error_message, the text full_clean() shows.

Why use them? The rule lives beside the fields it protects, makemigrations writes the SQL, sqlmigrate shows it, and full_clean() can check it before saving.

Now let’s use it. Steps 4 and 5 add six constraints, and Step 7 adds the seventh.

A condition is written with models.Q, a Q object: a filter condition, in the same double-underscore lookup syntax as filter(), kept as a value. Q(capacity__gt=0) reads “capacity greater than 0”, and Q(status='active', cancelled_at__isnull=True) reads “active, with no cancellation time”: both parts must hold. The | operator means “or”: Q(a) | Q(b) holds when either does. One rule compares two fields of the same row: an event must end after it starts. models.F('starts_at'), an F expression, names another column of the same row, so Q(ends_at__gt=models.F('starts_at')) reads “the end is later than the start”, and the database compares the two values itself. That is all this chapter needs. Chapter 22 combines Q objects in queries, with &, |, and ~, and uses F in queries and audits.

Table 21.2 lists every rule this chapter adds and where it lives. The time zone is the exception: no SQL condition can know the list of real time-zone names, so it stays a validator.

How the three places sit on the paths a row can take to its table is drawn in Figure 21.1.

One rule for some rows: a conditional unique constraint

Sai may cancel her place at the meetup and register again later. Her cancelled registration stays, because Chapter 2’s rules keep cancellations as history, so a plain unique rule on event and member would refuse her second registration. The conditional constraint builds an index that holds only active rows: cancelled rows are outside it, and a second active row for the same event and member collides with the first, as Figure 21.2 shows.

Under the Hood: what the constraints become in SQLite

A UniqueConstraint with a condition is not written as a table constraint. Django creates a partial index: CREATE UNIQUE INDEX "registration_one_active" ON "registrations_registration" ("event_id", "member_id") WHERE "status" = 'active'. The database keeps the index up to date on every write, and a write that would put a second entry for one pair into it fails. A CheckConstraint is part of the table’s definition. SQLite cannot add a CHECK to an existing table, so Django rebuilds the table: it creates new__registrations_registration with the rule, copies every row across, drops the old table, renames the new one, and recreates its indexes. Every row is copied, so one row that breaks the rule stops the whole migration, which is why Step 6 checks the data first. Two details from earlier chapters show up in the same SQL. PositiveIntegerField already writes CHECK ("capacity" >= 0), which allows zero; this chapter’s rule makes it > 0. And choices writes nothing at all: the database never knew the status list until now. On PostgreSQL, from Chapter 32, Django adds a constraint with ALTER TABLE instead of rebuilding.

IntegrityError and ValidationError

The same broken rule can reach you as two different errors, depending on how the row was written.

Prefer a constraint, a validator, or both?

If the database can express the rule, make it a constraint: nothing else covers update(), the shell, and every future script. Then give it a violation_error_message, so that full_clean(), and the forms that call it from Chapter 24, explain the rule in words a member understands, before the database has to refuse anything. If the database cannot express the rule, such as “this is a real time-zone name”, use a validator, and remember that it protects only code that validates. Django’s default message, Constraint “registration_one_active” is violated., is written for programmers; this chapter replaces it on every constraint.

IntegrityError comes from the database, during save(), create(), update(), or a migration. It means the write did not happen. ValidationError comes from Python, during full_clean(), before anything is written; its messages list the problems. A program should treat IntegrityError as the last line of defence, not as the normal way of telling a member that they are already registered.

Why a check in Python is not enough

Chapter 20 asked why a check in Python code alone cannot stop Sai’s second active registration. Imagine Otahque’s register view doing the obvious thing: look for an active registration for Sai and the meetup, and create one if there is none. Sai double-clicks. Two requests arrive a few milliseconds apart and are handled at the same time. Figure 21.3 follows them.

Each request checks before either one writes, so both checks pass, and both insert. No amount of checking in Python fixes this, because the gap between checking and writing is always there. The database closes it: it applies the unique index to each write as the write happens, one at a time, so the second insert fails whatever either request believed. The Custom Way in How We Build It plays this out with two calls. The harder version of the race, two members competing for the last place in a full event, involves counting rows rather than one pair, and needs a transaction and a lock; Chapter 33 builds it on PostgreSQL.

Email letter case: the decision

Chapter 17 left a product question for this chapter: are two addresses that differ only in capital letters one member? Mail systems treat the part after @ as case-insensitive. The part before it is case-sensitive in principle, but in practice almost every provider delivers Sai@example.org and sai@example.org to the same mailbox, and people type capitals by accident. If Otahque treated them as different, Sai could create a second account by mistake, and sign-in would fail when she typed her address differently.

Three options were considered: compare addresses without regard to case but store them as typed; store every address in lower case; or keep exact matching and accept duplicate accounts. Otahque’s decision, recorded in this chapter, is the second: every email address is stored in lower case. Three places carry it. The user manager lower-cases the whole address in create_user(), and in the lookup that sign-in uses. The model’s clean() lower-cases it during validation. And a CheckConstraint refuses any row whose email differs from its lower-case form, so a script that saves Sai@example.org directly is refused. Because the stored form is always lower case, Chapter 17’s unique=True on the email now treats Sai@Example.org and sai@example.org as the same address.

Two consequences come with the decision. The address a member sees on their account is lower-cased, even if they typed capitals. And SQLite’s LOWER() function changes only the letters A to Z, so on SQLite the constraint cannot catch an uppercase letter such as É that a script saves directly; Python’s lower() in the manager and clean() does handle it. PostgreSQL, from Chapter 32, lower-cases every letter. The L5 interview question returns to this.

In practice: importing events from a spreadsheet

Situation. Sam keeps last year’s events in a spreadsheet and wants them in Otahque. A script reads each row and creates an event with Event.objects.create(), or with bulk_create() for speed.

Application. Neither call validates, so a blank capacity cell read as 0, or a misspelt time zone, would be stored. With this chapter’s constraints, the capacity row is refused with an IntegrityError that names event_capacity_gt_0. A careful import script also calls full_clean() on each object first, so it can report every bad row with its line number before writing any.

Consideration. The time-zone rule is a validator, so only the script’s full_clean() call catches it. Chapter 41 builds Otahque’s import commands, and decides how a partly bad file is reported.
