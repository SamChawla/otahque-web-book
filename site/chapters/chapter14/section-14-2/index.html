What You Need to Know

From hand-written CSS to a design system

Chapter 13’s stylesheet is about sixty lines, and every colour in it is typed as a value. That is fine for three pages. As pages grow, teams usually combine four kinds of styling, and Table 14.1 compares them.

A token is a named design decision, such as “the primary colour is #0759ce”. Rules refer to the name, so changing the value in one place changes every use. The best names describe a role, what the value is for, rather than what it looks like: primary for links and main actions, neutral for the navigation, base-200 for the page behind the cards. Chapter 13 gave the same advice for class names: event-row stays true when the colours change, and blue-box does not.

New Tool: Node.js and npm

What problem exists? The Tailwind compiler and the daisyUI plugin are written in JavaScript. Something has to run them, and something has to install exact versions of both and record them.

What did people do before? They linked a framework’s stylesheet from a content delivery network (CDN) at an address whose contents could change, or downloaded files by hand and lost track of which version they had.

What are Node.js and npm? Node.js runs JavaScript outside a browser. npm, which comes with it, installs the packages that a project’s package.json lists into a node_modules folder, and records the exact versions it installed in package-lock.json.

Why use them? It is the arrangement uv gave us in Chapter 8: a project file says what we need, a lockfile pins what was installed, and a clean install reproduces it on any computer. Django never runs Node. It only serves the file that Node’s tools produce.

Now let’s use it.

Table 14.2 sets the two side by side. They stay separate: uv manages Python and Django, npm manages only the CSS build tools, and neither file mentions the other’s packages.

New Tool: Tailwind CSS

What problem exists? Writing a rule for every combination of spacing and colour makes a stylesheet grow and drift. Loading a whole prebuilt framework stylesheet sends thousands of rules that no page uses.

What did people do before? They grew hand-written sheets, as in Chapter 13, or linked a complete framework stylesheet such as Bootstrap and overrode the parts they did not want.

What is Tailwind CSS? A CSS compiler, version 4.3.4 in this book. It reads one input stylesheet and the files that input names as sources, finds the class names written in them, and writes one output stylesheet. The output has a rule for each Tailwind class it found, a reset that comes first, and anything else written in the input.

Why Tailwind? The output holds only what the pages use, and the class names follow a fixed scale: p-4 is always 1rem of padding and p-6 is always 1.5rem, so spacing stays consistent without anyone remembering numbers.

Now let’s use it.

Here is the class list the layout’s main element will carry at the end of this chapter. Read it as five small instructions:

HTML

<main class="mx-auto max-w-2xl space-y-4 px-4 pt-6 pb-12">

mx-auto centres the element with automatic side margins. max-w-2xl limits its width to 42rem. space-y-4 puts 1rem of space between each pair of children. px-4 adds 1rem of padding at the left and right, and pt-6 and pb-12 add 1.5rem above and 3rem below. Each class is one declaration you already know from Chapter 13, given a short name. The browser never sees the name mx-auto as anything special: it is an ordinary class selector in the compiled file.

Tailwind 4 writes CSS for current browsers: Chrome 111, Safari 16.4, and Firefox 128, or later. Older browsers may ignore some rules. That boundary comes with the tool, so we state it rather than promise more.

New Concept: utility, component, and semantic classes

What problem exists? Each style decision has to live somewhere: in the stylesheet under a name, or in the template beside the element it affects.

What did people do before? Chapter 13 put every decision in the stylesheet under an invented name, such as event-row. Each new variation needed another name and another rule.

What are the three kinds? A utility class does one job, such as p-4. A component class names a familiar piece with several declarations behind it, such as navbar or card. A semantic class is our own name for an Otahque idea, such as sample-label, with its rule in our source.

Why mix them? Utilities suit layout and spacing on one element. Components suit pieces that repeat with the same structure. Semantic classes suit Otahque’s own meanings, and elements we cannot or should not put utilities on.

Now let’s use it.

A row in the event list will combine all three: event-row names what the element is, card is the component, and border border-base-300 bg-base-100 p-4 adjust it. Keeping the semantic name costs nothing and tells the next reader, and the tests, what the element is for.

Preflight: the reset that comes first

Browsers start every page with their own default styles, and they do not all agree. Tailwind’s output therefore begins with Preflight, a reset that removes those defaults so that every browser starts the same. It removes margins, makes headings the same size and weight as body text, removes list bullets, and makes links take their colour from the surrounding text, with no underline.

That last change matters. Chapter 13’s links were blue and underlined because the browser’s defaults made them so, and our stylesheet only changed the blue. After the first build, links would look exactly like the text around them. We restore what we need on purpose: headings get a size again, and links get the primary colour and an underline.

The underline is not decoration. Our link blue against the dark body text measures 2.40:1, below the 3:1 that WCAG 2.2 expects when colour alone tells a link apart from the words around it (Success Criterion 1.4.1, Use of Color). The underline marks a link for everyone, whatever colours they can see.

daisyUI: components and a theme

New Tool: daisyUI

What problem exists? With utilities alone, every navigation bar or card repeats the same long list of classes, and the colours they use need names that every page shares.

What did people do before? They copied class lists between templates, or wrote component rules by hand and invented their own colour names.

What is daisyUI? A plugin for Tailwind, version 5.7.50 here. It adds component classes such as navbar, card, and btn, and themes: sets of colour variables with fixed role names, such as --color-primary. It is CSS only, with no JavaScript.

Why daisyUI? A short, readable vocabulary for common pieces, whose colours all come from the theme. Change a role’s value once, and every component that uses the role follows.

Now let’s use it.

We define one light theme named otahque, using the colours measured in Chapter 13. It is a proposal for this stage of the book, not a final brand. Table 14.3 lists its roles. The contrast ratios were calculated with the WCAG 2.2 formula; the requirement is at least 4.5:1 for normal text and at least 3:1 for a focus indicator against the colours beside it.

Two things are deliberately missing from the table. daisyUI has no role for keyboard focus, so focus stays an ordinary :focus-visible rule in our source: a 3-pixel outline in the primary colour, and white inside the navigation. And the orange of the Sample: label, #9d480c (6.24:1 on cards, 5.76:1 on the page), stays in its own rule, because only one element uses it. Figure 14.1 shows which part of each page takes which role.

Each theme variable also becomes a family of utilities. Because the theme defines --color-neutral, the class bg-neutral sets a navy background and text-neutral-content sets white text. Tailwind has its own way to define tokens, an @theme block, which also creates utilities; daisyUI’s theme does that job for our colours, so we do not need one yet. An ordinary CSS variable that you declare yourself can be used in a rule with var(), but it creates no utility class.

Layers decide which rule wins

Chapter 13’s cascade compared origin and importance, then specificity, then order. Cascade layers add a step before specificity: when two rules from the same stylesheet conflict, the one in the later layer wins, however specific the other is. Tailwind declares four layers in this order: theme, base, components, and utilities.

Preflight and our element rules, such as the one for a, go in base. Our own class rules, such as .sample-label, go in components. Utilities come last, so p-4 on an element beats a component’s padding. daisyUI places its components inside the utilities layer, in nested layers that sit beneath the plain utilities, so a utility still adjusts a daisyUI component, and a daisyUI component still beats a rule in our components layer.

Try it yourself

Our source has a { color: var(--color-primary); } in the base layer and .site-nav a { color: inherit; } in the components layer. The navigation’s text-neutral-content utility makes the nav element’s text white.

Answer. White. The components layer comes after the base layer, so .site-nav a wins before specificity is even compared. Its inherit takes the colour of the nav element, which the utility set to the neutral-content white.

Literal class names and source scanning

Tailwind does not run templates. It reads the text of the files its sources name, splits the text into words that could be class names, and writes a rule for each word it recognizes. Three consequences follow.

First, class names must appear whole. If a template writes class="bg-{{ role }}", the scanner sees bg- and role, neither of which is a class, so no rule is written; when the page renders bg-primary, there is no CSS for it. Choose between complete names instead, so each one appears in the file:

django

{% if featured %}border-primary
{% else %}border-base-300{% endif %}

Second, the scanner can find words that only look like classes. {% block %}, {% load static %}, and inline in our templates match real utilities named block, static, and inline, so the output has a few small rules that no element uses. They are harmless.

Third, we say exactly where to look. By default, Tailwind scans the whole project folder, which would include events/tests.py and its class-like strings. We switch that off with source(none) and name three folders with @source: the project templates, the events app’s templates, and its templatetags folder, because a filter can write class names in Python, as sample_label does.

Under the Hood: from source to browser

When you run the build, the compiler reads static/otahque/source.css. The @import "tailwindcss" line brings in Tailwind’s four layers and Preflight. @plugin "daisyui" loads daisyUI from node_modules, and the theme block becomes CSS variables. The compiler then scans each @source folder for words that could be classes, keeps every word it can generate a rule for, places each rule in its layer, and adds the rules we wrote ourselves. It writes the result to static/otahque/site.css, an ordinary stylesheet. From there the path is Chapter 13’s: the finder locates the file, the static tag writes its address, the development server sends it, and the browser applies it. Nothing from Tailwind runs while Django serves a page, and neither Django nor the browser can tell that a compiler was involved.

The whole route is in Figure 14.2, and Table 14.4 lists who is responsible for each part and how to prove it.

In practice: keeping a small component vocabulary

Situation. As Otahque grows, someone adds a registration page and pastes a twelve-class button from a tutorial, with colours that are not in the theme.

Application. Keep a short, reviewed list of the components Otahque uses (here, the navigation bar, the card, and the sample label) and add to it deliberately. A proposed component is checked for contrast and keyboard focus before it is used, and its colours come from theme roles.

Consideration. daisyUI offers dozens of components. Using one because it exists adds styles to review and checks to run, for no reader need. A component library also does not make a page accessible on its own: the colours in our theme are ours to measure.

The rest of this chapter’s tools are versions of things you already know. The compiled file is a static file, the theme variables are CSS custom properties, and the build is a command with a lockfile behind it.

Prefer not to install Node.js?

Tailwind also publishes a standalone executable with the compiler built in, and daisyUI’s Django guide shows how to use it with daisyUI’s own files. We use npm because one lockfile then pins Tailwind and daisyUI together, and npm ci reproduces both. If you cannot install Node.js on your computer, use the Tailwind 4.3.4 standalone executable in a separate copy of the project. The committed site.css still lets Django run while you sort it out.
