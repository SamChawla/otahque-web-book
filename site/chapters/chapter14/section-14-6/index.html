Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 and L2 check what you have just learned. L3 asks you to diagnose a problem in order. L4 and L5 look ahead to a larger application and to deployment: attempt them now, and return to them later. They are extension questions, not a gate to the next chapter. Run each code proof beside manage.py, in PowerShell, a macOS shell, or Linux/WSL Bash.

L1 (Junior): What does Tailwind compile, and why does Django still use the static tag?

What the interviewer is testing: Can you separate a build step from serving a page?

Flip to check your answerFold answer back

Perfect answer: Tailwind compiles one input stylesheet, together with the class names it finds in the files the input names, into an ordinary CSS file. It runs when a developer builds, not when someone requests a page. Django then treats that output like any other static file: the finder locates it and the {% static %} tag writes its address. The tag still matters because the address can change later, for example to a hashed file name or another server, without any template changing. Tailwind knows nothing about Django, and Django knows nothing about Tailwind.

Behind the scenes:

Tailwind build (summary)

read source.css; load tailwindcss and daisyui
scan each @source folder for class-like words
keep the words it can write a rule for
write the layers and our own rules to site.css

Code proof: the address the tag writes, and the file behind it:

Terminal

uv run python manage.py shell -c "
from pathlib import Path
from django.contrib.staticfiles import finders
from django.templatetags.static import static
css = Path(finders.find('otahque/site.css')).read_text(
    encoding='utf-8')
print(static('otahque/site.css'))
print(css.startswith('/*! tailwindcss v4.3.4'))
"

Output

12 objects imported automatically (use -v 2 for details).

/static/otahque/site.css
True

The address is the same as in Chapter 13, and the file behind it now starts with the compiler’s header.

Common mistakes:

  • Thinking Tailwind runs in the browser or on each request.
  • Linking source.css instead of the output.
  • Typing /static/... because “the build knows the path”.

Follow-up the interviewer might ask:

  • “What would change if site.css were served from another domain?”
  • “Why commit a generated file?”

L2 (Mid-Level): Trace a literal utility from a Django template to a rendered page.

What the interviewer is testing: Can you name each step between a class name and a styled element, and the check for each?

Flip to check your answerFold answer back

Perfect answer: Take max-w-2xl on the layout’s main. It is written whole in templates/base.html, a folder that an @source line names. When I build, the compiler scans that file, recognizes the word, and writes a .max-w-2xl rule with max-width into site.css. When a page is requested, Django renders the class into the HTML, and the static handler serves site.css. The browser matches the class selector to the element, and the Styles panel shows the rule and which file it came from. At each step there is a check: the template, a search of the output, the rendered HTML, and the browser.

Behind the scenes:

class trace (summary)

template text -> scanner finds max-w-2xl
compiler writes .max-w-2xl { max-width: ... }
Django renders class="... max-w-2xl ..."
browser matches the selector and applies it

Code proof: the class in the rendered page and its rule in the output:

Terminal

uv run python manage.py shell -c "
from pathlib import Path
from django.contrib.staticfiles import finders
from django.template.loader import render_to_string
css = Path(finders.find('otahque/site.css')).read_text(
    encoding='utf-8')
page = render_to_string('events/home.html')
print('max-w-2xl' in page, '.max-w-2xl {' in css)
"

Output

12 objects imported automatically (use -v 2 for details).

True True

Common mistakes:

  • Checking only the template, and assuming the rule exists.
  • Forgetting that the build must run after the template changes.
  • Looking for the class in source.css, where utilities never appear.

Follow-up the interviewer might ask:

  • “How would you find which file a rule in the Styles panel came from?”
  • “What happens to the trace if the template folder has no @source line?”

L3 (Senior): Why is a dynamically constructed class absent, and how should the template change?

What the interviewer is testing: Can you diagnose a missing rule from the scanner’s point of view, and fix the template rather than the output?

Flip to check your answerFold answer back

Perfect answer: The compiler never runs the template. It reads the template’s text, so bg-{{ role }} gives it bg- and role, and the finished name bg-primary exists only in the rendered page, after the build has finished. I would confirm it in order: the rendered HTML has the class, the output has no .bg-primary rule, and the template builds the name from parts. The fix is to write every possible name in full, as a choice in the template or a value from a small mapping written in a scanned file, then build. I would not add the rule to site.css by hand, and I would only list classes for the compiler to keep if a real case needed it.

Behind the scenes:

source scanning (summary)

scanned text:  class="bg-{{ role }}"
words found:   class, bg-, role
rule written:  none
rendered HTML: class="bg-primary"   (no CSS for it)

Code proof: one theme utility used in a template, and one that only exists by name:

Terminal

uv run python manage.py shell -c "
from pathlib import Path
from django.contrib.staticfiles import finders
css = Path(finders.find('otahque/site.css')).read_text(
    encoding='utf-8')
for name in ('bg-neutral', 'bg-primary'):
    print(name, '.' + name + ' {' in css)
"

Output

12 objects imported automatically (use -v 2 for details).

bg-neutral True
bg-primary False

bg-primary is a valid class, and the theme defines primary, but no template contains the name whole, so the output has no rule for it.

Common mistakes:

  • Editing site.css to add the missing rule.
  • Assuming that a valid class name is always in the output.
  • Scanning the whole project to catch it, which adds noise instead of fixing the template.

Follow-up the interviewer might ask:

  • “Where should a mapping from event status to class name live?”
  • “When is listing classes for the compiler to keep justified?”

L4 (Staff): When should a value become an Otahque token rather than a one-off utility?

What the interviewer is testing: Can you decide what belongs in the design system, and keep the system small?

Flip to check your answerFold answer back

Perfect answer: A value becomes a token when it carries a meaning that more than one place must share, so that changing it should change all of them together. The link and focus blue is a good example: it is the primary role, used by links and the focus outline. A value used in one place, such as the sample label’s orange, stays in that component’s rule until a second use appears; promoting it early adds a name nobody needs. Spacing and layout use Tailwind’s existing scale rather than new tokens. Before a new role goes in, I would check its contrast against the colours it sits on, and I would record the decision, because a theme is a shared contract, not a palette.

Behind the scenes:

where a value lives (summary)

spacing and layout            -> the utility scale
shared meaning, several uses  -> theme role (--color-...)
one component, one use        -> that component's rule

Code proof: how often the output uses the primary role, and the label’s orange:

Terminal

uv run python manage.py shell -c "
from pathlib import Path
from django.contrib.staticfiles import finders
css = Path(finders.find('otahque/site.css')).read_text(
    encoding='utf-8')
print(css.count('var(--color-primary)'))
print(css.count('#9d480c'))
"

Output

12 objects imported automatically (use -v 2 for details).

2
1

The primary role reaches two rules, links and focus, through one variable, so changing it changes both together. The orange appears once, in the one rule that needs it.

Common mistakes:

  • Turning every colour into a token, so the theme becomes a list nobody reads.
  • Keeping a shared colour as repeated values, so changes miss copies.
  • Adding a role without measuring its contrast.

Follow-up the interviewer might ask:

  • “What would justify a second theme, such as a dark one?”
  • “How would you review a proposed new component?”

L5 (Lead): How would you keep the CSS build reproducible and prepare it for deployment?

What the interviewer is testing: Can you separate a reproducible build from a development watcher and from a deployment design?

Flip to check your answerFold answer back

Perfect answer: I would pin exact versions in package.json, keep package-lock.json in Git, and install with npm ci everywhere, so every developer and any automated check runs the same compiler. The watcher is for editing only, and it never removes a rule while it runs; a release uses the one-off build. Because a build from the same inputs is byte-identical, a check can rebuild and fail if the committed site.css differs, which catches stale output. For deployment I would keep the templates and the {% static %} tag, run collectstatic so that the built file is copied with a hashed name, serve it with long cache times, and verify the deployed pages. Whether the source file is collected too, and whether the output is minified, are decisions for that design. Otahque makes them in Chapter 63, where they can be run and checked.

Behind the scenes:

release build (summary)

npm ci                -> exact tools from the lockfile
npm run build         -> site.css from source and templates
rebuild + git diff    -> committed output is current
collectstatic         -> hashed copy for the server (Ch. 63)

Code proof: the pins in package.json agree with the lockfile:

Terminal

uv run python -c "
import json
pkg = json.load(open('package.json'))
lock = json.load(open('package-lock.json'))
for name, pin in pkg['devDependencies'].items():
    got = lock['packages']['node_modules/' + name]['version']
    print(name, pin, got)
"

Output

@tailwindcss/cli 4.3.4 4.3.4
daisyui 5.7.50 5.7.50
tailwindcss 4.3.4 4.3.4

Every exact pin matches what the lockfile installed, so npm ci gives every computer the same three tools.

Common mistakes:

  • Running the watcher on a server, or treating it as the build.
  • Pinning with ranges or latest, so builds drift.
  • Committing output that a rebuild would change.

Follow-up the interviewer might ask:

  • “How would an automated check catch a stale site.css?”
  • “Should the server run Node.js at all?”
