How We Build It

Start from Chapter 13, in the directory containing manage.py, with your own .env, the locked environment, 16 passing tests, and the Chapter 13 work committed to your Git repository. We will change events/tests.py, .gitignore, templates/base.html, templates/includes/site_nav.html, events/templates/events/list.html, and events/templates/events/detail.html, and static/otahque/site.css becomes a generated file. We will add package.json, .node-version, and static/otahque/source.css, and npm will add package-lock.json and a node_modules folder. Settings, views, URLs, the home template, and the sample_label filter do not change. At the end, the same pages are built from a theme and a small vocabulary of classes.

The Custom Way

This illustration shows the drift a design system prevents; do not add it to the project:

illustration_only/hand_grown.css (not part of the project)

.event-row {
  border: 1px solid #d5dde8;
  padding: 1rem;
}

.venue-card {
  border: 1px solid #d6dde8;
  padding: 16px;
}

.speaker-box {
  border: 1px solid #d5dde8;
  padding: 0.9rem;
}

Three pages later, the hand-grown sheet has three rules for the same card. One border colour is a typing slip away from the others, and the same space is written three ways. Changing the border colour means finding every copy, and nothing says which copies were meant to match. The approach below keeps Django’s static files exactly as they are, and adds a compiler, a theme that names each colour once, and a short vocabulary of classes.

The Django Way

Step 1: Write the tests first

Common Error: a class in the HTML is not proof of CSS

A template test can prove that a page contains class="navbar", but not that any CSS exists for it. If the compiler never saw the class, the browser receives a class with no rule. We need a second test that reads the compiled stylesheet, and the browser still has the last word on what loads.

Run the Chapter 13 tests first, beside manage.py, in PowerShell, a macOS shell, or Linux/WSL Bash, and confirm all 16 pass:

Terminal

uv run python manage.py test events

Open events/tests.py. Add one import line at the very top, directly above from unittest.mock import patch:

events/tests.py (top of the file)

from pathlib import Path

Then add this class at the end of the file:

events/tests.py (end of the file)

class DesignSystemTests(SimpleTestCase):
    def test_navigation_uses_navbar(self):
        response = self.client.get('/')
        self.assertContains(
            response, '<nav class="site-nav navbar'
        )

    def test_stylesheet_defines_navbar(self):
        found = finders.find('otahque/site.css')
        css = Path(found).read_text(encoding='utf-8')
        self.assertTrue(
            '.navbar {' in css,
            'site.css has no .navbar rule',
        )

The first test is a template contract: the navigation keeps its site-nav hook and gains daisyUI’s navbar component class. The second asks the finder for the stylesheet, exactly as the development server will, reads the file, and checks that it contains a .navbar rule. It uses assertTrue with a short message rather than assertIn, whose failure message would print the whole stylesheet. Run the tests:

Terminal

uv run python manage.py test events

Step 2: Install Node.js and pin the build tools

Common Error: npm refused in Windows PowerShell

Windows PowerShell may refuse to run npm with npm : File C:\Program Files\nodejs\npm.ps1 cannot be loaded because running scripts is disabled on this system. The installer adds a small PowerShell script called npm.ps1, and Windows’ default execution policy blocks scripts. Type npm.cmd instead of npm in every command in this chapter, which needs no setting changed. Changing the policy for your account with Set-ExecutionPolicy -Scope CurrentUser RemoteSigned also works; read what it allows before you choose it.

Install Node.js 26.13.0, the newest long-term support release when this book was pinned. It comes with npm 11.20.0. The official files are at https://nodejs.org/dist/v26.13.0/.

  • Windows: download node-v26.13.0-x64.msi, run it with the default options, and then open a new PowerShell window so that it finds the new commands.
  • macOS: download node-v26.13.0.pkg and run it.
  • Linux and WSL: download node-v26.13.0-linux-x64.tar.xz, unpack it, and add its bin folder to your PATH; or, if you already use a Node version manager, ask it for exactly 26.13.0.

Check both versions, in any of the shells:

Terminal

node --version
npm --version

Output

v26.13.0
11.20.0

Common Error: moving versions and generated project files

Do not run npm install tailwindcss@latest: latest names whatever is newest on the day you run it, so two readers get different tools. Do not run npm init -y either, which writes a package.json with guessed fields, including a description copied from the README. And keep Node packages out of pyproject.toml; uv cannot install them.

Create package.json beside manage.py, typing it as shown:

package.json

{
  "name": "otahque",
  "private": true,
  "engines": {
    "node": "26.13.0"
  },
  "scripts": {
    "css": "tailwindcss -i static/otahque/source.css",
    "build": "npm run css -- -o static/otahque/site.css",
    "watch": "npm run build -- --watch"
  },
  "devDependencies": {
    "@tailwindcss/cli": "4.3.4",
    "daisyui": "5.7.50",
    "tailwindcss": "4.3.4"
  },
  "allowScripts": {
    "@parcel/watcher": false
  }
}

Read it from the top. private stops the project from ever being published to the npm registry by mistake. engines records the Node.js release we use. The three devDependencies are the compiler’s command-line tool, the compiler itself, and daisyUI, each at an exact version with no range in front of it. The scripts build on each other, so each line stays short: css runs the compiler on our source, build adds the output file, and watch adds --watch. The -- passes the words after it to the script being run.

allowScripts needs a word of its own. Some packages run a program while they install. One of the compiler’s helpers, @parcel/watcher, which notices file changes for --watch, has such a script, used only to build itself when no ready-made copy exists. Ready-made copies exist for Windows, macOS, and Linux, so the script is not needed. npm 11.20 asks a project to approve or deny each install script; the entry denies this one, and it is what npm install-scripts deny @parcel/watcher would write. Never approve a script you have not read about.

Create .node-version beside it, containing one line. Several Node version managers read this file:

.node-version

26.13.0

Now install, so that npm creates the lockfile:

Terminal

npm install

Output

added 29 packages, and audited 36 packages in ...

8 packages are looking for funding
  run `npm fund` for details

found 0 vulnerabilities

npm may also mention that a newer npm exists; ignore it, because the pinned version is deliberate. npm wrote package-lock.json with the exact version and a checksum of every package, including the helpers the three tools need, and put the packages in node_modules. Then reproduce the install from the lockfile alone, as another computer would:

Terminal

npm ci

Output

added 29 packages, and audited 36 packages in ...

8 packages are looking for funding
  run `npm fund` for details

found 0 vulnerabilities

npm ci deletes node_modules and installs exactly what the lockfile records, and it refuses to run if package.json and the lockfile disagree. From now on, use it whenever you set up the project. No install-scripts warning appears, because allowScripts covers the only install script.

The node_modules folder is large and can be rebuilt at any time, so keep it out of Git. Add a blank line and these two lines at the end of .gitignore:

.gitignore (end of the file)

# Node packages, rebuilt from package-lock.json by npm ci
node_modules/

Check what Git sees:

Terminal

git status --short

Output

 M .gitignore
 M events/tests.py
?? .node-version
?? package-lock.json
?? package.json

node_modules/ is not listed. The tests are unchanged since Step 1: both still fail.

Step 3: Carry Chapter 13’s rules into the source, then build

Common Error: building before the rules are in the source, or following Tailwind 3

The build overwrites site.css. Run it before copying Chapter 13’s rules into the source, and those rules are gone from the output. And many tutorials still show Tailwind 3, with a tailwind.config.js file and @tailwind base; lines: Tailwind 4 configures everything in CSS, and a source made of those lines builds without an error into a file with almost nothing in it.

Create static/otahque/source.css. It holds everything Chapter 13’s sheet did, translated to use the theme, plus the setup lines that only the compiler reads:

static/otahque/source.css

/* Otahque styles: Tailwind compiles this into site.css */
@import "tailwindcss" source(none);
@source "../../templates";
@source "../../events/templates";
@source "../../events/templatetags";

@plugin "daisyui" {
  themes: false;
}

@plugin "daisyui/theme" {
  name: "otahque";
  default: true;
  color-scheme: light;
  --color-base-100: #ffffff;
  --color-base-200: #f4f6f9;
  --color-base-300: #d5dde8;
  --color-base-content: #1b2735;
  --color-primary: #0759ce;
  --color-primary-content: #ffffff;
  --color-neutral: #142b46;
  --color-neutral-content: #ffffff;
  --radius-box: 0.375rem;
  --border: 1px;
}

@layer base {
  body {
    min-height: 100vh;
    background-color: var(--color-base-200);
  }

  h1 {
    font-size: 1.5rem;
    font-weight: 700;
    line-height: 1.25;
  }

  h1,
  p,
  ul {
    margin-bottom: 1rem;
  }

  a {
    color: var(--color-primary);
    text-decoration: underline;
  }

  :focus-visible {
    outline: 3px solid var(--color-primary);
    outline-offset: 2px;
  }
}

@layer components {
  main {
    max-width: 44rem;
    margin: 0 auto;
    padding: 1.5rem 1rem 3rem;
  }

  .site-nav {
    background: var(--color-neutral);
    padding: 0.75rem 1rem;
  }

  .site-nav a {
    color: var(--color-neutral-content);
    font-weight: 600;
    margin-right: 1.25rem;
  }

  .site-nav :focus-visible {
    outline-color: var(--color-neutral-content);
  }

  .event-row,
  .event-empty {
    background: var(--color-base-100);
    border: 1px solid var(--color-base-300);
    border-radius: var(--radius-box);
    padding: 1rem;
    margin-bottom: 0.75rem;
  }

  .event-row a {
    font-weight: 600;
  }

  .sample-label {
    color: #9d480c;
    font-size: 0.85em;
    font-weight: 700;
  }
}

Read it in five parts. The first five lines import Tailwind with automatic scanning switched off, then name the three source folders, relative to this file. The daisyui plugin block loads the components with themes: false, so none of daisyUI’s own themes is included. The theme block defines otahque with the roles from Table 14.3, makes it the default, and sets the corner radius for boxes and the border width that daisyUI’s components use. The base layer restores what Preflight removed and what Chapter 13 relied on: the page colour, a heading size, spacing below headings, paragraphs, and lists, underlined links, and the focus outline. The components layer holds Chapter 13’s class rules, with each colour replaced by its role.

A few Chapter 13 declarations are not here because Preflight and daisyUI now provide them: the body’s zero margin, font, and line height, the text colour, and the list’s removed bullets and indent.

Build it:

Terminal

npm run build

Expected result. npm first prints each script it runs, shortened here with ...:

Folder structure

> build
> npm run css -- -o static/otahque/site.css


> css
> tailwindcss -i static/otahque/source.css -o ...

≈ tailwindcss v4.3.4

/*! ... daisyUI 5.7.50 */
Done in ...

On screen, the line that starts > tailwindcss ends -o static/otahque/site.css, and daisyUI prints a small flower symbol where the last ... is. The compiler replaced Chapter 13’s sheet with its output. Check that Django still finds it:

Terminal

uv run python manage.py findstatic otahque/site.css

Output

Found 'otahque/site.css' here:
  ...\static\otahque\site.css

findstatic otahque/source.css finds the source too, because it lives in the same static folder. That is expected: the development server would send it if asked, but no page asks, because base.html links only site.css, and Chapter 13’s link test keeps it that way. Whether a deployment copies the source is a Chapter 63 decision.

Step 4: Use utilities and components in the templates

Common Error: classes on elements the tests pin, or class names built from parts

Two earlier tests compare the navigation links and the detail heading as whole HTML elements, attributes included. A class added to one of them fails those tests, so put classes on the elements that wrap them, and style the links and heading from the source. And never build a class from parts, such as bg-{{ role }}: the compiler cannot see it.

Replace templates/includes/site_nav.html. The nav element gains the navbar component and four utilities; the links do not change:

templates/includes/site_nav.html

<nav class="site-nav navbar gap-5 bg-neutral px-4
            text-neutral-content" aria-label="Site">
  <a href="{% url 'events:home' %}">Home</a>
  <a href="{% url 'events:list' %}">Events</a>
</nav>

A class attribute may continue on the next line, as here; the browser reads the line break as a space. Replace templates/base.html, where main gains the five utilities we read earlier:

templates/base.html

{% load static %}
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport"
        content="width=device-width, initial-scale=1">
  <title>{% block title %}Otahque{% endblock %}</title>
  <link rel="stylesheet"
        href="{% static 'otahque/site.css' %}">
</head>
<body>
  {% include "includes/site_nav.html" %}
  <main class="mx-auto max-w-2xl space-y-4 px-4 pt-6 pb-12">
    {% block content %}{% endblock %}
  </main>
</body>
</html>

Replace events/templates/events/list.html. The list gains spacing between its items, and each row and the empty state become cards:

events/templates/events/list.html

{% extends "base.html" %}
{% load event_labels %}

{% block title %}Sample events | Otahque{% endblock %}

{% block content %}
  <h1>Sample events</h1>
  <p>These fictional events are examples.</p>
  <ul class="event-list space-y-3">
    {% for event in events %}
      {% partialdef event-row inline %}
        <li class="event-row card border border-base-300
                   bg-base-100 p-4 font-semibold">
          <a href="{% url 'events:detail' event.id %}">
            {{ event.title|sample_label }}
          </a>
        </li>
      {% endpartialdef %}
    {% empty %}
      <li class="event-empty card border border-base-300
                 bg-base-100 p-4">No sample events yet.</li>
    {% endfor %}
  </ul>
{% endblock %}

Each card uses border border-base-300 rather than daisyUI’s card-border. That class draws its border in the base-200 colour, which in our theme is the page background, so the edge would vanish. Reading what a component actually sets, in its documentation or in the Styles panel, is part of choosing it.

Replace events/templates/events/detail.html. The heading and text become a card, and the back link moves into a paragraph below it. The <h1> itself keeps no class:

events/templates/events/detail.html

{% extends "base.html" %}
{% load event_labels %}

{% block title %}Sample event | Otahque{% endblock %}

{% block content %}
  <article class="card space-y-4 border border-base-300
                  bg-base-100 p-6">
    <h1>{{ title|sample_label }}</h1>
    <p>This fictional event is an example.</p>

Step 5: Check the result in the browser

Common Error: editing the generated file, or forgetting the build

A change typed into site.css works until the next build overwrites it. Edit source.css or a template, then build. If a change does not appear, check that the build ran after the edit before suspecting the browser.

Start the development server again and open http://127.0.0.1:8000/events/, with the developer tools open and Disable cache ticked:

Terminal

uv run python manage.py runserver

Check four things.

  • The file. In the Network panel, site.css loads with status 200. No request for source.css appears.
  • The rules. Right-click the sample event’s card and choose Inspect, then select its li element. The Styles panel lists .p-4 with padding, and .card with display: flex, both from site.css. Inspect a navigation link: .site-nav a sets color: inherit, and the base a rule’s colour below it is crossed out.
  • The keyboard. Click the address bar and press Tab. Focus moves to Home and Events, each with a white outline on the navy bar, then to the sample event with a blue outline. Every link is underlined, so none depends on colour alone.
  • Widths. In the device view, try widths of 320, 390, 768, and 1440 pixels on the home page, the list, and the detail page. The text fits without sideways scrolling, and the column stays centred on wide screens.

Open http://127.0.0.1:8000/events/999/. It returns a 404. That page is Django’s own debug page, not our layout, so it stays unstyled.

While you change styles, a watcher saves typing. Leave the server running, open a second terminal beside manage.py, and run:

Terminal

npm run watch

It builds once and then waits. Each time you save the source or a template, it rebuilds and prints another Done in ...; reload the page to see the result. While it runs, the watcher only adds rules: if you remove a class from a template, its rule stays in site.css until the next one-off build. That is one reason the watcher is a development convenience only, and why Step 6 ends with npm run build. Stop it with Ctrl+C, and if Windows asks Terminate batch job (Y/N)?, answer Y. Then stop the server.

Step 6: Prove the build reproduces, then rerun everything

Common Error: committing output that does not match its source

If site.css was built before your last template edit, or still holds rules a watcher kept for classes you removed, the committed output and its source disagree, and the next person who builds gets a different file. Build once more before committing, and let Git confirm that a rebuild changes nothing.

With the watcher stopped, reinstall from the lockfile, build, and stage the output, so Git keeps a copy to compare against:

Terminal

npm ci
npm run build
git add static/otahque/site.css

Now build again and ask Git whether the file changed:

Terminal

npm run build
git diff --exit-code -- static/otahque/site.css

git diff prints nothing and exits with status 0: the second build wrote exactly the same bytes. Given the same lockfile, source, and templates, the build always does. Finally, run the checks once more:

Terminal

uv run python manage.py check
uv run python manage.py test events

When something goes wrong

Table 14.5 lists the problems this chapter can produce. Most come from three places: the toolchain, the source, or the gap between the source and the output. Check them in that order.

Two of these need care. allowScripts exists so that you decide which install programs run; approving one to make a warning go away defeats it. And when the output looks wrong, the cure is in the source, the templates, or the toolchain, never in hand edits to site.css.

Keep your work while you diagnose a problem. Compare the one file a message names with its listing, and save a copy before replacing anything you want to keep. If Node.js cannot be installed at all, follow the standalone route from the “Prefer not to install Node.js?” note in a separate copy, and leave this project as it is. Do not delete the project or reset Git as a first response.
