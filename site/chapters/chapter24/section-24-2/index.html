What You Need to Know

From a link to a form: GET and POST

Every page you have built so far answers a GET request: the browser asks for an address, and the view returns a page. A GET request should never change anything on the server, because browsers, search engines, and link previews send them freely. A form that changes data uses POST instead.

New Concept: HTML forms and POST

What problem exists? A person needs to send values to the server, such as an event’s title and start, and the server must know they are a request to change something, not a request to read.

What did people do before? Early sites put values in the address, as ?title=Clinic, which every link preview and browser history then repeated, and which anyone could change by editing the address bar.

What is it? An HTML <form> element holds input elements, each with a name. When the person presses its button, the browser sends one request to the form’s address with each name and the value typed into it. With method="post", the values travel in the request’s body, and Django gives them to the view as request.POST, a dictionary-like object whose values are always text.

Why use it? POST tells everyone along the way that the request changes something, so browsers warn before sending it twice, and caches and previews leave it alone.

Now let’s use it. Step 5 writes the New event page’s <form method="post">, and Step 6 handles what it sends.

The whole journey of Sam’s new event is in Figure 24.1. The view handles both requests at one address, /events/new/. A GET returns the page with an empty form. A POST carries what Sam typed: if anything is wrong, the view returns the same page with the errors and with every value he typed; if everything holds, it saves the draft and answers with a redirect, a response that tells the browser to request another address, here the event’s own page. The browser then asks for that page with GET. This pattern is called Post/Redirect/Get: because the last request is a GET, refreshing the page, or pressing Back, can never send the form a second time and save the event twice.

Django’s Form class

Turning request.POST into something your code can trust takes work: every value is text, any can be missing, and each needs checks and a message a person understands. Django’s form library does that work.

New Tool: Django forms

What problem exists? Each value a person sends must be checked, converted from text, explained when it is wrong, and shown again so they can correct it, and the HTML for the inputs must match the checks.

What did people do before? They wrote the checks and the HTML by hand for every form, as The Custom Way below does, and the two drifted apart.

What is it? A form class, a subclass of django.forms.Form, lists fields, such as forms.CharField, each of which knows how to check and convert one value and how to draw its input with a widget, the object that writes the HTML for an input. An instance of the class is unbound when it holds no data, and bound when you give it data, such as request.POST.

Why use it? One class describes the checks and the HTML together, and Django supplies the messages, the conversions, and the rendering.

Now let’s use it. Step 2 creates a form in a practice file and asks it each question in Table 24.1.

The difference between data and cleaned_data is the one to keep. data['capacity'] is the text '50'; cleaned_data['capacity'] is the number 50. Code after is_valid() reads cleaned_data only, never request.POST, because only those values have passed every check.

Under the Hood: what is_valid() runs

is_valid() calls the form’s full_clean() once and returns whether errors is empty. full_clean() works through the fields in order: each field’s clean() converts the text and runs its validators, such as “required” and a maximum length, and stores the value in cleaned_data or the message in errors; then a method named clean_ followed by the field’s name runs, if the form has one. When every field is done, the form’s own clean() runs, for rules that need more than one value. For a ModelForm, one more stage follows: Django copies the cleaned values onto a model instance and calls the model’s validation, the full_clean() that Chapter 21 wrote rules for, with its field validators and its constraints, and any message the model raises joins errors. Nothing is written to the database by any of this; save() does that, and only you call it.

ModelForm: a form from the model, and its allowlist

Otahque’s Event model already lists the fields an event has, their kinds, and their rules. Writing a Form that repeats them would leave two copies to keep in step. A ModelForm builds its fields from the model instead, as the admin’s forms did in Chapter 23, and its save() creates or updates the model’s row.

A ModelForm needs to know which of the model’s fields to include, in an inner class called Meta. Its fields list is an allowlist: only the fields named in it are on the form, and only they can be set by what a browser sends. That is the safety rule of this chapter. The Event model has a status field, and Sam must not be able to publish an event by sending status=published, from a tampered browser or a script. Leaving status out of fields means a posted status value is ignored, and the model’s default, draft, is saved. Django’s documentation strongly recommends naming the fields explicitly: fields = '__all__' or a list of exclusions would quietly add any field the model gains later, such as an owner or a price.

Where each rule lives

Otahque’s event rules now have four possible homes, and each catches different mistakes. Figure 24.2 shows them in the order they run.

A field checks one value alone. The form’s clean() checks rules that compare fields, written for this page. The model’s validation holds the rules that apply wherever an event is saved through a form, the admin’s included. The database’s constraints, from Chapter 21, refuse a bad row however it arrives, from a form, the shell, or a script, but a refusal there is an error page, not a message. So each rule lives in the lowest layer that can state it, and is repeated above only when a person needs a better message. In this chapter, “ends after it starts” is checked in the form’s clean(), so its message appears beside the Ends field, while the database constraint stays as the backstop. “Capacity must be more than 0” stays in the model, and its message appears at the top of the form; Chapter 25 discusses moving such messages beside their field.

Times typed in the event’s own zone

Chapter 23 showed that Django reads a typed time in the current time zone, UTC in Otahque, so 15:00 typed for the Kolkata workshop became 15:00 UTC. Sam’s form fixes that for his page: it reads the times in the zone chosen for the event. Figure 24.3 follows his clinic from the text the browser sends to the instant that is stored.

Two more things make a typed time tricky. A clock change moves local time forward or back by an hour in many zones. When New York’s clocks go forward at 02:00 on 14 March 2027, the times from 02:00 to 02:59 do not exist that day; when they go back at 02:00 on 1 November 2026, the times from 01:00 to 01:59 happen twice. A form that guessed would store an event an hour away from what Sam meant, so Otahque’s form refuses those times and says why. The second is choosing the zone at all: the form asks for it in a list, and a small script fills in the zone the browser reports, so Sam usually leaves it alone. When the event’s audience is elsewhere, as with his New York clinic, he chooses another.

Who may open the page, and who may see a draft

Chapter 23 introduced Django’s model permissions. This page uses two of them. events.add_event lets an account create events, so the page is open only to signed-in people who hold it. events.view_event lets the administrator read every event, drafts included. And when Sam saves a draft, Otahque records him as its organizer with Chapter 20’s OrganizerAssignment, so the draft’s page can be shown to its organizers. Figure 24.4 lists who sees what.

Two decorators, functions that wrap a view, do the page’s checks. login_required sends anyone who is not signed in to the address in the LOGIN_URL setting, with ?next= holding the page they asked for. permission_required refuses a signed-in account without the permission, with status 403. Otahque has no sign-in page for members yet; Chapter 27 builds one. Until then, LOGIN_URL points at the admin’s sign-in page, which only staff accounts can use. That is enough on your computer, where you sign in as Sam, your Chapter 18 superuser. It also means a member who is not staff, given add_event, could not sign in through the browser before Chapter 27; the tests sign such members in directly.

Forged requests, and the CSRF token

A signed-in browser sends its session cookie with every request to Otahque, whichever page caused the request. That is what makes forms dangerous.

New Concept: cross-site request forgery (CSRF)

What problem exists? Another site can contain a hidden form that posts to /events/new/. If Sam visits that site while signed in to Otahque, his browser sends the form with his cookie, and Otahque would see a request from Sam.

What did people do before? Sites trusted the cookie, or checked where a request came from with headers that were easy to lose.

What is it? Cross-site request forgery is that attack. Django’s defence is a secret CSRF token: CsrfViewMiddleware, which your settings have had since Chapter 6, puts a token in a cookie, the template tag {% csrf_token %} writes it into the form as a hidden input named csrfmiddlewaretoken, and the middleware refuses any POST whose token is missing or wrong with status 403. Another site cannot read the token, so it cannot forge the request.

Why use it? It is on by default and costs one tag in each form.

Now let’s use it. Step 5 puts the tag in the form, and Step 9 proves the refusal with a test.

There is a trap for tests. Django’s test client skips the CSRF check by default, so that tests can post without fetching a token first. A test suite can therefore pass with the protection switched off. The one test that matters creates its client with enforce_csrf_checks=True, posts without a token, and expects 403.

Rendering fields people can use

A field is usable when everyone can tell what it is for, what is wrong with it, and how to fix it. That means a <label> element whose for names the input’s id, so clicking the label focuses the box and a screen reader announces the label with the box; help text and error messages that the input points to; and a sign that a value is wrong that does not depend on colour alone.

Django 6.1 does most of this when it renders a field. Each input gets an id, such as id_title. Help text is written with the id id_location_helptext, and the error list with id_title_error. The input’s aria-describedby attribute lists those ids, so a screen reader reads the help and the error after the label, and aria-invalid="true" marks a field with an error. Figure 24.5 shows the pieces for the Time zone field, which has both help text and an error.

Otahque’s look needs Tailwind and daisyUI class names on those elements, and there is a catch: Chapter 14’s build reads class names only from the template folders named in source.css, so a class written in a Python file would never reach the stylesheet. Django lets the templates win instead. A form renderer decides which templates draw forms, and Django’s TemplatesSetting renderer looks for them through your TEMPLATES setting, so a project template with the same name as one of Django’s replaces it. Step 8 writes one template for every field, and two widget templates, for text-like inputs and for lists, that add daisyUI’s classes, and keeps Django’s ids and attributes.

Try it yourself

Que. 1 Sam’s form is posted with the title empty and status=published. Which of these does the response contain: a saved event, a published event, the message “This field is required.”, or the location he typed?

Flip to check your answerFold answer back

Answer. The message and the location. The empty title makes the form invalid, so nothing is saved, and the page is returned with every value Sam typed. status is not in the form’s fields, so it would be ignored even if the form were valid.

Prefer a Form, a ModelForm, or HTML by hand?

Use a ModelForm when the form creates or edits one model’s row: it takes the model’s fields and rules, and its fields list keeps the allowlist in one place. Use a plain Form when the values are not one row, such as a search box or a contact form. Avoid reading request.POST by hand in a view: every check, conversion, message, and redisplay is then yours to write and test, and it drifts from the model.

A form decides only what a person may type. Whether that person may open the page at all, and what they may see afterwards, are separate checks in the view and the model, and each needs its own test.

In practice: one event, two time zones

Situation. A community in Leeds runs a joint online session with a group in Bengaluru, and the organizer who types it lives in Leeds.

Application. The organizer chooses the zone the session is announced in, Asia/Kolkata, types the times as the announcement states them, and the page shows them in that zone. Nobody converts anything by hand.

Consideration. Attendees in Leeds still read Kolkata times on the event page until Chapter 28 shows each viewer their own time beside the event’s. Choosing the zone the audience will read is a product decision, not a technical one.
