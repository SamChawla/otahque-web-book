Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead to a larger application with a team: attempt them now, and return to them after Chapters 25, 27, and 30. They are extension questions, not a gate to the next chapter. Each code proof is a short file in the practice folder that starts by importing Chapter 16’s setup_django.py; run it from the folder that holds manage.py with uv run python ../practice/ followed by the file name. The proofs only read your rows: any row they create is rolled back.

L1 (Junior): What is a Django form, and how do data and cleaned_data differ?

What the interviewer is testing: Do you know what a form does between the request and your code, and which values your code may trust?

Flip to check your answerFold answer back

Perfect answer: A Django form is a class that lists fields; each field knows how to check and convert one value and how to draw its input. I bind a form to what was sent, usually request.POST, and call is_valid(), which runs every field’s checks, the form’s clean(), and, for a ModelForm, the model’s validation. data is what the browser sent, always text; cleaned_data holds the converted values that passed, such as a number or a date and time, and exists only after is_valid(). My code reads cleaned_data, never request.POST. In Otahque, EventForm turns Sam’s text “2026-12-03T19:00” and “America/New_York” into an aware time, 19:00 in New York. When it is invalid, errors holds the messages, and I return the same bound form so the page shows them with what was typed.

Behind the scenes:

a form's checks (summary)

EventForm(request.POST) -> bound to the sent text
is_valid()              -> fields, clean(), model rules
errors                  -> messages by field
cleaned_data            -> values code may trust

Code proof: Sam’s clinic, before and after the checks:

../practice/l1_data.py

import setup_django
from events.forms import EventForm

form = EventForm({
    'title': 'Online Django clinic',
    'timezone': 'America/New_York',
    'starts_at': '2026-12-03T19:00',
    'ends_at': '2026-12-03T20:30',
    'location': 'Online',
    'capacity': '50',
})
print(form.is_bound, form.is_valid())
for name in ('capacity', 'starts_at'):
    sent, clean = form.data[name], form.cleaned_data[name]
    print(name, repr(sent), '->', clean)

Output

True True
capacity '50' -> 50
starts_at '2026-12-03T19:00' -> 2026-12-03 19:00:00-05:00

The capacity arrives as the text '50' and leaves as the number 50; the start arrives as text and leaves as 19:00 with New York’s offset, five hours behind UTC.

Common mistakes:

  • Reading request.POST after is_valid(), and getting text instead of checked values.
  • Reading cleaned_data before calling is_valid().
  • Creating a new form after a failure, which loses the messages and what was typed.

Follow-up the interviewer might ask:

  • “Where would a rule about two fields go, and where would its message appear?”
  • “Why are values in request.POST always text?”

L2 (Mid-Level): Sam posts an end before the start, and adds status=published. Predict the response and what is saved.

What the interviewer is testing: Can you trace a bad POST through the form’s layers and the view, and say exactly what reaches the database?

Flip to check your answerFold answer back

Perfect answer: Nothing is saved, and Sam sees the same page again with status 200. The fields each pass on their own. status is not in the form’s fields, so the posted value is never read. The form’s clean() reads both times in New York’s zone and finds the end is not after the start, so it attaches “An event must end after it starts.” to Ends. Because the form has an error, the model then skips its own constraint for that field, so the message appears once. is_valid() returns false, the view never calls save() or add_organizer(), and it renders the same bound form, so every value Sam typed is still in its box. If he fixes the end, the event is saved as a draft, still not published, and the response is a redirect to its page.

Behind the scenes:

one invalid POST (summary)

status in POST     -> not a field: ignored
clean()            -> error on ends_at
model constraint   -> skipped for ends_at
is_valid() False   -> 200, same form, no save()

Code proof: the same data, checked without a view:

../practice/l2_predict.py

import setup_django
from events.forms import EventForm
from events.models import Event

before = Event.objects.count()
form = EventForm({
    'title': 'Online Django clinic',
    'timezone': 'America/New_York',
    'starts_at': '2026-12-03T19:00',
    'ends_at': '2026-12-03T18:00',
    'location': 'Online',
    'capacity': '50',
    'status': 'published',
})
print(form.is_valid())
for name, messages in form.errors.items():
    print(name, messages[0])
print('status' in form.fields)
print(Event.objects.count() == before)

Output

False
ends_at An event must end after it starts.
False
True

Invalid, one message on ends_at, no status field, and the number of events unchanged.

Common mistakes:

  • Expecting a 4xx status for a form error: the page is a normal response, with 200.
  • Thinking a hidden or removed input protects a field; only the allowlist does.
  • Saving first and validating after.

Follow-up the interviewer might ask:

  • “What would change if status were in fields?”
  • “Why does the model’s constraint not add a second message?”

L3 (Senior): Defend an explicit fields list over exclude or ’__all__’.

What the interviewer is testing: Do you understand mass assignment, and can you prove a form’s boundary with a test?

Flip to check your answerFold answer back

Perfect answer: A ModelForm writes every field it holds from whatever the browser sends, and the browser is not under my control: anyone can add a value to a POST. With fields = '__all__', Otahque’s form would include status, and a crafted status=published would publish an event that was meant to be a draft. exclude is better only until someone adds a field to the model, such as an owner or a price, which then appears on the form unnoticed. An explicit list is an allowlist: a new field stays off the form until someone decides it belongs there. Django’s documentation recommends exactly that. I back it with a test that posts status=published and expects a draft, so a later change to the list fails the build rather than reaching production.

Behind the scenes:

a form's boundary (summary)

fields = [...]      -> only these are set
'__all__'           -> every editable field
exclude = [...]     -> new fields slip in
crafted POST test   -> the boundary holds

Code proof: the same POST through a form with every field and through EventForm, rolled back:

../practice/l3_allowlist.py

import setup_django
from django.db import transaction
from django.forms import modelform_factory

from events.forms import EventForm
from events.models import Event

SENT = {
    'title': 'Allowlist check',
    'timezone': 'America/New_York',
    'starts_at': '2026-12-03T19:00',
    'ends_at': '2026-12-03T20:30',
    'location': 'Online',
    'capacity': '50',
    'status': 'published',
}
every_field = modelform_factory(Event, fields='__all__')
with transaction.atomic():
    for label, form_class in (("'__all__'", every_field),
                              ('EventForm', EventForm)):
        event = form_class(SENT).save()
        print(label, event.status)
    transaction.set_rollback(True)
print(Event.objects.filter(title=SENT['title']).exists())

Output

'__all__' published
EventForm draft
False

The form with every field published the event; EventForm saved a draft; and the rollback left nothing behind.

Common mistakes:

  • Using '__all__' to save typing.
  • Removing an input from the template and thinking the field is protected.
  • Testing only what the form shows, not what a crafted POST can set.

Follow-up the interviewer might ask:

  • “How would you set a field the person must not choose, such as an owner?”
  • “Where else in Otahque could a crafted POST change more than it should?”

L4 (Staff): Organizers in New York report that their events appear five hours early. Diagnose and fix it.

What the interviewer is testing: Can you trace a time-zone bug from a report to its cause, prove it with a failing test, and fix it at the cause?

Flip to check your answerFold answer back

Perfect answer: Five hours is New York’s offset from UTC in winter, which points at the typed time being read in UTC. Django reads typed times in the current time zone, and Otahque’s is UTC, so 19:00 became 19:00 UTC, which New York shows as 14:00. I would confirm it with a test that posts 19:00 in New York and expects midnight UTC the next day; it fails with the five-hour difference. The fix belongs in the form: after the fields are cleaned, read each typed time again in the event’s own zone, which is what EventForm.clean() and in_zone() do. Activating the organizer’s zone would be wrong, because the event’s zone, not the organizer’s, gives the time its meaning. Then I would refuse the times a clock change skips or repeats, fix the stored rows that were saved wrongly, after checking which events were affected, and keep the test.

Behind the scenes:

a time read twice (summary)

field clean        -> 19:00 in UTC
make_naive()       -> back to 19:00, no zone
replace(tzinfo)    -> 19:00 in the event's zone
fold 0 and 1       -> differ: refuse the time

Code proof: a ModelForm that reads the time in UTC beside EventForm:

../practice/l4_zone.py

import setup_django
from datetime import UTC

from django.forms import modelform_factory

from events.forms import EventForm
from events.models import Event

SENT = {
    'title': 'Online Django clinic',
    'timezone': 'America/New_York',
    'starts_at': '2026-12-03T19:00',
    'ends_at': '2026-12-03T20:30',
    'location': 'Online',
    'capacity': '50',
}
plain = modelform_factory(Event, fields=list(SENT))
starts = []
for label, form_class in (('as UTC', plain),
                          ('in its zone', EventForm)):
    form = form_class(SENT)
    form.is_valid()
    starts.append(form.cleaned_data['starts_at'])
    print(label, starts[-1].astimezone(UTC))
print(starts[1] - starts[0])

Output

as UTC 2026-12-03 19:00:00+00:00
in its zone 2026-12-04 00:00:00+00:00
5:00:00

The same text, two instants, exactly five hours apart: the bug, reproduced, beside the fix.

Common mistakes:

  • Setting TIME_ZONE to New York, which breaks every event elsewhere.
  • Shifting the stored times by five hours, which is wrong in summer.
  • Fixing the rows but not the form, so the next event is wrong too.

Follow-up the interviewer might ask:

  • “When Chapter 28 activates each viewer’s zone, what changes for this form?”
  • “How would you find the events that were saved wrongly?”

L5 (Lead): A manager wants anyone, without an account, to be able to submit event ideas. What do you advise?

What the interviewer is testing: Can you weigh a product request against access rules and abuse, and keep the boundary decided rather than accidental?

Flip to check your answerFold answer back

Perfect answer: I would start from the goal, more good event ideas, and from Otahque’s boundary: creating an event needs an account with add_event, and visitors only read published events. Letting anonymous visitors create Event rows, even drafts, would invite spam and abuse, fill organizers’ lists with rows nobody owns, and need limits Otahque does not have yet. If the community wants ideas, I would propose a separate design: a proposal record, not an event, submitted after sign-in, which Chapter 27 provides, with rate limits, reviewed by organizers who can turn a good one into a draft. That is a scope change to Chapter 2’s requirements, so it is the community’s decision, recorded with its abuse cases and tests. Until then, the current tests prove the boundary: a visitor is sent to sign in, and a member without the permission is refused.

Behind the scenes:

ideas from visitors (summary)

Event rows        -> organizers with add_event
anonymous POST    -> spam, no owner, no limits
proposal record   -> sign-in, limits, review
scope change      -> decided, then tested

Code proof: the New event view, asked by a visitor and by Sai:

../practice/l5_access.py

import setup_django
from django.contrib.auth.models import AnonymousUser
from django.core.exceptions import PermissionDenied
from django.test import RequestFactory

from accounts.models import User
from events.views import event_create

factory = RequestFactory(HTTP_HOST='localhost')
sai = User.objects.get(email='sai@example.org')
for person in (AnonymousUser(), sai):
    request = factory.get('/events/new/')
    request.user = person
    try:
        response = event_create(request)
        print(person, response.status_code,
              response['Location'])
    except PermissionDenied:
        print(person, 'refused: 403')

Folder structure

AnonymousUser 302 /admin/login/?next=/events/new/
sai@example.org refused: 403

RequestFactory builds a request without the server, and HTTP_HOST='localhost' gives it an address your settings allow. The visitor is sent to sign in, and Sai, who holds no permission, is refused.

Common mistakes:

  • Opening the event form to visitors because the form already validates.
  • Treating a product question, who may propose, as a technical one.
  • Adding a public form without rate limits or review.

Follow-up the interviewer might ask:

  • “Which abuse cases would you write tests for first?”
  • “How would Chapter 30’s roles change who may create events?”
