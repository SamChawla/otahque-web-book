Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead: attempt them now, and return after Chapters 29 and 30. They are extension questions, not a gate to the next chapter.

L1 (Junior): What does signing in change in the session, and why does sign-out need a POST?

What the interviewer is testing: Do you know what the session holds, why its key changes, and why a state change is never a GET?

Flip to check your answerFold answer back

Perfect answer: Signing in stores the member’s id, and a value derived from their password hash, in the session, and Django gives the session a new key, so a key someone saw before sign-in no longer works. Signing out deletes that data. It is a state change, so it is a POST with the CSRF token; a GET only shows a confirmation page, and the member stays signed in. Otherwise any page could sign a member out with an image or a link.

Behind the scenes:

sign in, then sign out (summary)

POST /accounts/login/   -> new session key, member id stored
GET  /accounts/logout/  -> a page that asks; still signed in
POST /accounts/logout/  -> session cleared

Code proof: a demo member signs in and out, rolled back afterwards:

l1_session.py (practice file; delete it afterwards)

from django.db import transaction
from django.test import Client
from django.test.utils import setup_test_environment

from accounts.models import User

setup_test_environment()
PASSWORD = 'a-long-safe-pass-123'
with transaction.atomic():
    User.objects.create_user('demo@example.org', PASSWORD,
                             display_name='Demo')
    web = Client()
    web.get('/accounts/login/')
    session = web.session
    session['seen'] = True
    session.save()
    before = session.session_key
    web.post('/accounts/login/', {
        'login': 'demo@example.org', 'password': PASSWORD,
    })
    after = web.session.session_key
    print('new key after sign-in:', after != before)
    web.get('/accounts/logout/')
    signed_in = '_auth_user_id' in web.session
    print('signed in after GET:', signed_in)
    web.post('/accounts/logout/')
    signed_in = '_auth_user_id' in web.session
    print('signed in after POST:', signed_in)
    transaction.set_rollback(True)

Output

new key after sign-in: True
signed in after GET: True
signed in after POST: False

Common mistakes:

  • A sign-out link instead of a form.
  • Thinking the password itself is kept in the session.
  • Turning on allauth’s ACCOUNT_LOGOUT_ON_GET, which its documentation calls a last resort.

Follow-up the interviewer might ask:

  • “What is session fixation, and how does a new key prevent it?”
  • “Where is the session stored, and what does the cookie hold?”

L2 (Mid-Level): Sai signs up as SAI@Example.ORG without a name. Predict what is saved.

What the interviewer is testing: Can you trace a sign-up through Django’s checks, allauth, and Otahque’s form, and say what reaches the database?

Flip to check your answerFold answer back

Perfect answer: Nothing is saved. The address is valid, so Django’s check passes, and it is not disposable, so the adapter passes. But Otahque’s sign-up form makes the display name required, so the form is invalid and the page returns with status 200 and the message beside Display name. With a name, the member is saved with sai@example.org, because Chapter 21’s rule lower-cases the email, and the time zone goes to the profile.

Behind the scenes:

sign-up without a name (summary)

email field       -> valid address
clean_email()     -> not disposable
display_name      -> required: refused
form invalid      -> 200, same page, nothing saved

Code proof: the Mini-Challenge’s l2_signup.py:

Output

without a name: 200 ['This field is required.']
with a name: sai@example.org Sai

Common mistakes:

  • Expecting allauth to know about display_name without a sign-up form.
  • Lower-casing in the view only, so other paths store capitals.
  • Making the time zone required, which turns away people who do not know theirs.

Follow-up the interviewer might ask:

  • “Where would you put a rule that a display name must be unique?”
  • “How does a member who signs up with Google give a display name?”

L3 (Senior): Defend not linking a GitHub sign-in to an existing account by email alone.

What the interviewer is testing: Do you see the account-takeover risk, and know where the safe flow puts the proof?

Flip to check your answerFold answer back

Perfect answer: GitHub tells Otahque that this person controls an address. It does not tell Otahque who controls the Otahque account with that address: someone else could have signed up with it and never confirmed it, or the address could have changed hands. Linking by email would give whoever signs in with GitHub that account. So Otahque asks the person to sign in to the existing account first, which proves they control it, and then connect GitHub. It costs one extra step, once.

Behind the scenes:

GitHub with an address already registered (summary)

provider says  -> sam@example.org, confirmed
Otahque has    -> an account for sam@example.org
result         -> "already exists ... sign in first"
linked         -> only after signing in to the account

Code proof: the Step 9 test test_a_registered_email_is_asked_to_sign_in, run on its own:

Output

Found 1 test(s).
Creating test database for alias 'default'...
...
Ran 1 test in ...s

OK
Destroying test database for alias 'default'...

Common mistakes:

  • Turning on email authentication with automatic connection for every provider.
  • Trusting a provider’s email without checking that the provider marks it confirmed.
  • Merging two accounts without telling either owner.

Follow-up the interviewer might ask:

  • “When could automatic connection be acceptable?”
  • “How would you let a member disconnect a provider safely?”

L4 (Staff): Members report being signed out of other devices after a password change. Diagnose.

What the interviewer is testing: Do you know how Django ties sessions to the password, and whether this is a fault or a feature?

Flip to check your answerFold answer back

Perfect answer: It is intended. Django stores a hash derived from the password in each session and compares it on every request. After a change, the other devices’ sessions carry the old hash, so they are treated as signed out, and a session someone stole stops working too. The device where the member changed the password stays signed in because Django’s update_session_auth_hash() updates that one session; Chapter 29’s password-change page does this. Tell members it is a safety feature, and check that the current device is not signed out as well.

Behind the scenes:

two devices, one password change (summary)

phone, laptop   -> both signed in
password saved  -> new hash on the account
laptop request  -> old hash: signed out, sent to sign in

Code proof: a member signed in on two clients changes the password, rolled back afterwards:

l4_password.py (practice file; delete it afterwards)

from django.db import transaction
from django.test import Client
from django.test.utils import setup_test_environment

from accounts.models import User

setup_test_environment()
with transaction.atomic():
    raj = User.objects.create_user(
        'demo@example.org', 'first-long-pass-1',
        display_name='Demo',
    )
    phone, laptop = Client(), Client()
    for device in (phone, laptop):
        device.force_login(raj)
    raj.set_password('second-long-pass-2')
    raj.save()
    page = laptop.get('/accounts/profile/')
    print('laptop after the change:', page.status_code,
          page.get('Location', '').split('?')[0])
    transaction.set_rollback(True)

Output

laptop after the change: 302 /accounts/login/

Common mistakes:

  • Removing the hash check to stop the complaint.
  • Forgetting update_session_auth_hash() on a custom password page, which signs out the member who changed it.
  • Not telling members why it happened.

Follow-up the interviewer might ask:

  • “How would you let a member sign out of every other device on purpose?”
  • “What does Chapter 29’s two-factor sign-in add on top?”

L5 (Lead): The board wants sign-in with five more providers. What do you advise?

What the interviewer is testing: Can you turn a request into a decision with costs, privacy, and tests, and avoid adding everything because it is easy?

Flip to check your answerFold answer back

Perfect answer: Ask which providers the members already use, because each one is a company trusted with members’ email addresses and a set of credentials to keep secret and renew. allauth makes each addition small, a line in settings, credentials in .env, and a test, but each one also needs a line in the privacy notice and a check that it marks emails as confirmed. Add them one at a time, keep the same linking rule for all of them, and remove any that nobody uses. A community with a company identity service can use OpenID Connect or SAML instead of many separate providers.

Behind the scenes:

adding one provider (summary)

INSTALLED_APPS  -> its provider app
.env            -> client ID and secret
tests           -> a built answer, like Step 9's
notice          -> what the provider shares

Code proof: the providers in the installed allauth, counted:

l5_providers.py (run with uv run python l5_providers.py)

from pathlib import Path

import allauth.socialaccount.providers as providers

folder = Path(providers.__file__).parent
names = sorted(p.name for p in folder.iterdir()
               if (p / 'provider.py').exists())
print(len(names), 'providers, for example:')
print(', '.join(n for n in names if n in {
    'apple', 'microsoft', 'gitlab', 'discord', 'slack',
    'openid_connect', 'saml', 'okta'}))

Output

128 providers, for example:
apple, discord, gitlab, microsoft, okta, openid_connect,
    saml, slack

Common mistakes:

  • Adding every provider because the package offers them.
  • Storing provider secrets in the database or in Git.
  • Linking accounts across providers by email.

Follow-up the interviewer might ask:

  • “How would you retire a provider members still use?”
  • “What changes when the community needs single sign-on for a company?”
