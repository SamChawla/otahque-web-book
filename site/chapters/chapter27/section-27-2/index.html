What You Need to Know

Authentication, and what a session remembers

Authentication answers “who is this?”, and authorization, which Chapters 24 to 26 used, answers “may they do this?”. Signing in is authentication: the person proves who they are, usually with a password, and Django records the answer in the session, the small store on the server that Chapter 28 explores. The browser keeps only a cookie with the session’s key.

Two details matter for safety. When a person signs in, Django gives the session a new key, so a key someone saw before sign-in is useless afterwards; this chapter’s tests observe it. And signing out is a POST: Django’s documentation says its LogoutView “Logs a user out on POST requests”, and allauth’s sign-out page only asks when it is opened with a GET. That is Chapter 26’s rule about links and forms, applied to accounts.

Why a package, and why this one

New Tool: django-allauth

What problem exists? Sign-up, sign-in, sign-out, email confirmation, limits on repeated failed sign-ins, and sign-in through other services are each easy to start and hard to finish safely.

What did people do before? They wrote each page with Django’s own views and forms, as The Custom Way below starts to, and added a separate package for each provider.

What is it? django-allauth is a Django package that provides all of these pages and rules, for both ordinary accounts and accounts at other services, with settings for what to ask and how to behave.

Why use it? One maintained package covers this chapter, the provider sign-in, and Chapter 29’s two-factor sign-in, and it works with a custom user model. It is a dependency, so it is pinned to an exact version and recorded in an ADR.

Now let’s use it. Step 3 adds it with uv add, configures it for Otahque’s email-only user, and runs its migrations.

Table 27.1 shows who checks what once it is in place. Otahque’s own code is small, and it sits only where the community’s rules differ from allauth’s defaults.

A custom user, and email-only sign-in

Chapter 17 built accounts.User without a username: members sign in with their email. allauth’s documentation describes exactly this case. Three settings say it: there is no username field, the login method is the email, and sign-up asks for the email and the password twice. Otahque keeps everything else Chapter 17 and 21 decided, and allauth works with it: the email is still lower-cased on save, and the database still refuses a second account for the same address.

Extra details at sign-up, and a profile

Members choose a display name, shown on the pages of events they organize, and may give a time zone, which Chapter 28 will use to show them event times. The display name already lives on User. The time zone goes on a new model, Profile, one row per member, linked one-to-one. allauth asks for extra fields through a small form you name in settings: its signup() method runs once the account exists, and saves the extra details.

A profile row is made the first time it is needed, by Profile.of(user). That one path covers every way a member can arrive: the sign-up page, a provider, createsuperuser, and the members created in earlier chapters.

New Concept: a page that cannot reach anyone else

What problem exists? A profile page at /members/7/edit/ invites someone to try /members/8/edit/. Every such page needs an ownership check, and one forgotten check exposes every account.

What did people do before? They put the member’s id in the address and checked it on every request.

What is it? The profile page reads no id at all. It edits request.user, the member Django signed in, so there is no other member it could reach.

Why use it? The safest check is the one that cannot be forgotten, because there is nothing to check.

Now let’s use it. Step 5 builds /accounts/profile/ this way, and its tests send crafted fields that change nothing.

Real addresses only

Django’s email field already refuses text that is not an address. A disposable address is different: a working inbox from a service such as Mailinator, used for minutes and then abandoned, often to sign up many times. Otahque refuses them at sign-up. The list of such domains is long and changes daily, so Otahque uses a maintained one, the disposable-email-domains package, which holds about ten thousand domains in a plain Python set. allauth provides a place for the check: its adapter, a class whose methods allauth calls at fixed moments, and whose clean_email() method sees every address at sign-up. A setting lists any domain the community chooses to accept anyway.

Sign-in with Google and GitHub, and linking accounts

Many members already have a Google or GitHub account. With a provider, the person signs in at Google or GitHub, which tells Otahque, through a standard called OAuth, that this person controls a confirmed email address. Figure 27.4, in Step 9, shows the steps.

One rule matters more than the rest. A provider vouches for an email address, not for an Otahque account. If an account already exists for that address, Otahque does not join the two on its own: someone could have signed up with that address and never confirmed it, and the provider’s word does not prove who controls the Otahque account. So the page says the address already has an account and asks the person to sign in to it first; signed in, they connect the provider from Connected accounts. Figure 27.3 shows the two outcomes.

Provider credentials are secrets, like Chapter 8’s secret key, so they live in .env, never in Git and never in the database. allauth’s documentation says that setting them up in the admin “effectively stores secrets in your database”. In tests, nothing talks to Google: the tests build the provider’s answer themselves, so they run offline and the same way every time.
