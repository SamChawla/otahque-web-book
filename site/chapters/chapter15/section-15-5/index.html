Checkpoint: Quiz and Challenge

Quiz

Que. 1 Why is a member’s email address not the member’s primary key?

Flip to check your answerFold answer back

Answer. A primary key must identify one row and never change. A person can change their email address, so it is an attribute with a uniqueness rule. A meaningless id never needs to change, so every registration that refers to it stays correct.

Que. 2 Which table holds the foreign key between events and registrations, and why?

Flip to check your answerFold answer back

Answer. The registration table, as event_id. One event has many registrations, and the many side holds the key; an event row would need an unknown number of columns to list its registrations.

Que. 3 Why does cancelling change a status instead of deleting the registration?

Flip to check your answerFold answer back

Answer. A deleted row leaves no trace, so the member’s history and the reason a place was released are lost. A status, with cancelled_at, keeps the history Chapter 2 asked for, and the partial unique index still allows the member to register again.

Que. 4 The lab declared foreign keys with REFERENCES, yet the orphan registration was accepted. What was missing?

Flip to check your answerFold answer back

Answer. PRAGMA foreign_keys = ON on that connection. SQLite checks foreign keys only on connections that turn the check on. Django’s SQLite backend does this for every connection it opens.

Que. 5 Why can no constraint in this chapter stop two people from taking the last place?

Flip to check your answerFold answer back

Answer. The capacity rule spans many rows: it compares a count of active registrations with the event’s capacity. Each constraint here looks at one row, or at duplicates of one row. Two requests can each count one free place before either saves, so the protection needs a transaction that locks and rechecks, which Chapter 33 adds.

Then add a good row (Sai organizes event 7) and a bad row (a second current assignment for the same pair), and show that a revoked assignment followed by a new one is accepted.

Answer. Add the table and index to SCHEMA, after the registration index. An empty value in SQL is NULL, and the test for it is IS NULL:

../practice/challenge_lab.py (end of SCHEMA)

CREATE TABLE organizer_assignment (
    id INTEGER PRIMARY KEY,
    event_id INTEGER NOT NULL REFERENCES event (id),
    member_id INTEGER NOT NULL REFERENCES member (id),
    assigned_at TEXT NOT NULL,
    revoked_at TEXT
);
CREATE UNIQUE INDEX one_current_assignment
    ON organizer_assignment (event_id, member_id)
    WHERE revoked_at IS NULL;
"""

What We Learned

  • A relational database keeps each kind of thing in its own table and each fact in one place, so a change is made once and cannot leave copies that disagree.
  • A primary key identifies one row and never changes; a foreign key, on the side that has many, refers to it.
  • Crow’s foot marks give each end of a relationship its maximum (nearer the box) and minimum (further out); read every relationship in both directions.
  • A relationship with facts of its own, such as a registration’s status and times, is an association entity with its own key.
  • Constraints refuse bad rows whatever code saves them, but rules about who acts, or about actions that overlap, need later controls.
  • SQLite checks foreign keys only when a connection asks; Django asks for its own connections, and the lab had to ask for itself.
  • The ERD is a reviewed, versioned proposal with its status, open questions, and out-of-scope list written down.
