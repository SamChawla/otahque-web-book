What You Need to Know

From one spreadsheet to related tables

Sam’s spreadsheet is a single table: each row holds one registration, and every column a reader might want sits in the same row. That shape is easy to start with, and it fails in three predictable ways. A fact that appears in many rows, such as Sai’s email address, has to be changed in all of them, and missing one leaves the table contradicting itself. A fact that lives only in a row, such as Raj’s registration, disappears when the row is deleted. And nothing stops a row that should not exist, such as a registration for an event that was never arranged.

New Concept: a relational database

What problem exists? Records that many people read and change must not contradict each other, must survive a restart, and must be refused when they break a rule.

What did people do before? Spreadsheets and flat files, with every fact repeated wherever it was needed and every rule kept in someone’s head.

What is a relational database? A store that keeps each kind of thing in its own table. Each row is one record, and each column holds one kind of value for every row. Tables refer to each other through identifying values instead of copying each other’s data.

Why use one? Each fact is stored once, so it is changed in one place. The database can enforce rules on every row, however that row arrived. Django is built to work with relational databases, and the project uses SQLite now and PostgreSQL from Chapter 32.

Now let’s use it. The rest of this part reads a few small tables and the rules that connect them; How We Build It designs Otahque’s own.

The two shapes are side by side in Figure 15.1. On the right, the event titles, the member email addresses, and the registrations are separate tables. A registration row holds only the identifying numbers of its event and its member, and a status. When Sai changes her email address, one row changes, and every registration that refers to her sees the change. When Raj cancels, his row stays and its status says so.

The general rule is one fact in one place. Database designers call the work of reaching it normalization, and Under the Hood names its usual stages. You need only the plain rule: if a value would be repeated in many rows, it probably belongs in a table of its own, and the rows should refer to it.

Entities, attributes, and keys

An entity is a kind of thing the system keeps records about: a member, an event, a registration. Each entity becomes a table. An attribute is one fact about an entity, such as an event’s title or capacity, and becomes a column. Reading Chapter 2 for nouns is a good start, but not every noun earns a table. “Venue” is a noun, yet Otahque’s first release only needs to show where an event takes place, so the location is an attribute of the event. “Attendee” is a noun too, but Chapter 2 defined an attendee as a member registered for a particular event, so an attendee is a member plus a registration, not a third kind of person.

New Concept: primary keys and foreign keys

What problem exists? One row must be able to point at exactly one other row, and keep pointing at it even when that row’s details change.

What did people do before? They identified things by a name or an email address, which change and which two people can share.

What are keys? A primary key is a column whose value identifies one row in its table and never changes. A foreign key is a column in another table that holds a primary key value, so that its row refers to that row.

Why use them? A registration that stores member_id 1 refers to Sai whatever her email address becomes, and the database can check that a member with that key exists.

Now let’s use it. Every entity in this chapter gets a plain numeric primary key called id, the form Django creates by default in Chapter 16.

Choose identity before details. An email address looks unique, and Otahque may well require it to be unique, but it is still a detail a person can change, so it is an attribute with a uniqueness rule, not the key. A title is not even unique: two years of the same meetup can share one. A key such as id carries no meaning at all, which is exactly why it never needs to change.

The foreign key always goes on the side that has many. One event has many registrations, and each registration belongs to one event, so the registration row holds event_id. The event row cannot hold its registrations: it would need a column for each one, and nobody knows in advance how many there will be. Written in SQL, the language relational databases understand, the registration table begins like this. It is a read-only example; you will write and run your own in the lab.

sql

CREATE TABLE registration (
    id INTEGER PRIMARY KEY,
    event_id INTEGER NOT NULL REFERENCES event (id),
    member_id INTEGER NOT NULL REFERENCES member (id),
    status TEXT NOT NULL
);

REFERENCES event (id) declares the foreign key: every value in event_id must match an id in the event table. NOT NULL says the column must have a value, so no registration can belong to no event.

Relationships, cardinality, and optionality

A relationship says how rows of two entities are connected. Two questions describe each end of it. Cardinality asks how many: at most one, or many? Optionality asks whether any must exist: can the number be zero? Say each relationship aloud in both directions before drawing anything. “One event has zero or more registrations” and “each registration belongs to exactly one event” are two readings of the same line.

New Concept: crow’s foot notation

What problem exists? A line between two boxes says that they are related, but not how many rows take part or whether any must.

What did people do before? They wrote the rules in notes beside the drawing, where they drifted away from it.

What is crow’s foot notation? A way of marking both answers at each end of a relationship line. The mark nearer the box gives the maximum: a bar for one, a three-pronged “crow’s foot” for many. The mark further out gives the minimum: a circle for zero, a bar for one.

Why use it? It is a widely used ERD notation, it reads the same on paper and in tools, and the Mermaid text format you will use in the project draws it.

Now let’s use it. Figure 15.2 shows the four ends you will need, and one relationship read in both directions.

The marks you read are the ones at the far end. To say how many registrations one event has, start at Event and read the marks beside Registration. Most relationships in this book are one-to-many, like this one. A one-to-one relationship, where each side has at most one partner, would suit a member profile; Chapter 20 shows the idea, and Chapter 27 decides whether Otahque needs one. A many-to-many relationship needs the next idea.

When a relationship has facts of its own

A member can register for many events, and an event has many registered members. That is a many-to-many relationship, and no single foreign key can express it: neither table can hold a list of the other’s keys. The usual answer is a table in between, whose rows each pair one member with one event. In Otahque that table is not a mere link, because each pairing has facts of its own: a registration has a status, the time it was made, and, if it was cancelled, the time of cancellation.

New Concept: an association entity

What problem exists? A many-to-many relationship that also has its own facts, such as when it started and whether it still holds.

What did people do before? They stored only the pairing, and kept the extra facts elsewhere or not at all, which is how Raj’s cancellation was lost.

What is an association entity? An entity whose rows each connect one row of one entity with one row of another, and carry the facts about that connection. It has its own primary key and a foreign key to each side.

Why use one? Registration is the centre of Otahque. Its status decides whether a place is counted, and keeping cancelled rows keeps the history that Chapter 2’s cancellation rule asks for.

Now let’s use it. Otahque’s design has two association entities: Registration, between members and events, and Organizer assignment, which records that a member organizes an event until the assignment is revoked.

Keeping cancelled rows raises a question. If Sai cancels and later registers again for the same event, there will be two rows for the same member and event, and that is correct: one cancelled, one active. The rule Otahque needs is narrower than “one row per member and event”. It is “at most one active row per member and event”. The SQLite documentation illustrates the same shape with a team that may have many members but only one leader: the rule applies only to the rows that match a condition. Databases express it with a partial unique index, which you will build in the lab:

sql

CREATE UNIQUE INDEX one_active_registration
    ON registration (event_id, member_id)
    WHERE status = 'active';

Only rows whose status is active are included in this index, and within it each pair of event and member may appear once. Cancelled rows are outside it, so any number of them may exist.

What the database can refuse, and what it cannot

A constraint is a rule the database checks on every row it stores, refusing the change if the rule would be broken. Table 15.1 lists the kinds this chapter uses.

Constraints matter because they hold whichever code saves the row: a form, the admin, an import script, or a mistake in a view. Django’s own checks, which begin with forms in Chapter 24, give people helpful messages first. The database is the last line of defence, and it applies the same rules every time.

It also has limits. Some of Chapter 2’s rules are about who is acting, or about actions that overlap, and a single row cannot show that they are broken. Table 15.2 names those rules and where the book enforces them.

The first row shows a design choice. Otahque stores each event’s capacity, but not the number of places taken. That number is derived: it is counted from the active registrations whenever it is needed. A stored counter would be a second copy of the same fact, which would have to be kept equal to the count on every registration and cancellation. Some systems do keep counters, to avoid counting on every page, and repair them when they drift; that is a trade-off to make with measurements, not at the start.

What an ERD shows

An ERD can be drawn at different levels of detail. A conceptual diagram shows only the entities and how they relate. A logical diagram adds the attributes and the keys. A physical diagram adds the database’s column types, indexes, and storage details. This chapter’s ERD is logical: four entities, their keys and main attributes, and the relationships between them, with the rules beside it. Column types belong to Django’s fields in Chapter 16.

You will record the ERD as text, in a format called Mermaid, which several tools, including GitHub, draw as a diagram. The text itself is the record: it can be reviewed line by line, compared in Git, and read without any tool. Here is the relationship from Figure 15.2 in Mermaid:

Output

erDiagram
    EVENT ||--o{ REGISTRATION : "has"

|| is the exactly-one end at EVENT, and o{ is the zero-or-more end at REGISTRATION. Each two-character mark is read like the drawn ends: the character further from its entity is the minimum, and the one nearer the entity is the maximum.

Python’s sqlite3 module

The lab in this chapter needs a real database that refuses real rows, without touching the project. Python already includes one.

New Tool: Python’s sqlite3 module and an in-memory database

What problem exists? To watch constraints refuse rows, we need a database we can create, break, and throw away freely, without installing a server or touching the project’s db.sqlite3.

What did people do before? They installed a database server, created a practice database, and had to remember to remove it.

What is it? SQLite is a small database engine that keeps a whole database in one file, and Python’s standard library includes it as the sqlite3 module. Connecting to the special name :memory: creates a database that exists only in memory and vanishes when the program ends.

Why use it? There is nothing to install and nothing left behind, and it is the same SQLite engine that Django uses for the project’s development database.

Now let’s use it. Check which SQLite version your Python includes. Run this from the Chapter 14 project folder; it is the same in PowerShell and in macOS/Linux/WSL.

Terminal

uv run python -m sqlite3 -v

Output

SQLite version 3.53.1

That is the version bundled with Python 3.14.9 on Windows; macOS and Linux builds may report a different one. Django 6.1 supports SQLite 3.37.0 and later, and partial indexes need 3.8.0 or later, so any version Django accepts is enough here. Without -v, python -m sqlite3 opens an interactive shell where you type SQL; type .quit to leave it. The lab uses a small script instead, so that every run starts the same way.

Under the Hood: how the database decides to refuse a row

Before storing a row, SQLite checks each rule in turn. For NOT NULL and CHECK it looks only at the new row. For UNIQUE and the partial unique index, it looks the new values up in the index that backs the rule and refuses the row if a matching entry exists; a partial index simply leaves out the rows that do not match its condition. For a foreign key, it looks for a row in the parent table with that primary key and refuses the change if there is none. A refusal reaches Python as an sqlite3.IntegrityError, and the change is not stored. One rule surprises almost everyone: for compatibility with old databases, SQLite does not check foreign keys unless the connection asks it to, through a setting called a pragma, and that setting cannot be changed in the middle of a transaction. Django’s SQLite backend turns the check on for every connection it opens, but a connection you open yourself with sqlite3.connect() starts with it off. Finally, the plain rule of one fact in one place is what database theory calls normalization; its usual stages are named first, second, and third normal form, and this book uses the plain rule rather than the formal definitions.

The pragma looks like this. The first line asks for the current setting, which is 0 (off) on a new connection; the second turns checking on for that connection only.

sql

PRAGMA foreign_keys;
PRAGMA foreign_keys = ON;

Django’s own line is in its source, in django/db/backends/sqlite3/base.py, inside the get_new_connection method of the version installed in your project’s .venv folder. It is why the project will never need the pragma, and why your lab will.

In practice: keeping personal data where it belongs

Situation. Each entity in the design is a place where personal data could end up. It is tempting to add a phone number, a postal address, or a date of birth to the member entity in case they are useful later.

Application. Store only what a Chapter 2 rule needs, in the one entity it describes. The member entity holds an email address and a display name; a registration holds no copy of either, only member_id. Organizers will see participants through registrations, under the access rules of Chapter 30, rather than through a copied list.

Consideration. Chapter 2 left the exact contact details as an open decision, so the ERD names that question instead of guessing. Every column added later is something to protect, to explain to the people it describes, and eventually to delete.

You now have the vocabulary to design Otahque’s first data model: tables, keys, relationships, association entities, constraints, and the rules that need more than structure. How We Build It applies it to Chapter 2’s rules and checks the result against a real database.
