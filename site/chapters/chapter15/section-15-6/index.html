Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 and L2 check what you have just learned. L3 asks you to reason about a failure that tests rarely catch. L4 and L5 look ahead to a growing application: attempt them now, and return to them later. They are extension questions, not a gate to the next chapter. Each code proof is a short file in the practice folder; run it from the project folder with uv run python ../practice/ followed by the file name, in PowerShell, a macOS shell, or Linux/WSL Bash.

L1 (Junior): What are primary and foreign keys, and which side of a one-to-many relationship holds the foreign key?

What the interviewer is testing: Can you explain identity and reference, and place a key correctly?

Flip to check your answerFold answer back

Perfect answer: A primary key is the column whose value identifies one row in its table; it must be unique, present, and stable, so a meaningless number is usually better than a name or an email address. A foreign key is a column in another table that holds such a value, so its row refers to exactly one row elsewhere, and the database can refuse a reference to a row that does not exist. In a one-to-many relationship the foreign key goes on the many side: each registration holds the event_id of its one event, because the event cannot hold a variable number of registration columns.

Behind the scenes:

keys (summary)

insert a registration with event_id 99
look up 99 in event's primary key index
not found -> refuse the row: FOREIGN KEY constraint failed
found -> store the row

Code proof: a reference to a missing event is refused, and the valid one stays:

../practice/l1_keys.py

import sqlite3

db = sqlite3.connect(":memory:", autocommit=True)
db.execute("PRAGMA foreign_keys = ON")
db.execute("CREATE TABLE event (id INTEGER PRIMARY KEY)")
db.execute("""CREATE TABLE registration (
    id INTEGER PRIMARY KEY,
    event_id INTEGER NOT NULL REFERENCES event (id))""")
db.execute("INSERT INTO event VALUES (7)")
db.execute("INSERT INTO registration VALUES (1, 7)")
try:
    db.execute("INSERT INTO registration VALUES (2, 99)")
except sqlite3.IntegrityError as error:
    print(error)
print(db.execute("SELECT * FROM registration").fetchall())

Output

FOREIGN KEY constraint failed
[(1, 7)]

Common mistakes:

  • Using an email address or a title as the primary key.
  • Putting the foreign key on the one side, and then needing a list column.
  • Assuming SQLite checks a declared foreign key without the pragma.

Follow-up the interviewer might ask:

  • “When might a primary key made of two columns make sense?”
  • “What should happen to registrations when their event is deleted?”

L2 (Mid-Level): Why model Registration as an entity rather than a plain many-to-many link between members and events?

What the interviewer is testing: Can you recognize a relationship that carries its own facts and history?

Flip to check your answerFold answer back

Perfect answer: Members and events are many-to-many, so some table in the middle must pair them. If that pairing had no facts, a plain link holding the two keys would do, and Django can create one for you. But in Otahque the pairing is the most important record in the product: it has a status that decides whether a place is counted, a time it was made, and a time it was cancelled. Those facts belong to the pairing, not to either side. As its own entity, Registration has its own key and two foreign keys, can be cancelled by status rather than deleted, and can appear more than once for the same pair over time, with a partial unique index allowing only one active row. That keeps the history a support request or a dispute will need.

Behind the scenes:

association entity (summary)

plain link: (member_id, event_id) and nothing else
entity: id, member_id, event_id, status, times
cancel: change the status; the row stays
again: a new active row; the old one is history

Code proof: Raj, member 2, cancels and registers again; both rows remain:

../practice/l2_history.py

import sqlite3

db = sqlite3.connect(":memory:", autocommit=True)
db.execute("""CREATE TABLE registration (
    id INTEGER PRIMARY KEY, event_id INTEGER,
    member_id INTEGER, status TEXT)""")
db.executemany(
    "INSERT INTO registration VALUES (?, ?, ?, ?)",
    [(1, 7, 2, "cancelled"), (2, 7, 2, "active")],
)
for row in db.execute(
        "SELECT * FROM registration WHERE member_id = 2"):
    print(row)

Output

(1, 7, 2, 'cancelled')
(2, 7, 2, 'active')

The question marks are placeholders: sqlite3 fills them from the tuples, safely, in order. Never build SQL by pasting values into the string.

Common mistakes:

  • Storing the status on the member or the event, where it cannot belong to one pairing.
  • Deleting the link row to cancel, and losing the history.
  • Making the pair unique for ever, so nobody can register again.

Follow-up the interviewer might ask:

  • “How would you show a member their registration history?”
  • “What other relationship in Otahque carries its own facts?”

L3 (Senior): How do you guarantee one active registration per member and event while keeping history, and why is an application check alone not enough?

What the interviewer is testing: Can you see why check-then-insert fails when requests overlap, and put the guarantee where it holds?

Flip to check your answerFold answer back

Perfect answer: Keep every registration row and express the rule in the database as a partial unique index on event and member, limited to rows whose status is active. Cancelled rows fall outside it, so history and re-registration both work. An application check, “is there already an active registration?”, is still useful for a friendly message, but it cannot be the guarantee: two requests from the same member, such as a double click, can both run the check before either saves, both see nothing, and both insert. The index is checked as each row is stored, so the second insert is refused however the requests interleave, and the view turns the refusal into a clear result. In Django this becomes a UniqueConstraint with a condition, in Chapter 21.

Behind the scenes:

check then insert (summary)

request A: count active rows -> 0
request B: count active rows -> 0
request A: insert -> stored
request B: insert -> stored, or refused by the index

Code proof: the same interleaving, first without the index, then with it:

../practice/l3_race.py

import sqlite3

TABLE = """CREATE TABLE registration (
    event_id INTEGER, member_id INTEGER, status TEXT)"""
INDEX = """CREATE UNIQUE INDEX one_active
    ON registration (event_id, member_id)
    WHERE status = 'active'"""
CHECK = """SELECT COUNT(*) FROM registration
    WHERE event_id = 7 AND member_id = 1
    AND status = 'active'"""
ADD = "INSERT INTO registration VALUES (7, 1, 'active')"

for label, schema in [("no index", [TABLE]),
                      ("index", [TABLE, INDEX])]:
    db = sqlite3.connect(":memory:", autocommit=True)
    for sql in schema:
        db.execute(sql)
    seen = [db.execute(CHECK).fetchone()[0] for _ in "AB"]
    try:
        db.execute(ADD)
        db.execute(ADD)
        result = "both stored"
    except sqlite3.IntegrityError:
        result = "second refused"
    print(f"{label}: checks saw {seen}, {result}")

Output

no index: checks saw [0, 0], both stored
index: checks saw [0, 0], second refused

The proof plays both requests on one connection, in the order a real overlap can take; Chapter 33 tests true concurrency on PostgreSQL.

Common mistakes:

  • Relying on a check in the view as the only protection.
  • Using a full unique pair, which blocks registering again.
  • Letting the refusal surface as an error page instead of a message.

Follow-up the interviewer might ask:

  • “Would the same index protect capacity? Why not?”
  • “How would you tell a duplicate from other integrity errors in the view?”

L4 (Staff): Should Otahque store a count of places taken, or derive it? Where does each rule about capacity live?

What the interviewer is testing: Looking ahead: can you weigh one source of truth against read cost, and name what actually enforces an invariant?

Flip to check your answerFold answer back

Perfect answer: Start from the invariant: active registrations for an event never exceed its capacity. Store the capacity, which is a decision, and derive the count, which is a consequence; counting active registrations for one event is cheap with an index. A stored counter is a second copy of the same fact. Every registration, cancellation, import, and correction must update it in the same transaction, and any path that forgets makes it drift, which is why systems that keep counters also run reconciliation jobs. Neither choice enforces the invariant on its own: two requests can both see one free place. Enforcement belongs in a transaction that locks the event row, recounts, and inserts, which Chapter 33 builds on PostgreSQL. A counter becomes worth its cost only when measurements show that counting is the bottleneck, and then it is a cache of the derived value, not the authority.

Behind the scenes:

capacity (summary)

stored: event.capacity          the decision
derived: count of active rows   the consequence
counter: a copy that can drift  only after measuring
enforce: lock, recount, insert  one transaction

Code proof: one path forgets the counter, and the copy disagrees with the count:

../practice/l4_counter.py

import sqlite3

db = sqlite3.connect(":memory:", autocommit=True)
db.execute("""CREATE TABLE event (
    id INTEGER PRIMARY KEY, capacity INTEGER,
    taken INTEGER)""")
db.execute("""CREATE TABLE registration (
    event_id INTEGER, status TEXT)""")
db.execute("INSERT INTO event VALUES (7, 2, 0)")
for keeps_counter in (True, False):
    db.execute("INSERT INTO registration"
               " VALUES (7, 'active')")
    if keeps_counter:
        db.execute("UPDATE event SET taken = taken + 1")
stored = db.execute("SELECT taken FROM event").fetchone()[0]
counted = db.execute("""SELECT COUNT(*) FROM registration
    WHERE status = 'active'""").fetchone()[0]
print(f"stored counter: {stored}, derived count: {counted}")

Output

stored counter: 1, derived count: 2

Common mistakes:

  • Treating a counter column as the authority and trusting it.
  • Believing a CHECK constraint can compare a count across rows.
  • Adding a counter for speed without a measurement.

Follow-up the interviewer might ask:

  • “If you did add a counter, how would you detect and repair drift?”
  • “What changes when capacity is reduced below the current count?”

L5 (Lead): How should the ERD evolve as waitlists, attendance, and several communities arrive, without breaking existing records?

What the interviewer is testing: Looking ahead: can you lead schema change as a reviewed decision, protect existing data, and keep different facts in different places?

Flip to check your answerFold answer back

Perfect answer: Treat the ERD as the place where a data change is proposed and reviewed before any migration exists. Each new capability gets the smallest structure its rules need, and different facts stay separate: a waitlist position is not a registration status, and attendance is its own record with its own actor and time, because a registration does not prove anyone came. Several communities change the meaning of every uniqueness rule, which then holds within a community, so that change is designed in Chapters 67 and 68, not slipped in. For the change itself, existing rows constrain what is possible: a new column must start empty or with a default, and data is moved by a migration that can be tested on a copy. As lead, I make sure each change has a reason, an owner, updated rules and open questions in the ERD, tests for the rules it touches, and a record of the decision.

Behind the scenes:

schema change (summary)

propose in the ERD -> review the rules it touches
add new columns empty, or with a default
migrate and move existing data -> test on a copy
record the decision and its reason

Code proof: existing rows decide which new column can be added:

../practice/l5_evolve.py

import sqlite3

db = sqlite3.connect(":memory:", autocommit=True)
db.execute("CREATE TABLE registration"
           " (id INTEGER, status TEXT)")
db.execute("INSERT INTO registration VALUES (1, 'active')")
changes = [
    "ALTER TABLE registration ADD COLUMN attended_at TEXT",
    "ALTER TABLE registration ADD COLUMN source"
    " TEXT NOT NULL",
]
for sql in changes:
    column = sql.split()[5]
    try:
        db.execute(sql)
        print("added:", column)
    except sqlite3.OperationalError as error:
        print("refused:", error)
print(db.execute("SELECT * FROM registration").fetchall())

Output

added: attended_at
refused: Cannot add a NOT NULL column with default value NULL
[(1, 'active', None)]

The first change is allowed because the existing row can hold an empty value. The second is refused because the existing row would break NOT NULL. Chapter 18 shows how Django’s migrations handle both cases, including data migrations. The attended_at column shows the mechanics only: the design keeps attendance in a record of its own.

Common mistakes:

  • Changing the schema first and the documented design afterwards, or never.
  • Folding attendance or waitlist position into the registration status.
  • Adding a required column to a table that already holds data, without a default or a data step.

Follow-up the interviewer might ask:

  • “How would uniqueness rules change when there are several communities?”
  • “Who should approve a change to the data model, and what evidence should they see?”
