How We Build It

Start from Chapter 14, in the directory containing manage.py, with your own .env, the locked environment, 18 passing tests, and the Chapter 14 work committed to your Git repository. This chapter changes no Python, template, or stylesheet file. It adds one document to the project, docs/design/erd.md, and one throwaway script, relational_lab.py, in a practice folder beside the project folder, outside it, so that the lab never becomes part of Otahque. At the end, the design is committed, the lab shows the database refusing each bad row, and the project still has no tables.

The Custom Way

This illustration shows Sam’s spreadsheet as a single database table; do not add it to the project:

illustration_only/one_table.sql (not part of the project)

CREATE TABLE sheet (
    event_title TEXT,
    event_date TEXT,
    member_name TEXT,
    member_email TEXT
);
-- Raj cancels: his row, and every fact in it, is gone.
DELETE FROM sheet WHERE member_name = 'Raj';

It is quick to create and it accepts anything. Every event detail and every email address is repeated in each row that needs it. No column identifies a person, so two Sais cannot be told apart, and a deleted row leaves no trace that it existed. Nothing refuses an empty email address or an event that was never arranged. The approach below starts from the rules instead, gives each kind of thing its own table and key, and checks the result against a real database before anything reaches Django.

The Recorded Way

Design chapters build documents, so this part designs and records rather than writing Django code. Each step either adds to docs/design/erd.md or tests an idea in the lab.

Step 1: Check the starting point

Run the Chapter 14 tests beside manage.py, in PowerShell, a macOS shell, or Linux/WSL Bash:

Terminal

uv run python manage.py test events

Expected result, shortened with ... where lines are left out:

Output

Found 18 test(s).
System check identified no issues (0 silenced).
..................
...
Ran 18 tests in ...

OK

Next, look for a file called db.sqlite3 beside manage.py. You probably have one: Chapter 6 explained that the development server may create an empty database file while checking migrations. A file is fine; tables are what this chapter must not create yet. If the file exists, ask SQLite to list the names of everything in it. The command is split over two lines, with each shell’s own continuation character. In PowerShell, beside manage.py:

PowerShell

uv run python -m sqlite3 db.sqlite3 `
    "SELECT name FROM sqlite_schema"

In a macOS shell or Linux/WSL Bash, beside manage.py:

Terminal

uv run python -m sqlite3 db.sqlite3 \
    "SELECT name FROM sqlite_schema"

Expected result: nothing at all. sqlite_schema is SQLite’s own list of the tables and indexes in a database, so an empty answer means there are none. If there is no db.sqlite3, skip this check; do not run the command, because connecting to a missing file creates an empty one.

Common Error: running migrate to get a database

It is tempting to run uv run python manage.py migrate so that the database has something in it. Do not do it yet. migrate creates Django’s built-in tables, including a table of users, and Chapter 17 must choose Otahque’s user model before those tables exist, because changing the user model afterwards is difficult. A second trap: SQLite’s own command-line program accepts commands such as .tables, but python -m sqlite3 treats its argument as SQL, so .tables there fails with OperationalError and a syntax error near “.”. Use the SELECT above.

If the query lists tables such as django_migrations or auth_user, migrate has already been run. Keep the file: rename it, for example to db-before-ch15.sqlite3, so that the project starts Chapter 17 with no tables, and keep the renamed copy until Chapter 17 confirms that nothing in it is needed.

Finally, create the practice folder beside the project folder. The same command works in PowerShell and in a macOS shell or Linux/WSL Bash; PowerShell also prints a short table describing the new folder:

Terminal

mkdir ../practice

Step 2: Find the entities

Open Chapter 2’s rules and Sam’s spreadsheet, and list every noun that names something Otahque might store. Then decide, for each, whether it is a kind of thing with its own facts and identity, a fact about something else, or outside the first release. Table 15.3 records our decisions.

Create the folders docs/design beside manage.py, and in them a file called erd.md. Start it with its status, so that nobody mistakes it for an approved design:

Step 3: Add keys and relationships

Give each entity an id primary key. Then read each relationship aloud in both directions, and put the foreign key on the side that has many:

  • One member makes zero or more registrations; each registration is made by exactly one member.
  • One event has zero or more registrations; each registration is for exactly one event.
  • One member holds zero or more organizer assignments; each assignment belongs to exactly one member.
  • One event has zero or more organizer assignments; each assignment is for exactly one event.

An event may have no organizer assignment at all, because who appoints organizers, and whether every event needs one, is still an open decision. Add the diagram section to erd.md, below the status lines. The diagram sits between a line ~~~mermaid and a line ~~~, which Markdown treats as a fenced block and Mermaid-aware viewers draw:

docs/design/erd.md (continued)


## Diagram

~~~mermaid
erDiagram
    MEMBER ||--o{ REGISTRATION : "makes"
    EVENT ||--o{ REGISTRATION : "has"
    MEMBER ||--o{ ORGANIZER_ASSIGNMENT : "holds"
    EVENT ||--o{ ORGANIZER_ASSIGNMENT : "is run through"
    MEMBER {
        int id PK
        text email UK
        text display_name
    }
    EVENT {
        int id PK
        text title
        datetime starts_at "an instant, in UTC"
        datetime ends_at "after starts_at, in UTC"
        text timezone "IANA name"
        text location
        int capacity "more than 0"
        text status "draft, published, cancelled"
    }
    REGISTRATION {
        int id PK
        int event_id FK
        int member_id FK
        text status "active or cancelled"
        datetime registered_at
        datetime cancelled_at "empty until cancelled"
    }
    ORGANIZER_ASSIGNMENT {
        int id PK
        int event_id FK
        int member_id FK
        datetime assigned_at
        datetime revoked_at "empty while current"
    }
~~~

Each attribute line gives a type, a name, an optional key mark (PK, FK, or UK for unique), and an optional note in quotes. The types are words for people, not database column types; Django’s fields decide those in Chapter 16. starts_at and ends_at are instants, stored in UTC, and an event ends after it starts. timezone keeps the event’s own time-zone name, used for both, such as Europe/London, so pages can show the local time Chapter 2 asked for. Figure 15.3 draws the same design.

Common Error: a line without its marks, or a key on the wrong side

A line between two boxes with no marks at its ends says nothing about how many rows take part, and two readers will assume different answers. Mark both ends. If you find yourself wanting an event column that holds several registration numbers, the foreign key is on the wrong side: it belongs in the registration, the side that has many. And if a relationship needs a status or a time, it is an entity of its own, not a bare link.

Step 4: Write the lab test-first

A diagram can be wrong in ways that only a database reveals. The lab writes down, first, the rows the design says must be refused. Then it runs them against tables that have columns but almost no rules, and we watch every bad row being accepted. That is the red stage, the same habit as a test written before the code since Chapter 9.

Create relational_lab.py in the practice folder:

../practice/relational_lab.py

"""Chapter 15 lab: see which bad rows are refused."""
import sqlite3

SCHEMA = """
CREATE TABLE member (
    id INTEGER PRIMARY KEY,
    email TEXT NOT NULL UNIQUE
);
CREATE TABLE event (
    id INTEGER PRIMARY KEY,
    title TEXT NOT NULL,
    capacity INTEGER NOT NULL
);
CREATE TABLE registration (
    id INTEGER PRIMARY KEY,
    event_id INTEGER NOT NULL,
    member_id INTEGER NOT NULL,
    status TEXT NOT NULL
);
"""

GOOD_ROWS = [
    "INSERT INTO member VALUES (1, 'sai@example.org')",
    "INSERT INTO event VALUES (7, 'Python meetup', 2)",
    "INSERT INTO registration VALUES (1, 7, 1, 'active')",
]

BAD_ROWS = {
    "orphan registration": "INSERT INTO registration"
        " VALUES (2, 99, 1, 'active')",
    "capacity of 0": "INSERT INTO event"
        " VALUES (8, 'Data night', 0)",
    "unknown status": "INSERT INTO registration"
        " VALUES (3, 7, 1, 'maybe')",
    "second active place": "INSERT INTO registration"
        " VALUES (4, 7, 1, 'active')",
}


def fresh_database():
    db = sqlite3.connect(":memory:", autocommit=True)
    db.executescript(SCHEMA)
    for sql in GOOD_ROWS:
        db.execute(sql)
    return db


def report(name, error):
    kind, _, detail = str(error).partition(": ")
    print(f"refused   {name}: {kind}")
    if detail:
        print(f"          {detail}")


for name, sql in BAD_ROWS.items():
    db = fresh_database()
    try:
        db.execute(sql)
        print(f"accepted  {name}")
    except sqlite3.IntegrityError as error:
        report(name, error)
    db.close()

Read it from the top. SCHEMA holds the SQL that creates the three tables; only NOT NULL and the email’s UNIQUE are rules so far. GOOD_ROWS are a member (Sai, number 1), an event (number 7, with two places), and Sai’s active registration. BAD_ROWS names four rows that break a Chapter 2 rule, each written as two string literals side by side, which Python joins into one string so that each line stays short: a registration for event 99, which does not exist; an event with no places; a status Otahque does not have; and a second active registration by Sai for the same event. fresh_database() creates a new database in memory, with autocommit=True so that each statement takes effect on its own, builds the schema, and adds the good rows. The loop gives each bad row its own fresh database, so the bad rows cannot affect each other, and prints whether the database accepted or refused it. report() splits SQLite’s message at its first colon so that each line fits on the page.

Because every run builds its database from SCHEMA, nothing carries over between runs. Each change you make in Step 5 changes what the next run creates; there is never an old table to alter. Run the lab from the project folder, so that uv uses the project’s Python. The same command works in PowerShell and in a macOS shell or Linux/WSL Bash:

Terminal

uv run python ../practice/relational_lab.py

Output

accepted  orphan registration
accepted  capacity of 0
accepted  unknown status
accepted  second active place

Every bad row is accepted. That is the result we expect: nothing in the schema says otherwise yet.

Step 5: Add structure until each bad row is refused

Make four edits, and rerun the lab after each.

Common Error: foreign keys declared but not checked

After the first edit below, the schema declares foreign keys. If you add the REFERENCES clauses but not the PRAGMA line, the orphan registration is still accepted, with no error or warning, because SQLite checks foreign keys only on connections that ask for it. Both lines of the edit are needed. Django asks on every connection it opens, which is why the project will not need this line.

First, the foreign keys. In SCHEMA, give the registration table’s two key columns their references:

../practice/relational_lab.py (registration table)

    event_id INTEGER NOT NULL REFERENCES event (id),
    member_id INTEGER NOT NULL REFERENCES member (id),

Then, in fresh_database(), turn foreign-key checking on straight after connecting:

../practice/relational_lab.py (fresh_database)

    db = sqlite3.connect(":memory:", autocommit=True)
    db.execute("PRAGMA foreign_keys = ON")

Run the lab again:

Output

refused   orphan registration: FOREIGN KEY constraint failed
accepted  capacity of 0
accepted  unknown status
accepted  second active place

Second, the checks. A CHECK constraint can be given a name with CONSTRAINT, and SQLite then uses that name in its message, which makes refusals easy to recognize. Change the end of the event table:

../practice/relational_lab.py (event table)

    capacity INTEGER NOT NULL,
    CONSTRAINT positive_capacity CHECK (capacity > 0)
);

and the end of the registration table:

../practice/relational_lab.py (registration table)

    status TEXT NOT NULL,
    CONSTRAINT known_status
        CHECK (status IN ('active', 'cancelled'))
);

Run the lab:

Output

refused   orphan registration: FOREIGN KEY constraint failed
refused   capacity of 0: CHECK constraint failed
          positive_capacity
refused   unknown status: CHECK constraint failed
          known_status
accepted  second active place

Third, the partial unique index. Add it at the end of SCHEMA, after the registration table and before the closing """:

../practice/relational_lab.py (end of SCHEMA)

CREATE UNIQUE INDEX one_active_registration
    ON registration (event_id, member_id)
    WHERE status = 'active';
"""

Output

refused   orphan registration: FOREIGN KEY constraint failed
refused   capacity of 0: CHECK constraint failed
          positive_capacity
refused   unknown status: CHECK constraint failed
          known_status
refused   second active place: UNIQUE constraint failed
          registration.event_id, registration.member_id

All four bad rows are now refused, each by the rule written for it. For a unique index, SQLite names the columns rather than the index.

Common Error: uniqueness that blocks registering again

Writing UNIQUE (event_id, member_id) in the registration table also refuses the second active place, and looks finished. But it refuses every second row for the same member and event, cancelled or not, so a member who cancels can never register again, and the history Chapter 2 asked for has no room. The rule is about active rows only, which is what the partial index’s WHERE says. The last edit tests exactly this.

Fourth, the case that must succeed. Add this block at the end of the file. Sai cancels her registration, registers again for the same event, and the lab shows her history and one count of the places taken:

../practice/relational_lab.py (end of the file)


print()
print("Sai cancels, then registers again:")
db = fresh_database()
db.execute("UPDATE registration SET status = 'cancelled'"
           " WHERE id = 1")
db.execute("INSERT INTO registration"
           " VALUES (5, 7, 1, 'active')")
rows = db.execute("SELECT id, status FROM registration")
for row in rows:
    print(row)
places = db.execute("""
    SELECT event.title, event.capacity,
           COUNT(registration.id)
    FROM event
    JOIN registration ON registration.event_id = event.id
    WHERE registration.status = 'active'
    GROUP BY event.id
""").fetchall()
print(places)
db.close()

The query is the first join of the book: JOIN ... ON puts each registration beside the event its event_id names, WHERE keeps only active registrations, and GROUP BY event.id with COUNT counts them per event. This is the derived count from What You Need to Know.

Run the lab one last time:

Output

refused   orphan registration: FOREIGN KEY constraint failed
refused   capacity of 0: CHECK constraint failed
          positive_capacity
refused   unknown status: CHECK constraint failed
          known_status
refused   second active place: UNIQUE constraint failed
          registration.event_id, registration.member_id

Sai cancels, then registers again:
(1, 'cancelled')
(5, 'active')
[('Python meetup', 2, 1)]

The cancelled row is kept, the new active row is accepted, and the Python meetup has one of its two places taken. The complete lab, as it should now read:

../practice/relational_lab.py (complete)

"""Chapter 15 lab: see which bad rows are refused."""
import sqlite3

SCHEMA = """
CREATE TABLE member (
    id INTEGER PRIMARY KEY,
    email TEXT NOT NULL UNIQUE
);
CREATE TABLE event (
    id INTEGER PRIMARY KEY,
    title TEXT NOT NULL,
    capacity INTEGER NOT NULL,
    CONSTRAINT positive_capacity CHECK (capacity > 0)
);
CREATE TABLE registration (
    id INTEGER PRIMARY KEY,

## Rules the structure holds

- PR-1: at most one active registration per member and
  event (partial unique index on event_id and member_id
  where status is active).
- PR-1, PR-2: a registration refers to a real event and
  a real member (foreign keys).
- PR-2: a cancelled registration keeps its row, with
  its status and cancelled_at; it is never deleted.
- PR-4: at most one current assignment per member and
  event (partial unique index where revoked_at is empty).
- Capacity is more than 0; an event ends after it
  starts; each status comes from its fixed list
  (CHECK constraints).
- Intent: deleting an event or member that has
  registrations is refused, so history survives.

## Rules that need more than structure

- PR-2, cancelled_at filled exactly when status is
  cancelled: a CHECK constraint, Chapter 21.
- PR-3, never more active places than capacity:
  transactions, Chapter 33.
- PR-4, own registrations and assigned events only:
  Chapters 27 and 30.
- PR-5, valid details before publication; drafts hidden:
  Chapters 21, 25, and 26.
- PR-6, access administration: Chapters 23 and 30.

## Open questions

- Which contact details, beyond an email address?
- Are addresses that differ only in letter case one
  member? Decided in Chapter 21, before sign-up.
- Who appoints organizers, and must an event have one?
- When registration opens and closes (Chapter 2 policy).
- What happens to active registrations when an event
