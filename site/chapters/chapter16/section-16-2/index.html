What You Need to Know

From an entity to a model class

Chapter 15 described an event as an entity with attributes. Django describes the same thing as a Python class, and the class is what the rest of Django reads.

New Concept: a Django model

What problem exists? Many parts of a program need the same facts about one kind of record: which values it has, what type each value is, and which limits apply. When each part keeps its own copy of those facts, the copies drift apart.

What did people do before? They wrote the table in SQL, then repeated its columns by hand in the code that saved records, in the forms that collected them, and in the pages that showed them.

What is a model? A Python class that inherits from django.db.models.Model. Each class attribute made from a field class, such as models.CharField, is a field: one value that every record of that kind has. One model usually matches one database table, each field one column, and each instance of the class one row.

Why use one? Django reads the class to create and change the table, to save and fetch rows, and to build admin screens and forms, so the description is written once.

Now let’s use it. The rest of this part reads a model before you write one in How We Build It.

Here is the start of the model this chapter builds, with one field. Read it; you will type the complete version in Step 3:

Python

from django.db import models


class Event(models.Model):
    title = models.CharField(max_length=200)

models is Django’s module of model and field classes. Event inherits from models.Model, which is what makes it a model rather than an ordinary class. title is a field, and CharField says it holds text up to a maximum length. Django names the table after the app and the model, in lower case, joined by an underscore: events_event. It also adds a field you did not write. Every row needs the primary key that Chapter 15 described, so when no field declares one, Django adds id. Since Django 6.0, its type is BigAutoField: a whole number that the database assigns, counting up, with room for far more rows than Otahque will ever hold. The ERD’s int id PK is that number.

The dashed zone in Figure 16.1 matters. The table does not exist yet, and writing the class does not create it. An instance does not create a row either: Event(title='Python meetup') makes an object in Python’s memory, and nothing reaches the database until code calls its save() method. This chapter never calls save(), because there is no table to save into until Chapter 18.

Field types: what kind of value

A field type says what kind of value a field holds, and so which column type the database uses for it. Table 16.1 lists the four types the Event model uses.

Choose a type by what the value means, not by how it looks when typed. A capacity is a count, so it is a whole number that can be compared and added up. A start time could be typed as the text “19 Nov, 6.30pm”, but text cannot be sorted into time order or converted between time zones, so starts_at is a DateTimeField, and so is ends_at, the end time. For long text with no natural limit, such as a description, Django has TextField; the proposed Event has no such field yet.

Field options: limits, defaults, and empty values

New Concept: field options

What problem exists? A type says what kind of value a field holds, not which values are acceptable: how long it may be, whether it may be empty, and what a new record starts with.

What did people do before? They wrote checks by hand in each place that accepted input, and sooner or later one place was missed.

What are field options? Keyword arguments to the field class, such as max_length=200, default, blank, null, and choices. Each records one decision about the field’s values.

Why use them? Django turns each option into behaviour in the right places: a validation check, a column setting, or a form control.

Now let’s use it. Each option below comes with what it checks and where.

max_length is the most characters a CharField accepts. Django adds a validator that refuses longer text when a record is checked, and forms limit what can be typed. SQLite writes the number into the column type but does not enforce it; PostgreSQL, which Otahque uses from Chapter 32, does. In Django 6.1, a CharField on SQLite or PostgreSQL may leave max_length out, which means no limit at all, so its absence is not an error. Otahque sets every limit on purpose: 200 characters for a title and a location, and 64 for a time-zone name, well above the longest names in use.

default is the value a new instance starts with when none is given, either a fixed value or a function that Django calls. It is applied in Python when the object is created, not by the database.

blank and null answer two different questions, and they are easy to confuse:

  • blank is about validation: may the value be empty when Django checks the record? It defaults to False, which makes the field required.
  • null is about storage: may the column hold NULL, the database’s marker for no value? It defaults to False, which makes the column NOT NULL.

For text, Django’s convention is that an empty value is the empty string, ''. An optional text field therefore uses blank=True alone. Adding null=True as well would give the field two different ways of being empty, '' and NULL, and every query would have to check for both. A date has no empty string, so an optional date needs both options: null=True, so that the column can hold no value, and blank=True, so that validation accepts none.

Every Event field keeps both defaults, so every field is required. That includes the location: an online event records Virtual instead of leaving it empty.

Instants and time zones

starts_at and ends_at each hold an instant: one moment shared by everyone, whichever clock they read. The project’s settings, as Django generated them, contain USE_TZ = True and TIME_ZONE = 'UTC'. With USE_TZ on, Django expects aware datetimes, which carry their offset from Coordinated Universal Time (UTC), and converts them to UTC before storing them. A naive datetime, with no zone information, is ambiguous; Django warns when one is saved and assumes the default time zone. This read-only example creates one instant in Kolkata and prints it twice:

Python

from datetime import datetime
from zoneinfo import ZoneInfo

kolkata = ZoneInfo('Asia/Kolkata')
start = datetime(2026, 11, 19, 18, 30, tzinfo=kolkata)
print(start)
print(start.astimezone(ZoneInfo('UTC')))

Output

2026-11-19 18:30:00+05:30
2026-11-19 13:00:00+00:00

Both lines are the same instant. Storing only the instant loses something Sam needs: people deciding whether to attend a meetup in Kolkata expect to read 18:30, not 13:00. That is why the event also stores timezone, a name from the IANA time-zone database such as Asia/Kolkata or Europe/London, which Python’s zoneinfo module reads. To the model, the name is plain text: CharField(max_length=64) accepts Asia/Kolkata, and it also accepts a name that does not exist. Checking the name against the list in zoneinfo.available_timezones() is validation, which Chapter 21 adds.

A fixed list of statuses

New Concept: choices and TextChoices

What problem exists? A status must be one of a few agreed values. Free text would let “Draft”, “DRAFT”, and “drft” all appear, and every page would have to guess what each meant.

What did people do before? They scattered constants through the code, or repeated a list of pairs wherever a menu was needed.

What is TextChoices? A Django enumeration: a class whose members each pair a stored value, such as 'draft', with a reader-facing label, such as 'Draft'. Given to a field as its choices, it becomes the field’s list of allowed values.

Why use it? Values and labels live in one place, code can name Event.Status.DRAFT instead of typing a string, and Django uses the list for validation, forms, and the admin.

Now let’s use it. Here is Otahque’s list, as it will sit inside the Event model.

Python

class Status(models.TextChoices):
    DRAFT = 'draft', 'Draft'
    PUBLISHED = 'published', 'Published'
    CANCELLED = 'cancelled', 'Cancelled'

status = models.CharField(
    max_length=20,
    choices=Status,
    default=Status.DRAFT,
)

In each member, the first string is the stored value and the second is the label. Members are strings, so Event.Status.DRAFT == 'draft' is true. Event.Status.values lists the values and Event.Status.labels the labels, and Django gives every Event a get_status_display() method that returns the label for its current status. The longest value has nine characters; max_length=20 leaves room for a value added later. The default answers Sam’s third question: a new event starts as a draft, and stays hidden from members until it is published.

A list of choices is not a guarantee by itself. Table 16.2 shows which rules about an event are checked now, and by what.

full_clean() is a method every model instance has. It runs all the field checks and raises ValidationError, listing each field’s problems. Django’s forms call it, so data typed into a form is checked. Calling save() does not call it, though: code that saves directly can store a status outside the list, because the database has no rule about it. Chapter 21 adds database constraints, so that the database refuses such rows whichever code saves them.

A readable name and a default order

A model can also have methods and settings for the whole record. The __str__() method returns the text Python shows for an object. Django uses it in the shell, in admin lists, and in error messages, so it should name the record in words a person recognizes. Without one, every event appears as Event object (None); with one that returns the title, it appears as Python meetup.

A nested class named Meta holds options about the model as a whole rather than one field. ordering = ['starts_at'] makes every query for events return the earliest first, unless that query asks for a different order; '-starts_at' would reverse it. Ordering has a cost: the database sorts on every query that uses it, even where the order does not matter. For Otahque’s event lists, date order is nearly always wanted, so the model keeps it, and Chapter 22 shows how a single query chooses its own order. Later chapters add other Meta options, such as database constraints in Chapter 21.

Under the Hood: what happens when Django imports a model

When Django starts, django.setup() loads the settings and imports the models module of each app in INSTALLED_APPS. Python runs the class Event statement, and Django’s model machinery takes over: it collects each field, gives it its name and column, adds the id field, applies Meta, and stores the result as Event._meta, the model’s metadata. It then registers the model in the app registry, Django’s index of installed apps and their models, as events.Event. None of this touches the database. Creating the table is a separate, deliberate step: makemigrations compares the models with the project’s migration files and writes a new file describing the difference, and migrate applies it to the database. Chapter 18 does both. Because models need the registry, importing one before setup has finished fails with AppRegistryNotReady and the message “Apps aren’t loaded yet.”

You will look at Event._meta yourself in Step 4, through a small script that calls django.setup() first. _meta starts with an underscore, which in Python usually means “private”, but Django documents it as the Model _meta API, a supported way to inspect any model.

In practice: renaming a status

Situation. Later, Sam asks for cancelled events to say “Called off” instead of “Cancelled”, and a developer suggests changing the stored value to match.

Application. The label can change freely: it lives only in the code, and every page that calls get_status_display() shows the new words. The stored value 'cancelled' is written in every cancelled event’s row, in the tests, and in any export a partner reads, so changing it needs a data migration (Chapter 18) and a search for every comparison with the old value.

Consideration. Treat stored values as identifiers: short, lower case, and stable. Labels are for people and may later be translated; values are for the program.
