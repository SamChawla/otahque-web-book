How We Build It

Start from Chapter 15, in the folder containing manage.py, with your own .env, the locked environment, 18 passing tests, docs/design/erd.md committed, and a db.sqlite3 with no tables. You change two files: events/tests.py, where two tests are written first, and events/models.py, which receives the Event model. Views, templates, and the sample events stay as they are; the pages read real events from Chapter 19. One practice script goes in the practice folder beside the project, as in Chapter 15. At the end, 20 tests pass, Django loads the model, and the database still has no tables.

The Custom Way

This illustration shows the table written by hand in SQL; do not add it to the project:

illustration_only/event_table.sql (not part of the project)

CREATE TABLE event (
    id INTEGER PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    starts_at TEXT NOT NULL,
    ends_at TEXT NOT NULL,
    timezone VARCHAR(64) NOT NULL,
    location VARCHAR(200) NOT NULL,
    capacity INTEGER NOT NULL CHECK (capacity >= 0),
    status VARCHAR(20) NOT NULL DEFAULT 'draft'
);

SQLite would accept it, and it is close to what Django will generate. But it is only the table. The Python code that saves an event must list the same eight columns with the same spelling. The statuses and their labels live somewhere else again, and every form must repeat the length limits. When a column changes, each copy must change with it, by hand and in step with the database, and nothing checks that the copies agree. The Django way writes the description once, in Python, and derives the table, the validation, and later the forms from it.

The Django Way

Four steps build the model. The tests come first, so you see them fail before the model exists.

Step 2: Write the tests first

The tests say what the model must do before the model exists. Open events/tests.py. Three import lines are new: the first, the ValidationError line, and the last. Make the imports at the top of the file match this listing:

events/tests.py (imports at the top)

from datetime import UTC, datetime
from pathlib import Path
from unittest.mock import patch

from django.contrib.staticfiles import finders
from django.core.exceptions import ValidationError
from django.template import Context, Template
from django.template.loader import render_to_string
from django.test import SimpleTestCase
from django.urls import resolve, reverse

from . import views
from .models import Event

UTC is Python’s own UTC time zone, so the test’s start time is an aware datetime. Then add a new test class at the end of the file:

events/tests.py (end of the file)



class EventModelTests(SimpleTestCase):
    """The Event model's rules, checked without a database."""

    def make_event(self, **changes):
        """Make a valid unsaved event with these changes."""
        fields = {
            'title': 'Python meetup',
            'starts_at': datetime(2026, 11, 19, 18, 30,
                                  tzinfo=UTC),
            'ends_at': datetime(2026, 11, 19, 20, 30,
                                tzinfo=UTC),
            'timezone': 'Europe/London',
            'location': 'Virtual',
            'capacity': 40,
        }
        fields.update(changes)
        return Event(**fields)

    def test_str_is_title(self):
        event = self.make_event()
        self.assertEqual(str(event), 'Python meetup')

    def test_status_starts_draft_and_is_checked(self):
        event = self.make_event()
        self.assertEqual(event.status, Event.Status.DRAFT)
        event.full_clean()
        event.status = 'archived'
        with self.assertRaises(ValidationError) as caught:
            event.full_clean()
        self.assertEqual(
            caught.exception.message_dict,
            {'status': [
                "Value 'archived' is not a valid choice."
            ]},
        )

make_event() is a helper, not a test, because its name does not start with test. It builds a complete, unsaved event, and **changes lets a test replace any of its values. The first test checks the readable name. The second checks three things in order: a new event starts as a draft; the complete event passes full_clean(), which proves that the next error comes from the status alone; and a status outside the list is refused with exactly one message, for the status field. SimpleTestCase, which the earlier tests also use, refuses any database query, so these tests prove that nothing here needs a table.

Common Error: saving in a SimpleTestCase

Adding event.save() to one of these tests looks harmless, but saving is a database query. The test fails with DatabaseOperationForbidden and a message that begins “Database queries to ’default’ are not allowed in SimpleTestCase subclasses.” Remove the call: there is no table to save into yet. Tests that save records begin once Chapter 18 has created the tables.

Step 3: Write the Event model

Replace the contents of events/models.py, which still holds only the comment that startapp generated, with this listing:

events/models.py

"""Models for Otahque's events."""
from django.db import models


class Event(models.Model):
    """A proposed Otahque event, from the Chapter 15 ERD."""

    class Status(models.TextChoices):
        """Where an event is: draft, published, or cancelled."""

        DRAFT = 'draft', 'Draft'
        PUBLISHED = 'published', 'Published'
        CANCELLED = 'cancelled', 'Cancelled'

    title = models.CharField(max_length=200)
    starts_at = models.DateTimeField()
    ends_at = models.DateTimeField()
    timezone = models.CharField(max_length=64)
    location = models.CharField(max_length=200)
    capacity = models.PositiveIntegerField()
    status = models.CharField(
        max_length=20,
        choices=Status,
        default=Status.DRAFT,
    )

    class Meta:
        ordering = ['starts_at']

    def __str__(self):
        return self.title

Every line comes from What You Need to Know: the statuses nested inside the model, so code names them Event.Status; seven fields in the order of the ERD; Meta with the default order; and __str__(). The docstring records where the design came from. Field class names are case-sensitive, and a misspelling stops Django before any test runs.

Common Error: a misspelled field class

Writing models.Charfield instead of models.CharField stops every command with an AttributeError. Its message says that django.db.models has no attribute Charfield and ends Did you mean: 'CharField'?, after a traceback that names the line with the misspelling. Python’s suggestion is usually right; correct the spelling on that line and run the command again.

Step 4: Inspect the model without the database

manage.py shell starts Python with Django set up, and -c runs one line of Python and exits. The shell imports every model automatically and says how many objects it imported, so Event needs no import:

Terminal

uv run python manage.py shell -c "print(Event.Status.values)"

Output

13 objects imported automatically (use -v 2 for details).

['draft', 'published', 'cancelled']

If you write your own -c commands, put any quotation marks inside the Python in single quotes, so that the same command works in PowerShell and in a macOS shell or Linux/WSL Bash. For a longer look, use a script. A script run with uv run python is not set up for Django, so it needs a helper that loads the settings first. If you have no practice folder from Chapter 15, create it with mkdir ../practice, the same command in every shell. Then create the helper:

../practice/setup_django.py

"""Load Otahque's settings so a practice script can use them.

Run practice scripts from the folder that holds manage.py.
"""
import os
import sys

import django

sys.path.insert(0, os.getcwd())
os.environ.setdefault(
    'DJANGO_SETTINGS_MODULE', 'config.settings'
)
django.setup()

The helper puts the current folder, the one holding manage.py, on Python’s import path, names the settings module, and calls django.setup(), which builds the app registry described in Under the Hood. Now create the script that uses it:

../practice/inspect_event.py

import setup_django  # loads Otahque's settings first
from events.models import Event

print(Event._meta.db_table)
for field in Event._meta.fields:
    print(field.name, field.get_internal_type())
print(Event.Status.values)
print(Event._meta.ordering)

Run it from the folder that holds manage.py, in any of the three shells:

Terminal

uv run python ../practice/inspect_event.py

The table name, the added id, every field type, the statuses, and the order all come from the class, and none of it needed a table. Run the Step 1 query again: it still prints nothing. Then check what changed:

Terminal

Output

M in the second column marks a file changed but not yet staged. Nothing appears under events/migrations/, and the practice folder is outside the project, so Git does not see it.

Common Error: making a migration to see the table

Running Django’s makemigrations command now would write events/migrations/0001_initial.py, a migration file describing the table, and migrate would then create Django’s built-in tables, including the user table that Chapter 17 must choose first. If either has happened, keep what was made: move the new migration file into ../practice and rename db.sqlite3 as in Step 1, so that Chapter 18 starts from no migration and no tables. Do not delete them in this chapter.
