Checkpoint: Quiz and Challenge

Quiz

Que. 2 You saved events/models.py, and Django loads the Event model. Does the project now have an event table?

Flip to check your answerFold answer back

Answer. No. Importing the model builds its metadata and registers it with the app registry, without touching the database. A table is created only when a migration is written with makemigrations and applied with migrate, which Chapter 18 does.

Que. 3 An event title has 250 characters. Where is it refused?

Flip to check your answerFold answer back

Answer. By full_clean() and by forms, through the validator that max_length=200 adds. SQLite would store it anyway, because it does not enforce the length in varchar(200); PostgreSQL would refuse it.

Que. 4 Why does the status field have default=Status.DRAFT?

Flip to check your answerFold answer back

Answer. So that every new event starts as a draft, which Chapter 2’s rules keep hidden from members. An organizer must publish it deliberately. Without the default, a new event would start with an empty status, which is not in the list.

Que. 5 Code calls save() on an event whose status is 'archived'. Once tables exist, what stops it?

Flip to check your answerFold answer back

Answer. Nothing in this chapter. Choices are checked by full_clean() and forms, and save() does not call full_clean(). The database has no rule about the status column until Chapter 21 adds a constraint.

Que. 6 Why does location accept Virtual but not an empty value?

Flip to check your answerFold answer back

Answer. The field is required, because blank and null keep their defaults, so validation refuses an empty value and the column refuses NULL. Virtual is ordinary text: a convention organizers follow for online events, which the model does not check.

Mini-Challenge

Que. 7 Sam would like an optional one-line summary for each event, shown under its title. Write the field declaration you would propose, and explain whether it should use blank, null, or both. Write it in your notes, not in events/models.py: whether events have a summary is a product decision still to be made, and Chapter 17 starts from the model as it is now.

Flip to check your answerFold answer back

Answer. A summary is text, so the convention for optional text applies: blank=True, so validation accepts an empty summary, with an empty string as the default, and no null=True:

illustration_only/summary_field.py (not part of the project)

    summary = models.CharField(
        max_length=200, blank=True, default=''
    )

CharField with a limit suits a single line; TextField would suit a longer description. With null=True as well, an event could have no summary in two ways, '' and NULL, and every query looking for events without a summary would need to check for both. null=True is right when “no value yet” must be told apart from “empty”, as with Registration’s cancelled_at. Record the field as a proposal beside the ERD’s open questions until the product decision is made.

What We Learned

  • A Django model is a Python class that describes one kind of record; its fields usually become a table’s columns, and each instance is one row in waiting.
  • Django adds an id primary key, a BigAutoField, when no field declares one, and names the table after the app and the model.
  • A field type says what kind of value a field holds; options such as max_length, default, blank, null, and choices record which values are acceptable.
  • blank concerns validation and null concerns storage; optional text uses blank=True with the empty string, and optional dates need both.
  • TextChoices pairs stored values with labels; choices are checked by full_clean() and forms, not by save() or the database.
  • An aware DateTimeField stores the instant, and a separate time-zone name says how to show it.
  • Importing a model builds its metadata and registers it; it creates no table.

Git Commit

Stage the two changed files and check what is staged, in PowerShell, a macOS shell, or Linux/WSL Bash, beside manage.py:

Terminal

git add events/models.py events/tests.py
git status --short

Output

M  events/models.py
M  events/tests.py

M in the first column marks a change staged for the commit. Then record it:

Terminal

git commit -m "Add the proposed Event model and its tests"
