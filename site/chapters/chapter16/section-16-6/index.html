Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 and L2 check what you have just learned. L3 asks what happens inside Django, which tests rarely show. L4 and L5 look ahead to a growing application: attempt them now, and return to them later. They are extension questions, not a gate to the next chapter. Each code proof is a short file in the practice folder that starts by importing setup_django.py from Step 4; run it from the folder that holds manage.py with uv run python ../practice/ followed by the file name, in PowerShell, a macOS shell, or Linux/WSL Bash.

L1 (Junior): What does a Django model represent, and how does it relate to a database table?

What the interviewer is testing: Can you connect a class, its fields, and its instances to a table, its columns, and its rows?

Flip to check your answerFold answer back

Perfect answer: A model is a Python class, inheriting from models.Model, that describes one kind of record the application stores. Each field is a class attribute that says what kind of value every record has and which limits apply, and usually becomes one column. Each instance is one record in memory, and becomes a row when it is saved. Django creates the table from the model through migrations, adds an id primary key when none is declared, and uses the same class for queries, the admin, and forms, so the description of a record lives in one place.

Behind the scenes:

model (summary)

class Event(models.Model) -> table events_event
title = CharField(200)    -> column title varchar(200)
no primary key declared   -> Django adds id
Event(...)                -> an object; a row after save()

Code proof: an instance exists in Python before any row does:

../practice/l1_instance.py

import setup_django
from events.models import Event

event = Event(title='Python meetup')
print(event)
print(event.pk, event.status, event.get_status_display())

Output

Python meetup
None draft Draft

pk is None because only the database assigns a primary key, when a row is saved. The status already has its default.

Common mistakes:

  • Thinking that defining or importing a model creates its table.
  • Using one model for two kinds of record because they share a few fields.
  • Forgetting that Django adds the primary key, then declaring a second one by accident.

Follow-up the interviewer might ask:

  • “When would you declare your own primary key?”
  • “What does __str__() change, and where would you notice it?”

L2 (Mid-Level): How do blank and null differ, and when do you need each?

What the interviewer is testing: Can you separate validation from storage, and apply Django’s convention for empty text?

Flip to check your answerFold answer back

Perfect answer: blank is a validation setting: it decides whether full_clean() and forms accept an empty value. null is a storage setting: it decides whether the database column may hold NULL. Both default to False, so a field is required twice over. For text, an empty value is the empty string, so an optional text field uses blank=True alone; adding null=True would give two kinds of empty that every query must handle. For types with no empty value, such as dates and numbers, an optional field needs null=True so the column can hold nothing, and blank=True so validation accepts nothing. A field such as cancelled_at, which is empty until something happens, is the typical case.

Behind the scenes:

blank and null (summary)

blank=False -> full_clean(): "This field cannot be blank."
null=False  -> full_clean(): "This field cannot be null."
null=False  -> the column is NOT NULL
optional text -> blank=True, default ''
optional date -> blank=True, null=True

Code proof: an empty title and missing start and end times fail for different reasons:

../practice/l2_blank_null.py

import setup_django
from django.core.exceptions import ValidationError
from events.models import Event

event = Event(title='', timezone='Europe/London',
              location='Virtual', capacity=40)
try:
    event.full_clean()
except ValidationError as error:
    for name, messages in error.message_dict.items():
        print(name, messages)

Output

title ['This field cannot be blank.']
starts_at ['This field cannot be null.']
ends_at ['This field cannot be null.']

The empty title fails the blank check. The missing times are None, Python’s value for nothing, which would become NULL in their columns, so each fails the null check.

Common mistakes:

  • Adding null=True to optional text fields out of habit.
  • Setting blank=True on a date without null=True, so validation accepts a value the column cannot store.
  • Believing blank changes the database.

Follow-up the interviewer might ask:

  • “How would you find every event without a summary if both '' and NULL were allowed?”
  • “What does a form do with a field that has blank=True?”

L3 (Senior): What happens when Django imports a model class, and what does not happen yet?

What the interviewer is testing: Do you understand the app registry and the boundary between model definitions and the database schema?

Flip to check your answerFold answer back

Perfect answer: At start-up, django.setup() populates the app registry: it imports each installed app’s models module. Running the class statement hands the class to Django’s model machinery, which collects the fields, names their columns, adds a primary key if none is declared, applies Meta, and stores the result in _meta. The model is registered as events.Event, and other code can look it up by that label. Nothing touches the database: no table, column, or row is created, so a model can be loaded, inspected, and validated with no schema at all. The schema changes only through migrations, which compare the models with recorded migration files and apply the difference. That separation is why a model can be reviewed before it is frozen into a migration, and why importing models before setup has finished fails with AppRegistryNotReady.

Behind the scenes:

import (summary)

django.setup() -> import each app's models module
class Event     -> fields collected, id added, _meta built
registry        -> events.Event registered
database        -> unchanged until makemigrations, migrate

Code proof: the registry knows the model, and the database has no tables:

../practice/l3_import.py

import setup_django
from django.apps import apps
from django.db import connection
from events.models import Event

print(apps.get_model('events', 'Event') is Event)
print(Event._meta.db_table)
print(connection.introspection.table_names())

Output

True
events_event
[]

table_names() asks the database for its tables and only reads; the empty list is Otahque’s real db.sqlite3.

Common mistakes:

  • Expecting a new field to appear in the database without a migration.
  • Importing models at the top of a module that runs before setup, such as a settings file.
  • Treating _meta as private and copying field lists by hand instead.

Follow-up the interviewer might ask:

  • “Why does apps.get_model() exist, rather than always importing the class?”
  • “What does makemigrations compare to decide what to write?”

L4 (Staff): Defend the Event field types, and say what the database does not yet guarantee.

What the interviewer is testing: Can you justify modelling choices and separate validation from guarantees, with a plan to close the gaps?

Flip to check your answerFold answer back

Perfect answer: Each type follows the meaning of the value. The title and location are bounded text, CharField with limits a reviewer can see. starts_at and ends_at are aware DateTimeFields, so each instant is stored once in UTC and compared correctly, and timezone keeps the IANA name that says how to show both, because neither can be derived from the other. Capacity is a count, so PositiveIntegerField, which also gives the database a CHECK that refuses negative numbers. Status is a short, stable value from TextChoices, defaulting to draft so that nothing is published by accident. The gaps are explicit: zero passes both checks, although the ERD requires more than zero; a time-zone name is not checked against the IANA list; nothing checks that an event ends after it starts; the status list is enforced only by full_clean(), which save() does not call; and SQLite does not enforce text lengths. I would close these in Chapter 21 with CheckConstraints for capacity, status, and the end time, and a validator for the time-zone name, each with a test that tries to save a bad row.

Behind the scenes:

guarantees (summary)

capacity -1        -> full_clean() and CHECK refuse
capacity 0         -> accepted: ERD says more than 0
status 'archived'  -> full_clean() refuses; save() stores
timezone 'Mars/..' -> accepted: no check yet
ends before start  -> accepted: no check yet

Code proof: an event with a capacity of 0, an invented time zone, and an end before its start passes every current check:

../practice/l4_gaps.py

from datetime import UTC, datetime

import setup_django
from events.models import Event

event = Event(
    title='Python meetup',
    starts_at=datetime(2026, 11, 19, 18, 30, tzinfo=UTC),
    ends_at=datetime(2026, 11, 19, 17, 0, tzinfo=UTC),
    timezone='Mars/Olympus_Mons',
    location='Virtual',
    capacity=0,
)
event.full_clean()
print('accepted:', event.capacity, event.timezone)

Output

accepted: 0 Mars/Olympus_Mons

Common mistakes:

  • Storing a start time as text, or as a naive datetime with no zone.
  • Treating choices as a database guarantee.
  • Choosing PositiveIntegerField and assuming it means more than zero.

Follow-up the interviewer might ask:

  • “Why not store the start time in the event’s own time zone instead of UTC?”
  • “How would you validate the time-zone name, and where?”

L5 (Lead): Why must migrate wait until the custom user model is chosen?

What the interviewer is testing: Can you sequence decisions that are cheap now and expensive later, and explain the risk to a team?

Flip to check your answerFold answer back

Perfect answer: The AUTH_USER_MODEL setting names the model that represents users, and today it is Django’s built-in auth.User. Running migrate applies the built-in apps’ migrations, which create that model’s table, auth_user, and tables in other apps that refer to it. Django’s documentation says a new project can set up a custom user model before creating migrations or running migrate for the first time. Changing AUTH_USER_MODEL once those tables exist is not supported by an ordinary migration: the foreign keys and existing rows would all have to be moved. Otahque’s members are its users, and the ERD gives each member a unique email address and a display name, so the choice is real. As lead, I would make it a recorded decision before the first migrate, keep schema work behind it, and add a check that the database has no tables until then. The cost of waiting is small; the cost of changing later grows with every row.

Behind the scenes:

user model (summary)

AUTH_USER_MODEL = 'auth.User'  (the default)
migrate -> auth_user, and tables that refer to it
change later -> move keys and rows by hand
Chapter 17 -> choose it; Chapter 18 -> migrate

Code proof: the default user model is named, and its table does not exist yet:

../practice/l5_user.py

import setup_django
from django.apps import apps
from django.conf import settings
from django.db import connection

print(settings.AUTH_USER_MODEL)
user_model = apps.get_model(settings.AUTH_USER_MODEL)
print(user_model._meta.db_table)
print(connection.introspection.table_names())

Output

auth.User
auth_user
[]

Common mistakes:

  • Running migrate early “just to get a database”.
  • Assuming a later data migration can swap the user model cheaply.
  • Leaving the decision undocumented, so a new teammate runs migrate first.

Follow-up the interviewer might ask:

  • “If a project has already migrated with the default user, what are the options?”
  • “Which fields would Otahque’s user model need first?”
