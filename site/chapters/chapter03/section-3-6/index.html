Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 and L2 check what you have just learned. L3 asks how it works underneath. L4 and L5 ask about the design and leadership decisions that later chapters build on: attempt them now, and return to them when you reach those chapters. Use the readiness checkpoint to decide whether to continue. If an answer is difficult, revisit its worked example and explain the result in your own words. L4 and L5 are extension questions, not a gate to the next chapter.

L1 (Junior): What happens between typing an event address into a browser and seeing the page?

What the interviewer is testing: Can you describe the main steps of a page load in order, and name what each one does?

Flip to check your answerFold answer back

Perfect answer: The browser reads the URL and looks up the host name through DNS to obtain an IP address. It connects to that address; with HTTPS it first sets up TLS, which encrypts the connection and lets the browser check the server’s identity. It sends an HTTP GET request for the path. The server replies with a status code, such as 200, headers, and the HTML. The browser reads the HTML, makes further requests for the stylesheets, images, and scripts it names, and then displays the page (Figures 3.3 and 3.5).

Behind the scenes:

what the browser does, in order (summary)

1. split the URL; look up the host in DNS
2. connect; for https, negotiate TLS and check the certificate
3. send GET /events/42/ with a Host header
4. read the status; parse the HTML
5. request each resource the HTML names; display the page

Code proof: in the developer tools from Step 1, reload a page and compare the document row with the resource rows that follow it.

Common mistakes:

  • Saying that DNS returns the page.
  • Forgetting the separate requests for images and stylesheets.
  • Describing HTTPS as a different protocol rather than HTTP protected by TLS.

Follow-up the interviewer might ask:

  • “Which of these steps can fail, and what would the visitor see?”
  • “What might be different on a second visit?”

L2 (Mid-Level): Name the parts of a URL, and say which part the server never receives.

What the interviewer is testing: Do you know what each part of an address is for, and what travels in the request?

Flip to check your answerFold answer back

Perfect answer: In the address in Figure 3.9, the scheme is https, the host is otahque.example, the path is /events/42/, the query is view=details, and the fragment is venue. The fragment stays in the browser: it is not sent in the HTTP request, so the server cannot use it. The path and query are sent to the server, and the host is used to connect and is also sent with the request, in the Host header.

Behind the scenes:

what the request line carries (summary)

GET /events/42/?view=details HTTP/1.1
Host: otahque.example
# the scheme chose https; #venue was never sent

Code proof (once Chapter 4 has set up Python): Python’s urllib.parse splits the same address:

Python

from urllib.parse import urlsplit

url = "https://otahque.example/events/42/?view=details#venue"
parts = urlsplit(url)
print(parts.scheme, parts.netloc, parts.path)
print(parts.query, parts.fragment)

Folder structure

https otahque.example /events/42/
view=details venue

Common mistakes:

  • Relying on the fragment for a decision on the server.
  • Treating the query as private, although it appears in browser history and server logs.
  • Assuming a path names a file on disk.

Follow-up the interviewer might ask:

  • “Why might view=details be a query rather than part of the path?”
  • “Where could a query string end up recorded?”

L3 (Senior): Why should a form that changes data use POST, followed by a redirect?

What the interviewer is testing: Do you understand safe methods, repeated submissions, and the Post/Redirect/Get pattern?

Flip to check your answerFold answer back

Perfect answer: GET is for reading. It should not request a change to product state, because browsers, crawlers, and link previews may repeat or follow GET requests. Registering changes data, so the form uses POST. If the server answered the POST directly with a page, refreshing that page would ask the browser to send the POST again. With Post/Redirect/Get, the server processes the action and replies 303 See Other with the result page’s location; the browser then makes a GET for that page, so a refresh repeats only the GET (Figure 3.6). The server must still handle a repeated submission correctly, because a redirect does not stop someone sending the POST again.

Behind the scenes:

the three messages (summary)

POST /registrations/      -> 303 See Other
                             Location: /registrations/mine/
GET /registrations/mine/  -> 200 OK, the result page
# 303 tells the browser to follow with GET, whatever the
# original method was

Evidence: Figure 3.6 provides the worked Post/Redirect/Get trace. If you observe a harmless form you already intended to use, check whether it follows this pattern rather than assuming that it must. A form can use GET, return a response directly, or submit through JavaScript. Do not submit a registration or another consequential action merely to perform this exercise.

Common mistakes:

  • Using a plain link, which is a GET, to cancel a registration.
  • Believing the redirect alone prevents duplicates.
  • Returning a successful change’s result page directly when the intended design should make refresh repeat only a GET. Returning an invalid form with errors directly is a different, normal case.

Follow-up the interviewer might ask:

  • “Why 303 rather than 302?”
  • “What else stops a member registering twice?”

L4 (Staff): The browser hides the Register button when an event is full. Is that enough?

What the interviewer is testing: Do you know where rules must be enforced, and why the browser cannot be trusted?

Flip to check your answerFold answer back

Perfect answer: No. Everything in the browser is under the user’s control: the page can be changed, scripts can be turned off, and requests can be sent without the page at all. Hiding the button is helpful feedback, but on every request the server must check identity, access, the registration window, and capacity, and record only accepted results (Figure 3.7). The trust boundary is where browser data enters the server, and everything that crosses it is untrusted input. Checks in the browser improve the experience; checks on the server enforce the rules.

Behind the scenes:

two ways to register without the button (summary)

1. edit the page in the developer tools to show it again
2. send the POST directly with any HTTP tool
# both reach the server; only its checks stop them

Evidence: Figure 3.7 places each decision on its side of the boundary.

Common mistakes:

  • Treating checks in the browser as security.
  • Trusting hidden form fields.
  • Checking the rule when the page is displayed but not when the form is submitted.

Follow-up the interviewer might ask:

  • “What should the server send back when it refuses?”
  • “Which browser checks are still worth having?”

L5 (Lead): A member reports being registered twice after a slow connection. How do you lead the investigation and prevent it happening again?

What the interviewer is testing: Can you move from a report to evidence, a root cause, a lasting fix, and shared learning?

Flip to check your answerFold answer back

Perfect answer: Start with evidence, not a theory. Find both requests in the server’s records, with their times, methods, and outcomes, and compare them with what the member saw. Then look for the root cause among the usual candidates: a slow or lost reply that invited a second click (Figure 3.8), a double click, a missing redirect after the POST, or no rule against duplicates on the server. Whatever started it, the lasting fix is the same: enforce one active registration per member and event where the result is recorded, so that a repeated request returns the existing registration instead of creating another. Then improve the experience, by showing progress while a request is in flight and by showing members their existing registrations. Correct the member’s record, add a test that repeats the request, so that the problem cannot return unnoticed, and share a short, blame-free note on what happened and what changed.

Behind the scenes:

the timeline worth reconstructing (summary)

18:02:10  POST /registrations/  (first click)
18:02:14  no reply reaches the browser
18:02:20  POST /registrations/  (second click)
# without a server rule, both POSTs create a registration

Evidence: Figure 3.8 shows the lost reply that makes a second click likely, and Chapter 2’s PR-1 states the rule the server must keep: one current confirmed place.

Common mistakes:

  • Blaming the member for clicking twice.
  • Fixing only the button, so that a repeated request from elsewhere still creates a duplicate.
  • Deleting the duplicate without finding what allowed it.

Follow-up the interviewer might ask:

  • “How would a repeated request return the same result?”
  • “What do you tell the member while the fix is in progress?”
