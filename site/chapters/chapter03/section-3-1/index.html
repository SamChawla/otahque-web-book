3.1 Browsers, servers, and an event page

Soni wants to decide whether a community event is suitable for her. In our proposed Otahque application, she follows a link to its published event page. The page should show the information she needs to make that decision. What has to happen between following the link and reading the result?

Begin with the browser

A browser is an application that lets a person open and interact with web pages. Edge, Firefox, Chrome, and Safari are examples. Soni uses her browser to follow the event link; the browser does the communication needed to obtain the page.

The internet is the network infrastructure connecting devices and networks around the world. The web is one system that uses that infrastructure to make pages and other resources available through addresses and links. A resource is something a browser can ask for, such as an event page or an image. Other systems, including email, also use the internet.

A browser and a search engine have different jobs. A search engine helps find pages; a browser displays and lets us use them. Soni can follow an event link someone sent her without first searching for the event.

One website, several pages

Suppose Soni starts at an Otahque page listing upcoming events. She notices a Python workshop and follows its title. The browser now displays the detail page for that workshop. These are two pages within the same website: one helps her choose an event; the other helps her examine that choice.

A web page is a document the browser can display. Its content and structure are described using Hypertext Markup Language, shortened to HTML. Structure means such things as which text is a heading, which items form a list, and which words are links. We will write HTML later; for now, recognize that the browser receives a description of the page rather than a photograph of someone else’s screen.

A website groups related pages and resources. Otahque’s event list, individual event details, and account pages will belong to one site. Soni can move between those pages while continuing to use the same browser application. Figure 3.1 shows this distinction using a proposed reading journey.

Read the arrow as “follow this link”, not “move the entire website”. The detail page is about the selected event. The browser is the tool displaying it. The surrounding boundary groups pages that belong together; it does not represent the physical size of a server.

Que. 1 Soni follows the Python workshop link. Has she opened a different browser, a different page, or necessarily a different website?

Show answerHide answer

Answer. She has opened a different page. In this example, both pages belong to Otahque, and she is still using the same browser. A link can also lead to another website, but that is not what the illustrated link does.

Meet the other side: the web server

The browser needs another program to receive its request and return information. Software doing that job is called a web server. People also use “server” for the computer running that software. In this chapter, focus on the job: receiving a request, handling it, and sending a response.

The browser acts as a client: software asking a service for something. A request is the message it sends. A response is the message sent back. Soni is the person using the client; she does not need to construct these messages herself.

These are software roles, not two special types of computer. Later, your own computer will run both a browser and a development server. A public site may use several machines behind the service a visitor reaches. We can understand the basic exchange before deciding how Otahque will be hosted.

Que. 2 If Soni opens the same event on her phone instead of her laptop, which role does the phone’s browser perform?

Show answerHide answer

Answer. It is still the client. The device has changed, but the browser still asks the website for information and displays the result. Client and server describe jobs in the exchange.

Follow one successful page visit

First, Soni follows the event link. Her browser sends a request asking for that page. Next, the server handles the request and returns a response containing page content. Finally, the browser interprets that content and displays a page she can read. Figure 3.2 separates the outgoing request from the returning response.

This is a simplified successful exchange. A real page may need further requests for images and other supporting files. The diagram leaves out the intermediate network machinery so we can follow the two roles. Section 3.2 explains how an address helps the browser reach the right site.

The response does not have to be a page already saved as a finished file. An application can assemble page content when a request arrives. For example, Otahque will need to present information about the particular published event Soni chose. We will examine that distinction in Section 3.4; no application has been built at this point.

One page can need several exchanges

Imagine that the workshop page includes a photograph of the venue. The page document can identify where that photograph is available without containing the image itself. After reading the document, the browser can ask for the image in another request. The server then returns image data in another response.

In Figure 3.3, the messages are arranged over time. Start at the top and read downwards. The browser first obtains the document, discovers the image reference, and obtains the image. It combines the information into the page Soni sees. Each returning arrow answers a particular request.

This is one possible loading sequence, with only two resources shown. Browsers can fetch several resources at once and can sometimes reuse copies they already have. The picture is not a promise that every page always makes two requests in exactly this order. Its purpose is to show why “open a page” can involve more than one exchange.

Now give the example a problem: Soni can read the workshop description, but the venue photograph does not appear. The visible description is useful evidence: at least some page content is available to her. It does not tell her whether the image is missing on the server, could not be reached, or failed to display. Those possibilities require further observation.

Que. 3 Does a missing venue photograph prove that the whole Otahque website is unavailable?

Show answerHide answer

Answer. No. The document and photograph are separate resources in this example. Soni can report that the description is visible while the photograph is missing. That precise observation is more useful than claiming the whole site is down; the cause is still unknown.

Try it yourself: explain a partial page

Use Figure 3.3 on paper. Cover the final response arrow with your hand. Assume the event document has arrived but the image data has not. Name one thing Soni may still be able to read and one thing she cannot yet see. Then write a short problem report that states the observation without guessing its cause. No browser changes, commands, or project files are needed.

Que. 4 What would a useful explanation and problem report say?

Show answerHide answer

Answer. Soni may be able to read the workshop description contained in the document, but she cannot yet see the venue photograph. A useful report is: “The workshop description is visible, but the venue photograph is missing.” It identifies the affected part of the page without claiming that the server, network, or browser is definitely responsible.

Reading an event is different from registering

Chapter 2 separated browsing from registration. That distinction still matters here. Opening the event page asks to read about the event. Under our proposed requirements, it does not reserve a place for Soni.

If Soni later chooses to register, the application must handle a separate request for that action and check the relevant rules. A page that looks encouraging is not, by itself, evidence that a registration was recorded. When we implement registration, the confirmation must reflect the result of the server’s decision.

Que. 5 Soni can see the event description. Does this establish that she has a place at the event?

Show answerHide answer

Answer. No. It establishes that the browser has displayed event information. Registering is a separate action with its own result. Reading the page must not silently create a registration.

Consider Sai checking a confirmation while Sam plans the event. Sai needs a result about her own place; Sam needs an authorized view of registrations for the event he manages. Both use browsers, but their questions and permitted information differ. The client/server vocabulary tells us where the messages go. Chapter 2’s requirements tell us what the application must decide before answering.

That distinction will guide our later tests. A page appearing on screen is one observation. The application recording the right registration, refusing a duplicate, and showing the result to the right person are additional behaviours to verify. For this section, practise describing the exchange without treating the visible page as proof of every underlying rule.

Try it yourself

On paper, draw two boxes for Sai’s browser and the web server. Sai wants to read a published event before deciding whether to attend. Add one arrow for the request and another for the response. Label what each arrow carries, then write one sentence describing what the browser does after receiving the response. You do not need to visit a site or install anything.

Que. 6 What should the drawing and final sentence show?

Show answerHide answer

Answer. Draw the request arrow from Sai’s browser to the server and label it “Ask for the event page”. Draw the response arrow back to the browser and label it “Page content”. Write: “The browser interprets the returned content and displays the event information.” The arrows represent messages, not Sai travelling to the server. This drawing shows reading an event, not booking a place.
