3.5 Follow a complete Otahque journey

We can now follow Sai from an event page to a registration result. This is a proposed interaction based on Chapter 2’s draft requirements, not evidence of working software. Assume she is signed in, the event is published, and the application will enforce the agreed rules. Exact addresses and response choices remain implementation decisions.

Follow the successful path

First, Sai opens the event address. The browser reaches the named host, using a DNS result where needed, and makes a protected request. The server returns content for the event. The browser displays it and obtains any additional resources it needs. Sai reads the details before choosing to register.

Next, her deliberate submission sends a change request. The application identifies her, checks access and the registration rules, and records an accepted registration. Only after the result is established should the response lead her to a confirmation that reflects that result. If the application uses the redirect pattern from Section 3.3, the browser makes a separate reading request for the confirmation page.

Every arrow represents a boundary worth checking later. Did the request reach the application? Did the application identify the correct member? Were the rules applied before the record was accepted? Does the displayed message match the stored result? These questions turn a vague claim that “the page works” into observations we can verify.

Que. 19 At which point should Sai be told that her place is confirmed?

Show answerHide answer

Answer. After the application has established and recorded an accepted registration. Clicking the button expresses intent; sending a request starts an exchange. Neither alone proves that a place has been secured.

A refusal can be a correct result

Suppose registration closed before Sai submitted. A response explaining that she cannot register is the intended behaviour if the server correctly applies the rule. A successful product is not one that accepts every request; it is one that gives the right result for the circumstances.

Raj’s cancellation follows the same distinction between intent and result. He asks to cancel; the application checks that the registration is his and that cancellation is permitted. An accepted cancellation changes the stored participation and releases capacity under the proposed rules. An unauthorized request must not change another person’s place.

Que. 20 Sam can see an event page, but his request to edit an event he does not manage is refused. Is that necessarily a broken website?

Show answerHide answer

Answer. No. Browsing an event and editing it require different permissions. Refusing an unauthorized edit can be the correct result. To judge it, compare Sam’s role for that event with the intended access rule.

When the reply is missing, the outcome may be unknown

Now imagine that Sai submits and her connection stops before she receives the result. There are at least two possibilities: the request never reached the point of recording a registration, or the registration was recorded and the response failed to reach her. The empty or stalled browser page cannot distinguish those possibilities.

The recovery design should let Sai check her registrations after reconnecting. A retry must not create a second active place for the same member and event. This links directly to Chapter 2’s duplicate and confirmation requirements. Do not assume that a missing reply means “nothing happened”, and do not ask a learner to delete records or repeatedly submit to test that guess.

Que. 21 Why is immediately pressing the registration button several more times a poor recovery plan?

Show answerHide answer

Answer. The first attempt may already have succeeded. Repeated submissions add requests without resolving what happened. The application should offer an authoritative way to check the result and should prevent duplicate active registrations if a request is repeated.

Try it yourself: trace and diagnose the journey

On paper, describe Sai’s journey in six stages: locate the host; fetch the event; display it; submit registration; decide and record; show the result. Add two branches: the event is full, and the response is lost after submission. For each branch, state what Sai knows and what the application must ensure. Use the diagrams and Chapter 2’s requirements; no live actions or code are required.

Que. 22 What would a complete model walkthrough contain?

Show answerHide answer

Answer. The browser reaches the host and requests the event. The server returns content, which the browser displays. Sai submits a registration request. The application checks identity and current rules, records an accepted result, and returns or redirects to an accurate result page. If the event is full, it refuses the new registration and explains why. If the response is lost, Sai’s outcome is uncertain until she checks stored participation; a repeated request must not create a duplicate.

Key terms

Readiness checkpoint: You can label the parts of an address, explain the two directions of an exchange, distinguish reading from requesting a change, and place shared rules on the server. You can also explain why a lost reply leaves a registration outcome uncertain. If one step is unclear, revisit its diagram and model answer before moving on.

You have produced a reasoned walkthrough, not a deployed application. Keep it alongside Chapter 2’s requirements: later chapters will turn these messages, decisions, and observations into runnable behaviour and tests.
