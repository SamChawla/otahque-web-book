What You Need to Know

Browsers, servers, and an event page

Soni wants to decide whether a community event is suitable for her. In our proposed Otahque application, she follows a link to its published event page. The page should show the information she needs to make that decision. What has to happen between following the link and reading the result?

Begin with the browser

A browser is an application that lets a person open and interact with web pages. Edge, Firefox, Chrome, and Safari are examples. Soni uses her browser to follow the event link; the browser does the communication needed to obtain the page.

The internet is the network infrastructure connecting devices and networks around the world. The web is one system that uses that infrastructure to make pages and other resources available through addresses and links. A resource is something a browser can ask for, such as an event page or an image. Other systems, including email, also use the internet.

A browser and a search engine have different jobs. A search engine helps find pages; a browser displays and lets us use them. Soni can follow an event link someone sent her without first searching for the event.

One website, several pages

Suppose Soni starts at an Otahque page listing upcoming events. She notices a Python workshop and follows its title. The browser now displays the detail page for that workshop. These are two pages within the same website: one helps her choose an event; the other helps her examine that choice.

A web page is a document the browser can display. Its content and structure are described using Hypertext Markup Language, shortened to HTML. Structure means such things as which text is a heading, which items form a list, and which words are links. We will write HTML later; for now, recognize that the browser receives a description of the page rather than a photograph of someone else’s screen.

A website groups related pages and resources. Otahque’s event list, individual event details, and account pages will belong to one site. Soni can move between those pages while continuing to use the same browser application. Figure 3.1 shows this distinction using a proposed reading journey.

Read the arrow as “follow this link”, not “move the entire website”. The detail page is about the selected event. The browser is the tool displaying it. The surrounding boundary groups pages that belong together; it does not represent the physical size of a server.

Que. 1 Soni follows the Python workshop link. Has she opened a different browser, a different page, or necessarily a different website?

Flip to check your answerFold answer back

Answer. She has opened a different page. In this example, both pages belong to Otahque, and she is still using the same browser. A link can also lead to another website, but that is not what the illustrated link does.

Meet the other side: the web server

The browser needs another program to receive its request and return information. Software doing that job is called a web server. People also use “server” for the computer running that software. In this chapter, focus on the job: receiving a request, handling it, and sending a response.

The browser acts as a client: software asking a service for something. A request is the message it sends. A response is the message sent back. Soni is the person using the client; she does not need to construct these messages herself.

These are software roles, not two special types of computer. Later, your own computer will run both a browser and a development server. A public site may use several machines behind the service a visitor reaches. We can understand the basic exchange before deciding how Otahque will be hosted.

Que. 2 If Soni opens the same event on her phone instead of her laptop, which role does the phone’s browser perform?

Flip to check your answerFold answer back

Answer. It is still the client. The device has changed, but the browser still asks the website for information and displays the result. Client and server describe jobs in the exchange.

New Concept: HTTP

What problem exists? A browser and a server, written by different people, have to understand each other’s messages.

What did people do before? Before a shared format existed, each client and server needed their own agreement about how to interpret each message.

What is HTTP? The Hypertext Transfer Protocol: the agreed rules for web messages. A client sends a request with a method, an address, headers, and sometimes a body; the server returns a response with a status code, headers, and usually a body. HTTPS is the same protocol protected by TLS.

Why it matters to us? Django receives HTTP requests and returns HTTP responses, so every view we write answers one of these messages.

Now let’s follow one.

Follow one successful page visit

First, Soni follows the event link. Her browser sends a request asking for that page. Next, the server handles the request and returns a response containing page content. Finally, the browser interprets that content and displays a page she can read. Figure 3.2 separates the outgoing request from the returning response.

This is a simplified successful exchange. A real page may need further requests for images and other supporting files. The diagram leaves out the intermediate network machinery so we can follow the two roles. The next topic explains how an address helps the browser reach the right site.

The response does not have to be a page already saved as a finished file. An application can assemble page content when a request arrives. For example, Otahque will need to present information about the particular published event Soni chose. We will examine that distinction in “What runs in the browser and on the server”; no application has been built at this point.

One page can need several exchanges

Imagine that the workshop page includes a photograph of the venue. The page document can identify where that photograph is available without containing the image itself. After reading the document, the browser can ask for the image in another request. The server then returns image data in another response.

In Figure 3.3, the messages are arranged over time. Start at the top and read downwards. The browser first obtains the document, discovers the image reference, and obtains the image. It combines the information into the page Soni sees. Each returning arrow answers a particular request.

This is one possible loading sequence, with only two resources shown. Browsers can fetch several resources at once and can sometimes reuse copies they already have. The picture is not a promise that every page always makes two requests in exactly this order. Its purpose is to show why “open a page” can involve more than one exchange.

Now give the example a problem: Soni can read the workshop description, but the venue photograph does not appear. The visible description is useful evidence: at least some page content is available to her. It does not tell her whether the image is missing on the server, could not be reached, or failed to display. Those possibilities require further observation.

Que. 3 Does a missing venue photograph prove that the whole Otahque website is unavailable?

Flip to check your answerFold answer back

Answer. No. The document and photograph are separate resources in this example. Soni can report that the description is visible while the photograph is missing. That precise observation is more useful than claiming the whole site is down; the cause is still unknown.

In practice: reporting a partially loaded page

Situation. An event page shows its description, but the venue photograph is missing.

Application. Report which content is visible and which resource is absent. Thinking in separate request-and-response exchanges helps a developer narrow the investigation.

Consideration. The observation does not establish the cause. Avoid reporting that the entire service is down when only one part has been checked.

No browser changes, commands, or project files are needed.

Que. 4 What would a useful explanation and problem report say?

Flip to check your answerFold answer back

Answer. Soni may be able to read the workshop description contained in the document, but she cannot yet see the venue photograph. A useful report is: “The workshop description is visible, but the venue photograph is missing.” It identifies the affected part of the page without claiming that the server, network, or browser is definitely responsible.

Reading an event is different from registering

Chapter 2 separated browsing from registration. That distinction still matters here. Opening the event page asks to read about the event. Under our proposed requirements, it does not reserve a place for Soni.

If Soni later chooses to register, the application must handle a separate request for that action and check the relevant rules. A page that looks encouraging is not, by itself, evidence that a registration was recorded. When we implement registration, the confirmation must reflect the result of the server’s decision.

Que. 5 Soni can see the event description. Does this establish that she has a place at the event?

Flip to check your answerFold answer back

Answer. No. It establishes that the browser has displayed event information. Registering is a separate action with its own result. Reading the page must not silently create a registration.

Consider Sai checking a confirmation while Sam plans the event. Sai needs a result about her own place; Sam needs an authorized view of registrations for the event he manages. Both use browsers, but their questions and permitted information differ. The client/server vocabulary tells us where the messages go. Chapter 2’s requirements tell us what the application must decide before answering.

That distinction will guide our later tests. A page appearing on screen is one observation. The application recording the right registration, refusing a duplicate, and showing the result to the right person are additional behaviours to verify. For this section, practise describing the exchange without treating the visible page as proof of every underlying rule.

Finding and reaching a web address

Soni receives a link to a workshop. Before following it, she wants to know which site it opens and whether it points to the event she expects. Reading an address is useful to a visitor; later, it also helps a developer distinguish a wrong destination from a missing page.

Read the address in parts

A web address is a Uniform Resource Locator, or URL. Consider the fictional address below. It is an illustration to read on paper, not a working Otahque route or an instruction to visit a site.

Output

https://otahque.example/events/42/?view=details#venue

The scheme, https, names the protocol: the agreed rules for the exchange. Here it is HTTPS, a protected form of the Hypertext Transfer Protocol, or HTTP; the end of this section explains what that protection covers. The host, otahque.example, names the destination. The path, /events/42/, identifies a resource at that host. The query, view=details, supplies an extra value after the question mark. The fragment, venue, follows the hash sign and can identify a position within the returned page. Query and fragment are optional.

For this example, the site would decide what event 42 and view=details mean. A readable path is not evidence that a matching file exists on disk. The server can use the path to choose application behaviour. The fragment is not sent in the HTTP request; the browser uses it after obtaining the resource.

Que. 7 If Soni changes only #venue to #schedule, is she asking for a different host?

Flip to check your answerFold answer back

Answer. No. The host has not changed, so the browser is still dealing with the same site. The fragment points within the resource and is handled by the browser. Whether the page contains a matching location is a separate question.

Find the host before asking for its page

Computers use network addresses to communicate. An Internet Protocol address, shortened to IP address, is one kind of address used to reach a network destination. A memorable host name and an IP address are different things. The Domain Name System, or DNS, provides name lookups that can supply addresses associated with a host.

In a simplified fresh visit, the browser and operating system obtain an address for the host, establish the required connection, and then ask the web service for a resource. A DNS lookup does not return the event description and does not decide whether Soni may register. Those are later jobs.

The lookup step may use a previously saved result. A host can also have more than one address, so the diagram is not a claim that each visit performs a new lookup or always reaches the same machine. The useful distinction is between finding where to connect and asking the connected service what to return.

Que. 8 The host lookup fails before an event request can be made. Should Soni conclude that the workshop has been deleted?

Flip to check your answerFold answer back

Answer. No. The failure concerns reaching the named host. It says nothing about whether the workshop exists. First check the spelling of the host and whether other sites can be reached; do not change or delete event data to solve a connection problem.

What HTTPS protects

HTTP defines how web requests and responses are written and exchanged. HTTPS uses Transport Layer Security, or TLS, to encrypt communication between the client and server. Encryption makes the transmitted content unreadable to someone who merely observes that protected connection.

This protection matters when Sai later signs in. It does not decide whether Sai owns a registration, whether a place remains, or whether the displayed event details are truthful. Those questions belong to the application and its people. A protected connection to the wrong site is still the wrong destination, so Soni must read the host as well as the scheme.

Que. 9 Does HTTPS allow Raj to cancel another member’s place?

Flip to check your answerFold answer back

Answer. No. HTTPS protects the exchange in transit. Otahque must still identify Raj and enforce the rule that he can cancel only his own registration. Transport protection and permission checks solve different problems.

In practice: investigating a broken event link

Situation. A shared event link fails, although another page on the same website opens.

Application. Compare the host and path with the intended address before changing application settings. Distinguishing the site address from the requested page makes the report more precise.

Consideration. Do not paste private query values into a public issue. An address can contain information that was intended only for its recipient.

Try it yourself

On paper, annotate the fictional address above. Circle the host, underline the event path, and mark the optional query and fragment. Then describe which part changes if Soni opens event 43 on the same host. No site visit, installation, or file change is required.

Flip to check your answerFold answer back

Answer. Circle otahque.example and underline /events/42/. Mark view=details as the query and venue as the fragment. For event 43 in this invented naming scheme, the path becomes /events/43/; the host stays the same. This shows a different resource on the same host, not a different DNS name.

Asking for information and requesting changes

Soni reads the workshop page. Sai, who already has an account in our proposed application, wants to register. Both actions involve messages, but they have different purposes. Reading should not silently consume a place. Registration asks the application to change its records.

A request has an action as well as an address

An HTTP method names the kind of action requested. GET asks for information about a resource. POST sends data for the server to process and is commonly used for actions that change application state. State means the information the application currently holds, such as which members have active registrations.

For Otahque, opening an event is a reading action. Submitting a registration is a request for a change. A form is a page element through which a person supplies information or submits an action. The browser translates its submission into a request; the application must decide whether to accept it.

Choosing POST does not make a request trustworthy, encrypt it, or prevent a second submission. HTTPS provides transport protection; application checks enforce the rules. Repeating a POST can have further effects unless the application handles repetition correctly. This is why Chapter 2’s duplicate-registration requirement must become a server-side check later.

Que. 11 Should following a link to read an event register the visitor as a side effect?

Flip to check your answerFold answer back

Answer. No. Reading the event is a GET-style action. Registration should require a deliberate request for the change. If simply reading a link took a place, a visitor could register unintentionally while exploring the site.

The message carries context and content

A request identifies a target and method, and can carry headers: named pieces of information about the message. It may also have a body containing submitted data. A response carries a status code, headers, and sometimes a body. For a successful event-page request, the body can contain HTML; for an image request, it can contain image data.

A header named Content-Type describes the format of a message’s body. For now, think of it as a label helping the recipient interpret what arrived. The body is the content itself. A header and body have different roles, just as a document’s format label differs from the document’s text. We will read actual request objects when we reach Django views.

Under the Hood: what the messages look like

Underneath the browser’s display, an HTTP request is a short block of text: a request line naming the method, the path, and the protocol version, then headers such as Host, then an optional body. The response starts with a status line, then its headers, a blank line, and the body. The listing below shows the shape of a request for an event page and of its response. Real messages carry more headers, and HTTP/2 and HTTP/3 send the same information in a binary form, but the parts are the same.

the shape of one exchange (illustration)

GET /events/42/ HTTP/1.1
Host: otahque.example
Accept: text/html

HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8

<!DOCTYPE html> ... the event page ...

Read the response without over-interpreting it

A status code is a three-digit result attached to an HTTP response. Table 3.1 introduces a small useful set. These are general meanings, not final choices for every Otahque error or policy.

A browser connection error is different from receiving a 404 response. With a 404, a server has sent an HTTP response. A connection failure may prevent an HTTP response from arriving at all. Also, receiving 200 for a page does not prove that a registration was created: a page can successfully explain why an application action was refused.

Que. 12 Sai receives a page explaining that registration is closed. The page arrived successfully. Which result matters to her?

Flip to check your answerFold answer back

Answer. The application result: she does not have a newly confirmed place. Successful delivery of a page and successful registration are different observations. She should read the result message rather than infer a booking from the fact that a page appeared.

Common Error: a link that changes data

A plain link always makes a GET request, and browsers, link previews, and search crawlers may follow links on their own. A link that cancels a registration could therefore cancel it without anyone choosing to. Changes such as registering and cancelling belong in a form that sends POST, and the server must still check every rule when the form arrives.

A redirect asks the browser to make another request

A redirect is a response that points the browser towards another resource. One useful pattern after form processing is to return a 303 response with a Location header naming a result page. The browser then fetches that page with GET. In Figure 3.6, the result is a separate reading request after the submitted action.

Refreshing the resulting GET page normally reads it again rather than resubmitting the earlier form. This pattern helps the user experience, but it does not enforce the one-registration rule by itself. Sai could submit again from another tab, or a request could be repeated before the redirect arrives. The application still needs duplicate handling.

Que. 13 Does a redirect remove the need for a duplicate-registration check?

Flip to check your answerFold answer back

Answer. No. It separates form submission from the page subsequently displayed. It does not prevent every repeated submission. The server must still enforce the rule about one active registration per member and event.

In practice: reviewing a form submission

Situation. A registration form leads to a status page after submission, and the team wants to understand a reported duplicate.

Application. Separate the change request from the later page-reading request when describing the sequence. This helps reviewers ask which operation was repeated.

Consideration. A redirect can improve the navigation flow without enforcing uniqueness. Duplicate prevention remains an application responsibility.

Try it yourself

Classify these proposed Otahque actions on paper: Soni reads event details; Sai submits a registration; Raj submits a cancellation; Sam reads the list for an event he manages. For each, say whether it asks to read or requests a change, then name GET or POST as the method to consider. Do not perform these actions on a live site.

Que. 14 How should the four actions be classified?

Flip to check your answerFold answer back

Answer. Soni reads details: reading, GET. Sai registers: change request, POST. Raj cancels: change request, POST. Sam reads his event’s list: reading, GET. Reading can still require permission: GET does not mean that every visitor may see Sam’s list.

What runs in the browser and on the server

Sai sees an available place on an event page. While she reads, someone else may register. Which part of the system should decide whether her later request can succeed? To answer that, separate what her browser displays from what the shared application records.

Content, appearance, and interaction

HTML describes page content and structure. Cascading Style Sheets, or CSS, describe presentation such as spacing and colours. JavaScript is a programming language that can run in the browser to add behaviour. An event title can be HTML content, its visual spacing can be controlled by CSS, and a script can open or close an extra-details panel.

The three are not interchangeable. A title can remain meaningful when its styling is absent. Many links and forms work without custom JavaScript. Scripts can improve interaction, but the product should not depend on a decorative effect to communicate whether a registration succeeded. We will introduce each technology through a concrete need in later chapters.

Answer. No. Those observations concern presentation and interaction in the browser. Registration also requires the application to check the request, record the correct result, and return an accurate confirmation.

The shared decision belongs on the server

The server side is where Otahque will apply the shared rules and work with stored records. A database is an organized store of data that software can read and update. We have not designed its tables yet. At this point, it is enough to know that a lasting registration needs to be recorded somewhere beyond one open browser tab.

The page might disable a registration button after the closing time. That can help the visitor, but it cannot be the only check. Browser content can be altered, an old page may still be open, and a request can come from software other than our page. The server must check the relevant rule when it processes the request.

Suppose Sai’s page showed one remaining place, but another member took it before she submitted. The page was a view of information at an earlier time. The application must decide using current records and prevent conflicting requests from both taking the last place. Chapter 33 will address that concurrency problem; this chapter establishes why the decision cannot rely on the old page.

Que. 16 Sai edits the displayed number from zero places to ten on her own screen. What must happen if she then requests a place?

Flip to check your answerFold answer back

Answer. The server must use its own current records and rules. Editing a browser display must not create capacity or grant permission. The intended outcome comes from the application’s checks, not from a number supplied by the page.

Prefer checking rules in the browser?

Checking a form in the browser before it is sent, for example warning that an event looks full, gives quicker feedback and is worth having. It cannot replace the server’s check, because the person controlling the browser can change or skip it. We use browser checks for convenience and server checks for the rules, and we never treat the first as evidence of the second.

A page can be prepared in advance or assembled when requested

A static response can serve content prepared ahead of time. A dynamic response can be assembled for a particular request using current data. For example, the application could read Sai’s stored registrations and produce an HTML page listing them. The browser receives the resulting content; it never receives the database itself or the Python code used to produce the page.

Dynamic does not mean animated. A plain-looking page may be assembled from changing records, while a prebuilt page can contain an animation. Nor does a dynamic site have to regenerate every resource: its logo and styling can be served as ordinary files. The distinction concerns how content is prepared, not whether it looks lively.

Remembering a signed-in visitor across requests

HTTP is stateless: it does not by itself provide a continuous application memory of a visitor’s earlier requests. An application can add that continuity. A cookie is a small piece of data stored by a browser and sent with matching later requests according to its rules. A session is a way for the application to maintain context across requests.

One common arrangement gives the browser a session identifier in a cookie and keeps the related session information on the server. The identifier is a reference, not a copy of all the registration records. The server uses it to look up context, then applies permission checks. A session reference should be treated as sensitive; it is not something to paste into a problem report.

If Sai signs out, the application must stop treating subsequent requests as authorized through that sign-in. Closing a tab is not the same action as signing out. We will implement accounts in Chapter 27 and examine cookies and sessions in Chapter 28; the mechanism here is a conceptual preview, not a completed design.
