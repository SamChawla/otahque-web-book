3.4 What runs in the browser and on the server

Sai sees an available place on an event page. While she reads, someone else may register. Which part of the system should decide whether her later request can succeed? To answer that, separate what her browser displays from what the shared application records.

Content, appearance, and interaction

HTML describes page content and structure. Cascading Style Sheets, or CSS, describe presentation such as spacing and colours. JavaScript is a programming language that can run in the browser to add behaviour. An event title can be HTML content, its visual spacing can be controlled by CSS, and a script can open or close an extra-details panel.

The three are not interchangeable. A title can remain meaningful when its styling is absent. Many links and forms work without custom JavaScript. Scripts can improve interaction, but the product should not depend on a decorative effect to communicate whether a registration succeeded. We will introduce each technology through a concrete need in later chapters.

Que. 15 A photograph loads and a button changes colour when Sai points at it. Does that show that registration works?

Show answerHide answer

Answer. No. Those observations concern presentation and interaction in the browser. Registration also requires the application to check the request, record the correct result, and return an accurate confirmation.

The shared decision belongs on the server

The server side is where Otahque will apply the shared rules and work with stored records. A database is an organized store of data that software can read and update. We have not designed its tables yet. At this point, it is enough to know that a lasting registration needs to be recorded somewhere beyond one open browser tab.

The page might disable a registration button after the closing time. That can help the visitor, but it cannot be the only check. Browser content can be altered, an old page may still be open, and a request can come from software other than our page. The server must check the relevant rule when it processes the request.

Suppose Sai’s page showed one remaining place, but another member took it before she submitted. The page was a view of information at an earlier time. The application must decide using current records and prevent conflicting requests from both taking the last place. Chapter 33 will address that concurrency problem; this chapter establishes why the decision cannot rely on the old page.

Que. 16 Sai edits the displayed number from zero places to ten on her own screen. What must happen if she then requests a place?

Show answerHide answer

Answer. The server must use its own current records and rules. Editing a browser display must not create capacity or grant permission. The intended outcome comes from the application’s checks, not from a number supplied by the page.

A page can be prepared in advance or assembled when requested

A static response can serve content prepared ahead of time. A dynamic response can be assembled for a particular request using current data. For example, the application could read Sai’s stored registrations and produce an HTML page listing them. The browser receives the resulting content; it never receives the database itself or the Python code used to produce the page.

Dynamic does not mean animated. A plain-looking page may be assembled from changing records, while a prebuilt page can contain an animation. Nor does a dynamic site have to regenerate every resource: its logo and styling can be served as ordinary files. The distinction concerns how content is prepared, not whether it looks lively.

Remembering a signed-in visitor across requests

HTTP is stateless: it does not by itself provide a continuous application memory of a visitor’s earlier requests. An application can add that continuity. A cookie is a small piece of data stored by a browser and sent with matching later requests according to its rules. A session is a way for the application to maintain context across requests.

One common arrangement gives the browser a session identifier in a cookie and keeps the related session information on the server. The identifier is a reference, not a copy of all the registration records. The server uses it to look up context, then applies permission checks. A session reference should be treated as sensitive; it is not something to paste into a problem report.

If Sai signs out, the application must stop treating subsequent requests as authorized through that sign-in. Closing a tab is not the same action as signing out. We will implement accounts in Chapter 27 and examine cookies and sessions in Chapter 28; the mechanism here is a conceptual preview, not a completed design.

Que. 17 Does recognizing Sai’s session mean she may see Sam’s organizer list?

Show answerHide answer

Answer. No. Recognizing a signed-in member and authorizing access are separate decisions. The application must still check whether that member may view the requested event’s organizer information.

Try it yourself

Divide a sheet into Browser and Server. Place these tasks in the appropriate column: make an event heading blue; reject a duplicate registration; show or hide an explanation panel; decide whether Raj may cancel a particular registration; return a page showing the stored result. Explain why one task in the Server column cannot be entrusted only to a browser.

Que. 18 What is a model division of responsibility?

Show answerHide answer

Answer. Browser: display the blue heading and show or hide the panel. Server: reject duplicates, check cancellation ownership, and return content based on stored results. For example, a duplicate check must work even if the browser sends a second request or its display has been changed. The browser then renders the returned result.
