Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead and ask you to diagnose and to defend a decision. They are extension questions, not a gate to the next chapter. Practice files are run with uv run python manage.py shell -c "exec(open('NAME').read())" and deleted afterwards; the commands for L2 and L4 build and remove their own scratch database, and never touch otahque.

L1 (Junior): Why move from SQLite to PostgreSQL now, and not at deployment?

What the interviewer is testing: Can you tie a technical change to a need the product has today?

Flip to check your answerFold answer back

Perfect answer: Because the next feature cannot be proved without it. Chapter 33 must show that two members asking for the last place at the same moment get exactly one place between them. That needs separate connections running at once and a lock on the event row. SQLite has one writer at a time and no row locks, so the race can be neither shown nor fixed on it. Moving now also means every later chapter is developed and tested on the database production will use, so differences such as case-sensitive contains or sort order appear on a developer’s computer, not after deployment.

Behind the scenes:

two databases (summary)

SQLite      one file, one writer, no select_for_update
PostgreSQL  a server, many connections, row locks
Chapter 33  needs the second

Code proof: l1_features.py asks Django what each backend supports:

l1_features.py (practice file; delete it afterwards)

"""Compare what SQLite and PostgreSQL can do for Otahque."""
from django.db import connection
from django.db.backends.sqlite3.base import DatabaseWrapper

SQLite = DatabaseWrapper.features_class

print('running on:', connection.vendor)
for name in ('has_select_for_update',
             'has_select_for_update_skip_locked'):
    print(f'{name}: SQLite {getattr(SQLite, name)},',
          f'PostgreSQL {getattr(connection.features, name)}')
with connection.cursor() as cursor:
    cursor.execute('SHOW max_connections')
    print('connections at once:', cursor.fetchone()[0])

Output

running on: postgresql
has_select_for_update: SQLite False, PostgreSQL True
has_select_for_update_skip_locked: SQLite False, PostgreSQL
    True
connections at once: 100

Common mistakes:

  • Moving “for performance” without a measurement; Otahque’s reason is a capability, not speed.
  • Waiting until deployment, and meeting the differences for the first time on a live server.

Follow-up the interviewer might ask:

  • Would you keep SQLite for the tests to make them faster? (No: tests must use the database whose behaviour they prove.)
  • What else does PostgreSQL give Otahque later? (Full-text search in 56, constraints and indexes in 55.)

L2 (Mid-Level): Predict what loaddata does if the dump includes content types

What the interviewer is testing: Do you know which rows migrations create, and why ids differ between databases?

Flip to check your answerFold answer back

Perfect answer: It fails with a duplicate key on django_content_type. migrate has already created a content type for every model on PostgreSQL, numbered in the order the migrations ran there. The dump holds SQLite’s content types, with SQLite’s numbers. loaddata saves each by its id: where the id is free it inserts a row, and that row has the same app and model name as one PostgreSQL already holds, so the unique rule on app and model refuses it. The fix is to leave content types, permissions, and groups out, and let --natural-foreign point at them by name.

Behind the scenes:

content types (summary)

PostgreSQL  (admin, logentry) has id 1, made by migrate
dump        (admin, logentry) has SQLite's id
loaddata    new row, same app and model -> refused

Code proof: the commands dump everything from SQLite and load it into a scratch database otahque_l2. In PowerShell:

Common mistakes:

  • Deleting PostgreSQL’s content types before loading: it works once, and leaves permissions pointing at missing rows.
  • Leaving out content types without --natural-foreign: the admin’s history then points at the wrong models.

Follow-up the interviewer might ask:

  • Why is the error about (admin, logentry) in particular? (It is the first content type, the first row that collides.)
  • Would the same dump load into an empty database with no migrations? (No: there would be no tables to load into.)

L3 (Senior): Defend leaving out permissions and groups, but keeping the admin’s history

What the interviewer is testing: Can you separate data that code defines from data that people made, and prove the result?

Flip to check your answerFold answer back

Perfect answer: Permissions are defined by the models and created by Django after each migration; the Organizers and Administrators groups are defined by Chapter 30’s data migration. Both exist on the new database before anything is loaded, so copying them would duplicate them, and the copies would carry SQLite’s ids. What people did with them, such as Sam’s membership of Organizers, moves with the member, as group names. The admin’s history is different: each row records something a person did, and nothing can make it again, so it moves, with its content type written by name. The proof is the comparison script, which compares remade rows by name, every one of them, so a group with a missing permission would show.

Behind the scenes:

two kinds of rows (summary)

made by code    content types, permissions, groups
made by people  members, events, places, admin history
move            the second kind, by natural keys

Code proof: l3_ids.py shows that the same permission has different ids on the two sides:

l3_ids.py (practice file; delete it afterwards)

"""Show that a permission's id differs between the databases."""
import sqlite3

from django.contrib.auth.models import Permission

old = sqlite3.connect('db-before-32.sqlite3')
for codename in ('add_event', 'view_registration'):
    before = old.execute(
        'SELECT id FROM auth_permission WHERE codename = ?',
        [codename],
    ).fetchone()[0]
    now = Permission.objects.get(codename=codename).pk
    print(f'{codename}: SQLite id {before}, PostgreSQL id {now}')

Output

add_event: SQLite id 25, PostgreSQL id 34
view_registration: SQLite id 36, PostgreSQL id 46

Common mistakes:

  • Leaving out admin.logentry because “it is only a log”: it is Chapter 30’s record of who changed what in the admin.
  • Assuming a group someone edited in the admin moves: it does not; migrations define the groups, so an edit belongs in a migration.

Follow-up the interviewer might ask:

  • What if a reader had added a third group by hand? (It would be lost; the comparison would show auth_group differing, and the fix is to add it again, or by a migration.)
  • Why not keep sessions too? (They are short-lived and tied to the old setup; signing in again costs nothing.)

L4 (Staff): After a move, Soni’s profile address changed from 5 to 4. Diagnose it

What the interviewer is testing: Can you work from a symptom to an option, and prove the cause?

Flip to check your answerFold answer back

Perfect answer: Ids changed only for members, so look at what is special about members: they have a natural key, their email address. With --natural-primary, dumpdata leaves out the id of any row whose model has a natural key, and loaddata lets the new database number them. In the old database the twin account made and deleted in Chapter 21 left a gap at 4; on PostgreSQL the members were numbered without gaps, so Soni moved from 5 to 4. Everything pointing at members by key still works, because it was written by email, but every address, bookmark, and plain number that names a member, such as an audit row’s target, now means someone else. The fix is to dump with --natural-foreign only, which keeps every id. Looking ahead, it is also why the comparison script compares ids for ordinary rows.

Behind the scenes:

ids (summary)

SQLite       Sam 1, Sai 2, Raj 3, (deleted 4), Soni 5
--natural-primary  -> Soni 4 on PostgreSQL
--natural-foreign  -> Soni 5, as before

Common mistakes:

  • Copying a recipe’s options without asking what each does; --natural-primary is common in recipes.
  • Checking only the row counts, which match: the difference is in the ids.

Follow-up the interviewer might ask:

  • When is --natural-primary the right choice? (For fixtures loaded into databases that already hold other rows, where fixed ids would collide.)
  • How would you find every place an old member id is stored as a plain number? (Search the models for integer fields holding ids, such as AuditEvent.target_id.)

L5 (Lead): Defend a native PostgreSQL 18 now, and Docker in Chapter 62

What the interviewer is testing: Can you weigh a choice for a whole group of people, with its costs and the moment to revisit it?

Flip to check your answerFold answer back

Perfect answer: The readers are beginners on Windows, macOS, and Linux. A native install adds one program, managed the way their system manages programs, and they meet the database as a service they start, sign in to, and back up, which is exactly what Chapter 62 later puts in a container. Docker now would add a second new tool to a chapter that is already about a new tool, a chapter early. A hosted database would make every test depend on the network and an account. On the version: PostgreSQL 19 was three days old, hosts and the official image lag a new major version, and Django names nothing above its minimum of 15; version 18 is supported until 2030 and runs the whole suite. The decision is recorded in ADR-005 with two triggers to revisit it: Chapter 62 or the Django 6.2 upgrade, whichever comes first, and many readers unable to install a server.

Behind the scenes:

the choice (summary)

now     native PostgreSQL 18, three platforms
62      Docker image, same data, restore rehearsal
revisit 62 or Django 6.2: PostgreSQL 19

Code proof: l5_versions.py prints the versions in use and Django’s minimum:

l5_versions.py (practice file; delete it afterwards)

"""Print the versions in use here, and Django's minimum."""
import psycopg
from django.db import connection

floor = connection.features.minimum_database_version
server = connection.pg_version
print('PostgreSQL server:', server // 10000, server % 10000)
print('Django needs at least:', floor[0])
print('psycopg:', psycopg.__version__,
      '| libpq:', psycopg.pq.version() // 10000)

Output

PostgreSQL server: 18 3
Django needs at least: 15
psycopg: 3.3.9 | libpq: 18

Common mistakes:

  • Choosing the newest version because it is newest, without asking who must run it.
  • Recording the choice without the trigger that should reopen it.

Follow-up the interviewer might ask:

  • What would make you choose Docker now? (Readers failing to install, or a need for several services at once, such as Redis.)
  • How would you upgrade from 18 to 19 later? (A restore rehearsal into the new version first, as in Step 10, then the switch.)
