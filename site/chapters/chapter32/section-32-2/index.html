What You Need to Know

One file, or a server

Since Chapter 18 Django has opened db.sqlite3 itself, as a file, whenever it needed data. SQLite is excellent for that: nothing to install, nothing to start, and one file to copy. Its limits appear when several things happen at once. A write takes a lock on the whole file, so a second writer waits or fails, and there is no way to say “lock this one event row while I count its places”. Figure 32.1 sets the two side by side.

New Concept: a database server

What problem exists? Otahque must handle requests that arrive together, and the database must decide between them: who got the last place, and who must wait.

What did people do before? A file database such as SQLite serves one writer at a time. That is enough for one person developing, and not for a website at a busy moment.

What is it? A database server is a program that runs on its own, owns the data files, and answers clients over connections. Django becomes one client among others, such as psql, the command-line client, or a backup program. The server checks who is asking: each client signs in as a role, a database user with a password and permissions, and asks for one database, a named set of tables. The server listens on a port, 5432 by default.

Why use it? Many connections at once, row locks, and one place that enforces every rule for every client.

Now let’s use it. Step 2 installs PostgreSQL, and Step 3 creates the role and the database that Otahque signs in to.

A role is not an Otahque member. Sam signs in to Otahque with his email address, and Otahque signs in to PostgreSQL as the role otahque. Members never see the database, and the database never sees their passwords, only the hashes Django stores.

PostgreSQL 18 and psycopg

PostgreSQL releases a new major version every autumn and supports each for five years. Django 6.1 needs PostgreSQL 15 or later and, to talk to it, a driver: a Python package that speaks the server’s protocol. Django recommends psycopg 3.

New Tool: PostgreSQL and psycopg

What problem exists? Otahque needs a database server that Django supports, that runs on Windows, macOS, and Linux, and that every hosting service offers.

What did people do before? Commercial servers with licences, or MySQL, which Django also supports. Many Django projects start on SQLite and move later, as Otahque does now.

What is it? PostgreSQL is a free, open-source database server, developed by a community since 1996, with strict handling of types and constraints and many index types. psycopg is the PostgreSQL driver for Python; its binary package carries a ready-built copy of libpq, PostgreSQL’s client library, so nothing has to be compiled.

Why use it? It is the database most Django projects use in production, Django’s PostgreSQL support is the most complete, and Chapter 33 needs its row locks. psycopg 3 is the driver Django recommends, and Chapter 66 needs it for connection pooling.

Now let’s use it. Step 2 installs PostgreSQL 18; Step 5 adds psycopg[binary] to the project at an exact version.

The user decided to use PostgreSQL 18, not 19. Version 19 was released on 19 November 2026, three days before this chapter was checked, and hosts, installers, and the official container image take time to offer a new major version. Version 18 is supported until November 2030. Table 32.1 lists the versions this chapter pins.

The binary package is right for developing. For a production server, psycopg’s documentation prefers a build against the system’s own libpq, which security updates then reach; Chapter 62 makes that choice.

Moving data between two engines

Two kinds of rows live in Otahque’s database. Some were made by migrations: the content types that name each model (Chapter 23’s admin and Chapter 30’s permissions use them), the permissions Django creates for each model, and the Organizers and Administrators groups from Chapter 30’s data migration. Others were made by people: members, events, places, profiles, two-factor settings, and the audit trail. The first kind appears again by itself when you run migrate on the new database. Only the second kind needs moving.

Django’s dumpdata command writes rows out as a file, and loaddata reads them back into any database Django supports. Two things make the move work between engines:

  • Exclusions. Rows that migrations make again are left out of the file. If they were included, loading them would collide with the ones migrate just made: same name, different number.
  • Natural keys. A permission is 25 in one database and 34 in the other, but “events, add_event” in both. With --natural-foreign, a row that points at a permission, a content type, a group, or a member writes the name, and loaddata looks up the new number. Rows keep their own ids, so addresses such as /events/7/ stay the same.

Natural keys have a second option, --natural-primary, which leaves a row’s own id out of the file when the model has a natural key. Members have one, their email address. In Interview Question L4 you will see what that does to Soni.

Under the Hood: what loaddata does, and why the file is XML

loaddata reads the file and saves each object in raw form, skipping your models’ own save() methods, all in one transaction, so a failure leaves nothing half loaded. Rows that point at each other are fine, because PostgreSQL checks the foreign keys only when the transaction ends. Then it resets each table’s sequence, the counter PostgreSQL uses to hand out the next id, to just above the highest id loaded. Without that step, the next event Sam creates would be given id 1, which is taken. The file format matters too. Django’s JSON format writes times to the thousandth of a second, so 18:30:00.892481 becomes 18:30:00.892: every registration and cancellation time would change slightly, and a cancellation made in the same millisecond as its deadline could stop counting as late. The XML format writes all six digits, so this chapter uses XML.

Text order and collation

Ask a database to sort “apple day”, “Zebra talk”, and “Émile meets” and you may get three different answers. The rules for comparing text are called a collation. SQLite compares the numbers of the characters, their Unicode code points: capital letters (Z is 90) come before small ones (a is 97), and accented letters (É is 201) after both. PostgreSQL normally uses the collation of the computer it was installed on, so the same rows may sort one way on Windows and another on macOS, and differently again on the computer that runs the tests in Chapter 34.

New Concept: one sort order everywhere

What problem exists? Lists that Otahque sorts by text, such as the admin’s members by email address, and later search results and name lists, must come out the same for every reader and in every test run.

What did people do before? They accepted each computer’s collation and found the difference when a test passed on one machine and failed on another.

What is it? PostgreSQL 17 added a builtin collation provider that does not depend on the operating system. Its C.UTF-8 collation sorts by code point, exactly as SQLite does, on every platform.

Why use it? Otahque’s behaviour does not change in the move, and tests give one answer everywhere. Sorting names the way a language expects is a separate need, which Chapter 61 can meet column by column if other languages arrive.

Now let’s use it. Step 3 creates the database with C.UTF-8, and Step 9 makes the test database use it too.

Table 32.2 collects the differences between the two databases that matter to Otahque today.

One difference you might expect does not matter: the wording of database errors. Chapter 31’s register() never reads the message of an IntegrityError; it checks whether the member’s place exists. That is why all 342 tests pass on PostgreSQL unchanged.

A backup is proved by a restore

PostgreSQL’s own tool pg_dump writes a whole database to one file, and pg_restore reads it back. A backup that has never been restored proves nothing: the file may be empty, incomplete, or unreadable by the version you have. The habit this chapter starts is a restore rehearsal: restore into a new database, compare it with the original, then remove the copy. Chapter 65 schedules backups and Chapter 62 repeats the rehearsal with a container.

dumpdata and pg_dump have different jobs. dumpdata writes rows in a form any engine can read, which is what a one-off move between SQLite and PostgreSQL needs. pg_dump writes everything PostgreSQL holds, including indexes, constraints, and sequences, which is what a backup of PostgreSQL needs.

In practice: copies of personal data

Situation. The move file and the backup both hold every member’s email address, password hash, and phone number, and the two-factor secrets that Chapter 29 stores as plain text.

Application. Write them outside the project folder, so Git never sees them, and delete them as soon as they have done their job. Keep db-before-32.sqlite3 only until you trust the new database.

Consideration. Deleting a file is not destroying it: backups of your computer or a cloud folder may still hold a copy. Chapter 59 encrypts the two-factor secrets, and Chapter 65 decides how long Otahque keeps data at all.
