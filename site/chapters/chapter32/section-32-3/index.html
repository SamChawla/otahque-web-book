How We Build It

Start from Chapter 31, in the folder containing manage.py, with your own .env, the locked environment, 342 passing tests, every migration applied, and the work committed. This chapter installs PostgreSQL 18 and adds one package, psycopg. The new files are compare_databases.py beside manage.py and docs/adr/ADR-005-postgresql.md; config/settings.py, .env, .env.example, .gitignore, check_environment.py, events/tests.py, and seven templates and the stylesheet source change. The visible result is the same Otahque, with all its data, now served from PostgreSQL, and wider forms. Commands that differ between systems are labelled; the chapter’s checks ran in Windows PowerShell 5.1 and Git Bash, against PostgreSQL 18.3 server programs.

The Custom Way

The obvious way to move data is to read each table from SQLite and insert the same rows into PostgreSQL yourself. The practice file below does that for events. It is shown to explain what Django’s tools do for you; you do not need to run it, and it was run once against a separate, empty database:

s_by_hand.py (illustration only)

"""Copy events by hand, to see what loaddata does for us."""
import sqlite3

from django.db import IntegrityError, connection, transaction

from events.models import Event

old = sqlite3.connect('db-before-32.sqlite3')
cursor = old.execute('SELECT * FROM events_event')
names = [column[0] for column in cursor.description]
rows = [dict(zip(names, row)) for row in cursor]
print('SQLite starts_at:', repr(rows[0]['starts_at']))
print('SQLite phone_required:', repr(rows[0]['phone_required']))

columns = ', '.join(names)
marks = ', '.join(['%s'] * len(names))
sql = f'INSERT INTO events_event ({columns}) VALUES ({marks})'
with connection.cursor() as pg:
    try:
        with transaction.atomic():
            pg.execute(sql, list(rows[0].values()))
    except Exception as error:
        print('as it is:', str(error).splitlines()[0])
    for row in rows:
        row['phone_required'] = bool(row['phone_required'])
        pg.execute(sql, list(row.values()))
print('copied events:', Event.objects.count())

new = Event.objects.first()
new.pk = None
try:
    with transaction.atomic():
        new.save()
except IntegrityError as error:
    print('a new event:', str(error).splitlines()[0])

Output

SQLite starts_at: '2026-11-19 18:30:00'
SQLite phone_required: 0
as it is: column "phone_required" is of type boolean but
    expression is of type integer
copied events: 7
a new event: duplicate key value violates unique constraint
    "events_event_pkey"

Three problems in a few lines. SQLite stores times as text and true or false as 0 or 1, while PostgreSQL has real types and refuses 0 for a boolean: every column has to be translated. The rows went in with their ids, but PostgreSQL’s counter for new ids still stood at 1, so the next event Sam creates collides with an existing one. And this is one table: members, places, and permissions point at each other by number, and those numbers differ on each side. The Django Way leaves translation to dumpdata and loaddata, which know every field’s type, reset the counters, and follow relations by name.

The Django Way

The move runs in the order that Figure 32.2 shows. Steps 1 to 3 prepare, Step 4 writes the file, Steps 5 to 7 connect Django to PostgreSQL, and Step 8 loads and checks.

.gitignore (add at the end)


# The SQLite copy kept from before Chapter 32

Step 2: Install PostgreSQL 18

Install the newest PostgreSQL 18 for your system. Each installer also installs the command-line programs psql, createdb, pg_dump, and pg_restore, which this chapter uses.

  • Windows. From the PostgreSQL download page for Windows, run the installer for version 18. Keep “PostgreSQL Server” and “Command Line Tools”; pgAdmin and Stack Builder are optional. Choose a password for the postgres administrator and store it in your password manager. Keep port 5432 and the default locale.
  • macOS. Install Postgres.app with PostgreSQL 18 and follow its page for adding the command-line tools to your PATH, or use Homebrew: brew install postgresql@18, then brew services start postgresql@18, and put $(brew --prefix postgresql@18)/bin on your PATH.
  • Linux (Debian, Ubuntu). Add the PostgreSQL project’s repository with sudo apt install -y postgresql-common and sudo /usr/share/postgresql-common/pgdg/apt.postgresql.org.sh, then run sudo apt install postgresql-18. The server starts by itself.

The installer runs PostgreSQL as a background service that starts with the computer, so nothing needs to be started by hand.

Common Error: psql is not recognized

On Windows, the installer does not add its programs to PATH. A new terminal then answers:

Output

psql : The term 'psql' is not recognized as the name of a
    cmdlet, function, script file, or operable program. Check
    the spelling of the name, or if a path was included,
    verify that the path is correct and try again.

Add C:\Program Files\PostgreSQL\18\bin to your user’s Path in Windows’ Environment Variables settings, and open a new terminal, which reads the new Path. On macOS, open a new terminal after following Postgres.app’s or Homebrew’s PATH instructions.

To use the programs in the current window while you fix Path for good:

PowerShell

# PowerShell
$env:Path += ';C:\Program Files\PostgreSQL\18\bin'
psql --version

Terminal

# Git Bash
export PATH="$PATH:/c/Program Files/PostgreSQL/18/bin"
psql --version

Output

psql (PostgreSQL) 18.3

Any 18 is right; your last number may be higher. The checks for this chapter ran on 18.3, and 18.7 was the newest on 22 November 2026.

Step 3: A role and a database for Otahque

Otahque gets its own role, so the administrator’s password never goes in its settings. Sign in to PostgreSQL as the administrator; how depends on your system, as Table 32.3 shows.

On Windows:

Terminal

psql -h localhost -U postgres

At the postgres=# prompt, type:

psql, as the administrator

CREATE ROLE otahque LOGIN CREATEDB;
\password otahque
\q

CREATE ROLE makes a role that may sign in (LOGIN) and create databases (CREATEDB), which the test runner needs in Step 9. \password asks for the new password twice without showing it, and sends only its hash, so it never lands in your shell history. Choose a new password, not one you use elsewhere, and keep it for .env. \q leaves psql.

Now create the database, owned by otahque, with the code-point sort order. The command is split; in PowerShell the backtick continues it, with no space after it:

PowerShell

# PowerShell
createdb -h localhost -U postgres -O otahque -T template0 `
  --locale-provider=builtin --builtin-locale=C.UTF-8 otahque
psql -h localhost -U otahque -d otahque -x -c "\l otahque"

Terminal

# Git Bash, macOS, Linux, WSL
createdb -h localhost -U postgres -O otahque -T template0 \
  --locale-provider=builtin --builtin-locale=C.UTF-8 otahque
psql -h localhost -U otahque -d otahque -x -c "\l otahque"

On macOS leave out -U postgres in the first command; on Linux start it with sudo -u postgres and leave out -h localhost -U postgres. Each program asks for the password of the role it signs in as. -T template0 builds the database from PostgreSQL’s untouched template, which is required when the new database’s sort order differs from the server’s default. The second command signs in as otahque and lists the database:

Output

List of databases
-[ RECORD 1 ]-----+---------------------------
Name              | otahque
Owner             | otahque
Encoding          | UTF8
Locale Provider   | builtin
Collate           | English_United States.1252
Ctype             | English_United States.1252
Locale            | C.UTF-8
ICU Rules         |
Access privileges |

-x prints one field per line. Look for builtin on the Locale Provider line and C.UTF-8 on the Locale line. Collate and Ctype show the server’s own default, which a database with the builtin provider does not use for sorting. Typing the password for every command soon becomes tiring. psql and the other programs can read it from a password file: on Windows %APPDATA%\postgresql\pgpass.conf, elsewhere ~/.pgpass with permissions 600, one line localhost:5432:*:otahque:yourpassword. It is a secret like .env; use it only on your own computer.

Step 4: Write the data out of SQLite

Django still reads SQLite, so this is the moment to write the data out. The command leaves out the four kinds of rows that migrations make again or that should not move, follows relations by name, and writes XML to a file one folder up, outside the project:

PowerShell

# PowerShell
uv run python -X utf8 manage.py dumpdata --format xml `
  --natural-foreign --exclude contenttypes `
  --exclude auth.permission --exclude auth.group `
  --exclude sessions -o ../otahque-data.xml

Terminal

# Git Bash, macOS, Linux, WSL
uv run python -X utf8 manage.py dumpdata --format xml \
  --natural-foreign --exclude contenttypes \
  --exclude auth.permission --exclude auth.group \
  --exclude sessions -o ../otahque-data.xml

The command prints nothing when it succeeds. ../otahque-data.xml now holds your members, events, places, profiles, email addresses, two-factor settings, organizer assignments, audit rows, and the admin’s history. Group memberships travel with each member, as group names.

Common Error: ’charmap’ codec can’t encode character

Without -X utf8, Python on Windows writes files in the computer’s old code page, which has no room for many characters. One Hindi word in an event description is enough:

Output

CommandError: Unable to serialize database: 'charmap' codec
    can't encode characters in position 43-48: character maps
    to <undefined>

A half-written file is left behind. Delete it and run the command again with -X utf8, which makes Python write UTF-8. macOS and Linux already use UTF-8; the option does no harm there.

Step 6: Choose the database from .env

The settings have named one SQLite file since Chapter 6. Replace the whole Database section of config/settings.py, from the # Database comment to the closing brace of DATABASES, with:

config/settings.py (replace the Database section)

# Database
# https://docs.djangoproject.com/en/6.1/ref/settings/#databases
# SQLite until DB_ENGINE names another backend, such as
# PostgreSQL from Chapter 32 (docs/adr/ADR-005-postgresql.md).

SQLITE = 'django.db.backends.sqlite3'
# An empty DB_ENGINE line in .env also means SQLite.
DB_ENGINE = config('DB_ENGINE', default='') or SQLITE
if DB_ENGINE == SQLITE:
    DATABASES = {
        'default': {
            'ENGINE': SQLITE,
            'NAME': BASE_DIR / 'db.sqlite3',
        }
    }
else:
    try:
        DATABASES = {
            'default': {
                'ENGINE': DB_ENGINE,
                'NAME': config('DB_NAME'),
                'USER': config('DB_USER'),
                'PASSWORD': config('DB_PASSWORD'),
                'HOST': config('DB_HOST', default='localhost'),
                'PORT': config('DB_PORT', default='5432'),
            }
        }
    except UndefinedValueError as error:
        raise ImproperlyConfigured(
            f'{error} See .env.example.'
        ) from None

With DB_ENGINE missing or empty, nothing changes: Django uses SQLite, as every earlier chapter’s checkpoint expects. With DB_ENGINE set, the other five values are read, and a missing one stops Django with a message naming it, as a missing secret key has since Chapter 8. Add the six names, without the password, at the end of .env.example:

.env.example (add at the end)

# The database (Chapter 32). Leave DB_ENGINE empty for
# SQLite; for PostgreSQL set it and the five values below.
DB_ENGINE=
DB_NAME=otahque
DB_USER=otahque
DB_PASSWORD=
DB_HOST=localhost
DB_PORT=5432

And the real values at the end of your own .env, which Git ignores:

.env (add at the end)

DB_ENGINE=django.db.backends.postgresql
DB_NAME=otahque
DB_USER=otahque
DB_PASSWORD=the password you chose in Step 3
DB_HOST=localhost
DB_PORT=5432

Put the password you chose in Step 3 after DB_PASSWORD=. Then let check_environment.py, the helper from Chapter 4, also say which database is in use. Replace the file with:

check_environment.py

"""Show the Python, environment, Django, and database in use."""
import os
import sys

import django


def database():
    """Return the database Django uses here, and its version."""
    os.environ.setdefault('DJANGO_SETTINGS_MODULE',
                          'config.settings')
    django.setup()
    from django.db import connection

    with connection.cursor() as cursor:
        if connection.vendor == 'postgresql':
            cursor.execute('SHOW server_version')
        else:
            cursor.execute('SELECT sqlite_version()')
        return f'{connection.vendor} {cursor.fetchone()[0]}'


print(sys.version.split()[0])
print(sys.executable)
print(sys.prefix != sys.base_prefix)
print(django.get_version())
print(database())

Terminal

uv run python check_environment.py

Output

3.14.9
...\.venv\Scripts\python.exe
True
6.1.2
postgresql 18.3

The last line is the proof that Django now talks to PostgreSQL, not to SQLite. Run this check whenever you are unsure which database a terminal is using.

Common Error: password authentication failed

A wrong password in .env, or a role name that does not match, ends in:

Output

psycopg.OperationalError: connection failed: connection to
    server at "127.0.0.1", port 5432 failed: FATAL:
    password authentication failed for user "otahque"

Step 8: Load the data and compare

The comparison is a small program of its own, kept in the project so that Chapter 62 can use it again. Create compare_databases.py beside manage.py:

compare_databases.py

"""Compare Otahque's database with a copy, table by table.

Run: uv run python compare_databases.py OTHER
OTHER is a SQLite file, such as db-before-32.sqlite3, or the
name of another PostgreSQL database on the same server.
"""
import os
import sys

import django
from django.conf import settings

# Rows that migrations make again, with new ids.
REMADE = {'contenttypes.contenttype', 'auth.permission',
          'auth.group', 'auth.group_permissions'}
# Rows left behind on purpose.
NOT_MOVED = {'sessions.session': 'everyone signs in again'}


def other_database(name):
    """Return settings for the database to compare with."""
    if name.endswith('.sqlite3'):
        return {'ENGINE': 'django.db.backends.sqlite3',
                'NAME': settings.BASE_DIR / name}
    return {**settings.DATABASES['default'], 'NAME': name}


def value(obj, field):
    """Return a field's value; a related row by natural key."""
    if field.is_relation:
        related = getattr(obj, field.name)
        if hasattr(related, 'natural_key'):
            return related.natural_key()
    return field.value_from_object(obj)


def rows(model, alias, limit):
    """Return up to limit rows of a model, as tuples."""
    remade = (model._meta.label_lower in REMADE
              or model._meta.auto_created)
    fields = [f for f in model._meta.concrete_fields
              if not (remade and f.primary_key)]
    found = [tuple(value(obj, f) for f in fields)
             for obj in model._default_manager.using(alias)
             .order_by('pk')[:limit]]
    return sorted(found, key=repr) if remade else found


def main():
    """Print one line per table; return how many differ."""
    from django.apps import apps
    from django.db import connections

    here = connections['default']
    print(f'here:  {here.vendor} {here.settings_dict["NAME"]}')
    print(f'other: {sys.argv[1]}')
    differ = 0
    for model in apps.get_models(include_auto_created=True):
        label = model._meta.label_lower
        table = model._meta.db_table
        if label in NOT_MOVED:
            print(f'skip  {table}: {NOT_MOVED[label]}')
            continue
        a = model._default_manager.using('default').count()
        b = model._default_manager.using('other').count()
        # Ten rows each, or every row that migrations remake.
        limit = 10 if label not in REMADE else None
        same = a == b and (rows(model, 'default', limit)
                           == rows(model, 'other', limit))
        differ += not same
        mark = 'ok  ' if same else 'DIFF'
        print(f'{mark}  {table}: {a} / {b}')
    print('every table matches' if not differ
          else f'{differ} table(s) differ')
    return differ


if __name__ == '__main__':
    os.environ.setdefault('DJANGO_SETTINGS_MODULE',
                          'config.settings')
    # Add the second database before Django reads the list.
    settings.DATABASES['other'] = other_database(sys.argv[1])
    django.setup()
    sys.exit(1 if main() else 0)

For every model, including the hidden tables behind many-to-many fields, the script counts the rows in both databases and compares the first ten, field by field. Rows that migrations made again have different ids on each side, so it compares those by natural key instead, and every one of them, so a group that lost a permission would show. Step 12: Record the decision and commit

The move is an architecture decision with alternatives and consequences, so it gets an ADR, the fifth. Create docs/adr/ADR-005-postgresql.md:

docs/adr/ADR-005-postgresql.md

# ADR-005: PostgreSQL as Otahque's database

## Status

Proposed, November 2026 (Chapter 32). The choices follow
the user's decisions of 22 November 2026 (Chapter 32
D32.1-D32.7); this record is not yet reviewed or accepted.

## Context

Since Chapter 18 Otahque has stored its data in SQLite, a
single file that one process writes at a time. Chapter 33
must prove that two members cannot both take the last
place, which needs a database that runs separate
connections at once and locks rows (select_for_update).
SQLite does neither. Readers' practice data, including
members' two-factor rows, must survive the move.

## Options

- A: PostgreSQL 18, installed natively on each computer,
  reached through psycopg 3.
- B: PostgreSQL in Docker now (Docker arrives in
  Chapter 62).
- C: a hosted PostgreSQL service on a free tier.
- D: stay on SQLite and simulate the race.

## Decision

A. PostgreSQL 18 (18.7 was the newest patch on 22 November
2026; 19.0 was three days old), installed natively, with
psycopg[binary] 3.3.9. Settings read DB_ENGINE, DB_NAME,
DB_USER, DB_PASSWORD, DB_HOST, and DB_PORT through
python-decouple; with DB_ENGINE empty Django uses SQLite,
so earlier checkpoints still run. The database and an
empty template for tests use the builtin C.UTF-8
collation, so text sorts by code point on every computer,
as it did on SQLite. Data moved once, with dumpdata in XML
(JSON keeps times only to the millisecond) and natural
foreign keys, leaving out rows that migrations make again
and sessions, then checked by compare_databases.py.

## Consequences

- Each reader installs and runs a database server, with
  a role and password kept in .env, never in Git.
- Tests create test_otahque from otahque_template; the
  role needs CREATEDB. The whole suite runs with
  --parallel at checkpoints, one app within steps.
- contains lookups become case-sensitive; Chapter 56's
  search uses icontains or full-text search.
- The dump and backup files hold password hashes, phone
  numbers, and two-factor secrets: kept outside the
  project and deleted after use.
- Chapter 33 can lock rows; Chapter 62 moves the server
  into a container; Chapter 66 adds connection pooling.

## Revisit

At the Django 6.2 upgrade or in Chapter 62, whichever
comes first: PostgreSQL 19, once hosts and the official
image offer it. If many readers cannot install a server,
reconsider B.
