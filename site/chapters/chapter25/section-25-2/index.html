What You Need to Know

Editing a saved row: a ModelForm with an instance

Chapter 24’s EventForm created a new event. The same class can edit one, and that is all Chapter 24’s promise of “the same form” needs.

New Concept: a ModelForm with an instance

What problem exists? An edit page must start from the saved values, check what the person changes, and update that one row, never create a second one.

What did people do before? They loaded the row, copied each saved value into the page by hand, then copied each sent value back onto the row, as The Custom Way below does, and every copy was a chance to forget a check.

What is it? A ModelForm takes an optional instance= argument, a model object. Unbound, EventForm(instance=event) starts each field from the object’s values. Bound, EventForm(request.POST, instance=event) checks what was sent and copies the clean values onto that object, and its save() updates the object’s row instead of inserting a new one.

Why use it? One class, one allowlist, one set of rules for creating and editing, so a rule added for one page protects the other.

Now let’s use it. Step 3 opens the Edit event page with EventForm(instance=event), and Step 5 saves Sam’s changes.

Two details matter more on an edit than on a new event. First, a field missing from what the browser sends is not “left as it was”: a required field that is missing is an error, This field is required., exactly as on the New event page. The form never quietly keeps the stored value for a field that went missing, so a broken page cannot save half an event. Second, the allowlist still decides everything. Fields outside Meta.fields, such as status, are neither shown nor read, so an edit cannot publish a draft, and the organizer assignments, which are other rows entirely, cannot be touched through this form at all.

The validation lifecycle, in order

Chapter 24’s Under the Hood callout listed what is_valid() runs. On an edit, the order is worth learning by heart, because it decides which rule sees which value, and where its message appears. Figure 25.1 shows it.

Table 25.1 lists the stages with what each one is for and where its message goes. Two rows are new in this chapter: Step 6 writes a clean_capacity() method, and a clean() method on the model.

Two consequences follow from that order. A rule that has already failed for a field stops later rules from checking it: when the form reports an error on Ends, the model skips Chapter 21’s “ends after it starts” constraint, so the message appears once. And the instance is changed before the model checks it, valid or not.

Under the Hood: what _post_clean() does

After the form’s clean(), a ModelForm runs a method called _post_clean(). It copies every value in cleaned_data that belongs to a model field onto the instance, so event.title now holds the typed title, then calls the instance’s full_clean() with every field that is not on the form excluded, and with the fields that already failed left out of the unique and constraint checks. Any message the model raises is added to the form’s errors. Django’s documentation warns that the instance is changed this way even when the form is invalid, and advises against reusing it. That is why Step 5’s view reads the event’s title before it binds the form: after an invalid post, event.title holds the text Sam typed, not the title that is saved.

save() is the only stage that writes. A ModelForm’s save(commit=False) returns the changed instance without writing it, so the view can set something the form does not own, then call the instance’s save() itself. Otahque has no such value on the edit page, so it does not need commit=False: Chapter 24 already records the organizer after save(), in the same transaction. Step 2 shows both in a practice file.

Who may edit an event

Chapter 23 and Chapter 24 used Django’s model permissions, such as events.change_event. A model permission says what a person may do to every event, and Django checks only that. It knows nothing about who organizes which event, and its documentation leaves a check for one object to the project. Chapter 2’s PR-4 needs exactly that: organizers manage only the events assigned to them.

So the edit page asks two questions, and both must be yes: does the person hold events.change_event, and does Chapter 20’s OrganizerAssignment record them as a current organizer of this event? An administrator who holds the permission but organizes nothing is refused here, and uses the admin site, which Chapter 23 made the administrator’s tool. Figure 25.2 shows the answers.

The two refusals differ on purpose. A person who may see the event, because it is published or because they hold view_event, gets 403 Forbidden: the page exists, and they may not use it. A person who may not even see the event, such as Sai looking at Sam’s draft, gets 404 Not Found, as on the draft’s own page in Chapter 24: answering 403 would tell her that a draft with that number exists. So the view checks visibility first and the edit right second.

A saved time, shown and kept

The event’s starts_at is stored as one instant in UTC, and its zone as a name. The box on the page holds clock text, such as 2026-12-03T19:00. Editing turns the stored instant into text and, when Sam presses Save changes, turns the text back into an instant. Figure 25.3 follows that round trip.

Three rules come from it, each decided for Otahque in this chapter’s plan:

  • Shown in the event’s zone. Django writes a stored time into a box in the current zone, UTC, so Sam would see 00:00 on 4 December for his 19:00 clinic. Pressing Save changes without touching it would then read 00:00 as New York time and store 05:00 UTC: the event moves five hours, and the form calls it valid. The edit form therefore converts each stored time to the event’s zone before showing it, and adds a line under the box with both clocks together: the event’s time and the same instant in UTC.
  • Kept when untouched. If the zone is unchanged and the text in a box is exactly what the page showed, the stored instant is kept and the text is not read again. That keeps any seconds a stored time has, which the box cannot show, and it saves an event whose start falls in a repeated hour, such as 01:30 on 1 November in New York. Chapter 24’s form refuses that text, because it could mean either 01:30, but a time stored by the admin or an import can sit there, and without this rule Sam could not even correct the title.
  • Confirmed when the zone changes. Changing Time zone alone re-reads the clock text in the new zone, as creating an event does, so the event happens at a different moment. Because that is easy to do by accident, the form refuses the first save, shows the saved reading and the new one together, and adds a tick box, Yes, move the event to this zone. Ticking it and saving again stores the new instant.

Other event services make the same choice in different ways. Luma shows an event’s own time with the viewer’s local time beside it in parentheses, and users of content tools complain about whichever reading they did not expect. No rule is right everywhere. What matters is one clear rule, stated on the page, with both clocks shown together.

Capacity and the places already taken

Chapter 21 made the database refuse a capacity below 1, and Chapter 24’s form reported that refusal at the top of the page, because a model constraint’s message belongs to the whole form. Chapter 2’s PR-3 adds a second rule for an edit: a capacity reduction that would leave fewer places than members already hold is refused. A database CHECK cannot state that, because it compares a row of one table with a count from another. The model’s clean() method can, and because the admin’s forms call the model’s validation too, a rule there protects both Otahque’s page and the admin. Figure 25.4 shows the three layers that now guard capacity.

The count and the save are two steps. If a member registers between them, the event can still end up one place short. Closing that gap needs a database lock, which Chapter 33 adds for the last available place; this chapter states the rule and tests it.

What a crafted request can and cannot change

A browser sends whatever the page holds, and a script sends whatever its author wants. An edit form must assume both. Figure 25.5 shows what a crafted POST to the edit page can reach.

The rule is the same as for a new event, and Step 7 proves it with tests rather than trust. The tests matter because the edit page has more to lose: a crafted status would publish a draft, and a crafted id that the form obeyed could overwrite another event.

Two organizers, one event

An event can have several current organizers. Suppose Sam and a co-organizer both open the edit page in the morning. Sam changes the location and saves. Later, the co-organizer, whose page still holds the old location, changes the capacity and saves. The second save writes every field on its form, so the old location goes back: Sam’s change is lost, and nobody is told. This is a lost update, and the usual cure is a version check: the page carries the version it was opened at, and a save from an older version is refused with a message to reload. Step 8 shows the lost update in a practice file, and why the tempting shortcut of saving only the changed fields does not prevent it. Building the version check needs a new field and a migration, so it waits for Chapter 33, beside the lock on the last available place, and Chapter 47 gives Otahque’s future programming interface the same protection through HTTP. Until then, the last save wins, and the design note says so.

Prefer one form for creating and editing, or two?

Use one ModelForm when the fields and rules are the same, as for Sam’s events: one allowlist and one set of messages, with a few lines that run only when the form has a saved instance. Split into a second class only when the pages genuinely differ, such as a field that can be set once and never changed; then share the rules through a parent class, not by copying them.
