Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead to a larger application with a team: attempt them now, and return to them after Chapters 30 and 33. They are extension questions, not a gate to the next chapter. Each code proof is a short file in the practice folder that starts by importing Chapter 16’s setup_django.py; run it from the folder that holds manage.py with uv run python ../practice/ followed by the file name. The proofs only read your rows: any row they create is rolled back.

L1 (Junior): What does a ModelForm do between is_valid() and save()?

What the interviewer is testing: Do you know the validation lifecycle, and what has and has not happened to the object and the database before save()?

Flip to check your answerFold answer back

Perfect answer: is_valid() runs the whole lifecycle once. Each field converts and checks its text, then any clean_<name>() method adds a rule for that field. The form’s clean() checks rules across fields. Then the ModelForm copies the cleaned values onto the instance and runs the model’s full_clean(): field validators, the model’s clean(), unique checks, and constraints, skipping checks for fields that have already failed. Every message lands in errors, beside a field or at the top. Nothing is written: the instance in memory has changed, valid or not, and the row in the database has not. save() writes it, or save(commit=False) returns it unsaved so I can set something the form does not own. In Otahque, Sam’s typed title is on the event after is_valid(), and still not in the database.

Behind the scenes:

the lifecycle of one edit (summary)

fields, clean_<name>()  -> each value
form clean()            -> values together
_post_clean()           -> copy onto instance
model full_clean()      -> model rules, constraints
save()                  -> the only write

Code proof: Sam’s clinic, after a valid is_valid() and before save():

../practice/l1_order.py

import setup_django
from events.forms import EventForm
from events.models import Event

clinic = Event.objects.get(title='Online Django clinic')
sent = {'title': 'Django clinic',
        'timezone': 'America/New_York',
        'starts_at': '2026-12-03T19:00',
        'ends_at': '2026-12-03T20:30',
        'location': 'Online', 'capacity': '50'}
form = EventForm(sent, instance=clinic)
print(form.is_valid(), clinic.title)
stored = Event.objects.get(pk=clinic.pk)
print('stored:', stored.title)
print('times kept:', form.cleaned_data['starts_at']
      == stored.starts_at)

Output

True Django clinic
stored: Online Django clinic
times kept: True

The form is valid and the instance already holds “Django clinic”, while the stored row still says “Online Django clinic”. The start was left as shown, so the cleaned start is exactly the stored one.

Common mistakes:

  • Believing is_valid() leaves the instance alone, and showing it after a failure.
  • Thinking a constraint runs before the form’s clean().
  • Using commit=False and forgetting to save the instance.

Follow-up the interviewer might ask:

  • “Where would you put a rule that needs a query, and why?”
  • “When do you need save_m2m()?”

L2 (Mid-Level): Two members hold places. Sam sets capacity to 1, then to 2. Predict each response and what is saved.

What the interviewer is testing: Can you trace a rule that spans two tables through the lifecycle, and say exactly where its message appears and what reaches the database?

Flip to check your answerFold answer back

Perfect answer: With 1, the field converts the text to the number 1, and clean_capacity() passes, because 1 is more than 0. The form’s clean() passes too. The ModelForm copies 1 onto the event and runs the model’s clean(), which counts the active registrations, two, and raises a ValidationError naming capacity: “Capacity cannot be below the places already taken: 2.” The form shows it beside Capacity, is_valid() is false, the view returns the page with status 200 and Sam’s other values, and nothing is saved. With 2, every stage passes, a cancelled registration is not counted, save() updates the row, and the response is a redirect to the event page with “Changes saved.” The same rule refuses 1 in the admin, because the admin’s form runs the model’s clean() as well.

Behind the scenes:

capacity 1, two places (summary)

field             -> 1
clean_capacity()  -> passes: more than 0
model clean()     -> 2 taken: error on capacity
is_valid() False  -> 200, same page, no save()

Code proof: two registrations, made and rolled back inside a transaction:

../practice/l2_capacity.py

import setup_django
from django.db import transaction
from accounts.models import User
from events.forms import EventForm
from events.models import Event
from registrations.models import Registration

with transaction.atomic():
    clinic = Event.objects.get(title='Online Django clinic')
    for email in ('sai@example.org', 'raj@example.org'):
        member = User.objects.get(email=email)
        Registration.objects.create(event=clinic,
                                    member=member)
    for capacity in ('1', '2'):
        clinic = Event.objects.get(pk=clinic.pk)
        form = EventForm({
            'title': clinic.title,
            'timezone': clinic.timezone,
            'starts_at': '2026-12-03T19:00',
            'ends_at': '2026-12-03T20:30',
            'location': clinic.location,
            'capacity': capacity,
        }, instance=clinic)
        valid = form.is_valid()
        errors = form.errors.get('capacity', ['valid'])
        print(capacity, valid, errors[0])
    transaction.set_rollback(True)

Output

1 False Capacity cannot be below the places already taken: 2.
2 True valid

Common mistakes:

  • Putting the floor only in Otahque’s form, so the admin can still lower capacity.
  • Counting every registration, cancelled ones included.
  • Claiming the check prevents a race: a registration can arrive between the count and the save.

Follow-up the interviewer might ask:

  • “How would you stop a registration slipping in between the count and the save?”
  • “Why not a database CHECK for this rule?”

L3 (Senior): The form already refuses a capacity of 0. Defend keeping the database constraint.

What the interviewer is testing: Do you understand layered validation, and which layer is the last line rather than the friendly message?

Flip to check your answerFold answer back

Perfect answer: Each layer covers a different way in. The form’s clean_capacity() exists for people: it explains the rule beside the field, in words Sam understands. The model’s validation covers every ModelForm, the admin’s included. But code can write rows without either: QuerySet.update(), bulk_create(), a data migration, a management command, or someone in the shell. Only the database sees every write. Chapter 21’s constraint is that last line, so a bug in a later script cannot store an event with no places. The cost is small: one CHECK, already written. To keep the layers from disagreeing, the form reuses the constraint’s message, through one constant, so they can never say different things.

Behind the scenes:

who checks capacity (summary)

clean_capacity()  -> the page: friendly message
model full_clean  -> ModelForms, the admin
database CHECK    -> everything: update(), shell

Code proof: the model’s check and the database, both bypassing the form:

../practice/l3_backstop.py

import setup_django
from django.core.exceptions import ValidationError
from django.db import IntegrityError, transaction
from events.models import Event

clinic = Event.objects.get(title='Online Django clinic')
clinic.capacity = 0
try:
    clinic.full_clean()
except ValidationError as error:
    print('full_clean():', error.messages[0])
try:
    with transaction.atomic():
        Event.objects.filter(pk=clinic.pk).update(capacity=0)
except IntegrityError as error:
    print('update():', type(error).__name__)
print('stored:', Event.objects.get(pk=clinic.pk).capacity)

Output

full_clean(): Capacity must be more than 0.
update(): IntegrityError
stored: 50

full_clean() reports the constraint’s message, update() skips Python entirely and is refused by the database, and the stored capacity is unchanged.

Common mistakes:

  • Dropping the constraint because “the form already checks it”.
  • Writing the message twice, so the page and the database drift apart.
  • Catching IntegrityError and showing it to people instead of validating first.

Follow-up the interviewer might ask:

  • “Which writes skip full_clean() in Django?”
  • “How would you add such a constraint to a table that already has bad rows?”

L4 (Staff): Organizers report that saving an edit, without changing anything, moved their event by five hours. Diagnose and fix it.

What the interviewer is testing: Can you find a round-trip bug between display and input, prove it with a failing test, and fix it without breaking edge cases?

Flip to check your answerFold answer back

Perfect answer: I would compare what the page shows with what the form reads. Django writes a stored time into a box in the current zone, UTC, so a 19:00 New York event shows 00:00 on the next day. On save, the form reads the text in the event’s zone, as it must for typed times, so 00:00 becomes 00:00 in New York: five hours later than stored. Every unchanged save moves the event. First I write a failing test that sends the edit page back exactly as shown and expects the same instant. The fix has two parts: show stored times converted to the event’s zone, and keep the stored instant when the zone and the text are unchanged. The second part also keeps seconds the box cannot show, and an event in a repeated clock hour, which reading the text again would refuse. I would also check the data: events edited since the bug shipped may already have moved.

Behind the scenes:

one unchanged save (summary)

stored            -> 00:00 UTC, 4 December
shown in UTC      -> 2026-12-04T00:00
read in New York  -> 05:00 UTC: moved 5 h
shown in zone     -> 2026-12-03T19:00: kept

Code proof: the same clinic, sent back first with UTC text, then with the text the page shows:

../practice/l4_drift.py

import setup_django
from events.forms import EventForm
from events.models import Event

clinic = Event.objects.get(title='Online Django clinic')
NAMES = ('starts_at', 'ends_at')
in_utc = {name: f'{getattr(clinic, name):%Y-%m-%dT%H:%M}'
          for name in NAMES}
in_zone = EventForm(instance=clinic).shown
for label, texts in (('UTC text', in_utc),
                     ('zone text', in_zone)):
    clinic = Event.objects.get(pk=clinic.pk)
    before = clinic.starts_at
    form = EventForm({
        'title': clinic.title, 'timezone': clinic.timezone,
        'location': clinic.location, 'capacity': '50',
    } | texts, instance=clinic)
    form.is_valid()
    moved = form.cleaned_data['starts_at'] - before
    print(label, texts['starts_at'], 'moved by', moved)

Output

UTC text 2026-12-04T00:00 moved by 5:00:00
zone text 2026-12-03T19:00 moved by 0:00:00

Common mistakes:

  • Setting the server’s TIME_ZONE to New York, which breaks every event in another zone.
  • Using changed_data, which reports both times as changed.
  • Fixing the display and forgetting the events already moved.

Follow-up the interviewer might ask:

  • “How would you find the events the bug already moved?”
  • “What changes when Chapter 28 shows each viewer their own zone?”

L5 (Lead): A manager wants any staff account to edit any event from Otahque’s own pages. What do you advise?

What the interviewer is testing: Can you weigh convenience against a written rule, and offer a safe path rather than a flat no?

Flip to check your answerFold answer back

Perfect answer: I would ask what problem they are solving: usually, fixing a mistake while the organizer is away. Otahque’s requirement PR-4 says organizers manage only the events assigned to them, and today the edit page enforces it: change_event and a current assignment, both. Staff already have a tool for exceptions, the admin site, which records each change in its history. Letting every staff account edit every event on Otahque’s pages would make PR-4 false, widen what one stolen staff account can change, and blur who answers for an event. If the need is real, I would offer to assign a staff member as an organizer of that event, which is recorded and can be revoked, and design proper roles in Chapter 30. If the manager still wants the change, it is a requirement change: update PR-4, then change can_be_edited_by() and its tests together.

Behind the scenes:

who may edit (summary)

change_event alone  -> the admin site
plus assignment     -> Otahque's edit page
assignment          -> recorded, revocable
rule change         -> PR-4 first, then code

Code proof: Sam and a staff account that holds change_event but organizes nothing, made and rolled back:

../practice/l5_staff.py

import setup_django
from django.contrib.auth.models import Permission
from django.db import transaction
from accounts.models import User
from events.models import Event

with transaction.atomic():
    clinic = Event.objects.get(title='Online Django clinic')
    staff = User.objects.create_user(
        'staff@example.org', display_name='Staff',
        is_staff=True,
    )
    staff.user_permissions.add(Permission.objects.get(
        codename='change_event'))
    staff = User.objects.get(pk=staff.pk)
    sam = User.objects.get(email='sam@example.org')
    for person in (sam, staff):
        print(person.email,
              person.has_perm('events.change_event'),
              clinic.has_organizer(person),
              clinic.can_be_edited_by(person))
    transaction.set_rollback(True)

Output

sam@example.org True True True
staff@example.org True False False

Both hold the permission; only Sam organizes the clinic, so only he may edit it.

Common mistakes:

  • Treating a permission as ownership of every object.
  • Answering “no” without offering a recorded, revocable alternative.
  • Changing the code before changing the requirement it breaks.

Follow-up the interviewer might ask:

  • “How would Chapter 30’s roles express a staff override that is recorded?”
  • “What should the history show when staff edit an event?”
