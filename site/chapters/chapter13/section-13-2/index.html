What You Need to Know

Three kinds of files a page depends on

So far every response has been HTML that a view builds from a template. A styled page also needs files that are sent to the browser exactly as they are, such as a stylesheet, a script, or a logo. Django calls these static files: they belong to the code of the site and change only when we change the code.

A third kind looks similar but is very different. When a member uploads something, such as an event cover image in a later chapter, that file comes from a user at run time. Django calls it media. It needs storage, size limits, and checks that static files do not, so Django keeps the two apart from the start. Table 13.1 compares all three.

New Tool: Django’s static files app

What problem exists? The browser asks for a stylesheet by address. Something has to turn that address into the right file on disk, and every template has to write the address the same way.

What did people do before? They copied files into a folder that the web server published and typed paths such as /static/site.css into each page. When the folder or address changed, every page had to change too.

What is the static files app? django.contrib.staticfiles, already in INSTALLED_APPS since Chapter 6. It searches known folders for a file by its relative name, called finding it, and gives templates the {% static %} tag, which builds the file’s address from the STATIC_URL setting.

Why use it? The name in the template, such as otahque/site.css, stays the same wherever the file is stored and however it is served. During development, the development server sends found files for us.

Now let’s use it.

Three settings and one tag do the work. STATIC_URL, already 'static/' in our settings, is the start of every static address, so otahque/site.css is served at /static/otahque/site.css. STATICFILES_DIRS lists extra folders to search; we will add a project-level static folder, just as Chapter 12 added a project-level templates folder through DIRS. Django also searches a static folder inside each installed app, with no setting; packaged apps such as the admin bring their files that way. In a template, {% load static %} makes the tag available, and {% static 'otahque/site.css' %} writes the address.

The otahque/ folder inside static is a namespace. Two folders can each hold a file called site.css, and Django uses the first match it finds, so a bare name invites a clash. A folder named after its owner keeps the name unique, just as events/templates/events/ did for templates. Otahque keeps all its own static files in the one project folder, with a subfolder for each owner: static/otahque/ for what the whole site shares, and a folder named after an app, such as static/events/, for files only that app uses. Figure 13.1 follows the stylesheet from the file to the browser.

Under the Hood: how a stylesheet request reaches the finder

When django.contrib.staticfiles is installed, runserver wraps the application in a small handler. For each request, the handler checks whether the path starts with STATIC_URL. If it does, the request never reaches our URL patterns, views, or middleware: the handler removes the prefix, asks each finder for the remaining name, and sends the first file found, or a 404 if none matches. It does this only while DEBUG is True. The response carries the file’s modification time, so on a later visit the browser can ask whether the file has changed, and receive a short “304 Not Modified” answer instead of the whole file. The {% static %} tag takes no part in any of this. It only joins STATIC_URL and the name, and it never checks that the file exists.

That last point matters when something goes wrong. A correct-looking link proves only that the template wrote an address. Whether the file behind it exists is a separate question. The findstatic management command answers it by printing where the finder found the file. We will use both checks.

Reading a CSS rule

New Concept: a CSS rule

What problem exists? HTML says what each part of a page is: a heading, a navigation area, a list. It says nothing about how those parts should look.

What did people do before? Early HTML put presentation inside the markup, with attributes for colour and font on each element. Every page repeated them, and changing the look meant editing every page.

What is a CSS rule? Cascading Style Sheets (CSS) describe presentation separately from the HTML. A rule has a selector, which chooses elements, and a block of declarations, each a property and a value, such as color: #0759ce;.

Why CSS? One stylesheet styles every page that links to it, so the look changes in one place and the HTML keeps meaning only what it says.

Now let’s use it.

Here is a rule from the stylesheet we will write, followed by Table 13.2, which names each part:

css

.event-row {
  padding: 1rem;
  border: 1px solid #d5dde8;
}

Values use a few units. px is a fixed size on screen, and rem is a multiple of the root font size, so 1rem is normally 16 pixels and grows when a reader enlarges the text. Colours such as #0759ce give red, green, and blue amounts in hexadecimal.

A selector can combine parts. .site-nav a matches links inside the element with the site-nav class and no others. a:focus-visible matches a link while it has keyboard focus that the browser decides to show, which is how a keyboard user sees where they are.

Choose class names for what a thing is, not how it looks. event-row will still be right when the rows turn green; blue-box will not.

Boxes and normal flow

Every element is drawn as a rectangular box made of four layers, from the inside out: the content, the padding around it, the border, and the margin that keeps other boxes away. Padding is inside the border and shows the element’s background; margin is outside it and is always transparent. Figure 13.2 shows our event-row rule acting on one row.

Without any layout rules, boxes follow normal flow. Block elements such as headings, paragraphs, lists, and main stack from top to bottom and take the full available width. Inline elements such as links and span sit within a line of text. Well-structured HTML in normal flow is already readable on every screen width, which is why we start there. Arranging boxes side by side, with Flexbox or Grid, waits until a page needs it.

When rules disagree

Two rules can set the same property on the same element. The browser settles it with the cascade, which compares candidate declarations in order and stops at the first difference. For the rules in this book, three steps matter:

  • Origin and importance. Our stylesheet beats the browser’s built-in defaults. A declaration marked !important jumps ahead, which is why it is a last resort, not a fix.
  • Specificity. A more specific selector wins. Roughly, an ID outweighs any number of classes, and a class outweighs any number of element names. .site-nav a, one class and one element, beats a, one element.
  • Order of appearance. Only when everything above is equal does the later rule win.

So “the last rule wins” is true only between rules of equal specificity from the same source. A style attribute written on an element counts as more specific than any selector, another reason to keep styles in the stylesheet. Browser developer tools show the result: the Styles panel lists every matching rule and crosses out each declaration that lost.

Try it yourself

A stylesheet contains these two rules, in this order:

css

.site-nav a {
  color: #ffffff;
}

a {
  color: #1b2735;
}

Que. 1 What colour is a link inside the navigation, and what colour is a link in an event row?

Answer. The navigation link is white. .site-nav a is more specific than a, so it wins even though a comes later. The event-row link is dark, #1b2735: .site-nav a does not match it, so a is the only rule setting its colour. Order of appearance never decided either case.

In practice: styling that keeps the page usable

Situation. Sam wants the navigation links to look cleaner, and a common snippet removes the browser’s focus outline with outline: none.

Application. That snippet leaves keyboard users unable to see which link is active. We keep the outline and restyle it with :focus-visible, in a colour that contrasts with the background behind it: white on the navy bar, blue on the pale page.

Consideration. Measure rather than guess. The Web Content Accessibility Guidelines (WCAG) 2.2 ask for a contrast ratio of at least 4.5:1 for normal text, and a free contrast checker gives the ratio for any two colours. Then press Tab through the page yourself.

The colours in this chapter come from Otahque’s recorded design direction: navy navigation, blue links, white surfaces, and dark text. Chapter 14 turns them into a design system; here they are plain values in one file.

Prefer a CSS framework now?

A framework such as Tailwind gives you a ready-made set of classes and a consistent scale. It also adds a build step and its own vocabulary, and both are easier to judge once you can read the CSS they produce. We write a small stylesheet by hand first, so that Chapter 14’s framework is a choice you understand rather than a mystery. The static files setup from this chapter carries over unchanged.
