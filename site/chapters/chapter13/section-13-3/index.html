How We Build It

Start from Chapter 12, in the directory containing manage.py, with your own .env, the locked environment, and 14 passing tests. We will change events/tests.py, config/settings.py, templates/base.html, templates/includes/site_nav.html, and events/templates/events/list.html. We will add one folder and one file, static/otahque/site.css. The views, URLs, and the detail and home templates do not change. At the end, every page loads the stylesheet, and the navigation, list, and detail page look like the start of a real site.

The Custom Way

This illustration shows what Django saves us from; do not add it to the project:

illustration_only/hand_styled.html (not part of the project)

<link rel="stylesheet" href="/static/site.css">
<nav style="background: #142b46; padding: 12px;">
  <a href="/" style="color: white;">Home</a>
  <a href="/events/" style="color: white;">Events</a>
</nav>

The hand-typed path breaks as soon as STATIC_URL changes, for example when a later deployment serves files from another address. The style attributes repeat on every page, beat any rule in the stylesheet, and are the kind of inline style a Content Security Policy in a later security chapter can block. The Django Way keeps one name in the template and every style in one file.

The Django Way

Step 1: Write the tests first

Common Error: requesting the stylesheet in a test

It is tempting to request the stylesheet’s address in a test and expect a 200 response. Django runs tests with DEBUG set to False, whatever your settings say, so ordinary test requests are never served static files and that test fails even when everything works. Test the link in the page and the finder instead, and check the served file in the browser.

Open events/tests.py. Add one import line at the top, directly above from django.template import Context, Template:

events/tests.py (top of the file)

from django.contrib.staticfiles import finders

Then add this class at the end of the file:

events/tests.py (end of the file)

class StylesheetTests(SimpleTestCase):
    """Pages link the stylesheet, and Django can find it."""

    def test_pages_link_stylesheet(self):
        for url, template, title in LayoutTests.pages:
            with self.subTest(url=url):
                response = self.client.get(url)
                self.assertContains(
                    response,
                    '<link rel="stylesheet"'
                    ' href="/static/otahque/site.css">',
                    html=True,
                )

    def test_finder_locates_stylesheet(self):
        self.assertIsNotNone(
            finders.find('otahque/site.css')
        )

The first test reuses the three pages listed in LayoutTests and checks that each contains the stylesheet link, comparing it as HTML. The second asks the finder for the file by name, exactly as the development server will. finders.find returns the file’s path, or None when nothing matches.

Run the tests beside manage.py in PowerShell, a macOS shell, or Linux/WSL Bash:

Terminal

uv run python manage.py test events

Expected result, shortened with ... where lines are left out:

The 14 Chapter 12 tests still pass. The finder finds nothing, and each of the three pages lacks the link, so subTest reports three failures for one test. Both are the failures we expect.

Step 2: Add the project static folder

Common Error: a folder Django does not know about, or does not exist

Creating static/ without adding it to STATICFILES_DIRS leaves the finder unaware of it. Adding the setting before the folder exists makes check warn (staticfiles.W004) The directory ... in the STATICFILES_DIRS setting does not exist. Do both, and keep the folder beside manage.py, not inside an app.

In config/settings.py, find the static files section near the end and add one line below STATIC_URL, so that it reads:

config/settings.py (static files section)

STATIC_URL = 'static/'
STATICFILES_DIRS = [BASE_DIR / 'static']

Now create the folder and its namespace folder. In PowerShell, beside manage.py:

PowerShell

New-Item -ItemType Directory -Force static/otahque

In a macOS shell or Linux/WSL Bash, beside manage.py:

Terminal

mkdir -p static/otahque

Create static/otahque/site.css with a single comment for now. CSS comments sit between /* and */:

static/otahque/site.css

/* Otahque shared styles */

Before writing any styles, prove that Django can find the file:

Terminal

uv run python manage.py check
uv run python manage.py findstatic otahque/site.css

Expected result. The path starts with your own project folder, and macOS and Linux show forward slashes:

Output

System check identified no issues (0 silenced).
Found 'otahque/site.css' here:
  ...\static\otahque\site.css

Run the tests again. test_finder_locates_stylesheet now passes, and the three link failures remain:

Terminal

uv run python manage.py test events

Output

Found 16 test(s).
System check identified no issues (0 silenced).
...
Ran 16 tests in ...

FAILED (failures=3)

Step 3: Link the stylesheet from the layout

Common Error: the tag without its load, or a typed path

Using {% static %} in a template that has not loaded the library fails with TemplateSyntaxError: ... Invalid block tag on line 9: 'static'. Did you forget to register or load this tag? Typing /static/otahque/site.css by hand passes today’s test but breaks when STATIC_URL changes. Use the tag, and load it in each template that uses it.

Replace templates/base.html with this version. It adds {% load static %} as the first line and a link element at the end of the head:

templates/base.html

{% load static %}
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport"
        content="width=device-width, initial-scale=1">
  <title>{% block title %}Otahque{% endblock %}</title>
  <link rel="stylesheet"
        href="{% static 'otahque/site.css' %}">
</head>
<body>
  {% include "includes/site_nav.html" %}
  <main>
    {% block content %}{% endblock %}
  </main>
</body>
</html>

base.html extends nothing, so {% load %} can come first. The child pages do not use the tag, so they need no load of their own. Run the tests:

Terminal

uv run python manage.py test events

Output

Found 16 test(s).
System check identified no issues (0 silenced).
................
Ran 16 tests in ...

OK

All 16 pass. Now check what the tests cannot: that the browser receives the file. Start the development server:

Terminal

uv run python manage.py runserver

Open http://127.0.0.1:8000/events/. The page looks the same as before, because the stylesheet holds only a comment. Open the browser’s developer tools (F12, or Cmd+Option+I in Safari after enabling its Develop menu), choose the Network panel, and tick Disable cache, so that while the developer tools are open the browser always fetches the current file instead of reusing a saved copy. Reload. The list shows site.css with status 200 and type css or stylesheet. The terminal running the server logs the same request, shown here with the date and size left out:

Output

[...] "GET /events/ HTTP/1.1" 200 ...
[...] "GET /static/otahque/site.css HTTP/1.1" 200 ...

With the cache enabled, a later visit may show 304 instead of 200 for site.css, or no request at all: the browser is reusing its saved copy. That is useful for members and confusing while you edit, so keep the developer tools open with the cache disabled while you work on styles. Leave the server running for the next step.

Step 4: Add the hooks and the styles

Common Error: removing the focus outline, or naming classes by appearance

outline: none on links hides where keyboard focus is. Restyle the outline with :focus-visible instead. And a class such as blue-text stops being true when the design changes; name the thing, as in event-row.

The stylesheet needs a few stable names to aim at. Replace templates/includes/site_nav.html, which gains a site-nav class:

templates/includes/site_nav.html

<nav class="site-nav" aria-label="Site">
  <a href="{% url 'events:home' %}">Home</a>
  <a href="{% url 'events:list' %}">Events</a>
</nav>

Replace events/templates/events/list.html. The list, each row, and the empty state gain a class; nothing else changes:

events/templates/events/list.html

{% extends "base.html" %}
{% load event_labels %}

{% block title %}Sample events | Otahque{% endblock %}

{% block content %}
  <h1>Sample events</h1>
  <p>These fictional events are examples.</p>
  <ul class="event-list">
    {% for event in events %}
      {% partialdef event-row inline %}
        <li class="event-row">
          <a href="{% url 'events:detail' event.id %}">
            {{ event.title|sample_label }}
          </a>
        </li>
      {% endpartialdef %}
    {% empty %}
      <li class="event-empty">No sample events yet.</li>
    {% endfor %}
  </ul>
{% endblock %}

The sample-label class already exists: the Chapter 12 filter puts it on every label. Now replace static/otahque/site.css with the complete stylesheet:

static/otahque/site.css

/* Otahque shared styles */

body {
  margin: 0;
  font-family: system-ui, "Segoe UI", Roboto, sans-serif;
  line-height: 1.5;
  color: #1b2735;
  background: #f4f6f9;
}

main {
  max-width: 44rem;
  margin: 0 auto;
  padding: 1.5rem 1rem 3rem;
}

  color: #0759ce;
}

a:focus-visible {
  outline: 3px solid #0759ce;
  outline-offset: 2px;
}

.site-nav {
  background: #142b46;
  padding: 0.75rem 1rem;
}

.site-nav a {
  color: #ffffff;
  font-weight: 600;
  margin-right: 1.25rem;
}

.site-nav a:focus-visible {
  outline-color: #ffffff;
}

.event-list {
  list-style: none;
  padding: 0;
}

.event-row,
.event-empty {
  background: #ffffff;
  border: 1px solid #d5dde8;
  border-radius: 6px;
  padding: 1rem;
  margin-bottom: 0.75rem;
}

.event-row a {
  font-weight: 600;
}

.sample-label {
  color: #9d480c;
  font-size: 0.85em;
  font-weight: 700;
}

Read it from the top. body sets the text colour, font, line spacing, and a pale page background, and removes the browser’s default margin so the navigation reaches the edges. main limits the reading width to 44rem and centres it with margin: 0 auto; its side padding keeps text off the edges of a phone screen. Links are blue, and every link’s keyboard focus gets a solid outline. The navigation is a navy bar whose links are white, with a white focus outline that shows against the navy. The event list drops its bullets and indentation, and each row, or the empty state, becomes a white box with a border, rounded corners, padding inside, and a margin below. The sample label is a smaller, bold, dark orange word. A comma between selectors, as in .event-row, .event-empty, applies one rule to both.

Save the file and reload http://127.0.0.1:8000/events/, with the developer tools still open. The navigation is now a navy bar with white links, the content sits in a centred column, and the sample event is a white card. Open the event: its heading shows the orange Sample: label. Every colour pair here has a contrast ratio of at least 5.7:1, measured with a contrast checker, above the 4.5:1 that WCAG asks for.

Run the tests again; the classes change no text the tests depend on:

Terminal

uv run python manage.py test events

Step 5: Diagnose a competing rule, then check with the keyboard

Common Error: reaching for !important

When a rule seems ignored, adding !important usually makes it win, and hides why it lost. The next rule that needs to win then needs !important too. Find the winning rule first, then fix the selector or remove the duplicate.

To watch the cascade decide, add this experiment at the end of static/otahque/site.css, below every other rule:

static/otahque/site.css (end of the file, experiment)

/* Experiment: remove after Step 5 */
a {
  color: #1b2735;
}

Save and reload the list page. The event link turns dark, but the navigation links stay white. Right-click a navigation link, choose Inspect, and read the Styles panel. Three rules set its color. .site-nav a is listed first with #ffffff; below it, both a rules are crossed out, the new one with #1b2735 and the original with #0759ce. The newest rule lost because .site-nav a is more specific. On the event link, the new a rule crosses out the earlier a rule: equal specificity, so the later one wins.

If the change does not appear at all, the browser is probably showing its saved copy: check that Disable cache is still ticked and the developer tools are open, reload, and confirm that the request for site.css returned 200.

Now delete the experiment, the comment and the three lines below it, so that the file ends with the .sample-label rule again. Save and reload; the event link is blue once more.

Finally, check the page with the keyboard. Click the address bar, then press Tab. Focus moves to Home, with a white outline on the navy bar, then to Events, then to the sample event, with a blue outline. Narrow the browser window, or use the developer tools’ device view at a phone width: the text fits without sideways scrolling. Stop the server with Ctrl+C, then run the full suite once more:

Terminal

uv run python manage.py check
uv run python manage.py test events

When something goes wrong

Table 13.3 lists the problems this chapter can produce. Most come from one of three places: the file, its address, or the cascade. Check them in that order.

Two of these need care. findstatic exits successfully even when it finds nothing, so read its message rather than trusting that the command ran. And runserver --insecure forces static serving with DEBUG off; it exists for unusual local cases, and is never the fix for a missing .env value.

Keep your work while you diagnose a problem. Compare the one file a message names with its listing, and save a copy before replacing anything you want to keep. Fix one problem at a time and rerun the tests. Do not delete the project or reset Git as a first response.
