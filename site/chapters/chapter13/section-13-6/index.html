Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 and L2 check what you have just learned. L3 asks you to diagnose a problem in order. L4 and L5 look ahead to a larger application and to deployment: attempt them now, and return to them later. They are extension questions, not a gate to the next chapter. Run each code proof beside manage.py, in PowerShell, a macOS shell, or Linux/WSL Bash.

L1 (Junior): What is a static file, and why use the static tag?

What the interviewer is testing: Can you tell static files from templates and media, and explain why addresses are generated?

Flip to check your answerFold answer back

Perfect answer: A static file is part of the site’s code that the browser receives unchanged, such as a stylesheet, a script, or an icon. Templates are different because Django renders them with context, and media is different because users upload it. The {% static %} tag builds the file’s address from STATIC_URL, so templates name the file, not the address. If the address changes later, for example when files move to another server, no template changes.

Behind the scenes:

django/templatetags/static.py (summary)

# {% static name %} asks the static files storage for
#     the name's URL: STATIC_URL joined with the name.
#     It does not look for the file.

Code proof: build two addresses, one for a file that does not exist:

Terminal

uv run python manage.py shell -c "
from django.templatetags.static import static
print(static('otahque/site.css'))
print(static('otahque/logo.svg'))
"

Output

12 objects imported automatically (use -v 2 for details).

/static/otahque/site.css
/static/otahque/logo.svg

There is no logo.svg, yet the address is built all the same.

Common mistakes:

  • Typing /static/... into templates.
  • Treating uploaded files as static files.
  • Expecting the tag to report a missing file.

Follow-up the interviewer might ask:

  • “Where would a file a user uploads be stored instead?”
  • “What would you change to serve static files from another domain?”

L2 (Mid-Level): Trace otahque/site.css from the file to the browser.

What the interviewer is testing: Can you name each step and the check that proves it?

Flip to check your answerFold answer back

Perfect answer: The file is static/otahque/site.css, in a folder listed in STATICFILES_DIRS; findstatic proves the finder sees it. The layout’s {% static %} tag writes /static/otahque/site.css into the page, which a test checks. The browser reads the link and requests that address. Because the path starts with STATIC_URL, the development server’s static handler takes the request before any view, asks the finders for otahque/site.css, and returns the file, while DEBUG is True. The Network panel shows the 200. Each step has its own proof, and none of them proves the next.

Behind the scenes:

django/contrib/staticfiles/handlers.py (summary)

# StaticFilesHandler: if the path starts with STATIC_URL,
#     strip the prefix, find the file with the finders,
#     and serve it; otherwise pass the request on.

Code proof: the file the finder uses and the address the tag writes:

Terminal

uv run python manage.py shell -c "
from pathlib import Path
from django.conf import settings
from django.contrib.staticfiles import finders
from django.templatetags.static import static
found = Path(finders.find('otahque/site.css'))
print(found.relative_to(settings.BASE_DIR).as_posix())
print(static('otahque/site.css'))
"

Output

12 objects imported automatically (use -v 2 for details).

static/otahque/site.css
/static/otahque/site.css

Common mistakes:

  • Treating a passing link test as proof that the file is served.
  • Forgetting that the request skips URL patterns and views.
  • Assuming runserver serves files with DEBUG off.

Follow-up the interviewer might ask:

  • “What does a 304 for site.css mean?”
  • “Which step changes when the site is deployed?”

L3 (Senior): A CSS rule does not apply. How do you find out why?

What the interviewer is testing: Can you diagnose in order, from the file to the selector to the cascade, without guessing?

Flip to check your answerFold answer back

Perfect answer: I check the layers in order, because each one hides the next. First the file: does the page link it, and does the Network panel show 200, not 404? If it is 404, findstatic --verbosity 2 shows where Django looked. Second, freshness: is the browser using a cached copy, or did I edit a different file? Third, the selector: does it match this element, for example is the class spelled the same in the template? Last, the cascade: the Styles panel shows the declaration crossed out and the rule that beat it, by specificity or order. Only then do I change anything, and I fix the cause instead of adding !important.

Behind the scenes:

browser cascade (summary)

For one property on one element:
  1. collect every declaration whose selector matches
  2. compare origin and importance
  3. then specificity
  4. then order of appearance
The first difference decides; the others are crossed out.

Code proof: the first layer, a misspelled file name:

Terminal

uv run python manage.py findstatic otahque/stie.css

Output

No matching file found for 'otahque/stie.css'.

The command still exits successfully, so a script that checks only its exit code would miss the problem. Read the message, or test with finders.find as our test does.

Common mistakes:

  • Editing selectors before checking that the file loads.
  • Adding !important instead of finding the winning rule.
  • Forgetting the browser cache after an edit.

Follow-up the interviewer might ask:

  • “How would you compare the specificity of two selectors?”
  • “How could a style attribute in a template cause this?”

L4 (Staff): Where should shared and app-owned static files live?

What the interviewer is testing: Can you design static file ownership for a growing project?

Flip to check your answerFold answer back

Perfect answer: I would keep the project’s own static files in one project folder found through STATICFILES_DIRS, with a subfolder for each owner. Shared presentation, such as the site stylesheet the base layout links, goes in static/otahque/. A file that belongs to one app, such as a script only the event pages use, goes in a folder named after that app, such as static/events/. One place makes the project’s assets easy to find and review, and the app-named folders still show who owns each file. Django can also find a static folder inside each app; that suits apps packaged for reuse elsewhere, such as the admin, which carry their files with them. The finders search the configured folders first, then each app in INSTALLED_APPS order, and the first match wins, so a duplicate name silently hides the other file. Namespaces prevent that, and findstatic shows which file a name resolves to.

Behind the scenes:

django/contrib/staticfiles/finders.py (summary)

# find(path): ask each finder in STATICFILES_FINDERS
#     in turn; FileSystemFinder searches STATICFILES_DIRS,
#     AppDirectoriesFinder searches each app's static/.

Code proof: the finders in use and the folders they searched:

Terminal

uv run python manage.py shell -c "
from pathlib import Path
from django.conf import settings
from django.contrib.staticfiles import finders
for name in settings.STATICFILES_FINDERS:
    print(name.rsplit('.', 1)[1])
finders.find('otahque/site.css', find_all=True)
for place in finders.searched_locations:
    path = Path(place).relative_to(settings.BASE_DIR)
    print(path.as_posix())
"

Output

12 objects imported automatically (use -v 2 for details).

FileSystemFinder
AppDirectoriesFinder
static
.venv/Lib/site-packages/django/contrib/admin/static

The last line differs on macOS and Linux, where it starts .venv/lib/python3.14/. The admin app brings its own static folder. The events app has no static folder of its own, and keeps none: its files will go in static/events/.

Common mistakes:

  • Putting app-specific files in the shared otahque/ folder, so nobody can tell which app owns them.
  • Putting files straight into static/, with no owner folder.
  • Overriding a file by accident because two names match.

Follow-up the interviewer might ask:

  • “How would you deliberately override a third-party app’s stylesheet?”
  • “Where would Chapter 14’s compiled CSS live?”

L5 (Lead): How would you prepare static files for production?

What the interviewer is testing: Can you separate local serving from a deployment design, without treating runserver as a static server?

Flip to check your answerFold answer back

Perfect answer: Development serving is a convenience: it searches folders on every request and only runs with DEBUG on, which production never has. For deployment I would keep the templates and names exactly as they are, set STATIC_ROOT to a folder outside the source, and run collectstatic during the release to copy every found file there. I would choose a storage backend that adds a content hash to each file name, so browsers can cache files for a long time and still receive changes immediately. A web server, a static file service, or a package such as WhiteNoise then serves that folder. Then I would check the deployed pages and their static responses. Otahque does this in Chapter 63, where it can be run and verified.

Behind the scenes:

django/contrib/staticfiles/management/commands/ (summary)

# collectstatic: for every file the finders find, copy it
#     into STATIC_ROOT through the configured storage,
#     which may also rename it with a content hash.

Code proof: our project is not ready for collection, and Django says so:

Terminal

uv run python manage.py collectstatic --noinput

Output

...
django.core.exceptions.ImproperlyConfigured: You're using
the staticfiles app without having set the STATIC_ROOT
setting to a filesystem path.

The message is one line, wrapped here to fit the page. Nothing is copied, and the project is unchanged. That is the correct state for Chapter 13: no production setting without a production server to verify it.

Common mistakes:

  • Running runserver, or --insecure, as a production static server.
  • Hand-renaming files to defeat browser caches.
  • Adding production settings that nothing yet runs or checks.

Follow-up the interviewer might ask:

  • “Why do hashed file names allow long cache times?”
  • “What fails if a template names a file that collectstatic did not find?”
