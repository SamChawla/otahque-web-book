How We Build It

Starting point: the verified Chapter 6 project, with the boundary decision from Table 7.3. Work in otahque/, the folder that contains manage.py and .venv/. These steps create an events/ package beside config/ and change one line of config/settings.py. The visible result is a passing check events command and a registry lookup that prints the app’s configuration.

The Custom Way: an app by hand

Before we let Django generate anything, it helps to see how little an app needs. Read this listing; do not create these files. An app can be just a package with a configuration class:

illustration_only/ (do not type into your project)

events/
    __init__.py      (empty: marks events/ as a package)
    apps.py

illustration_only/events/apps.py

from django.apps import AppConfig


class EventsConfig(AppConfig):
    name = 'events'

Listed in INSTALLED_APPS, those two files are already a working, if empty, app. Writing them by hand for every app is error-prone, though: a misspelled class name or a missing __init__.py produces confusing errors, and each later chapter would need its own placeholder files. That is what Django’s generator saves us.

The Django Way: startapp

Step 1: Choose a name Django will accept

The app name becomes a Python package name, so it must be a valid identifier: letters, digits, and underscores, not starting with a digit. event-pages is refused because a hyphen cannot appear in a Python name. The name must also not clash with a module Python can already import. email and calendar are part of Python’s standard library, so Django refuses both. In each case, Django creates nothing.

We use events: it is a valid identifier, it does not clash with an installed module, and it names the responsibility in Table 7.2. By convention, app names are short, lowercase, and often plural. The name also becomes the app’s label, which appears in default table names such as events_event, so choose it once.

Common Error: a name that conflicts with an existing module

If you see CommandError saying the name conflicts with the name of an existing Python module, nothing was created. Choose another name. The same message appears if you run startapp events a second time, because events is then importable; inspect the existing folder instead of regenerating it.

Que. 7 Why does Django refuse calendar but accept events?

Flip to check your answerFold answer back

Answer. calendar is already importable as a module in Python’s standard library. If our app used that name, imports of calendar could find the wrong package, so Django refuses it before creating any files. events is a valid identifier that no installed module uses, so Django can create it.

Step 2: Generate the app beside manage.py

The startapp management command creates the app in the current folder. Run it through manage.py from otahque/, so the new package sits beside config/ and manage.py, where Python and Django will look for it.

PowerShell, in otahque/:

PowerShell

uv run --no-project --python .venv python manage.py `
  startapp events

macOS shell or Linux/WSL Bash, in otahque/:

Terminal

uv run --no-project --python .venv python manage.py \
  startapp events

As with startproject, success returns to the prompt without a message. Open the folder in your editor. The new files are inside events/; everything else, including config/, is unchanged from Chapter 6:

Folder structure

otahque/
    .python-version
    .venv/
    check_environment.py
    manage.py
    config/    (unchanged)
    events/
        __init__.py
        admin.py
        apps.py
        migrations/
            __init__.py
        models.py
        tests.py
        views.py

If you see events/ somewhere else, such as inside config/, or Django reports an error, do not run the command again. “When something goes wrong”, at the end of this part, shows how to diagnose and recover without losing work.

Step 3: Read the generated files

Table 7.4 lists each generated file and its job. Most contain only an import and a comment marking where code will go later. They are starting points, not working features.

Our explicit installation entry will name EventsConfig in apps.py, so that file is the one to inspect now. Open it and compare it with the Custom Way listing; it is the same class. Then add two docstrings, as Chapter 6 did for check_environment.py: one at the top for the module, and one as the first line inside the class:

events/apps.py

"""Configuration Django reads to load the events app."""
from django.apps import AppConfig


class EventsConfig(AppConfig):
    """The events app: events and their pages."""

    name = 'events'

From Chapter 4, you can read this as a class, EventsConfig, that inherits from Django’s AppConfig and sets one class attribute. name is the full dotted path of the app’s package, here simply events. Django creates one object of this class when it loads the app.

Some files you might expect are missing. There is no urls.py and no templates/ folder. startapp creates the minimum, and we add routes in Chapter 9 and templates in Chapter 11, when the first page needs them. Do not create placeholders now.

Que. 8 events/migrations/ now exists. Have we created or applied a migration?

Flip to check your answerFold answer back

Answer. No. The folder contains only an empty __init__.py, which makes it a package ready to hold migration files later. No migration file exists, and the database is untouched. Migrations stay unapplied until the custom user is chosen in Chapter 17.

Step 4: Confirm that generated is not installed

Run the system check from Chapter 6 again, in PowerShell, a macOS shell, or Linux/WSL Bash, still beside manage.py:

Terminal

uv run --no-project --python .venv python manage.py check

Expected result:

Output

System check identified no issues (0 silenced).

The check passes, but that does not mean Django is using events. Nothing in the settings mentions it yet, so Django does not load it. The check command can also check a single app by its label. Ask it about events:

Terminal

uv run --no-project --python .venv python manage.py check events

Expected result: a traceback, which Django prints when a command stops with an error. Only the first and last lines are shown here:

Output

Traceback (most recent call last):
  [...]
LookupError: No installed app with label 'events'.

The last line is the message to read: the package exists, but it is not an installed app. This failing check is useful evidence. After Step 5, the same command should pass.

In practice: generating once

Situation. Raj is unsure whether startapp worked, because it printed nothing, and considers running it again.

Application. Look in the editor first. If events/ and its files are present, generation succeeded. Running startapp events again is refused, because events is now importable, and Django leaves the existing files untouched.

Consideration. Generation is a starting action, not a repair. If a generated file seems wrong, compare it with a freshly generated copy, as shown at the end of this part, rather than regenerating over your work.

Step 5: Install the app

Open config/settings.py and find the INSTALLED_APPS list. Add one line after django.contrib.staticfiles, keeping the comma at the end of the line. The list should now read:

config/settings.py (excerpt)

INSTALLED_APPS = [
    'django.contrib.admin',
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    'django.contrib.messages',
    'django.contrib.staticfiles',
    'events.apps.EventsConfig',
]

Save the file and change nothing else in it. The new entry is a dotted path to the class in apps.py: events.apps is the module, and EventsConfig is the class inside it. Naming the class tells Django exactly which configuration to use. You will also see the shorter entry 'events' in guides. It works here too, because apps.py defines exactly one AppConfig class, but list the app once, in one form only. Django processes the list in order; we put our app after Django’s own so the framework’s apps are set up first.

Que. 9 What do the two halves of events.apps.EventsConfig refer to?

Flip to check your answerFold answer back

Answer. events.apps is the dotted path to the module apps.py inside the events package. EventsConfig is the class defined in that module. Together they tell Django to import events.apps and use EventsConfig as the app’s configuration.

Step 6: Confirm with the system check and the registry

Run both checks again, in PowerShell, a macOS shell, or Linux/WSL Bash, beside manage.py:

Terminal

uv run --no-project --python .venv python manage.py check
uv run --no-project --python .venv python manage.py check events

Expected result, once for each command:

Output

System check identified no issues (0 silenced).
System check identified no issues (0 silenced).

The second line is the change that matters: before installation, check events stopped with LookupError; now Django finds an installed app with the label events and checks it. A development server left running from Chapter 6 needs a restart, or at least a reload, before it uses the new list.

The registry described under the hood was built for our project as Figure 7.3 shows. All three phases still run for our app. Django imports the generated models.py, which defines no model classes yet, and calls the inherited ready() method, which does nothing because we have supplied no start-up code.

Django’s shell command starts Python with the project’s settings loaded, so we can ask the registry directly. The -c option runs the quoted lines and exits. The quoted text spans three lines; type it exactly, including the final double quote. In PowerShell, a macOS shell, or Linux/WSL Bash:

Terminal

uv run --no-project --python .venv python manage.py shell -c "
from django.apps import apps
config = apps.get_app_config('events')
print(config.name, config.label, config.verbose_name)"

Expected result:

Output

12 objects imported automatically (use -v 2 for details).

events events Events

The first line comes from the shell itself: it imports some commonly used names for convenience and reports how many. The last line is our print. get_app_config looks an app up by its label and returns the configuration object Django created. Table 7.5 explains the three values.

None of this used the database. Checking and looking up apps does not create tables or apply migrations, so the unapplied-migration state from Chapter 6 is unchanged.

Que. 10 If get_app_config('events') succeeds, what has been confirmed, and what has not?

Flip to check your answerFold answer back

Answer. Django imported the entry from INSTALLED_APPS, created EventsConfig, and recorded the app under the label events. That confirms installation. It does not show that the app does anything useful: it has no models, routes, views, or templates yet.

Do not change apps.py for this exercise. Suppose EventsConfig gained the line verbose_name = 'Community events'. Predict what the registry lookup would print, and say whether the label, and so the default table names, would change.

When something goes wrong

Raj follows the same steps on his computer, but his check ends with a long traceback. Regenerating the app or the project would throw away the clue. Most app problems come from one of a few places: the folder where a command ran, the name chosen, or the INSTALLED_APPS entry. A traceback lists the calls that led to an error, and its final line names the error itself; for app problems, that last line is usually enough. Table 7.6 pairs the messages we reproduced under Django 6.1.2 with their causes and a recovery.

Each correction changes one line or moves one generated folder. None of them needs a new project, a reinstall, or a database change. After any correction, rerun check and check events and expect both to report no issues.

Common Error: the missing comma

Python joins string literals that stand next to each other with nothing between them. Without the comma, 'django.contrib.staticfiles' and 'events.apps.EventsConfig' become one string, and Django tries to import a module, django.contrib.staticfilesevents, that was never written anywhere in the file. When an error names a module you never typed, look for a missing comma on the line above.

Move a misplaced app without losing work

If startapp ran from the wrong folder, events/ ends up in the wrong place. Running the command from inside config/, for example, creates config/events/, and Django cannot import it as events. First confirm that there is no events/ folder beside manage.py and that the misplaced folder holds only the generated files from Table 7.4. Then move it from otahque/. PowerShell:

PowerShell

Move-Item config/events events

macOS shell or Linux/WSL Bash:

Terminal

mv config/events events

Both commands move the folder; they do not copy or delete its contents. If an events/ folder already exists beside manage.py, stop: compare the two folders instead of moving one over the other. Then rerun the two checks.

Compare with a fresh app when needed

If you suspect an accidental edit to a generated file, generate a fresh events app in a new, empty sibling folder and compare the file. You need this only when something has gone wrong. As in Chapter 6’s comparison-copy recovery, the commands work outside your project, so they do not touch it. If otahque-compare-app already exists, stop and choose a new unused sibling name in both commands. If you named your work folder otahque-learning, use that name in place of otahque. PowerShell, starting in otahque/:

PowerShell

cd ..
mkdir otahque-compare-app
cd otahque-compare-app
uv run --no-project --python ../otahque/.venv `
  python -m django startapp events
cd ../otahque

macOS shell or Linux/WSL Bash, starting in otahque/:

Terminal

cd ..
mkdir otahque-compare-app
cd otahque-compare-app
uv run --no-project --python ../otahque/.venv \
  python -m django startapp events
cd ../otahque

The last command returns you to otahque/. Every generated app file is identical for the same Django version and name, so any difference is a change in your copy. Correct only the unintended change in your own file. Do not install the comparison copy or copy it over your project. Delete otahque-compare-app/ when you have finished.

In practice: reporting an app problem

Situation. Raj asks for help with his failing check.

Application. Send the command, the last line of the error, and the INSTALLED_APPS list. For the problems in Table 7.6, those three items usually identify the cause without any further detail.

Consideration. Remove anything private before sharing, such as your secret key or personal folder names. The last line names the error, but not always its cause: a ModuleNotFoundError can come from a misplaced folder or a missing comma.

Try it yourself

Diagnose two reports on paper. In the first, check passes but check events ends with LookupError: No installed app with label 'events'. In the second, check ends with ImportError: Module 'events.apps' does not contain a 'EventConfig' class. Choices are: 'EventsConfig'. For each, name the cause and the smallest correction.

Flip to check your answerFold answer back
