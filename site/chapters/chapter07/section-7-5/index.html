Checkpoint: Quiz and Challenge

Quiz

Que. 13 What is the difference between an importable package and an installed app?

Flip to check your answerFold answer back

Answer. Any package Python can find can be imported. Only a package listed in INSTALLED_APPS is an installed app, so only then does Django register it and look inside it for models, templates, and other app files.

Que. 14 Which three questions draw an app boundary?

Flip to check your answerFold answer back

Answer. Responsibility: what the app answers for. Data ownership: which records it defines and keeps correct. Dependency direction: which apps it refers to, and which should not need to refer back to it, so that no circular dependency forms.

Que. 15 Why did we create events now but leave accounts and registrations for later?

Flip to check your answerFold answer back

Answer. The next chapters need events only. Creating the others now would add unused names and settings and freeze early guesses, while the boundary decision in Table 7.3 already records where they will go.

Que. 16 Why does check pass before the app is installed, while check events fails?

Flip to check your answerFold answer back

Answer. The plain check examines the project’s current configuration, which has no problems; it does not know that an events package exists. check events asks for an installed app with that label, and until the entry is listed there is none, so Django raises LookupError.

Que. 17 In what order does Django load installed apps?

Flip to check your answerFold answer back

Answer. In the order of INSTALLED_APPS, in three phases: it imports each entry and creates its configuration, then imports each app’s models module, then runs each configuration’s ready() method.

Mini-Challenge

Otahque will later record where events take place: a venue with a name, an address, and accessibility notes. Using the three boundary questions and Table 7.2, decide on paper whether venues belong in the events app or in a new app, and write a one-row decision record in the shape of Table 7.3. Do not create anything in your project.

Que. 18 What would a reasonable decision say?

Flip to check your answerFold answer back

Answer. Either answer can be defended if the reasons are stated. If a venue matters only as a detail of an event, events can own it. If venues are shared between many events, managed by organizers, and checked for accessibility on their own, a venues app owning venue records, with events referring to venues, gives a clearer boundary. A good record states the responsibility, the records owned, the dependency direction, and when to revisit, for example when venues gain their own pages.

What We Learned

  • A Django app is a package that supplies one capability; an installed app is one listed in INSTALLED_APPS, and the project is the configuration that assembles them.
  • The generated project already uses six apps from django.contrib, and an app can supply a capability without owning database tables.
  • Boundaries come from the product: responsibility, data ownership, and dependency direction, decided before the first model because default table names follow the app label.
  • We created only events now, recorded why in Table 7.3, and left accounts for Chapter 17 and registrations for Chapter 20.
  • startapp generates the minimum package; installing it is one line in INSTALLED_APPS, and the check command and the registry prove that Django loaded it.
  • Most app problems are diagnosed from the last line of the traceback and fixed by changing one line or moving one folder, never by regenerating.
