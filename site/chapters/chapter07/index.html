CHAPTER SEVEN

Django apps and application boundaries

Chapter 6 gave us a project that answers a browser but contains no Otahque behaviour yet. Before Sam’s first event page exists, we need to decide where its code will live. Django organizes a project’s features into apps. In this chapter, we find the apps our project already uses, propose Otahque’s first boundary, create an events app, install it, and confirm that Django loads it.

By the end of the chapter, you will be able to:

  • explain what a Django app is and how it differs from a project and from an ordinary Python package;
  • identify the apps a project installs and what each one supplies;
  • propose app boundaries from Otahque’s requirements and explain the trade-offs;
  • generate an app and explain the job of each generated file;
  • install an app and confirm that Django has loaded it;
  • diagnose common app-creation and installation problems without overwriting your work.

You will produce an installed, empty events app and a short record of why its boundary was chosen. Start from the verified Chapter 6 project: the otahque/ work folder with its .venv/, manage.py, and config/ package, and a passing system check. Migrations stay unapplied throughout this chapter. Routes and views begin in Chapters 9–10 and the first model in Chapter 16; dependency locking and Git follow in Chapter 8. This draft currently contains Section 7.1 of the five planned sections.
