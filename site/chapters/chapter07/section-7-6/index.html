Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 and L2 check what you have just learned. L3 asks how it works underneath. L4 and L5 ask about the design and leadership decisions that later chapters build on: attempt them now, and return to them when you reach those chapters. Use the readiness checkpoint to decide whether to continue. If an answer is difficult, revisit its worked example and explain the result in your own words. L4 and L5 are extension questions, not a gate to the next chapter.

L1 (Junior): What does INSTALLED_APPS do?

What the interviewer is testing: Do you know what installing an app means, as opposed to importing it?

Flip to check your answerFold answer back

Perfect answer: It lists the apps the project registers, in order. At startup Django imports each entry and builds its app registry, and installed apps can then supply models and migrations, templates, static files, management commands, and checks. A package that is not listed can still be imported as ordinary Python, but Django does not treat it as an installed app. An entry can name a package, such as 'events', or an AppConfig class, such as 'events.apps.EventsConfig'.

Behind the scenes:

django/apps/registry.py (summary, not the source)

# django.setup() calls apps.populate(settings.INSTALLED_APPS)
# for each entry:  AppConfig.create(entry) -> one config object
# apps.is_installed(name) then checks the registered configs
# by dotted name; nothing else in the work folder is consulted.

Code proof: in PowerShell, a macOS shell, or Linux/WSL Bash, beside manage.py:

Terminal

uv run --no-project --python .venv python manage.py shell -c "
from django.apps import apps
print(apps.is_installed('events'))
print(apps.is_installed('config'))"

Output

12 objects imported automatically (use -v 2 for details).

True
False

Common mistakes:

  • Thinking that listing an app is what makes it importable.
  • Forgetting a comma, so that two entries join into one name.
  • Listing the project package itself as an app.

Follow-up the interviewer might ask:

  • “Why does the order of INSTALLED_APPS matter?”
  • “What is the difference between 'events' and 'events.apps.EventsConfig'?”

L2 (Mid-Level): Walk through creating and installing an app, and how you confirm that Django loaded it.

What the interviewer is testing: Can you carry out the steps and verify each one, rather than assume it worked?

Flip to check your answerFold answer back

Perfect answer: From the folder that contains manage.py, manage.py startapp events generates the package, including apps.py with EventsConfig, models.py, and an empty migrations package. Before it is installed, check passes but check events fails with LookupError, because Django does not know the label. After adding 'events.apps.EventsConfig' to INSTALLED_APPS, both checks pass, and the registry returns the app’s name, label, and verbose name. Each step has evidence, so nobody has to assume the app is in use.

Behind the scenes:

django/core/management/commands/startapp.py (summary)

# startapp is a TemplateCommand: it validates the name, refuses
# names that are already importable, then copies the files in
# django/conf/app_template/, rendering each *.py-tpl as *.py.

Code proof: list the template Django copies, in PowerShell, a macOS shell, or Linux/WSL Bash:

Terminal

uv run --no-project --python .venv python -c "
import django, pathlib
base = pathlib.Path(django.__file__).parent
for item in sorted((base / 'conf/app_template').iterdir()):
    print(item.name)"

Output

__init__.py-tpl
admin.py-tpl
apps.py-tpl
migrations
models.py-tpl
tests.py-tpl
views.py-tpl

Common mistakes:

  • Running startapp inside config/, so the app cannot be imported as events.
  • Choosing a name that clashes with a Python module, such as calendar.
  • Generating the app and forgetting to install it.

Follow-up the interviewer might ask:

  • “What does startapp refuse to do?”
  • “Why does check pass before the app is installed?”

L3 (Senior): What happens when Django loads the installed apps at startup?

What the interviewer is testing: Do you understand the phases of the app registry and what each phase allows?

Flip to check your answerFold answer back

Perfect answer: Django works through INSTALLED_APPS in three phases. First it imports each entry and creates its AppConfig; labels must be unique, so a repeated label stops loading with ImproperlyConfigured. Second, it imports each app’s models module, if there is one. Third, it calls each configuration’s ready() method and marks the registry ready. Model lookup becomes available after phase 2, and ready() may import model classes. Keep model imports out of apps.py at module level, and avoid database queries during initialization. The registry keeps the order of INSTALLED_APPS, which later decides, for example, whose template wins when two apps provide one with the same name.

Behind the scenes:

django/apps/registry.py (summary of populate)

# Phase 1: for entry in installed_apps:
#              app_config = AppConfig.create(entry)
#          duplicate labels -> ImproperlyConfigured
# Phase 2: for app_config in configs: app_config.import_models()
# Phase 3: for app_config in configs: app_config.ready()
#          self.ready = True

Code proof: ask whether the registry has finished loading:

Terminal

uv run --no-project --python .venv python manage.py shell -c "
from django.apps import apps
print(apps.ready)"

Output

12 objects imported automatically (use -v 2 for details).

True

Common mistakes:

  • Importing models at the top of apps.py.
  • Querying the database in ready().
  • Assuming ready() can never run twice; Django’s documentation notes that it can, for example in tests.

Follow-up the interviewer might ask:

  • “Where would you connect code that must run at startup?”
  • “Why does a misspelled class name fail in the first phase?”

L4 (Staff): How do you decide app boundaries, and what goes wrong when they are drawn badly?

What the interviewer is testing: Can you draw boundaries by responsibility and data ownership, and spot the cost of bad ones?

Flip to check your answerFold answer back

Perfect answer: Give each app one responsibility and the records that go with it: events for what is offered, accounts for who people are, and registrations for who holds a place. In the proposed record-reference diagram, registrations refers to events and accounts. Avoid circular imports when implementing operations that cross those boundaries. The arrows show which records refer to which; some operations still need information across a boundary, such as the registration count when capacity is reduced, and that should be obtained deliberately rather than by reversing the dependency. Bad boundaries show up as circular imports, changes that always touch several apps, catch-all apps such as utils, or one large app on which everything depends. Decide before the first model, because the app label becomes part of each default table name.

Behind the scenes:

django/db/models/options.py (summary)

# A model's default table name is built from its app label:
#     db_table = "%s_%s" % (app_label, model_name)
# so Event in the events app is stored as events_event, and
# its migrations live in events/migrations/.

Code proof: Django’s own Group model shows the pattern:

Terminal

uv run --no-project --python .venv python manage.py shell -c "
from django.contrib.auth.models import Group
print(Group._meta.app_label, Group._meta.db_table)"

Output

12 objects imported automatically (use -v 2 for details).

auth auth_group

Common mistakes:

  • One app per model or per page.
  • Naming apps after technology, such as forms, instead of responsibility.
  • Splitting before the responsibility is clear.

Follow-up the interviewer might ask:

  • “Where should the logic for cancelling a registration live?”
  • “What does it cost to move a model to another app later?”

L5 (Lead): The team wants to split Otahque into many small apps now, “to be ready for scale”. How do you respond?

What the interviewer is testing: Can you weigh the cost of structure against its benefit, and set conditions for change?

Flip to check your answerFold answer back

Perfect answer: Start with the problem, not the structure: ask which problem the split would solve. Boundaries are easiest to change before stored data exists, but splitting early adds references between apps, dependencies between migrations, and coordination, without a present benefit. Agree the proposed boundaries as a decision (Table 7.3: events now, accounts in Chapter 17, registrations in Chapter 20), create each app when a chapter needs it, and record the signs that justify a split: an app with unrelated responsibilities, changes that keep crossing one boundary, or a capability worth reusing. One boundary must be decided early: the user model is best chosen before the first migration, because Django cannot switch it automatically afterwards, which is why accounts is planned before any migration is applied. Explaining that reasoning to the team matters as much as the decision, so that the next proposal is argued from the same criteria.

Behind the scenes:

why the user model is decided first (summary)

# AUTH_USER_MODEL must be chosen before the first migrate:
# auth's migrations, and every app that refers to users,
# record the user model they depend on. Changing it after
# tables exist is a difficult manual migration.

Code proof: the shipped auth migrations are still unapplied in our project. PowerShell:

PowerShell

uv run --no-project --python .venv python manage.py `
  showmigrations auth

macOS shell or Linux/WSL Bash:

Terminal

  showmigrations auth

[...]

Common mistakes:

  • Splitting by team structure or by fashion.
  • Ignoring the migration work that moving models requires later.
  • Making the change without recording why.

Follow-up the interviewer might ask:

  • “Which boundary is hardest to change later, and why?”
  • “How would you review a proposal for a new app?”
