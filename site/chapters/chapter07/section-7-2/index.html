What You Need to Know

An app supplies a capability

New Concept: Django app

What problem exists? A website does many unrelated things: it signs people in, remembers them between requests, shows events, and records registrations. Kept in one place, that code becomes a pile in which every change risks something unrelated.

What did people do before? Projects often grouped code by technical layer: all the pages in one folder and all the database code in another. That spread one feature across several folders.

What is a Django app? A Python package that supplies one related set of website features, a capability. It can bring any of the pieces we traced in Chapter 5 for that capability, such as views, models, and templates, together with related files such as static files, administration settings, and tests. It does not need all of them.

Why apps? Django finds an installed app’s models, templates, and other files automatically, so each capability can be read, tested, and reused as a unit. Django’s own features, from accounts to sessions, are shipped as apps in exactly this way.

Now let’s look at the ones we already have.

The project is the assembly. Its settings say which apps take part, and its root URL configuration connects the addresses this project exposes to views or to other URL configurations. Django learns which apps are installed from one setting, INSTALLED_APPS. A package that is not listed there is still ordinary Python code that can be imported. Django simply does not register it as an installed app, so it does not look inside it for the files it finds automatically.

The apps your project already has

It is tempting to think that our project has no apps because we have not created one. In fact, the project generated in Chapter 6 already uses six. Open config/settings.py in your editor and find the assignment that begins with INSTALLED_APPS. This step only reads the file; change nothing. In a freshly generated Django 6.1.2 project, it looks like this:

config/settings.py (excerpt, unchanged)

INSTALLED_APPS = [
    'django.contrib.admin',
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    'django.contrib.messages',
    'django.contrib.staticfiles',
]

From Chapter 4, you can read this as a Python list of strings. Each string is a dotted path, the same form we use after import. django.contrib is a package inside Django that holds optional apps shipped with the framework, and the generated project switches these six on by default. Table 7.1 shows what each supplies and where the book develops it.

If your list differs, do not edit it now. A difference means the file is not the one generated in Chapter 6, or it has since changed. Compare it with a fresh copy, as described in Chapter 6, How We Build It, “Compare with a fresh copy when needed”, before continuing.

Que. 1 Chapter 6, How We Build It, shortened the runserver output in the server-starting step. The full migration warning names the apps with unapplied migrations: admin, auth, contenttypes, and sessions. Why are messages and staticfiles not named?

Flip to check your answerFold answer back

Answer. In this generated project, admin, auth, contenttypes, and sessions include database models and shipped migrations that have not yet been applied. messages and staticfiles have no tables or migrations of their own. An app can supply a capability without owning database tables.

A project, an app, and a package are different things

Three words can describe the same folder, so it helps to separate them. A Python package is a directory of importable modules; config/ became one through its __init__.py file. A Django app is a Python package that supplies related website features. An installed app is one that this project registers through INSTALLED_APPS. A Django project is the configuration that brings apps together, chiefly its settings. Figure 7.1 shows the relationship.

Being importable is not the same as being installed. Python can import a package from the work folder whether or not it is listed. Only a listed package becomes an installed app, so Django includes it when it looks for models, templates, and other app files. The config/ package holds the project’s configuration and is not in the list.

Que. 2 config/ is a Python package in the project folder. Is it a Django app?

Flip to check your answerFold answer back

Answer. No. It is importable because it contains __init__.py, but it does not appear in INSTALLED_APPS. Its job is project configuration: settings, the root URL configuration, and the server interfaces. Django does not treat it as an app or look in it for models.

How Django loads installed apps

Each time a management command or the development server starts, Django reads the settings and loads the listed apps in order. Because loading happens at startup, a change to INSTALLED_APPS affects the next command or server start. During development, runserver usually reloads when a Python file changes; if you are unsure whether a running server has seen a change, stop it and start it again.

Under the Hood: How Django builds the app registry

At startup, django.setup() calls the registry’s populate() method in django/apps/registry.py with your INSTALLED_APPS. It works in three phases. Phase 1 imports each entry and creates its configuration object with AppConfig.create(); every app’s label must be unique, so a repeated label stops loading with ImproperlyConfigured. Phase 2 imports each app’s models module, if it has one. Phase 3 calls each configuration’s ready() method, then marks the registry ready. Model lookup becomes available after phase 2, and ready() may import model classes. Keep model imports out of apps.py at module level, and avoid database queries during initialization.

Later in this chapter, Figure 7.3 draws these phases once our own app takes part. For now, remember the order: import and configure, then models, then start-up code.

In practice: reading an unfamiliar project

Situation. A new contributor joins Otahque later and needs to understand what the project depends on before changing it.

Application. INSTALLED_APPS is a fast first map. It shows which capabilities Django will load, which came with Django, and which belong to the project. The same habit helps when a guide suggests adding a package: check whether it is an app that needs listing, and what capability it adds.

Consideration. The list shows what is loaded, not how each app is used or whether it is configured well. Treat it as a starting point for reading the code, not as a review.

Answer. The one-time notice comes from messages. Staying signed in combines auth, which knows the account, with sessions, which remembers the browser between requests. Listing the apps does not finish the job on its own: INSTALLED_APPS registers each app, but its feature may also need middleware, template settings, or other wiring. Drawing Otahque’s first app boundaries

A boundary is the line between what one app looks after and what belongs to another. Three questions help us draw it:

  • Responsibility: which part of the product does this app answer for? Name it in one short phrase, such as “what is offered”.
  • Data ownership: which stored records does it define and keep correct? From Chapter 16, an app’s models describe those records.
  • Dependency direction: which other apps does it need to refer to, and which should never need to refer back to it?

These questions come from the product, not from the pages. A page often shows information owned by several apps. Sai’s registration page shows an event and her place in it, but that does not make the page an app. An app is not a single page, a URL prefix, or a layer such as “all the views”.

Chapter 2’s requirements give us the material. PR-1 to PR-3 concern places: one confirmed place per eligible registration, cancellation that releases a place, and capacity that holds when two people compete. PR-4 concerns who may see and change what. Underneath them sit three kinds of record: events, the people who use Otahque, and the registrations that connect people to events. Table 7.2 turns those records into candidate apps. Read it as a proposal for review, not as an accepted design.

The arrows show dependency direction. A registration refers to one event and one member, so registrations depends on both. An event refers to its organizer, so events depends on accounts. These proposed record references do not require a reverse reference from an event or account to a registration. The arrows record which records refer to which; some operations still need information across a boundary. Reducing an event’s capacity, for example, needs the current registration count, which should be obtained deliberately rather than by reversing the arrow.

All three apps live in one project and run as one application. Chapter 5’s proposed ADR-001 chose a single server-rendered Django application. Apps divide the code inside it; they are not separate services.

Que. 4 Why is registrations proposed as its own app rather than part of events?

Flip to check your answerFold answer back

Answer. They answer for different things and own different records. Events describe what is offered. A registration connects a member to an event and carries the rules in PR-1 to PR-3. Keeping them apart lets the events app make sense on its own, while registrations depends on events and accounts. Both are still part of the same project and the same running application.

Too few apps, or too many

Both extremes are common. One large app holding everything works for a tiny project but turns into a pile of unrelated code: event rules, sign-in, and capacity checks side by side. The opposite mistake creates an app for each page or small feature, such as event_list, event_detail, and cancel_button. Those apps share the same records, so every change crosses several of them.

Where a model lives matters later. Django uses the app label in each model’s default database table name. By default, a model named Event in the events app is stored in a table called events_event, and the app’s migration history records it there. Moving a model to another app after migrations exist requires a plan for migration state, table names, and stored data as well as the code; do not rewrite already-applied migrations. So we choose boundaries before writing the first model, and we keep the first choice small.

Que. 5 Someone suggests one app per page: event_list, event_detail, and registration_form. What is the main problem?

Flip to check your answerFold answer back

Answer. Those pages all work with the same event and registration records, so the responsibility is split by screen rather than by what the code answers for. Every rule change would touch several apps, and it would be unclear which app owns the records and keeps them correct. A page belongs inside the app that owns its main responsibility, or is decided separately, as the home page will be in Chapter 9.

Prefer creating all three apps now?

Empty apps cost little to generate, so creating accounts and registrations today is tempting. We do not, because they would add names and settings that nothing uses yet, and an early guess may change once we reach those chapters. We create events now, because the next chapters build event pages and the first model. accounts follows in Chapter 17, which chooses the user model before the first migration is applied, and registrations in Chapter 20, with its first model. Where the home page lives is decided in Chapter 9.

Table 7.3 records the decision in the same shape as Chapter 5’s architecture record. It is the “short record of why” promised at the start of the chapter.

In practice: placing a later feature

Application. Ask the three questions before writing code. A waitlist place connects a member to an event and depends on capacity, which suggests registrations as its owner rather than a new app.

Consideration. The answer is a proposal for that chapter to confirm. A boundary table records today’s reasoning; it does not settle future decisions automatically.

Que. 6 Which app should own each need?

Flip to check your answerFold answer back

Answer. Sam’s attendee list reads registrations for one event, so registrations owns it; the page may appear in organizer screens, but the records belong to registrations.
