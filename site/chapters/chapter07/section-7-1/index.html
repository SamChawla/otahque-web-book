7.1 Find the apps your project already uses

It is tempting to think that our project has no apps yet because we have not created one. In fact, the project generated in Chapter 6 already uses six. Looking at them first shows what an app is in practice before we write our own.

Starting point: the verified Chapter 6 project, with no Otahque app. Work in the otahque/ folder and open config/settings.py in your editor. This section reads that file and changes nothing. No command or server is needed. The result is an annotated list of the apps the project installs and what each one supplies.

An app supplies a capability to the project

Table 6.5 described a Django app as a Python package supplying a capability used by a project. A capability is something the website can do, such as remembering a browser between requests or offering an administration site. In Chapter 5, we traced a request through a URL configuration, a view, a model, and a template. An app can bring any of those pieces for its capability, together with related files such as static files, administration settings, and tests. It does not need all of them.

The project is the assembly. Its settings say which apps take part, and its root URL configuration connects addresses to them. Django learns which apps belong to the project from one setting: INSTALLED_APPS. An app that is not listed there is still ordinary Python code, but Django does not load it as part of the project.

Read the list Django already has

In config/settings.py, find the assignment that begins with INSTALLED_APPS. In a freshly generated Django 6.1.2 project, it looks like this:

INSTALLED_APPS = [
    'django.contrib.admin',
    'django.contrib.auth',
    'django.contrib.contenttypes',
    'django.contrib.sessions',
    'django.contrib.messages',
    'django.contrib.staticfiles',
]

From Chapter 4, you can read this as a Python list of strings. Each string is a dotted path, the same form we use after import. django.contrib is a package inside Django that holds optional apps shipped with the framework. The generated project switches these six on by default. Table 7.1 shows what each supplies and where Otahque first relies on it.

If your list differs, do not edit it now. A difference means the file is not the one generated in Chapter 6, or it has since been changed. Compare it with a fresh copy, as described in Section 6.5, before continuing.

Que. 1 Section 6.4 shortened the runserver output. The full migration warning names the apps with unapplied migrations: admin, auth, contenttypes, and sessions. Why are messages and staticfiles not named?

Show answerHide answer

Answer. An app needs migrations only when it defines stored records with database tables. admin, auth, contenttypes, and sessions do, so their tables are waiting to be created. messages and staticfiles keep no tables of their own. An app can supply a useful capability without any database records.

A project, an app, and a package are different things

Three words can describe the same folder, so it helps to separate them. A Python package is a directory of importable modules; config/ became one through its __init__.py file. A Django app is a package that the project lists in INSTALLED_APPS. A Django project is the configuration that brings those apps together, chiefly its settings. Figure 7.1 shows the relationship.

Being importable is not enough. Python can import a package from the work folder whether or not it is listed. Only a listed package becomes an installed app, so Django looks inside it for models, templates, and other app files. The config/ package is not in the list. It holds the project’s configuration; it is not an app.

Que. 2 config/ is a Python package in the project folder. Is it a Django app?

Show answerHide answer

Answer. No. It is importable because it contains __init__.py, but it does not appear in INSTALLED_APPS. Its job is project configuration: settings, the root URL configuration, and the server interfaces. Django does not treat it as an app or look in it for models.

Django loads installed apps when it starts

Each time a management command or the development server starts, Django reads the settings and imports the listed apps in order. It records each one in its app registry: an internal list of the apps it has loaded and their configuration. Later parts of Django use that registry to find an app’s models or files. Section 7.4 looks at the loading steps more closely and asks the registry to confirm that our own app is present.

Because loading happens at startup, a change to INSTALLED_APPS affects the next command or server start. During development, runserver usually reloads when a Python file changes. If you are unsure whether a running server has seen a change, stop it and start it again.

In practice: reading an unfamiliar project

Situation. A new contributor joins Otahque later and needs to understand what the project depends on before changing it.

Application. INSTALLED_APPS is a fast first map. It shows which capabilities Django will load, which came with Django, and which belong to the project. The same reading habit helps when a guide suggests adding a package: check whether it is an app that needs listing, and what capability it adds.

Consideration. The list shows what is loaded, not how each app is used or whether it is configured well. Treat it as a starting point for reading the code, not as a review.

Try it yourself

Using Table 7.1, decide which installed app is most directly involved in each future need. Sai registers for the workshop and sees a one-time notice saying her place is confirmed. Soni signs in and stays signed in as she moves between pages. Sam’s event page loads its stylesheet during development. Then say whether any of the three needs could be met by an app that is importable but missing from INSTALLED_APPS.

Que. 3 Which app supports each need, and why does the list matter?

Show answerHide answer

Answer. The one-time notice comes from messages. Staying signed in combines auth, which knows the account, with sessions, which remembers the browser between requests. The stylesheet during development comes from staticfiles. None of these would work from an unlisted package, because Django loads only listed apps. Each capability supports a need; it does not by itself enforce Otahque’s rules, such as who may register.

Before continuing, you should be able to point to the INSTALLED_APPS list, name its six entries, and explain why config/ is not among them. No file has changed, so the Chapter 6 system check still describes your project.
