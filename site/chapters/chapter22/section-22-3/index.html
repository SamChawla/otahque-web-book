Step 6 then changes the list page on purpose, in events/views.py, events/templates/events/list.html, and the stylesheet, Step 7 adds RegistrationQuerySet to registrations/models.py, and Step 8 shows the places left on both pages, with a new template, events/templates/events/places.html. The Custom Way

Without a query layer, composition is done in Python. This illustration filters a list of dictionaries with two functions; run it with any Python, and do not add it to the project:

illustration_only/by_hand.py (not part of the project)

events = [
    {'title': 'Python meetup', 'status': 'published',
     'location': 'Leeds Central Library, Room 2'},
    {'title': 'Django workshop', 'status': 'published',
     'location': 'Virtual'},
    {'title': 'Spring planning', 'status': 'draft',
     'location': 'Leeds Central Library'},
]


def published(rows):
    return [row for row in rows
            if row['status'] == 'published']


def in_person(rows):
    return [row for row in rows
            if row['location'] != 'Virtual']


chosen = in_person(published(events))
print([row['title'] for row in chosen])

Output

['Python meetup']

It works, and the two rules have names. Now list what it costs. Every row is already in Python’s memory: with a database, published() would first fetch every event ever stored, then throw most of them away. Each function runs at once and builds a new list, so the work is repeated for every rule. The calls nest inside out, in_person(published(events)), so a third rule makes the line harder to read. And nothing connects the rules to the Event model. A custom QuerySet keeps the names but sends all the conditions to the database in one statement. Functions that return finished lists are also the shape of a repository layer, which the L5 interview question weighs.

class EventQuerySetTests(TestCase):
    """The named questions EventQuerySet answers."""

    @classmethod
    def setUpTestData(cls):
        save_event(
            title='Django workshop',
            starts_at=datetime(2026, 12, 3, 9,
                               tzinfo=UTC),
            location='Virtual',
        )
        save_event(title='Python meetup')
        save_event(title='Spring planning',
                   status=Event.Status.DRAFT)
        save_event(title='Autumn social',
                   status=Event.Status.CANCELLED)

    def test_published_keeps_only_published(self):
        self.assertQuerySetEqual(
            Event.objects.published(),
            ['Python meetup', 'Django workshop'],
            transform=str,
        )

    def test_published_chains_with_other_methods(self):
        virtual = Event.objects.filter(location='Virtual')
        self.assertQuerySetEqual(
            virtual.published(), ['Django workshop'],
            transform=str,
        )
        self.assertQuerySetEqual(
            Event.objects.published().exclude(
                location='Virtual'
            ),
            ['Python meetup'],
            transform=str,
        )

    def test_upcoming_and_past_split_at_now(self):
        published = Event.objects.published()
        during = datetime(2026, 11, 19, 19, tzinfo=UTC)
        self.assertQuerySetEqual(
            published.upcoming(during),
            ['Python meetup', 'Django workshop'],
            transform=str,
        )
        later = datetime(2026, 11, 25, tzinfo=UTC)
        self.assertQuerySetEqual(
            published.upcoming(later), ['Django workshop'],
            transform=str,
        )
        self.assertQuerySetEqual(
            published.past(later), ['Python meetup'],
            transform=str,
        )

assertQuerySetEqual() runs the query and compares the rows, in order, with the list; transform=str turns each event into its title first. The first test also checks the order: the Python meetup, on 19 November, comes before the Django workshop, on 3 December, because published() keeps the model’s ordering. The second test is the reason for a QuerySet rather than a manager: published() must work after filter(), and exclude() must work after published(). The third fixes the clock twice. At 19:00 on 19 November the meetup, which runs from 18:30 to 20:30, has started but not ended, so it is still upcoming, before the workshop. On 25 November it has ended, so it moves to the past list. save_event() gives each event an end two hours after its start. Notice what none of the chapter’s tests check: which method a view calls. They check what a method returns, what a page shows, and how many queries it costs, so code can move between view, model, and QuerySet without a test changing, which is how Step 5 will prove it changed nothing.

Step 4: Give Event a QuerySet

Open events/models.py. Add a class after validate_timezone_name() and before class Event(models.Model):, separated from both by two blank lines:

events/models.py (1 of 2: before the Event class)

class EventQuerySet(models.QuerySet):
    """Named questions about events."""

    def published(self):
        """Events that visitors may see."""
        return self.filter(status=Event.Status.PUBLISHED)

    def upcoming(self, now):
        """Events not yet ended at now, soonest first."""
        return self.filter(ends_at__gt=now).order_by(
            'starts_at'
        )

    def past(self, now):
        """Events ended by now, the latest first."""
        return self.filter(ends_at__lte=now).order_by(
            '-ends_at'
        )

self is the QuerySet the method is called on, whatever conditions it already has, so self.filter() adds the rule to them. upcoming() and past() each add a condition on the end time and choose their own order, which replaces the model’s: soonest start first for what is to come, latest end first for what is over. Neither checks the status, so the page asks for published().upcoming(now): two rules, two names, one query. The method refers to Event, which is defined further down the file; that works, because the name is looked up only when the method runs. Then, inside Event, add one line after the status field, before class Meta::

events/models.py (2 of 2: after the status field)

        default=Status.DRAFT,
    )

    objects = EventQuerySet.as_manager()

Only the last line is new; the first two show where it goes. Naming the manager objects replaces Django’s plain manager with one built from EventQuerySet, so every existing Event.objects call keeps working and gains published().

Common Error: the class is defined after the model

If EventQuerySet comes after class Event, the project stops with NameError: name 'EventQuerySet' is not defined. The line objects = EventQuerySet.as_manager() runs while Python builds the Event class, so the QuerySet must already exist. Move the class above Event.

Common Error: the method is on a manager

A method written on a models.Manager subclass, the shape of Chapter 17’s UserManager, passes the first test but fails the second with AttributeError: 'QuerySet' object has no attribute 'published'. filter() returns a plain QuerySet, which has no such method. Step 5: Ask the views for published events

Open events/views.py and change the two views, so the whole file reads:

events/views.py

"""The events app's views: one function per page."""
from django.shortcuts import get_object_or_404, render

from .models import Event


def home(request):
    """Welcome visitors to Otahque."""
    return render(request, 'events/home.html')


def event_list(request):
    """List published events: upcoming, then past."""
    events = Event.objects.published()
    return render(
        request, 'events/list.html', {'events': events}
    )


def event_detail(request, event_id):
    """Show one published event, or 404."""
    event = get_object_or_404(
        Event.objects.published(), pk=event_id
    )
    return render(
        request, 'events/detail.html', {'event': event}
    )

The list view asks for published events, and the template’s loop runs the query, as before. get_object_or_404() accepts a QuerySet as well as a model, and calls get() on it, so the detail view finds the event among published events only: a draft’s address still raises Http404. Leaving out the parentheses, get_object_or_404(Event.objects.published, pk=event_id), fails on the detail page with ValueError: First argument to get_object_or_404() must be a Model, Manager, or QuerySet, not 'method'. Without (), Python passes the method itself instead of calling it. Write Event.objects.published().

class EventListTests(TestCase):
    """The list: upcoming first, then past, published only."""

    @classmethod
    def setUpTestData(cls):

        save_event(title='Spring planning',
                   status=Event.Status.DRAFT)
        save_event(title='Autumn social',
                   status=Event.Status.CANCELLED)

    def test_upcoming_first_then_past(self):
        with self.assertNumQueries(2):
            response = self.client.get('/events/')
        html = response.content.decode()
        titles = ['Open lab', 'Python meetup',

    def with_places(self):
        """Add places_left: capacity minus active places."""
        taken = models.Count(

Step 9: Combine conditions with Q and F

Start the shell. First, name two conditions and combine them:

Django shell

>>> from django.db.models import F, Q
>>> virtual = Q(location='Virtual')
>>> small = Q(capacity__lt=20)
>>> Event.objects.filter(virtual | small)
<EventQuerySet [<Event: Django workshop>, <Event: Spring...
>>> Event.objects.filter(~Q(status='published'))
<EventQuerySet [<Event: Winter social>, <Event: Spring pl...
>>> Event.objects.filter(Q(status='draft') & ~small)
<EventQuerySet [<Event: Winter social>]>
>>> Event.objects.published().filter(~virtual)
<EventQuerySet [<Event: Python meetup>]>

The first two lines are shortened here; both end <Event: Spring planning>]>. The Django workshop is virtual and Spring planning has 12 places, so either condition puts it in the first result. ~Q(status='published') is every event that is not published: the two drafts, soonest first. The third asks for drafts that are not small, and the last chains a combined condition after a named method. The repr now says EventQuerySet: every event query is built from the new class.

Common Error: a Q object after a keyword argument

Event.objects.filter(status='draft', Q(capacity__lt=20)) stops with SyntaxError: positional argument follows keyword argument. Python itself refuses the call, before Django sees it. Put the Q object first, filter(Q(capacity__lt=20), status='draft'), or combine both as Q objects.

Chapter 21 made two time rules constraints: a registration is never cancelled before it was made, and an assignment never revoked before it started. The database now refuses a new row that breaks them, but the same questions, asked as queries, are how you check rows written before a rule existed, or plan a constraint you have not added yet. Each compares two columns of the same row:

Django shell

>>> Registration.objects.filter(
...     cancelled_at__lt=F('registered_at')
... )
<RegistrationQuerySet []>
>>> OrganizerAssignment.objects.filter(
...     revoked_at__lt=F('assigned_at')
... )
<QuerySet []>

No registration was cancelled before it was made, and no assignment was revoked before it started. OrganizerAssignment has no custom QuerySet, so its repr still says QuerySet. Now write the first rule as a condition, “a cancellation is never earlier than the registration”, and look for rows that break it with exclude(), as Chapter 21’s L4 proof did:

Django shell

>>> later = Q(cancelled_at__gte=F('registered_at'))
>>> Registration.objects.exclude(later).count()
2
>>> Registration.objects.exclude(later).active().count()
2
>>> rule = later | Q(cancelled_at__isnull=True)
>>> Registration.objects.exclude(rule).count()
0

Two rows seem to break the rule, and both are active. They have no cancellation time, so cancelled_at >= registered_at is not true for them, and exclude() keeps every row where the condition is not true. The rule must say what an empty value means: “cancelled at or after registering, or never cancelled”. With that branch, no row breaks it, and it is exactly the condition of Chapter 21’s cancelled_after_registered constraint. Why the constraint needed no such care is the last quiz question. Step 10: Order, count, and fetch related rows

Start the shell again. First, order, and the SQL that a QuerySet will send. str() of a QuerySet’s query gives its SQL, and Python’s textwrap.fill() folds the long line to fit the page:

Django shell

>>> import textwrap
>>> published = Event.objects.published()
>>> published.order_by('-starts_at')
<EventQuerySet [<Event: Django workshop>, <Event: Python...
>>> titles = published.values('title')
>>> print(textwrap.fill(str(titles.query), 60))
SELECT "events_event"."title" AS "title" FROM "events_event"
WHERE "events_event"."status" = published ORDER BY
"events_event"."starts_at" ASC
>>> latest = titles.order_by('-starts_at')[:1]
>>> print(textwrap.fill(str(latest.query), 60))
SELECT "events_event"."title" AS "title" FROM "events_event"
WHERE "events_event"."status" = published ORDER BY
"events_event"."starts_at" DESC LIMIT 1

The third line ends <Event: Python meetup>]>: newest first. values('title') asks for only the title column, which keeps the SQL short. ORDER BY ... ASC comes from Meta.ordering; order_by('-starts_at') replaced it with DESC, and the slice [:1] became LIMIT 1, so the database returns one row. The value appears as published without quotes because str(query) is only a picture of the SQL: the real statement sends the value separately, and the database driver quotes it. Copy SQL from str(query) only to read it, never to run it.

Next, count. Name the condition “the registration is active”, seen from an event, and count each event’s matching registrations:

Django shell

False
>>> for event in counted.order_by('starts_at'):

Python meetup 1
Django workshop 1
Winter social 0
Spring planning 0

...     total=Count('id'),

registrations__status reads from the event across Chapter 20’s reverse relation. The meetup has two registrations, but Raj’s is cancelled, so it counts 1. ordered is False, because a grouped query does not use Meta.ordering; the loop adds order_by('starts_at') to get date order back. aggregate() returns a dictionary, not a QuerySet: three registrations in all, two of them active.

Now two of Chapter 21’s audits as single queries. Its duplicate search fetched pairs and counted them with Counter; here the database groups and counts. values() before annotate() groups the rows by the listed fields, one result per pair:

Django shell

>>> pairs = Registration.objects.active().values(
...     'event__title', 'member__email'
... )
>>> pairs.annotate(rows=Count('id')).filter(rows__gt=1)
<RegistrationQuerySet []>
>>> Event.objects.alias(
...     places=Count('registrations', filter=active)

<EventQuerySet []>

No pair holds more than one active place, as Chapter 21’s constraint guarantees. The second query compares each event’s count of active places with its own capacity, with F: none is over. alias() computes the count for the filter without adding it to each event. This is an audit, not a guard: two members could still take the last place together, which Chapter 33 prevents.
