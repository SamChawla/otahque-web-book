What You Need to Know

What Chapter 19 already showed

Two facts from Chapter 19 carry this chapter. A QuerySet is lazy: building one, or adding filter() to it, sends nothing to the database, and the query runs only when something needs the rows, such as a loop, list(), or a template. And every QuerySet method that refines a query, such as filter(), exclude(), or order_by(), returns a new QuerySet and leaves the old one unchanged. If either is unfamiliar, reread Chapter 19’s “When a query runs” before going on: everything below depends on them.

Managers and QuerySets, again

Chapter 19 called Event.objects the model’s manager: the object that starts every query. Chapter 17 wrote a manager of its own, UserManager, and Chapter 21 extended it. Its methods, create_user() and create_superuser(), create rows. This chapter adds methods that select rows, and those need a different home.

A manager’s methods exist only on the manager. User.objects.create_user() works, but User.objects.filter(is_staff=True).create_user() fails, because filter() returns a QuerySet, and create_user() is not a QuerySet method. For creating rows that does not matter: you never create a user from the middle of a query. For selecting rows it matters a great deal. You want Event.objects.published(), and also Event.objects.filter(location='Virtual').published(), and Event.objects.published().order_by('-starts_at'), all to work.

New Concept: a custom QuerySet

What problem exists? A rule such as “visitors see published events” is a condition that many queries need, in different combinations with other conditions.

What did people do before? They wrote the condition in each view, as Chapter 19 did, or added a method to a custom manager, which works only at the start of a query.

What is it? A custom QuerySet is a subclass of models.QuerySet whose methods return refined QuerySets, such as return self.filter(status=...). Because every QuerySet method returns a QuerySet of the same class, these methods can be called anywhere in a chain. EventQuerySet.as_manager() builds a manager with a copy of the same methods, so the chain can also start with them.

Why use it? The rule gets one name and one home, beside the model it describes, and every query that needs it says so in words: Event.objects.published().

Under the Hood: what as_manager() builds

as_manager() creates a new Manager subclass at the moment the model class is defined, named after the QuerySet, such as ManagerFromEventQuerySet, and copies the QuerySet’s public methods onto it. Each copied method simply calls get_queryset(), which returns a fresh EventQuerySet, and then calls the method on it. Methods whose names start with an underscore are not copied, and neither is delete(), so that Event.objects.delete() cannot empty a table by accident. Two more consequences matter in this chapter. A reverse relationship’s manager, such as meetup.registrations from Chapter 20, is built as a subclass of the related model’s default manager class, so a method on RegistrationQuerySet also works on meetup.registrations. And a manager is stored in a migration only when it sets use_in_migrations = True, as Chapter 17’s UserManager does so that data migrations can create users. These QuerySet managers do not, so this chapter writes no migration.

Manager.from_queryset() is the third shape. It builds a manager from a manager class of your own and a QuerySet class, for the rare model that needs both: methods that create rows and methods that select them. Otahque’s UserManager could become one if members ever need named queries; nothing needs that yet.

Combining conditions: Q and F

Keyword arguments to filter() are joined by “and”: filter(status='draft', capacity__lt=20) means both. Chapter 21 wrote one condition as a Q object and joined two with |. A Q object is a condition kept as a value, so it can be named, stored in a variable, and combined:

  • a | b holds when either holds (“or”);
  • a & b holds when both hold (“and”);
  • ~a holds when a does not (“not”).

Q objects go into filter(), exclude(), and get() as positional arguments, before any keyword arguments.

The second tool compares a field with another field of the same row. Chapter 21 used it once, inside the constraint that an event ends after it starts; here it goes into queries. filter(cancelled_at__lt=...) needs a value on the right, but “cancelled before it was made” compares two columns. An F expression, F('registered_at'), refers to a field’s value in the database, row by row. filter(cancelled_at__lt=F('registered_at')) becomes WHERE cancelled_at < registered_at. F also works in arithmetic, such as F('capacity') + 10, and in update(), where the database computes the new value itself.

New Concept: Q and F expressions

What problem exists? Some questions need “or” and “not”, and some compare one column with another, which keyword arguments alone cannot say.

What did people do before? They loaded rows into Python and tested each one, or wrote SQL by hand.

What are they? Q(...) is a condition object, combined with &, |, and ~. F('field') is a reference to a column, used where a value would go. Both become part of the SQL, so the database does the work.

Why use them? One query answers the question, however many rows there are, and the condition can be given a name and reused.

Now let’s use it. Step 9 asks Otahque’s audit questions with both.

One case needs care: a column that can be empty. In SQL, a comparison with NULL, the database’s “no value”, is neither true nor false, so cancelled_at < registered_at is not true for an active registration, whose cancelled_at is empty. filter() keeps only rows where the condition is true, so it skips them. exclude() keeps the rows where it is not true, so it includes them. Step 9 shows the difference with real rows.

Choosing an order

Chapter 16 gave Event the option ordering = ['starts_at'], so every event query is soonest first unless it says otherwise. order_by('-starts_at') says otherwise: the minus sign reverses the order, and each order_by() call replaces any earlier order, including the model’s. order_by() with no arguments removes ordering altogether, which saves the database a sort when order does not matter. A QuerySet’s ordered attribute tells you whether it has an order at all.

Upcoming and past: asking about now

Whether an event is upcoming or past depends on one more value: the current time. django.utils.timezone.now() returns it as an aware datetime in UTC, the same form as starts_at and ends_at, so comparing them is correct whatever zone an event is in: the Kolkata workshop and the Leeds meetup are compared as instants, and each page still shows its own local time. An event is past once its end time has gone by. An event that has started but not ended is still worth showing at the top, because people can still join it, so “upcoming” means “not yet ended”: ends_at__gt=now.

A method that called now() itself would be hard to test, because its answer changes with the clock: a test written in November would fail in December. So Otahque’s methods take now as an argument. Tests pass a fixed instant, and the list view calls timezone.now() once and passes the same instant to both methods, so no event can fall between the two lists while the page is being built.

Counting: annotate() and aggregate()

Chapter 21 found duplicate registrations by fetching pairs into Python and counting them with Counter. The database can count for you.

New Tool: annotate(), aggregate(), and Count

What problem exists? Questions such as “how many active places does each event hold?” need a number per row, or one number for a whole set of rows.

What did people do before? They looped over rows in Python, which fetches every row and runs a query per event to count its registrations.

What are they? Count('registrations') is an aggregate: a value computed from many rows. annotate(places=Count(...)) adds it to each object in the result, as event.places, and returns a QuerySet you can keep refining. aggregate(total=Count(...)) computes it over the whole QuerySet and returns a dictionary; it ends the chain. Count(..., filter=Q(...)) counts only the related rows that match. alias() is annotate() without returning the value, for a number you only filter on.

Why use them? The database counts in one query, with a join and grouping, whatever the number of events.

Now let’s use it. Step 8 puts the count of places left on both event pages, and Step 10 counts in the shell and redoes Chapter 21’s duplicate check.

One annotated query counts each event’s active places, as Figure 22.2 shows.

Under the Hood: the SQL behind annotate()

Event.objects.annotate(places=Count('registrations', filter=...)) becomes one statement: SELECT the event’s columns and COUNT("registrations_registration"."id") FILTER (WHERE ... = 'active'), FROM "events_event" LEFT OUTER JOIN "registrations_registration", then GROUP BY the event’s columns. The LEFT OUTER JOIN keeps events with no registrations, which count 0. FILTER (WHERE ...) is how SQLite and PostgreSQL count only matching rows; on databases without it, Django writes a CASE expression instead. Grouping has a side effect that surprises people: Django does not apply the model’s Meta.ordering to a query with GROUP BY, so the result comes back in whatever order the database chooses, and ordered is False. Add order_by() whenever the order matters. A second surprise comes from joining two relations in one query, such as registrations and organizer assignments: each event’s row is repeated once for every combination, and both counts grow. The L3 interview question works through it.

Related rows inside named queries

Chapter 20 fixed a query per row with select_related(), which joins a forward relation into the same query, and named prefetch_related(), which fetches a reverse relation in one extra query. Both are QuerySet methods, so they chain with named methods: Registration.objects.active().select_related('member') is the active places, each with its member already loaded.

A Prefetch object goes one step further: it tells prefetch_related() which QuerySet to use for the related rows, and where to put them. Prefetch('registrations', queryset=Registration.objects.active(), to_attr='active_places') loads each event’s active registrations, and only those, into a list called event.active_places. The named method appears inside the prefetch, so the rule “active” still has one home.

Answer. Still one. published() and filter() each return a new QuerySet, and nothing runs until the template loops over the result, so both conditions are joined into one WHERE clause. Named methods cost nothing extra: they only build the query.

Prefer a QuerySet method, a manager method, or a helper function?

A method that selects rows belongs on a custom QuerySet, attached with as_manager(), so it works at any point in a chain and on related managers. A method that creates rows, or does something before a query exists, belongs on a manager, as create_user() does. A plain function such as published_events() in views.py works for one view, but it cannot follow filter(), related managers do not have it, and the next view’s author has to know it exists. Give a rule a method only when real code repeats it: a QuerySet with thirty one-line methods is as hard to read as the views it replaced.

Two cautions go with that advice. Name methods after the question, not the SQL: published(), not status_equals_published(). And keep the default manager, objects, unfiltered. The L4 interview question explains what goes wrong when it hides rows.

In practice: a weekly count for organizers

Situation. Sam wants to know, each Monday, how many active places each of his events holds, to plan rooms and refreshments.

Application. One annotated query answers it: Event.objects.annotate(places=Count('registrations', filter=Q(registrations__status='active'))), filtered to his events and ordered by start time. It runs as one query whether Sam organizes three events or three hundred.

Consideration. The number is a snapshot, true when the query ran. It does not stop the next registration from going over capacity: that needs a transaction and a lock, in Chapter 33. Visitors see the same kind of snapshot from Step 8: the places left when the page was built. Organizers such as Sam will see counts on Otahque’s own organizer pages, which later chapters build; the admin site is the administrator’s tool, not an organizer page.
