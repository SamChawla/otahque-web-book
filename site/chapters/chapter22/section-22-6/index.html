Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead to a larger application with a team: attempt them now, and return to them after Chapters 23, 36, and 57. They are extension questions, not a gate to the next chapter. Each code proof is a short file in the practice folder that starts by importing Chapter 16’s setup_django.py; run it from the folder that holds manage.py with uv run python ../practice/ followed by the file name. The proofs only read your rows.

L1 (Junior): What is the difference between a manager and a QuerySet, and where would you put a published() method?

What the interviewer is testing: Do you know what each object is for, and why a selecting method must be chainable?

Flip to check your answerFold answer back

Perfect answer: A manager, such as Event.objects, is the model’s entry point for queries; Django adds a plain one called objects unless the model defines its own. A QuerySet is a lazy description of a query, and every refining method, such as filter(), returns a new QuerySet of the same class. A method on a manager is available only at the start, so it cannot follow filter(). A method on a custom QuerySet is available everywhere in the chain, and as_manager() copies it onto the manager too. So published() goes on an EventQuerySet, attached as objects = EventQuerySet.as_manager(). Manager methods are right for things that do not refine a query, such as create_user(). I would add published() because two views already repeat the rule, and I would keep objects itself unfiltered.

Behind the scenes:

managers and QuerySets (summary)

Event.objects             -> ManagerFromEventQuerySet
Event.objects.filter(...) -> EventQuerySet
.published()              -> EventQuerySet, one more WHERE
User.objects.create_user  -> manager only, not chainable

Code proof: a QuerySet method after filter(), and a manager method that cannot follow it:

../practice/l1_chain.py

import setup_django

from accounts.models import User
from events.models import Event

virtual = Event.objects.filter(location='Virtual')
print(virtual.published())
try:
    User.objects.filter(is_staff=True).create_user
except AttributeError as error:
    print(error)

Output

<EventQuerySet [<Event: Django workshop>]>
'QuerySet' object has no attribute 'create_user'

published() refines a filtered query, and create_user does not exist once filter() has returned a QuerySet.

Common mistakes:

  • Writing selecting methods on a Manager subclass, so they cannot be chained.
  • Overriding get_queryset() on objects to hide rows, which hides them from the admin site too.
  • Adding a method for every condition used once.

Follow-up the interviewer might ask:

  • “When would you use Manager.from_queryset() instead of as_manager()?”
  • “Why is delete() not copied onto the manager?”

L2 (Mid-Level): Why can filter(a, b) and filter(a).filter(b) return different events when both conditions are about registrations?

What the interviewer is testing: Do you understand how conditions across a multi-valued relationship are joined?

Flip to check your answerFold answer back

Perfect answer: An event has many registrations, so a condition such as registrations__status='active' asks whether some registration matches. Inside one filter() call, all the conditions on that relation must hold for the same registration: “an event where Raj has an active registration”. In chained calls, Django joins the registrations table once for each call, and each condition may be met by a different registration: “an event where Raj has some registration, and some registration is active”. At the Python meetup, Raj’s place is cancelled and Sai’s is active, so the first question finds nothing and the second finds the meetup. The chained form can also return the same event more than once. I choose the form that matches the question, use one call or a Q object for “the same related row”, and check with a test. exclude() has its own rules for multi-valued relations, so for “events without an active registration by Raj” I would exclude using a subquery of registrations.

Behind the scenes:

multi-valued conditions (summary)

filter(a, b)        -> one JOIN; same related row
filter(a).filter(b) -> two JOINs; rows may differ
duplicates          -> possible with chained JOINs

Code proof: the two forms, asked about Raj:

../practice/l2_relations.py

import setup_django

from events.models import Event

raj = {'registrations__member__email': 'raj@example.org'}
active = {'registrations__status': 'active'}
print(Event.objects.filter(**raj, **active))
print(Event.objects.filter(**raj).filter(**active))

Output

<EventQuerySet []>
<EventQuerySet [<Event: Python meetup>]>

**raj unpacks the dictionary into keyword arguments. Raj has no active place anywhere, but the meetup has a registration of his and an active registration of Sai’s.

Common mistakes:

  • Treating chained filters on a relation as the same as one call.
  • Fixing duplicate events with distinct() without asking why they appeared.
  • Assuming exclude() mirrors filter() for multi-valued relations.

Follow-up the interviewer might ask:

  • “How would you write ’events where Raj has no active place’ correctly?”
  • “Why do chained filters on a forward foreign key behave the same as one call?”

L3 (Senior): A report counts each event’s registrations and organizers in one annotate(), and both numbers are too high. Why, and how do you fix it?

What the interviewer is testing: Can you see the joins behind an aggregation and choose a correct fix?

Flip to check your answerFold answer back

Perfect answer: annotate(places=Count('registrations'), organizers=Count('organizer_assignments')) joins both tables to events in one query. Each event’s row is repeated once for every combination of a registration and an assignment, and each COUNT counts the repeated rows. The meetup has two registrations and one assignment, so the join has two rows, and the organizer count is 2 instead of 1; with more of each, both counts grow. For Count, distinct=True counts each related row once. For Sum or Avg, distinct gives wrong answers too, so I would compute each aggregate in its own subquery, with Subquery and OuterRef, which Chapter 55 covers, or run two queries. I would also write a test with known counts, and read the SQL with str(queryset.query) when in doubt.

Behind the scenes:

two counts (summary)

JOIN registrations and assignments -> rows multiply
Count(..., distinct=True)          -> each row once
Sum over two joins                 -> subqueries

Code proof: the meetup’s two counts, without and with distinct:

../practice/l3_counts.py

import setup_django
from django.db.models import Count

from events.models import Event

meetup = Event.objects.filter(title='Python meetup')
for distinct in (False, True):
    row = meetup.annotate(
        places=Count('registrations', distinct=distinct),
        organizers=Count('organizer_assignments',
                         distinct=distinct),
    ).get()
    print(distinct, row.places, row.organizers)

Output

False 2 2
True 2 1

The registrations count is 2 both times, Sai’s and Raj’s places, because the meetup has one assignment. The organizer count doubles without distinct, one row for each registration.

Common mistakes:

  • Trusting a report’s numbers without a test that knows the answer.
  • Adding distinct=True to a Sum, which merges equal values.
  • Using annotate() over two relations for a page that shows both counts.

Follow-up the interviewer might ask:

  • “How would you write the organizer count as a subquery?”
  • “Would the counts be wrong if one relation were a forward foreign key?”

L4 (Staff): A teammate proposes making Event.objects return only published events, so that no view can forget the rule. What do you advise?

What the interviewer is testing: Do you know which manager Django’s own tools use, and the cost of hiding rows by default? This looks ahead to Chapters 23 and 30.

Flip to check your answerFold answer back

Perfect answer: The goal is right; the mechanism is wrong. The first manager a model defines is its default manager, _default_manager, and Django’s tools use it: the admin site lists rows with it, dumpdata exports with it, and the reverse managers of related models are built from its class. If objects overrode get_queryset() to return published events only, the administrator could not see or correct drafts in Chapter 23’s admin site, backups would miss drafts, and a registration’s reverse queries would silently skip rows. Following a foreign key, such as registration.event, uses the plain base manager, so the same object would be visible one way and invisible the other. I would keep objects whole and make the rule explicit with Event.objects.published(), as Otahque does. To stop a view forgetting it, I would give every public page a test with a draft and a cancelled event, review new pages against that rule, and, in Chapter 30, check permissions as well. If a filtered manager is truly wanted, it is a second manager with its own name, declared after objects, as some tutorials do with published.

Behind the scenes:

managers Django uses (summary)

_default_manager -> first manager: admin, dumpdata
reverse managers -> subclass the default's class
_base_manager    -> plain Manager: registration.event
rule             -> keep objects whole; name the filter

Code proof: which manager each path uses, in the reader’s project:

../practice/l4_managers.py

import setup_django

from events.models import Event
from registrations.models import Registration

print(Event._meta.default_manager.name)
print(type(Event._base_manager).__name__)
place = Registration.objects.active().first()
related = place.event.registrations
print(type(related).__mro__[1].__name__)
print(related.active())

Output

objects
Manager
ManagerFromRegistrationQuerySet
<RegistrationQuerySet [<Registration: sai@example.org at...

The last line is shortened; it ends Python meetup>]>. __mro__ lists a class’s parents in order, so its second entry shows that the reverse manager place.event.registrations was built from Registration’s default manager class, which is why active() works on it. The base manager is Django’s plain Manager.

Common mistakes:

  • Filtering the default manager and discovering it in the admin site.
  • Assuming related access and queries use the same manager.
  • Treating a code convention as a guarantee without per-page tests.

Follow-up the interviewer might ask:

  • “What does Meta.default_manager_name change?”
  • “How would you find every public view that does not use published()?”

L5 (Lead): Should Otahque wrap the ORM in a repository layer, so that views never build queries themselves?

What the interviewer is testing: Can you weigh an architecture pattern against what the framework already provides, and set a boundary the team can follow? This looks ahead to Chapters 36 and 55 to 57.

Flip to check your answerFold answer back

Perfect answer: A repository, a class whose methods return rows, such as EventRepository.published_in_person_soonest_first(), is meant to give each query one home and to hide the database from the rest of the code. With Django, a custom QuerySet already does the first, and the second costs more than it saves. A repository that returns lists ends the chain: the view can no longer add order_by(), a slice, select_related(), or Chapter 36’s pagination, which needs a QuerySet to count and slice in the database. So the repository grows a method or a parameter for every combination. Named QuerySet methods compose instead: Event.objects.published().exclude(location='Virtual')[:10] stays one query. Repositories are common in FastAPI projects for a good reason: their usual ORM, SQLAlchemy, follows the Data Mapper pattern, where plain classes are loaded and saved through a session that code must pass around, and nothing gives queries a built-in home, so a repository class holds the session and the named queries. Django follows Active Record, as its design philosophy says: a model carries its own data and behaviour, and its manager and QuerySet already are that home. My boundary for the team is “fat models, thin views”: rules about which rows are selected live in QuerySet methods; actions on a record live in model methods, such as registration.cancel() in Chapter 31 or event.register(member), with its capacity check inside a transaction, in Chapter 33; views only read the request, call one method, and choose a response. If a model grows too large, or an action has no single owning model, I extract that action into a small service module, on evidence rather than in advance, and record the decision.

Behind the scenes:

query boundary (summary)

which rows   -> QuerySet methods, on the model
what happens -> model methods (fat models)
views        -> thin: request in, one call, response
repository   -> lists end the chain; Django has one

Code proof: a named method sliced, and the SQL that the database receives:

../practice/l5_slice.py

import textwrap

import setup_django
from django.db import connection
from django.test.utils import CaptureQueriesContext

from events.models import Event

with CaptureQueriesContext(connection) as queries:
    first = list(Event.objects.published()[:1])
print(first)
sql = queries[0]['sql']
print(textwrap.fill(sql[sql.index('WHERE'):], 60))

Output

[<Event: Python meetup>]
WHERE "events_event"."status" = 'published' ORDER BY
"events_event"."starts_at" ASC LIMIT 1

The slice became LIMIT 1, so the database returned one row; a method that returned a list would have fetched every published event first. The captured SQL quotes 'published', unlike str(query), because it shows the statement as the database ran it.

Common mistakes:

  • Copying a pattern another stack needs, such as a FastAPI repository over SQLAlchemy, into Django, where QuerySets already fill that role.
  • Returning lists from query helpers, so pagination fetches every row.
  • Putting actions in views, where the admin, the shell, and tests cannot reuse them, or in QuerySet methods, where transactions are hard to see.

Follow-up the interviewer might ask:

  • “What would make you add a repository after all?”
  • “Where does a function that registers a member and checks capacity belong?”
