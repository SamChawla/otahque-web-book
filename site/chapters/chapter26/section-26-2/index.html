What You Need to Know

An event’s life: states and moves

Chapter 16 gave Event a status with three values: draft, published, and cancelled. Until now the only way to change it was the admin site. This chapter makes the moves explicit.

New Concept: a state machine

What problem exists? A status column can hold any of its values at any time. Nothing says that a cancelled event may not become a draft again, or that a draft may not be cancelled.

What did people do before? They wrote if event.status == 'draft' in whichever view needed it, and each view invented its own rule.

What is it? A state machine is a short list of states and the moves allowed between them, each move with a rule about who may make it and when it is refused. Anything not on the list is refused.

Why use it? The list is small enough to draw, test, and defend. A new rule is a change to one place.

Now let’s use it. Step 2 draws Otahque’s three states, and Steps 6 to 9 give each move one method on the model.

The states and the moves this chapter allows are drawn in Figure 26.1.

Table 26.1 lists each move with where it starts, where it ends, and when it is refused. The last row is not a move between states: copying makes a new draft and leaves the original alone.

Two choices in the table are decisions, not facts about Django. There is no unpublish: a published event may already have registrations, and hiding it would leave those members without a page. And cancelled is final: to run a cancelled event again, you copy it, which creates a fresh draft with none of the old registrations. These choices are Chapter 26’s design, recorded in docs/design/event-states.md in Step 10, and you can revisit them when members’ needs are clearer.

Ready is not the same as valid

Chapter 21 and Chapter 25 made sure that every saved event is valid: it ends after it starts, its capacity is above zero and never below the places taken. A draft, though, may be valid and still unfinished. Sam saved the clinic without a description, and that is allowed.

Readiness is a stricter test, applied only at the move from draft to published. Chapter 2’s publishing criteria name a description, a start in the future, and an assigned organizer. The registration window is the fourth criterion, and it waits for Chapter 31, which defines it. So this chapter’s rule has three conditions, and each missing one gets its own message.

New Concept: readiness, kept in the model

What problem exists? Where should “is this event ready to publish?” live? If it lives in the view, the shell and the admin cannot ask it. If it lives in the template, hiding a button looks like a check but a hand-made request still gets through.

What did people do before? They hid the Publish button when something was missing, and checked nothing on the server.

What is it? A model method, readiness_problems(), returns the list of what is missing, and publish() refuses when the list is not empty. The page only shows the result.

Why use it? One question, one answer, in one place, asked the same way by every caller.

Now let’s use it. Step 6 writes both methods before any view uses them.

A description, and a migration

Readiness needs a description to check, so the first job is to add one. Event.description is a TextField(blank=True): a draft may leave it empty, and readiness demands it later. Django’s convention, stated in its documentation for string-based fields, is to use an empty string, not NULL, as the “no data” state, so the field has blank=True and no null=True.

Adding a field to a table that already has rows is the first schema change since Chapter 21. Django’s migration for it is generated from the model and then applied. Two commands let you see what will happen before it does, and one lets you undo it:

  • sqlmigrate events 0004 prints the SQL for a migration without running it, and --backwards prints the SQL that would unapply it;
  • migrate --plan lists what a migrate command would do;
  • migrate events 0003 moves the events app back to its third migration, which unapplies the fourth.

Step 3 runs all of them on the real project. The SQL depends on the database: on SQLite, Django rebuilds the table, while other databases add a column in one statement, so read the output on your own machine.

Under the Hood: what unapplying a migration does

Unapplying 0004 runs the SQL that sqlmigrate --backwards prints. For a new column, that SQL drops the column, so the descriptions you typed are gone with it. Unapplying is therefore safe on your own machine and a serious step on a database holding real data. Django’s documentation says a migration containing an irreversible operation cannot be reversed at all. On a shared or deployed database, the usual route is a new migration that moves forward, not a rollback.

A link and a form are not the same thing

A web browser sends a GET request when you follow a link or type an address, and a POST request when you submit a form. HTTP, the protocol under every web page, calls GET and three other methods safe: RFC 9110, section 9.2.1, says a safe method’s semantics are essentially read-only, and that this lets automated processes, such as search crawlers, and browsers that prefetch a page, use it freely. A client that follows every link on a page is not misbehaving. A page that changes data when it is followed is.

So Otahque’s rule is plain: a GET only reads. Anything that changes data, publishing, cancelling, deleting, or copying, is a POST, sent by a form with Chapter 24’s CSRF token. A view that accepts only POST answers a GET with 405 Method Not Allowed. The standard requires a 405 response to carry an Allow header listing the methods the resource does support, and Django’s decorator sets it, as Step 6’s test shows.

Deleting adds one step. A delete cannot be undone, so Otahque shows a confirmation page on GET, which only reads, and deletes on the POST that page’s button sends. Publishing and cancelling have no confirmation page: publishing is checked by readiness and is reversible only by cancelling, and cancelling says plainly beside its button that it cannot be undone. You can change that choice if your community wants a confirmation page there too.

Why Django refused to delete Sam’s draft

Chapter 20 made OrganizerAssignment.event a ForeignKey with on_delete=PROTECT. That setting forbids deleting an event while an assignment points at it: Django raises ProtectedError, which Django’s documentation describes as a subclass of IntegrityError. The protection is deliberate, because an assignment is part of who ran an event. It also means that deleting Sam’s own draft fails today. Step 2 shows the message.

For a draft with no registrations, the right order is clear: delete the draft’s assignments, then the draft, and do both in one transaction, so that either both happen or neither does. A draft that someone registered for is another matter, and Otahque refuses to delete it.

Who may do what

Chapter 25 decided who may edit an event: someone who holds events.change_event and is a current organizer of that event, written once in Event.can_be_edited_by(). This chapter’s actions use the same rule. Chapter 30 will design roles and groups properly, and the one method is where it will plug in, so no view tests roles on its own.

The access check has two outcomes, as in Chapter 25. A person who may not see the event gets 404, so a draft’s existence stays private. A person who may see it but not change it gets 403. A visitor who is not signed in is sent to sign in. The answers for the three actions are in Figure 26.3.

The cancelled event, as members see it

Chapter 24 hid cancelled events from everyone but organizers, as it hid drafts. That is wrong for a cancelled event, because members who hold places need to learn that the event is off. This chapter changes the rule: a cancelled event’s page is shown to everyone who has its address, under a Cancelled tag, with no line about places left. It stays out of the upcoming and past lists, and the registrations are untouched. Organizers still see it, tagged, on their own My events page.

Two earlier choices change with it, and you will see both in Step 7: Event.is_visible_to() now hides only drafts, and one Chapter 24 test, which expected a 404 for a cancelled event, changes in place.
