Test Your Knowledge: Interview Questions

These seven questions rehearse the chapter at interview level, from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead to a larger application with a team: attempt them now, and return to them after Chapters 30 and 33. L6 and L7 are about migrations, and you can answer them now with the commands from Step 3. They are extension questions, not a gate to the next chapter.

L1 (Junior): Why must publishing or deleting never happen on a GET request?

What the interviewer is testing: Do you know what a safe method is, and what a link, a prefetch, and a crawler do with one?

Flip to check your answerFold answer back

Perfect answer: A GET is defined as read-only, and the web relies on that. Browsers prefetch links, search crawlers follow every link they find, and people paste addresses into chats, which open previews. If a GET changes data, each of them can publish or delete an event without anyone deciding to. So a change goes in a POST, sent by a form, and for an organizer’s page it also carries the CSRF token. A view that takes only POST answers anything else with 405 and an Allow header.

Behind the scenes:

GET to the three addresses (summary)

publish and cancel -> require_POST -> 405, Allow: POST
delete page        -> shows a confirmation; deletes nothing

Code proof: a signed-in Sam opens the three addresses with GET, inside a transaction that is rolled back:

l1_get.py (practice file; delete it afterwards)

from django.db import transaction
from django.test import Client
from django.test.utils import setup_test_environment

from accounts.models import User
from events.models import Event

setup_test_environment()
sam = User.objects.get(email='sam@example.org')
with transaction.atomic():
    web = Client()
    web.force_login(sam)
    for name in ('publish', 'cancel'):
        reply = web.get(f'/events/6/{name}/')
        print(name, reply.status_code, reply['Allow'])
    page = web.get('/events/6/delete/')
    print('delete page', page.status_code)
    print('still there:', Event.objects.filter(pk=6).exists())
    clinic = Event.objects.get(pk=6)
    print('status:', clinic.status)
    transaction.set_rollback(True)

Folder structure

Method Not Allowed (GET): /events/6/publish/
publish 405 POST
Method Not Allowed (GET): /events/6/cancel/
cancel 405 POST
delete page 200
still there: True
status: draft

Common mistakes:

  • Writing <a href="/events/6/delete/"> and having that view delete.
  • Hiding the button instead of refusing the method.
  • Forgetting that a link with onclick JavaScript still sends a GET when JavaScript is off.

Follow-up the interviewer might ask:

  • “Is a POST enough, by itself, to protect a delete?”
  • “What does the Allow header tell a client?”

L2 (Mid-Level): Predict what happens when Sam presses Publish on a draft with no description that starts next week.

What the interviewer is testing: Can you trace a refused publish through the access check, the model, and the page, and say what is stored?

Flip to check your answerFold answer back

Perfect answer: The POST reaches event_publish, and the access check passes: Sam is a current organizer and holds change_event. publish() first checks the status, which is a draft, then calls readiness_problems(). The start is next week and an organizer exists, so the list holds one message, Add a description. publish() raises a ValidationError before changing anything, the view turns the message into an error message and redirects to the draft, and the status is still draft.

Behind the scenes:

publish on an unfinished draft (summary)

access check        -> passes
status is draft     -> continues
readiness_problems  -> ['Add a description.']
publish()           -> raises; no write
redirect            -> the draft page shows the message

Code proof: the same draft in the shell, rolled back afterwards:

l2_not_ready.py (practice file; delete it afterwards)

from datetime import timedelta

from django.core.exceptions import ValidationError
from django.db import transaction
from django.utils import timezone

from accounts.models import User
from events.models import Event

sam = User.objects.get(email='sam@example.org')
with transaction.atomic():
    soon = timezone.now() + timedelta(days=7)
    draft = Event.objects.create(
        title='Next week', timezone='Europe/London',
        starts_at=soon, ends_at=soon + timedelta(hours=1),
        location='Online', capacity=20,
    )
    draft.add_organizer(sam)
    print(draft.readiness_problems())
    try:
        draft.publish()
    except ValidationError as error:
        print('refused:', error.messages)
    draft.refresh_from_db()
    print('status:', draft.status)
    transaction.set_rollback(True)

Output

['Add a description.']
refused: ['Add a description.']
status: draft

Common mistakes:

  • Returning only the first problem, so the person fixes one, tries again, and meets the next.
  • Checking readiness in the template, so the button is hidden but a crafted POST works.
  • Saving first and then checking, which leaves a published event in the database for a moment.

Follow-up the interviewer might ask:

  • “How would you show the problems before the person presses the button?”
  • “Where would you add the registration window later?”

L3 (Senior): Defend refusing to delete published events, and cancelling them instead.

What the interviewer is testing: Do you weigh what a delete destroys against what a cancel keeps, and know which layer is the last line?

Flip to check your answerFold answer back

Perfect answer: A published event has been public, and members may hold places in it. Deleting it would erase their registrations, which are the record of who planned to come, and Sai would find a “not found” page where she had a place. Cancelling keeps every row, tags the page so everyone learns what happened, and leaves the history for later chapters, such as the notification email and Chapter 31’s reports. The model enforces it twice: delete_draft() refuses anything but a draft, and the database refuses to delete an event while a registration points at it.

Behind the scenes:

delete or cancel a published event (summary)

delete_draft() -> refused: only a draft
event.delete() -> refused: a registration protects it
cancel()       -> allowed; every row stays

Code proof: a published event with one registration, rolled back afterwards:

l3_keep.py (practice file; delete it afterwards)

from datetime import timedelta

from django.core.exceptions import ValidationError
from django.db import transaction
from django.db.models import ProtectedError
from django.utils import timezone

from accounts.models import User
from events.models import Event
from registrations.models import Registration

sai = User.objects.get(email='sai@example.org')
with transaction.atomic():
    soon = timezone.now() + timedelta(days=7)
    event = Event.objects.create(
        title='Meetup', timezone='Europe/London',
        starts_at=soon, ends_at=soon + timedelta(hours=1),
        location='Online', capacity=20, status='published',
    )
    Registration.objects.create(event=event, member=sai)
    try:
        event.delete_draft()
    except ValidationError as error:
        print('delete_draft:', error.messages[0])
    try:
        event.delete()
    except ProtectedError:
        print('delete(): ProtectedError')
    event.cancel()
    print('after cancel:', event.status,
          event.registrations.count())
    transaction.set_rollback(True)

Output

delete_draft: Only a draft can be deleted.
delete(): ProtectedError
after cancel: cancelled 1

Common mistakes:

  • Deleting published events with a cascade, so the registrations go with them.
  • Adding a soft-delete flag for a draft nobody has seen.
  • Treating the database’s protection as the first line, when a clear message in the model is kinder.

Follow-up the interviewer might ask:

  • “When would you want a soft delete?”
  • “What would you tell the members who hold places?”

L4 (Staff): A crawler deleted rows in production by following links. Diagnose and fix.

What the interviewer is testing: Can you find a state-changing GET, fix it without breaking the page, and prove the fix with a test?

Flip to check your answerFold answer back

Perfect answer: Look at the access log for GET requests to the delete address, from a crawler’s address or user agent, and find the view that deletes for any method. Restore the rows from the latest backup. Then change the view: a GET shows a confirmation page and changes nothing, and only a POST deletes, with the CSRF token from Chapter 24 and the same permission check as before. Add the test that proves it: a GET leaves the row, a DELETE method is refused with 405, and a POST without the token is refused with 403. Keep crawlers away from private pages with sign-in, not with robots.txt alone.

Behind the scenes:

the fixed delete address (summary)

GET     -> a page that asks first
DELETE  -> 405
POST, no token  -> 403
POST, token     -> the delete

  • Fixing the page and leaving the old address working for any method.
  • Turning off the CSRF check to make the form work.
  • Restoring the data without a test, so the fault returns with the next refactor.

Follow-up the interviewer might ask:

  • “How would you find which rows were deleted?”
  • “What makes a request idempotent, and is a delete idempotent?”

L5 (Lead): The community wants to unpublish events after members registered. What do you advise?

What the interviewer is testing: Can you turn a request into a requirement, name what it breaks, and offer a smaller step that serves the real need?

Flip to check your answerFold answer back

Perfect answer: Ask what they need. If an event is wrong, cancelling it, with the tag, tells everyone what happened, and copying it gives a corrected draft quickly. Unpublishing would hide the page from the members who hold places, so they would meet “not found” with a registration they cannot see, which is the problem Chapter 26 set out to remove. If they still want it, it is a requirement to decide: what happens to the registrations, who is told, and how it is recorded. Chapter 30’s audit record and Chapters 43 and 44’s email are where that belongs.

Behind the scenes:

a member holds a place, then the event is cancelled (summary)

cancel() -> status cancelled, registration kept
page     -> 200, with the Cancelled tag, for the member

Code proof: Sai holds a place at a published event, which is then cancelled; she opens its page, rolled back afterwards:

from datetime import timedelta

Common mistakes:

  • Adding an unpublish move without deciding what happens to the registrations.
  • Treating the request as a button, not a requirement.
  • Promising a notification that Otahque cannot send yet.

Follow-up the interviewer might ask:

  • “Who should be allowed to unpublish, and how would you record it?”
  • “What would make you reverse the decision that cancelled is final?”

L6 (Mid-Level): The description migration is applied and a problem appears. How do you roll it back?

What the interviewer is testing: Do you know the command, what it destroys, and when not to use it?

Flip to check your answerFold answer back

Perfect answer: Name the migration you want to go back to, and run uv run python manage.py migrate events 0003: Django unapplies every later migration of the events app, here 0004. Check first with showmigrations events and with migrate --plan, because Django’s documentation warns that dependent migrations in other apps are unapplied too. After the command, showmigrations shows 0004 unticked. For an added column the SQL is a drop, so the descriptions typed since the migration are gone, and sqlmigrate events 0004 --backwards shows that before you run anything. That is acceptable on your own machine. On a shared or deployed database, where rows matter, you do not unapply: you write a new migration that moves forward, and deploy it. Some migrations cannot be reversed at all, and Django then raises an error, as its documentation says.

Behind the scenes:

rolling back events 0004 (summary)

showmigrations events   -> [X] 0004
migrate events 0003     -> Unapplying events.0004
showmigrations events   -> [ ] 0004
migrate                 -> Applying events.0004

Code proof: the commands from Step 3, on the project:

Output

Operations to perform:
  Target specific migration: 0003_rules, from events
Running migrations:
  Rendering model states... DONE
  Unapplying events.0004_event_description... OK

Common mistakes:

  • Rolling back on a database that holds data you cannot type again.
  • Editing the numbered migration instead of adding a new one.
  • Forgetting that migrate with no arguments applies everything again.

Follow-up the interviewer might ask:

  • “What does migrate events zero do?”
  • “How would you test a migration before you apply it to production?”

Perfect answer: Run uv run python manage.py sqlmigrate events 0004. It prints the SQL for that migration without changing the database, and --backwards prints the SQL that unapplies it. It needs a database connection, because it uses it to resolve constraint names, so run it against a copy of the target database. Read the output for what it does to existing rows: here, '' goes into the new column of every row, and on SQLite the table is rebuilt, while on other databases it is one ALTER TABLE ... ADD COLUMN. Two other checks belong beside it: makemigrations --check --dry-run fails when the models and migrations disagree, and migrate --plan lists what a migrate would do. TextField(blank=True) gives existing rows an empty string, never NULL, so the field’s “no data” value is consistent.

Common mistakes:
