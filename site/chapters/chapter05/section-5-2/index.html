What You Need to Know

What a framework contributes

New Concept: web framework

What problem exists? Every web application repeats the same machinery: connecting addresses to code, building pages, storing records, checking forms, and identifying people. Written by hand each time, that machinery is slow to build and easy to get subtly wrong.

What did people do before? Teams wrote that machinery themselves, or assembled separate libraries and decided how they fitted together.

What is a web framework? Reusable software that supplies structure and tools for building web applications. Django is a Python web framework. We write application code that works with its components and conventions; a convention is an agreed way of arranging or naming things so that the pieces work together predictably.

Why a framework? Because more of our effort can go on the shared registration record, clear outcomes, and ownership boundaries our people need, rather than on plumbing.

Now let’s separate what it supplies from what we decide.

In the small programs from Chapter 4, we started a file and followed its statements to the end. In a web application, incoming requests repeatedly trigger application work, and Django calls our code when a request needs it. Reusing a framework does not remove Python from the picture. Functions still receive inputs and return results; objects still hold attributes and provide methods. Some of the objects and calling conventions come from Django, while the application supplies its own behaviour.

Que. 1 Does choosing Django mean that we no longer need the Python skills from Chapter 4?

Flip to check your answerFold answer back

Answer. No. Django application code still uses Python. Reading a function call, a returned value, an import, or an error message helps us understand how our code works with the framework. Django adds tools and conventions; it does not replace those language concepts.

Chapter 3 separated the browser from the server-side application, and that separation still applies. The browser sends a request and interprets the response. Our Python application uses Django on the server side to help produce that response. Installing Django on the development computer does not install Python inside each visitor’s browser.

The diagram shows responsibilities, not a deployment plan. It does not say how many computers we need or which hosting service to use. The two parts inside the application cooperate; they are not two independently deployed services.

Que. 2 Soni opens an Otahque page. Does her browser run the Django code shown inside the application box?

Flip to check your answerFold answer back

Answer. No. Django runs as part of the server-side Python application in this design. Soni’s browser sends the request and receives the response. For a normal page response, the browser interprets the returned HTML, together with the page’s styling and any browser-side scripts.

Reusable mechanisms and product rules

Django brings several reusable mechanisms into one framework. For the registration problem in Chapter 1, their value is concrete:

  • URL routing connects an address to the view that handles its request; a view is the Python code that returns the response.
  • Templates turn supplied event details into HTML pages for visitors and members.
  • The object-relational mapper, or ORM, lets Python code work with database records. We will use it to read and change events and registrations.
  • Forms and account tools help process input and identify members. Otahque must still decide when registration is allowed and who may change each record.
  • The admin site provides a starting interface for trusted staff to manage records. Attendees and organizers will need pages designed for their own tasks.
  • Security mechanisms help protect common web interactions. We must still configure them correctly and enforce Otahque’s access and capacity rules.

Table 5.1 separates framework support from product responsibilities; it describes future work, not features already built.

For example, knowing which account is signed in does not answer whether that account may edit Sam’s event. Our requirements assign organizers responsibility for particular events; the implementation must enforce that relationship, and our tests must show that a different organizer cannot bypass it. Likewise, a page can display a Register button while the server must still reject a registration that violates the rules. The button is a way to request an action, not proof that the action is allowed.

Que. 3 If an edit button is hidden from another organizer, have we proved that Sam’s event is protected?

Flip to check your answerFold answer back

Answer. No. Hiding the button changes the interface. A request could still reach the server through another route. The server-side operation must check whether the account may edit that event, and later verification must include a request from an account that lacks that permission.

Common Error: “Django handles security”

Django supplies protections against several common web attacks, but their effectiveness depends on how we use and configure the framework. An application-specific rule, such as keeping an unpublished event out of a public response, still needs an implementation and a check. For every feature, ask two questions: what mechanism can the framework supply, and what result must our application guarantee?

A review of a finished feature asks the same two questions.

In practice: reviewing a framework-based feature

Situation. A team uses Django’s account tools and is ready to review who may edit an event.

Application. Ask separately whether the requester is signed in and whether that account may edit this particular event. Use the requirements to define the second answer.

Consideration. Framework support does not establish event ownership rules automatically. A review must include an account that should be refused, as well as the permitted organizer.

Then explain why seeing the published event alone would be an incomplete check if you had never created a draft for the test.

Que. 4 What should the responsibility split and check show?

Flip to check your answerFold answer back

Answer. Soni should see the published event and should not receive the private draft’s details. Django can help handle the request and produce the page response. Otahque must apply the visibility rule when choosing what data the response contains. Including both kinds of event in the test lets us check inclusion and exclusion; a test containing only published events cannot expose accidental disclosure of a draft. Private data should not be included in a public response and then merely hidden on screen.

Following a request through Django

Soni follows a link to the Python workshop’s detail page. In Chapter 3 we traced that request as far as “the server”. Now we look inside the server-side application. Django divides the work of answering a request among a few kinds of component, each with one job. Learning their names now means that the files you meet in Chapter 6 and the code you write from Chapter 9 will look familiar rather than arbitrary.

The first job is choosing which code should answer. A URL configuration, often shortened to URLconf, is an ordered list of address patterns, each connected to a view. Django compares the requested path, such as /events/42/, with the patterns in order and uses the first one that matches. A pattern can capture part of the path, such as the number 42, and pass it on. If no pattern matches, Django answers with a “not found” response, the 404 status from Chapter 3.

A view is a Python function, or a class, that receives the request and returns a response. It is where the application decides what this request should produce: which event is wanted, whether it is published, and which page to show. In Django, a view is the code that prepares a response, not the screen the visitor sees.

A model is a Python class that describes one kind of stored record, such as an event, and gives the view a way to read and change those records. Django translates model operations into database queries, so a view can ask for “the published event numbered 42” in Python rather than in the database’s own language. We design Otahque’s models in Chapters 15 and 16.

A template is a text file, usually HTML, with marked places where values are inserted. The view chooses a template and supplies the values; Django fills in the template, and the result becomes the body of the response. By default, Django’s templates escape inserted values, so text typed by a member and placed in ordinary HTML text is displayed as text rather than treated as part of the page’s code. Values placed in other contexts, such as scripts or addresses, and values deliberately marked as safe need separate care; Chapter 11 explains the limits.

Finally, the view returns a response: a status code, headers, and a body, the same parts introduced in Chapter 3. Django hands it back to the web server, which sends it to the browser.

Read the figure as one possible path for a reading request. Not every view uses every component. A view that redirects after a registration may use no template, and a page of fixed text may need no model. What stays constant is the order of decisions: match the address, run the view, gather what it needs, and return a response.

Under the Hood: how Django finds the view

Each request enters a handler, BaseHandler in django/core/handlers/base.py, which passes it through the middleware chain. The handler’s resolve_request() asks the root URL resolver to resolve() the request’s path. The resolver, in django/urls/resolvers.py, tries the patterns in order and stops at the first match, returning a ResolverMatch that carries the view and the captured values, such as 42. Django then calls that view with the request and those values. If nothing matches, the resolver raises Resolver404, which becomes the “not found” response.

Que. 5 Soni’s request is for /events/42/. Which component decides which Python function handles it?

Flip to check your answerFold answer back

Answer. The URL configuration. Django compares the path with its patterns in order and calls the view connected to the first match, passing the captured value 42. The URL configuration chooses the code; it does not decide whether event 42 is published. That is the view’s job.

Where Otahque’s rules run

The view, together with the model code it uses, is where Otahque decides whether event 42 is published, whether Sai may see a registration, or whether a registration request may succeed. The template displays the result of those decisions. A template that hides a Register button is still presentation.

Django also runs shared steps, called middleware, on the way into a request and on the way out with its response. Middleware handles concerns common to many pages, such as attaching the signed-in account to the request or adding security headers to the response. We use it with accounts in Chapter 27 and study it directly in Chapter 39. A middleware step can also return a response itself, in which case the view never runs. It does not replace a view’s event-specific checks.

Prefer the model, view, controller names?

If you have met the model, view, controller pattern elsewhere, Django’s names can seem shuffled. Django’s own documentation describes its division as model, template, and view: Django’s view does much of what other descriptions call a controller, while the framework’s routing machinery does the rest, and the template is the presentation. We use Django’s names, because they are the ones in its files and documentation. The names matter less than the jobs.

Que. 6 A template contains a condition that hides draft events. Is that enough to keep drafts private?

Flip to check your answerFold answer back

Answer. No. The template shows whatever the view supplies. If the view passes a draft’s details, private data has already been selected for a public response, and one mistake in the template would reveal it. The view should select only published events for a public page, and a test should check that a draft is absent from the response.

Que. 7 Does every Django view need a model and a template?

Flip to check your answerFold answer back

Answer. No. A view must return a response. It may build that response from stored records and a template, but a redirect, a short message, or a “not found” response may need neither. The components are tools a view can use, not a checklist every view must follow.

In practice: tracing an unexpected page

Situation. An organizer reports that the address for one event shows a different event’s details.

Application. Follow the request trace: which URL pattern matched, what value it captured, which record the view asked the model for, and which template displayed it. Each step narrows the investigation to one job.

Consideration. The visible page shows only the final result. Confirm each step with the application’s own evidence, such as a test or a log entry, rather than guessing from the screen.

Try it yourself

On paper, write the trace for Raj opening his registration page at the illustrative address /registrations/7/. For each of the URL configuration, view, model, template, and response, write one line saying what it does in this request. Then add the Chapter 2 rule the view must check, and say what Raj should receive if registration 7 belongs to someone else.

Que. 8 What should the trace and the refusal show?

Flip to check your answerFold answer back

Answer. URL configuration: matches /registrations/7/ and calls the registration view with 7. View: identifies the signed-in member, asks the model for registration 7, and checks that it belongs to Raj. Model: reads registration 7 and its event from the database. Template: shows Raj’s status and the event details. Response: 200 with his page. The rule is ownership: a member may see only their own registration.
