5.4 Comparing architecture choices

Sam asks a fair question: “Why build an application at all? A form and a spreadsheet already work for most of our events.” A volunteer suggests the opposite: a separate JavaScript application that talks to Django through an API, as many sites are built today. Both suggestions deserve a reasoned answer rather than an appeal to habit or popularity.

Starting point: the requirements from Chapter 2 and the sketch from Section 5.3. Your output is a comparison of three options against those requirements, with their costs and limits stated.

Compare against requirements, not reputation

An architecture choice is a decision about a system’s main structure that would be expensive to change later. We judge it by the requirements it must serve and the constraints we work under, not by how fashionable a technology is or what a large company uses. A structure that suits a team of fifty may burden a small volunteer project, and the reverse is also true.

Our criteria come from earlier chapters. Organizers and attendees need one current registration record. Ownership and capacity rules must hold whatever a browser sends. The main journeys must work with a keyboard and on narrow screens. A small volunteer team, and a reader learning Django, must be able to build, test, and maintain the result. One constraint is fixed by the book itself: the application uses Django. The open question is the shape of the application.

Three options

Option A keeps the simple workflow from Chapter 1: a hosted form and a spreadsheet, perhaps with automatic copying between them. There is no application code to write or host. Capacity and ownership, however, depend on what the chosen tools allow. We have not evaluated a particular product or configuration, and some tools offer integrations and extra controls, so the comparison describes the basic workflow rather than every hosted service.

Option B is a server-rendered Django application. Server-side rendering means producing complete HTML pages on the server, as traced in Section 5.2, with a database behind the application. The rules run in one place, and pages work with ordinary links and forms. JavaScript can later improve particular interactions without becoming necessary, an approach called progressive enhancement that Chapter 45 develops.

Option C uses Django only to provide data through an API, while a separate JavaScript application builds the pages in the browser. Building pages in the browser this way is called client-side rendering. It suits highly interactive screens and products with several kinds of client, such as a website and a mobile app. It also means two applications, an agreed data format between them, and pages that depend on JavaScript running correctly on each visitor’s device.

The table does not award points, because its rows are not equally important. The first two rows are requirements. The last is not, because nothing in the first release’s scope needs other software to use Otahque.

Read the trade-offs

Option A, in the basic form described here, has not shown that it meets the first two requirements: one current record with capacity and ownership enforced. That is the problem that started the book. A particular tool with extra controls might do better, but it would need evaluating against the same criteria. Option A remains a sensible choice for a community without that problem.

Options B and C can both satisfy the essential rules if built carefully. Option B does so with fewer moving parts, and its pages work before any JavaScript runs. Option C pays now for capabilities the first release does not need, such as serving a mobile app, and doubles the places where a beginner must keep data formats in step. Neither option is modern or old-fashioned; each fits some situations better than others, and many teams mix them, rendering most pages on the server and adding client-side behaviour where it clearly helps.

Option B has limits too, and stating them is part of the comparison. Without enhancement, each action loads a new page, and a highly interactive feature, such as a live seating map, would need extra work. Choosing B now does not rule out an API: Chapters 47 to 54 add one for other software while the HTML pages remain.

Que. 12 Is “most new websites use a JavaScript framework” a good reason to choose Option C?

Show answerHide answer

Answer. No. It describes other projects, not ours. A reason must connect to our requirements or constraints, such as a need for an app that works offline. If a requirement like that appears, it becomes part of the context for a new decision.

Que. 13 Option A needs the least coding effort at the start. Why is it not chosen?

Show answerHide answer

Answer. Because, in the basic form we described, it has not shown that it meets an essential requirement: one current registration record with capacity and ownership enforced. Less coding at the start is not the same as lower total cost, which also includes reconciling records and handling mistakes. Effort and cost decide only between options that meet the requirements; they cannot compensate for missing one.

In practice: answering “why not the other option?”

Situation. Months after a choice, a new contributor asks why the team did not build an API and a mobile-ready client first.

Application. Point to the comparison: the requirements at the time, the options considered, and what each would have cost. The contributor can then judge whether the situation has changed.

Consideration. A comparison records reasoning; it does not prove the choice was right. If the requirements change, revisit the decision rather than defend it.

Try it yourself

A new requirement is proposed: organizers must be able to check attendees in at the venue on a phone with a poor signal. Add it to Table 5.3 as a criterion. For each option, write a short note on how it might cope. Then say whether the new requirement changes the decision for the first release.

Que. 14 How might the options cope, and does the decision change?

Show answerHide answer

Answer. The new criterion is working with an unreliable connection. A: depends on whether the form tool works offline, and its records still need reconciling later. B: each page needs a connection, so a poor signal means slow or failed requests; small pages help, and offline support would need extra work. C: a client application can be designed to store check-ins and send them later, at the cost of handling duplicated or conflicting records. Check-in is deferred from the first release, so the first-release decision stands. The requirement is exactly the kind of change that should prompt a review of the decision when check-in is planned in Chapter 46.
