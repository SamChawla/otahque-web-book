5.1 What Django contributes

Sam has prepared an event, but its details should remain private until publication. Soni visits the public event list to see what she can attend. The server must decide which events belong in that response. In Chapter 4, an if statement could choose a message from a Boolean value. A website needs that decision to work inside a complete request journey.

Starting point: the requirements and Python exercises from earlier chapters; no Django application exists yet. You can complete this section on paper. Its output is an explanation of which work a framework supports and which behaviour we must define and verify ourselves.

A framework gives the application a working structure

A web framework is reusable software that supplies structure and tools for building web applications. Django is a Python web framework. Instead of inventing every common web mechanism, we write application code that works with Django’s components and conventions. A convention is an agreed way of arranging or naming things so that the pieces can work together predictably.

In the small programs from Chapter 4, we started a file and followed its statements to the end. In a web application, incoming requests repeatedly trigger application work. Django provides a way to connect a requested address to the code responsible for its response. We will give those pieces their Django names and trace their interaction in Section 5.2.

Reusing a framework does not remove Python from the picture. Functions still receive inputs and return results. Objects still hold attributes and provide methods. The difference is that some of the objects and calling conventions come from Django, while the application supplies its own behaviour. When a name is unfamiliar, we will separate the Python idea from the framework feature built on it.

Que. 1 Does choosing Django mean that we no longer need the Python skills from Chapter 4?

Show answerHide answer

Answer. No. Django application code still uses Python. Reading a function call, a returned value, an import, or an error message helps us understand how our code works with the framework. Django adds tools and conventions; it does not replace those language concepts.

Place Django inside the server-side application

Chapter 3 separated the browser from the server-side application. That separation still applies. The browser sends a request and interprets the response. Our Python application uses Django on the server side to help produce that response. Installing Django on the development computer does not install Python inside each visitor’s browser.

The diagram shows responsibilities, not a deployment plan. It does not say how many computers we need or which hosting service to use. The two parts inside the application cooperate; they are not two independently deployed services. Storage and other boundaries will be added to the design sketch in Section 5.3.

Que. 2 Soni opens an Otahque page. Does her browser run the Django code shown inside the application box?

Show answerHide answer

Answer. No. Django runs as part of the server-side Python application in this design. Soni’s browser sends the request and receives the response. For a normal page response, the browser interprets the returned HTML, together with the page’s styling and any browser-side scripts.

Separate reusable mechanisms from product rules

Django includes support for matching addresses, producing responses, working with stored data, handling forms, and managing user accounts. These capabilities are useful building blocks. They do not contain the meaning of an Otahque event or the rules agreed for this community. Table 5.1 makes that distinction concrete; it describes future implementation work, not features already built.

For example, knowing which account is signed in does not answer whether that account may edit Sam’s event. Those are different questions. Our requirements assign organizers responsibility for particular events. The implementation must enforce that relationship when handling a request, and our tests must show that a different organizer cannot bypass it.

Likewise, a page can display a Register button while the server must still reject a registration that violates the rules. The button is a way to request an action. It is not proof that the action is allowed. Keeping this distinction clear prevents us from treating a convincing screen as evidence of correct application behaviour.

Que. 3 If an edit button is hidden from another organizer, have we proved that Sam’s event is protected?

Show answerHide answer

Answer. No. Hiding the button changes the interface. A request could still reach the server through another route. The server-side operation must check whether the account may edit that event. Later verification must include a request from an account that lacks that permission.

Useful defaults still need correct use

Django supplies protections against several common web attacks, but their effectiveness depends on how we use and configure the framework. An application-specific rule, such as keeping an unpublished event out of a public response, still needs an implementation and a check. Choosing Django does not establish that Otahque is secure, correct, or ready to deploy.

We will introduce protections alongside the features that need them. At this stage, the useful habit is to ask two questions: what mechanism can the framework supply, and what result must our application guarantee? That habit applies to ordinary mistakes as well as security problems. A correctly delivered page can still show the wrong event.

In practice: reviewing a framework-based feature

Situation. A team uses Django’s account tools and is ready to review who may edit an event.

Application. Ask separately whether the requester is signed in and whether that account may edit this particular event. Use the requirements to define the second answer.

Consideration. Framework support does not establish event ownership rules automatically. A review must include an account that should be refused, as well as the permitted organizer.

Try it yourself

On paper, consider this proposed check: Sam has one published event and one unpublished draft. Soni opens the public event list. State the expected result, identify one task Django can help with, and identify the rule Otahque must enforce. Then explain why seeing the published event alone would be an incomplete check if you had never created a draft for the test.

Que. 4 What should the responsibility split and check show?

Show answerHide answer

Answer. Soni should see the published event and should not receive the private draft’s details. Django can help handle the request and produce the page response. Otahque must apply the visibility rule when choosing what data the response contains. Including both kinds of event in the test lets us check inclusion and exclusion. A test containing only published events cannot expose accidental disclosure of a draft. This is a test scenario on paper, not evidence that an application has passed it.

If your answer says only “Django handles it,” add the exact rule that determines the result. If it says “hide the draft with page styling,” return to the request journey: private data should not be included in a public response and then merely concealed on screen. The purpose of this exercise is to name the responsibility before we write the code.
