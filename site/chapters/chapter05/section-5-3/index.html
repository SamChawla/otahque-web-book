5.3 Sketching the application boundaries

A volunteer developer offers to help Sam maintain Otahque and asks a simple question: “What are the pieces, and what talks to what?” Section 5.2 followed one request through the application. A design sketch answers the volunteer’s question by showing the whole system at once.

Starting point: Sections 5.1 and 5.2, still on paper. Your output is a small proposed architecture sketch with its boundaries labelled, plus a list of what it deliberately leaves out.

What a high-level design is

A high-level design, often shortened to HLD, describes a system’s main parts, how they communicate, and where responsibility and trust change, without the detail of individual functions or tables. It answers “what are the pieces?” before “how is each piece written?”. More detailed documents follow when decisions need them: an entity–relationship diagram for stored data in Chapter 15, and low-level designs for particular features from Chapter 24.

A design sketch is a proposal. Drawing a box does not build it, choose a hosting service, or prove that the parts will cope with any amount of traffic. Its value is that people can review it and find problems while changes are still cheap.

Name the parts that must be running

A useful way to sketch is to name each separately running part. The C4 model, a widely used approach to architecture diagrams created by Simon Brown, calls such a part a container: an application or data store that must be running for the system to work. The word has nothing to do with Docker containers. Otahque’s first release needs only three, plus the files it serves:

  • The visitor’s browser runs on the visitor’s own device. It displays pages and sends requests, and it is outside our control.
  • The Otahque web application is our Django project: the URL configuration, views, models, templates, and Otahque’s rules, running as one Python application on a server.
  • The database stores events, accounts, and registrations so that they survive between requests and restarts. During development we use SQLite, the database a new Django project is configured to use by default and which is included with Python. Chapter 32 moves Otahque to PostgreSQL.
  • Static files are the stylesheets, images, and scripts that are the same for every visitor. The application delivers them alongside its pages; Chapter 13 introduces them.

Static files are not a separate container in this first sketch because the web application delivers them. Production hosting may serve them differently, which is a decision for Chapter 63.

Each connection in the sketch is worth naming. Between the browser and the application travel the HTTPS requests and responses from Chapter 3. Between the application and the database travel queries made through Django’s models; the browser never connects to the database directly. Browser requests therefore reach stored registrations only through the application. Other routes, such as the admin site, maintenance commands, or background work, can also change records later, so every operation that changes a registration must apply the relevant rules. The sketch shows where that responsibility belongs; it does not prove that every route does so.

Mark where trust changes

A trust boundary is a line in a design where data passes between parts under different control. Everything arriving from a browser crosses one. Form fields, addresses, cookies, and headers can be changed by whoever controls the browser, including someone experimenting deliberately. The application must treat that data as untrusted input and check it before relying on it.

The database sits inside the boundary because only our application connects to it. That does not make its contents harmless: an event description typed by an organizer is still text from a person, which is why templates escape it when it is displayed as ordinary page text.

Que. 9 Sai changes the event number in a registration form before submitting it. Which side of the trust boundary is that change on, and what should happen?

Show answerHide answer

Answer. The browser side: everything in the submitted form is untrusted input. The application must check the requested event like any other: that it exists and is published, that registration is open and a place remains, and that Sai has no active registration for it. Editing the form changes what is requested, not what is allowed.

Say what the sketch leaves out

A good sketch is as clear about its omissions as about its contents. This one leaves out email delivery (Chapter 43), background tasks (Chapter 44), an application programming interface, or API, through which other software could use Otahque (Chapters 47 to 54), and the production arrangement of servers, certificates, and backups (Chapters 62 and 63). It does not say how many copies of the application run or how much traffic they can serve. Each later chapter that adds a part will update the design when it makes that decision.

Que. 10 Does the sketch show that Otahque can handle a busy event with hundreds of simultaneous registrations?

Show answerHide answer

Answer. No. It shows parts and connections, not capacity. Chapter 2 left performance targets open until a workload is agreed, and Chapter 33 protects the last place with database transactions. A sketch can show where a check will run; only measurement and tests can show that it works.

In practice: onboarding with a design sketch

Situation. A new contributor wants to fix a bug and asks where to start reading.

Application. Walk through the sketch first: browser, application, database, and the trust boundary. Then point to where each component from Section 5.2 lives in the project. The sketch tells them which part a bug report is likely to concern.

Consideration. Update the sketch when a chapter adds a part, such as email delivery. An out-of-date diagram misleads more than a missing one.

Try it yourself

Copy Figure 5.3 onto paper. Add one future part: reminder emails sent through an outside email service. Draw its connection, label what crosses it, and decide whether the connection crosses a trust boundary. Then name one Otahque rule that must still be applied inside the application rather than by the email service.

Que. 11 What should the extended sketch show?

Show answerHide answer

Answer. Draw the email service outside the server-side boundary, with an arrow from the application labelled with what it sends: a recipient address, a subject, and the message. The service is an external system we do not control, so the connection crosses a trust boundary. The application should send only what the message needs and should treat delivery as uncertain. The rule that stays inside the application is choosing recipients: only members with an active registration for that event receive a reminder. The email service delivers what it is given; it does not know Otahque’s rules. Reminders remain deferred from the first release.
