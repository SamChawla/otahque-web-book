How We Build It

This chapter builds design documents rather than code. Starting point: Chapter 2’s requirements and the responsibilities and request trace from What You Need to Know. Work on paper or in a text file. The steps produce three artefacts: a sketch of the system with its trust boundary, a comparison of three options, and a draft decision record.

The Custom Way: deciding in conversation

Most small projects make their first architecture choice in a chat thread or a meeting. Someone suggests a framework, someone else suggests a different one, and whoever has the most time starts building. That works until a year later, when a new contributor asks why, and the answer is “I think we discussed it once”. The reasons, the options that were rejected, and the conditions under which the choice should change have all gone. The steps below do the same thinking, but leave a record.

The Recorded Way: sketch, compare, record

Step 1: Sketch the application boundaries

A volunteer developer offers to help Sam maintain Otahque and asks: “What are the pieces, and what talks to what?” A high-level design, often shortened to HLD, answers that question. It describes a system’s main parts, how they communicate, and where responsibility and trust change, without the detail of individual functions or tables. More detailed documents follow when decisions need them: an entity-relationship diagram for stored data in Chapter 15, and low-level designs for particular features from Chapter 24. A sketch is a proposal: drawing a box does not build it, choose a hosting service, or prove that the parts will cope with any amount of traffic.

A useful way to sketch is to name each separately running part. The C4 model, a widely used approach to architecture diagrams created by Simon Brown, calls such a part a container: an application or data store that must be running for the system to work. The word has nothing to do with Docker containers. Otahque’s first release needs three, plus the files it serves:

  • The visitor’s browser runs on the visitor’s own device. It displays pages and sends requests, and it is outside our control.
  • The Otahque web application is our Django project: the URL configuration, views, models, templates, and Otahque’s rules, running as one Python application on a server.
  • The database stores events, accounts, and registrations so that they survive between requests and restarts. During development we use SQLite, the database a new Django project is configured to use by default and which is included with Python. Chapter 32 moves Otahque to PostgreSQL.
  • Static files are the stylesheets, images, and scripts that are the same for every visitor. The application delivers them alongside its pages in this first sketch; production hosting may serve them differently, a decision for Chapter 63.

Name each connection. Between the browser and the application travel the HTTPS requests and responses from Chapter 3. Between the application and the database travel queries made through Django’s models; the browser never connects to the database directly. Other routes, such as the admin site, maintenance commands, or background work, can also change records later, so every operation that changes a registration must apply the relevant rules.

Then mark where trust changes. A trust boundary is a line in a design where data passes between parts under different control. Everything arriving from a browser crosses one: form fields, addresses, cookies, and headers can be changed by whoever controls the browser. The application must treat that data as untrusted input and check it before relying on it. The database sits inside the boundary because only our application connects to it, but its contents are still text from people, which is why templates escape it when it is displayed.

Que. 9 Sai changes the event number in a registration form before submitting it. Which side of the trust boundary is that change on, and what should happen?

Answer. The browser side: everything in the submitted form is untrusted input. The application must check the requested event like any other: that it exists and is published, that registration is open and a place remains, and that Sai has no active registration for it. Editing the form changes what is requested, not what is allowed.

Finally, say what the sketch leaves out. This one leaves out email delivery (Chapter 43), background tasks (Chapter 44), an application programming interface, or API, through which other software could use Otahque (Chapters 47 to 54), and the production arrangement of servers, certificates, and backups (Chapters 62 and 63). It does not say how many copies of the application run or how much traffic they can serve.

Que. 10 Does the sketch show that Otahque can handle a busy event with hundreds of simultaneous registrations?

Flip to check your answerFold answer back

Answer. No. It shows parts and connections, not capacity. Chapter 2 left performance targets open until a workload is agreed, and Chapter 33 protects the last place with database transactions. A sketch can show where a check will run; only measurement and tests can show that it works.

In practice: onboarding with a design sketch

Situation. A new contributor wants to fix a bug and asks where to start reading.

Application. Walk through the sketch first: browser, application, database, and the trust boundary. Then point to where each request component lives in the project. The sketch tells them which part a bug report is likely to concern.

Consideration. Update the sketch when a chapter adds a part, such as email delivery. An out-of-date diagram misleads more than a missing one.

Step 2: Compare the architecture choices

Sam asks a fair question: “Why build an application at all? A form and a spreadsheet already work for most of our events.” A volunteer suggests the opposite: a separate JavaScript application that talks to Django through an API. Both deserve a reasoned answer rather than an appeal to habit or popularity.

An architecture choice is a decision about a system’s main structure that would be expensive to change later. We judge it by the requirements it must serve and the constraints we work under, not by how fashionable a technology is. Our criteria come from earlier chapters. Organizers and attendees need one current registration record. Ownership and capacity rules must hold whatever a browser sends. The main journeys must work with a keyboard and on narrow screens. A small volunteer team, and a reader learning Django, must be able to build, test, and maintain the result. One constraint is fixed by the book itself: the application uses Django. The open question is its shape.

Option A keeps the simple workflow from Chapter 1: a hosted form and a spreadsheet, perhaps with automatic copying between them. There is no application code to write or host, but capacity and ownership depend on what the chosen tools allow. We have not evaluated a particular product, so the comparison describes the basic workflow rather than every hosted service.

Option B is a server-rendered Django application. Server-side rendering means producing complete HTML pages on the server, as traced in What You Need to Know, with a database behind the application. The rules run in one place, and pages work with ordinary links and forms. JavaScript can later improve particular interactions without becoming necessary, an approach called progressive enhancement that Chapter 45 develops.

Option C uses Django only to provide data through an API, while a separate JavaScript application builds the pages in the browser, which is called client-side rendering. It suits highly interactive screens and products with several kinds of client, such as a website and a mobile app. It also means two applications, an agreed data format between them, and pages that depend on JavaScript running correctly on each visitor’s device.

The table does not award points, because its rows are not equally important. The first two rows are requirements; the last is not, because nothing in the first release’s scope needs other software to use Otahque. Option A, in the basic form described here, has not shown that it meets the first two requirements, which is the problem that started the book; it remains a sensible choice for a community without that problem. Options B and C can both satisfy the essential rules if built carefully. Option B does so with fewer moving parts, and its pages work before any JavaScript runs. Option C pays now for capabilities the first release does not need and doubles the places where a beginner must keep data formats in step.

Option B has limits too. Without enhancement, each action loads a new page, and a highly interactive feature, such as a live seating map, would need extra work. Choosing B now does not rule out an API: Chapters 47 to 54 add one while the HTML pages remain.

Que. 12 Is “most new websites use a JavaScript framework” a good reason to choose Option C?

Flip to check your answerFold answer back

Answer. No. It describes other projects, not ours. A reason must connect to our requirements or constraints, such as a need for an app that works offline. If a requirement like that appears, it becomes part of the context for a new decision.

Que. 13 Option A needs the least coding effort at the start. Why is it not chosen?

Flip to check your answerFold answer back

Answer. Because, in the basic form we described, it has not shown that it meets an essential requirement: one current registration record with capacity and ownership enforced. Less coding at the start is not the same as lower total cost, which also includes reconciling records and handling mistakes. Effort and cost decide only between options that meet the requirements.

A new requirement is proposed: organizers must be able to check attendees in at the venue on a phone with a poor signal. Add it to Table 5.3 as a criterion. For each option, write a short note on how it might cope. Then say whether the new requirement changes the decision for the first release.

Que. 14 How might the options cope, and does the decision change?

Flip to check your answerFold answer back

Answer. The new criterion is working with an unreliable connection. A: depends on whether the form tool works offline, and its records still need reconciling later. B: each page needs a connection, so a poor signal means slow or failed requests; offline support would need extra work. C: a client application can store check-ins and send them later, at the cost of handling duplicated or conflicting records. Check-in is deferred from the first release, so the decision stands; the requirement should prompt a review when check-in is planned in Chapter 46.

Step 3: Record the decision

In a year, someone will ask why Otahque renders its pages on the server. The volunteers who compared the options may have moved on. A short written record keeps the reasoning available. An architecture decision record, or ADR, is a short document that captures one significant decision, the situation that led to it, and its consequences. Michael Nygard proposed the form in 2011 so that teams would stop losing the reasons behind their designs. A record is usually a page or two, numbered in sequence, and kept with the project’s code.

A useful ADR states a title that names the decision; its status; the context, meaning the requirements, constraints, and pressures at the time; the options considered; the decision; its consequences, both helpful and costly; and the changes that would justify revisiting it. It summarizes the comparison and points to where the detail lives.

The status tells a reader whether to rely on the record. A proposed record is written for review and not yet agreed. An accepted record has been agreed by the people responsible. A rejected record was considered and not adopted; keeping it saves repeating the discussion. A superseded record has been replaced by a later one that links back to it. An accepted record is not rewritten to match a later choice; a new record supersedes it, so the history of the design stays visible.

Que. 15 The team later adds an API so that a partner’s app can list Otahque events. Should they edit the accepted record for the first release so that it seems to have included an API all along?

Flip to check your answerFold answer back

Answer. No. Write a new record for the API decision and link it to the earlier one. If the new decision replaces the old one, mark the old record superseded. If it adds to it, as the planned API in Chapters 47 to 54 would, both records remain valid. Editing the old record would erase the reasoning a future reader needs.

Table 5.4 is our draft. As the project’s first decision record, it is numbered ADR-001. Its status is proposed, because no one responsible for a real Otahque project has reviewed it, and this book does not invent an approval. The following chapters build on this proposal as the working design; if review changes it, a new record will say so.

Notice what the record does not decide: which database runs in production, how the application is hosted, or how pages are styled. Each is a separate decision, recorded when its chapter needs it. One decision per record keeps each record short, reviewable, and easy to supersede. Once the project exists, keep decision records as numbered Markdown files in a folder such as docs/adr/ inside the repository, so that they are versioned with the code; Chapter 8 introduces Git for that purpose.

For you as a reader, the decision means that you begin with one Django project and follow an event request through Python code to a complete HTML page, learning routing, views, templates, and stored records one step at a time, without first building a separate JavaScript application.

In practice: making a disagreement reviewable

Situation. Two contributors disagree about rebuilding the event list with client-side rendering.

Application. Ask the proposer to write a short decision record: context, options, and consequences. The disagreement becomes specific: which requirement does the change serve, and what does it cost?

Consideration. Writing the record does not settle the question. Someone responsible for the project still has to accept or reject it, and the status should say which.
