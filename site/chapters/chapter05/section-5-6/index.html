Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 and L2 check what you have just learned. L3 asks how it works underneath. L4 and L5 ask about the design and leadership decisions that later chapters build on: attempt them now, and return to them when you reach those chapters. Django is not installed until Chapter 6, so the code proofs here are for you to run once it is. Use the readiness checkpoint to decide whether to continue. If an answer is difficult, revisit its worked example and explain the result in your own words. L4 and L5 are extension questions, not a gate to the next chapter.

L1 (Junior): What does Django provide, and what must Otahque’s own code still decide?

What the interviewer is testing: Can you separate a framework’s mechanisms from a product’s rules?

Flip to check your answerFold answer back

Perfect answer: Django provides common web mechanisms: matching addresses to views, request and response objects, templates that escape inserted values, models and queries for the database, forms and validation, accounts and sessions, an administration site, protections such as defence against cross-site request forgery, and a development server. It does not know Otahque’s rules: who may register, how many places an event has, when registration closes, or what cancelling releases. Our code expresses those rules using Django’s tools.

Behind the scenes:

the split in one line of a future view (illustration)

# Django: calls the view and passes the captured event number.
# Otahque: decides what the response may contain, for example
#     events = Event.objects.filter(status='published')
# Chapter 16 defines the model; Chapter 19 writes the query.

Evidence: Table 5.1 and Figure 5.1 show the split for each first-release need.

Common mistakes:

  • “Django handles security, so we need not think about it.”
  • Expecting the framework to define product behaviour.
  • Treating a hidden button as an enforced permission.

Follow-up the interviewer might ask:

  • “Name a rule that Django cannot enforce for you.”
  • “Which Django feature saves Otahque the most work?”

L2 (Mid-Level): Trace a request for /events/42/ through Django.

What the interviewer is testing: Can you name each component a request meets and what each one is responsible for?

Flip to check your answerFold answer back

Perfect answer: The request first passes through middleware, the shared steps every request takes. The URL configuration compares the path with its patterns in order and calls the matching view with 42. The view asks the model for event 42 and checks that it is published; the model queries the database. The view passes the event to a template, which produces the HTML, and returns a response with status 200. The response passes back through middleware on its way to the browser. If no pattern matches, Django returns 404 Not Found, and the view itself decides what to return when the event cannot be shown.

Behind the scenes:

django/core/handlers/base.py (summary)

# get_response(request) runs the middleware chain, then
# _get_response(request):
#     callback, args, kwargs = self.resolve_request(request)
#     response = callback(request, *args, **kwargs)
# resolve_request() asks the URL resolver for the first match.

Code proof (after Chapter 6): the new project’s only route is the admin, so /events/42/ matches nothing yet. In PowerShell, a macOS shell, or Linux/WSL Bash, beside manage.py:

Common mistakes:

  • Saying that the template fetches the data.
  • Forgetting that middleware also handles the response.
  • Assuming every view uses a model and a template.

Follow-up the interviewer might ask:

  • “Where would you check that event 42 is published?”
  • “What happens when no URL pattern matches?”

L3 (Senior): Django describes itself as model, template, view rather than model, view, controller. What do the parts mean, and where is the controller?

What the interviewer is testing: Do you know how responsibilities are divided, rather than only the labels?

Flip to check your answerFold answer back

Perfect answer: The model describes stored records and their rules. The template describes presentation. Django’s view decides which data is presented and returns the response, so it is not the presentation layer that MVC calls a view. Django’s own FAQ suggests that the controller is the framework itself: the machinery that sends each request to the right view according to the URL configuration. What matters is that each kind of decision has one home: rules with models and views, presentation in templates.

Behind the scenes:

where an Otahque rule should live (summary)

# model:    "an event's capacity can never be below zero"
# view:     "this public page shows published events only"
# template: "show the date in the event's own timezone"
# routing:  "/events/<number>/ goes to the event view"

Evidence: Table 5.2 assigns each part one job, and the “Prefer the model, view, controller names?” callout explains the naming.

Common mistakes:

  • Mapping Django’s view onto MVC’s view.
  • Putting business rules in templates.
  • Arguing about labels instead of responsibilities.

Follow-up the interviewer might ask:

  • “Where should the capacity rule live: the view, the model, or the template?”
  • “What goes wrong when templates start making decisions?”

L4 (Staff): Compare server-rendered pages with a separate JavaScript application and an API for Otahque’s first release. Defend a choice.

What the interviewer is testing: Can you weigh options against requirements and constraints instead of fashion?

Flip to check your answerFold answer back

Perfect answer: Server-rendered pages give one application to build, test, and host, keep the rules in one place, and work with ordinary links and forms before any JavaScript, which helps keyboard and narrow-screen use. A separate JavaScript application with an API allows richer interaction, offline work, and reuse by mobile apps, but adds a second codebase, an API to design and secure, and more for a small volunteer team to learn. For the first release’s requirements, server rendering fits better, as ADR-001 proposes. Record when to revisit: a partner or mobile application needs the data, work must continue offline, or measurements miss an agreed performance target.

Behind the scenes:

the comparison, reduced to its deciding rows (summary)

# must meet:  one current record; rules enforced on server
#   A form + spreadsheet  -> not shown
#   B server-rendered     -> yes, one application
#   C API + JS client     -> yes, two applications
# then cost:  B has fewer parts for a small team

Evidence: Table 5.3 and the consequences row of Table 5.4.

Common mistakes:

  • Choosing by popularity.
  • Claiming server-rendered pages can never be interactive.
  • Ignoring the team’s skills and the cost of maintenance.

Follow-up the interviewer might ask:

  • “What evidence would make you revisit the decision?”
  • “How could you add an API later without rewriting the application?”

L5 (Lead): How do you use architecture decision records across a team, and what makes one useful a year later?

What the interviewer is testing: Can you make decisions reviewable and durable, and lead the habit?

Flip to check your answerFold answer back

Perfect answer: Write a record when a decision is significant and costly to reverse. Keep it short: title, status, context, options, decision, consequences, and when to revisit. Store records as numbered files beside the code and review them as you would review code. The status tells readers whether to rely on a record. Never rewrite an accepted record; write a new one that supersedes it and links back. A record is useful a year later because it keeps the context and the options not chosen, so a newcomer understands why the decision was made and can tell when it should be reopened. A lead makes this the normal way to settle significant disagreements and names who accepts each record.

Behind the scenes:

docs/adr/0001-server-rendered-django.md (outline)

# ADR-001: Build the first release as a server-rendered
#          Django application
Status:       Proposed
Context:      ...   Options: A, B, C (Table 5.3)
Decision:     ...   Consequences: ...
Revisit if:   ...   Supersedes: none

Evidence: ADR-001 in Table 5.4 and the status flow in Figure 5.4.

Common mistakes:

  • Writing records afterwards to justify a decision.
  • Recording the decision without the options.
  • Editing an accepted record, or writing records for trivial choices.

Follow-up the interviewer might ask:

  • “Who should accept a decision record?”
  • “How would you notice that a record’s revisit condition has been met?”
