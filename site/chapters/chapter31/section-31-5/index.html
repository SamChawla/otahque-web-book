Checkpoint: Quiz and Challenge

Quiz

Que. 3 Why is the cancellation deadline required to publish, when members may cancel after it anyway?

Flip to check your answerFold answer back

Answer. The deadline does not stop cancelling; it decides how a cancellation is counted. Without it, Otahque could not say which cancellations were late, and Sam’s late count would mean nothing. Requiring it before publication means every published event can answer the question.

Que. 4 register() catches IntegrityError. Why does it look for the member’s place before answering “You already have a place”?

Flip to check your answerFold answer back

Answer. Because an IntegrityError can come from any database rule, not only registration_one_active. Finding the active place proves that the expected rule refused the insert, so the request was a repeat. If no place exists, the error had another cause, and it is raised again instead of being hidden behind a friendly message.

Que. 5 Two copies of Raj’s place are loaded by two requests, and both call cancel(). Why does the count drop by exactly one?

Flip to check your answerFold answer back

Answer. cancel() sends one UPDATE that matches only a row whose status is still active. The database changes the row for the first request and finds nothing to change for the second, whatever each copy in Python says. The second call returns False and the member is told the place was already cancelled.

Que. 6 The attendee list page is at /events/<id>/registrations/. Raj organizes another event. What does he get for Sam’s published event, and for Sam’s draft, and why the difference?

Flip to check your answerFold answer back

Answer. 403 for the published event, because anyone may see that event exists and Raj is simply not allowed to see its list. 404 for the draft, because Raj may not even know the draft exists, so the page answers as if there were none. Both attempts are recorded as refused view_attendees rows.

Mini-Challenge

Que. 7 When registration has not opened yet, the event page lists “Registration has not opened yet.” but does not say when it opens. Make the page say “Registration opens” followed by the time, in the event’s zone, and add a test. Run the test first and watch it fail.

Flip to check your answerFold answer back

Answer. In registrations/templates/registrations/panel.html, after the list of reasons (after </ul>), add:

registrations/templates/registrations/panel.html (after </ul>)

    {% if now < event.registration_opens_at %}
      {% with at=event.registration_opens_at %}
      <p>Registration opens
        {% include "events/when.html" %}.</p>
      {% endwith %}
    {% endif %}

now is already in the event page’s context, and events/when.html shows a time in the event’s zone, with the viewer’s own time when it differs, as the start does. A comparison with a blank opening time is false in a template, so nothing shows for events without one. The test, at the end of registrations/tests.py:

registrations/tests.py (add at the end)

class OpeningTimeTests(TestCase):
    """The event page says when registration opens."""

    def test_the_page_says_when_it_opens(self):
        later = timezone.now() + timedelta(days=1)
        event = soon(registration_opens_at=later)
        page = self.client.get(event.get_absolute_url())
        self.assertContains(page, 'Registration opens')

What We Learned

  • A rule with several conditions is clearer as a list of named reasons, each with a stable code that tests and views compare.
  • Half-open windows include their opening and exclude their closing; tests pass the exact instants on either side.
  • Optional and required times can live on one model: NULL allowed in the database, required at publication, ordered by CHECK constraints with a branch for blanks.
  • A data migration fills existing rows, inside the database with F(), so old records keep their meaning under new rules.
  • An action belongs in a model method inside transaction.atomic(); a database rule stays the backstop for what a check can miss.
  • Catch an expected database error around its own inner atomic(), confirm it is the expected one, and raise anything else again.
  • One conditional UPDATE changes a row exactly once, however many requests try.
  • Register and Cancel are POST only; repeated requests show the result the member already has, and Post/Redirect/Get keeps refresh harmless.
  • Scoped lookups and an owner check answer someone else’s record with 404, and the attempt is recorded.
  • select_related() keeps a list of people at a fixed number of queries.
  • A phone number is stored once, in E.164, with a maintained library; members are told who will see their contact details.
