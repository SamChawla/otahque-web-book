Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead: attempt them now, and return after Chapter 33. They are extension questions, not a gate to the next chapter. Each code proof is a practice file run with uv run python manage.py shell -c "exec(open('NAME').read())"; each rolls back its own changes, so delete it afterwards.

L1 (Junior): Why is a cancelled registration kept instead of deleted?

What the interviewer is testing: Do you see a record as history, and can you name what depends on it?

Flip to check your answerFold answer back

Perfect answer: A registration records that a member held a place, and cancelling changes that fact without erasing it. Keeping the row lets the member see what happened, lets Sam count cancellations and late ones, and lets Chapter 2’s rule hold that history is kept. The count of places uses only active rows, so a kept cancellation costs no place. Registering again makes a new row, so each attempt stays visible, and the database rule allows at most one active row per member and event.

Behind the scenes:

two rows for Raj (summary)

row 1: cancelled, on time   -> kept, not counted
row 2: cancelled, late      -> kept, not counted
places taken                -> active rows only

Code proof: l1_keep.py registers Raj twice and cancels both, the second time late:

l1_keep.py (practice file; delete it afterwards)

"""Proof: a cancelled place is kept, and lateness read."""
from datetime import timedelta

from allauth.account.models import EmailAddress
from django.db import transaction
from django.utils import timezone

from accounts.models import User
from events.models import Event

with transaction.atomic():
    start = timezone.now() + timedelta(days=7)
    event = Event.objects.create(
        title='Practice clinic', starts_at=start,
        ends_at=start + timedelta(hours=1), timezone='UTC',
        location='Online', capacity=2, status='published',
        registration_closes_at=start,
        cancellation_deadline=start - timedelta(days=2),
    )
    raj = User.objects.create_user('raj@example.net',
                                   display_name='Raj')
    EmailAddress.objects.create(user=raj, email=raj.email,
                                verified=True)
    now = start - timedelta(days=3)
    event.register(raj, now).cancel(now)
    late = start - timedelta(days=1)
    event.register(raj, now).cancel(late)
    rows = event.registrations.filter(member=raj)
    print('rows kept:', rows.count())
    print('active now:', rows.active().count())
    print('late:', [place.is_late() for place in rows])
    print(event.registrations.cancellation_counts())
    transaction.set_rollback(True)

Output

rows kept: 2
active now: 0
late: [False, True]
{'cancelled': 2, 'late': 1}

Common mistakes:

  • Deleting the row on cancel, and losing every count that depends on it.
  • Storing “late” in a field that can disagree with the deadline after an edit.
  • Reusing the old row on re-registration, which hides the earlier cancellation.

Follow-up the interviewer might ask:

  • “When would you delete registrations, and who decides?”
  • “How would you show a member their own history?”

L2 (Mid-Level): Soni registers at exactly the closing time, then a moment earlier on a full event. Predict both answers.

What the interviewer is testing: Can you read a boundary rule precisely, and see which reasons apply together?

Flip to check your answerFold answer back

Perfect answer: At exactly the closing time she is refused with closed, because closing is exclusive: registration is open strictly before it. One microsecond earlier the window is open, so on an event with room she would get a place. On a full event, one microsecond earlier, the answer is full. Neither request writes a row, and each answer names its reason, so the page can say “Registration has closed.” or “This event is full.”

Behind the scenes:

open_problems(now) (summary)

now <  opens   -> not_open
now >= closes  -> closed
taken >= cap   -> full

Code proof: l2_predict.py:

l2_predict.py (practice file; delete it afterwards)

"""Proof: the closing instant, and a full event."""
from datetime import timedelta

from allauth.account.models import EmailAddress
from django.db import transaction
from django.utils import timezone

from accounts.models import User
from events.models import Event

TICK = timedelta(microseconds=1)


def member(name):
    """Create a member whose email address is confirmed."""
    user = User.objects.create_user(f'{name}@example.net',
                                    display_name=name)
    EmailAddress.objects.create(user=user, email=user.email,
                                verified=True)
    return user


with transaction.atomic():
    start = timezone.now() + timedelta(days=7)
    closes = start - timedelta(days=1)
    event = Event.objects.create(
        title='Practice clinic', starts_at=start,
        ends_at=start + timedelta(hours=1), timezone='UTC',
        location='Online', capacity=1, status='published',
        registration_closes_at=closes,
        cancellation_deadline=closes,
    )
    soni = member('soni')
    print('a tick before closing:',
          event.registration_problems(soni, closes - TICK))
    print('at closing:          ',
          event.registration_problems(soni, closes))
    event.register(member('sai'), closes - TICK)
    print('full, a tick before: ',
          event.registration_problems(soni, closes - TICK))
    transaction.set_rollback(True)

Output

a tick before closing: []
at closing:           ['closed']
full, a tick before:  ['full']

Common mistakes:

  • Writing now > closes, which lets a request through at the closing instant.
  • Checking the time in the browser, which the member’s device controls.
  • Reporting only the first reason, so a member fixes one problem and meets the next.

Follow-up the interviewer might ask:

  • “Which clock does Otahque trust, and why?”
  • “How would you show the closing time in the member’s own zone?”

L3 (Senior): register() already checks for an existing place. Why keep the unique constraint, and why translate only one error?

What the interviewer is testing: Can you defend defence in depth, and keep an error handler from hiding faults?

Flip to check your answerFold answer back

Perfect answer: The check gives members a clear answer in the ordinary case, but it runs before the insert, and two requests from the same member can both pass it before either writes. Only the database sees every insert, so the partial unique index is the rule that cannot be skipped, by a race, a script, or a future view that forgets. When it refuses, register() confirms that the member now holds a place before calling it a repeat; any other IntegrityError is raised again, so a real fault is reported instead of shown as success.

Behind the scenes:

register() (summary)

atomic:
  problems? -> ValidationError
  atomic: insert
  IntegrityError:
    place found -> already_registered
    no place    -> raise again

Code proof: l3_backstop.py skips the checks, then breaks the save:

l3_backstop.py (practice file; delete it afterwards)

"""Proof: the backstop, and errors it must not hide."""
from datetime import timedelta
from unittest import mock

from allauth.account.models import EmailAddress
from django.core.exceptions import ValidationError
from django.db import IntegrityError, transaction
from django.utils import timezone

from accounts.models import User
from events.models import Event
from registrations.models import Registration

with transaction.atomic():
    start = timezone.now() + timedelta(days=7)
    event = Event.objects.create(
        title='Practice clinic', starts_at=start,
        ends_at=start + timedelta(hours=1), timezone='UTC',
        location='Online', capacity=5, status='published',
        registration_closes_at=start,
        cancellation_deadline=start,
    )
    sai = User.objects.create_user('sai@example.net',
                                   display_name='Sai')
    raj = User.objects.create_user('raj@example.net',
                                   display_name='Raj')
    for person in (sai, raj):
        EmailAddress.objects.create(user=person,
                                    email=person.email,
                                    verified=True)
    now = timezone.now()
    event.registrations.create(member=sai)
    skip = mock.patch.object(Event, 'registration_problems',
                             return_value=[])
    with skip:
        try:
            event.register(sai, now)
        except ValidationError as error:
            print('checks skipped:', error.messages)
    print('active places:', event.places_taken())
    other = IntegrityError('NOT NULL constraint failed')
    with skip, mock.patch.object(Registration, 'save',
                                 side_effect=other):
        try:
            event.register(raj, now)
        except IntegrityError as error:
            print('other error re-raised:', error)
    transaction.set_rollback(True)

Output

checks skipped: ['You already have a place.']
active places: 1
other error re-raised: NOT NULL constraint failed

Common mistakes:

  • Dropping the constraint because “the code already checks”.
  • Catching every IntegrityError as a duplicate.
  • Catching it without an inner atomic(), which leaves the transaction unusable.

Follow-up the interviewer might ask:

  • “Would a ModelForm with fields = ['event'] check the rule?”
  • “How would an API return this refusal?”

L4 (Staff): A registration test passes all day and fails in one evening run. Diagnose it.

What the interviewer is testing: Can you find time-dependent flakiness and remove it by design rather than by retrying?

Flip to check your answerFold answer back

Perfect answer: The test builds an event whose closing time is relative to the real clock, then checks the rules with the real clock again. If the run is slow, or the times fall near midnight or a clock change, the boundary passes between the two readings and the answer flips. The fix is in the design: the rules take now as an argument, and the test passes fixed instants on each side of the boundary. Freezing the clock with a package also works for Python, but not for the database’s own clock, so passing now is the more complete answer.

Behind the scenes:

two readings of the clock (summary)

setup:  closes = clock() + 1 s
check:  clock() later  -> may be after closes
fixed:  check(closes - 1 microsecond) -> always open

Code proof: l4_clock.py asks the same question twice with the real clock, then once with a fixed instant:

l4_clock.py (practice file; delete it afterwards)

"""Proof: a check against the real clock changes answer."""
import time
from datetime import timedelta

from django.db import transaction
from django.utils import timezone

from events.models import Event

with transaction.atomic():
    soon = timezone.now() + timedelta(seconds=1)
    start = soon + timedelta(days=1)
    event = Event.objects.create(
        title='Practice clinic', starts_at=start,
        ends_at=start + timedelta(hours=1), timezone='UTC',
        location='Online', capacity=5, status='published',
        registration_closes_at=soon,
        cancellation_deadline=soon,
    )
    print('real clock, now:  ', event.open_problems(
        timezone.now()))
    time.sleep(1.2)
    print('real clock, later:', event.open_problems(
        timezone.now()))
    fixed = soon - timedelta(microseconds=1)
    print('fixed instant:    ', event.open_problems(fixed))
    transaction.set_rollback(True)

Output

real clock, now:   []
real clock, later: ['closed']
fixed instant:     []

Common mistakes:

  • Rerunning the suite until it passes and calling the failure “flaky”.
  • Freezing Python’s clock while the query uses the database’s now().
  • Fixing one test instead of making every rule take now.

Follow-up the interviewer might ask:

  • “Where would a fixed now be wrong, and the real clock right?”
  • “How would you test a deadline across a daylight-saving change?”

L5 (Lead): Otahque counts places inside a transaction on SQLite. Is capacity safe? What must Chapter 33 change?

What the interviewer is testing: Can you state what a design proves and what it does not, and plan the step that closes the gap?

Flip to check your answerFold answer back

Perfect answer: Not proved. The count and the insert share a transaction, so a failure leaves nothing half-done, but a transaction alone does not stop two requests from both counting one place left and both inserting. SQLite happens to let one writer at a time, which hides the problem in development, and it cannot lock rows, so the fix cannot be shown here either. The unique rule protects against duplicates from one member, not against too many members. On PostgreSQL, Chapter 33 locks the event row with select_for_update() at the top of register(), so a second request waits until the first has committed and then counts again, and proves it with a test that runs two connections at once. Because every caller goes through register(), nothing else changes.

Behind the scenes:

two requests, capacity 1 (summary)

A: count 0 -> room     B: count 0 -> room
A: insert              B: insert
result: 2 places       (Chapter 33: B waits, counts 1)

Code proof: l5_sqlite.py runs both checks before either insert, as two overlapping requests could on PostgreSQL. It is the chapter’s optional lab:

l5_sqlite.py (practice file; delete it afterwards)

"""Proof: what SQLite cannot show about overlapping requests."""
from datetime import timedelta

from allauth.account.models import EmailAddress
from django.db import connection, transaction
from django.utils import timezone

from accounts.models import User
from events.models import Event

print('database:', connection.vendor)
print('can lock rows:',
      connection.features.has_select_for_update)
with transaction.atomic():
    start = timezone.now() + timedelta(days=7)
    event = Event.objects.create(
        title='Practice clinic', starts_at=start,
        ends_at=start + timedelta(hours=1), timezone='UTC',
        location='Online', capacity=1, status='published',
        registration_closes_at=start,
        cancellation_deadline=start,
    )
    people = []
    for name in ('sai', 'soni'):
        user = User.objects.create_user(
            f'{name}@example.net', display_name=name)
        EmailAddress.objects.create(
            user=user, email=user.email, verified=True)
        people.append(user)
    now = timezone.now()
    # Both checks run before either insert, as two
    # overlapping requests could on PostgreSQL.
    print('checks:', [event.registration_problems(p, now)
                      for p in people])
    for person in people:
        event.registrations.create(member=person)
    print('capacity 1, places taken:', event.places_taken())
    transaction.set_rollback(True)

Output

database: sqlite
can lock rows: False
checks: [[], []]
capacity 1, places taken: 2

Common mistakes:

  • Treating atomic() as a lock.
  • Trusting SQLite’s single writer, which PostgreSQL does not share.
  • Adding select_for_update() here, where SQLite ignores it and a test passes for the wrong reason.
