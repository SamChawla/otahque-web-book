How We Build It

Start from Chapter 30, in the folder containing manage.py, with your own .env, the locked environment, 288 passing tests, every migration applied, and the Organizers and Administrators groups. One package is added, django-phonenumber-field. The new files are docs/design/registration.md, registrations/urls.py, seven templates in registrations/templates/registrations/, and five migrations, one of which fills in existing events. The visible result is a Register button on each open event, a “My registrations” link in the menu, and, for organizers, an “Attendee list” link on their events. The commands are written the same for Windows PowerShell, Git Bash, macOS, Linux, and WSL; the chapter’s checks ran in the first two. Each step with new behaviour writes its tests first and runs them to see them fail.

The new tests use helpers from Chapter 30, in_group() and outcome(), and four of their own: verified() makes a member whose email address is confirmed, clinic() Sam’s published clinic with fixed times, soon() the same clinic a week from now, open for registration, and url() the address of a registrations page.

The Custom Way

The registration code in most tutorials counts the places in the view and inserts a row if there is room, often behind a link. Save this practice file as s_count.py beside manage.py, run it with uv run python manage.py shell -c "exec(open('s_count.py').read())", and delete it. It works inside a transaction that it rolls back, so your rows are unchanged:

s_count.py (practice file; delete it afterwards)

"""Practice: the Custom Way, counting before inserting."""
from datetime import timedelta

from django.db import IntegrityError, transaction
from django.utils import timezone

from accounts.models import User
from events.models import Event


def count_then_insert(event, member, counted):
    """Insert a place if the count taken earlier had room."""
    if counted < event.capacity:
        return event.registrations.create(member=member)
    return None


with transaction.atomic():
    start = timezone.now() + timedelta(days=7)
    event = Event.objects.create(
        title='Practice clinic', starts_at=start,
        ends_at=start + timedelta(hours=1), timezone='UTC',
        location='Online', capacity=2, status='published',
    )
    a, b, c = [User.objects.create_user(
        f'{name}@example.net', display_name=name)
        for name in ('ann', 'ben', 'cal')]
    event.registrations.create(member=a)
    # Two requests arrive together; each counts first.
    seen_by_b = event.places_taken()
    seen_by_c = event.places_taken()
    count_then_insert(event, b, seen_by_b)
    count_then_insert(event, c, seen_by_c)
    print('capacity 2, places taken:', event.places_taken())
    try:
        with transaction.atomic():
            count_then_insert(event, b, 0)
    except IntegrityError:
        print('same member twice: refused by the database')
    transaction.set_rollback(True)

Output

capacity 2, places taken: 3
same member twice: refused by the database

Two requests that count before either inserts both see room, and a clinic for two now has three places. The database refused the second place for the same member, because Chapter 21’s unique rule holds whatever the code does, but no rule limits the total. Behind a GET link the code would also run whenever a browser prefetched the link or a chat app built a preview of it. The Django Way keeps the count and the insert inside one transaction in one model method, answers only POST, and states plainly what remains open: on SQLite two overlapping requests cannot be reproduced, so the total under load is proved in Chapter 33.

Step 2: The rules on paper

Before code, write down what Table 31.1 decided in the terms the code will use: each reason by its code, each state of a place, each page, and who sees what. Create docs/design/registration.md:

docs/design/registration.md

# Registration and cancellation: low-level design

Status: Drafted in Chapter 31, for review. Not approved.
Rules: PR-1 (one active place each), PR-2 (cancel your
own place; history kept), PR-3 (no more places than
capacity), PR-4 (own places; organizers see their
events' lists). Timing: Chapter 2, decided 21 November
2026.

## Registration times (on Event)

- registration_opens_at: optional; blank means open as
  soon as the event is published. Inclusive.
- registration_closes_at: needed to publish. Exclusive:
  at that instant registration has closed.
- cancellation_deadline: needed to publish. Cancelling
  stays possible until the start; from the deadline on,
  a cancellation counts as late.
- Opening before closing; closing and deadline no later
  than the start (CHECK constraints). Typed in the
  event's own zone; moved with the start by a copy.

## Who may register, and why not

Event.registration_problems(member, now) returns codes,
checked in this order. Test: RegistrationRuleTests.

| Code               | When                                   |
|--------------------|----------------------------------------|
| already_registered | member holds an active place           |
| not_published      | a draft or a cancelled event           |
| not_open           | before registration_opens_at           |
| closed             | at or after registration_closes_at     |
| full               | active places reach capacity           |
| unverified         | the account email is not confirmed     |
| phone_missing      | phone_required, and no number on file  |

No code: Event.register() makes the place, inside a
transaction. A repeat finds the place and says "You
already have a place". The unique rule
registration_one_active (code already_registered) is the
backstop; only that error is read as a repeat.

## States of a place

| State     | Counts as taken | Shown to the member      |
|-----------|-----------------|--------------------------|
| active    | yes             | You have a place         |
| cancelled | no              | Cancelled, or Cancelled  |
|           |                 | late (from the deadline) |

Lateness is worked out from cancelled_at and the
deadline; no field stores it. Registering again after
cancelling makes a new row, under the same rules.
Registration.cancel(now) changes only an active row, in
one UPDATE: a repeat changes nothing.

## Pages

- POST events/<id>/register/: Register (signed in).
- GET/POST events/<id>/register/phone/: asks once for a
  phone number, keeps it on the Profile, then registers.
- GET registrations/: My registrations.
- GET/POST registrations/<id>/cancel/: confirm, cancel.
- GET events/<id>/registrations/: the attendee list.

## Who sees what

- A member: their own places only. Another member's
  place: 404, recorded as a refused AuditEvent.
- The attendee list (display name, email, phone, time
  of registration; counts of cancellations and late
  ones): the event's current organizers and the
  administrator. Members are told at registration.
- No public attendee list; contacts on no other page.

## Not here

- Two requests at the same moment: Chapter 33.
- Emails to members: Chapters 43-44.
- Waitlist and check-in: Chapter 46.
- Registration questions: Chapter 38; download: 41.

Each row of the reasons table becomes a test in Step 5, and the “Who sees what” list becomes the matrix in Step 11. The note says what is not decided here and where it will be, so a reader of the design is not left guessing.

class RegistrationWindowTests(TestCase):
    """The registration times and their database rules."""

    @classmethod
    def setUpTestData(cls):
        cls.sam = editor()
        cls.event = future_draft(cls.sam)

    def test_the_order_holds_in_the_database(self):
        rows = Event.objects.filter(pk=self.event.pk)
        start = self.event.starts_at
        hour = timedelta(hours=1)
        for changes in (
            {'registration_closes_at': start + hour},
            {'cancellation_deadline': start + hour},
            {'registration_opens_at': start,
             'registration_closes_at': start - hour},
        ):
            with self.subTest(changes=changes):
                with self.assertRaises(IntegrityError):
                    with transaction.atomic():
                        rows.update(**changes)

    def test_blank_times_pass_the_rules(self):
        Event.objects.filter(pk=self.event.pk).update(
            registration_opens_at=None,
            registration_closes_at=None,
            cancellation_deadline=None,
        )
        self.event.refresh_from_db()
        self.event.full_clean()

from django.db import migrations
from django.db.models import F


def fill_window(apps, schema_editor):
    """Close registration at the start of older events.

    Drafts are left blank: publishing asks for both times.
    """
    Event = apps.get_model('events', 'Event')
    Event.objects.exclude(status='draft').filter(
        registration_closes_at=None,
    ).update(registration_closes_at=F('starts_at'))
    Event.objects.exclude(status='draft').filter(
        cancellation_deadline=None,
    ).update(cancellation_deadline=F('starts_at'))


class Migration(migrations.Migration):

    dependencies = [
        ('events', '0006_registration'),
    ]

    operations = [
        migrations.RunPython(
            fill_window, migrations.RunPython.noop
        ),
    ]

For published and cancelled events, registration closes and cancellation becomes late at the start, which is what was true before this chapter: nobody could register after an event began. F('starts_at') copies each event’s own start inside the database, in one UPDATE. Drafts keep blank times, and publishing will ask for them.
