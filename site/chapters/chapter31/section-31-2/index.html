What You Need to Know

Rules as named reasons

Chapter 2 wrote Otahque’s registration rules in plain words, and in November 2026 the user decided the details this chapter builds: when registration opens and closes, what happens to a late cancellation, and who may register. Table 31.1 collects them.

A rule like “you may register” is really several questions, and when the answer is no, the member deserves to know which one failed. Chapter 26 met the same need for publishing: readiness_problems() returns a list of what is missing, and an empty list means ready. This chapter does the same for registering, with one change: each reason has a short code, such as closed or full, as well as a message. Tests and views compare codes, which do not change when the wording does. Figure 31.1 shows the reasons in the order they are checked.

The first two reasons end the list on their own. A member who already holds a place should hear “You already have a place”, not “full”; and on a draft or a cancelled event, nothing else matters. The other reasons are all collected, so a member who is both late and unconfirmed is told both.

Times at the edge

Every time rule has an edge, and the edge must be decided, not left to chance. Chapter 2 chose them: the opening time is inclusive, so a member may register at exactly that instant, and the closing time is exclusive, so at exactly that instant registration has closed. A window that includes its start and excludes its end is called half-open, written [opens, closes). Half-open windows meet without overlapping: one closing at 18:00 and the next opening at 18:00 never both apply.

The cancellation deadline works differently since the user’s decision. Cancelling is always allowed until the event starts, because a place that will not be used should go back to the pool. The deadline only decides how the cancellation is counted: before it, on time; from it on, late. Figure 31.3, in Step 7, puts the four times on one line.

Actions as model methods, inside a transaction

Chapter 22 decided where code like this lives: fat models, thin views. Reads are QuerySet methods, actions are model methods, and a view reads the request, calls one method, and answers. Registering is an action on an event, so it becomes Event.register(member, now), and cancelling an action on a place, Registration.cancel(now). Both take now, the moment the request is decided, rather than reading the clock themselves. The tests, the views, and later the API (Chapter 50) all call the same methods, so the rules cannot drift apart.

New Concept: a transaction around check and write

What problem exists? Registering is two database steps: count the places taken and check the member, then insert a row. If the second step fails, nothing from the first should remain, and nothing in between should be half-done.

What did people do before? Each step was saved on its own, and a failure in the middle left a mess to tidy by hand.

What is it? transaction.atomic() runs a block as one unit: at the end every change is kept, and on an exception every change is undone. Blocks can nest; an inner block becomes a savepoint, which can be undone without undoing the outer block.

Why use it? The check and the write succeed or fail together, and Chapter 33 can add a lock inside the same block without changing anything around it.

Now let’s use it. Step 6 writes register() with an outer block for the whole action and an inner one around the insert.

A transaction alone does not stop two requests from both counting “one place left” before either inserts. Chapter 21 already gave Otahque one rule the database enforces whatever the code does: registration_one_active, at most one active place per member and event. This chapter keeps that rule as the backstop. The method checks first and gives a readable answer; if two requests from the same member slip past the check together, the database refuses the second insert with an IntegrityError.

Catching that error needs care. Django’s transaction documentation is plain about it: do not catch database errors inside an atomic() block, because the block is then broken; wrap the risky statement in its own inner atomic() and catch the error outside that inner block. And not every IntegrityError means “already registered”. A different failure, such as a value the database refuses, must not be reported as a repeat, or a real fault would be hidden behind a friendly message. So register() looks for the member’s active place after the error: if it is there, the request was a repeat; if not, the error is raised again.

Under the Hood: what a savepoint undoes

When the inner atomic() starts, Django asks the database for a savepoint, a named mark inside the open transaction. The insert fails, and Django marks the transaction as broken (PostgreSQL does the same on its side). Leaving the inner block with an exception rolls back to the savepoint, which clears that mark and keeps everything before it. Only then may the outer block run another query, such as looking for the existing place. Catch the error without an inner block and the next query fails with TransactionManagementError, on every database, which is why the rule is “inner block, then catch”.

Safe methods, repeats, and Post/Redirect/Get

HTTP’s specification, RFC 9110, calls GET and HEAD safe: a client may send them without expecting anything to change. Browsers prefetch links, crawlers follow them, and link checkers in chat apps open them to show a preview. A “Register” link would register whoever’s browser opened it, so the specification says that an action reached by GET must be disabled. Register and Cancel are POST forms, protected by the CSRF token from Chapter 24.

POST is not idempotent: sending it twice may do two things. Browsers do not resend it on their own, but people do: a double click, the Back button, a page refreshed after a slow network lost the answer. Chapter 2 asked for these repeats to show the result the member already has. A second Register finds the place and says “You already have a place”; a second Cancel finds the place cancelled and says so. Neither writes anything. OWASP’s testing guide names this kind of check: an action that may be used once per person must be limited on the server, ideally by the database, and tested by repeating the request.

After each POST the view redirects to a page, the Post/Redirect/Get pattern from Chapter 24, so refreshing the page repeats a harmless GET, not the action. And because a released place may be taken by someone else at once, Cancel first shows a confirmation page, as Chapter 26 did for deleting a draft.

Your own records, and an organizer’s list

Chapter 30 named the risk: an IDOR is a page that finds a record by the number in its address and forgets to ask whose it is. A cancel page at /registrations/7/cancel/ is exactly such a page. The defence is the same: look the record up, compare its member with the signed-in member, and answer “not found” when they differ, so the number reveals nothing. Chapter 30’s deny() records the refused attempt.

The attendee list is the opposite case: a page that must show other people’s details, but only to a few. Its rule joins two earlier ones. Sam may open it because he is a current organizer of the event (has_organizer(), Chapter 25); the administrator may open it because the Administrators group holds registrations.view_registration (Chapter 30). Everyone else is refused with 404 when they cannot see the event at all, and 403 when they can. Figure 31.4, in Step 10, shows who sees what.

The list shows each person’s name, email, and phone, so one more rule applies: members are told before they register. The Register button carries one sentence saying that the event’s organizers will see these details. A notice is not consent to anything else; Chapter 65 deals with keeping, exporting, and removing personal data.

New Tool: django-phonenumber-field

What problem exists? Members type phone numbers in many shapes: “98765 43210”, “098765-43210”, “+91 98765 43210”. Stored as typed, the same number looks like three, and a mistyped one is only found when Sam calls it.

What did people do before? A plain text field, perhaps with a pattern that accepted digits, spaces, and a plus sign, and no idea whether the number could exist.

What is it? A Django model and form field built on phonenumbers, the Python port of Google’s libphonenumber. It reads a number, checks it against each country’s numbering plan, and stores it in E.164, the international form: a plus sign, the country code, and the number, such as +919876543210.

Why use it? One stored form, a real validity check, and readable display formats, maintained by others as countries change their plans. Version 9.0.0 declares Django 6.1 support.

Now let’s use it. Step 3 installs it and adds Profile.phone; a number typed without a country code is read as Indian, Otahque’s default region.

A valid number is not a verified one. Otahque never sends a text message, so it cannot know that the number belongs to the member: it is a contact detail the member gave, and the attendee list says no more than that.

Testing time

A test that compares with the real clock gives different answers at different times. Registration that closes “in one hour” is open when the test starts and may be closed when it ends; a test run at 23:59 meets a different day from one run at noon. Chapter 22 avoided this by passing now into upcoming(now). This chapter does the same everywhere: registration_problems(member, now), register(member, now), and cancel(now) take the moment as an argument, and the tests pass exact instants: one microsecond before closing, and exactly at closing.

Packages such as time-machine freeze Python’s clock instead. They work, but they do not change the database’s own clock, and passing now needs no package at all. The page tests still use the real clock, with events far enough away that no boundary is near.
