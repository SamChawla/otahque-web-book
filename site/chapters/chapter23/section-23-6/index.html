Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead to a larger application with a team: attempt them now, and return to them after Chapters 26, 30, and 57. They are extension questions, not a gate to the next chapter. Each code proof is a short file in the practice folder that starts by importing Chapter 16’s setup_django.py; run it from the folder that holds manage.py with uv run python ../practice/ followed by the file name. The proofs only read your rows: any row they create is rolled back.

L1 (Junior): What is the Django admin site for, and who should use it?

What the interviewer is testing: Do you know the admin’s purpose, how a model gets into it, and who it is not for?

Flip to check your answerFold answer back

Perfect answer: The admin site is Django’s built-in tool for viewing and editing the data of registered models, for the people who run an application, not for its users. I register each model with a ModelAdmin in the app’s admin.py, and choose its columns, filters, search, and what may be added, changed, or deleted. Only active accounts with is_staff can sign in, and permissions decide what each one sees. In Otahque, the community administrator uses it to check rows and make corrections, such as granting or revoking organizer access. Members and organizers use Otahque’s own pages, because their work has rules about ownership that the admin does not check per event. I keep every important rule in the model, so it applies in the admin too, and I test the admin’s limits.

Behind the scenes:

the admin site (summary)

admin.py + @admin.register -> pages built from the model
is_active and is_staff     -> may sign in
model permissions          -> what each page allows
full_clean()               -> model rules on every save

Code proof: which models are registered, and which accounts may sign in:

../practice/l1_registered.py

import setup_django
from django.apps import apps
from django.contrib import admin

from accounts.models import User

for model in apps.get_models():
    if admin.site.is_registered(model):
        print(model._meta.label)
staff = User.objects.filter(is_staff=True)
print(list(staff.values_list('email', flat=True)))

Output

admin.LogEntry
auth.Group
accounts.User
events.Event
events.OrganizerAssignment
registrations.Registration
['sam@example.org']

Every model with an admin page, in the order of INSTALLED_APPS, and the one staff account on your computer: Sam’s, from Chapter 18.

Common mistakes:

  • Building members’ or organizers’ pages in the admin because it is quick.
  • Leaving business rules out of the model, so the admin skips them.
  • Treating the admin’s address as its security.

Follow-up the interviewer might ask:

  • “Why does Django not register LogEntry with the admin by default?”
  • “How would you find which admin class a model uses?”

L2 (Mid-Level): Why is a staff flag not a role, and how would you prove it in Otahque?

What the interviewer is testing: Can you separate Django’s access flags from the application’s own roles, and prove the separation?

Flip to check your answerFold answer back

Perfect answer: is_staff answers one question: may this account sign in to the admin site? It grants no page by itself; each page needs a model permission, and is_superuser grants them all. A role, such as an Otahque organizer, is a product idea with its own rules: it applies to particular events, it is granted and revoked by the administrator, and its history is kept. That is why Otahque stores it as an OrganizerAssignment row, and why Otahque’s own pages, not the admin’s flags, will decide what an organizer may do. Using is_staff as the organizer role would let every organizer into the admin and, with a permission, into every event. I prove the separation with a test: a staff account with no permissions sees “no permission to view or edit anything”, gets 403 on the event list, and holds no assignment.

Behind the scenes:

flags and roles (summary)

is_staff              -> sign in to the admin only
model permission      -> one action on one model
is_superuser          -> every permission
OrganizerAssignment   -> organizes one event

Code proof: a staff account with nothing else, created and rolled back:

../practice/l2_staff.py

import setup_django
from django.contrib import admin
from django.db import transaction
from django.test import RequestFactory

from accounts.models import User

with transaction.atomic():
    helper = User.objects.create_user(
        'helper@example.org', display_name='Helper',
        is_staff=True,
    )
    request = RequestFactory().get('/')
    request.user = helper
    print(admin.site.has_permission(request))
    print(admin.site.get_app_list(request))
    print(helper.organizer_assignments.exists())
    transaction.set_rollback(True)
kept = User.objects.filter(email='helper@example.org')
print(kept.exists())

Output

True
[]
False
False

It may sign in, it sees no models, and it organizes no event; the last line shows that the rollback left no account behind.

Common mistakes:

  • Ticking is_staff to make someone an organizer.
  • Giving every staff account is_superuser to save time.
  • Testing that the right person gets in, but not that others stay out.

Follow-up the interviewer might ask:

  • “Where should Otahque check that an organizer may edit an event?”
  • “How would you give the administrator exactly the permissions the role needs?”

L3 (Senior): An event appears hours off on the public page after someone edited it in the admin. What happened, and what do you change?

What the interviewer is testing: Do you understand how typed times are interpreted with USE_TZ, and can you fix the cause rather than the symptom?

Flip to check your answerFold answer back

Perfect answer: With USE_TZ on, Django stores aware datetimes in UTC and reads every typed time in the current time zone, which is TIME_ZONE unless code activates another. Otahque’s TIME_ZONE is UTC, so 15:00 typed for the workshop in Kolkata became 15:00 UTC, which the public page, showing the event’s own zone, displays as 20:30. Nothing was corrupted; the person and the form meant different zones. The immediate fix is to correct the time, typed in UTC. The lasting fixes are to make the zone visible, as Otahque does with help text and a Local start column, and to read typed times in a zone the person chose: Chapter 28 activates each person’s zone for every request, and from Chapter 24 Otahque’s own event form reads typed times in the event’s own zone. I would not change the stored values to local times: one zone in storage keeps comparisons and sorting correct.

Behind the scenes:

typed times (summary)

USE_TZ = True     -> stored in UTC
TIME_ZONE = 'UTC' -> typed times read as UTC
activate(zone)    -> typed times read in that zone
display           -> converted to the event's zone

Code proof: the same text, read in UTC and in Kolkata’s zone:

../practice/l3_typed.py

import setup_django
from zoneinfo import ZoneInfo

from django import forms
from django.utils import timezone

field = forms.DateTimeField()
typed = '2026-12-03 15:00'
as_utc = field.clean(typed)
with timezone.override(ZoneInfo('Asia/Kolkata')):
    as_kolkata = field.clean(typed)
print(as_utc)
print(as_kolkata)
print(as_utc - as_kolkata)

Output

2026-12-03 15:00:00+00:00
2026-12-03 15:00:00+05:30
5:30:00

timezone.override() activates a zone for the block, as Chapter 28’s middleware will for each request. The same text means two instants, five and a half hours apart.

Common mistakes:

  • Storing local times in the database to make the admin “look right”.
  • Setting TIME_ZONE to the administrator’s own zone, which is wrong for every event elsewhere.
  • Fixing the one event and leaving the form unlabelled.

Follow-up the interviewer might ask:

  • “Which zone should an organizer’s form use: the organizer’s, or the event’s?”
  • “What happens to a time typed during the hour that a clock change skips?”

L4 (Staff): The admin’s registration list has become slow as Otahque grows. How do you find the cause and keep it fixed?

What the interviewer is testing: Can you trace a slow admin page to its queries, fix it with the admin’s own tools, and stop it returning?

Flip to check your answerFold answer back

Perfect answer: A slow list usually means a query per row: a column whose text comes from another table, such as a registration’s __str__(), which reads its member and its event, runs two more queries for each row, so the list’s queries grow with the page size. I would confirm it by counting queries, with a query-count test or a database toolbar, rather than guessing. The fix is to join the related rows into the list’s query: list_select_related on the ModelAdmin, select_related() in get_queryset() for an inline, or an annotation for counts, as Otahque’s places column does. Django joins foreign keys named in list_display by itself, but only while they are named, so I set the joins explicitly and guard each page with assertNumQueries. If the list is still slow with a fixed number of queries, the next suspects are counting every row for the paginator, a search across relations without an index, and filters that list every related row; Chapters 56 and 57 measure those.

Behind the scenes:

admin list queries (summary)

__str__ reads relations -> 1 + 2 per row
list_select_related     -> joined into 1
inline get_queryset()   -> select_related
assertNumQueries        -> count stays fixed

Code proof: the registrations’ text, with and without the join:

../practice/l4_queries.py

import setup_django
from django.db import connection
from django.test.utils import CaptureQueriesContext

from registrations.models import Registration

plain = Registration.objects.all()
joined = plain.select_related('event', 'member')
for rows in (plain, joined):
    with CaptureQueriesContext(connection) as queries:
        labels = [str(row) for row in rows]
    print('rows:', len(labels), 'queries:', len(queries))

Output

rows: 3 queries: 7
rows: 3 queries: 1

Three registrations, read plainly, cost one query for the rows and two more for each row’s event and member, seven in all; joined, one.

Common mistakes:

  • Adding database indexes before counting the queries.
  • Fixing the list but not the inline, which has its own query.
  • Removing a column instead of joining what it needs.

Follow-up the interviewer might ask:

  • “What does show_full_result_count change on a large list?”
  • “When would list_per_page or a search on an indexed field matter more than joins?”

L5 (Lead): A teammate proposes letting organizers use the admin site to manage their own events, to save building pages. What do you advise?

What the interviewer is testing: Can you weigh a shortcut against the product’s access rules, and explain the limits of model permissions?

Flip to check your answerFold answer back

Perfect answer: I would start from the requirement: an organizer manages only the events they are assigned to, and only in the ways the product allows. The admin’s permissions are per model: change_event lets an account change every event, so an organizer with it could edit another organizer’s event. Restricting it means overriding get_queryset() and the permission methods to check assignments, hiding fields, and keeping all of that in step with Django’s admin across upgrades, while the admin also shows organizers a tool with more power than they need. It also makes every organizer a staff account, which mixes the two ideas Otahque keeps apart. The pages are not much saved either: an organizer needs a few focused screens, which Chapter 26 builds with forms, ownership checks, and tests. So I would keep the admin for the administrator, and build organizer pages. If time is short, the administrator can make changes on an organizer’s behalf through the admin until those pages exist, and the audit log records each change.

Behind the scenes:

organizers in the admin (summary)

change_event        -> every event, not one
per-event checks    -> custom admin code
staff organizers    -> mixes flags and roles
Chapter 26 pages    -> ownership by assignment

Code proof: an account with change_event, and no assignment, against every event:

../practice/l5_per_model.py

import setup_django
from django.contrib import admin
from django.contrib.auth.models import Permission
from django.db import transaction
from django.test import RequestFactory

from accounts.models import User
from events.models import Event

with transaction.atomic():
    helper = User.objects.create_user(
        'helper@example.org', display_name='Helper',
        is_staff=True,
    )
    helper.user_permissions.add(
        Permission.objects.get(codename='change_event')
    )
    request = RequestFactory().get('/')
    request.user = User.objects.get(pk=helper.pk)
    event_admin = admin.site.get_model_admin(Event)
    for event in Event.objects.all():
        allowed = event_admin.has_change_permission(
            request, event
        )
        print(event, allowed)
    print(helper.organizer_assignments.count())
    transaction.set_rollback(True)

Output

Python meetup True
Django workshop True
Winter social True
Spring planning True
0

The admin would let it change all four events, although it organizes none of them: the permission names a model, not an event.

Common mistakes:

  • Treating the admin as a free front end for a role with ownership rules.
  • Adding per-object checks to the admin without tests for each refusal.
  • Making organizers staff accounts.

Follow-up the interviewer might ask:

  • “If you did restrict the admin per event, which methods would you override?”
  • “How would Chapter 30’s permissions design change your answer?”
