What You Need to Know

What the admin site is, and who it is for

New Tool: the Django admin site

What problem exists? People who look after an application need to read and correct its data, and the application’s own pages show only what visitors and members need.

What did people do before? They typed queries into a database client, or wrote a private page for every table, each with its own list, form, checks, and permissions.

What is it? The admin site is an application that ships with Django, django.contrib.admin. For every model you register with it, it builds a list page, an add page, a change page, a delete page, and a history page, from the model’s fields. It signs people in, checks Django’s permissions, validates with the model’s own rules, and records each change it makes.

Why use it? One configuration class per model gives the administrator a complete, consistent tool, so you spend your effort on the limits rather than on the pages.

Now let’s use it. Step 2 signs in, Steps 4 to 7 register Otahque’s models, and Step 8 writes down where the admin’s job ends.

Django’s documentation is direct about the admin’s purpose: it is an organization’s internal management tool, not the place to build a site’s own pages. That matches Otahque’s plan, and Figure 23.1 shows it. Four kinds of people use Otahque. Visitors read published events. Members have accounts, and from Chapter 31 they register for events and cancel their places. Organizers are members who run particular events, and Chapter 26 gives them pages for those events. The administrator looks after the whole community, and is the only one who uses the admin site.

Three flags on Chapter 17’s user model decide what an account can do in the admin. is_active must be true for the account to sign in at all. is_staff lets an active account sign in to the admin site, and does nothing else: a staff account with no permissions sees an empty page. is_superuser grants every Django permission without listing any. Being an organizer is none of these. It is a row in Chapter 20’s OrganizerAssignment table, which says which member organizes which event, and only Otahque’s own pages will read it. Chapter 18 said a superuser can change everything in the admin site. That is Django’s default, and this chapter narrows it: some refusals in this chapter apply to every account, superusers included, because they are product rules, such as “registrations are history”, and not questions of trust.

Registering a model: ModelAdmin

Until a model is registered, the admin site does not know it exists. Registration pairs a model with a class that describes its pages.

New Concept: ModelAdmin

What problem exists? A generated page needs to know which columns to list, what to search, which fields may be edited, and what is refused.

What did people do before? They wrote each list and form by hand, as The Custom Way below does.

What is it? A ModelAdmin is a class, a subclass of admin.ModelAdmin, whose attributes describe the pages for one model. The decorator @admin.register(Event) registers the model with the class that follows it. Attributes such as list_display choose the list’s columns; methods such as has_delete_permission() answer questions the admin asks while it builds each page.

Why use it? The pages stay Django’s, so they keep working as Django changes, while every Otahque decision lives in one short class beside the app that owns the model.

Now let’s use it. Step 4 writes EventAdmin, and Steps 5 to 7 write one class for each of the other models.

Table 23.1 lists the options this chapter uses. Each is introduced again where a step first needs it.

admin.py in each app is where these classes go. When the project starts, the admin site calls autodiscover(), which imports the admin.py module of every installed app, so a class registered there is found without being imported anywhere else. Your three admin.py files are still the stubs startapp wrote, which is why the admin is empty.

Who may do what: permissions

When Chapter 18 ran migrate, Django created four model permissions for every model, stored in the auth_permission table: add_event, change_event, delete_event, and view_event for events, and the same four for each other model. An account holds a permission directly, or through a group, a named set of permissions. The admin offers a page or a button only when the account holds the matching permission: no delete_registration, no delete button.

A ModelAdmin can narrow that further. has_add_permission(), has_change_permission(), has_delete_permission(), and has_view_permission() are methods the admin calls with each request. By default they check the account’s model permissions; a method that returns False refuses the action for everyone, superusers included. This chapter uses that to state Otahque’s rules once, in code, as Figure 23.2 shows.

Under the Hood: how the admin decides what to show

Every admin page starts with AdminSite.has_permission(), which requires an active account with is_staff; anyone else is sent to the admin’s sign-in page. The index page then asks each registered ModelAdmin for get_model_perms(), a dictionary of the four permission methods’ answers, and lists only models where at least one is true, with an Add link only when adding is allowed. A list page needs view or change permission; when change is refused but view is allowed, the change page becomes a read-only “View” page with no Save button. Bulk actions are filtered the same way: the built-in “Delete selected” action carries allowed_permissions = ('delete',), so it disappears wherever has_delete_permission() says no. A refused request, such as a forged form sent to a read-only page, gets status 403, “Forbidden”, so the rule holds even when the button is not there to press.

Chapter 30 designs Otahque’s groups and permissions. This chapter assigns none: Sam holds them all as a superuser, and the tests in Step 3 create accounts with one permission or none to prove what each sees.

Times in the admin

Chapter 16 stored every event’s start and end as an instant in UTC, with the event’s own zone, such as Asia/Kolkata, in a separate field. Pages show those instants in the event’s zone. The admin does not know that convention. When someone types a date and time into the admin’s form, Django reads it in the current time zone, which is TIME_ZONE in settings, UTC, unless code activates another. So 15:00 typed for the Django workshop in Kolkata is stored as 15:00 UTC, which is 20:30 in Kolkata, five and a half hours later than the organizer meant.

Otahque’s answer in this chapter is to make the mismatch impossible to miss rather than to hide it: the form says “In UTC, not the event’s own time zone” beside each time field, the list shows the start in UTC and again as a “Local start” in the event’s zone, and the change page shows the local start too. If the browser’s zone differs from the server’s, the admin also adds its own note, such as “Note: Enter times in the UTC timezone. (You are 5.5 hours ahead.)”: that note is about your computer’s zone, not the event’s. Each person’s own time zone arrives later: Chapter 27 adds it to a profile, and Chapter 28 activates it for each request, so that pages show times in the viewer’s zone as well as the venue’s.

Forms the admin builds, and the rules they check

The admin’s add and change pages are forms. Django builds each one from the model, as a ModelForm, a form generated from a model’s fields; Chapter 24 writes ModelForms of its own. When someone saves, the form calls the model’s full_clean(), which Chapter 21 wrote rules for: field validators, such as validate_timezone_name(), the model’s clean(), and its constraints, such as “capacity must be more than 0”. So Chapter 21’s messages reach a person for the first time here, beside the field or at the top of the form, and nothing is saved until they pass, as Figure 23.3 shows.

There is one gap, and Step 5 meets it. A form checks only the fields it holds. A field the page shows read-only, or leaves out, is not on the form, and full_clean() then skips any constraint that names that field, because it cannot be sure the value it would check is the one that will be saved. The database still refuses a row that breaks the constraint, but the person sees an error page instead of a message. Step 5 shows the failure, and fixes it for the one model that needs it.

The admin’s change history

Chapter 18’s migrations created a table called django_admin_log. Its model is LogEntry, in django.contrib.admin.models. Every add, change, and delete made through the admin writes one row: who did it, when, which object, as its text at that moment, and, for a change, which fields changed, such as “Changed Location.”. Each object’s page has a History button that lists its rows. Django does not register LogEntry with the admin, so there is no page listing them all; Step 7 adds one, read-only, and calls it Otahque’s audit log.

The log is useful and narrow. It records only what passes through the admin’s pages: changes made in the shell, by scripts, by migrations, or by Otahque’s own pages are not in it, and nor are sign-ins. Its rows are ordinary rows, so anyone who can write to the database can change them. A business audit trail, recording important actions from every part of Otahque, is planned for Chapters 30 and 65.

Try it yourself

Que. 1 A member, Raj, has an account with is_active true and is_staff false, and he opens /admin/. What does he see, and what would change if an administrator ticked is_staff and gave him nothing else?

Flip to check your answerFold answer back

Answer. He is sent to the admin’s sign-in page, and his own email and password are refused there with a message asking for a staff account. With is_staff ticked and no permissions, he could sign in, and the index would say he has no permission to view or edit anything. He would still not organize any event: that needs an organizer assignment.

Prefer the admin site, your own pages, or the shell?

Use the admin site for the administrator’s checks and occasional corrections to individual rows, by one trusted person, with the limits this chapter sets. Write Otahque’s own pages for anything that ordinary users do, or that follows a workflow with rules of its own, such as registering, cancelling, or organizing an event: those pages check who owns what, which the admin’s permissions cannot (the L5 interview question explains why). Use the shell, or a management command written with tests, for changes to many rows at once, and remember that the admin’s log does not see them.

Two more cautions go with that choice. The admin site is a high-value target, because it can change every table: Step 2 moves its address out of the code, and the planned hardening adds two-factor sign-in and more. And because the admin edits rows directly, every rule that matters must already be in the model, as Chapter 21’s are, or it does not apply in the admin.

In practice: a room change the night before

Situation. The library moves the Python meetup to a different room the evening before it starts, and the organizer cannot reach a computer.

Application. The administrator opens the event in the admin site, corrects the location, and saves. Chapter 21’s rules check the change, the public page shows the new room at once, and the audit log records who changed the location and when.

Consideration. The log shows that the location changed, not why, and nobody who had already read the page is told. Telling registered members about changes is a separate feature, planned with Otahque’s emails in later chapters; the admin site is not a messaging tool.
