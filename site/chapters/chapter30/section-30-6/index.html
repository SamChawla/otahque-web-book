Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead: attempt them now, and return after Chapters 50 and 67. They are extension questions, not a gate to the next chapter. L5’s code proof is the chapter’s optional lab.

L1 (Junior): What is the difference between authentication and authorization?

What the interviewer is testing: Can you separate the two, and give an example where one passes and the other fails?

Flip to check your answerFold answer back

Perfect answer: Authentication checks who someone is: a password, a code, a second factor. Authorization checks what that person may do. A member who signs in is authenticated, and may still not create an event, because creating needs a permission they do not hold. In Django, user.is_authenticated answers the first and user.has_perm() and the application’s own rules answer the second. Staff status is neither a role nor a right in Otahque: it only opens the admin.

Behind the scenes:

three people asking to create an event (summary)

visitor     -> not signed in: sent to sign in
member      -> signed in, no add_event: 403
staff only  -> signed in, staff, no add_event: 403

Code proof: l1_who.py:

Output

visitor     signed in: False  may create: False
member      signed in: True   may create: False
staff only  signed in: True   may create: False

Common mistakes:

  • Treating “signed in” as “allowed”.
  • Using is_staff as an application role.
  • Checking authorization only by hiding buttons in templates.

Follow-up the interviewer might ask:

  • “Where does a 401 fit beside 403 and a redirect to sign in?”
  • “How would you test that every page checks authorization?”

L2 (Mid-Level): Raj requests the edit page of Sam’s draft. Predict the response.

What the interviewer is testing: Can you trace a request through a shared check and choose between 404 and 403?

Flip to check your answerFold answer back

Perfect answer: 404. The edit view calls event_to_manage(), which finds the event and asks is_visible_to(Raj). A draft is visible only to its organizers and holders of view_event; Raj is neither, so the answer is the same 404 as for a number with no event, and the draft’s existence stays hidden. For Sam’s published event the answer would be 403, because anyone may see it. Either way, a refused edit_event record names Raj.

Behind the scenes:

one shared check (summary)

draft, not his       -> 404, recorded
published, not his   -> 403, recorded
number with no event -> 404, not recorded

Code proof: the Mini-Challenge’s l2_predict.py:

Output

Raj edits Sam draft : 404
Raj edits Sam meetup: 403
recorded: edit_event refused Sam draft
recorded: edit_event refused Sam meetup

Common mistakes:

  • Answering 403 for a hidden draft, which confirms that it exists.
  • Checking only in the template, so the URL still works.
  • A new view that looks the event up itself instead of through the shared check.

Follow-up the interviewer might ask:

  • “Would random identifiers instead of numbers fix IDOR?”
  • “What should an API return for the same request?”

L3 (Senior): Why does editing need both the Organizers group and an assignment?

What the interviewer is testing: Can you defend a two-part rule with evidence, and say what each part protects?

Flip to check your answerFold answer back

Perfect answer: They answer different questions. The group says whether someone may organize at all; the administrator grants it once, and removing it ends every organizer right at once. The assignment says which events, PR-4’s “organizers manage only assigned events”. Either alone is wrong: the group alone would let every organizer edit every event, and the assignment alone would let an assignment outlive a revoked role. The matrix test proves each row, including the people who must be refused: staff, superusers, and administrators manage no event on Otahque’s pages.

Behind the scenes:

Soni and the book swap (summary)

group, no assignment   -> cannot edit
assignment, no group   -> cannot edit
group and assignment   -> can edit

Code proof: l3_two.py:

l3_two.py (practice file; delete it afterwards)

from datetime import timedelta

from django.contrib.auth.models import Group
from django.db import transaction
from django.utils import timezone

from accounts.models import User
from events.models import Event


def fresh(user):
    """Fetch the user again, without cached permissions."""
    return User.objects.get(pk=user.pk)


with transaction.atomic():
    organizers = Group.objects.get(name='Organizers')
    soni = User.objects.create_user(
        'soni.demo@example.org', display_name='Soni demo')
    start = timezone.now() + timedelta(days=7)
    swap = Event.objects.create(
        title='Book swap', starts_at=start,
        ends_at=start + timedelta(hours=2),
        timezone='UTC', location='Delhi', capacity=20)
    soni.groups.add(organizers)
    print('group only:     ',
          swap.can_be_edited_by(fresh(soni)))
    swap.add_organizer(soni)
    soni.groups.remove(organizers)
    print('assignment only:',
          swap.can_be_edited_by(fresh(soni)))
    soni.groups.add(organizers)
    print('both:           ',
          swap.can_be_edited_by(fresh(soni)))
    transaction.set_rollback(True)

Output

group only:      False
assignment only: False
both:            True

Common mistakes:

  • One “is organizer” flag on the user, which cannot say which event.
  • Letting staff or superusers bypass the rule on the site “for convenience”.
  • Testing only the allowed row, never the refusals.

Follow-up the interviewer might ask:

  • “How would co-organizer invitations change this, and PR-6?”
  • “Where would a community’s own organizers fit (Chapter 67)?”

L4 (Staff): A test adds Soni to Organizers and still gets 403. Diagnose it.

What the interviewer is testing: Can you reason from how Django evaluates permissions to a fix, without weakening the rule?

Flip to check your answerFold answer back

Perfect answer: Django caches a user’s permissions on the user object the first time has_perm() runs, and refresh_from_db() does not clear that cache. If the test asked before adding the group, or the code under test kept the same object, the old answer stays. Fetching the user again gives the new one, and so does a request through the test client, which loads the user afresh. The fix is in the test, not the rule. If the 403 survives a fresh user, check the second condition: is there a current assignment? And is the account active, since has_organizer() now requires it?

Behind the scenes:

one member, one group added (summary)

same object         -> False
refresh_from_db()   -> False
fetched again       -> True

Code proof: l4_cache.py:

l4_cache.py (practice file; delete it afterwards)

from django.contrib.auth.models import Group
from django.db import transaction

from accounts.models import User

ADD = 'events.add_event'
with transaction.atomic():
    soni = User.objects.create_user(
        'soni.demo@example.org', display_name='Soni demo')
    print('before the group:     ', soni.has_perm(ADD))
    soni.groups.add(Group.objects.get(name='Organizers'))
    print('same object:          ', soni.has_perm(ADD))
    soni.refresh_from_db()
    print('after refresh_from_db:', soni.has_perm(ADD))
    soni = User.objects.get(pk=soni.pk)
    print('fetched again:        ', soni.has_perm(ADD))
    transaction.set_rollback(True)

Output

before the group:      False
same object:           False
after refresh_from_db: False
fetched again:         True

Common mistakes:

  • Loosening the rule until the test passes.
  • Clearing private cache attributes instead of fetching the user.
  • Forgetting the assignment, the second half of the rule.

Follow-up the interviewer might ask:

  • “Could the cache ever affect a real request?”
  • “How would you make this failure message clearer?”

L5 (Lead): Should Otahque use django-rules, django-guardian, or its own model methods?

What the interviewer is testing: Can you compare designs by how they fail, and name when you would change your mind?

Flip to check your answerFold answer back

Perfect answer: Model methods, for now, as ADR-004 records. django-rules puts predicates behind has_perm(perm, obj), which reads well, but has_perm() lets every active superuser through before any backend is asked, so every superuser could manage every event on the site. django-guardian stores a permission row per member and object, which would repeat what OrganizerAssignment already holds, and two sources of truth drift apart. Model methods keep the rule beside the data, the same for everyone, with one test per matrix row. I would revisit when the API (Chapter 50) needs the rules in a shared module, or when communities (Chapter 67) bring per-community roles, where a package or a fuller role model may earn its place.

Behind the scenes:

the same draft, two ways to ask (summary)

ModelBackend, organizer       -> False: objects ignored
any backend, superuser        -> True: asked before backends
can_be_edited_by(superuser)   -> False: the same rule as all

Code proof: the optional lab. l5_backend.py writes the smallest object backend, answering events.change_event through can_be_edited_by(), and puts it in place only while the file runs, so your settings are untouched:

l5_backend.py (optional lab; delete it afterwards)

from datetime import timedelta
from unittest import mock

from django.contrib.auth.backends import ModelBackend
from django.contrib.auth.models import Group
from django.db import transaction
from django.utils import timezone

from accounts.models import User
from events.models import Event

CHANGE = 'events.change_event'


class OrganizerBackend:
    """Lab only: answers change_event for one event."""

    def has_perm(self, user, perm, obj=None):
        if perm != CHANGE or obj is None:
            return False
        return obj.can_be_edited_by(user)


with transaction.atomic():
    sam = User.objects.create_user(
        'sam.demo@example.org', display_name='Sam demo')
    sam.groups.add(Group.objects.get(name='Organizers'))
    root = User.objects.create_superuser(
        'root.demo@example.org', display_name='Root demo')
    start = timezone.now() + timedelta(days=7)
    draft = Event.objects.create(
        title='Sam demo draft', starts_at=start,
        ends_at=start + timedelta(hours=2),
        timezone='UTC', location='Leeds', capacity=20)
    draft.add_organizer(sam)
    sam = User.objects.get(pk=sam.pk)
    print('ModelBackend only')
    print('  organizer Sam:', sam.has_perm(CHANGE, draft))
    print('  superuser:    ', root.has_perm(CHANGE, draft))
    backends = [ModelBackend(), OrganizerBackend()]
    with mock.patch('django.contrib.auth.get_backends',
                    return_value=backends):
        print('With the lab backend')
        print('  organizer Sam:',
              sam.has_perm(CHANGE, draft))
        print('  superuser:    ',
              root.has_perm(CHANGE, draft))
    print('can_be_edited_by(superuser):',
          draft.can_be_edited_by(root))
    transaction.set_rollback(True)

Output

ModelBackend only
  organizer Sam: False
  superuser:     True
With the lab backend
  organizer Sam: True
  superuser:     True
can_be_edited_by(superuser): False

With the backend, the organizer is finally allowed through has_perm(), and the superuser is allowed whatever the backend says. That is the reason Otahque does not route its rule this way.

Common mistakes:

  • Adding a package before writing down the rules it must enforce.
  • Keeping the same rule in two places, such as a package and model methods.
  • Choosing role-based access for decisions that depend on one record.

Follow-up the interviewer might ask:

  • “What would make you move the rules into their own module?”
  • “How would you migrate if Otahque later adopted django-rules?”
