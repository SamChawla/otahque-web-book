Checkpoint: Quiz and Challenge

Quiz

Que. 3 Sam is staff and a superuser. Which of Otahque’s roles does that give him?

Flip to check your answerFold answer back

Answer. None by itself. is_staff only opens the admin, and is_superuser holds every Django permission. Otahque’s organizer role needs an assignment to each event, and its administrator role is the Administrators group. Sam organizes his events because he is assigned to them.

Que. 4 Why does Otahque create its groups in a migration instead of in the admin?

Flip to check your answerFold answer back

Answer. So that every database gets exactly the same groups: yours, every reader’s, the test database, and the deployed one. A test then checks their permissions exactly. Groups made by hand in the admin exist only where someone made them.

Que. 5 Why does Otahque not use user.has_perm('events.change_event', event)?

Flip to check your answerFold answer back

Answer. Django’s ModelBackend returns no permissions for an object, so it would always say no, and has_perm() says yes to any active superuser before a backend is asked. Otahque’s rule is in Event.can_be_edited_by(), which asks for the permission and a current assignment, the same questions for everyone.

Que. 6 When does Otahque answer 404, and when 403?

Flip to check your answerFold answer back

Answer. 404 when the person may not see the event at all, such as someone else’s draft, so the refusal reveals nothing. 403 when they may see it but not change it, such as someone else’s published event. A visitor who is not signed in is sent to sign in.

Que. 7 Publishing a draft with no description fails. What does the audit trail record?

Flip to check your answerFold answer back

Answer. Nothing. The rule refuses before anything is saved, and the record shares the action’s transaction, so it is rolled back too. The trail records refused attempts at access, not a member’s mistakes; the message on the page tells them what to fix.

Mini-Challenge

Que. 8 Raj, an organizer of his own event, opens the edit page of Sam’s draft, then of Sam’s published meetup. Predict the two answers and what the audit trail records, then check with l2_predict.py below, run with uv run python manage.py shell -c "exec(open('l2_predict.py').read())".

Flip to check your answerFold answer back

Answer. The draft answers 404: Raj may not see it, so it is treated as if it did not exist. The published meetup answers 403: anyone may see it, but Raj does not organize it. Both attempts are recorded as refused edit_event rows naming Raj. The file undoes its work, so your rows are unchanged:

l2_predict.py (practice file; delete it afterwards)

import logging
from datetime import timedelta

from django.contrib.auth.models import Group
from django.db import transaction
from django.test import Client
from django.test.utils import setup_test_environment
from django.utils import timezone

from accounts.models import User
from audit.models import AuditEvent
from events.models import Event

setup_test_environment()
# Quieten Django's warnings: the status codes say enough.
logging.disable(logging.WARNING)
with transaction.atomic():
    organizers = Group.objects.get(name='Organizers')
    sam, raj = [
        User.objects.create_user(f'{name}.demo@example.org',
                                 display_name=name)
        for name in ('sam', 'raj')
    ]
    for person in (sam, raj):
        person.groups.add(organizers)
    start = timezone.now() + timedelta(days=7)
    events = [
        Event.objects.create(
            title=title, status=status, starts_at=start,
            ends_at=start + timedelta(hours=2),
            timezone='UTC', location='Leeds', capacity=20)
        for title, status in (('Sam draft', 'draft'),
                              ('Sam meetup', 'published'))
    ]
    client = Client()
    client.force_login(raj)
    for event in events:
        event.add_organizer(sam)
        page = client.get(f'/events/{event.pk}/edit/')
        print(f'Raj edits {event.title:10}:',
              page.status_code)
    rows = AuditEvent.objects.filter(actor=raj)
    for row in rows.order_by('id'):
        title = Event.objects.get(pk=row.target_id).title
        print('recorded:', row.action, row.outcome, title)
    transaction.set_rollback(True)

Output

Raj edits Sam draft : 404
Raj edits Sam meetup: 403
recorded: edit_event refused Sam draft
recorded: edit_event refused Sam meetup

The 404 hides the draft’s existence; the 403 hides nothing, because the meetup’s page is public. Both checks happen in event_to_manage(), the one place every event action passes through.

What We Learned

  • Authentication proves who someone is; authorization decides what they may do, and most security mistakes are authorization mistakes.
  • is_staff and is_superuser are Django’s flags, not Otahque’s roles; a staff account may organize nothing, and an organizer needs no admin.
  • Model permissions name actions on a model; Meta.permissions adds custom ones; groups collect permissions into roles given in one step.
  • Groups belong in a data migration, which must create the permission rows first on a new database.
  • Django caches a user’s permissions on the object; fetch the user again after changing groups.
  • A permission is never about one record; Otahque’s rule follows the organizer assignment, in one model method every view calls.
  • has_perm() lets every active superuser through before any backend is asked, which is why the rule is not behind it.
  • IDOR is a page that trusts the number in its address; a shared check, scoped lookups, and a test for every row of the matrix prevent it.
  • The rule for organizer access lives in the models, so the admin and the Organizer access page refuse the same cases, including removing the last organizer.
  • An administrator who may change users must not be able to change their own permissions or join Administrators.
  • An audit record says who did what to which record, and whether it was allowed; it shares the action’s transaction and is kept apart from logs.
