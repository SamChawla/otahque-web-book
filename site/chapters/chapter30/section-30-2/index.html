What You Need to Know

Who you are, and what you may do

Authentication answers “who are you?”. Chapters 27 to 29 built it: sign-up, sign-in, sign-in codes, and two factors. Authorization answers “may you do this?”. A signed-in member is authenticated, but that alone gives no right to edit anything. Most security mistakes in web applications are authorization mistakes: the person is exactly who they claim, and the application lets them do something it should not.

Django’s user model carries two flags that look like roles and are not. Chapter 17 explained them: is_staff only lets an account open the admin site, and is_superuser grants every Django permission at once. Otahque’s roles are different: an organizer may manage the events assigned to them, and the administrator decides who organizes. Chapter 23 proved that a staff account can organize nothing, and from Chapter 26 organizers have worked without being staff. This chapter keeps the flags apart from the roles, and Table 30.1 lists the roles.

Permissions and groups

Django gives every model four model permissions when it is migrated: add, change, delete, and view. Chapter 23 used them in the admin, and Chapters 24 and 25 used two of them on Otahque’s pages: creating an event needs events.add_event, and editing needs events.change_event. A permission is named app_label.codename, and user.has_perm('events.add_event') asks whether a user holds it.

A model can also declare its own permissions, for actions that are not add, change, delete, or view. This chapter adds one: manage_organizers, “Can manage organizer access”, on OrganizerAssignment. It names the right to open the page where organizers are added and removed, which is neither adding nor changing an assignment in the admin.

New Tool: Django groups

What problem exists? Each organizer needs the same two permissions, and each administrator the same dozen. Ticking them for each person is slow, easy to get wrong, and hard to review: nobody can see at a glance what “an organizer” may do.

What did people do before? Permissions were given to each user, and roles lived in a spreadsheet or in someone’s memory.

What is it? A Group, from django.contrib.auth, is a named set of permissions. A user in a group holds every permission the group holds, as if each had been given to them directly.

Why use it? A role is written down once, as a group, and giving the role is one step: add the member to the group. Removing them takes the role away just as quickly.

Now let’s use it. Step 4 creates Organizers and Administrators with a migration, so that every database, including the test database, has them.

Groups need care in one place. Django creates its permission rows after the last migration has run, so a new database has none while the migrations are running. A migration that looks permissions up must first ask Django to create them. Step 4 does this, and its Common Error shows what happens otherwise.

Under the Hood: permissions are remembered

The first time has_perm() runs for a user object, Django reads all of that user’s permissions from the database and keeps them on the object. Later calls on the same object do not read the database again. That is fast, and it means that adding a member to a group does not change what the same Python object answers. Even refresh_from_db() keeps the old answer. Fetch the user again, and the new answer appears. Each request fetches the user afresh, so the website is never affected: this catches tests and shell sessions. Step 5 shows it.

Rules for one object

A permission is about a model, never about one row. events.change_event says “may change events”, not “may change this event”. Otahque’s rule needs both: Sam may edit the clinic because he holds the permission and organizes it. Figure 30.1 shows the two questions, each answered in its own place.

Django’s has_perm() accepts an object, user.has_perm('events.change_event', event), but it does not answer the second question. Its standard backend, ModelBackend, returns no permissions at all when it is given an object. Django leaves rules for one object to other backends, and packages such as django-rules and django-guardian provide them.

New Concept: a rule that follows a relationship

What problem exists? “Organizers manage their own events” depends on a link between a person and a row. A list of roles cannot say which row.

What did people do before? Each view compared the event’s owner with the signed-in user, and each new view had to remember to.

What is it? A check that follows the relationship already in the data: OrganizerAssignment links a member to an event, so “does Sam organize the clinic?” is one query. OWASP’s Authorization Cheat Sheet recommends such relationship-based checks over role lists for decisions about single records.

Why use it? The rule lives where the data lives, it changes when an assignment changes, and every view can ask it the same way.

Now let’s use it. Otahque’s rule already works this way, in Event.has_organizer() and Event.can_be_edited_by(). Step 6 proves it row by row and closes one gap.

Under the Hood: the superuser shortcut

user.has_perm() answers True for any active superuser before it asks a single backend. That is how the superuser holds every permission. It also means that if Otahque moved its rule behind has_perm('events.change_event', event), every superuser could manage every event on Otahque’s pages, whatever the rule said. Chapter 25 decided that staff without an assignment use the admin instead. So Otahque keeps its rule in model methods, where the superuser is asked the same questions as everyone else. The optional lab in the interview’s L5 proves the shortcut.

Refusing without revealing: IDOR, 404, and 403

An insecure direct object reference, or IDOR, is a page that finds a record by the number in its address and forgets to check that the person may see it. Raj changes 7 to 8, and the page shows him Sam’s draft. Nothing was broken into; the page simply never asked. OWASP’s guidance is to check each object on every request, through one shared check, and to test with several accounts. Figure 30.2 follows Raj’s attempt.

Chapter 25 chose the answers, and OWASP’s IDOR cheat sheet gives the same advice. When the person may not even see the event, the answer is 404 Not Found, exactly what a number with no event gets, so the refusal reveals nothing. When they may see it but not change it, as with a published event that is not theirs, the answer is 403 Forbidden. A visitor who is not signed in is sent to sign in first.

A permission matrix writes every one of these answers down: a row for each kind of person, a column for each action. Figure 30.3 is Otahque’s matrix for Sam’s draft. Step 6 turns it into a test that runs every row.

Read the administrator’s row. The administrator holds view_event, so the draft opens, but holds no assignment, so editing and publishing are refused. The superuser’s row is the same, except that the superuser may create events, because a superuser holds every permission. Neither can manage the draft on Otahque’s pages: that is the rule from Figure 30.1 at work.

Who did what: an audit trail

When something goes wrong, someone asks who did it. Otahque needs an answer for three kinds of action: changes to who may organize, actions on events, and attempts that were refused. An audit record answers it: who acted, what they did, to which record, whether it was allowed, and when. Figure 30.4 shows how it differs from the two kinds of log Otahque already has or will have.

New Concept: the audit record

What problem exists? The admin log covers the admin only, and diagnostic logs are written for developers, mixed with errors and requests, and thrown away after a while.

What did people do before? People searched server logs, or asked around.

What is it? A table of facts about decisions: AuditEvent, with an actor, an action, an outcome of allowed or refused, a target such as an event, a small detail, and a time. Rows are added and never changed.

Why use it? An administrator can answer “who removed Sam?” in the admin, and refused attempts, such as Raj’s, show where someone tried a door.

Now let’s use it. Step 2 builds the app, and Steps 7 to 10 write to it.

Each record is written inside the same database transaction as the action it describes. If the action fails, its record disappears with it, so the trail never claims something that did not happen. Records hold names and numbers, never private values: an edit records which fields changed, not what they held. And they are ordinary rows: anyone with access to the database could change them, so they are evidence, not proof. Chapter 65 decides how long they are kept, what is removed from them, and who is alerted.
