Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead, to debugging and to choices under load. They are extension questions, not a gate to the next chapter. Practice files are run with uv run python manage.py shell -c "exec(open('NAME').read())" and deleted afterwards; each undoes its own changes.

L1 (Junior): What does a transaction guarantee, and what does it not?

What the interviewer is testing: Can you tell atomicity from isolation?

Flip to check your answerFold answer back

Perfect answer: A transaction guarantees that its changes are kept or undone together: if a later step fails, the earlier ones are rolled back, and other transactions never see half of it. It does not guarantee that what it read stays true while it works. Other transactions run at the same moment, and under PostgreSQL’s default, READ COMMITTED, each statement sees whatever was committed before it began. A decision based on an earlier read, such as “one place left”, can be wrong by the time it is acted on, unless something, such as a row lock, makes others wait.

Behind the scenes:

a transaction (summary)

atomic()        all changes kept, or all undone
READ COMMITTED  each statement sees committed data
row lock        others wait for this row until commit

Code proof: l1_atomic.py undoes a change when a later step fails, and asks PostgreSQL for the isolation level:

l1_atomic.py (practice file; delete it afterwards)

"""Show what a transaction keeps, and what it reads."""
from django.db import connection, transaction

from events.models import Event

event = Event.objects.get(title='Python meetup')
before = event.capacity
try:
    with transaction.atomic():
        Event.objects.filter(pk=event.pk).update(
            capacity=before + 9
        )
        raise RuntimeError('a later step failed')
except RuntimeError:
    pass
after = Event.objects.get(pk=event.pk).capacity
print('undone after the failure:', after == before)
with connection.cursor() as cursor:
    cursor.execute('SHOW transaction_isolation')
    print('isolation level:', cursor.fetchone()[0])

Output

undone after the failure: True
isolation level: read committed

Common mistakes:

  • Believing atomic() alone stops two requests from both seeing one place.
  • Turning on SERIALIZABLE for everything without handling the errors it raises.

Follow-up the interviewer might ask:

  • What does REPEATABLE READ change? (Every statement sees the data as at the transaction’s first statement; a conflicting update raises an error instead of waiting.)
  • Does the lock block someone who only views the event page? (No: plain reads are never blocked by a row lock.)

L2 (Mid-Level): Predict the result of two registrations for the last place, without a lock

What the interviewer is testing: Can you step through an interleaving and predict it exactly?

Flip to check your answerFold answer back

Perfect answer: Both get a place. Each request counts the active places and sees none for the other, because the other’s insert is either not done or not committed. Both pass the “full” check, both insert, and both commit. The one-active-place rule does not help, because it is one place per member, and they are different members. The event ends with two places for a capacity of one. The test makes this happen every time by meeting after the count.

Behind the scenes:

the interleaving (summary)

Sai counts 0   Raj counts 0
Sai inserts    Raj inserts
2 places, capacity 1

Code proof: the race test of Step 3, run before the lock:

Output

AssertionError: Element counts were not equal:
First has 2, Second has 1:  'place'
First has 0, Second has 1:  ['full']

Common mistakes:

  • Expecting the database to refuse the second place: no rule compares a count with capacity.
  • Expecting the second request to see the first’s uncommitted insert.

Follow-up the interviewer might ask:

  • Could a CHECK constraint stop it? (Not on a count across rows; a counter column with a CHECK could, at the price of a second copy of the count.)
  • What changes with three requests? (The same: each counts before any insert, so all three get places.)

L3 (Senior): Defend locking the event row instead of keeping a counter column

What the interviewer is testing: Can you weigh two correct designs and pick one for this product?

Flip to check your answerFold answer back

Perfect answer: A counter column, such as places_taken, updated with F() and limited by a CHECK constraint, also prevents overselling, and it can be faster under heavy load. But it is a second copy of a fact the registrations already hold: every place given, cancelled, or moved by an administrator must keep it in step, forever. Locking the event row keeps one source of truth, the rows themselves, and puts the rule in one method. Otahque’s events take tens of registrations, not thousands per second, and the lock is held for milliseconds. The decision is recorded with a trigger to revisit it: Chapter 66 measures lock waits under load.

Behind the scenes:

two designs (summary)

counter column  fast, a second copy to keep in step
row lock        one source of truth, requests take turns
Otahque         row lock; measure in Chapter 66

Code proof: l3_sql.py shows the two statements register() sends first, then undoes everything:

l3_sql.py (practice file; delete it afterwards)

"""Show the SQL register() sends first, then undo it."""
from django.core.exceptions import ValidationError
from django.db import connection, transaction
from django.test.utils import CaptureQueriesContext
from django.utils import timezone

from accounts.models import User
from events.models import Event

event = Event.objects.get(title='Leeds meetup')
soni = User.objects.get(email='soni@example.org')
with (transaction.atomic(),
      CaptureQueriesContext(connection) as seen):
    try:
        event.register(soni, timezone.now())
    except ValidationError as error:
        print('answer:', error.messages)
    transaction.set_rollback(True)
for query in seen:
    sql = query['sql']
    if 'lock_timeout' in sql or 'FOR UPDATE' in sql:
        print(sql if len(sql) < 50 else sql[:24] + ' ... '
              + sql[-24:])

Output

answer: ['You already have a place.']
SET LOCAL lock_timeout = '3s'
SELECT "events_event"."i ...  = 7 LIMIT 21 FOR UPDATE

Common mistakes:

  • Locking the registration rows instead of the event: a new place has no row yet to lock.
  • Locking the whole table: every event’s registrations would wait for each other.

Follow-up the interviewer might ask:

  • When would you choose the counter? (When measurements show lock waits dominate, as with ticket sales at very high volume.)
  • What about ON CONFLICT in PostgreSQL 19? (It handles duplicates of one key, not a count against capacity.)

L4 (Staff): A race test always passes, even with the lock removed. Diagnose it

What the interviewer is testing: Can you find why a test proves nothing?

Flip to check your answerFold answer back

Perfect answer: First, check the test’s base class. In a TestCase nothing is ever committed, so a second thread cannot see the test’s event: it fails inside the thread, and if the assertion only checks that “at most one place” exists, it passes. Second, check where the threads meet. If they start together but nothing makes them overlap, one usually finishes before the other counts, and the test passes by timing. The fix is TransactionTestCase, one connection per thread, and a meeting point right after the count. Then remove the lock and confirm the test fails: a test that has never failed has not been proved.

Behind the scenes:

a race test (summary)

TestCase             never commits: threads see nothing
no meeting point     overlap by luck
TransactionTestCase  + meeting after the count: certain

Code proof: l4_testcase.py is the race test’s setup written as a TestCase. Save it in registrations/, run it as a test, and delete it:

registrations/l4_testcase.py (practice file; delete it afterwards)

"""Practice: the race test written as a TestCase."""
from django.test import TestCase

from events.models import Event
from registrations.tests import at_once, soon


class InsideOneTransactionTests(TestCase):
    """A TestCase never commits, so threads see nothing."""

    def test_another_thread_looks_for_the_event(self):
        event = soon(capacity=1)
        print('another thread sees the event:', at_once(
            lambda: Event.objects.filter(pk=event.pk).exists()
        ))

Terminal

uv run python manage.py test registrations.l4_testcase

Output

Found 1 test(s).
another thread sees the event: [False]
Ran 1 test in 0.051s
OK

Common mistakes:

  • Adding time.sleep() to make the race likely: slower, and still luck.
  • Never running the test without the fix, so nobody knows it can fail.

Follow-up the interviewer might ask:

  • Why does TransactionTestCase remove the groups? (It empties every table after each test, and nothing makes the groups again; only content types and permissions are recreated.)
  • How would you test two real processes? (Two runserver workers and concurrent HTTP requests, in Chapter 66.)

L5 (Lead): Defend “busy, try again” with no retry loop, and say where SERIALIZABLE would be right

What the interviewer is testing: Can you choose failure behaviour under load, and know when a stronger tool fits?

Flip to check your answerFold answer back

Perfect answer: A wait without a limit lets one stuck request hold every other request for the same event, and a website should answer quickly even when the answer is “not now”. So the wait is limited to three seconds, and then the member is told Otahque is busy, with nothing changed. A hidden retry loop would hide that the system is overloaded, repeat work, and can make a pile-up worse; a person pressing the button again is a natural, visible retry. SERIALIZABLE isolation is the right tool when a rule spans many rows that no single row can stand for, such as “no organizer runs two events at overlapping times”. Then PostgreSQL detects conflicts itself, and every caller must be ready to retry a serialization failure. For one event’s capacity, the event row stands for the rule, so a row lock is simpler. Chapter 66 measures before anything changes.

Behind the scenes:

failure under load (summary)

wait     at most LOCK_TIMEOUT, this transaction only
then     "busy", nothing changed, no retry loop
later    measure in 66; SERIALIZABLE for multi-row rules

Code proof: l5_timeout.py shows that the limit lasts one transaction and is gone after it:

l5_timeout.py (practice file; delete it afterwards)

"""Show that the lock's time limit lasts one transaction."""
from django.db import connection, transaction

from events.models import Event


def lock_timeout():
    """Return the connection's lock_timeout now."""
    with connection.cursor() as cursor:
        cursor.execute('SHOW lock_timeout')
        return cursor.fetchone()[0]


event = Event.objects.get(title='Python meetup')
with transaction.atomic():
    event.locked()
    print('inside the transaction:', lock_timeout())
print('after it:', lock_timeout())

Output

inside the transaction: 3s
after it: 0

Common mistakes:

  • Setting lock_timeout for the whole server, which PostgreSQL’s documentation advises against.
  • Retrying automatically after a timeout without a limit or a delay.

Follow-up the interviewer might ask:

  • Why three seconds? (Long enough for many turns of a millisecond lock, short enough for a person; Chapter 66 checks it with measurements.)
  • What would the admin show if it timed out? (The admin does not set the limit; it waits, which is acceptable for one administrator and is stated in the design note.)
