Checkpoint: Quiz and Challenge

Quiz

Que. 3 register() was already inside transaction.atomic() in Chapter 31. Why did that not stop the clinic from being oversold?

Flip to check your answerFold answer back

Answer. A transaction keeps its own changes together; it does not stop another transaction from reading at the same time. Under READ COMMITTED, each request’s count saw only committed places, so both saw one left before either inserted. The row lock makes the second request wait until the first has committed, so its count sees the first place.

Que. 4 Why does register() check event, the row from locked(), and not self?

Flip to check your answerFold answer back

Answer. self is the copy the view loaded at the start of the request. By the time the lock is granted it may be cancelled, edited, or full. The locked row is the newest committed version, and nobody can change it until the transaction ends, so checks on it stay true until the insert.

Que. 5 locked() turns an OperationalError into “busy” only when its cause has the code 55P03. What would go wrong if it caught every OperationalError?

Flip to check your answerFold answer back

Answer. A lost connection or a server shutting down would also be shown as “Otahque is busy. Please try again.” The member would retry for ever and nobody would see the real fault in the logs. Only the expected error becomes a friendly answer, as with IntegrityError in Chapter 31.

Que. 6 Sam opens the edit page at version 4. Raj publishes the event. Sam saves. Is Sam’s save refused?

Flip to check your answerFold answer back

Answer. No. Publishing does not change the version, because the edit form has no status field: Sam’s save cannot undo Raj’s publish. The version grows only with saves of the edit page and the admin’s event form, the two places that write the form’s fields.

events/models.py (replace delete_draft())

    def delete_draft(self):
        """Delete a draft nobody registered for.

        Reads the status under the lock, like publish().
        """
        with transaction.atomic():
            event = self.locked()
            if event.status != self.Status.DRAFT:
                raise ValidationError(
                    'Only a draft can be deleted.'
                )
            if event.registrations.exists():
                raise ValidationError(
                    'This draft has registrations, so it '
                    'is kept.'
                )
            event.organizer_assignments.all().delete()
            event.delete()

What We Learned

  • A transaction keeps changes together; it does not stop others from reading at the same time.
  • Under READ COMMITTED each statement sees what was committed before it began, so “count, then insert” can race.
  • select_for_update() inside atomic() locks a row until commit; other requests for the same row take turns, and plain reads and other rows are not affected.
  • Every check after the lock reads the locked row, never a copy loaded earlier.
  • SET LOCAL lock_timeout bounds the wait; only the lock-not-available error becomes “busy”, and there is no hidden retry.
  • A race test needs TransactionTestCase, one connection per thread, and a meeting point placed after the count; then it fails every time without the fix.
  • TransactionTestCase empties the tables after each test, including rows a data migration made.
  • A version number refuses a save from a page that is out of date; the lock and the version solve different problems and can work together.
