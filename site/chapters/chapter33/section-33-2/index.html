What You Need to Know

What a transaction promises

Chapter 31 put register() inside transaction.atomic(). A transaction promises that its changes are kept together or undone together: if the insert fails, nothing of the request remains. It does not promise that the data it read stays true. Two transactions can run at the same moment, and each sees the world as it was when its statement started.

PostgreSQL’s default isolation level, the rule for what one transaction sees of another, is READ COMMITTED: each statement sees every change that was committed before it began, and nothing that is not yet committed. So when Sai’s request counts, it sees no place for Raj, whose insert has not happened; when Raj’s request counts, it sees none for Sai, whose insert has happened but is not committed yet. Both counts are correct for the moment they were made. The decision built on them is wrong. Figure 33.1 shows the two requests side by side.

This interleaving is called a race: the result depends on which request happens to run first, and on timing nobody controls. Races are rare on a quiet site and certain on a busy one, which is the worst kind of bug: it passes every manual check.

Locking a row

New Concept: a row lock with select_for_update()

What problem exists? Two requests must not both decide on “one place left”. The second must decide after the first has finished.

What did people do before? Counters in a separate table, locks on the whole table, or “hope it is rare”. Each either slowed everything or failed under load.

What is it? Event.objects.select_for_update().get(pk=...) reads the event row and locks it until the transaction ends. Any other transaction that asks to lock or change the same row waits. Plain reads are not blocked, and other events are not affected.

Why use it? It makes requests for one event take turns, exactly where the decision is made, and nowhere else. The count stays where it is: the real rows.

Now let’s use it. Step 4 adds Event.locked() and calls it first in register().

Two details decide whether the lock helps. First, it only works inside a transaction: outside one, Django refuses with TransactionManagementError. Second, the decision must be made on the row the lock returned. When the waiting request finally gets the lock, PostgreSQL hands it the newest committed version of the row. A copy of the event that a view loaded a moment earlier may already be out of date: cancelled, edited, or full. So every check runs on the locked row.

Under the Hood: what the waiting request sees

When Raj’s request asks to lock a row that Sai’s transaction holds, PostgreSQL makes it wait. As soon as Sai’s transaction commits, PostgreSQL gives Raj’s request the row as it is now, not as it was when Raj’s statement started, and the lock passes to him. His next statement, the count, is a new statement, so under READ COMMITTED it sees Sai’s committed place. That is why the order “lock, then count, then insert” works: the lock decides who goes first, and READ COMMITTED makes sure the second sees what the first did.

A waiting request should not wait forever. PostgreSQL’s lock_timeout setting ends a wait after a limit, and SET LOCAL sets it for one transaction only. When the limit is reached, PostgreSQL stops the statement with the error code 55P03, “lock not available”. Otahque turns exactly that error into “Otahque is busy. Please try again.” and changes nothing. Any other database error is still raised, as Chapter 31 did with IntegrityError.

Testing a race

A race test needs two requests running at once, on two connections, each seeing what the other has committed. Django’s TestCase cannot do that: it runs each test inside one transaction that is never committed, so another connection sees nothing of the test’s rows. `TransactionTestCase` commits for real and empties the tables after each test instead. Each thread, a second line of execution inside the same Python program, gets its own database connection, as a second request would.

Starting two threads together is not enough. They might run one after the other, and the test would pass by luck. A barrier (threading.Barrier) is a meeting point: each thread waits there until the other arrives. The chapter’s test puts the meeting point right after the count, so both requests have counted before either inserts. Without a lock, the race happens every time. With the lock, the second request is still waiting for the row and never reaches the meeting point, so the first one’s wait times out after two seconds and it carries on. Figure 33.3, in Step 3, shows both.

A version for edits

A lock lasts one transaction, a fraction of a second. Sam’s edit page stays open for minutes, and nothing can be locked for that long. The edit needs a different tool: a version number on the event that grows by one with each save. The page sends the version it was opened at. The save compares it with the event’s version now; if they differ, someone saved in between, and Otahque refuses instead of overwriting. This is called optimistic locking, because it lets everyone work and checks at the end; the row lock is pessimistic, because it makes others wait in case of a conflict. Figure 33.2 places the two side by side.

In practice: a busy evening

Situation. Sam announces the clinic in a chat with three hundred members, and forty of them press Register within the first minute.

Application. Each request locks the clinic’s row for the few milliseconds of its check and insert, so they take turns; requests for other events do not wait at all. The first twenty-five get places and the rest see “This event is full.”

Consideration. Turns cost time. Chapter 66 measures how long requests wait under load and decides whether this lock is still the right tool.
