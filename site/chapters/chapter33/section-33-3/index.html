How We Build It

Start from Chapter 32, in the folder containing manage.py, with Otahque on PostgreSQL 18, 343 passing tests, every migration applied, and the work committed. No package is added. The changed files are events/models.py, events/views.py, events/forms.py, events/admin.py, events/templates/events/edit.html, events/tests.py, and registrations/tests.py, plus one migration, two templates, the stylesheet source, and three design notes. The visible result: a full event stays full however many people press Register, a stale edit is refused with a message, and the “full” and “closed” states are easier to read. The chapter’s checks ran in Windows PowerShell 5.1 and Git Bash, against PostgreSQL 18.3.

The Custom Way

Before Django does it for you, see a row lock with your own eyes, in two psql windows. Open two terminals and, in each, sign in as Otahque’s role:

Terminal

psql -h localhost -U otahque -d otahque

In the first window, start a transaction and lock the first event’s row:

psql, window 1

BEGIN;
SELECT id, title FROM events_event WHERE id = 1 FOR UPDATE;

Output

BEGIN
 id |     title
----+---------------
  1 | Python meetup
(1 row)

In the second window, type the same two lines. psql answers BEGIN and then nothing more: the SELECT is waiting for the row. Go back to the first window and type COMMIT;. At once the second window shows the row:

Output

BEGIN
 id |     title
----+---------------
  1 | Python meetup
(1 row)

Type COMMIT; in the second window too. Now try a time limit. Lock the row again in the first window, then run this in the second:

psql, window 2

BEGIN;
SET LOCAL lock_timeout = '2s';
SELECT id, title FROM events_event WHERE id = 1 FOR UPDATE;
ROLLBACK;

Output

BEGIN
SET
ERROR:  canceling statement due to lock timeout
CONTEXT:  while locking tuple (0,1) in relation
    "events_event"
ROLLBACK

After two seconds the second window gives up with an error, and ROLLBACK; ends its failed transaction. Type COMMIT; in the first window and \q in both. Every part of the Django Way is here already: FOR UPDATE locks, the other session waits, and lock_timeout ends the wait. Django adds the transaction around the request, the query, and a test that proves it.

Then three helpers at the end of the file. at_once() runs actions in threads, each with its own connection, closed at the end. meet_after_counting() patches Event.places_taken so that each request waits for the other right after counting. organizer() makes Sam an organizer without any group, because TransactionTestCase empties every table after each test, including the groups Chapter 30’s migration made:

registrations/tests.py (add at the end)

def at_once(*actions):
    """Run each action in its own thread; return outcomes.

    An outcome is what the action returned, or the codes
    of the ValidationError it raised. Each thread has its
    own database connection, closed at the end, as two
    requests would.
    """
    outcomes = [None] * len(actions)

    def run(n, action):
        try:
            outcomes[n] = action()
        except ValidationError as error:
            outcomes[n] = [e.code for e in error.error_list]
        finally:
            connection.close()

    threads = [threading.Thread(target=run, args=(n, act))
               for n, act in enumerate(actions)]
    for thread in threads:
        thread.start()
    for thread in threads:
        thread.join()
    return outcomes


def meet_after_counting(timeout=2):
    """Make each request wait, after counting, for the other.

    Without a lock both count before either inserts, so
    the race happens every time. With the lock the other
    request is still waiting for the event row, so the
    meeting times out and the requests take turns.
    """
    barrier = threading.Barrier(2, timeout=timeout)
    count = Event.places_taken

    def counted(event):
        taken = count(event)
        try:
            barrier.wait()
        except threading.BrokenBarrierError:
            pass
        return taken

    return mock.patch.object(Event, 'places_taken', counted)


def organizer(event):
    """Create Sam, who may edit event, without any group.

    TransactionTestCase empties every table after a test,
    including the groups Chapter 30's migration made, so
    the permission is given to Sam directly.
    """
    sam = User.objects.create_user('sam@example.org',
                                   display_name='Sam')
    sam.user_permissions.add(
        Permission.objects.get(codename='change_event')
    )
    OrganizerAssignment.objects.create(event=event,
                                       member=sam)
    return sam

Now the test. skipUnlessDBFeature('has_select_for_update') skips it on a database that cannot lock rows, such as SQLite when DB_ENGINE is empty:

registrations/tests.py (add at the end)

@skipUnlessDBFeature('has_select_for_update')
class RaceTests(TransactionTestCase):
    """Requests for one event at the same moment.

    PostgreSQL only. Each test commits its rows, so other
    threads see them, and the tables are emptied after it.
    """

    def setUp(self):
        self.event = soon(capacity=1)
        self.now = timezone.now()

    def register(self, member):
        """Return an action that registers, as a request does."""
        def action():
            event = Event.objects.get(pk=self.event.pk)
            event.register(member, self.now)
            return 'place'
        return action

    def test_the_last_place_goes_to_one_member(self):
        sai = verified('sai@example.org')
        raj = verified('raj@example.org')
        with meet_after_counting():
            outcomes = at_once(self.register(sai),
                               self.register(raj))
        self.assertCountEqual(outcomes, ['place', ['full']])
        self.assertEqual(self.event.places_taken(), 1)

Common Error: the race test passes, or cannot see its own event

Written as a TestCase, the same test either fails with Event.DoesNotExist inside a thread, because the thread’s connection cannot see rows that were never committed, or, if both calls run in one thread, passes every time. Neither proves anything. Race tests use TransactionTestCase, and one connection per thread.

Step 4: Lock the event row

In events/models.py, add a method above register() and replace register() with this version:

events/models.py (replace register())

    def locked(self):
        """Return this event's row, locked until commit.

        Another request that asks for the row waits until
        this transaction ends. Call it inside atomic().
        """
        return Event.objects.select_for_update().get(
            pk=self.pk
        )

    def register(self, member, now):
        """Give member a place, or raise ValidationError.

        The event row is locked first, so requests for it
        take turns, and every check reads the locked row,
        not this copy, which may be out of date. The unique
        rule is still the backstop for the same member.
        """
        with transaction.atomic():
            event = self.locked()
            problems = event.registration_problems(member,
                                                   now)
            if problems:
                raise refusal(problems)
            try:
                with transaction.atomic():
                    return event.registrations.create(
                        member=member, registered_at=now
                    )
            except IntegrityError:
                # Only the one-active-place rule means a
                # repeat; any other failure is re-raised.
                if event.place_of(member) is None:
                    raise
            raise refusal(['already_registered'])

Two changes matter. self.locked() asks for the row and its lock, so a second request for the same event waits here. And every check after it reads event, the row the lock returned, not self, the copy the view loaded: the problems, the count, the insert, and the repeat check. Run the test again:

Common Error: select_for_update cannot be used outside of a transaction

Called in autocommit, outside transaction.atomic(), select_for_update() raises TransactionManagementError, because a lock would end the moment the query did. locked() is only called inside atomic(). Inside a TestCase the error does not appear, because the whole test is one transaction: one more reason to test locks with TransactionTestCase.

Step 6: A time limit, and “busy”

A request that waits for a lock should not wait for ever. The test holds the row in one thread, the way a slow request would, and expects the other to be told Otahque is busy. Add it to RaceTests:

registrations/tests.py (in RaceTests, at the end)

    def test_busy_while_another_request_holds_it(self):
        sai = verified('sai@example.org')
        held, finished = threading.Event(), threading.Event()

        def hold():
            with transaction.atomic():
                Event.objects.select_for_update().get(
                    pk=self.event.pk
                )
                held.set()
                finished.wait(5)

        def try_to_register():
            held.wait(5)
            try:
                return self.register(sai)()
            finally:
                finished.set()

        with mock.patch('events.models.LOCK_TIMEOUT',
                        '100ms', create=True):
            outcomes = at_once(hold, try_to_register)
        self.assertEqual(outcomes[1], ['busy'])
        self.assertEqual(self.event.places_taken(), 0)

# How long a request waits for an event row that another
# request has locked, before Otahque says it is busy.
LOCK_TIMEOUT = '3s'
# PostgreSQL's error code for "lock not available".
LOCK_NOT_AVAILABLE = '55P03'

And locked() gets its final form:

events/models.py (replace locked())

    def locked(self):
        """Return this event's row, locked until commit.

        Another request that asks for the row waits until
        this transaction ends, for at most LOCK_TIMEOUT;
        then it is told Otahque is busy. Call it inside
        atomic(). SQLite ignores both.
        """
        if connection.vendor == 'postgresql':
            with connection.cursor() as cursor:
                cursor.execute('SET LOCAL lock_timeout = %s',
                               [LOCK_TIMEOUT])
        try:
            return Event.objects.select_for_update().get(
                pk=self.pk
            )
        except OperationalError as error:
            # Only the lock timeout means busy; any other
            # database error is raised again.
            code = getattr(error.__cause__, 'sqlstate', None)
            if code != LOCK_NOT_AVAILABLE:
                raise
            raise refusal(['busy']) from None

SET LOCAL limits the wait for this transaction only. If the wait runs out, psycopg raises an error whose code is 55P03, which Django passes on as an OperationalError with psycopg’s error as its cause. Only that code becomes “busy”; a lost connection, for example, is still an error. The test patches LOCK_TIMEOUT to a tenth of a second so that it does not wait three:

    def publish(self):
        """Draft to published, or ValidationError.

        Reads the status under the lock, so a copy loaded
        earlier cannot publish twice or publish a change.
        """
        with transaction.atomic():
            event = self.locked()
            if event.status != self.Status.DRAFT:
                raise ValidationError(
                    'Only a draft can be published.'
                )
            problems = event.readiness_problems()
            if problems:
                raise ValidationError(problems)
            event.status = self.Status.PUBLISHED
            event.save(update_fields=['status'])
        self.status = event.status

    def cancel(self):
        """Cancel if published, or raise ValidationError.

        Reads the status under the lock, like publish().
        """
        with transaction.atomic():
            event = self.locked()
            if event.status != self.Status.PUBLISHED:
                raise ValidationError(
                    'Only a published event can be '
                    'cancelled.'
                )
            event.status = self.Status.CANCELLED
            event.save(update_fields=['status'])
        self.status = event.status

Each locks, checks the locked row, saves it, and then updates self so the caller sees the new status.

    Return None once saved, or the form to show again.
    The lock makes the capacity floor count the places

@login_required

    """Edit the event, for those who may change it."""

                            Action.EDIT_EVENT)

        cleaned = super().clean()
        if (self.instance.pk is not None
                and cleaned.get('seen_version')
                != self.instance.version):

                'This event was changed after you opened '
                'this page. Reload it and make your changes '
                'again.', code='stale',
            )
        return cleaned

## Requests at the same moment (Chapter 33)

- register(), publish(), cancel(), and the edit save
  lock the event row (Event.locked(): select_for_update
  inside atomic) and check the locked row, never the
  copy a view loaded.
- Requests for one event take turns; requests for

- A request waits at most LOCK_TIMEOUT (3 s), then is
  told "Otahque is busy. Please try again." with
  nothing changed. Only PostgreSQL's lock-not-available
  error (55P03) means busy; no automatic retry.
- The same member twice: the one-active-place rule and
  the inner atomic() (Chapter 31) give one place.
- Cancelling a place does not lock the event: a count
  made while a place is being given back may still see
  it. That can only refuse a place, never oversell.
- Proved by RaceTests (TransactionTestCase, threads,
  PostgreSQL only; skipped on SQLite).
