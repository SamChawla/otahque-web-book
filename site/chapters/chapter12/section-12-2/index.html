What You Need to Know

One layout, many pages

New Concept: template inheritance

What problem exists? Every page repeats the same outer structure: the document head, the navigation, and the main area. A change to any of them means editing every page.

What did people do before? They copied the shared parts into each file, or joined a header string and a footer string around each page in code. Both drift apart as soon as one copy is changed and another is not.

What is template inheritance? A base template holds the structure every page shares and marks named places, called blocks, that a page may fill. A child template names its parent with {% extends %} and supplies its own content for those blocks. Django renders the parent with the child’s blocks put in place.

Why inheritance? The shared structure exists once. Each page holds only what makes it different, and a site-wide change is one edit.

Now let’s use it.

A block is written {% block name %}...{% endblock %}. In the base template, whatever sits between the two tags is the fallback: it is shown when a child does not fill that block. Our layout will have two blocks. The title block holds the text in the browser tab, with Otahque as its fallback. The content block holds the page’s own content, with no fallback.

Inside a child’s block, {{ block.super }} inserts the parent’s content for that block, so a child can add to the fallback instead of replacing it. A block name may appear only once in a template.

Under the Hood: how a child is rendered

Django meets {% extends "base.html" %} and loads the parent first. It collects the child’s blocks by name, then renders the parent from top to bottom. At each block in the parent, it uses the child’s version if there is one, and the parent’s fallback if not. Anything in the child outside a block has nowhere to go and is dropped. A block name the parent does not define is dropped too, silently. That is why extends must be the first tag in the child: the whole child is read as a set of replacements for its parent.

Two of those silent cases deserve a warning now. A misspelled block name, such as contnet, raises no error; its content simply never appears. Text written in the child outside every block disappears in the same way. In both cases the page still returns 200. Our tests will check for content, not only for a successful status.

Try it yourself

Assume base.html defines a title block with the fallback Otahque and an empty content block. A child extends it and contains three things: the word Hello outside any block, a block named contnet holding Welcome, and a title block holding {{ block.super }} | Events.

Que. 1 What do the browser tab and the main area show?

Answer. The tab shows Otahque | Events, because block.super inserts the parent’s fallback before the child’s text. The main area is empty. Hello is outside every block, so it is dropped. contnet is not a block the parent defines, so Welcome is dropped too. Neither mistake raises an error.

Where the shared layout lives

In Chapter 11, APP_DIRS let Django find events/list.html inside the events app. A layout that every page uses belongs to no single app: accounts and registrations will need it as well, when their pages arrive in Chapters 27 and 31. So we put it in a templates folder at the project level, beside manage.py, and tell Django about it with the DIRS setting. Django searches the folders in DIRS first, then each installed app’s templates folder. Our layout will be templates/base.html, and its name in {% extends %} is simply base.html.

Que. 2 Why not put base.html in events/templates/ and leave the settings alone?

Flip to check your answerFold answer back

Answer. It would work today, but the layout would then belong to the events app. When the accounts app needs the same layout, it would depend on the events app for something that is not about events. A project-level folder makes the shared layout visibly shared.

Including one template in another

{% include "includes/site_nav.html" %} renders another template at that point and inserts its output. The included template sees the same context as the template that includes it, so it can use any variable the page has. Two options limit that. with passes extra values, as in {% include "row.html" with event=item %}, and only gives the included template nothing except what with supplies. Use only when a fragment should not depend on whatever the surrounding page happens to contain.

Our navigation will be an included template, so the layout stays short and the navigation has a file of its own. Both links will use route names with {% url %}, as Chapter 11’s links did, so a changed address needs no template edit.

Partials: a named piece of a template

New Concept: template partials

What problem exists? Some markup, such as one row of the event list, is used in one template but is worth naming: we want to test it alone, and later chapters will want to send just that row to the browser.

What did people do before? They moved the row into its own small file and included it, which scatters one page across several files. Before Django 6.0, a third-party package provided partials.

What is a partial? A named fragment defined inside a template with {% partialdef name %}...{% endpartialdef %}. It can be used in the same template with {% partial name %}, and loaded from outside as template_name#partial_name.

Why partials? The fragment stays where it is used, keeps one name, and can still be rendered on its own.

Now let’s use it.

A plain partialdef only defines the fragment; nothing appears until {% partial %} uses it. Adding inline, as in {% partialdef event-row inline %}, defines it and renders it in the same place. Our list will define the row inline, inside its loop, so the page looks exactly as before. A test can then ask for events/list.html#event-row and receive just one row, without the layout.

Custom filters

New Tool: a custom template filter

What problem exists? We want every sample title shown with the same visible label, Sample:, wrapped in an element that later styles can target. Writing that markup by hand in every template repeats it and invites mistakes.

What did people do before? They built the HTML string in each view, which mixes markup into Python, or repeated it in each template.

What is a custom filter? A Python function registered with Django’s template library and used after a value with |, as {{ title|sample_label }}. It lives in a templatetags package inside an installed app and is loaded into a template with {% load %}.

Why a filter? The label is defined once, can be tested alone, and is used with the same syntax as Django’s own filters.

Now let’s use it.

A filter that returns HTML must take care with its input. If it joins the title into a string and marks the result safe, it switches off the escaping we tested in Chapter 11. Django’s format_html builds the HTML from a template string with {} placeholders and escapes each argument before inserting it, then marks the result safe. Our label’s span element stays markup; the title stays text.

Two details catch everyone at least once. {% load %} is not inherited: a child that uses the filter must load it itself, even if its parent has. And the development server only discovers a new templatetags module when it starts, so restart it after creating one.

In practice: a site-wide notice

Situation. Sam wants every page to say that the events shown are fictional samples until real publishing is built.

Application. One line in base.html, inside the layout and outside every block, puts the notice on every page that extends it, with no change to the pages themselves.

Consideration. A notice in the layout appears everywhere, including pages added later. If some pages must not show it, give the layout a block for it, so those pages can replace it with nothing.

Everything in this chapter uses Django’s own template language. One alternative deserves a short answer before we build.

Prefer Jinja2?

Django can also render templates with Jinja2, a separate template engine with similar syntax. It needs installing, looks in each app’s jinja2 folder instead of templates, and does not know Django’s own tags and filters unless they are added to its environment. We keep Django’s template language: it needs no new dependency, and every later chapter and Django’s admin use it. The choices in this chapter, layout, include, partial, and filter, carry over to Jinja2 in spirit.
