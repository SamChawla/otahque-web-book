Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 and L2 check what you have just learned. L3 asks you to choose between tools. L4 and L5 look ahead to a larger application and a code review: attempt them now, and return to them later. They are extension questions, not a gate to the next chapter. Run each code proof beside manage.py, in PowerShell, a macOS shell, or Linux/WSL Bash.

L1 (Junior): What is the difference between extends and include?

What the interviewer is testing: Can you tell the outer structure of a page from a piece placed inside it?

Flip to check your answerFold answer back

Perfect answer: extends says this template is a variation of a parent: the parent is rendered as the page and the child only fills its blocks. include goes the other way: it inserts another template’s output at one point inside the current one. A page extends one layout at most, but it can include many pieces. In Otahque, every page extends base.html, and base.html includes the navigation.

Behind the scenes:

django/template/loader_tags.py (summary)

# ExtendsNode: load the parent, collect the child's blocks
#     by name, and render the parent with them.
# IncludeNode: load another template and render it here
#     with the current context, or only the given values.

Code proof: list the templates used to render the event list:

Terminal

uv run python manage.py shell -c "
from django.test import Client
from django.test.utils import setup_test_environment
setup_test_environment()
response = Client().get('/events/')
for name in sorted({t.name for t in response.templates}):
    print(name)
"

Output

12 objects imported automatically (use -v 2 for details).

base.html
events/list.html
includes/site_nav.html

Common mistakes:

  • Using include for the outer layout, and repeating it in every page.
  • Placing a tag above extends.
  • Expecting a child’s text outside blocks to appear.

Follow-up the interviewer might ask:

  • “Can a base template itself extend another template?”
  • “When would you use include with only?”

L2 (Mid-Level): How does Django decide what a child page renders?

What the interviewer is testing: Can you trace blocks, fallbacks, and the silent cases?

Flip to check your answerFold answer back

Perfect answer: Django loads the parent named by extends, collects the child’s blocks by name, and renders the parent. At each block it uses the child’s version if there is one, otherwise the parent’s fallback; block.super inside a child’s block adds the fallback back. Everything else in the child is dropped: text outside blocks, and blocks the parent does not define. None of that raises an error, so I would test that each page shows its own content, not just that it returns 200.

Behind the scenes:

django/template/loader_tags.py (summary)

# BlockNode.render(): take the most specific version of
#     this block from the block context; block.super renders
#     the next version up the chain.

Code proof: render a child with a misspelled block and text outside blocks:

Terminal

uv run python manage.py shell -c "
from django.template import engines
child = engines['django'].from_string(
    '{% extends layout %}outside'
    '{% block contnet %}typo{% endblock %}'
    '{% block title %}{{ block.super }} | Test{% endblock %}'
)
page = child.render({'layout': 'base.html'})
print('outside' in page, 'typo' in page)
print([x.strip() for x in page.splitlines() if 'title' in x])
"

Output

12 objects imported automatically (use -v 2 for details).

False False
['<title>Otahque | Test</title>']

extends also accepts a variable, which the proof uses to avoid nested quotes in the shell.

Common mistakes:

  • Expecting an error for a misspelled block name.
  • Forgetting block.super and losing the parent’s content.
  • Defining the same block name twice.

Follow-up the interviewer might ask:

  • “What does a block nested inside another block do?”
  • “How would you test that every page fills the title block?”

L3 (Senior): When would you choose a partial, an include, or an inclusion tag?

What the interviewer is testing: Can you choose a reuse mechanism by who uses the piece and what context it needs?

Flip to check your answerFold answer back

Perfect answer: A partial, when the piece belongs to one template but is worth naming: it stays beside its use and can still be rendered alone, as our event row is in a test and, later, in a partial page update. An include, when several templates share a self-contained piece that works with the context it is given, such as the navigation; only keeps that dependency explicit. An inclusion tag, when the piece needs to prepare its own context and be called like a function from many templates. In every case I want a test that renders the piece alone.

Behind the scenes:

django/template/loader_tags.py (summary)

# A name such as 'events/list.html#event-row' loads the
#     template, then returns its partial 'event-row' as a
#     template of its own.

Code proof: render the event row alone, without the layout:

Terminal

uv run python manage.py shell -c "
from django.template.loader import render_to_string
event = {'id': 1, 'title': 'Python meetup'}
row = render_to_string(
    'events/list.html#event-row', {'event': event}
)
for line in row.splitlines():
    if line.strip():
        print(line.strip())
"

Output

12 objects imported automatically (use -v 2 for details).

<li>
<a href="/events/1/">
<span class="sample-label">Sample:</span> Python meetup
</a>
</li>

Common mistakes:

  • Moving every fragment into its own file before anything else needs it.
  • Letting an included template depend on variables it never states.
  • Rendering a partial alone without its own test.

Follow-up the interviewer might ask:

  • “What would change if two templates needed the event row?”
  • “Why might a server send just one row back to the browser?”

L4 (Staff): How would you organize templates across many apps?

What the interviewer is testing: Can you design template ownership and lookup for a growing project?

Flip to check your answerFold answer back

Perfect answer: Shared structure, the base layout and site-wide includes, lives in the project templates folder found through DIRS. Each app keeps its own pages under a folder named after the app, such as events/templates/events/, so names never collide. Because DIRS is searched before app folders, a project template with the same name as an app’s would win, which is useful for deliberate overrides and confusing by accident; I would keep the names distinct and check origins when in doubt. Apps extend the shared layout instead of each keeping their own.

Behind the scenes:

django/template/engine.py (summary)

# find_template(name): try each loader in order: the
#     filesystem loader searches DIRS, then the app
#     directories loader searches each app's templates.

Code proof: show which file each template name resolves to:

Terminal

uv run python manage.py shell -c "
from pathlib import Path
from django.conf import settings
from django.template.loader import get_template
for name in ('base.html', 'events/list.html'):
    origin = get_template(name).origin
    path = Path(origin.name).relative_to(settings.BASE_DIR)
    print(name, '->', path.as_posix())
"

Output

12 objects imported automatically (use -v 2 for details).

base.html -> templates/base.html
events/list.html -> events/templates/events/list.html

Common mistakes:

  • Putting the shared layout inside one app.
  • Leaving out the app-named folder, so names collide.
  • Overriding a template by accident because a name repeats.

Follow-up the interviewer might ask:

  • “How would you override a template from a third-party app?”
  • “Where would an email template live?”

L5 (Lead): A review finds mark_safe in a custom filter. How do you respond?

What the interviewer is testing: Can you review an escaping risk with evidence and a clear fix?

Flip to check your answerFold answer back

Perfect answer: I would ask what is inside the string being marked safe. If any part comes from data, such as a title, the filter has switched off escaping for that data on every page that uses it. I would show it with a test that passes an HTML-looking value and expects it escaped, which fails. The fix is format_html, or conditional_escape on each input before joining, and the test stays as a regression guard. mark_safe on a fixed string with no data is fine; the review question is always where the data enters.

Behind the scenes:

django/utils/html.py (summary, not the source)

# format_html(pattern, *args): escape each argument,
#     fill the pattern, and mark the result safe.
# mark_safe(text): mark the text safe exactly as it is.

Code proof: the same title through both approaches:

Terminal

uv run python manage.py shell -c "
from django.utils.html import format_html
from django.utils.safestring import mark_safe
title = '<b>Not a tag</b>'
print(format_html('<span>Sample:</span> {}', title))
print(mark_safe('<span>Sample:</span> ' + title))
"

Output

12 objects imported automatically (use -v 2 for details).

<span>Sample:</span> &lt;b&gt;Not a tag&lt;/b&gt;
<span>Sample:</span> <b>Not a tag</b>

The first line keeps the title as text; the second would put a real b element on the page. Rewriting our filter the second way makes four tests fail: the three escaping tests and the partial test, which renders an HTML-looking title too.

Common mistakes:

  • Approving mark_safe because the current data looks harmless.
  • Fixing the filter without adding a test that would catch it again.
  • Treating format_html as validation; it escapes, it does not check meaning.

Follow-up the interviewer might ask:

  • “How would you find every mark_safe in a large project?”
  • “When is mark_safe the right tool?”
