Step 2: A class in Python terms

Create a practice file beside manage.py, practice_class.py. It is plain Python, with no Django:

practice_class.py

"""Practice: the class ideas a Django view class needs."""


class Page:
    """A page that answers by method name."""

    greeting = 'Hello'

    def __init__(self, who):
        self.who = who

    def get(self):
        return f'{self.greeting}, {self.who}'


class FriendlyPage(Page):
    """A Page with its own greeting."""

    greeting = 'Welcome'

    def get(self):
        return super().get() + '!'


page = FriendlyPage('Sai')
print(page.get())
print(getattr(page, 'get')())
print(hasattr(page, 'post'))
print(getattr(page, 'post', None))

Terminal

uv run python practice_class.py

Output

Welcome, Sai!
Welcome, Sai!
False
None

Read the four lines of output against the code. FriendlyPage('Sai') makes an instance; __init__ stores who on it, and every method reaches that through self. FriendlyPage inherits from Page, replaces greeting, and replaces get(), but its get() still calls the parent’s through super(), so the result is the parent’s sentence with the child’s greeting and an exclamation mark. getattr(page, 'get') finds the method from the string 'get', and the () after it calls it. hasattr(page, 'post') is False, and getattr() with a third argument returns that default instead of failing. Delete the file; you have everything dispatch() needs.

Step 3: Pin every answer first

Each table needs a helper that sends one request and names the answer in the words of Table 35.1. It belongs in config/helpers.py, beside outcome(), because both apps’ tables use it. Add two imports there, Client and AuditEvent, so that its Django and project imports read:

config/helpers.py

from django.contrib.auth import get_user_model
from django.contrib.auth.models import Group
from django.test import Client
from django.urls import reverse

from audit.models import AuditEvent
from events.forms import EventForm

Then add two functions at the end of the file:

config/helpers.py

def answer(client, method, path):
    """Name how a page answered one request, for a table.

    First outcome()'s name ('sign in', 'ok', or the status
    code), then the Allow header if there is one, then
    'recorded' if a refused attempt was recorded.
    """
    refused = AuditEvent.objects.filter(
        outcome=AuditEvent.Outcome.REFUSED
    )
    before = refused.count()
    response = client.generic(method, path)
    words = [outcome(response)]
    if response.has_header('Allow'):
        words.append(response['Allow'])
    if refused.count() > before:
        words.append('recorded')
    return ' '.join(words)


def answers(path, member, method):
    """Return a page's answers signed out and as member."""
    signed_in = Client()
    signed_in.force_login(member)
    return (answer(Client(), method, path),
            answer(signed_in, method, path))

client.generic() sends a request with any method name, which is how the tables reach PUT, TRACE, and the rest. answer() counts refused-access records before and after, so a row can say whether the attempt was recorded. answers() asks twice, once with a fresh client that is signed out and once as the given member, and returns both.

Now the event page’s table. Create events/tests/test_methods.py:

events/tests/test_methods.py

"""How the event page answers every HTTP method.

Written before the page became a class (Chapter 35), so
that any change in its answers fails a test.
"""
from django.contrib.auth import get_user_model
from django.test import TestCase

from config.helpers import answers, save_event
from events.models import Event

User = get_user_model()

# A method, then the answer signed out and the answer
# signed in as a member who organizes nothing.
PUBLISHED = [
    ('GET', 'ok', 'ok'),
    ('HEAD', 'ok', 'ok'),
    ('POST', 'ok', 'ok'),
    ('PUT', 'ok', 'ok'),
    ('PATCH', 'ok', 'ok'),
    ('DELETE', 'ok', 'ok'),
    ('OPTIONS', 'ok', 'ok'),
    ('TRACE', 'ok', 'ok'),
]
HIDDEN = [
    ('GET', '404', '404 recorded'),
    ('HEAD', '404', '404 recorded'),
    ('POST', '404', '404 recorded'),
    ('PUT', '404', '404 recorded'),
    ('OPTIONS', '404', '404 recorded'),
]


class EventPageMethodTests(TestCase):
    """The event page's answer to each method, pinned."""

    @classmethod
    def setUpTestData(cls):
        cls.event = save_event()
        cls.draft = save_event(status=Event.Status.DRAFT)
        cls.sai = User.objects.create_user(
            'sai@example.org', display_name='Sai'
        )

    def check(self, event, table):
        """Compare the page's answers with each row."""
        path = event.get_absolute_url()
        for method, signed_out, signed_in in table:
            with self.subTest(method):
                self.assertEqual(
                    answers(path, self.sai, method),
                    (signed_out, signed_in),
                )

    def test_a_published_event(self):
        self.check(self.event, PUBLISHED)

    def test_a_hidden_draft(self):
        self.check(self.draft, HIDDEN)

Each row is one method. The published event answers ok to everything, because event_detail never looks at the method: that is what the function does today, written down. The hidden draft gives 404 to everyone, and a signed-in member’s attempt is recorded, as Chapter 30 decided. self.subTest(method) reports each failing row separately, by method, instead of stopping at the first.

Common Error: a table that is green for the wrong reason

If a row is wrong, say you wrote '405 POST' where the page answers '405 GET, POST', the test fails now, before any change, and you correct the row. But a table can also pass while testing nothing, if check() loops over an empty list or the path is wrong for every row. Read each table once against Table 35.1, and break one row on purpose to see it fail.

Step 4: The Custom Way: a hand-made as_view()

A URL pattern needs something it can call with a request, and a class is not that. Write the bridge yourself. Create custom_as_view.py beside manage.py. It is illustration only: it sets Django up so it can make requests, then throws everything away:

custom_as_view.py

"""Practice: a hand-made as_view(), to compare with Django's.

Illustration only: run it once, then delete it.
"""
import os

import django

os.environ.setdefault('DJANGO_SETTINGS_MODULE',
                      'config.settings')
django.setup()

from django.http import (  # noqa: E402
    HttpResponse, HttpResponseNotAllowed,
)
from django.test import RequestFactory  # noqa: E402


def as_view(cls):
    """Return a function that answers with cls's handlers."""
    def view(request, *args, **kwargs):
        instance = cls()
        instance.request = request
        name = request.method.lower()
        handler = getattr(instance, name, None)
        if handler is None:
            allowed = [m.upper() for m in ('get', 'post')
                       if hasattr(instance, m)]
            return HttpResponseNotAllowed(allowed)
        return handler(request, *args, **kwargs)
    view.view_class = cls
    return view


class Hello:
    """A view class with one handler."""

    def get(self, request, name):
        return HttpResponse(f'Hello, {name}')


view = as_view(Hello)
factory = RequestFactory()
for method in ('get', 'post', 'delete'):
    request = getattr(factory, method)('/hello/')
    response = view(request, name='Sai')
    print(method.upper(), response.status_code,
          response.get('Allow', response.content.decode()))
print(view.view_class.__name__)

Terminal

uv run python custom_as_view.py

Output

GET 200 Hello, Sai
POST 405 GET
DELETE 405 GET
Hello

as_view(Hello) returns a new function, view, that remembers cls (a closure, a function that keeps the variables of the function that made it). Each call makes a fresh instance, so two requests never share self. getattr(instance, name, None) finds get for a GET; there is no post or delete, so those get 405, with an Allow header built from the handlers that exist. view.view_class lets a test ask which class is behind a URL. RequestFactory, from Chapters 10 and 34, builds the requests without a server.

Notice what your version lacks. It answers 405 to OPTIONS and to HEAD. It has no way to pass settings to the class. It checks only get and post. And there is no place to put code that must run before every handler. Delete the file, then read how Django fills each gap.

Step 5: Read Django’s View

Django’s View lives in your virtual environment. Ask Python where:

Terminal

uv run python -c "import django.views as v; print(v.__file__)"

Output

...\.venv\Lib\site-packages\django\views\__init__.py

Open the folder it names, then generic/base.py inside it, and find class View. Here is the part this chapter uses, from Django 6.1.2, shortened where the ... marks are, and with one line rewrapped to fit the page:

django/views/generic/base.py (excerpt)

class View:
    http_method_names = [
        "get", "post", "put", "patch",
        "delete", "head", "options", "trace",
    ]

    @classonlymethod
    def as_view(cls, **initkwargs):
        ...
        def view(request, *args, **kwargs):
            self = cls(**initkwargs)
            self.setup(request, *args, **kwargs)
            ...
            return self.dispatch(request, *args, **kwargs)

        view.view_class = cls
        ...
        return view

    def setup(self, request, *args, **kwargs):
        if hasattr(self, "get") and not hasattr(self, "head"):
            self.head = self.get
        self.request = request
        self.args = args
        self.kwargs = kwargs

    def dispatch(self, request, *args, **kwargs):
        method = request.method.lower()
        if method in self.http_method_names:
            handler = getattr(
                self, method, self.http_method_not_allowed
            )
        else:
            handler = self.http_method_not_allowed
        return handler(request, *args, **kwargs)

The shape is yours: as_view() returns a function that makes a new instance for each request and hands the request on. Three things are added. setup() runs first and stores the request and the URL’s values on the instance, so every method can use self.request and self.kwargs; it also makes head the same as get. dispatch() then picks the handler by name, as yours did, but from the full list http_method_names, and calls http_method_not_allowed() for anything missing, which answers 405 with an Allow header listing every name in that list the instance has. And because View itself defines options(), options is always on that list. Figure 35.1 draws the path.

The dashed zone matters in Step 9. Decorators for a class are applied to dispatch(), so they run after setup(), never before it.

registrations/views.py

@method_decorator(login_required, name='dispatch')
class RegistrationDetailsView(View):
    """Ask for what an event needs, then register.

    Today that is a phone number; Chapter 38 adds the
    event's own questions.
    """

    def dispatch(self, request, *args, **kwargs):
        """Load the event, then call get() or post()."""
        self.event = event_for(request, kwargs['event_id'])
        return super().dispatch(request, *args, **kwargs)

    def get(self, request, event_id):
        """Show the empty form."""
        return self.show(PhoneForm())

    def post(self, request, event_id):
        """Keep the number and take a place, or show errors."""
        form = PhoneForm(request.POST)
        if form.is_valid():
            form.save(request.user)
            return take_place(request, self.event)
        return self.show(form)

    def show(self, form):
        """Render the page with the form."""
        return render(
            self.request, 'registrations/phone.html',
            {'event': self.event, 'form': form},
        )

dispatch() loads the event once, before either handler, so both use self.event, then calls the parent’s dispatch() to pick the handler. show() is an ordinary helper method; Django never calls it. Step 11: Write the house rule

Two pages converted, seventeen to go, or not. Before Chapters 36 and 37 convert more, write down which views become classes, and the rules any conversion follows. Create docs/adr/ADR-006-views.md:

docs/adr/ADR-006-views.md

# ADR-006: Function views and class views

## Status

Proposed, November 2026 (Chapter 35). The choices follow
the user's decisions of 24 November 2026 (Chapter 35
D35.1-D35.4); this record is not yet reviewed or accepted.

## Context

For 34 chapters every Otahque view was a function. Many
of them repeat one shape: load an event the viewer may
see, refuse with 404 or 403, render. Django's generic
views (Chapters 36 and 37) remove that repetition, but
they are classes, and a class answers some requests on
its own: HEAD, OPTIONS, and 405 with an Allow header.
Converting a view can change what it answers, and the
existing tests did not notice (Chapter 35, Step 3).

## Options

- A: convert every view to a class.
- B: keep every view a function.
- C: classes where a generic view fits or a page has
  several handlers; small functions for one-off actions.

## Decision

C, with four rules.

1. Before a view is converted, a method table pins its
   answer to every method, signed in and signed out.
2. A conversion keeps every answer the function chose.
   The function's decorators move, in the same order, to
   one method_decorator list on dispatch().
3. Where the function chose nothing, Django's defaults
   are accepted and the table says so (D35.4: the event
   page answers 405 to methods other than GET and HEAD,
   and OPTIONS itself).
4. Nothing that needs sign-in or visibility goes in
   setup(): it runs before the decorators. Load objects
   in dispatch() or in the handlers.

## Inventory (19 views)

Kind now, then where each view goes and why.

events
- home: function, stays (one template, nothing shared).
- event_list: function, ListView in 36.
- EventDetailView: View class since 35; DetailView in 36.
- event_create: function, CreateView in 37.
- event_edit: function, UpdateView in 37.
- event_manage (My events): function, ListView in 36.
- event_publish: function, stays (one-off POST action).
- event_cancel: function, stays (one-off POST action).
- event_delete: function, DeleteView in 37.
- event_copy: function, FormView in 37.
- organizer_events: function, stays until Chapter 67
  makes organizer roles per community.
- event_organizers: function, stays until Chapter 67
  (add-by-email form behind re-authentication).
- remove_organizer: function, stays (one-off POST).

registrations
- register: function, stays (one-off POST action).
- RegistrationDetailsView: View class since 35; gains
  the event's questions in 38.
- my_registrations: function, ListView in 36.
- cancel_registration: function, a class in 37.
- attendees: function, stays until Chapter 41 adds the
  download (a report, not a list of one model).

accounts
- profile: function, FormView in 37 (proposed; not yet
  in Chapter 37's plan).

## Consequences

- Eleven views become classes by Chapter 37; eight stay
  functions, each with a reason above.
- Each converted page's table shows any change in its
  answers, so a change is a decision, not an accident.
- The event page no longer records a refused POST to a
  hidden draft: the method is refused (405) before the
  event is loaded. 405 is the same for every number.
- Chapter 37's LoginRequiredMixin and Chapter 39's
  LoginRequiredMiddleware put sign-in before the method
  check; the tables will show it, and those chapters say
  so.
