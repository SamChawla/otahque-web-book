Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead, to debugging a conversion and to setting a rule for a team. They are extension questions, not a gate to the next chapter. Proof files are run with uv run python manage.py shell -v 0 -c "exec(open('NAME').read())" and deleted afterwards.

L1 (Junior): What does as_view() return, and what happens when a request arrives?

What the interviewer is testing: Do you know the path from a URL to your method?

Flip to check your answerFold answer back

Perfect answer: as_view() is a class method that returns a plain function, and that function is what the URL pattern holds. For each request, the function makes a new instance of the class, calls setup() to store the request and the URL’s values on it, then calls dispatch(). dispatch() lowers the method name and calls the handler of that name, such as get(), or answers 405 with an Allow header if there is none. A new instance per request means two requests never share self. The returned function also carries the class as view_class, so a test can ask which view answers an address.

Behind the scenes:

as_view() (summary)

view = Cls.as_view()      once, when urls.py loads
view(request, **kwargs)   each request:
  self = Cls()            new instance
  self.setup(...)         request, args, kwargs
  self.dispatch(...)      handler or 405

Code proof: the event page’s address, resolved:

Output

function view
EventDetailView
['get', 'post', 'put', 'patch', 'delete', 'head', 'options',
    'trace']

Common mistakes:

  • Putting the class in the URL pattern without .as_view().
  • Storing per-request data on the class instead of the instance, where every request would share it.

Follow-up the interviewer might ask:

  • Where would you pass a setting to the class? (As a keyword to as_view(), which accepts only names the class already has, such as template_name.)
  • Why is view_class useful in tests? (It identifies the view without depending on a function’s name.)

L2 (Mid-Level): Predict what a PUT and an OPTIONS get from the event page, before and after

What the interviewer is testing: Can you predict what a class adds before you run anything?

Flip to check your answerFold answer back

Perfect answer: Before, as a function with no method check, both got 200 and the full page; the function did not look at the method. After, EventDetailView has only get(). A PUT finds no put(), so dispatch() calls http_method_not_allowed(): 405, with Allow: GET, HEAD, OPTIONS, because setup() added head and View itself has options. An OPTIONS finds options(): 200, an empty body, and the same Allow header. Otahque accepted both changes on purpose (D35.4) and declared them in the table.

Behind the scenes:

dispatch() for the event page (summary)

GET, HEAD   get()                 200 or 404
OPTIONS     options()             200, Allow
anything    not allowed           405, Allow

Code proof: three requests to an event, through the test client:

Folder structure

GET 200 -
Method Not Allowed (PUT): /events/1/
PUT 405 GET, HEAD, OPTIONS
OPTIONS 200 GET, HEAD, OPTIONS

The second line is Django’s request log, which records every 405 while DEBUG is on.

Common mistakes:

  • Saying “nothing changes, the tests pass”: the old suite never sent a PUT.
  • Forgetting HEAD and OPTIONS in the Allow header.

Follow-up the interviewer might ask:

  • Would a browser ever send the PUT? (Not from a page; a script or tool can, and must still get a sensible answer.)
  • Does the 405 reveal whether a draft exists? (No: it is the same for every number, existing or not.)

L3 (Senior): Defend keeping Register a function

What the interviewer is testing: Can you resist converting something just because you can?

Flip to check your answerFold answer back

Perfect answer: Register is a one-off action: one method, POST, two decorators, and three lines that hand over to take_place(). A class would share nothing with any other view and has no generic view to inherit from. It would add answers to keep: View brings OPTIONS, and the decorators would need to move, in order, into a method_decorator list to keep 405 before sign-in. That is more code for the same behaviour and a new way to get the order wrong. The house rule keeps classes for pages that a generic view fits or that have several handlers, and Register is neither. Its method table still pins it, so a future change to sign-in, such as Chapter 39’s middleware, shows up as a decision.

Behind the scenes:

Register's answers (summary)

POST, signed out    sign in
POST, signed in     a place, then the event page
anything else       405, Allow: POST

Common mistakes:

  • Converting for consistency alone; consistency with a rule that has reasons is the goal, not one style everywhere.
  • Keeping a function but not pinning it, so a later change to sign-in goes unnoticed.

Follow-up the interviewer might ask:

  • When would you convert it? (If it gained a confirmation page, so two handlers, or if a generic view fitted.)
  • What will Chapter 39’s login-by-default middleware change? (Signed out, every method goes to sign in first; the table’s signed-out rows will say so.)

L4 (Staff): After a refactor, a signed-out visitor gets 404 for a hidden draft instead of the sign-in page. Diagnose it

What the interviewer is testing: Can you reason about the order in which a class runs your code?

Flip to check your answerFold answer back

Perfect answer: First, find which rows changed: the method table names the method and the person, so the failure says exactly which answers moved. Here only the hidden draft’s rows changed, and the 404 arrives even for PUT, which should be refused before anything else. Something is loading the event, and refusing, before both decorators. Decorators added with method_decorator(..., name='dispatch') wrap dispatch(), and as_view()’s function calls setup() before dispatch(). So the lookup has been put in setup(). Move it into dispatch(), before super().dispatch(), where it runs after the method check and sign-in, and the rows go green. ADR-006 rule 4 writes this down, because Chapters 36 and 37 will tempt you to load objects early.

Behind the scenes:

order of work (summary)

setup()                      no decorator yet
require_http_methods         405 for PUT
login_required               sign in
dispatch(): event_for()      404, recorded
get() or post()

Common mistakes:

  • Adding another login_required inside setup(); the fix is to move the lookup, not to repeat the check.
  • Reading only the status code: the table’s “recorded” also shows which code ran.

Follow-up the interviewer might ask:

  • Is anything safe in setup()? (Work that does not depend on who is asking or reveal anything, such as reading a setting.)
  • How do generic views load objects? (get_object(), called from the handlers, after dispatch(): Chapter 36.)

L5 (Lead): Your team wants to convert every view to a class. Defend the house rule

What the interviewer is testing: Can you set a rule a team can follow, with reasons and a way to revisit it?

Flip to check your answerFold answer back

Perfect answer: The goal is less repetition without behaviour nobody can see. Classes pay off where a generic view fits, such as lists, detail pages, and forms, because the shared code is written once and tested once; and where a page has several handlers. They cost something everywhere: answers the page never chose, a call order spread over parent classes, and decorators that must keep their order. So ADR-006 classifies all 19 views. Eleven become classes in Chapters 35 to 37; eight stay functions, each with a reason: four one-off POST actions, a single-template home page, and three pages waiting for a later chapter. Every conversion starts with a method table, keeps chosen answers, and declares new ones. “Convert everything” trades eight clear functions for consistency; “convert nothing” keeps the repetition that caused Chapter 30’s missed checks. The rule names when to revisit: the API in Chapter 49, and any function that gains a second handler.

Behind the scenes:

ADR-006 (summary)

1  tables before any conversion
2  keep chosen answers: decorators in order
3  accept defaults only where nothing was chosen
4  nothing visitor-dependent in setup()

Common mistakes:

  • A rule without an inventory: “where it fits” means nothing until each view has a destination.
  • Arguing style instead of behaviour; the tables make the argument about answers.

Follow-up the interviewer might ask:

  • What would make you convert attendees? (Chapter 41’s download, if a shared list view would serve both the page and the file.)
  • How do you stop the rule drifting? (The ADR names its revisit points, and a review checks new views against it.)
