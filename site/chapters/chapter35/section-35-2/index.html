What You Need to Know

Views as classes

New Concept: class-based views

What problem exists? Many views repeat the same shape. Copying that shape into each function means each copy can drift, and a forgotten check in one copy is a security hole (Chapter 30).

What did people do before? Wrote helper functions, such as Otahque’s event_for() and event_to_manage(), and called them from every view.

What is it? A class-based view is a class whose instances answer requests. Instead of one function with if request.method == 'POST': inside it, the class has one method per HTTP method: get() answers GET, post() answers POST. Django’s View class supplies the machinery that picks the right method.

Why use it? Classes can inherit. A generic view such as DetailView already knows how to load one object and render it; you write only what is different. Chapters 36 and 37 rely on that.

Now let’s use it. Steps 4 to 9 build the machinery by hand, read Django’s version, and convert two of Otahque’s pages.

Django does not ask you to choose one style. Its documentation says plainly that class-based views are an alternative to functions, not a replacement, and most real projects mix both. Some experienced developers prefer functions for almost everything, because a function shows every step in one place, while a generic class spreads its steps across several parent classes. Others like classes for the repetitive pages. Both camps are right about something, which is why this chapter ends with a written rule instead of “convert everything”.

The Python you need

A class view uses four Python ideas. The first three are from Chapter 4. A class is a template for objects; each object made from it is an instance. A method is a function defined in a class; Python passes the instance as its first argument, named self, so a method can reach the instance’s attributes. A class can inherit from another and replace some of its methods; super() calls the parent’s version. The fourth may be new: because methods are attributes, Python can find one by its name at run time with the built-in functions getattr() and hasattr(): getattr(page, 'get') returns the get method, and hasattr(page, 'post') says whether there is one. That last idea is the whole trick behind dispatch(). Step 2 runs all four.

HTTP methods and the answers a page can give

Chapter 3 introduced GET (read a page) and POST (send a form). HTTP defines more methods, and anything can send them, not only a browser. A program can send PUT, PATCH, or DELETE to any address; HEAD asks for a page’s headers without its body; OPTIONS asks which methods an address accepts. A page has to answer all of them somehow.

The answer for “this page does not accept that method” is the status 405 Method Not Allowed, and HTTP requires it to carry an Allow header listing the methods the page does accept. Otahque has used 405 since Chapter 26: require_POST answers 405 with Allow: POST to anything but POST. Table 35.1 lists the answers this chapter’s tests name.

Under the Hood: why a class answers methods you never wrote

A function view sees every request that reaches its address, whatever the method, and does whatever its code does. Otahque’s event page is a function with no method check at all, so today it answers PUT and DELETE with the full page, exactly as it answers GET. A View class is different. Before your code runs, dispatch() lowers the request’s method name and looks for a method of that name on the instance. If there is none, Django answers 405 itself, and builds the Allow header from the handlers the class does have. Two handlers appear without you writing them: View defines options(), which answers OPTIONS with 200 and the Allow header, and setup() makes head() the same as get() when a class has a get() but no head(). So the moment a page becomes a class, it starts answering three kinds of request differently. Whether that matters is a decision; that it happens is not.

Evidence before change

New Concept: a method table

What problem exists? A refactor, a change to how code is written that should not change what it does, needs proof of “no change”. Otahque’s tests check what each page should do for the methods it was written for. None of them asks what happens to the methods nobody thought about.

What did people do before? Trusted the existing suite, or clicked through the pages by hand.

What is it? A method table is a test whose data is a table: one row per HTTP method, with the answer the page gives signed out and signed in. A small helper sends each request and names the answer in the words of Table 35.1.

Why use it? It is written before the change and passes on the old code, so it records what the page does today. After the change, any row that turns red is a difference, named by method and person.

Now let’s use it. Step 3 writes tables for the event page, the phone page, and Register.

Writing the test first is the habit you have kept since Chapter 9. Here it has a sharper purpose: you cannot argue afterwards about what a page “used to” do if a test wrote it down beforehand.

Two pages to convert, and one to keep

The chapter converts two pages, chosen because they teach different lessons. The event page (event_detail) has one handler, GET, and no decorators: it never chose how to answer other methods, so the class’s answers will be new, and you will decide whether to accept them. The phone page (register_phone, from Chapter 31) asks a member for the phone number an event needs, then registers them. It has two handlers, GET shows the form and POST saves it, and two decorators that chose its answers deliberately: require_http_methods(['GET', 'POST']) outside login_required. Chapter 38 will add each event’s own registration questions to the same page, so as a class it gets a name that covers both: RegistrationDetailsView, the “your details” step of registering.

Register stays a function. It is a one-off action: one method, POST, two decorators, three lines. A class would add answers to OPTIONS and HEAD and an order of decorators to keep, and give nothing back. Its table still pins it, because Chapters 37 and 39 will change how sign-in works, and its rows will show exactly what changes then.

In practice: refactoring a page other programs call

Situation. A page has been live for months. Some clients you do not control, such as a monitoring tool, a browser extension, or a partner’s script, may send it requests you never planned for.

Application. Before rewriting it, a method table records what every method gets today. The refactor then either keeps those answers or changes them on purpose, with a note in the changelog.

Consideration. A table records answers, not reasons. A row that says 200 for DELETE pins a behaviour nobody wanted; the right response is to decide, as Step 7 does, not to preserve it forever.
