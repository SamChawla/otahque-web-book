What You Need to Know

What a test proves

A test proves one thing: in this situation, the code did this. test_a_full_event_says_so proves that one full event refuses one member, on the database the test used. It does not prove that the page shows the refusal, that two requests at once are handled, or that the rule is the right rule. Each kind of test answers a different question, and Django gives you a tool for each. Figure 34.1 sets them side by side.

You have used all of them. Chapter 9’s first tests were SimpleTestCase; most of Otahque’s tests are TestCase, which wraps each test in a transaction and undoes it. The page tests use the test client, which sends a request through the whole of Django. Chapter 10 met RequestFactory, and the time-zone tests in accounts use it to build requests by hand, skipping URLs and middleware so that one piece can be checked alone. Chapter 33’s race tests needed TransactionTestCase, because other connections must see what each test commits. Sixty-two classes already share their rows through setUpTestData, which makes them once per class instead of once per test.

People often name these unit, integration, and acceptance tests. In Django terms, a unit test checks one function or method, often with SimpleTestCase; an integration test checks pieces working together, such as a page through the test client and the database; an acceptance test checks a rule the product promised, in words the person who asked for it would recognize. The last kind is not a different tool. It is a test chosen and named for a rule, and this chapter makes that link explicit.

Coverage: what ran, not what was checked

New Concept: test coverage

What problem exists? You cannot read 362 tests and know which lines of code none of them ever runs.

What did people do before? Guess, or add tests wherever a bug had appeared.

What is it? Coverage measures which lines, and which branches of each if, ran while the tests ran. coverage.py is the standard Python tool. It reports each file’s percentage and the line numbers that never ran.

Why use it? A line that never ran during the tests is a line no test checked. The report points at them.

Now let’s use it. Step 4 measures Otahque; Step 5 reads the report and writes the tests it reveals.

Coverage has one trap: a line that ran is not a line that was checked. A test can run a function and assert nothing about its result. So coverage finds candidates, places that no test reaches, and people decide what to test. This chapter sets no target percentage. You will see Otahque at 99% of its lines with three of its rules unchecked.

Tests that depend on each other

Every test should pass alone, in any order, and beside any other test. A test that passes only after another one, or fails only after another one, depends on something left behind: a row, a file, a setting, or a value in the cache. Such failures appear “at random”, because the order changes when tests are added. Django’s test --reverse runs the suite backwards, and --shuffle runs it in a random order whose seed it prints, so that the same order can be run again. Both shake out these dependencies on purpose.

Under the Hood: --parallel and worker processes

Since Chapter 32, the checkpoint runs test --parallel. Django starts one worker process for each processor core, gives each a copy of the test database, and shares the test classes out among them. Two consequences follow. First, a tool that watches the program, such as coverage.py, sees only the main process unless it is told to follow the workers. Second, a failure happens inside a worker and must be sent back to the main process; Python cannot send a traceback between processes without help, so Django asks for a small package, tblib, that can.

Continuous integration

Continuous integration, or CI, means running the project’s checks automatically on every change, on a machine nobody configured by hand. If the checks pass only on the author’s laptop, the laptop is part of the product. A CI service starts a fresh machine, installs exactly what the lock file names, starts a fresh database, and runs the same command the author runs. A green mark then means “passes from a clean start”, and a red mark names the change that broke it.

This chapter uses GitHub Actions, the CI service built into GitHub. A workflow is a file in .github/workflows/ that says when to run (on every push), on what machine, and which steps to take. Figure 34.4, in Step 10, shows Otahque’s. If you use another host, such as GitLab or Codeberg, the same steps fit its own CI file; Chapter 64 compares them.

GitHub is optional

You need a GitHub account for Steps 10 and 11 and the final push. Without one, run check.py yourself before every commit and skip the pushes; everything else in the chapter, including the release checklist and the tag, works the same.

Acceptance: rules, cases, tests, evidence

Chapter 2 wrote six product rules, PR-1 to PR-6, and planned a check for each. Table 2.3 marked every row “Planned”. Acceptance is the decision that the product meets its rules well enough to use. It needs evidence, not confidence: for each rule, the cases that prove it, the tests that check each case, and the run that shows they pass. That record is an acceptance trace. Figure 34.2 follows one rule through it.

A trace is honest only if it shows its gaps. Where a rule is only partly met, or a case is deliberately not handled, the trace says so and says why. A release with written limits can be accepted; a release with hidden ones cannot.

In practice: the pilot meeting

Situation. Soni will let Sam’s Django clinic and the Leeds meetup use Otahque next month, if she can see the evidence for each rule.

Application. Sam opens docs/acceptance/M2.md. Under PR-3 he points at three tests and the overlap case, and at the known limit written below them. He opens the green CI run for the commit he will tag.

Consideration. Soni accepts PR-3 with its limit. She asks for the keyboard check to be repeated with a screen reader before a wider launch; that request goes into the trace as future work, not into this release.

Que. 1 Otahque’s coverage report shows 99% of lines run. Name one thing that number cannot tell you.

Que. 2 A test passes when run alone and fails in the full suite. What kind of cause should you look for first?

Answer. Something an earlier test left behind: a row it committed, a value it cached, a setting it changed, or a file it wrote. Run the suite with --reverse or --shuffle to make the failure repeat, then find what the failing test assumed was empty.
