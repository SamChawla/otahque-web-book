Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead, to debugging a suite and to deciding a release. They are extension questions, not a gate to the next chapter.

L1 (Junior): What are unit, integration, and acceptance tests, in Django terms?

What the interviewer is testing: Can you map the words people use to the tools Django gives?

Flip to check your answerFold answer back

Perfect answer: A unit test checks one function or method alone, often a SimpleTestCase with no database: Otahque’s database_error() cases in LockErrorTests check one method’s answer to one error. An integration test checks pieces together: a page test sends a request through URLs, middleware, the view, the template, and the database with the test client. An acceptance test checks a rule the product promised, in terms the person who asked for it would recognize, such as “two members for the last place get one place”. It uses the same tools; what makes it acceptance is that it is chosen and named for a rule, and recorded in a trace.

Behind the scenes:

test kinds (summary)

unit         one function, alone
integration  pieces together, often through a page
acceptance   a promised rule, named in the trace

Code proof: the trace’s own test checks that every acceptance test it names exists:

Output

Found 15 test(s).
Creating test database for alias 'default'...
...
Ran 15 tests in ...s

OK

Common mistakes:

  • Calling every test that touches the database an integration test, whatever it checks.
  • Treating acceptance as a separate tool rather than a choice of what to check.

Follow-up the interviewer might ask:

  • Is RequestFactory unit or integration? (Closer to unit: it skips URLs and middleware to check one piece.)
  • Would a browser test change the kinds? (It is integration across the browser too; Chapter 58.)

L2 (Mid-Level): Predict what coverage reports for a parallel run with no settings

What the interviewer is testing: Do you know how coverage.py measures, and where processes hide code?

Flip to check your answerFold answer back

Perfect answer: A figure far too low. coverage run measures the process it starts. manage.py test --parallel starts worker processes, and the tests run there; the main process mostly waits, so most of the code that ran is never recorded. Setting parallel = true gives each process its own data file, concurrency = ["multiprocessing", "thread"] makes coverage.py start in each worker and follow threads, and coverage combine joins the files. Then the figure matches a run without --parallel.

Behind the scenes:

coverage and processes (summary)

main process   measured, mostly waiting
workers        run the tests; measured only if told
combine        joins one data file per process

Code proof: Step 4’s first run, without the settings:

Output

Name                     Cover
----------------------------------------------------
events\models.py           36%
events\views.py            28%
...
----------------------------------------------------
TOTAL                      34%

Common mistakes:

  • Reading the low figure as missing tests and writing tests for code already tested.
  • Forgetting combine, then reporting only the main process’s file.

Follow-up the interviewer might ask:

  • Why add thread to concurrency? (Naming multiprocessing alone turns off thread measurement; the race tests run code in threads.)
  • Would running without --parallel be simpler? (Yes, and slower; CI runs the same command people run.)

L3 (Senior): Defend an acceptance trace over a coverage target

What the interviewer is testing: Can you argue what evidence a release needs?

Flip to check your answerFold answer back

Perfect answer: A coverage target measures lines that ran. Otahque was at 99% of its lines while three rules had no test, including “a database error that is not a timeout must not be called busy”. Adding those tests moved the figure one point. A target invites tests that run lines and check nothing, and says nothing about a rule with no code. A trace starts from the rules: for each, the allowed and refused cases, the tests that check them, the run that passed, and the limits. It answers the release question directly. Coverage is still useful, as a list of candidates for the trace to consider.

Behind the scenes:

two kinds of evidence (summary)

coverage  which lines ran
trace     which rule, which case, which test, which run

Code proof: the report after Step 5: three rules more, one point more:

Output

Name                     Cover  Missing
----------------------------------------------------
accounts\admin.py          99%  99
accounts\models.py         97%  73
audit\views.py              0%  1
config\asgi.py              0%  11-19
config\settings.py         86%  29-30, 48, 136, 157-158, 273
config\wsgi.py              0%  11-19
events\admin.py            97%  122->124, 140, 204->exit
events\forms.py            98%  186, 189->197
events\models.py           99%  485->489
----------------------------------------------------
TOTAL                      98%

28 files skipped due to complete coverage.

Common mistakes:

  • Setting a percentage gate and calling it quality.
  • Writing a trace that lists only passing tests and hides the gaps.

Follow-up the interviewer might ask:

  • Would you ever gate on coverage? (On a drop, perhaps, as a prompt to look; never as the definition of done.)
  • How do you keep a trace from going stale? (Make it fail: TraceTests checks every name.)

L4 (Staff): A test passes alone and fails in the full suite. Diagnose it

What the interviewer is testing: Can you find shared state systematically, not by guessing?

Flip to check your answerFold answer back

Perfect answer: Something an earlier test left behind is changing this one. First make it repeatable: run with --reverse, or --shuffle and keep the seed, then narrow the run to the failing test plus the classes that ran before it. Then ask what state is shared outside the test transaction: the cache, settings changed without override_settings, files, class attributes, rows committed by a TransactionTestCase, mocks left running. In Otahque, the sign-up test failed reversed because django-allauth counts confirmation emails per address in the cache, and an earlier test had used the allowance. The fix is to start the class clean, as its neighbours do, not to reorder the tests.

Behind the scenes:

shared state (summary)

TestCase undoes   database rows of the test
not undone        cache, files, module state, mocks

Code proof: Step 6, reversed, before the fix:

Output

Found 86 test(s).
Creating test database for alias 'default'...
...
AssertionError: 0 != 1
Ran 86 tests in ...s

FAILED (failures=1)

Common mistakes:

  • Marking the test as flaky and rerunning until it passes.
  • Fixing the order instead of the state, so the next new test breaks it again.

Follow-up the interviewer might ask:

  • Why does TestCase not undo the cache? (It undoes the database transaction only; the cache is outside it.)
  • When would you use --shuffle in CI? (With the seed printed, regularly; a failing seed can be repeated.)

L5 (Lead): Defend when to tag the first release

What the interviewer is testing: Can you decide a release on evidence and say what it does not include?

Flip to check your answerFold answer back

Perfect answer: Tag when the checklist is complete on one commit: every check passes, the suite passes in reverse order, CI is green for that commit, the trace covers every rule with its gaps and limits written, and the UI checks are done at both widths. Not before, because a tag is a promise people will refer back to; and not later, waiting for perfection, because written limits are acceptable for a pilot and hidden ones are not. Otahque’s v0.1.0 goes to two events with known limits: a cancel during a request can refuse that request, the keyboard journey is checked by hand, and responsiveness has no agreed target. Each limit names the chapter that continues it.

Behind the scenes:

a release (summary)

checklist  every box, on one commit
tag        an annotated name for that commit
trace      what it proves, and what it does not

Code proof: the tag and the commits it closes:

Output

v0.1.0          First release: M2, the trace holds
36bd0f5 Add the release checklist
346a603 Trace M2, measure coverage, and check in CI
7704048 Move the tests into packages; share helpers
befbc11 Lock the last place; refuse stale edits

Common mistakes:

  • Tagging a commit CI never ran on, or tagging before the trace is updated.
  • Treating the tag as a deployment: it names a version; deploying it is Chapters 63 and 64.

Follow-up the interviewer might ask:

  • What would make you move a tag? (Nothing: make a new version, v0.1.1, and say why.)
  • When does Otahque reach 1.0? (When the product is promised to be stable for its users; that is a product decision, not a test result.)
