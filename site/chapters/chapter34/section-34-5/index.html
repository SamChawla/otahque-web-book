Checkpoint: Quiz and Challenge

Quiz

Que. 3 After Step 2, from . import views in the moved events tests failed. Why?

Flip to check your answerFold answer back

Answer. A relative import is relative to the package of the file that contains it. The file now lives in the events.tests package, so . means events.tests, which has no views. from events import views names the app.

Que. 4 Why is the shared helpers module called helpers.py and not testing.py?

Flip to check your answerFold answer back

Answer. The runner collects every module whose name matches test*.py. testing.py would be imported as a test module; helpers.py is imported only by the tests that need it.

Que. 5 Coverage under --parallel reported a fraction of the real figure until pyproject.toml was changed. What did the settings change?

Flip to check your answerFold answer back

Answer. parallel = true makes each process write its own data file, and concurrency = ["multiprocessing", "thread"] makes coverage.py follow the worker processes and threads. coverage combine joins the files before the report.

Que. 6 The three new tests of Step 5 passed at once. Why make one fail on purpose?

Flip to check your answerFold answer back

Answer. A test that has never failed may be unable to fail, for example if it asserts the wrong thing. Breaking the code it guards and seeing it fail proves it checks what it claims.

Que. 7 Why does the workflow make a new secret key for every run instead of using a repository secret?

Flip to check your answerFold answer back

Answer. The tests need some key, not the real one. A throwaway key cannot leak anything, and nothing has to be stored or rotated. The real key is a deployment matter (Chapter 63).

Que. 8 What does uv sync --locked refuse to do, and why does that matter in CI?

Flip to check your answerFold answer back

Answer. It refuses to install when uv.lock no longer matches pyproject.toml, instead of quietly resolving new versions. CI then tests exactly what the lock names, and a forgotten uv lock turns the run red.

Mini-Challenge

The report still lists accounts/models.py, line 73. Decide whether it deserves a test, and if it does, write one in a new file, accounts/tests/test_profile.py, then measure again.

Hint: open the file at that line. What calls it, and would anyone notice if it broke?

Model answer: line 73 is Profile.__str__, the name the admin’s pages use for a profile. It is cheap to test and visible to the administrator, so a test is worth it:

accounts/tests/test_profile.py

"""A profile's name, as the admin's pages show it."""
from django.test import TestCase

from accounts.models import Profile, User


class ProfileNameTests(TestCase):
    """Profile.__str__, the line coverage left untested."""

    def test_a_profile_is_named_after_its_member(self):
        sai = User.objects.create_user('sai@example.org',
                                       display_name='Sai')
        profile = Profile.objects.create(user=sai)
        self.assertEqual(str(profile), f'Profile of {sai}')

What We Learned

  • Each Django test tool answers one question; acceptance tests are tests chosen and named for a product rule.
  • A tests/ package per app lets new subjects get their own files; move first, split later, and check that the count is unchanged.
  • Shared helpers belong in one module the runner does not collect; one app’s helpers stay with its tests.
  • Coverage under --parallel needs parallel, concurrency, and coverage combine; without them the workers are not measured.
  • Coverage shows what ran, not what was checked: read the report for behaviours, and make a new test fail once.
  • --reverse and --shuffle find tests that depend on what an earlier test left behind.
  • A test that fails now and then depends on something it does not control, such as time; find it rather than rerunning.
  • tblib lets --parallel report failures from worker processes.
  • An acceptance trace links each rule to named tests, states its limits, and can check its own names.
  • CI runs one command, check.py, on a clean machine with a fresh PostgreSQL, the locked packages, and a throwaway key.
  • A release is a tagged commit that passed its checklist, with its limits written down.
