Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 and L2 check what you have just learned. L3 asks what happens inside Django when a password is stored. L4 and L5 look ahead to a growing application: attempt them now, and return to them after Chapters 18 and 20. They are extension questions, not a gate to the next chapter. Each code proof is a short file in the practice folder that starts by importing setup_django.py; run it from the folder that holds manage.py with uv run python ../practice/ followed by the file name, in PowerShell, a macOS shell, or Linux/WSL Bash.

L1 (Junior): What is AUTH_USER_MODEL, and why would a project set it?

What the interviewer is testing: Do you know how Django finds the user model, and when the choice has to be made?

Flip to check your answerFold answer back

Perfect answer: AUTH_USER_MODEL is the setting that names the model Django uses for accounts, as an app label and a model name, such as 'accounts.User'. Its default is Django’s own auth.User. A project sets it when the default does not fit, for example when people sign in with an email address instead of a username. Django then uses that model for sign-in, permissions, and the admin, and the built-in user steps aside. The setting must be chosen before the first migrate, because the user table is created then and other tables refer to it; changing it afterwards is not automatic. Code refers to the model through the setting or get_user_model(), never by importing the class.

Behind the scenes:

AUTH_USER_MODEL (summary)

unset        -> 'auth.User' is the user model
set          -> 'accounts.User'; auth.User is swapped out
first migrate -> creates the named model's table
change later -> keys and rows moved by hand

Code proof: the setting, the model Django uses, and the built-in model stepping aside:

../practice/l1_setting.py

import setup_django
from django.conf import settings
from django.contrib.auth import get_user_model
from django.contrib.auth.models import User as DefaultUser

print(settings.AUTH_USER_MODEL)
print(get_user_model()._meta.label)
print(DefaultUser._meta.label, 'swapped for',
      DefaultUser._meta.swapped)

Output

accounts.User
accounts.User
auth.User swapped for accounts.User

_meta.swapped names the model that replaced auth.User. Django creates no table for a swapped model.

Common mistakes:

  • Running migrate before deciding, then trying to change the setting.
  • Writing the setting as a module path, such as 'accounts.models.User', instead of 'app_label.ModelName'.
  • Importing django.contrib.auth.models.User in project code after swapping it out.

Follow-up the interviewer might ask:

  • “When would you keep the default user model?”
  • “Where else in a project would you expect the user model to be referred to?”

L2 (Mid-Level): AbstractUser or AbstractBaseUser with PermissionsMixin: how do you choose?

What the interviewer is testing: Can you weigh code you inherit against code you own, and name the costs of each choice?

Flip to check your answerFold answer back

Perfect answer: Start from the account the product needs, then compare what each base class brings. AbstractUser is the complete default user without its table: username, email, first and last names, the staff and active flags, the join date, permissions, and helper methods such as get_full_name(). It suits a project that wants the default with small changes, and it is less code. AbstractBaseUser provides only the password, the last sign-in time, and the password methods; PermissionsMixin adds Django’s permissions. Every other field is yours to declare, so the account holds exactly what you chose, and the code shows it. It costs more lines, and the admin and forms need more configuration because they expect the default fields. Both need a custom manager when username is removed. For Otahque, where members sign in by email and have a display name instead of first and last names, I chose AbstractBaseUser for clarity, and recorded AbstractUser as a sound alternative in the decision record.

Behind the scenes:

base classes (summary)

AbstractUser     -> default fields and methods, no table
AbstractBaseUser -> password, last_login, password methods
PermissionsMixin -> is_superuser, groups, permissions
either + email   -> USERNAME_FIELD and a custom manager

Code proof: the fields Otahque’s model leaves out, and the one it adds:

../practice/l2_fields.py

import setup_django
from django.contrib.auth.models import AbstractUser
from accounts.models import User

ours = {field.name for field in User._meta.fields}
theirs = {field.name for field in AbstractUser._meta.fields}
print('only AbstractUser:', sorted(theirs - ours))
print('only ours:', sorted(ours - theirs - {'id'}))
print(hasattr(User, 'get_full_name'),
      hasattr(AbstractUser, 'get_full_name'))

Output

only AbstractUser: ['first_name', 'last_name', 'username']
only ours: ['display_name']
False True

id is left out of the comparison because an abstract model has no primary key of its own. The last line shows a method AbstractUser provides and Otahque’s model does not.

Common mistakes:

  • Choosing AbstractBaseUser and forgetting PermissionsMixin, then finding that permissions and the admin do not work.
  • Removing username from AbstractUser without writing a manager.
  • Treating the choice as a security decision rather than one of fit and maintenance.

Follow-up the interviewer might ask:

  • “What would you need to change in the admin for each choice?”
  • “When would a separate profile model be better than more fields on the user?”

L3 (Senior): How does Django store and check a password?

What the interviewer is testing: Do you understand salted, slow hashing, and why nothing is decrypted?

Flip to check your answerFold answer back

Perfect answer: set_password() passes the password to the first hasher in Django’s PASSWORD_HASHERS setting, which by default is PBKDF2 with SHA-256. The hasher chooses a random salt for this password, applies a one-way function many times, 1,500,000 in Django 6.1.2, and returns algorithm$iterations$salt$hash, which is what the password field stores. check_password() reads the algorithm, iteration count, and salt from that value, repeats the calculation on the password typed, and compares the results in constant time. Nothing is decrypted, because the function cannot be reversed. The salt means equal passwords give different values and precomputed tables do not help; the iteration count makes each guess slow. Because the parameters are stored with each hash, a newer Django with a higher count, or a different algorithm, can upgrade a hash when its owner next signs in. set_password(None) stores an unusable password, for accounts that must not sign in with one.

Behind the scenes:

password storage (summary)

set_password(raw) -> new salt; PBKDF2-SHA256, many times
stored            -> pbkdf2_sha256$1500000$salt$hash
check_password()  -> recompute with stored salt, compare
set_password(None) -> unusable: no password matches

Code proof: the same password hashed twice, then checked:

../practice/l3_hash.py

import setup_django
from django.contrib.auth.hashers import (
    check_password,
    make_password,
)

first = make_password('correct horse')
second = make_password('correct horse')
print(first == second)
print(first.split('$')[:2])
print(check_password('correct horse', first))
print(check_password('correct horse', make_password(None)))

Output

False
['pbkdf2_sha256', '1500000']
True
False

make_password() is the function set_password() uses. Different salts make the two values differ, the right password still checks, and no password matches an unusable one.

Common mistakes:

  • Assigning user.password = 'secret' directly, which stores the plain text and makes every check fail.
  • Hashing passwords with a fast general-purpose hash, such as plain SHA-256.
  • Believing an administrator can look up a member’s password.

Follow-up the interviewer might ask:

  • “How would you raise the cost of hashing for existing users?”
  • “What should a site do if its database of hashes is stolen?”

L4 (Staff): Another app needs to point at the user. How should it refer to it, and why?

What the interviewer is testing: Can you keep apps independent of one concrete user class, and explain how Django resolves the reference?

Flip to check your answerFold answer back

Perfect answer: In a model relationship, such as a registration’s member, write models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=...). The setting is a string label, so Django can resolve it after all apps are loaded, without import-order problems, and the migration it generates depends on the setting rather than on a particular app. In code that runs after start-up, such as views, forms, and tests, call get_user_model(), which returns the class the setting names. Importing accounts.models.User directly would tie the app to one project’s model, would break if the model changed, and in a reusable app would ignore the project’s choice. Inside the accounts app itself, importing its own model is fine. Chapter 20 uses this rule for Registration and Organizer assignment.

Behind the scenes:

referencing (summary)

ForeignKey(AUTH_USER_MODEL) -> a label, resolved later
get_user_model()     -> the class, after apps are loaded
migration            -> depends on the swappable setting
import accounts.User -> only inside accounts

Code proof: a practice model that points at the setting, resolved to Otahque’s class:

../practice/l4_reference.py

import setup_django
from django.conf import settings
from django.db import models


class Note(models.Model):
    author = models.ForeignKey(
        settings.AUTH_USER_MODEL, on_delete=models.CASCADE
    )

    class Meta:
        app_label = 'events'


print(settings.AUTH_USER_MODEL)
print(Note._meta.get_field('author').related_model)

Output

accounts.User
<class 'accounts.models.User'>

The practice model exists only while the script runs; it is not added to the project. The relationship was written with a string, and Django turned it into the class.

Common mistakes:

  • Copying 'auth.User' into a relationship from an older tutorial, which check refuses with fields.E301 once the model is swapped out.
  • Importing django.contrib.auth.models.User in a project that has replaced it.
  • Writing 'accounts.User' as a literal in many places instead of using the setting.

Follow-up the interviewer might ask:

  • “Why does a relationship use the setting, but a view use get_user_model()?”
  • “What does the generated migration for such a relationship depend on?”

L5 (Lead): After launch, the team wants a different user model. What is involved, and how would you plan it?

What the interviewer is testing: Can you judge the cost of a late schema change and plan it safely, rather than treating it as a settings edit?

Flip to check your answerFold answer back

Perfect answer: Changing AUTH_USER_MODEL after tables exist is not a settings change. Django’s documentation says it cannot be done automatically: the user model must be created in its app’s first migration, every foreign key to the old table must move to the new one, and Django’s own tables for permissions, groups, admin history, and sessions refer to it too. I would first ask whether the need can be met without swapping, for example by adding fields to the current custom model with an ordinary migration, or by adding a profile model. If a swap is unavoidable, I would inventory every reference and row, write the new model and its migrations, copy users and their password hashes, which stay valid, move each foreign key in a data migration, and rehearse the whole change on a copy of production data with a tested way back. I would schedule it with the team, record it as a new decision record that supersedes the old one, and verify sign-in, permissions, and ownership checks afterwards. The cheapest version is the one Otahque took: decide before the first migrate.

Behind the scenes:

late change (summary)

user model -> in its app's first migration
tables     -> auth, admin, sessions, our own keys
swap       -> new model, copy rows, move keys
better     -> extend the current model, or add a profile

Code proof: the built-in user is the swappable model, and every migration that depends on the user depends on the first migration of the app the setting names:

../practice/l5_swap.py

import setup_django
from django.conf import settings
from django.contrib.auth.models import User as DefaultUser
from django.db import migrations

print(DefaultUser._meta.swappable)
dependency = migrations.swappable_dependency(
    settings.AUTH_USER_MODEL
)
print(dependency)

Output

AUTH_USER_MODEL
('accounts', '__first__')

__first__ means “the first migration of accounts”, which is why Chapter 18 must create accounts.User in accounts/migrations/0001_initial.py.

Common mistakes:

  • Changing the setting on a live project and running migrate, expecting Django to move the data.
  • Forgetting Django’s own tables that refer to the user.
  • Swapping when an extra field or a profile would have met the need.

Follow-up the interviewer might ask:

  • “How would you keep members signed in, or not, during the switch?”
  • “What would you put in the decision record that supersedes ADR-002?”
