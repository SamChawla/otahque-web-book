How We Build It

Start from Chapter 16, in the folder containing manage.py, with your own .env, the locked environment, 20 passing tests, the Event model committed, and a db.sqlite3 with no tables. You create a new app, accounts, with three files of your own: accounts/tests.py, written first; accounts/managers.py; and accounts/models.py. You change one existing file, config/settings.py, twice: once to install the app and once to name the user model. You add two decision records under docs/adr/. A practice script goes in ../practice, beside setup_django.py from Chapter 16. Pages, templates, and the Event model stay as they are. At the end, 25 tests pass, Django loads accounts.User as the user model, no migration file exists, and the database still has no tables.

The Custom Way

This illustration stores accounts by hand, with Python’s sqlite3 and hashlib modules; do not add it to the project:

illustration_only/users.py (not part of the project)

import hashlib
import sqlite3

db = sqlite3.connect(':memory:')
db.execute(
    'CREATE TABLE users (id INTEGER PRIMARY KEY,'
    ' email TEXT UNIQUE NOT NULL, password TEXT NOT NULL)'
)


def add_user(email, password):
    digest = hashlib.sha256(password.encode()).hexdigest()
    db.execute('INSERT INTO users (email, password)'
               ' VALUES (?, ?)', (email, digest))


add_user('sai@example.org', 'correct horse')
add_user('raj@example.org', 'correct horse')
rows = db.execute('SELECT password FROM users').fetchall()
print(rows[0] == rows[1])

Output

True

It looks careful: the email is unique and the password is hashed. The output shows the first problem. Two members who chose the same password store the same value, so cracking one cracks both, and a table of precomputed hashes cracks common passwords at once. SHA-256 is also fast by design, so an attacker with a stolen table can try a great many guesses quickly. Fixing that means a salt for each password, a deliberately slow function, and a way to upgrade old hashes when the function changes. After that come sign-in and sign-out, sessions, permissions, an admin screen, and password reset, each with its own mistakes to avoid. Django’s user model supplies all of these, and the work below is to describe Otahque’s account so that Django can use them.

Step 3: Write the tests first

The tests describe the user model before it exists. startapp wrote accounts/tests.py with an import and a comment; replace its contents with this listing:

accounts/tests.py

from django.contrib.auth import get_user_model
from django.core.exceptions import ValidationError
from django.test import SimpleTestCase

from .models import User


class UserModelTests(SimpleTestCase):
    def test_user_model_is_accounts_user(self):
        self.assertIs(get_user_model(), User)
        self.assertEqual(User.USERNAME_FIELD, 'email')

    def test_password_is_stored_as_a_hash(self):
        user = User(email='sai@example.org',
                    display_name='Sai')
        user.set_password('correct horse')
        self.assertNotEqual(user.password, 'correct horse')
        self.assertTrue(
            user.password.startswith('pbkdf2_sha256$')
        )
        self.assertTrue(user.check_password('correct horse'))
        self.assertFalse(user.check_password('wrong horse'))

    def test_email_and_display_name_are_required(self):
        user = User()
        user.set_password('correct horse')
        with self.assertRaises(ValidationError) as caught:
            user.full_clean(validate_unique=False)
        self.assertEqual(
            sorted(caught.exception.message_dict),
            ['display_name', 'email'],
        )


class UserManagerTests(SimpleTestCase):
    def test_create_user_requires_an_email(self):
        with self.assertRaisesMessage(
            ValueError, 'An email address is required.'
        ):
            User.objects.create_user(
                email='', password='correct horse',
                display_name='Sai',
            )

    def test_superuser_flags_must_be_true(self):
        with self.assertRaisesMessage(
            ValueError, 'needs is_superuser=True.'
        ):
            User.objects.create_superuser(
                email='sam@example.org',
                password='correct horse',
                display_name='Sam',
                is_superuser=False,
            )

Each test checks one promise. The first checks that get_user_model() returns Otahque’s class, which proves the setting is in place, and that people sign in with the email. The second checks that a password becomes a PBKDF2 hash, that the right password is accepted, and that a wrong one is refused. The third builds an empty user with a password and runs full_clean(); exactly two fields must complain, display_name and email, which proves they are required and that nothing else is. validate_unique=False skips the uniqueness check, because checking that no other account has the same email is a database query. The last two tests check the manager’s two refusals by their messages, so that a different error cannot pass by accident; assertRaisesMessage() accepts a message that contains the given text.

All five run without a database, as Chapter 16’s model tests did, and each refusal happens before the manager would save. That also marks their limit. They do not prove that create_user() or create_superuser() stores a user, because there is no table to store one in. Chapter 18 adds those tests once the tables exist.

Step 4: Write the manager, the model, and the setting

Create accounts/managers.py with the contract from What You Need to Know:

accounts/managers.py

from django.contrib.auth.base_user import BaseUserManager


class UserManager(BaseUserManager):
    """Create Otahque users, who sign in with an email."""

    use_in_migrations = True

    def create_user(self, email, password=None,
                    **extra_fields):
        if not email:
            raise ValueError('An email address is required.')
        email = self.normalize_email(email)
        user = self.model(email=email, **extra_fields)
        user.set_password(password)
        user.save(using=self._db)
        return user

    def create_superuser(self, email, password=None,
                         **extra_fields):
        extra_fields.setdefault('is_staff', True)
        extra_fields.setdefault('is_superuser', True)
        for flag in ('is_staff', 'is_superuser'):
            if extra_fields[flag] is not True:
                raise ValueError(
                    f'A superuser needs {flag}=True.'
                )
        return self.create_user(
            email, password, **extra_fields
        )

self.model is the model this manager is attached to, so the manager never names User itself. save(using=self._db) saves to whichever database the manager was asked to use, which matters only once a project has more than one. use_in_migrations = True makes the manager available inside migrations, as Django’s own user manager does; Chapter 18’s first migration records it. create_superuser() uses setdefault(), which sets a value only when the caller has not given one, so a caller who passes is_superuser=False is refused rather than silently corrected. The manager does not check display_name: the model requires it, so full_clean() and, later, forms report a missing one.

Then replace the contents of accounts/models.py with the model:

accounts/models.py

from django.contrib.auth.models import (
    AbstractBaseUser,
    PermissionsMixin,
)
from django.db import models
from django.utils import timezone

from .managers import UserManager


class User(AbstractBaseUser, PermissionsMixin):
    """An Otahque member, who signs in with an email."""

    email = models.EmailField('email address', unique=True)
    display_name = models.CharField(max_length=100)
    is_active = models.BooleanField(default=True)
    is_staff = models.BooleanField(default=False)
    date_joined = models.DateTimeField(default=timezone.now)

    objects = UserManager()

    USERNAME_FIELD = 'email'
    EMAIL_FIELD = 'email'
    REQUIRED_FIELDS = ['display_name']

    def __str__(self):
        return self.email

Table 17.2 explains each field the table will hold.

EmailField is a CharField that also checks that its value looks like an email address. default=timezone.now passes the function itself, without brackets, so that Django calls it for each new user rather than once when the file loads. __str__() returns the email, which is unique, so lists in the admin and error messages name each account unambiguously. Public pages must never show it: other members see the display name, which later templates use. The values 100 for display_name and the default flags are proposals recorded with the model, not product rules from Chapter 2.

Do not run anything yet. The model now exists beside Django’s built-in auth.User, and Django still uses the built-in one, so the two clash.

Common Error: a user model without AUTH_USER_MODEL

If you run check or the tests now, Django stops with four fields.E304 errors, such as Reverse accessor 'Group.user_set' for 'accounts.User.groups' clashes with reverse accessor for 'auth.User.groups'. Each error’s hint suggests adding a related_name, which would silence the clash but leave Django using its own user. The real cause is the missing setting: once AUTH_USER_MODEL names accounts.User, the built-in model steps aside and the clash disappears.

Add the setting to config/settings.py, directly after INSTALLED_APPS:

config/settings.py (after INSTALLED_APPS)

# Otahque's own user model, set before the first migration.
# See docs/adr/ADR-002-user-model.md.
AUTH_USER_MODEL = 'accounts.User'

The check reports a user model’s most likely mistakes before anything runs. Removing unique=True from email gives (auth.E003) 'User.email' must be unique because it is named as the 'USERNAME_FIELD'. Adding 'email' to REQUIRED_FIELDS gives (auth.E002) The field named as the 'USERNAME_FIELD' for a custom user model must not be included in 'REQUIRED_FIELDS'. A misspelled model name in the setting, such as 'accounts.Users', stops every command with ImproperlyConfigured: AUTH_USER_MODEL refers to model 'accounts.Users' that has not been installed, and so does a correct name when the app is missing from INSTALLED_APPS.

The check cannot see everything. If objects = UserManager() is left out, check still reports no issues, and Django gives the model an ordinary manager without create_user(). The last two tests catch that: they fail with AttributeError: 'Manager' object has no attribute 'create_user', and the same for create_superuser.

Common Error: running migrate to see the table

With the setting in place and no migration for accounts, migrate stops before creating anything, with ValueError: Dependency on app with no migrations: accounts. That is the safety net working: Django’s own apps depend on the user model, which has no migration yet. This message is what Django 6.1.2 was observed to print; the documentation does not promise its wording. A failed migrate leaves db.sqlite3 with no tables, so there is nothing to recover; carry on. If makemigrations has run instead, it has written accounts/migrations/0001_initial.py and events/migrations/0001_initial.py. Keep them: move both into ../practice, so that Chapter 18 starts from no migrations, and do not delete them in this chapter.

Step 5: Inspect the user model

import setup_django  # loads Otahque's settings first

Step 6: Record the decision

Chapter 5 drafted ADR-001 on paper and said that decision records belong in docs/adr/, versioned with the code. Chapter 15 put the ERD in docs/design/. Now the project gets its decision records: ADR-001, transcribed from Chapter 5’s Table 5.4, and ADR-002 for the user model. Both stay Proposed, because nobody responsible for a real Otahque has accepted them. Create a docs/adr folder beside docs/design, with mkdir docs/adr, the same command in every shell. Then create the first file:

docs/adr/ADR-001.md

# ADR-001: Build a server-rendered Django application

## Status

Proposed, October 2026. Not yet reviewed or accepted.

## Context

Organizers and attendees need one current registration
record. Ownership and capacity rules must hold whatever a
browser sends. Main journeys must work with a keyboard and
on narrow screens. A small volunteer team must be able to
build and maintain the application, and the book's readers
are learning Django.

## Options

- A: a connected form and spreadsheet.
- B: a server-rendered Django application with a database.
- C: a Django API with a separate JavaScript client.

## Decision

Build the first release as one Django application that
renders HTML pages on the server, stores records in a
relational database, and applies Otahque's rules in its
views and models.

## Consequences

One application to build, test, and host. Rules run in one
place. Pages work with links and forms before any
JavaScript. Highly interactive screens need extra work, and
other software has no API until one is added.

## Revisit if

A mobile or partner application needs Otahque's data;
check-in or other work must continue offline; measurement
shows that server rendering cannot meet an agreed
performance target.

# ADR-002: A custom user model that signs in by email

## Status

Proposed, November 2026. Not yet reviewed or accepted.

## Context

Members sign in with a unique email address and are shown
by a display name; the ERD (docs/design/erd.md) gives a
member no username. Django's default user signs in with a
username and does not require a unique email. The user
model must be chosen before the first migration, because
Django cannot switch it automatically once tables exist.

## Options

- A: Django's default user, with an extra sign-in backend
  that accepts an email address.
- B: AbstractUser, with username removed and email unique.
- C: AbstractBaseUser with PermissionsMixin, declaring each
  remaining field.

## Decision

Option C. accounts.User signs in with a unique email, has
a required display_name, and is created through
UserManager. AUTH_USER_MODEL names it. It implements the
ERD's Member entity.

## Consequences

Every stored field is declared or comes from a small,
documented class. There is more code than option B, no
get_full_name() or email_user(), and the admin site
(Chapter 23) needs a custom user admin. Other code refers
to the model through settings.AUTH_USER_MODEL or
get_user_model(). is_staff and is_superuser are Django
flags, not Otahque's organizer or administrator roles.

## Open questions

Whether addresses that differ only in letter case are one
account is decided in Chapter 21, before sign-up. Until
then, only the domain is lowercased.

## Revisit if

Members need a public username, or sign-in moves to an
outside identity provider. Changing the model after the
first migration needs a planned data migration.
