What You Need to Know

Who someone is, and what they may do

Two questions run through every page that is not public. The first is “who is this?”, and the second is “may they do this?”. Keeping them apart avoids a common confusion.

New Concept: authentication, authorization, and the user model

What problem exists? A web application has to recognize returning people and decide what each of them may see and change. Without a shared record of who someone is, every page would invent its own idea of a person.

What did people do before? Each application wrote its own accounts table, its own password checks, and its own rules for who may do what, and each one repeated the same mistakes.

What is a user model? Authentication establishes who someone is, usually from something they know, such as a password. Authorization decides what an authenticated person may do. Django’s authentication system keeps both around one model, the user model: each row is one account, and Django’s sign-in, sessions, permissions, and admin site all work with it.

Why use Django’s? Its password storage, sign-in checks, and permissions are tested by many projects, and other Django components, such as the admin, already know how to use them.

Now let’s use it. The rest of this part decides which user model Otahque has and how other code finds it.

Chapter 2 named four kinds of people, and the user model covers only some of them. A visitor is anyone reading public pages, without an account; a visitor has no row at all. A member has an account and signs in; in the ERD, the MEMBER entity is that account, and in Django it becomes a user. An organizer is a member who has been assigned to manage a particular event. That is a fact about the member and the event together, which the ERD records as an organizer assignment, not as part of the member’s own row. The administrator is the person Chapter 2 makes responsible for accounts and access, including granting and removing organizer access. How that responsibility is given to someone is still an open policy. Django’s own flags, which you meet below, do not settle it.

Choosing the user model before the first migration

Django finds the user model through one setting, AUTH_USER_MODEL. When a project does not set it, its value is 'auth.User': the User model that ships in django.contrib.auth, which Chapter 16’s L5 code proof printed.

New Concept: AUTH_USER_MODEL

What problem exists? Many parts of Django, and later parts of Otahque, need to point at “the user” without knowing in advance which model a project uses.

What did people do before? Code imported Django’s built-in User class directly, and a project that needed different fields had to keep a second “profile” table beside it or change Django itself.

What is AUTH_USER_MODEL? A setting holding a model label, the app label and the model name joined by a dot, such as 'accounts.User'. Django uses the model it names everywhere a user is needed, and the built-in auth.User steps aside. Django calls this a swappable model.

Why set it now? The first migrate creates the user model’s table, and other tables refer to it. Django’s documentation says that changing the setting once those tables exist cannot be done automatically: keys and rows would have to be moved by hand. Setting it before the first migration avoids that work entirely.

Now let’s use it. Otahque sets it to a model of its own, accounts.User.

Django does not require every project to replace the default. Since Django 5.1, its documentation says that a new project “can” set up a custom user model from the start, and asks the reader to consider whether it is right for the project; earlier versions recommended it more strongly, and many tutorials still repeat that older advice. The current position is a choice, so a project needs a reason. Otahque has one. The ERD’s member signs in with a unique email address and has a display name, and no username. Django’s default user has a required, unique username, an email that does not have to be unique, and first_name and last_name fields that the ERD does not ask for. Making the default user sign in by email would need extra code to cope with two accounts sharing an address. A custom model can make the email itself the unique sign-in field.

Three ways to get a user model

Django offers three starting points. Table 17.1 compares what each brings.

AbstractUser and AbstractBaseUser are abstract models: classes that hold fields and methods for other models to inherit, and that have no table of their own. AbstractUser is the default user without its table. You inherit everything, then change what you need, such as removing username and making email unique. AbstractBaseUser holds only the core of an account: the hashed password, the time of the last sign-in, and the methods that set and check a password. PermissionsMixin adds is_superuser, membership of groups, and individual permissions, which Chapter 30 uses. Together they give you an account in which every other field is one you declared.

Otahque uses AbstractBaseUser with PermissionsMixin. The reason is clarity, not security. Every field the user table will hold is either declared in Otahque’s own code or comes from one of two small, documented classes, so a reader can see the whole account in one place, and the table holds no name fields that the ERD did not ask for. The cost is real: more lines now, no get_full_name() or email_user() methods, and more configuration when Chapter 23 sets up the admin site.

Prefer AbstractUser?

AbstractUser is a sound choice, and many projects make it. With username = None, a unique email, a display_name, and a manager, it would meet Otahque’s needs in fewer lines, and it keeps Django’s name methods and email helper. Its table also has first_name and last_name columns, left as empty text. Choose it when you want the default behaviour with small changes; choose AbstractBaseUser when you want each field to be a deliberate decision. Both need a custom manager once username is gone, and both need a custom admin and custom forms later. Otahque’s decision record names AbstractUser as the option not chosen, with its reasons.

Telling Django how the model is used

A custom user model answers three questions with class attributes, and supplies a manager.

  • USERNAME_FIELD names the field people sign in with. It must be unique: Django’s sign-in looks up exactly one account by it. Otahque uses 'email'.
  • REQUIRED_FIELDS lists the extra fields that Django’s createsuperuser command asks for, beyond the sign-in field and the password. It must not include USERNAME_FIELD. Otahque lists 'display_name'. It affects only that command; the model’s own field options decide what is required everywhere else.
  • EMAIL_FIELD names the field that holds the email address, which Django’s password reset uses in Chapter 29. For Otahque it is the same field, 'email'.

New Concept: a model manager

What problem exists? Creating a user is more than saving a row. The email has to be tidied, the password has to be hashed, and a superuser needs particular flags. Doing this by hand in every place that creates users would sooner or later miss a step.

What did people do before? They wrote helper functions in different modules and hoped that everyone called the right one.

What is a manager? The object on a model’s class through which Django creates and finds rows, objects by default, as in User.objects. A custom manager adds methods to it. For users, Django expects two: create_user() and create_superuser().

Why write one? Django’s own tools call these methods. createsuperuser calls create_superuser() with the answers it collects. The manager Django provides for its default user expects a username, so a model without one needs its own.

Now let’s use it. Otahque’s UserManager follows a short contract, below.

Django supplies a base class, BaseUserManager, with a normalize_email() method. Otahque’s manager builds on it with two methods:

  • create_user(email, password=None, **extra_fields) refuses an empty email with a ValueError, before anything else happens. It then normalizes the email, builds the user with any other fields, such as display_name, hashes the password, saves the user, and returns it. A password of None stores an unusable password: the account exists, but no password signs in to it.
  • create_superuser(email, password=None, **extra_fields) sets is_staff and is_superuser to True unless they were given. It refuses a superuser with either flag set to anything other than True, then hands over to create_user(), so the email and password rules live in one method.

normalize_email() does less than its name suggests. It lowercases only the part after the @, the domain, so Sai@EXAMPLE.org becomes Sai@example.org. The part before the @ is left as typed, because mail systems may treat its capital letters as significant. Whether Otahque treats Sai@example.org and sai@example.org as one account is the product question that Chapter 21 settles before sign-up. Until then, the model makes no promise either way.

Answer. Django adds id, a BigAutoField, because no field declares a primary key, as with Event. email and display_name are declared in Otahque’s class. Fields the ERD did not list include password and last_login from AbstractBaseUser, is_superuser from PermissionsMixin, and the declared is_active, is_staff, and date_joined. They serve Django’s authentication; they are implementation details, not new product requirements.

How Django stores a password

Under the Hood: what set_password() stores

A user’s password field never holds the password. set_password() passes it to a hasher, which runs a one-way function many times over the password and a salt, a random value chosen for this password alone. Django 6.1’s default hasher is PBKDF2 with SHA-256, and the installed Django 6.1.2 repeats it 1,500,000 times, which makes each guess slow for anyone who steals the table. The field stores four parts joined by dollar signs: the algorithm, the number of iterations, the salt, and the resulting hash. To check a password, check_password() reads the algorithm, iterations, and salt from the stored value, repeats the calculation on what was typed, and compares the two results. Nothing is ever decrypted, because no step can be reversed. Because each password has its own salt, two members with the same password store different values. And because the algorithm and the iteration count are stored with each hash, a later Django can raise the count, or change the algorithm, and upgrade each password when its owner next signs in.

This read-only example shows the parts. You will run something like it in Step 5:

Python

user.set_password('correct horse')
print(user.password.split('$')[:2])

Output

['pbkdf2_sha256', '1500000']

Only the first two parts are printed; the salt and the hash follow. Storing a hash protects members’ passwords if the database is ever copied, but it is not a whole security policy. Which passwords Otahque accepts is set by the password validators already listed in the settings, which Chapter 29 reviews with password reset; the security review in Chapters 59 and 60 revisits both.

Referring to the user from other code

Code outside the accounts app should not import the user class by name. If it wrote from accounts.models import User everywhere, a reusable app, or Django’s own apps, could not work with a project that uses a different model. Django gives two documented ways instead:

  • In a relationship, such as a registration’s link to its member, use the setting itself: models.ForeignKey(settings.AUTH_USER_MODEL, ...). Chapter 20 writes these relationships.
  • In other code, such as a view or a test, call get_user_model() from django.contrib.auth, which returns whichever model the setting names.

Figure 17.1 puts the pieces together. The ERD stays a design. accounts.User implements its member, the setting names that model, and later code goes through the setting.

In practice: an organizer is not a staff flag

Situation. Sam needs to manage the November meetup, and a teammate suggests ticking is_staff on his account so that he “has access”.

Application. is_staff decides only whether an account may sign in to Django’s admin site, and is_superuser grants every Django permission without assigning any. Neither says which events Sam may manage. In Otahque, that is an organizer assignment for one event, which can be revoked and leaves a record (Chapters 20 and 30). Who may grant it is the administrator’s workflow from Chapter 2, which Chapters 23 and 30 decide.

Consideration. Ticking a framework flag to stand in for a product role works on the first day and leaks access later: Sam could sign in to the admin site, and the next shortcut, is_superuser, would let him change every event. Keep each flag to its documented meaning, and give product roles their own records.
