Checkpoint: Quiz and Challenge

Quiz

Que. 2 Why does Otahque choose its user model in this chapter, rather than after the first migrate?

Flip to check your answerFold answer back

Answer. The first migrate creates the user model’s table, and other tables refer to it. Django cannot switch the user model automatically once those tables exist, so changing it later would mean moving keys and rows by hand. With no tables yet, the choice costs nothing to make.

Que. 3 A teammate writes from accounts.models import User in the Registration model in Chapter 20. What should they write instead, and why?

Flip to check your answerFold answer back

Answer. models.ForeignKey(settings.AUTH_USER_MODEL, ...), which refers to whichever model the setting names. Code outside a relationship would call get_user_model(). Both keep working if the user model ever changes, and Django can resolve the model when the apps load.

Que. 4 Two members choose the same password. Are their stored password values the same?

Flip to check your answerFold answer back

Answer. No. set_password() picks a new random salt for each password, and the salt is part of what is hashed, so the stored values differ. check_password() reads each salt back from the stored value to check a typed password.

Que. 5 What does User.objects.normalize_email('Raj@EXAMPLE.ORG') return, and what question does that leave open?

Flip to check your answerFold answer back

Answer. Raj@example.org: only the domain is lowercased. Whether Raj@example.org and raj@example.org count as one account is a product decision for Chapter 21, made before anyone can sign up.

Que. 6 The five tests pass. Have they proved that create_user() saves a user?

Flip to check your answerFold answer back

Answer. No. They prove that the setting names Otahque’s model, that passwords are hashed, that email and display name are required, and that the manager refuses an empty email and a superuser without its flags. Every refusal happens before the save. Saving needs a table, so Chapter 18 tests successful creation.

Mini-Challenge

Que. 7 A teammate proposes adding is_organizer = models.BooleanField(default=False) to accounts.User, so that pages can check user.is_organizer. Using the ERD and Chapter 2’s rules, explain in your notes why Otahque records an organizer assignment instead. Do not change accounts/models.py: the user model is complete for this chapter, and Chapter 18 starts from it as it is.

Flip to check your answerFold answer back

Answer. A flag on the user answers the wrong question. Chapter 2 says organizers manage only the events assigned to them, so the fact to record is “this member organizes this event”, which belongs to a member and an event together; one boolean would let any organizer manage every event. Organizer access is also granted and removed through the administrator’s workflow, and the ERD’s ORGANIZER ASSIGNMENT keeps assigned_at and revoked_at, so removing access leaves a record of who had it and when, while turning a flag off erases that history. A member can organize one event and attend another, which an assignment row expresses directly. A flag would also invite confusion with is_staff, which is only Django’s admin-site gate. Chapter 20 models the assignment and Chapter 30 checks it.

What We Learned

  • Authentication establishes who someone is; authorization decides what they may do. Django’s user model is the account record both rely on.
  • AUTH_USER_MODEL names the user model. It is set before the first migration, because Django cannot switch it automatically once tables refer to it.
  • Django permits a custom user model from the start; Otahque chooses one because its members sign in with a unique email address and have no username.
  • AbstractUser changes the default user; AbstractBaseUser with PermissionsMixin starts from the core of an account, so every other field is declared. Both need a manager once username is gone.
  • USERNAME_FIELD, REQUIRED_FIELDS, and EMAIL_FIELD tell Django how the model is used; the manager’s create_user() and create_superuser() tell it how to create users.
  • A password is stored as a salted, slow, one-way hash with its algorithm and iteration count, and checked by repeating the calculation.
  • Other code refers to the user through settings.AUTH_USER_MODEL in relationships and get_user_model() elsewhere.
  • is_staff and is_superuser are Django flags, not Otahque’s organizer or administrator roles.
