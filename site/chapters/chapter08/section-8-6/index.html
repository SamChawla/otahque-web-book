Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 and L2 check what you have just learned. L3 asks how it works underneath. L4 and L5 ask about decisions that later chapters build on, when Otahque gains automated checks and a production server: attempt them now, and return to them when you reach those chapters. Use the readiness checkpoint to decide whether to continue. If an answer is difficult, revisit its worked example and explain the result in your own words. L4 and L5 are extension questions, not a gate to the next chapter.

L1 (Junior): Why should a Django project’s secret key stay out of settings.py and out of Git?

What the interviewer is testing: Do you know what the secret key protects, and why recording it is the risk?

Flip to check your answerFold answer back

Perfect answer: Django uses the secret key to sign values it will later trust, such as session data, password reset links, and messages. Anyone who knows the key can create values that Django accepts as genuine. A key written in settings.py is known to everyone who can read the code, and once it is committed, every copy of the history contains it, even after a later commit deletes it. So each environment gets its own key, supplied from outside the code, and a key that has been exposed is replaced rather than hidden.

Behind the scenes:

django/core/signing.py (summary, not the source)

# dumps(value) serializes the value, then appends a signature
# computed from the value and SECRET_KEY (an HMAC).
# loads(token) recomputes the signature; if the value or the
# key differs, it raises BadSignature instead of returning it.

Code proof: in PowerShell, a macOS shell, or Linux/WSL Bash, beside manage.py:

Terminal

uv run python manage.py shell -c "
from django.core import signing
token = signing.dumps({'member': 'sai'})
print(signing.loads(token))
def check(value, key=None):
    try:
        return signing.loads(value, key=key)
    except signing.BadSignature:
        return 'rejected'
print(check(token + 'a'))
print(check(token, key='another-key'))
"

Output

12 objects imported automatically (use -v 2 for details).

{'member': 'sai'}
rejected
rejected

The signed value comes back intact; a changed token and a different key are both rejected.

Common mistakes:

  • Thinking the key encrypts data; it signs it, so anyone can still read a signed value.
  • Deleting the key in a later commit and assuming the history no longer holds it.
  • Sharing one key between development and production.

Follow-up the interviewer might ask:

  • “What happens to signed-in members when the key changes?”
  • “How would you replace a key without signing everyone out at once?”

L2 (Mid-Level): How do you make a Django project reproducible on a teammate’s computer?

What the interviewer is testing: Can you separate what is recorded from what each computer supplies, and prove the result?

Flip to check your answerFold answer back

Perfect answer: Record everything that should be the same: the code, .python-version, pyproject.toml, and uv.lock, which pins every package and its checksums for every operating system. Keep out what each computer supplies: .venv/, the local database, and .env, with .env.example listing the names it needs. The teammate clones the repository, runs uv sync --locked, which fails rather than changing the lock, creates their own .env with their own key, and runs the system checks. If uv lock --check passes and the checks pass, both computers run the same versions with their own values.

Behind the scenes:

uv.lock (summary, not the file)

# one [[package]] table per package, for example:
#   name = "tzdata", version = "2026.5"
#   with the download URL, size, and sha256 checksum
# platform conditions sit on the dependency that needs them:
#   { name = "tzdata", marker = "sys_platform == 'win32'" }

Code proof: ask uv to show the lock as a list of exact pins:

Terminal

uv export --format requirements-txt --no-hashes

Output

Resolved 6 packages in ...
# This file was autogenerated by uv via the following command:
#    uv export --format requirements-txt --no-hashes
asgiref==3.13.0
    # via django
django==6.1.2
    # via otahque
python-decouple==3.8
    # via otahque
sqlparse==0.6.0
    # via django
tzdata==2026.5 ; sys_platform == 'win32'
    # via django

Every package, direct and transitive, has one exact version, and tzdata carries its Windows condition.

Common mistakes:

  • Recording .venv/ instead of the lock.
  • Pinning only the direct dependency, so transitive versions drift.
  • Sharing a .env file instead of documenting its names.

Follow-up the interviewer might ask:

  • “What is the difference between uv sync and uv sync --locked?”
  • “How would you upgrade one package without changing the others?”

L3 (Senior): How does Django find and load its settings, and what happens when a required value is missing?

What the interviewer is testing: Do you understand the lazy settings object, the merge over defaults, and where a configuration error appears?

Flip to check your answerFold answer back

Perfect answer: manage.py sets DJANGO_SETTINGS_MODULE to config.settings unless the environment already names a module. django.conf.settings is a lazy object: the first time anything reads a setting, it builds a Settings object by copying every capitalized name from django/conf/global_settings.py, then importing the named module and copying its capitalized names over them. The module runs top to bottom as ordinary Python, so our config() lookups, which read the environment and then .env, happen at that moment. A missing DJANGO_SECRET_KEY raises our ImproperlyConfigured during that import, so the command stops before it does any work. Settings are read once per process and should never be changed at runtime.

Behind the scenes:

django/conf/__init__.py (summary, not the source)

# class LazySettings: on first attribute access, _setup()
#     reads os.environ['DJANGO_SETTINGS_MODULE']
#     and creates Settings(module_name)
# class Settings: copy UPPERCASE names from global_settings,
#     import_module(module_name), copy its UPPERCASE names

Code proof: show which module was loaded, and a default that our file never sets:

Terminal

uv run python manage.py shell -c "
from django.conf import settings, global_settings
print(settings.SETTINGS_MODULE)
print(settings.DEFAULT_CHARSET, global_settings.DEFAULT_CHARSET)
"

Output

12 objects imported automatically (use -v 2 for details).

config.settings
utf-8 utf-8

DEFAULT_CHARSET appears nowhere in our settings.py, yet it has a value: Django’s default, copied before our module was read.

Common mistakes:

  • Changing settings.DEBUG in code and expecting Django to behave differently.
  • Defining a lowercase name and expecting it to become a setting.
  • Importing application code into settings.py, which runs before apps are loaded.

Follow-up the interviewer might ask:

  • “How would you run one command with a different settings module?”
  • “Why fail at startup rather than when the key is first used?”

L4 (Staff): How would you design Otahque’s configuration for local development, automated checks, staging, and production?

What the interviewer is testing: Can you keep one codebase while making each environment’s differences explicit, few, and checked?

Flip to check your answerFold answer back

Perfect answer: Keep one codebase and one lock for every environment, and treat the differences as a short, documented list: the secret key, debug mode, host names, and later the database, email, and storage settings. Give each value a name, and decide whether it is required, like the key, or has a safe default, like debug off. Local development reads a .env file; automated checks, staging, and production receive their values from the platform’s own store for secrets. Validate at startup so a missing value stops the process instead of half-working. Before each release, run Django’s deployment checks against the production values; Chapter 63 does this for Otahque. A separate production settings module becomes worthwhile when the structure differs, not merely the values, which is why the book waits for Chapters 62 and 63.

Behind the scenes:

django/core/checks (summary, not the source)

# Checks are registered with tags. Those registered with
# deploy=True, such as most security checks, run only when
# check --deploy, or run_checks(include_deployment_checks=True),
# asks for them. They read the settings currently loaded.

Code proof: run the deployment checks against our local values, sorted by identifier:

Terminal

uv run python manage.py shell -c "
from django.core import checks
found = checks.run_checks(include_deployment_checks=True)
for message_id in sorted(message.id for message in found):
    print(message_id)
"

Output

12 objects imported automatically (use -v 2 for details).

mail.E001
security.W004
security.W008
security.W012
security.W016
security.W018
security.W020

Our local values fail these checks on purpose. W018 is debug mode, W020 the empty host list, and mail.E001 the console email backend, which only prints messages. The other warnings concern HTTPS settings. Production must clear each one, which Chapters 43 and 63 do.

Common mistakes:

  • One settings file per environment that copies everything, so the copies drift apart.
  • Defaults that are unsafe in production, such as debug on.
  • Secrets passed on the command line, where shell history and process listings keep them.

Follow-up the interviewer might ask:

  • “Where would you keep production secrets, and who can read them?”
  • “How do automated checks get a secret key without one being recorded?”

L5 (Lead): A secret key was committed and pushed to a shared repository. How do you lead the response?

What the interviewer is testing: Can you contain the exposure first, coordinate the clean-up, and prevent a repeat without blame?

Flip to check your answerFold answer back

Perfect answer: Treat the key as exposed the moment it was pushed, because copies may already exist. First contain it: generate a new key and deploy it to every environment that used the old one, without listing the old key in SECRET_KEY_FALLBACKS. Everyone is signed out and outstanding password reset links stop working, and that is the price of closing the exposure: while the old key is listed, whoever holds it can still create values Django accepts. A fallback is for a planned change of a key that is still secret; using one here is a risk decision to state openly and keep short. Next, stop tracking the file with git rm --cached, and decide with the team whether to rewrite the shared history; that needs everyone with a copy to cooperate, so it never replaces replacing the key. Then review activity during the exposure, such as unexpected password resets. Finally, prevent a repeat: ignore rules written before the first commit, a review of staged files, and automated secret scanning when the project gains automated checks. Share a short, blame-free note on what happened and what changed.

Behind the scenes:

django/core/signing.py (summary, not the source)

# Signer(key=None, fallback_keys=None) uses SECRET_KEY to sign
# and accepts a signature made with SECRET_KEY or any key in
# SECRET_KEY_FALLBACKS when verifying. New values are always
# signed with the current key.

Code proof: two demonstration keys, used only in this example, show what a fallback does:

Terminal

uv run python manage.py shell -c "
from django.core import signing
old, new = 'old-key-for-demo', 'new-key-for-demo'
token = signing.dumps('sai', key=old)
print(signing.loads(token, key=new, fallback_keys=[old]))
try:
    signing.loads(token, key=new)
except signing.BadSignature:
    print('rejected without the fallback')
"

Output

12 objects imported automatically (use -v 2 for details).

sai
rejected without the fallback

A value signed with the old key still verifies while the old key is a fallback, and stops verifying once the fallback is removed. That suits a planned change of key; for an exposed key, it is exactly the risk.

Common mistakes:

  • Rewriting the history first and replacing the key later, or never.
  • Keeping an exposed key as a fallback, which leaves it usable by whoever holds it.
  • Treating the incident as one person’s fault rather than a gap in the process.

Follow-up the interviewer might ask:

  • “Which other values would you replace if a whole .env file leaked?”
  • “How would you know whether the old key had been used?”
