What You Need to Know

One project, several environments

An environment is the place where the project runs, together with everything it runs with: the computer, the Python interpreter, the installed packages, and the configuration values it is given. So far we have had exactly one, your computer. Soon there will be more. Chapter 9 starts running automated tests, Chapter 34 runs them automatically on a separate machine, and Chapter 63 puts Otahque on a production server that members reach over the internet.

The aim is that the code is the same in every environment, while a small set of values differs. If each computer carries its own edited copy of the code, a change made on one is easily lost on another, and nobody can say which copy is right. Table 8.1 sorts the parts of our project into the two kinds.

The rows marked “No” are configuration. The rest of this part explains how Django reads configuration, which values are dangerous to share, how a program receives values from outside its code, and how the shared parts, code and dependencies, are recorded.

Que. 1 Chapter 32 moves Otahque to a PostgreSQL database, which needs a password. Which kind of value is that password, and where should it live?

Flip to check your answerFold answer back

Answer. It is configuration that differs between environments, and it is also a secret. Each environment would have its own database and its own password, supplied by that environment rather than written into settings.py. If the password were in the code, everyone who could read the code could reach the database.

How Django finds its settings

Every Django command starts by finding its settings module. Open manage.py and read the line that mentions settings; change nothing:

manage.py (excerpt, unchanged)

os.environ.setdefault(
    'DJANGO_SETTINGS_MODULE', 'config.settings'
)

DJANGO_SETTINGS_MODULE names the settings module as a dotted import path, the form Chapter 7 used in INSTALLED_APPS. config.settings means the file config/settings.py. The setdefault call sets the name only if it has not been set already, so a value supplied from outside the program would win. We will meet that idea, values supplied from outside, again shortly.

A settings module is ordinary Python. Django imports it once, when a command or the server starts, and runs it from top to bottom. Two rules follow from how Django reads the result. Only names written entirely in capital letters count as settings. And any setting the file does not mention keeps Django’s built-in default value.

Under the Hood: How Django loads settings

from django.conf import settings does not import your file straight away. It gives you a stand-in object, LazySettings, defined in django/conf/__init__.py. The first time code reads a setting, the stand-in looks up DJANGO_SETTINGS_MODULE and builds a Settings object. That object first copies every capitalized name from Django’s defaults in django/conf/global_settings.py, then imports your module and copies every capitalized name from it, replacing the defaults it names. Lowercase names are skipped. Because this happens once, at the first read, an error inside settings.py stops a command as it starts, and a change to the file takes effect the next time a command or the server starts.

Django can show the result of that merge. The diffsettings command prints each setting whose value differs from Django’s default. We do not need it in our build steps, but one detail of its output matters here. Run it beside manage.py, in PowerShell, a macOS shell, or Linux/WSL Bash:

Terminal

uv run --no-project --python .venv python manage.py diffsettings

Expected result, shortened to a few of its lines:

Output

DEBUG = True
...
ROOT_URLCONF = 'config.urls'  ###
SECRET_KEY = 'django-insecure-(your own key)'
...

Settings marked ### have no default in Django at all. The line to notice is SECRET_KEY: where this listing shows a placeholder, your terminal shows your own key in full, because so far it is just text in a file. Anything that prints your settings prints your secrets, so never paste this output into a public question or issue report.

Que. 2 A teammate adds site_name = 'Otahque' to settings.py, then reads settings.site_name in Django’s shell and gets AttributeError: 'Settings' object has no attribute 'site_name'. Why?

Flip to check your answerFold answer back

Answer. Django copies only names written entirely in capital letters from the settings module. site_name is an ordinary lowercase variable, so Django ignores it. Naming it SITE_NAME would make it a setting. Even then, it is better to choose a name that cannot clash with one of Django’s own settings.

Three settings that must differ

The file generated in Chapter 6 marks two of its lines with SECURITY WARNING comments, and a third line depends on them. These three settings are the ones that are dangerous to share between environments. Table 8.2 summarizes them.

The secret key needs the most care. “Signs” means that Django attaches a code to a value, worked out from the value and the key, so that a changed value can be detected later. Chapter 28 shows this with sessions. The protection holds only while the key stays secret. The key generated in Chapter 6 begins with django-insecure-, Django’s reminder that it was created for local development and written straight into a file. Nobody else knows yours yet, but anything recorded in a shared history stops being secret, and the book’s reference copy uses a key printed on its pages, which was never secret at all. So this chapter replaces the key before Git records anything.

Debug mode is the reason Django could show us its helpful error pages in Chapters 6 and 7. Those pages include parts of our code and settings, which is exactly what a developer needs and exactly what a visitor must never see. The Django deployment checklist states plainly that debug must never be enabled in production.

ALLOWED_HOSTS explains a small mystery: our list is empty, yet the development server answered 127.0.0.1. While debug is on and the list is empty, Django quietly allows the local names localhost, 127.0.0.1, and [::1]. Turn debug off, and that allowance disappears.

Que. 3 You switch DEBUG to False on your computer, leave ALLOWED_HOSTS empty, and try to start the development server. What do you expect, and why?

Flip to check your answerFold answer back

Answer. The server refuses to start. With debug off, Django no longer allows the local names automatically, so an empty list would refuse every request; runserver reports CommandError: You must set settings.ALLOWED_HOSTS if DEBUG is False. Setting debug and allowed hosts belongs together, which is why both move out of the code in this chapter.

Values supplied from outside the code

New Concept: environment variable

What problem exists? Each environment needs its own secret key and its own debug setting, but we want the same settings.py everywhere. The values must reach the program without being written into its code.

What did people do before? Many projects edited settings.py on each server by hand, or kept an extra settings file on each computer that was never shared and imported it at the end. Both meant several versions of the code drifting apart, and the extra file was easily lost or accidentally shared.

What is an environment variable? A named text value that the operating system gives a program when it starts. A program started from a terminal receives a copy of that terminal’s variables. Python reads them through os.environ, which behaves like a dictionary.

Why environment variables? Every operating system and every hosting platform supports them, so the same code can run anywhere while each place supplies its own values. Django’s deployment checklist reads the secret key this way.

Now let’s use it.

This experiment changes nothing in the project. It sets a variable for the current terminal only, then reads it from Python. In PowerShell, in otahque/:

PowerShell

$env:OTAHQUE_GREETING = 'hello'
uv run --no-project --python .venv python -c "
import os
print(os.environ['OTAHQUE_GREETING'])
print(os.environ.get('OTAHQUE_MISSING', 'no value'))
"

In a macOS shell or Linux/WSL Bash, in otahque/:

Terminal

export OTAHQUE_GREETING=hello
uv run --no-project --python .venv python -c "
import os
print(os.environ['OTAHQUE_GREETING'])
print(os.environ.get('OTAHQUE_MISSING', 'no value'))
"

Expected result in either shell:

Output

hello
no value

The two lookups behave differently, and the difference matters for settings. Square brackets demand the value: os.environ['OTAHQUE_MISSING'] would stop the program with KeyError. get() returns the default we supply when the variable is missing. Use brackets for a value the program must never run without, such as the secret key, and get() with a safe default for the rest. Remove the experiment’s variable afterwards: Remove-Item Env:OTAHQUE_GREETING in PowerShell, or unset OTAHQUE_GREETING in Bash.

Every environment variable is text. That catches many beginners out: bool('False') is True in Python, because any non-empty string counts as true. A setting such as debug mode must therefore compare the text with an exact expected value, rather than trusting Python to convert it.

A file of local values

Typing variables into every new terminal is tedious and easy to forget. A .env file holds them instead: a plain-text file of NAME=value lines, kept beside manage.py. Python does not read it by itself, so our settings will use a small library to read it. Because the file holds this computer’s secret key, it is never shared or recorded. A companion file, .env.example, lists the same names with harmless placeholder values, so a teammate can see which variables to provide.

New Tool: python-decouple

What problem exists? settings.py needs this computer’s values from .env, and real environment variables must still be able to supply them on other computers. Python reads environment variables but not .env files.

What did people do before? Projects wrote a small reader of their own, like the one in How We Build It, or asked everyone to set the variables by hand in every new terminal.

What is python-decouple? A small library whose config() function looks up a name in the environment variables first, then in a .env file that it finds by searching upward from the folder of the code that calls it, and finally in a default that you supply. It can also convert the text it finds, for example into a list.

Why python-decouple? It does one job, works the same on every platform, and leaves the choice of safe defaults to us. It is not specific to Django, so the same habit works in any Python project. We add it to the project in How We Build It.

Now let’s use it.

Two details of the file’s format matter. python-decouple reads each value exactly as written, with one convenience: a pair of matching quotes around a value is removed. It does not treat a # after a value as a comment, so in DJANGO_DEBUG=True # local, the value is the whole text True # local. Other programs that read .env files are less literal: some treat $ as the start of another variable’s name, and Django’s generated keys can contain $. So we always write the secret key inside single quotes, which stop those readers from changing it, and we put comments on lines of their own.

In practice: replacing a key after a laptop is lost

Situation. Later, an organizer who looks after Otahque’s production server loses a laptop that held a copy of the production values.

Application. Because the secret key lives in the environment rather than the code, the response is to generate a new key and give it to the server, with no change to the code.

Consideration. Replacing the key ends signed sessions and invalidates outstanding password reset links. Django’s SECRET_KEY_FALLBACKS setting can keep them working during a planned change of key, but not here: a key listed there still verifies, so it would stay useful to whoever has the laptop. Chapters 28 and 59 return to keys and signing.

Que. 4 Which of these two lines is safer for reading debug mode, and why? DEBUG = bool(os.environ.get('DJANGO_DEBUG')) or DEBUG = os.environ.get('DJANGO_DEBUG') == 'True'.

Flip to check your answerFold answer back

Answer. The second. In the first, any non-empty text turns debug on, including False and no. The second turns it on only for the exact text True, and leaves it off when the variable is missing, so a forgotten variable fails safe.

Dependencies: declared, locked, and installed

New Tool: uv projects

What problem exists? Chapter 6 installed Django==6.1.2, and uv quietly installed asgiref and sqlparse with it, plus tzdata on Windows, because Django needs them. Nothing records their versions. A teammate installing next month could receive newer ones, and “it works on my computer” would stop being a guarantee.

What did people do before? A common habit was pip freeze > requirements.txt, a snapshot of whatever one computer happened to have installed, including packages nobody chose deliberately, and recorded for that computer’s operating system only. Many projects recorded nothing at all.

What is a uv project? A folder that uv manages through two files. pyproject.toml declares what the project needs: its Python version and its direct dependencies. uv.lock records the exact version of every package uv chose to satisfy that declaration, with checksums, for every supported operating system. The .venv/ folder is the installed result on one computer.

Why uv projects? We already use uv to install Python and create environments, so nothing new needs installing. Before every uv run, uv brings the lock up to date with the declaration and .venv/ up to date with the lock, so the three agree whenever a command runs. That update happens quietly, so uv lock --check exists to report a lock that would change, without changing it.

Now let’s use it.

Two words help here. A direct dependency is a package our project chose, such as Django. A transitive dependency is one that arrives because a direct dependency needs it. Ask uv what Django requires, beside manage.py, in PowerShell, a macOS shell, or Linux/WSL Bash:

Terminal

uv pip show --python .venv django

Expected result on Windows, shortened:

Output

Name: django
Version: 6.1.2
...
Requires: asgiref, sqlparse, tzdata
Required-by:

On macOS and Linux, tzdata is not listed, because Django asks for it only on Windows. So far, Django is our only direct dependency, and the three packages it requires are transitive. How We Build It adds a second direct dependency, python-decouple. A good record pins both kinds. Figure 8.2 shows how the three parts of a uv project relate, and why two computers that start from the same lock end up with the same packages.

The lock is written by uv, not by hand. We edit the declaration, usually through commands such as uv add, and uv updates the lock to match. The lock covers every operating system at once: for example, Django needs tzdata only on Windows, and the lock records that condition, so a Linux computer installing from the same lock simply skips it.

Prefer a requirements.txt file?

Some hosting platforms and older tools expect a requirements.txt file rather than a lock. We do not keep one by hand, because it would be a second record that can disagree with the first. If a tool needs one later, uv can produce it from the lock with uv export, so uv.lock stays the single source.

Que. 5 Which of pyproject.toml, uv.lock, and .venv/ would you change by hand, and which should be recorded in Git?

Flip to check your answerFold answer back

Answer. Only pyproject.toml is meant to be edited by people, directly or through uv add. uv.lock is written by uv and should never be edited by hand. .venv/ is rebuilt from the lock on each computer and is never edited or recorded. Both files, pyproject.toml and uv.lock, are recorded in Git, so every computer installs the same versions.

Recording history with Git

New Tool: Git

What problem exists? We have no record of how the project reached its current state. When something breaks, we cannot see what changed, and undoing a mistake means comparing folders by eye.

What did people do before? Copies of the whole folder with names such as otahque-final and otahque-final-2, or archives sent back and forth. Nobody could tell which copy was current or what differed between them.

What is Git? A version control system: a tool that records snapshots of a project’s files, called commits, each with an author, a date, and a message saying why. The history lives in a hidden .git/ folder inside the project, on your computer. An online copy is optional and can be added later.

Why Git? It is the standard tool for recording code history, it works without a network, and every hosting platform and team workflow later in the book builds on it. From this chapter on, each chapter ends with a commit.

Now let’s use it.

Git keeps files in three places, shown in Figure 8.3. The working tree is the project folder as you see and edit it. The staging area holds the changes you have chosen for the next commit; git add puts them there. The history holds the commits; git commit turns the staged changes into a new one. The extra step between editing and committing is deliberate: it lets you review exactly what will be recorded before it is recorded.

A file named .gitignore lists patterns for files Git should not offer to stage, such as .env, .venv/, and the local database. Two facts about the history explain why we write that file first. A commit is permanent: deleting a file in a later commit removes it from the working tree, but the earlier commit still contains it. And ignore rules apply only to files Git is not already recording, so adding a pattern later does not remove a file that was already committed. The safe order is therefore: remove the secret from the code, write the ignore rules, and only then let Git see the folder.

Que. 6 Someone commits .env, notices, deletes it, and makes a second commit. Is the secret key safe now?

Flip to check your answerFold answer back

Answer. No. The first commit still contains .env, and anyone with a copy of the history can read it. The key must be treated as exposed and replaced with a new one. Removing a file from earlier commits is possible with specialist tools, but replacing the key comes first, because copies of the history may already exist elsewhere.

Sort them into files Git should record and files it should ignore. Decide before reading the answer.

Que. 7 Which files belong in the history, and which should be ignored?

Flip to check your answerFold answer back

Answer. Record manage.py, config/settings.py, events/models.py, .python-version, pyproject.toml, uv.lock, and .env.example: they are the same in every environment, and the example file holds no real values. Ignore .env, because it holds this computer’s secret key; .venv/, because each computer rebuilds it from the lock; db.sqlite3, because each computer has its own local data; and __pycache__/, because Python regenerates those compiled files automatically.
