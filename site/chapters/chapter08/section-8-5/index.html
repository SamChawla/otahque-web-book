Checkpoint: Quiz and Challenge

Quiz

Que. 8 Why does our settings.py stop with ImproperlyConfigured when the secret key is missing, instead of falling back to a default key?

Flip to check your answerFold answer back

Answer. A default key would be written in the code, so everyone who can read the code would know it, and a forgotten variable on a server would silently run with that shared key. Stopping with a clear message makes the mistake visible at once and names the fix.

Que. 9 A teammate’s .env contains DJANGO_DEBUG=yes. Is debug mode on? Why?

Flip to check your answerFold answer back

Answer. No. Our setting turns debug on only for the exact text True, so yes, true, and a missing variable all leave it off. That is deliberate: a mistake fails safe. With debug off and no allowed hosts, the development server then refuses to start, which tells the teammate to fix the line.

Que. 10 What is the difference between pyproject.toml and uv.lock, and which one do you change?

Flip to check your answerFold answer back

Answer. pyproject.toml declares what the project needs: its Python version and its direct dependencies. uv.lock records the exact version of every package that satisfies the declaration, for every operating system. We change the declaration, usually through uv add, and let uv rewrite the lock; the lock is never edited by hand. Both are recorded in Git.

Que. 11 You ran git add . before writing .gitignore, and .env is now staged. What do you run, and why does one option in the command matter?

Flip to check your answerFold answer back

Answer. .env is not the only problem: git add . also staged db.sqlite3 and the compiled Python files. Write .gitignore, run git rm -r --cached . to empty the staging area, then run git add . and read the list with git status --short. --cached removes files only from what Git will record and leaves them on your disk. Without it, Git refuses, and forcing it with -f would delete them. Because nothing has been committed yet, the key has not entered the history.

Que. 12 How does settings.py find .env, and what happens when the same variable is also set in your terminal?

Flip to check your answerFold answer back

Answer. python-decouple’s config() searches for .env starting in the folder of the file that calls it, config/, and then in each parent folder, so it finds the file beside manage.py whichever folder the terminal is in. It checks environment variables first, so a value already set in the terminal wins over the file. A leftover value from an experiment can therefore override .env until you remove it or open a new terminal. The upward search has a similar catch: a stray .env in a folder above the project supplies its values without warning, so if a check passes when you expected a refusal, look for one.

Mini-Challenge

Prove that the project can be rebuilt on another computer from what Git records. Clone the repository into a new sibling folder, install the environment from the lock, give the copy its own key, and run both checks. Then confirm that the copy’s key differs from yours, without printing either key. Work it out before reading the model answer. Before you start, check that no otahque-clone/ folder exists beside otahque/; if one does, choose another new name and use it throughout.

Que. 13 What commands prove it, and what should each one show?

Flip to check your answerFold answer back

Answer. From the folder that contains otahque/, in PowerShell, a macOS shell, or Linux/WSL Bash, clone and install:

Terminal

git clone otahque otahque-clone
cd otahque-clone
uv sync --locked

git clone prints Cloning into 'otahque-clone'... and done.; the copy has every recorded file and no .env or .venv/. uv sync --locked reports Creating virtual environment at: .venv, then installs the five locked packages on Windows, or four on macOS and Linux, each at its locked version. A warning that uv failed to hardlink files is harmless: it only means uv copied files from its cache instead of linking them. The copy has no .env yet, so the system check should refuse to run:

Terminal

uv run python manage.py check

The error report ends with ImproperlyConfigured and the message Set DJANGO_SECRET_KEY; see .env.example. If it passes instead, a .env in a folder above is supplying the key; Que. 12 explains why. Now run Step 3’s key command inside otahque-clone/, followed by both checks:

Terminal

uv run python manage.py check
uv run python manage.py check events

Each prints System check identified no issues (0 silenced). Compare the two files without printing them:

Terminal

uv run python -c "
mine = open('.env', encoding='utf-8').read()
theirs = open('../otahque/.env', encoding='utf-8').read()
print(mine != theirs)
"

It prints True. The copy works with its own key, from recorded files alone: that is what this chapter set out to make possible. Return with cd ../otahque and delete otahque-clone/ when you have finished; it shares nothing with your project.

What We Learned

  • An environment is where the project runs and what it runs with; the code stays the same everywhere, and a few values, the configuration, differ.
  • Django finds its settings through DJANGO_SETTINGS_MODULE, reads them once over its own defaults, and counts only capitalized names.
  • The secret key, debug mode, and allowed hosts must differ between environments; ours now come from environment variables, with no default key and debug off unless asked for.
  • A .env file supplies one computer’s values, read by python-decouple from settings.py; it is never recorded, while .env.example documents the names.
  • pyproject.toml declares, uv.lock pins every package for every platform, and .venv/ is rebuilt from the lock on each computer.
  • Git records commits from the staging area; .gitignore written first, a fresh key, and a review of the staged list kept every secret out of the first commit.
