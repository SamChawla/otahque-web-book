How We Build It

Starting point: the verified Chapter 7 project, with both system checks passing. Work in otahque/, the folder that contains manage.py, .venv/, config/, and events/. These steps change config/settings.py and add pyproject.toml, uv.lock, .env, .env.example, .gitignore, and Git’s hidden .git/ folder. The visible result: both system checks pass using .env, git log shows one commit, and git status reports nothing left to record. The development server shows the same welcome page as before; no Otahque page changes.

The Custom Way: a .env reader by hand

python-decouple will read .env for us, but it helps to see what such a reader has to do. Read this listing; do not add it to the project.

illustration_only/read_env.py (not part of the project)

import os


def load_env(path):
    """Copy NAME=value lines from a file into os.environ."""
    with open(path, encoding='utf-8') as lines:
        for line in lines:
            line = line.strip()
            if not line or line.startswith('#'):
                continue
            name, _, value = line.partition('=')
            if len(value) > 1 and value[0] == value[-1] == "'":
                value = value[1:-1]
            os.environ.setdefault(name.strip(), value)

It skips blank lines and comments, splits each line at its first =, and removes a pair of surrounding single quotes. setdefault, which we met in manage.py, means a variable already set in the terminal wins over the file. That is close to how python-decouple reads a .env file, and decouple keeps the same rule about the terminal. What decouple adds is the rest of the job. It finds the file by searching upward from the folder of the code that calls it, so config/settings.py finds the .env beside manage.py whichever folder the terminal is in. Each lookup states what happens when a name is missing: use a default, or stop with an error. It converts text into other types, such as lists. And many projects use and test it, so we do not maintain a reader of our own.

The Django Way: settings, lock, and history

Step 1: Make the folder a uv project

Common Error: running uv init without --bare

In a folder that already holds a project, plain uv init adds more than we want: a README.md, a src/ folder, a .gitignore, and a Git repository, and it copies your Git name and email into pyproject.toml if Git knows them. Type --bare exactly. If you have already run the plain command, Table 8.4 shows how to recover.

Two commands turn the folder into a uv project. In PowerShell, a macOS shell, or Linux/WSL Bash, beside manage.py:

Terminal

uv init --bare --name otahque
uv add "Django==6.1.2" "python-decouple==3.8"

--bare writes only pyproject.toml, and --name gives the project its name, which otherwise comes from the folder. uv add records Django and python-decouple as dependencies with their exact versions, works out every package those versions need, writes them to uv.lock, and makes .venv/ match. Our environment already holds Django and its dependencies from Chapter 6, so uv installs only python-decouple. Expected result:

Output

Initialized project `otahque`
Resolved 6 packages in ...
Prepared 1 package in ...
Installed 1 package in ...
 + python-decouple==3.8

The timings differ on every run, and the Prepared line is absent if uv already has the package. The six resolved packages are Django, its three dependencies, python-decouple, and our project itself. Open the new file:

pyproject.toml

[project]
name = "otahque"
version = "0.1.0"
requires-python = ">=3.14.9"
dependencies = [
    "django==6.1.2",
    "python-decouple==3.8",
]

requires-python comes from the .python-version file of Chapter 6 and states the oldest Python this project accepts. dependencies lists our direct dependencies; uv writes package names in lower case. Leave uv.lock closed: it is long, written by uv, and never edited by hand. To see what it records, ask uv for the dependency tree:

Terminal

uv tree

Expected result on Windows:

Output

Resolved 6 packages in ...
otahque v0.1.0
├── django v6.1.2
│   ├── asgiref v3.13.0
│   ├── sqlparse v0.6.0
│   └── tzdata v2026.5
└── python-decouple v3.8

On macOS and Linux, the tzdata line is absent, because the tree shows what this computer needs. From now on, Django commands are shorter. Because the folder is a uv project, uv run finds .venv/ by itself and brings the lock and the environment up to date before every command. Chapter 6’s --no-project --python .venv told uv to ignore any project, and we no longer need it. In any of the three shells:

Terminal

uv run python manage.py check

Expected result:

Output

System check identified no issues (0 silenced).

Step 2: Read the three settings from the environment

Open config/settings.py. The first change goes at the top, after the long comment at the start of the file. Add two import lines, so that the imports read:

config/settings.py (top of the file, after the docstring)

from pathlib import Path

from decouple import Csv, UndefinedValueError, config
from django.core.exceptions import ImproperlyConfigured

config is python-decouple’s lookup function, Csv turns comma-separated text into a list, and UndefinedValueError is the error config raises when a name has no value and no default. ImproperlyConfigured is the exception Django raises when its configuration is wrong; we met it in Chapter 7, when a repeated app label stopped loading. The second change replaces a block lower down. Find the lines from # Quick-start development settings to ALLOWED_HOSTS = [], just above # Application definition, and replace them with this:

config/settings.py (replaces the quick-start block)

# Values that differ between environments come from the
# environment or the .env file. .env.example lists them.

# SECURITY WARNING: keep the secret key used in production
# secret! There is no default: a missing key stops Django.
try:
    SECRET_KEY = config('DJANGO_SECRET_KEY')
except UndefinedValueError:
    raise ImproperlyConfigured(
        'Set DJANGO_SECRET_KEY; see .env.example.'
    ) from None

# SECURITY WARNING: don't run with debug turned on in
# production! Debug is on only for the exact text True.
DEBUG = config('DJANGO_DEBUG', default='') == 'True'

# Host names separated by commas, such as:
# otahque.example,www.otahque.example
ALLOWED_HOSTS = config(
    'DJANGO_ALLOWED_HOSTS', default='', cast=Csv()
)

Each setting follows a rule from What You Need to Know. config() without a default behaves like square brackets: it demands the value, and raises UndefinedValueError when the name is in neither the environment nor .env. We catch that and raise ImproperlyConfigured with a message that names the fix. from None leaves the first error out of the report, so its last line is our instruction. With default=, config() behaves like get(). Debug mode is on only when the value is exactly True, so a missing or misspelled value fails safe. decouple could convert the text for us with cast=bool, but that also accepts yes, on, and 1; comparing with one exact spelling keeps the rule simple. cast=Csv() splits the host names at commas, and turns empty text into an empty list, which matches the generated ALLOWED_HOSTS = [].

Save the file and run the check again, still without any values:

Terminal

uv run python manage.py check

This time Django refuses to start. The error report ends with ImproperlyConfigured and our message, Set DJANGO_SECRET_KEY; see .env.example. That is the safe failure we wanted: without a key of its own, the project stops, instead of starting with a key that other people know. Every command that needs the settings stops the same way until the next step.

Step 3: Give this computer its own values

Common Error: a comment after a value

If you add a note after a value in .env, such as DJANGO_DEBUG=True # local only, python-decouple reads the whole text as the value. Debug mode then stays off, and the development server refuses to start with no allowed hosts. Put each comment on a line of its own, starting with #.

This command generates a new key with the same Django function that startproject used in Chapter 6, and writes it into a new .env file. It is the same in PowerShell, a macOS shell, and Linux/WSL Bash; type it exactly, including the final double quote:

Terminal

uv run python -c "
from django.core.management.utils import get_random_secret_key
key = repr(get_random_secret_key())
with open('.env', 'x', encoding='utf-8') as env:
    print('DJANGO_SECRET_KEY=' + key, file=env)
    print('DJANGO_DEBUG=True', file=env)
"

repr() returns the key wrapped in single quotes, which keeps it exact for the programs that commonly read .env. The 'x' mode creates the file only if it does not exist yet, so running the command a second time cannot replace your key; it stops with FileExistsError instead. The command prints nothing when it succeeds, and the key never appears in your terminal. Open .env to see its shape:

.env (shape only; your key differs)

DJANGO_SECRET_KEY='(50 random characters)'
DJANGO_DEBUG=True

DJANGO_ALLOWED_HOSTS is left out: its default, an empty list, lets the development server answer the local names while debug is on. Now create .env.example beside it in your editor, with exactly these lines:

.env.example

# Names this project reads. Create .env with the key command
# in Chapter 8, Step 3. Never record .env in Git.
DJANGO_SECRET_KEY=
DJANGO_DEBUG=True
# Host names separated by commas; leave empty locally.
DJANGO_ALLOWED_HOSTS=

This file names every variable and holds no real value, so it is safe to record. The key is empty on purpose: someone who copies this file to .env cannot end up running on a key printed in a book, because Django stops with The SECRET_KEY setting must not be empty. the first time the key is read. The system check does not read the key, so it passes until then. Run both checks again. The settings now find .env by themselves, so the commands are the same as in Step 1:

Terminal

uv run python manage.py check
uv run python manage.py check events

Expected result, once for each command:

Output

System check identified no issues (0 silenced).

Confirm that the values arrived as intended. This prints the key’s length, never the key itself:

Terminal

uv run python manage.py shell -c "
from django.conf import settings
print(settings.DEBUG, settings.ALLOWED_HOSTS)
print(len(settings.SECRET_KEY))
"

Expected result:

Output

12 objects imported automatically (use -v 2 for details).

True []
50

If the last line is not 50, the key was changed when .env was edited; Table 8.4 shows the fix. The development server works exactly as before. Start it, visit http://127.0.0.1:8000/, see Django’s welcome page, then stop it with Ctrl+C:

Terminal

uv run python manage.py runserver

Every Django command reads .env through the settings, so none of them needs anything extra. A running server does not notice an edit to .env, though: its reloader watches Python files, so stop and start it after changing a value. One more rule from the Custom Way applies: a variable already set in your terminal wins over the file. If an experiment left DJANGO_DEBUG or DJANGO_SECRET_KEY set in your terminal, remove it, or open a new terminal.

Step 4: Install Git and tell it who you are

Check whether Git is installed, in any of the three shells:

Terminal

git --version

Expected result: a line such as git version 2.51.0, possibly with a Windows suffix. This book was checked with Git 2.51; the commands in this chapter need version 2.28 or later. If the command is not found, install Git, then open a new terminal so that it can find the new program.

PowerShell, on Windows:

PowerShell

winget install --id Git.Git -e --source winget

macOS shell, which installs Apple’s command-line tools, including Git:

Terminal

xcode-select --install

Linux or WSL Bash, on Debian or Ubuntu; other distributions use their own package manager:

Terminal

sudo apt update
sudo apt install git

Every commit records its author’s name and email address. Ask Git what it already knows:

Terminal

git config --global user.name
git config --global user.email

If both commands print a value, keep them and go on to Step 5. Otherwise, set them, replacing the examples with your own name and address:

Terminal

git config --global user.name "Your Name"
git config --global user.email "you@example.com"

--global stores the values for every repository on this computer. The address becomes part of every commit, so if you later publish the history, consider the private address that most hosting services offer.

Common Error: Author identity unknown

If the identity is not set, git commit stops with Author identity unknown and suggests the two git config commands above. Nothing is lost: the staged changes wait. Set the identity and run the commit again.

Step 5: Write the ignore rules, then create the repository

Create .gitignore beside manage.py, with these lines:

.gitignore

# Local values, including this computer's secret key
.env

# The environment, rebuilt from uv.lock on each computer
.venv/

# Files Python regenerates automatically
__pycache__/
*.pyc

# This computer's local development database
db.sqlite3

Lines starting with # are comments. Table 8.3 explains each pattern.

A pattern matches whole names, so .env does not match .env.example, which we want recorded. Now create the repository:

Terminal

git init -b main

Expected result, with your own folder’s path:

Output

Initialized empty Git repository in .../otahque/.git/

-b main names the first line of history main. Teams work with several such lines, called branches, which Chapters 34 and 64 introduce. Before staging anything, look at what Git sees:

Terminal

git status --short

Expected result:

Folder structure

?? .env.example
?? .gitignore
?? .python-version
?? check_environment.py
?? config/
?? events/
?? manage.py
?? pyproject.toml
?? uv.lock

?? marks a file Git is not recording yet, and a folder appears once for all its files. Neither .env nor .venv/ appears. Ask Git which rule keeps each one out:

Terminal

git check-ignore -v .env .venv db.sqlite3

Expected result:

Output

.gitignore:2:.env	.env
.gitignore:5:.venv/	.venv
.gitignore:12:db.sqlite3	db.sqlite3

Each line names the ignore file, the line number, the pattern, and the path. Git reports db.sqlite3 even if the file does not exist yet, because the rule is ready for it.

Step 6: Make the first commit

Common Error: staging .env

If .env appears in a status listing marked A, it has been staged. Remove it from the staging area with git rm --cached .env, then check the spelling in .gitignore. --cached matters: it removes the file from what Git will record but leaves it on your disk. Without --cached, Git refuses here; forcing it with -f would delete the file from your disk. If other unwanted files are staged too, Table 8.4 shows how to start the staging again.

Stage everything that is not ignored, then review the list:

Terminal

git add .
git status --short

Expected result, shortened:

Output

A  .env.example
A  .gitignore
A  .python-version
...
A  manage.py
A  pyproject.toml
A  uv.lock

A marks a file staged to be added. Read the whole list: it should hold 19 files, including the seven in events/ and five in config/, and no .env, .venv/, or db.sqlite3. To read the staged changes line by line, run git diff --cached, and press q to leave it. On Windows, git add may first print warnings such as LF will be replaced by CRLF the next time Git touches it. They are about line endings, the invisible characters that end each line, which Windows and other systems write differently. Git for Windows usually adjusts them when it writes files back; your files’ content is unaffected, and nothing needs fixing. Record the commit:

Terminal

git commit -m "Prepare settings, lock, and Git"

Finally, confirm that no secret was recorded. Both commands should print nothing: the first lists .env only if Git records it, and the second searches every recorded file for the start of Chapter 6’s key.

Terminal

git grep -n "django-insecure"

When something goes wrong

Table 8.4 lists the problems this chapter’s steps can produce. Each recovery keeps your work: it corrects one file, one setting, or the staging area, or renames a file instead of deleting it.

A recorded secret needs a new key even after git rm --cached, because earlier commits still contain the old one. While the history exists only on your computer, the new key is enough. Once a history has been shared, removing a file from earlier commits needs specialist tools and the cooperation of everyone with a copy, which is why replacing the key always comes first.

For further reference, Django 6.1 documents settings at https://docs.djangoproject.com/en/6.1/topics/settings/, the deployment checklist at https://docs.djangoproject.com/en/6.1/howto/deployment/checklist/, and cryptographic signing at https://docs.djangoproject.com/en/6.1/topics/signing/.
