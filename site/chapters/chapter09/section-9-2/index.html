What You Need to Know

An address and its path

In Chapter 3 we saw that a browser uses an address to find a server and ask for a resource. Consider http://127.0.0.1:8000/events/?page=2. The scheme http describes the protocol, 127.0.0.1 names the local computer, and 8000 is the port. The path is /events/. The query string begins after ?; here it carries page=2. A fragment after #, if present, is used by the browser and is not sent as part of the HTTP request.

Django’s URL patterns normally match the request path, not the host or query string. The leading slash is not written in a path() route. For example, /events/ is represented by events/. The home address / corresponds to an empty route, ''. A trailing slash is a character in the route: use the exact addresses shown in this chapter. A redirect for a missing slash depends on settings and middleware; do not rely on it as a substitute for the right route.

Que. 1 Does /events/?page=2 need a different route from /events/?page=3?

Flip to check your answerFold answer back

Answer. No. Both have the same path, /events/; the query strings differ. A view may later choose to read those values, but the URL pattern does not match them.

The route and the view

New Concept: URL configuration

What problem exists? Our project needs to choose the right code for each requested path.

What did people do before? A program could compare paths by hand and call a different function for each one, as The Custom Way shows in How We Build It.

What is a URL configuration? A URL configuration, often called a URLconf, is a Python module containing Django’s URL patterns.

Why a URLconf? Django’s path() and include() let us describe and organize those patterns without writing the dispatcher ourselves.

Now let’s use it.

Each path() connects a route to a view or another URLconf. Our root URLconf is config/urls.py, selected by ROOT_URLCONF in the settings. The project will keep Django’s existing admin route and include events/urls.py for Otahque’s own routes. The app URLconf will name its routes home and list, inside an events namespace. A namespace is a prefix that distinguishes one app’s route names from another’s: events:home means the home name belonging to events.

include() passes the remaining path to the included patterns after the prefix matches. We will include our app at the empty prefix, so the app will match both the empty home route and events/. Chapter 7 left one decision for this chapter: where the home page lives. For now its view sits in the events app, because finding events is all the home page offers so far; if it later draws on several apps, we will move it and record why. Including an app at the root does not mean it must own every future page. The project can include other apps at other prefixes as they arrive. Figure 9.2 shows the two files we will end up with, and how a request for /events/ passes through them.

Under the Hood: Choosing a view

Django begins with the root URLconf and tries its patterns in order. A matching include() leads to another set of patterns, which are also tried in order. A matching view is called with the request and any values captured by the route. If no complete route matches, Django returns a 404 response. Earlier broad patterns can hide later matches, so route order deserves attention. A 404 can also be raised by view code; the status alone does not identify the cause.

The view returns an HttpResponse object. That object contains the response sent back for the request. Our two responses are deliberately simple text; a view does not have to be a template or a database query. Chapter 10 will examine requests and responses more closely.

Names work in the other direction

Routing usually starts with a path and finds a view. reverse() starts with a route name and finds its path. For example, after we add the routes, reverse('events:list') returns /events/. A stable name can keep other code from repeating a path, although renaming the route or changing required arguments still requires updating callers. Later, templates will use the same idea to build links.

In practice: a mistyped address

Situation. Later, Soni mistypes the address of a workshop she is reading about.

Application. Django finds no matching route and returns a 404, which tells her that the requested resource was not found. While developing, compare the actual path with the patterns in both files, and check the spelling and slashes before changing any code.

Consideration. The detailed debug page you see locally is a development aid, not a public error page. Chapter 8 keeps debug mode off everywhere else.

Tests that run without a browser

New Tool: Django’s test client

What problem exists? Checking pages by hand is slow, and it is easy to forget a page that a later change has broken.

What did people do before? Someone clicked through the site after each change, or nobody did.

What is the test client? A tool that sends simulated requests through Django’s URLs, middleware, and views without starting a server or a browser, then hands the response to your test.

Why the test client? It comes with Django and runs quickly, so we can repeat the whole check after every change. It does not show how a browser displays a page, so we keep the browser check too.

Now let’s use it.

A test is a method whose name starts with test, inside a class. We will use SimpleTestCase, Django’s test class for tests that do not touch a database, because no database is involved yet. We run the tests with manage.py test. It reports each test with one character: . when the test passed, F when an assertion failed, and E when the test stopped with an unexpected error.

Writing a test first has a practical benefit beyond tidiness. A test you have seen fail is a test you know can fail. A test written after the code might pass for the wrong reason, and you would never find out.
