How We Build It

Start with the Chapter 8 project in the folder containing manage.py, its locked environment, and your own local .env. We will replace events/tests.py and events/views.py, create events/urls.py, and replace config/urls.py. We will not add packages, models, or migrations. The visible result is two text pages on the local development server, three passing tests, and a second Git commit.

The Custom Way

Imagine a small dispatcher with two comparisons. This is an illustration only; do not add it to the project. It has no HTTP server and does not replace Django.

illustration_only/choose.py (not part of the project)

def choose(path):
    if path == '/':
        return 'home'
    if path == '/events/':
        return 'event list'
    return 'not found'

The idea is useful, but a real dispatcher must cooperate with requests, responses, nested routes, errors, and middleware. Django already supplies that machinery. We describe our routes instead.

The Django Way

Step 1: Write the tests first

Decide what the finished routes should do, and write it down as tests. Replace the contents of events/tests.py with this complete file:

events/tests.py

"""Tests for the events app."""
from django.test import SimpleTestCase
from django.urls import resolve, reverse

from . import views


class RoutingTests(SimpleTestCase):
    """Each address reaches its view; others are not found."""

    def test_home(self):
        response = self.client.get('/')
        self.assertEqual(response.status_code, 200)
        self.assertContains(
            response, 'Welcome to Otahque.'
        )
        self.assertEqual(reverse('events:home'), '/')
        self.assertIs(resolve('/').func, views.home)

    def test_event_list(self):
        response = self.client.get('/events/')
        self.assertEqual(response.status_code, 200)
        self.assertContains(
            response, 'Event list coming soon.'
        )
        self.assertEqual(reverse('events:list'), '/events/')
        self.assertIs(
            resolve('/events/').func, views.event_list
        )

    def test_unknown_path(self):
        response = self.client.get('/does-not-exist/')
        self.assertEqual(response.status_code, 404)

self.client.get() sends a simulated GET request. assertContains checks a useful part of the response as well as its status. reverse() asks for the path belonging to a name; resolve() asks Django which view a path selects; and assertIs checks that the selected function is the same function we intended. Now run the tests. In PowerShell, a macOS shell, or Linux/WSL Bash, beside manage.py:

Terminal

uv run python manage.py test events

Expected result, shortened with ... where lines are left out:

Output

Found 3 test(s).
System check identified no issues (0 silenced).
FF.
...
FAIL: test_event_list (events.tests.RoutingTests...
...
AssertionError: 404 != 200
...
FAIL: test_home (events.tests.RoutingTests.test_home)
...
AssertionError: 404 != 200
...
Ran 3 tests in ...

FAILED (failures=2)

Read this from the top. FF. means that two tests failed and one passed, in alphabetical order. Each FAIL block names the test and the assertion that stopped it, and 404 != 200 says that the response was 404 where the test wanted 200. That is correct: no routes exist yet. The unknown-path test already passes, because every path is unknown so far. It will start to mean something once real routes exist beside it. Leave the tests failing and continue. The elapsed time varies, and the system check and the summary can appear in a different order because they use separate output streams.

Step 2: Write the two views

Open events/views.py. Replace its generated contents with this complete file. A function receives the request; each returns a response with distinct text.

events/views.py

"""The events app's views: one function per page."""
from django.http import HttpResponse


def home(request):
    """Welcome visitors to Otahque."""
    return HttpResponse('Welcome to Otahque.')


def event_list(request):
    """List Otahque's events."""
    return HttpResponse('Event list coming soon.')

Step 3: Add the app URLconf

Common Error: calling the view too soon

Use views.home, not views.home(). Parentheses call the function while the URLconf is loading, before Django has supplied a request, and every command then stops with TypeError: home() missing 1 required positional argument: 'request'.

Create events/urls.py beside views.py. The first argument of path() is the route, the second is the view function itself, and name gives the route a reusable name. We pass the functions without parentheses; Django calls them when a request matches.

events/urls.py

"""Addresses of the events app's pages."""
from django.urls import path

from . import views

app_name = 'events'

urlpatterns = [
    path('', views.home, name='home'),
    path('events/', views.event_list, name='list'),
]

Step 4: Include the app in the project

Replace config/urls.py with the complete file below. The empty prefix delegates paths to the events app. The names config/urls.py and events/urls.py refer to two different files.

config/urls.py

"""URL configuration for the Otahque project."""
from django.contrib import admin
from django.urls import include, path

urlpatterns = [
    path('admin/', admin.site.urls),
    path('', include('events.urls')),
]

Run the system check and the tests again, in any of the three shells:

Terminal

uv run python manage.py check
uv run python manage.py test events

Expected result, shortened; the dashed line is left out:

Output

System check identified no issues (0 silenced).
Found 3 test(s).
System check identified no issues (0 silenced).
...
Ran 3 tests in ...

OK

The three dots mean three passing tests, and no test database was created, because SimpleTestCase does not use one. The tests that failed in Step 1 now pass, and we saw them fail for the reason we expected.

Step 5: Visit the pages

The tests do not prove that a browser displays the pages, so look at them as well. In the same folder, start the local development server:

Terminal

uv run python manage.py runserver

Open http://127.0.0.1:8000/, where the page reads Welcome to Otahque. Then open http://127.0.0.1:8000/events/, where it reads Event list coming soon. If the first address still shows Django’s rocket and “The install worked successfully!”, then config/urls.py does not yet include the app. Now open http://127.0.0.1:8000/does-not-exist/ and observe a 404 page. With local debug mode enabled, Django shows diagnostic information; its appearance is not the production error page. Stop the server with Ctrl+C. A warning about unapplied migrations is expected at this checkpoint; do not run migrations yet.

When something goes wrong

Table 9.1 lists the problems these steps can produce. Each recovery corrects one file; none of them replaces your work.

Keep your work if a correction is needed. Compare each file with the listing and save a separate copy before replacing anything you want to preserve. If the server has stopped, start it again after correcting the file. Do not delete the project or reset Git to diagnose a route.
