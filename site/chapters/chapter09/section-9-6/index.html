Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 and L2 check what you have just learned. L3 asks how it works underneath. L4 and L5 look ahead to the larger URL configurations Otahque will need later: attempt them now, and return to them when you reach those chapters. They are extension questions, not a gate to the next chapter. Run each code proof beside manage.py, in PowerShell, a macOS shell, or Linux/WSL Bash. These proofs show our configuration, not every possible Django project.

L1 (Junior): What connects a URL to a view?

What the interviewer is testing: Can you explain the request path without confusing the route with the response?

Flip to check your answerFold answer back

Perfect answer: A URLconf holds patterns that Django checks against the request path, in order. A matching pattern identifies a view, Django calls that view with the request, and the view returns the response. The URLconf only chooses; it renders nothing itself. In Otahque, config/urls.py hands over to events/urls.py, whose events/ pattern selects event_list.

Behind the scenes:

django/urls/resolvers.py (summary, not the source)

# URLPattern.resolve(path): if the route matches, return a
#     ResolverMatch holding the view and captured values.
# The handler then calls view(request, **captured values).

Code proof: ask Django which view a path selects, without sending a request:

Terminal

uv run python manage.py shell -c "
from django.urls import resolve
match = resolve('/events/')
print(match.func.__name__, match.view_name)
"

Output

12 objects imported automatically (use -v 2 for details).

event_list events:list

Common mistakes:

  • Saying a URLconf renders a page.
  • Forgetting that the view returns the response.
  • Writing the leading slash in a path() route.

Follow-up the interviewer might ask:

  • “What changes when a view returns a template rather than text?”
  • “Does the query string take part in the match?”

L2 (Mid-Level): What does include() do?

What the interviewer is testing: Do you understand the handoff from the project to an app?

Flip to check your answerFold answer back

Perfect answer: include() connects another URLconf to a prefix. When the prefix matches, Django removes the matched part and continues with the remaining path against the included patterns. That lets each app own its routes while the project decides where they live. We use an empty prefix, which consumes no characters, so the app sees the whole path. Moving the app to community/ would change every full address in the app and none of its patterns.

Behind the scenes:

django/urls/resolvers.py (summary, not the source)

# URLResolver.resolve(path): match this resolver's prefix,
#     then try each pattern with the remaining path.
#     Return the first match, or raise Resolver404 listing
#     the patterns that were tried.

Code proof: print the patterns at both levels:

Terminal

uv run python manage.py shell -c "
from django.urls import get_resolver
root = get_resolver()
for item in root.url_patterns:
    print(repr(str(item.pattern)), type(item).__name__)
for item in root.url_patterns[1].url_patterns:
    print(repr(str(item.pattern)), item.name)
"

Output

12 objects imported automatically (use -v 2 for details).

'admin/' URLResolver
'' URLResolver
'' home
'events/' list

Common mistakes:

  • Adding the same prefix in both files, which gives /events/events/.
  • Expecting include() to call a view by itself.
  • Assuming that an empty prefix means the app owns every path.

Follow-up the interviewer might ask:

  • “What would you change to serve this app under /community/, and what would you test?”
  • “Does it matter here whether admin comes first?”

L3 (Senior): Why name a route?

What the interviewer is testing: Can you distinguish path resolution from reverse lookup, and explain what a namespace adds?

Flip to check your answerFold answer back

Perfect answer: A route name gives code an identifier from which Django can construct the configured path, so links and redirects do not repeat it. If the path changes while the name stays the same, those callers keep working. A namespace separates names belonging to different apps, so two apps can each have a list. A name does not remove every dependency: renaming a route or changing its required arguments still means updating callers, and reverse() raises NoReverseMatch when it cannot build a path, without sending any request.

Behind the scenes:

django/urls/base.py (summary, not the source)

# reverse('events:list'): split the namespace from the name,
#     find the resolver registered for that namespace,
#     and build the path from its pattern and arguments.
#     No match raises NoReverseMatch.

Code proof: reverse the name with its namespace, then without:

Terminal

uv run python manage.py shell -c "
from django.urls import NoReverseMatch, reverse
print(reverse('events:list'))
try:
    reverse('list')
except NoReverseMatch as error:
    print(type(error).__name__)
"

Folder structure

12 objects imported automatically (use -v 2 for details).

/events/
NoReverseMatch

Common mistakes:

  • Assuming reverse() sends an HTTP request.
  • Leaving out the namespace once app_name is set.
  • Treating a route name as if it could never change.

Follow-up the interviewer might ask:

  • “Can two apps both name a route list?”
  • “How would you find every caller before renaming a route?”

L4 (Staff): How can route order cause a surprise?

What the interviewer is testing: Can you reason about overlapping patterns before a larger URL configuration makes them hard to see?

Flip to check your answerFold answer back

Perfect answer: Django uses the first complete match, not the most specific one. A broad pattern placed before a narrower one takes every path they share, and nothing warns you. Our present patterns do not overlap, so their order does not matter yet. Once Otahque gains routes with captured values, such as event pages addressed by a short name, the order becomes a design decision. I would put exact routes first, keep broad patterns behind a distinct prefix, and test the view each concrete address selects, because a shadowed route still returns a response.

Behind the scenes:

django/urls/resolvers.py (summary, not the source)

# for pattern in self.url_patterns:
#     match = pattern.resolve(remaining_path)
#     if match: return it. Later patterns are never tried.

Code proof: two throwaway URLconfs, used only here, hold the same patterns in opposite orders:

Terminal

uv run python manage.py shell -c "
from django.urls import path, resolve
def broad(request, slug): pass
def exact(request): pass
class BroadFirst:
    urlpatterns = [
        path('<slug:slug>/', broad),
        path('events/', exact),
    ]
class ExactFirst:
    urlpatterns = BroadFirst.urlpatterns[::-1]
for urls in (BroadFirst, ExactFirst):
    print(resolve('/events/', urlconf=urls).func.__name__)
"

Output

12 objects imported automatically (use -v 2 for details).

broad
exact

Common mistakes:

  • Assuming Django chooses the most specific route.
  • Testing only the status, which a shadowing view can also return as 200.
  • Placing a broad pattern at the empty prefix of a shared project URLconf.

Follow-up the interviewer might ask:

  • “How would you detect a shadowed route in a large project?”
  • “When would you give a broad pattern its own prefix instead?”

L5 (Lead): A route returns 404. How do you lead the investigation?

What the interviewer is testing: Can you lead a careful diagnosis that preserves evidence and work?

Flip to check your answerFold answer back

Perfect answer: First record the exact address, method, and response, because a reproduction is worth more than a theory. Next ask what Django tried: compare the path with the project and app patterns in order, and check includes, prefixes, and slashes. If a pattern did match, the view itself may have raised the 404, and the cause is in its data or rules rather than its route. Change one thing at a time, and add a regression test that fails before the fix. I would also ask the team to leave the failing state in place until it is understood, rather than deleting routes to see what happens. Debug output helps locally, but must never be exposed publicly.

Behind the scenes:

django/urls/resolvers.py (summary, not the source)

# When nothing matches, URLResolver raises
#     Resolver404({'tried': [...], 'path': path})
# With DEBUG on, the 404 page lists those tried patterns.

Code proof: ask Django what it tried for a path that matches nothing:

Terminal

uv run python manage.py shell -c "
from django.urls import Resolver404, resolve
try:
    resolve('/does-not-exist/')
except Resolver404 as error:
    for tried in error.args[0]['tried']:
        names = [repr(str(p.pattern)) for p in tried]
        print(' then '.join(names))
"

Output

12 objects imported automatically (use -v 2 for details).

'admin/'
'' then ''
'' then 'events/'

Common mistakes:

  • Treating every 404 as a missing route.
  • Deleting work or changing several routes before capturing the failing address.
  • Fixing the route without adding a test that would have caught it.

Follow-up the interviewer might ask:

  • “How do you tell a missing route from a view that raised 404?”
  • “Does one unknown-path test prove that every invalid path is handled correctly?”
