Checkpoint: Quiz and Challenge

Quiz

Que. 2 Why does Django need two commands, makemigrations and migrate, rather than one that updates the database directly?

Flip to check your answerFold answer back

Answer. They change different things. makemigrations writes a file in the code, which you read, test, and commit with the model change. migrate changes one database, applying the files it has not received. Keeping them apart means every database, yours, a teammate’s, the test database, and a server, receives the same reviewed files in the same order.

Que. 3 showmigrations events shows [X] 0001_initial and [ ] 0002_event_slug. What does each mark mean, and what will migrate do?

Flip to check your answerFold answer back

Answer. [X] means this database’s django_migrations table has a row for 0001_initial, so it was applied. [ ] means the file 0002_event_slug.py exists but has not been applied here. migrate will apply 0002 and record it.

Que. 4 Inside RunPython, why does fill_slugs() call apps.get_model('events', 'Event') instead of importing Event from events.models?

Flip to check your answerFold answer back

Answer. apps.get_model() returns the historical model, matching the table at that point in the migration history. The imported model is the current one, which may have fields that a later migration adds; when the migration runs on a fresh database months later, those columns do not exist yet, and it fails.

Que. 5 In the lab, going back to 0001 unapplied 0002_event_slug. What happened to the slug values, and what happened to the three events?

Flip to check your answerFold answer back

Answer. Unapplying 0002 removed the slug column, and the values went with it; the reverse code had already cleared them. The three events, and every other column, remained. Reversing a migration that removes a column always removes that column’s data, so reverse code needs as much thought as forward code.

Que. 6 The 29 tests pass. Which test fails if a teammate later adds a field to Event and commits without running makemigrations?

Flip to check your answerFold answer back

Answer. test_every_model_change_has_a_migration in config/tests.py. It runs makemigrations --check --dry-run, which finds the missing migration and ends with SystemExit; the test fails with a message naming the missing migration file and its operation.

Mini-Challenge

Que. 7 In the lab copy only, imagine the team wants to split location into venue and city, both text. Without running anything, write in your notes the migrations you would need, in order, and the forward and reverse functions of the data migration. Assume each current location reads like Community hall, Leeds, and the reverse should join the two parts with a comma and a space.

Flip to check your answerFold answer back

Answer. Three migrations, as in Step 7. First, makemigrations writes a schema migration that adds venue and city, each CharField(max_length=200, blank=True), so the existing rows are valid with empty text. Second, a data migration from makemigrations events --empty --name split_location holding RunPython(split_location, join_location). split_location() gets Event with apps.get_model('events', 'Event'), and for each event uses event.location.partition(', ') to set venue to the part before the comma and city to the part after, saving with update_fields=['venue', 'city']. A location without a comma keeps all its text in venue and an empty city. join_location() does the opposite: it sets location to venue and city joined by ', ', or to venue alone when city is empty, and saves location. Third, once the code reads the new fields, a schema migration removing location. Its reverse would bring the column back empty, so the reverse of the data migration must run after it, which the dependency order guarantees: unapplying goes newest first. Whether the split is a good idea for Otahque is a product question; the ERD keeps one location.

What We Learned

  • A migration is a versioned file describing one step in the schema’s history. makemigrations writes it by comparing the models with the existing files; migrate applies it to one database and records it.
  • A migration file holds dependencies and operations; dependencies across apps put every migration into one graph, which is why the custom user had to be in accounts’ first migration.
  • The autodetector replays migration files, not the database; the django_migrations table records what each database has applied.
  • sqlmigrate and migrate --plan preview a migration’s SQL and order; showmigrations shows what is applied.
  • TestCase tests use a test database built from the migrations and discarded afterwards; SimpleTestCase tests cannot use a database.
  • createsuperuser asks for the fields the user model names, and saves the account through the manager.
  • Migrations are committed with their model change; db.sqlite3 never is.
  • A required, unique field on a table with rows takes three migrations: add it nullable, fill it with a data migration, then require it. Data migrations use historical models from apps.get_model() and need reverse code.
  • On SQLite and PostgreSQL, each migration is a transaction, so a failed run stops between migrations, never inside one.

Your Chapter 18 work was committed at the end of Step 6, before the lab, so that the lab could copy it. For the record, these were the commands, in PowerShell, a macOS shell, or Linux/WSL Bash, beside manage.py:

Terminal

git add accounts config events
git status --short

Output

A  accounts/migrations/0001_initial.py
M  accounts/tests.py
A  config/tests.py
A  events/migrations/0001_initial.py

Terminal

git commit -m "Add the first migrations and database tests"
