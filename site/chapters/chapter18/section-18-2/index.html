What You Need to Know

From models to tables

A model describes a table, and Chapter 16 showed that importing one creates nothing. Something has to turn the description into a real table, and later turn each change to the description into a change to the table.

New Concept: a migration

What problem exists? The database’s structure, its schema, has to match the models on every computer that runs Otahque: yours, a teammate’s, the test database, and one day the server. Each change has to be made once, in order, and never forgotten.

What did people do before? They kept SQL scripts with numbered names, ran them by hand, and wrote down somewhere which ones each database had received. When the note was wrong, databases drifted apart.

What is a migration? A Python file, kept in an app’s migrations folder, that describes one step in the schema’s history, such as “create the Event table” or “add a column”. makemigrations compares the models with the existing migration files and writes a new file for the difference. migrate applies the files a database has not yet received, and records each one in that database.

Why use migrations? They are reviewable like any code, committed with the model change they belong to, applied in a known order, and can often be reversed. A migration is to the schema what a commit from Chapter 8 is to the code: a named step in a shared history.

Now let’s use it. Otahque’s first two migrations create the event and user tables.

The two commands are separate on purpose. Writing a migration is a change to the code: you read it, test it, and commit it. Applying it is a change to one database: yours now, the test database in a moment, a server later. Keeping them apart means the same reviewed file is what every database receives. Figure 18.1 shows the route a model change takes.

Inside a migration file

Django writes migration files for you, but you read every one before committing it, as you would a teammate’s code.

New Concept: the parts of a migration file

What problem exists? A file you cannot read is a file you cannot review. You need to know what a migration will do before it runs.

What did people do before? A hand-written SQL script said exactly what it did, but not what it needed first or how to undo it.

What is in the file? One class, Migration, with a few attributes. initial = True marks an app’s first migration. dependencies lists the migrations that must already be applied, as pairs of app label and migration name. operations lists the changes, in order: CreateModel makes a table, AddField adds a column, AlterField changes one, and RunPython runs Python code that changes data. A model with a custom manager marked use_in_migrations, like Chapter 17’s UserManager, also lists it under managers.

Why read it? The file is what every database will receive. Reading it shows whether Django understood your change, and whether it depends on what you expect.

Now let’s use it. Step 3 reads Otahque’s two first migrations.

Dependencies decide the order. Each app’s migrations form a chain, 0001, 0002, and so on, in which each one depends on the one before. Migrations can also depend on another app’s migrations. Otahque’s user model has many-to-many links to Django’s auth permissions and groups, so its first migration depends on the latest auth migration. In the other direction, Django’s own admin app records which user made each change, so its first migration depends on whichever app AUTH_USER_MODEL names. Chapter 17’s L5 code proof showed that dependency as ('accounts', '__first__'). Django puts every migration of every installed app into one migration graph and applies them in an order that satisfies every dependency. That is why accounts.User had to be created in the first migration of the accounts app: Django’s own apps wait for it.

How Django knows what changed, and what has run

Under the Hood: the autodetector and the django_migrations table

To decide what to write, makemigrations never looks at the database’s tables or columns. It loads every migration file and replays their operations, in dependency order, into an in-memory description of each model, called the project state. It then compares that state with the models in your code. The part of Django that does the comparison is the autodetector. Each difference becomes an operation: a model in the code but not in the state becomes CreateModel, a new field becomes AddField, a changed option becomes AlterField. If nothing differs, it reports “No changes detected”. migrate, on the other hand, depends on the database, and on one table in particular, django_migrations, which it creates on its first run. Each row records one applied migration by app and name, with the time it was applied. migrate applies, in graph order, every migration that has no row, and adds a row after each. So the files say what the schema should be, and the table says how far this database has come. A file without a row is waiting to be applied; this is why deleting a database’s rows, or its files, causes confusion that is hard to undo. makemigrations reads the same table for one purpose only: to check that the applied history is consistent with the files, which matters in Step 2.

Because each database keeps its own record, your db.sqlite3, a teammate’s, and the test database can be at different points in the same history, and migrate brings each one forward from where it is.

Schema migrations and data migrations

Most migrations change structure. Some must also change the rows inside a table, because the new structure needs values the old rows do not have.

New Concept: data migrations and historical models

What problem exists? Adding a column to a table with rows leaves every existing row without a value. If the column must hold something meaningful, such as a value worked out from each row’s title, no single default will do.

What did people do before? They ran a one-off script against each database after changing the table, and hoped every copy received it.

What is a data migration? A migration whose operation, RunPython, calls a function you write. The function receives apps, a registry of historical models: versions of each model as they stood at that point in the migration history, built from the migration files. You get one with apps.get_model('events', 'Event'). A second function, the reverse code, undoes the change when the migration is unapplied. RunPython.noop, a function that does nothing, stands in when there is nothing to undo.

Why historical models? A migration may run months after it was written, when the real model has changed again. Importing events.models.Event would give the model as it is today, with fields that may not exist yet at that point in the history. A historical model matches the table at exactly that point. It has the fields, and managers marked use_in_migrations, but none of your own methods.

Now let’s use it. The lab in Step 7 fills a new column with a data migration, and reverses it.

Table 18.1 compares the two kinds.

On SQLite and PostgreSQL, Django runs each migration inside a transaction: either every operation in that migration takes effect, or none does. If a run of several migrations fails, the ones already applied stay applied, the one that failed is rolled back, and the rest are not attempted, so the run stops between two migrations, never in the middle of one. On MySQL, schema changes cannot be rolled back this way. Otahque uses SQLite until Chapter 32 moves it to PostgreSQL. Step 7 shows both a rollback and a run that stops part-way.

Try it yourself

Que. 1 Raj suggests that makemigrations should look at db.sqlite3 to see which columns already exist. Why does it compare with the migration files instead?

Flip to check your answerFold answer back

Answer. The migration files are the shared history every database receives, and they are in Git; each database is only one copy, at some point in that history. If makemigrations read your database, a column you had added by hand, or a migration you had not yet applied, would change what it wrote, and the file would not suit anyone else’s database. Comparing the code with the replayed files gives the same answer on every computer.

Tests that use a database

Every test so far has been a SimpleTestCase, which refuses to touch a database. Saving a user needs one.

New Concept: TestCase and the test database

What problem exists? A test that saves rows must not touch your development database, and each test must start from the same empty tables, whatever the test before it saved.

What did people do before? Tests ran against a shared database and cleaned up after themselves, until one forgot and the next test failed for no visible reason.

What is TestCase? A test class whose tests may use the database. When a run includes one, Django first creates a separate test database and builds it by applying every migration, then runs each TestCase test inside a transaction that it rolls back afterwards, and destroys the test database at the end. With SQLite, the test database lives in memory, so db.sqlite3 is never touched.

Why use it? The test database is built from the same migrations as yours, so the tests also prove that the migrations work from an empty database. Each test sees empty tables.

Now let’s use it. Step 2 writes four TestCase tests, before the migrations exist.

Use SimpleTestCase whenever a test does not need the database: it is faster, and it fails loudly if a database query sneaks in. Use TestCase when the behaviour is about saved rows, as it is for a user who must be stored and read back.

Prefer committing db.sqlite3?

Committing the database file can seem simpler than committing migrations: a teammate would receive the tables and the rows at once. It works for a day. Then two people’s copies diverge, Git cannot merge a binary file, and private data, such as account emails and password hashes, ends up in the repository’s history for good. Chapter 8’s .gitignore already keeps db.sqlite3 out. Migrations are the shared part: small text files that each computer applies to its own database. Sample data, when Otahque needs it, comes from tools chosen in Chapter 41, not from a copied file.

Changing a table that already holds rows

Adding a column to an empty table is one migration. Adding a required, unique column to a table that already holds rows takes three, because each row needs its own value before the database can insist on one.

In practice: changing a populated table in steps

Situation. A team wants each event to have a readable address part, a slug, such as python-meetup-3, and wants the database to guarantee that no two events share one. The table already holds events.

Application. Django’s documentation describes a three-step pattern. First, add the column allowing empty values, so the existing rows are valid. Second, a data migration gives each row its own value. Third, change the column to require a value and to be unique, which now succeeds because every row has a distinct one. Each step is a separate migration, reviewed and reversible.

Consideration. Between the second and third steps, a row saved by code that does not yet set a slug would break the third step. On a small project with one database, the steps run back to back. On a live site, the order of code and migration deployments has to be planned, which is Chapter 64’s subject.

Otahque’s ERD has no slug, and Chapter 10’s addresses use each event’s id, so the lab in Step 7 adds one only in a disposable copy, to practise the pattern. The reader project is not changed.
