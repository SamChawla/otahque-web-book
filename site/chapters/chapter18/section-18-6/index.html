Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 and L2 check what you have just done. L3 asks why data migrations work the way they do. L4 and L5 look ahead to a live application with a team: attempt them now, and return to them after Chapter 64. They are extension questions, not a gate to the next chapter. Each code proof is a short file in the practice folder that starts by importing setup_django.py. Run the L1 to L3 proofs from the folder that holds manage.py with uv run python ../practice/ followed by the file name, and the L4 and L5 proofs from the lab folder, as each one says.

L1 (Junior): What do makemigrations and migrate each do, and why are they separate?

What the interviewer is testing: Do you know the difference between describing a schema change and applying it?

Flip to check your answerFold answer back

Perfect answer: makemigrations compares the models with the migrations already written, and writes a new migration file in each app for the difference: operations such as CreateModel or AddField. It does not change the database, and it does not read its tables to decide what to write. migrate applies the migration files a database has not received, in dependency order, and records each one in that database’s django_migrations table. They are separate because the migration is code: it is reviewed, tested, and committed with the model change, and the same file is then applied to every database: a developer’s, the test database, and production. A command that changed the database straight from the models would leave nothing to review and no shared history.

Behind the scenes:

two commands (summary)

models + files -> makemigrations -> new 0002_... file
review, test, commit the file with the model change
file + django_migrations -> migrate -> table changed
each database records its own applied migrations

Code proof: the migration files Django found for Otahque’s apps, and the ones this database has applied:

../practice/l1_files_and_records.py

import setup_django
from django.db import connection
from django.db.migrations.loader import MigrationLoader

loader = MigrationLoader(connection)


def ours(keys):
    return sorted(f'{app}.{name}' for app, name in keys
                  if app in ('accounts', 'events'))


print('files:', *ours(loader.disk_migrations))
print('applied:', *ours(loader.applied_migrations))

Output

files: accounts.0001_initial events.0001_initial
applied: accounts.0001_initial events.0001_initial

MigrationLoader is the part of Django both commands use to read the files and the applied records. After Step 5, the two sets are the same.

Common mistakes:

  • Running migrate after a model change and expecting it to notice, without makemigrations.
  • Committing the model change but not its migration file.
  • Thinking makemigrations reads the database’s columns.

Follow-up the interviewer might ask:

  • “What would showmigrations print if a teammate’s migration had been pulled but not applied?”
  • “How would you catch a missing migration before code is merged?”

L2 (Mid-Level): What is inside a migration file, and how does Django decide the order to apply migrations?

What the interviewer is testing: Can you read a migration and explain dependencies across apps?

Flip to check your answerFold answer back

Perfect answer: A migration file defines a Migration class. initial marks an app’s first migration. dependencies lists the migrations that must already be applied, as app label and name pairs. operations lists the changes in order, such as CreateModel, AddField, AlterField, or RunPython, and a CreateModel may record options and managers. Within an app, each migration depends on the previous one, forming a chain. Across apps, a migration depends on whatever it needs: Otahque’s user migration depends on auth’s latest migration for the group and permission tables, and Django’s admin app depends on the user model’s app through swappable_dependency(settings.AUTH_USER_MODEL), which resolves to that app’s first migration. The loader combines every app’s migrations into one graph, and migrate applies them in an order that satisfies all the dependencies; migrate --plan shows that order.

Behind the scenes:

ordering (summary)

dependencies -> edges between migrations
graph        -> every installed app, one graph
swappable    -> ('accounts', '__first__') for the user
plan         -> an order that respects every edge

Code proof: the admin app’s dependencies, and the last two steps of the plan that leads to it:

../practice/l2_order.py

import setup_django
from django.db import connection
from django.db.migrations.loader import MigrationLoader

loader = MigrationLoader(connection)
admin = loader.get_migration('admin', '0001_initial')
print(admin.dependencies)
plan = loader.graph.forwards_plan(('admin', '0001_initial'))
print(plan[-2:])

Output

[('accounts', '__first__'), ('contenttypes', '__first__')]
[('accounts', '0001_initial'), ('admin', '0001_initial')]

admin.0001_initial depends on the first migration of whichever app holds the user model, so accounts.0001_initial comes immediately before it.

Common mistakes:

  • Renaming a migration file, which breaks every migration that depends on it by name.
  • Editing dependencies by hand to make an error go away.
  • Assuming migrations run in alphabetical or date order.

Follow-up the interviewer might ask:

  • “What would happen if the user model were created in accounts’ second migration?”
  • “How would you see the SQL one migration will run?”

L3 (Senior): Why must a data migration use apps.get_model() instead of importing the model?

What the interviewer is testing: Do you understand historical models, and why a migration must keep working long after it was written?

Flip to check your answerFold answer back

Perfect answer: A migration runs whenever a database reaches it in the history: today on my database, next year on a new developer’s empty database, or in the test database on every run. If the migration imports events.models.Event, it gets the model as it is when it runs, which may include fields that later migrations add. On a fresh database those columns do not exist yet at that point, so the queries fail. RunPython passes the function an apps registry instead, and its get_model() returns a historical model, rebuilt by replaying the migrations up to that point. Its fields match the table exactly. It does not have the model’s own methods, such as __str__(), or custom managers unless they set use_in_migrations = True, so data migration code should depend only on fields. The same applies to the reverse function, which should restore the state before the migration, or be RunPython.noop when there is nothing to undo.

Behind the scenes:

historical models (summary)

import events.models.Event -> today's model, any time
apps.get_model(...)        -> model at this migration
has                        -> fields, migration managers
lacks                      -> your methods, e.g. __str__

Code proof: the historical Event at 0001_initial, compared with the current class:

../practice/l3_historical.py

import setup_django
from django.db import connection
from django.db.migrations.loader import MigrationLoader

from events.models import Event

loader = MigrationLoader(connection)
state = loader.project_state(('events', '0001_initial'))
Old = state.apps.get_model('events', 'Event')
print(Old is Event)
print(str(Event(title='Python meetup')))
print(str(Old(title='Python meetup')))
print(hasattr(Event, 'Status'), hasattr(Old, 'Status'))

Output

False
Python meetup
Event object (None)
True False

The historical model is a different class. It prints Django’s generic text because it lacks Chapter 16’s __str__(), and it has no Status choices class; it has only what the migration files record.

Common mistakes:

  • Importing the current model inside RunPython.
  • Calling a custom model method inside a data migration.
  • Writing no reverse function, so the migration cannot be unapplied.

Follow-up the interviewer might ask:

  • “How would a data migration create users with the custom manager?”
  • “When is RunPython.noop the right reverse function, and when is it hiding a problem?”

L4 (Staff): You must add a required, unique field to a table with a million rows in production. How do you plan it?

What the interviewer is testing: Looking ahead: can you turn a one-line model change into a safe sequence of reviewable, reversible steps?

Flip to check your answerFold answer back

Perfect answer: I would not add it in one migration: every existing row would need a value at once, and a one-off default would give them all the same one, which the unique rule forbids. I would use the three-step pattern from Django’s documentation, planned around deployments. First, a migration adds the column allowing NULL, which most databases can do quickly. Second, a code release writes a value for every new or changed row, so the gap stops growing. Third, a data migration fills the existing rows; for a million rows I would process them in batches, and consider making that migration non-atomic or running the backfill as a separate command, because one long transaction can hold locks and run out of time. Fourth, once every row has a distinct value, a migration requires it and adds the unique rule. Each step has reverse code and is rehearsed forwards and backwards on a copy of production data, with timings, before the real run. This chapter showed the pattern on three rows; Chapter 64 adds the deployment and database details.

Behind the scenes:

large table (summary)

0002 AddField null=True      -> quick, rows stay valid
release                      -> new rows get values
0003 RunPython, in batches   -> old rows get values
0004 AlterField unique=True  -> only when every row is set

Code proof: run from the lab folder, the three lab migrations, their operations, and whether each can be reversed:

../practice/l4_operations.py

import setup_django
from django.db import connection
from django.db.migrations.loader import MigrationLoader

loader = MigrationLoader(connection)
for name in ('0002_event_slug', '0003_fill_slugs',
             '0004_alter_event_slug'):
    migration = loader.get_migration('events', name)
    for operation in migration.operations:
        print(name, '|', operation.describe(), '|',
              operation.reversible)

Output

0002_event_slug | Add field slug to event | True
0003_fill_slugs | Raw Python operation | True
0004_alter_event_slug | Alter field slug on event | True

Run it in the lab, where the practice folder is one level up. Every step can be reversed; 0003 only because it has clear_slugs. Without it, the middle line ends in False.

Common mistakes:

  • Adding unique=True and a required value in one migration on a populated table.
  • Filling a large table in one transaction without measuring it first.
  • Deploying the final migration before the code that writes the new field.

Follow-up the interviewer might ask:

  • “How would you know the backfill has finished before the last step?”
  • “What would you do if the unique step failed in production?”

L5 (Lead): Two developers each created 0005 in the same app, and a teammate wants to edit an applied migration. What rules would you set?

What the interviewer is testing: Looking ahead: can you set working rules that keep a shared migration history trustworthy?

Flip to check your answerFold answer back

Perfect answer: Two 0005 files that both depend on 0004 give the app two latest migrations, two leaf nodes, and Django refuses to continue until they are joined. Joining them with a merge migration, from makemigrations --merge, is Chapter 64’s subject. Editing an applied migration is a different problem: databases that already ran it will never run the new version, so their schemas silently diverge. Django’s documentation says migrations should rarely be edited by hand. My working rules for Otahque, which are team rules, not Django’s: commit each model change with its migration, in the same commit; never edit or delete a migration once it has been applied anywhere but your own computer, and make a new one instead; run the migration guard test and makemigrations --check in CI, which Chapter 34 sets up, so missing migrations and two leaf nodes are caught before merging; resolve conflicts with a merge migration, then rerun the tests; never put demo data in a migration, because migrations run in every environment, production included; and never “fix” a problem by deleting a shared database or its migration files.

Behind the scenes:

team rules (summary)

model + migration -> one commit
applied elsewhere -> never edit; add a new migration
two 0005 leaves   -> caught by --check; merge, Chapter 64
demo data, db     -> never in migrations or Git

Code proof: in the lab folder, two migrations with the same parent make Django stop. In PowerShell:

PowerShell

uv run python manage.py makemigrations events --empty `
    --name sam_note
cd events/migrations
Copy-Item 0005_sam_note.py 0005_raj_note.py
cd ../..
uv run python manage.py makemigrations --check --dry-run

In a macOS shell or Linux/WSL Bash:

Terminal

uv run python manage.py makemigrations events --empty \
    --name sam_note
cd events/migrations
cp 0005_sam_note.py 0005_raj_note.py
cd ../..
uv run python manage.py makemigrations --check --dry-run

The last command prints, shortened:

Output

CommandError: Conflicting migrations detected; multiple ...
To fix them run 'python manage.py makemigrations --merge'

The full first line names both leaves. Afterwards, delete the two 0005 files, with rm or Remove-Item, and the check prints No changes detected again.

Common mistakes:

  • Editing an applied migration and expecting others to receive it.
  • Renumbering one of two conflicting files by hand.
  • Seeding sample data in a migration, so it reaches production.

Follow-up the interviewer might ask:

  • “When would you allow a migration to be edited?”
  • “How would you review a merge migration?”
