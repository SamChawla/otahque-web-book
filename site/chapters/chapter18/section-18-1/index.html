Why This Matters

Sam wants to put the November meetup into Otahque for real. Until now, every event the pages showed came from a list in the code, and the Event model from Chapter 16 described a table that did not exist. Sai’s account is in the same position: Chapter 17 wrote the user model and tested that it hashes passwords, but nothing could be saved, because the database was still empty. If Otahque restarted, nothing would be lost, because nothing had been kept. That changes in this chapter. Otahque gets its tables, and the first accounts it saves survive a restart.

Creating tables once is the easy part. The harder part comes months later, when the team needs to change a table that already holds registrations. Imagine someone adding a required column to the event table by typing a command into the live database. The command fails on the rows that already exist, or quietly fills them with a value nobody chose. Another teammate’s copy of the database no longer matches the code, and nobody can say which changes have been made where. Django’s answer is the migration: a small, versioned file that describes one change to the database’s structure, travels with the code in Git, and is applied in the same order on every computer that runs Otahque.

This chapter turns the models from Chapters 16 and 17 into tables, through migrations you generate, read, and preview before you apply them. Your tests start using a real database. You create the first account, an administrator account for your own computer. Then, in a disposable copy of the project, you change a table that already holds events, run the change forwards and backwards, and see that no row is lost.

By the end of the chapter, you will be able to:

  • explain what a migration is, and why Django separates writing one (makemigrations) from applying it (migrate);
  • read a generated migration file and preview its SQL and the order Django will apply it in;
  • apply migrations and confirm what Django has recorded as applied;
  • write tests that save to a database, and say where that database comes from;
  • create a local superuser with createsuperuser;
  • change a table that holds rows in reviewable, reversible steps, including a data migration that uses historical models.

This chapter creates the tables the Chapter 15 ERD describes for events and members, and changes nothing else in the reader project. It does not teach queries: the few lines that save and read rows are previews of Chapter 19. Relationships between tables, such as registrations, arrive in Chapter 20, and database constraints, including the decision about email letter case, in Chapter 21. The superuser is not used to sign in anywhere yet; Django’s admin site is Chapter 23. PostgreSQL is Chapter 32, and conflicts between teammates’ migrations, squashing, and production rollouts are Chapter 64.
