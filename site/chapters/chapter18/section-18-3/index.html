How We Build It

Start from Chapter 17, in the folder containing manage.py, with your own .env, the locked environment, 25 passing tests, the user model committed, and a db.sqlite3 with no tables. You change one file, accounts/tests.py, and create one, config/tests.py, both before any migration exists. makemigrations then writes a first migration, 0001_initial.py, in the migrations folder of each app. migrate creates the tables in db.sqlite3, and createsuperuser saves the first account. A practice script goes in ../practice. At the end of Step 6, 29 tests pass, every migration is applied, and the work is committed. Step 7 then copies the committed project into ../practice/migrations-lab, a lab you discard afterwards, and changes the event table there.

The Custom Way

This illustration keeps a schema up to date by hand, with numbered SQL scripts and a home-made table of applied versions; do not add it to the project:

illustration_only/apply_scripts.py (not part of the project)

import sqlite3

SCRIPTS = {
    1: 'CREATE TABLE event (id INTEGER PRIMARY KEY,'
       ' title TEXT NOT NULL)',
    2: 'ALTER TABLE event ADD COLUMN slug TEXT',
}

db = sqlite3.connect(':memory:')
db.execute('CREATE TABLE schema_version (number INTEGER)')


def upgrade():
    done = {n for (n,) in db.execute(
        'SELECT number FROM schema_version')}
    for number in sorted(SCRIPTS):
        if number not in done:
            db.execute(SCRIPTS[number])
            db.execute('INSERT INTO schema_version'
                       ' VALUES (?)', (number,))


upgrade()
upgrade()
print(db.execute('SELECT number FROM schema_version')
      .fetchall())

Output

[(1,), (2,)]

It works: running upgrade() twice applies each script once. Now list what it does not do. It has one sequence of numbers for the whole project, so two apps, or two teammates, cannot add scripts without colliding, and nothing says that one script needs another app’s table first. The scripts are written by hand, so nothing checks that they match the models, and a forgotten column only appears when a page fails. There is no way back: undoing script 2 means writing another script. Tests would need their own copy of the whole routine. And Django’s own apps, which need the user table to exist before their tables can point at it, would have no way to say so. Django’s migrations do each of these things, and the steps below use them.

The Django Way

Seven steps follow. Steps 1 to 6 work in the reader project; Step 7 works in a lab copy. The tests come before the migrations, so you see them fail first.

Terminal

uv run python manage.py makemigrations --check --dry-run

Output

Migrations for 'events':
  events\migrations\0001_initial.py

  accounts\migrations\0001_initial.py
    + Create model User

On Windows, in PowerShell and in Git Bash, Django prints paths with backslashes; on macOS and Linux they have forward slashes. + Create model names the operation each file would hold. Both apps need a first migration. No file has been written: each app’s migrations folder still holds only __init__.py. Finally, git status --short should print nothing.

If the table query lists tables, migrate ran at some point since Chapter 15. Rename db.sqlite3, for example to db-before-ch18.sqlite3, keep it, and carry on: Django creates a new, empty file the next time it needs one. If a 0001_initial.py file already exists in either app, from an earlier attempt, do not delete it; move it into ../practice and keep it to compare with the one you generate in Step 3.

Step 2: Write the database tests first

Chapter 17’s tests stopped before anything was saved. These tests save users and read them back. Open accounts/tests.py and change its imports to these:

accounts/tests.py (imports)

from django.contrib.auth import get_user_model
from django.core.exceptions import ValidationError
from django.db import IntegrityError
from django.test import SimpleTestCase, TestCase

from .models import User

Then add a third class at the end of the file, after UserManagerTests:

accounts/tests.py (end of file)

class UserCreationTests(TestCase):
    """Members saved through the manager, in the database."""

    def test_create_user_saves_a_member(self):
        user = User.objects.create_user(
            email='Sai@EXAMPLE.org',
            password='correct horse',
            display_name='Sai',
        )
        saved = User.objects.get(pk=user.pk)
        self.assertEqual(saved.email, 'Sai@example.org')
        self.assertTrue(
            saved.check_password('correct horse')
        )
        self.assertTrue(saved.is_active)
        self.assertFalse(saved.is_staff)
        self.assertFalse(saved.is_superuser)

    def test_create_superuser_saves_both_flags(self):
        user = User.objects.create_superuser(
            email='sam@example.org',
            password='correct horse',
            display_name='Sam',
        )
        saved = User.objects.get(pk=user.pk)
        self.assertTrue(saved.is_staff)
        self.assertTrue(saved.is_superuser)

    def test_email_is_unique_in_the_database(self):
        User.objects.create_user(
            email='raj@example.org',
            password='correct horse',
            display_name='Raj',
        )
        with self.assertRaises(IntegrityError):
            User.objects.create_user(
                email='raj@example.org',
                password='another horse',
                display_name='Raj K.',
            )

User.objects.get(pk=user.pk) fetches the saved row again by its primary key. It is a one-line preview of Chapter 19’s queries, used here so that each test checks what the database holds, not only the object in memory. The first test completes Chapter 17’s manager contract: create_user() saves the email with its domain lowercased and its local part as typed, which says nothing yet about whether Sai@ and sai@ are one member; Chapter 21 decides that. The second checks that create_superuser() saves both flags. The third saves two accounts with the same email and expects the database itself to refuse the second with an IntegrityError, the error Django raises when a database rule is broken. unique=True was only a description in Chapter 17; once the table exists, it is a rule the database enforces.

The second new file guards every app at once. A model change committed without its migration is one of the most common mistakes in Django projects: the code expects a column that no database has. Create config/tests.py:

config/tests.py

"""Tests that cover the whole project."""
from io import StringIO

from django.core.management import call_command
from django.test import TestCase


class MigrationTests(TestCase):
    """Every model change has a migration."""

    def test_every_model_change_has_a_migration(self):
        output = StringIO()
        try:
            call_command(
                'makemigrations', '--check', '--dry-run',
                stdout=output,
            )
        except SystemExit:
            self.fail(
                'Missing migrations:\n' + output.getvalue()
            )

call_command() runs a management command from Python, as if you had typed it. StringIO collects what it prints, so the failure message can show it. When something is missing, --check ends the command with SystemExit, which the test turns into a failure naming the missing migrations. It lives in config, the project package, because the rule covers every app. It must be a TestCase, not a SimpleTestCase, because makemigrations reads the database’s applied migrations to check that they are consistent.

Common Error: a database test written as SimpleTestCase

If either new class inherits from SimpleTestCase, its tests fail with DatabaseOperationForbidden, and the message says that database queries are not allowed in a SimpleTestCase. The guard test fails the same way, because makemigrations queries the applied migrations. Change the base class to TestCase, as in the listings.

Run every test:

Terminal

uv run python manage.py test

Expected result, shortened with ...:

Output

Found 29 test(s).
Creating test database for alias 'default'...
Traceback (most recent call last):
...
ValueError: Dependency on app with no migrations: accounts

This red stage looks different from earlier ones. Django finds 29 tests, then stops while building the test database, before any test runs, with the same error migrate gave in Chapter 17. The test database is built from migrations, and there are none. The manager tests describe behaviour that needs tables; the guard test is different, because it cannot fail first in the usual way. It is a guard against future mistakes, and Step 7 makes it fail on purpose.

Step 3: Generate and read the migrations

Write the migrations, beside manage.py, in any of the three shells. With no app label, makemigrations writes what every installed app needs:

Terminal

uv run python manage.py makemigrations

Output

Migrations for 'events':
  events\migrations\0001_initial.py
    + Create model Event
Migrations for 'accounts':
  accounts\migrations\0001_initial.py
    + Create model User

Open events/migrations/0001_initial.py. Django wrote it in its own layout, with some lines over 150 characters wide, and its first line records the Django version and the moment you ran the command, so your file carries a different date. Keep it exactly as Django wrote it: generated files are not reformatted or edited by hand. This excerpt wraps the long lines and marks left-out parts with ...:

events/migrations/0001_initial.py (excerpt)

# Generated by Django 6.1.2 on ...

from django.db import migrations, models


class Migration(migrations.Migration):

    initial = True

    dependencies = [
    ]

    operations = [
        migrations.CreateModel(
            name='Event',
            fields=[
                ('id', models.BigAutoField(
                    auto_created=True, ...)),
                ('title', models.CharField(max_length=200)),
                ('starts_at', models.DateTimeField()),
                ('ends_at', models.DateTimeField()),
                ...
                ('status', models.CharField(
                    choices=[('draft', 'Draft'), ...],
                    default='draft', max_length=20)),
            ],
            options={
                'ordering': ['starts_at'],
            },
        ),
    ]

initial = True marks the app’s first migration. The event table needs nothing else first, so dependencies is empty. CreateModel repeats every field from Chapter 16’s model, including the id Django adds, and the ordering option. The migration keeps its own copy of the fields, so it still means the same thing after the model changes later. Now open accounts/migrations/0001_initial.py:

accounts/migrations/0001_initial.py (excerpt)

# Generated by Django 6.1.2 on ...

import accounts.managers
import django.utils.timezone
from django.db import migrations, models


class Migration(migrations.Migration):

    initial = True

    dependencies = [
        ('auth', '0012_alter_user_first_name_max_length'),
    ]

    operations = [
        migrations.CreateModel(
            name='User',
            fields=[
                ...
                ('email', models.EmailField(
                    max_length=254, unique=True, ...)),
                ('display_name', models.CharField(
                    max_length=100)),
                ...
                ('groups', models.ManyToManyField(
                    ..., to='auth.group', ...)),
                ('user_permissions', models.ManyToManyField(
                    ..., to='auth.permission', ...)),
            ],
            ...
            managers=[
                ('objects', accounts.managers.UserManager()),
            ],
        ),
    ]

This is the migration Chapter 17 prepared for. User is created in accounts’ first migration, as the swapped user model must be. It depends on auth’s latest migration because groups and user_permissions link to auth’s group and permission tables. The managers list records UserManager, because Chapter 17 marked it use_in_migrations, so a data migration that creates users could call create_user() on the historical model.

Common Error: No changes detected

If makemigrations prints No changes detected here, either the migration files already exist, from an earlier run, or an app is missing from INSTALLED_APPS. Check both folders for 0001_initial.py, and compare INSTALLED_APPS with Chapter 17’s listing. Never rename a generated migration, or edit its dependencies, to make it fit: other migrations refer to it by name.

Step 4: Preview before applying

Two commands show what migrate would do, without changing the database. sqlmigrate prints the SQL one migration would run on this database. Run it for the events app:

Terminal

uv run python manage.py sqlmigrate events 0001

Expected result, with the long line shortened:

Output

BEGIN;
--
-- Create model Event
--
CREATE TABLE "events_event" ("id" integer NOT NULL ...
COMMIT;

BEGIN; and COMMIT; are the transaction from What You Need to Know: the whole migration takes effect, or none of it does. On your screen, the CREATE TABLE line continues with one column for each field. Near its end, the capacity column carries CHECK ("capacity" >= 0): the database rule behind PositiveIntegerField, which Chapter 16 predicted. The app label is events, plural; sqlmigrate event 0001 stops with CommandError: No installed app with label 'event'.

Run the same command for accounts 0001. It prints three CREATE TABLE statements: accounts_user, with "email" varchar(254) NOT NULL UNIQUE, and two link tables, accounts_user_groups and accounts_user_user_permissions, which hold the many-to-many links, followed by CREATE INDEX statements that make those links fast to look up.

migrate --plan lists every migration migrate would apply, in order, with its operations:

Terminal

uv run python manage.py migrate --plan

Expected result, shortened with ...:

Output

    Create model ContentType
...
auth.0001_initial
    Create model Permission
    Create model Group
    Create model User
...

Common Error: a migration that fails

If migrate stops with an error, read the last line of the message and fix its cause; do not delete db.sqlite3 or any migration file. On SQLite, the failed migration was rolled back and the ones before it stay recorded, so running migrate again after the fix is safe: it skips what is applied and retries the rest. That advice holds for SQLite and PostgreSQL. On a database without transactional schema changes, check the failed migration and the database state before retrying; Chapter 64 covers recovery on a live system.

Step 6: Create a superuser and commit

A superuser is an account with is_staff and is_superuser set: Django treats it as holding every permission, and its admin site, in Chapter 23, lets it change everything. Create one for your own computer. The command asks for the fields USERNAME_FIELD and REQUIRED_FIELDS name, then a password twice; the password is not shown as you type. Use the fictional address below and a password of your own that you have not used anywhere else. Never write it in a file. Beside manage.py, in PowerShell, Git Bash, a macOS shell, or Linux/WSL Bash:

Terminal

Output

Email address: sam@example.org
Display name: Sam

Password (again):

The prompts come from Chapter 17’s model: Email address from USERNAME_FIELD and the field’s name, Display name from REQUIRED_FIELDS. The command then calls the manager’s create_superuser(), so the email is normalized and the password hashed as Step 2’s tests require.

The command also checks your answers before saving. Each refusal asks again, so you can carry on in the same run:

  • Error: That email address is already taken. The account exists already, perhaps from an earlier attempt; keep it, and press Ctrl+C to stop, or enter a different address.
  • Error: This field cannot be blank. The display name was left empty.
  • Error: Your passwords didn't match. Type the same password twice.
  • This password is too common., followed by Bypass password validation and create user anyway? [y/N]:. Answer N, then choose a stronger password. These checks are the password validators listed in config/settings.py, which Chapter 29 reviews.

Common Error: Superuser creation skipped

createsuperuser needs a terminal to read the password from. If its input is not a terminal, it prints Superuser creation skipped due to not running in a TTY. and creates nothing. In this book’s checks, Git for Windows 2.51 gave the command a terminal in Git Bash; an older Git Bash window may not. If you see the message there, run the same command in PowerShell, or start it with winpty, a helper that ships with Git for Windows: winpty uv run python manage.py createsuperuser.

For scripts, such as an automated check, the command also has a form that asks nothing: --noinput reads the email, display name, and password from environment variables named DJANGO_SUPERUSER_EMAIL, DJANGO_SUPERUSER_DISPLAY_NAME, and DJANGO_SUPERUSER_PASSWORD. This book’s verification uses that form; you do not need it.

The file has a dependencies list naming 0002_event_slug and an empty operations list. This is the one migration you write yourself, so replace its whole contents, header line included, with this:

events/migrations/0003_fill_slugs.py (lab)

from django.db import migrations
from django.utils.text import slugify


def fill_slugs(apps, schema_editor):
    """Give every event a slug from its title and number."""
    Event = apps.get_model('events', 'Event')
    for event in Event.objects.all():
        event.slug = f'{slugify(event.title)}-{event.pk}'
        event.save(update_fields=['slug'])


def clear_slugs(apps, schema_editor):
    """Undo fill_slugs(): empty every slug."""
    Event = apps.get_model('events', 'Event')
    Event.objects.update(slug=None)


class Migration(migrations.Migration):

    dependencies = [
        ('events', '0002_event_slug'),
    ]

    operations = [
        migrations.RunPython(fill_slugs, clear_slugs),
    ]

RunPython takes the forward function and the reverse function. Both receive apps, the historical models, and schema_editor, which these functions do not need. apps.get_model('events', 'Event') returns the Event model as it stands after 0002: with a nullable slug, and without the model’s own __str__(). slugify(), from Django’s text utilities, turns Python meetup into python-meetup, and adding the id makes each value distinct, even for the two meetups. save(update_fields=['slug']) writes only that column. Event.objects.update(slug=None) changes every row in one statement; the reverse code puts the rows back as 0002 left them. As before, the queries are previews of Chapter 19.

Common Error: importing the model in a migration

Writing from events.models import Event in a migration works on the day you write it, because the model and the table match. Later, when the model gains a field that a later migration adds, the import gives the newest model, and this older migration fails on a column that does not exist yet at its point in the history. Always use apps.get_model() inside RunPython.

Migration 0004: require a value and make it unique. Replace the slug line in the lab’s events/models.py, removing null=True and adding unique=True in one edit:

events/models.py (lab only, after title)

    slug = models.SlugField(max_length=200, unique=True)

Option 2 tells Django that the existing rows are handled elsewhere, “with a RunPython or RunSQL operation”, as the full line says, and that is true: 0003 gives every row a slug before 0004 runs. Option 1 would ask for one value to put into every row still empty, which is the wrong tool for a unique column: one shared value is exactly what unique=True forbids. ~ marks an operation that changes something: the new file holds one AlterField, which makes the column required and unique.

Common Error: adding a unique, required field in one step

Skipping 0002 and 0003, and adding the final, unique field line straight away, makes makemigrations ask for a one-off default. Whatever you give it, every existing row receives the same value, and migrate stops with an IntegrityError that reports a failed UNIQUE constraint on the slug column. The failed migration is rolled back: showmigrations shows it unapplied, and the three rows are untouched. Fix it by removing that migration file, which no database has applied, and following the three steps. This was observed in a second, separate lab copy; you need not try it.

Optional: a migration with no way back. To see why the reverse function matters, change the operation in 0003_fill_slugs.py to migrations.RunPython(fill_slugs), leaving out clear_slugs, and run uv run python manage.py migrate events 0001. Django unapplies 0004, then stops at 0003 with a traceback whose last line is an IrreversibleError, saying that this migration’s operation is not reversible. Run showmigrations events: 0002 and 0003 are still applied, and 0004 is not. The run stopped between two migrations, exactly as the transaction rule says. Put clear_slugs back, then run migrate events to return to the latest state. When a data migration truly has nothing to undo, pass migrations.RunPython.noop as the reverse function, so that it can still be unapplied.
