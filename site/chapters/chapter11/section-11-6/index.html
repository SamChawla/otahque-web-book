Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 and L2 check what you have just learned. L3 asks how to test it. L4 and L5 look ahead to a larger application’s design and evidence: attempt them now, and return to them when you reach those chapters. They are extension questions, not a gate to the next chapter. Run each code proof beside manage.py, in PowerShell, a macOS shell, or Linux/WSL Bash.

L1 (Junior): What does a template do?

What the interviewer is testing: Can you distinguish structure from the values supplied by a view?

Flip to check your answerFold answer back

Perfect answer: A template describes the output structure and holds variables and instructions. A view chooses the data and passes it as context, and the template engine combines the two into a response. Keeping them apart means a page’s structure can change without touching the view’s decisions. A template sees only what it is given: a view’s local variables reach it only through the context.

Behind the scenes:

django/shortcuts.py (summary, not the source)

# render(request, name, context):
#     html = loader.render_to_string(name, context, request)
#     return HttpResponse(html)

Code proof: render the detail template directly, then print its heading line:

Terminal

uv run python manage.py shell -c "
from django.template.loader import render_to_string
page = render_to_string(
    'events/detail.html', {'title': 'Python meetup'}
)
print([x.strip() for x in page.splitlines() if 'h1' in x])
"

Output

12 objects imported automatically (use -v 2 for details).

['<h1>Sample: Python meetup</h1>']

Common mistakes:

  • Calling the context an HTML page.
  • Assuming a template can read a view’s local variables.
  • Putting decisions in the template that belong in the view.

Follow-up the interviewer might ask:

  • “Can a context contain a list?”
  • “What does a template show for a name the context lacks?”

L2 (Mid-Level): How does Django find an app template?

What the interviewer is testing: Can you trace a template name to the configured loader and file?

Flip to check your answerFold answer back

Perfect answer: Our settings use the Django template backend with APP_DIRS set to True, so the engine searches the templates folder of each installed app, in INSTALLED_APPS order, and uses the first match. The name events/list.html therefore points to events/templates/events/list.html. The repeated folder is a namespace: templates from every app share one search, so another app’s list.html could otherwise be found instead of ours, with no error to warn us.

Behind the scenes:

django/template/loaders/app_directories.py (summary)

# Loader.get_dirs(): the templates folder of each installed
#     app, in order. get_template(name) tries each folder in
#     turn, and raises TemplateDoesNotExist if none has it.

Code proof: ask the engine which file a name leads to:

Terminal

uv run python manage.py shell -c "
from pathlib import Path
from django.conf import settings
from django.template.loader import get_template
origin = get_template('events/list.html').origin
print(origin.template_name)
path = Path(origin.name).relative_to(settings.BASE_DIR)
print(path.as_posix())
"

Output

12 objects imported automatically (use -v 2 for details).

events/list.html
events/templates/events/list.html

Common mistakes:

  • Leaving out the inner app-named folder.
  • Forgetting that the app must be in INSTALLED_APPS.
  • Assuming every project’s loader configuration is the same.

Follow-up the interviewer might ask:

  • “What happens if two apps both provide events/list.html?”
  • “When would a project-level template folder be useful?”

L3 (Senior): How would you test an empty list?

What the interviewer is testing: Can you control inputs and check observable output without permanently changing the project?

Flip to check your answerFold answer back

Perfect answer: Supply an empty collection in an isolated test, request the page, and assert that the empty-state message appears. Then make sure the sample state is restored, even if the test fails, so that other tests are not affected by the order they run in. patch.dict used as a context manager does all of that for us. A 200 status alone would prove little here, because a blank page also returns 200, so the assertion must be on the message itself.

Behind the scenes:

unittest/mock.py (summary, not the source)

# patch.dict(target, values, clear=True): on entering, copy
#     target, then empty and fill it. On leaving, even after
#     an exception, restore the copy.

Code proof: run only that test by name:

Terminal

uv run python manage.py test events -k test_empty_list

Output

Found 1 test(s).
System check identified no issues (0 silenced).
...
Ran 1 test in ...

OK

Common mistakes:

  • Deleting real data to simulate an empty state.
  • Checking only a 200 status.
  • Leaving shared state changed, so that a later test fails for no visible reason.

Follow-up the interviewer might ask:

  • “Does this test a database query?”
  • “How would this test change once events are stored?”

L4 (Staff): What are the limits of HTML autoescaping?

What the interviewer is testing: Can you reason about untrusted data and output contexts?

Flip to check your answerFold answer back

Perfect answer: Ordinary template variables are HTML-escaped by default, which stops a value from becoming markup in HTML text. That protection can be switched off by safe and by disabling autoescaping, so those need review wherever they appear. It is also limited to what it does. Escaping changes < and &, not the meaning of a value, so a javascript: address passes through untouched, and a link built from it can still run code. So a URL must be validated for its purpose, and data for JavaScript or CSS needs handling suited to that context. I would keep autoescaping on, restrict safe by code review, and test the contexts we actually use.

Behind the scenes:

django/template/base.py (summary, not the source)

# render_value_in_context(value, context):
#     if context.autoescape and value is not marked safe:
#         return conditional_escape(value)
#     return value

Code proof: the same engine, three values:

Terminal

uv run python manage.py shell -c "
from django.template import Context, Template
def show(source, value):
    context = Context({'value': value})
    print(Template(source).render(context))
show('{{ value }}', '<b>Sample</b>')
show('{{ value|safe }}', '<b>Sample</b>')
show('{{ value }}', 'javascript:alert(1)')
"

Output

12 objects imported automatically (use -v 2 for details).

&lt;b&gt;Sample&lt;/b&gt;
<b>Sample</b>
javascript:alert(1)

Common mistakes:

  • Applying safe to untrusted input.
  • Claiming one escaping rule secures every context.
  • Treating an escaped value as validated.

Follow-up the interviewer might ask:

  • “What else would you do for a link that members can supply?”
  • “How would you find every use of safe in a large project?”

L5 (Lead): What does an escaping test prove?

What the interviewer is testing: Can you explain the strength and boundary of the evidence?

Flip to check your answerFold answer back

Perfect answer: It proves that this value is escaped on this rendering path, in these two templates. It guards against a specific regression, such as someone adding safe to the title. It does not prove that every future template, data source, browser, or output context is safe, and it is not a security certification. So I would report it in exactly those terms, keep it as a regression test, and revisit the risk when real user data arrives, because that is when the threat changes. A reviewer should be able to see both what was tested and what was not.

Behind the scenes:

events/tests.py (summary, not the source)

# assertContains(response, '&lt;strong&gt;'): the escaped
#     form is in the response.
# assertNotContains(response, '<strong>Not a tag'): the raw
#     form is not. Each alone would prove less.

Code proof: run only the two escaping tests:

Terminal

uv run python manage.py test events -k escapes

Output

Found 2 test(s).
System check identified no issues (0 silenced).
...
Ran 2 tests in ...

OK

Common mistakes:

  • Treating one test as a security certification.
  • Testing only a successful status, not the rendered content.
  • Checking for the escaped form without also checking that the raw form is absent.

Follow-up the interviewer might ask:

  • “What changes when data comes from users?”
  • “Which change to the template would make this test fail?”
