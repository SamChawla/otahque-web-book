What You Need to Know

Cookies and sessions

HTTP forgets. Each request arrives on its own, and nothing in it says that the same person sent the one before. A cookie fixes that from the browser’s side: the server’s answer says Set-Cookie: name=value, with some rules attached, and the browser sends name=value back with every later request to that site until the cookie expires.

A cookie can hold the data itself, but then the person can read it and change it, and a cookie holds only about four thousand characters. So Django keeps a session instead: a row in the django_session table holding the data, and a cookie named sessionid holding only the row’s key, 32 random characters. The browser sees the key; the data stays on the server. Signing in, from Chapter 27, is the first thing Otahque keeps there.

Three rules on a cookie matter in this chapter. HttpOnly hides it from the page’s scripts, so a script injected into a page cannot steal it. SameSite=Lax keeps the browser from sending it with a form posted from another site, while still sending it when a person follows a link to Otahque. Max-Age says how long it lives; without one, the cookie is deleted when the browser closes. Table 28.1 lists the cookies Otahque uses by the end of the chapter.

Two weeks is Django’s default, SESSION_COOKIE_AGE, counted from the last time the session changed. Chapter 27’s sign-in page has a Remember me box: a member who leaves it clear gets a sessionid cookie with no Max-Age, which ends when the browser closes. Otahque keeps Django’s defaults, and Step 2 turns them into tests, so that any later change to them is deliberate.

Messages: stored for one request

Chapter 24’s New event page saves the draft, adds “Draft saved.”, and redirects to the event page, which shows the message. The redirect is a second request. The view that added the message has finished before the page that shows it starts, so Django has to keep the message somewhere in between.

That somewhere is Django’s messages framework. By default it stores waiting messages in a cookie named messages, falling back to the session for any that do not fit in it. The cookie is signed, so a person cannot add a message of their own. When the layout’s {% for message in messages %} loop runs, the messages are marked as used, and at the end of that request Django deletes the cookie. Figure 28.1 follows “Draft saved.” through the two requests.

So a message is already “dismissed” on the server once it has been shown. Raj’s close button only needs to hide it on the page in front of him, which is a job for a few lines of JavaScript. Each message has a level, such as success or error, and Otahque’s layout styles them differently.

What belongs in a session

A session is the right place for something small that the person can afford to lose: who is signed in, a filter, a step in a form. It is lost when the person signs out, when it expires, or when they switch browser. Everything else, such as events, registrations, and profiles, belongs in the database, where it is shared, kept, and checked by Chapter 21’s rules. Figure 28.2 sorts what Otahque keeps.

Raj’s filter is a display preference: it changes what the list shows him, never what is true. The view reads it from the session and asks the database for the events on every request, so a place cancelled a minute ago brings a full event straight back. Saving to the session also creates a row and sets a cookie, so the view saves the filter only when Raj changes it. A visitor who merely opens the list gets no session at all.

New Concept: a GET that remembers

What problem exists? Chapter 26’s rule says a GET must not change anything. Raj’s filter arrives as /events/?places=1, a GET, and is saved in his session.

What did people do before? Some sites send a filter as a POST with a CSRF token, so it cannot be bookmarked or shared, and the Back button asks to resend a form.

What is it? The rule protects the community’s data. A display preference changes only how this one browser sees the list, and the address shows the choice, so a GET is the right method: it can be bookmarked, shared, and repeated safely.

Why use it? The worst a link from another site can do is tick Raj’s filter. Nothing about events or registrations can change this way, and Step 4’s tests prove it.

Now let’s use it. Step 4 saves the choice when places is in the address, and nothing otherwise.

A time zone for every request

Chapter 24 stores every time in UTC and shows each event in its own zone. Django can also show times in the viewer’s zone. It keeps a current time zone for each request, set with timezone.activate(), and templates and forms use it. Until now, Otahque never set one, so the current zone was always TIME_ZONE = 'UTC'.

Django cannot find out the viewer’s zone by itself: Django’s documentation notes that no request header carries it. Otahque decided on 13 November 2026 to take it from three places, in order: the member’s profile, which Chapter 27 added; the browser, through a cookie; and UTC. The browser knows its zone, and one line of JavaScript, Intl.DateTimeFormat().resolvedOptions().timeZone, returns it, for example Asia/Kolkata. Otahque’s script writes it into a cookie named otahque_tz, and the server reads it on the next request.

New Concept: a cookie the browser wrote

What problem exists? otahque_tz comes from the browser, so anyone can set it to anything, such as Mars/Base or ../../etc/passwd.

What did people do before? Code that trusted such a value passed it straight to the zone library, which raises an error for an unknown name, or reads a file path it should not.

What is it? A value the browser writes is untrusted input, like a form field. The server accepts it only if it is in the list of real zone names, and uses UTC for anything else.

Why use it? A false zone then changes nothing but the times shown to the person who set it. It cannot reach anyone else’s pages or any stored time.

Now let’s use it. Step 6 checks the cookie against available_timezones(), and its tests send the odd values above.

A piece of middleware, code Django runs around every request, finds the zone and activates it. Django’s own documentation shows one that reads the zone from the session; Otahque reads a cookie instead, so a visitor who is not signed in gets no session, and the zone survives signing out. The middleware must run after Django’s AuthenticationMiddleware, because it reads request.user, and it skips the admin, which keeps Chapter 23’s UTC. Figure 28.3 shows the order.

The current zone also changes how forms read typed times, and that matters for Chapter 24’s event form. A DateTimeField first reads “2027-03-14 02:30” in the current zone, and refuses a time that does not exist there, or exists twice. Only then does Chapter 24’s in_zone() read the same clock time in the event’s zone. With New York as Sai’s current zone, the first stage refuses a time that is perfectly good in Delhi. So Otahque’s event forms check their fields under UTC, which has no clock changes, and leave the real check to in_zone(), as Figure 28.4 shows.

On public pages, Otahque shows the venue’s time first and, when the viewer’s clock says something different, the viewer’s too. “Different” means a different offset from UTC at that moment, not a different name: Asia/Calcutta, the old name some browsers still report, and Asia/Kolkata show the same clock, while London and UTC agree in winter and differ in summer.

Signed is not encrypted

Chapter 8 said the secret key “signs” values, so that a change can be detected, and promised to show it with sessions. The messages cookie is such a value. Django’s django.core.signing makes one from any data: the data, written in a form called base64, then a time, then a signature worked out from the data and SECRET_KEY. Anyone can decode the data, because it is not encrypted, but nobody without the key can change it and produce a matching signature. Django’s sessions documentation says the same of its cookie-based sessions: “signed but not encrypted”.

Three more properties follow. A salt separates uses, so a value signed for one purpose fails for another. A TimestampSigner refuses a value older than a max_age you choose. And a signed value works until it expires, however many times it is used, which is called replay; nothing records that it was used. To change the secret key without breaking every signed value at once, put the old key in SECRET_KEY_FALLBACKS: Django checks with it, but never signs with it.

A token is any value a program sends to prove who it is. A JWT, a JSON Web Token, is a signed value of this kind, often recommended in tutorials for signing in. Figure 28.5 compares the three options. Otahque’s own pages come from Otahque’s own site, so a session cookie, with HttpOnly, SameSite, and CSRF protection, is simpler and easier to end; a token is chosen only when a named program outside the site needs one, in Chapter 50.
