Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead: attempt them now, and return after Chapters 29 and 50. They are extension questions, not a gate to the next chapter.

L1 (Junior): What is the difference between a cookie and a session?

What the interviewer is testing: Do you know which side holds what, and why that matters for safety?

Flip to check your answerFold answer back

Perfect answer: A cookie is a value the browser keeps and sends back with every request to the site, so the person can read it and change it. A session is data the server keeps for one browser; the browser holds only a cookie with the session’s random key. Django stores sessions in the database by default and marks the cookie HttpOnly and SameSite=Lax. So a session suits data the person must not change, such as who is signed in, and the server can end it at any time by deleting the row.

Behind the scenes:

one visit with the filter (summary)

GET /events/?places=1  -> session row saved: places_only
answer                 -> Set-Cookie: sessionid=<key>
next request           -> sessionid sent; row read again

Code proof: a visitor ticks the filter; what each side holds, rolled back afterwards:

l1_session.py (practice file; delete it afterwards)

from django.contrib.sessions.models import Session
from django.db import transaction
from django.test import Client
from django.test.utils import setup_test_environment

setup_test_environment()
with transaction.atomic():
    web = Client()
    web.get('/events/?places=1')
    print('browser holds:', sorted(web.cookies))
    key = web.cookies['sessionid'].value
    row = Session.objects.get(session_key=key)
    print('server holds:', row.get_decoded())
    transaction.set_rollback(True)

Output

browser holds: ['sessionid']
server holds: {'places_only': True}

Common mistakes:

  • Thinking the session’s data is in the cookie.
  • Storing data in a plain cookie that the person could change.
  • Forgetting that every saved session is a database row.

Follow-up the interviewer might ask:

  • “When would you store sessions in the cache instead of the database?”
  • “What does HttpOnly protect against, and what does it not?”

L2 (Mid-Level): Sam saves his profile, then reloads the page. Predict what each page shows.

What the interviewer is testing: Can you trace a message across a redirect and say why it appears once?

Flip to check your answerFold answer back

Perfect answer: The page after the redirect shows “Profile saved.”; the reload shows no message. The view adds the message and answers with a redirect, so Django stores it in the signed messages cookie. The next request sends the cookie back, the layout’s loop shows the message and marks it used, and Django deletes the cookie with that response. The reload has nothing to show.

Behind the scenes:

a message across two requests (summary)

POST /accounts/profile/  -> 302; Set-Cookie: messages=...
GET  /accounts/profile/  -> shown; cookie deleted
GET  (reload)            -> no message

Code proof: the Mini-Challenge’s l2_messages.py:

Output

waiting in a cookie: True
first page: True
after a reload: False

Common mistakes:

  • Rendering the page after a POST instead of redirecting, so a reload sends the form again.
  • Leaving out the messages loop on a page, so a message waits and appears on a later one.
  • Storing a message in the session by hand and never deleting it.

Follow-up the interviewer might ask:

  • “Where would a message go if it were too large for the cookie?”
  • “How would you show a message that must stay until the member reads it?”

L3 (Senior): Defend reading registrations from the database, never from the session.

What the interviewer is testing: Can you say what may be lost, what must be true, and prove the boundary with a test?

Flip to check your answerFold answer back

Perfect answer: A session belongs to one browser and may be lost at any time: at sign-out, at expiry, or on another device. Registrations are shared and must be true for everyone, with Chapter 21’s rules checking them. If a page trusted a copy in the session, a place cancelled by someone else would not show, and a lost session would hide a member’s place. So the session keeps only Raj’s choice to filter; the database counts places on every request. The test cancels a place behind the session’s back, and the full event reappears in the filtered list.

Behind the scenes:

a filtered list after a cancellation (summary)

session      -> places_only = True
database     -> workshop full, then a place cancelled
next request -> places counted again; workshop shown

Code proof: the Step 4 test test_places_are_read_from_the_database, run on its own:

Output

Found 1 test(s).
Creating test database for alias 'default'...
...
Ran 1 test in ...s

OK
Destroying test database for alias 'default'...

Common mistakes:

  • Caching a member’s registrations in the session to save a query.
  • Treating a value in the session as checked because the person cannot edit it.
  • Testing only the happy path, never a change made by someone else.

Follow-up the interviewer might ask:

  • “When would caching places be acceptable, and how would you keep it correct?”
  • “What belongs in a session in a multi-step form?”

L4 (Staff): Sai’s 02:30 Delhi event is refused with a message naming America/New_York. Diagnose.

What the interviewer is testing: Can you trace a refusal to the stage that made it, and fix the cause rather than the symptom?

Flip to check your answerFold answer back

Perfect answer: The message names New York, not Delhi, so it is not Otahque’s in_zone() check; it is Django’s DateTimeField, which reads typed text in the current zone. Since the middleware activates each viewer’s zone, Sai’s form is read in New York first, where 02:30 on 14 March 2027 is skipped by the clock change. The fix is not to switch the middleware off: clean the form under UTC, which has no clock changes, and let in_zone() read the time in the event’s zone. A test with New York active proves it, beside one showing that London still refuses its own missing hour.

Behind the scenes:

one typed time, two readings (summary)

field, in New York  -> 02:30 does not exist: refused
field, under UTC    -> accepted as text
in_zone(), Delhi    -> 02:30 IST = 21:00 UTC, saved

Code proof: a plain field and EventForm, with New York active:

l4_zone.py (practice file; run it like l2_messages.py)

from zoneinfo import ZoneInfo

from django import forms
from django.utils import timezone

from events.forms import EventForm


class Typed(forms.Form):
    starts_at = forms.DateTimeField()


delhi = {'title': 'Delhi clinic', 'location': 'Online',
         'timezone': 'Asia/Kolkata', 'capacity': '20',
         'starts_at': '2027-03-14T02:30',
         'ends_at': '2027-03-14T04:00'}
with timezone.override(ZoneInfo('America/New_York')):
    plain = Typed({'starts_at': delhi['starts_at']})
    print('a plain field:', plain.is_valid())
    print(plain.errors['starts_at'][0])
    print('EventForm:', EventForm(delhi).is_valid())

Output

a plain field: False
2027-03-14 02:30:00 couldn’t be interpreted in time zone
    America/New_York; it may be ambiguous or it may not
    exist.
EventForm: True

Common mistakes:

  • Turning the middleware off for every form page.
  • Reading times under the event’s zone, so the same gap is checked twice.
  • Testing forms only with the default zone, UTC, which never shows the fault.

Follow-up the interviewer might ask:

  • “Which other forms in a project would be affected by activating a zone?”
  • “How would you show a member a time that falls in their own clock change?”

L5 (Lead): A developer proposes JWTs instead of sessions for Otahque’s pages. What do you advise?

What the interviewer is testing: Can you compare the two on what matters, ending a sign-in, theft, and effort, and keep a decision open for the right case?

Flip to check your answerFold answer back

Perfect answer: Keep sessions for Otahque’s own pages. A JWT is a signed value: anyone holding it can read it, and it works until it expires, so signing out, a password change, or a stolen token cannot end it without a list of withdrawn tokens kept on the server, which is a session again in another form. A session cookie is HttpOnly, so page scripts cannot read it, the server ends it by deleting the row, and Django already pairs it with CSRF protection. The pages and the server share one site, so nothing needs a token. When a named outside client appears, such as a mobile app, choose its authentication then, in Chapter 50.

Behind the scenes:

after sign-out (summary)

session        -> row deleted: the key is worthless
signed token   -> still valid until it expires
stored token   -> valid until its row is deleted

Code proof: a session and a signed token, after the same sign-out:

l5_tokens.py (practice file; run it like l2_messages.py)

from django.contrib.sessions.backends.db import SessionStore
from django.core import signing

session = SessionStore()
session['member'] = 7
session.save()
key = session.session_key
token = signing.dumps({'member': 7}, salt='otahque.demo')

session.flush()  # what signing out does
print('session after sign-out:',
      dict(SessionStore(session_key=key).items()))
print('signed token after sign-out:',
      signing.loads(token, salt='otahque.demo'))

Output

session after sign-out: {}
signed token after sign-out: {'member': 7}

Common mistakes:

  • Choosing JWTs because they are “stateless”, then adding a list of withdrawn tokens.
  • Keeping a token where page scripts can read it.
  • Deciding the API’s authentication before there is an API client.

Follow-up the interviewer might ask:

  • “What would change for a mobile app that uses the same accounts?”
  • “How does Chapter 46’s check-in token differ from a signed value?”
