Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 and L2 check what you have just learned. L3 asks how it works underneath. L4 and L5 look ahead to decisions a larger application must make: attempt them now, and return to them when you reach those chapters. They are extension questions, not a gate to the next chapter. Run each code proof beside manage.py, in PowerShell, a macOS shell, or Linux/WSL Bash.

L1 (Junior): What does a function-based view do?

What the interviewer is testing: Can you describe the request and response contract in plain language?

Flip to check your answerFold answer back

Perfect answer: Django calls the view with a request object, plus any values captured from the path. The view makes a decision and either returns a response object or raises an exception that Django handles, such as Http404. It does not print to the browser, and it does not return bare text: printing goes to the server’s terminal, and only the returned response travels back to the browser.

Behind the scenes:

django/core/handlers/base.py (summary, not the source)

# BaseHandler._get_response(request):
#     match = resolver.resolve(request.path_info)
#     response = view(request, *args, **kwargs)
#     if response is None: raise ValueError(...)

Code proof: call the view directly with a built request:

Terminal

uv run python manage.py shell -c "
from django.test import RequestFactory
from events.views import event_detail
request = RequestFactory().get('/events/1/')
response = event_detail(request, 1)
print(response.status_code, response['Content-Type'])
print(response.content)
"

Output

12 objects imported automatically (use -v 2 for details).

200 text/plain
b'Sample: Python meetup'

Common mistakes:

  • Confusing server terminal output with an HTTP response.
  • Returning a bare string.
  • Assuming every view returns HTML; ours returns plain text.

Follow-up the interviewer might ask:

  • “What happens if a view forgets to return anything?”
  • “Why is a view easy to test without a server?”

L2 (Mid-Level): How does the event ID reach the view?

What the interviewer is testing: Can you follow a captured URL value into Python?

Flip to check your answerFold answer back

Perfect answer: The route events/<int:event_id>/ has a named integer converter. It matches digits in that part of the path and converts them, and Django passes the value to the view as the keyword argument event_id. So the name in the route must match the view’s parameter, and the view receives an integer rather than text. The converter checks only the shape of the value: 999 passes it, even though no such sample exists, and abc fails it, so that path matches no route.

Behind the scenes:

django/urls/converters.py (summary, not the source)

# class IntConverter:
#     regex = '[0-9]+'
#     def to_python(self, value): return int(value)

Code proof: resolve a path and read what the view will receive:

Terminal

uv run python manage.py shell -c "
from django.urls import resolve
match = resolve('/events/1/')
print(match.func.__name__, match.kwargs)
print(type(match.kwargs['event_id']).__name__)
"

Output

12 objects imported automatically (use -v 2 for details).

event_detail {'event_id': 1}
int

Common mistakes:

  • Assuming the converter finds a stored record.
  • Using a different parameter name in the view.
  • Treating the integer as trusted because it was converted; it still came from the request.

Follow-up the interviewer might ask:

  • “What happens to letters in place of the ID?”
  • “What would you use for an address built from an event’s short name?”

L3 (Senior): Why can two different problems both return 404?

What the interviewer is testing: Can you distinguish URL resolution from a missing resource?

Flip to check your answerFold answer back

Perfect answer: A path can fail to match any route, so Django raises Resolver404 and no view runs. Or a path can match a route whose view then raises Http404, because the resource it was asked for is missing. A visitor sees the same status in both cases, and that is the right answer for both, but the causes live in different places. So a developer asks whether a view ran. Returning a 200 page containing the words “not found” would be worse than either, because browsers, search engines, and tests would all take it for success.

Behind the scenes:

django/urls/exceptions.py (summary, not the source)

# class Resolver404(Http404): raised when no route matches.
# Because it is a kind of Http404, the handler turns
# both into the same 404 response.

Code proof: the two addresses from this chapter, one for each cause:

Terminal

uv run python manage.py shell -c "
from django.http import Http404
from django.test import RequestFactory
from django.urls import Resolver404, resolve
try:
    resolve('/events/abc/')
except Resolver404:
    print('abc: no route matched')
match = resolve('/events/999/')
try:
    match.func(RequestFactory().get('/'), **match.kwargs)
except Http404 as error:
    print('999:', match.view_name, 'raised', error)
"

Output

12 objects imported automatically (use -v 2 for details).

abc: no route matched
999: events:detail raised Sample event not found

Common mistakes:

  • Concluding that every 404 means the route is missing.
  • Returning a 200 response containing the words “not found”.
  • Testing a 404 without checking which view, if any, was selected.

Follow-up the interviewer might ask:

  • “How does test_missing_event show that its 404 came from the view?”
  • “Should a visitor be told which cause applied?”

L4 (Staff): How would you prevent unsafe HTML output?

What the interviewer is testing: Can you separate this controlled example from untrusted data in a real application?

Flip to check your answerFold answer back

Perfect answer: First identify which values come from untrusted sources, and where each is written. HttpResponse writes exactly what it is given and labels it HTML by default, so joining untrusted text into a response is how pages get hijacked. For HTML, I would render through Django templates, which escape ordinary values, and avoid marking untrusted content as safe. Validation is separate: it decides what a value may be, not how it is written out, and no single control covers every output context. Finally I would test hostile-looking input. Our sample avoids the problem only because its title is fixed and it is sent as plain text. Chapter 11 takes up templates.

Behind the scenes:

django/utils/html.py (summary, not the source)

# escape(text): replace & < > " and ' with HTML entities,
#     so a browser shows those characters as text.
# HttpResponse(content) applies no escaping at all.

Code proof: the same harmless title, written out directly and then escaped:

Terminal

uv run python manage.py shell -c "
from django.http import HttpResponse
from django.utils.html import escape
title = '<b>Sample</b>'
print(HttpResponse(title).content)
print(escape(title))
"

Output

12 objects imported automatically (use -v 2 for details).

b'<b>Sample</b>'
&lt;b&gt;Sample&lt;/b&gt;

Common mistakes:

  • Assuming that a plain-text example proves arbitrary HTML is safe.
  • Treating validation as a replacement for escaping suited to the output.
  • Building HTML by joining strings in a view.

Follow-up the interviewer might ask:

  • “Where will Otahque render HTML?”
  • “Which values would you treat as untrusted once members can edit events?”

L5 (Lead): What does this checkpoint actually prove?

What the interviewer is testing: Can you state evidence and its limits without overstating readiness?

Flip to check your answerFold answer back

Perfect answer: It proves that these local routes and this fixed sample behave as stated, under the tested conditions, on the platforms we ran. It says nothing about stored events, access rules, production deployment, accessibility, or other browsers, and a report that claimed those would mislead whoever plans the next step. So I would report the check, the result, and the gaps together, and name who decides whether the gaps matter yet. Listing what the tests actually cover is often the quickest way to show the boundary.

Behind the scenes:

django/test/runner.py (summary, not the source)

# The runner collects test methods and reports each result.
# It knows nothing about behaviour that no test asserts:
# anything unasserted is simply absent from the report.

Code proof: list every test the project has, which is also the list of what it claims:

Terminal

uv run python manage.py shell -c "
import unittest
tests = unittest.defaultTestLoader.loadTestsFromName(
    'events.tests'
)
for group in tests:
    for test in group:
        print(test.id().removeprefix('events.tests.'))
"

Output

12 objects imported automatically (use -v 2 for details).

EventDetailTests.test_invalid_id
EventDetailTests.test_missing_event
EventDetailTests.test_sample_event
RoutingTests.test_event_list
RoutingTests.test_home
RoutingTests.test_unknown_path

Nothing here mentions a database, a permission, or a browser, and that absence is part of the evidence.

Common mistakes:

  • Calling a sample dictionary a database.
  • Treating a passing test as proof of the whole product.
  • Reporting a pass without saying what was not checked.

Follow-up the interviewer might ask:

  • “What would you check next, and why that first?”
  • “Who should decide that a known gap is acceptable?”
