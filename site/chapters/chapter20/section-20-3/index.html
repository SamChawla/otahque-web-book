How We Build It

Start from Chapter 19, in the folder containing manage.py, with your own .env, the locked environment, 30 passing tests, every migration applied, the local superuser from Chapter 18, and three events: two published and one draft. Step 2 creates a new app, registrations, and installs it in config/settings.py. Steps 3 to 5 write the tests first, then registrations/models.py, add a model to events/models.py, and create two migrations. Steps 6 and 7 work in the Django shell and add rows: two members, one organizer assignment, and three registrations. At the end of Step 8, 36 tests pass, every migration is applied, the public pages are unchanged, and the work is committed. The optional lab in Step 9 then adds event topics, a many-to-many field, in a disposable copy.

The Custom Way

This illustration reads related rows by hand from two small tables in memory, the way hand-written database code often did; do not add it to the project. set_trace_callback() is a sqlite3 feature that calls a function with each SQL statement the connection runs, so the list sent counts the queries:

illustration_only/related_rows.py (not part of the project)

import sqlite3

db = sqlite3.connect(':memory:')
db.executescript('''
    CREATE TABLE event (id INTEGER PRIMARY KEY, title TEXT);
    CREATE TABLE registration (
        id INTEGER PRIMARY KEY,
        event_id INTEGER NOT NULL REFERENCES event (id),
        member TEXT NOT NULL
    );
    INSERT INTO event VALUES (1, 'Python meetup'),
                             (2, 'Django workshop');
    INSERT INTO registration (event_id, member)
    VALUES (1, 'Sai'), (1, 'Raj'), (2, 'Sai');
''')
sent = []
db.set_trace_callback(sent.append)

listed = 'SELECT event_id, member FROM registration'
for event_id, member in db.execute(listed).fetchall():
    (title,) = db.execute(
        'SELECT title FROM event WHERE id = ?', (event_id,)
    ).fetchone()
    print(member, title)
print('queries:', len(sent))

sent.clear()
joined = '''
    SELECT registration.member, event.title
    FROM registration
    JOIN event ON event.id = registration.event_id
'''
for member, title in db.execute(joined):
    print(member, title)
print('queries:', len(sent))

Output

Sai Python meetup
Raj Python meetup
Sai Django workshop
queries: 4
Sai Python meetup
Raj Python meetup
Sai Django workshop
queries: 1

The first loop is the N+1 pattern, written out: one query for the registrations, then one for each row’s event. The JOIN asks once, and the database matches every registration to its event. Both print the same lines. Now list what the hand-written version still lacks: each row is a tuple to unpack by position, nothing turns event_id into an event object, the reverse question, “which registrations does this event have?”, needs another query written by hand, and nothing decides what happens when an event is deleted. Relationship fields give you all four.

Step 3: Write the tests first

The tests describe what both models must do before either exists. Replace the contents of registrations/tests.py, which holds only an import and a comment, with this:

registrations/tests.py

from datetime import UTC, datetime

from django.contrib.auth import get_user_model
from django.db.models import ProtectedError
from django.test import TestCase

from events.models import Event
from .models import Registration

User = get_user_model()


class RegistrationTests(TestCase):
    @classmethod
    def setUpTestData(cls):
        cls.event = Event.objects.create(
            title='Python meetup',
            starts_at=datetime(2026, 11, 19, 18, 30,
                               tzinfo=UTC),
            ends_at=datetime(2026, 11, 19, 20, 30,
                             tzinfo=UTC),
            timezone='Europe/London',
            location='Leeds Central Library',
            capacity=40,
        )
        cls.member = User.objects.create_user(
            'sai@example.org', display_name='Sai'
        )
        cls.registration = Registration.objects.create(
            event=cls.event, member=cls.member
        )

    def test_registration_links_event_and_member(self):
        registration = self.registration
        self.assertEqual(registration.event, self.event)
        self.assertEqual(registration.member, self.member)
        self.assertEqual(
            registration.status, Registration.Status.ACTIVE
        )
        self.assertQuerySetEqual(
            self.event.registrations.all(), [registration]
        )
        self.assertQuerySetEqual(
            self.member.registrations.all(), [registration]
        )

    def test_event_with_registration_is_kept(self):
        with self.assertRaises(ProtectedError):
            self.event.delete()
        self.assertTrue(
            Event.objects.filter(pk=self.event.pk).exists()
        )

    def test_member_with_registration_is_kept(self):
        with self.assertRaises(ProtectedError):
            self.member.delete()
        self.assertTrue(
            User.objects.filter(pk=self.member.pk).exists()
        )

get_user_model() returns the user class, as the Prefer callout advised for code like this. create_user() without a password gives Sai an account that cannot sign in yet, which is all a test needs. The first test checks both directions: the registration’s event and member, its default status, and the two reverse managers, event.registrations and member.registrations. assertQuerySetEqual() compares a QuerySet with a list, in order. The other two tests try to delete the event and the member, expect ProtectedError, and then check that each row is still there, so that a refused delete cannot pass by deleting something anyway.

events/tests.py (2 of 2: add at the end)

class OrganizerAssignmentTests(TestCase):
    @classmethod
    def setUpTestData(cls):
        cls.event = save_event()
        cls.member = User.objects.create_user(
            'sam@example.org', display_name='Sam'
        )
        cls.assignment = OrganizerAssignment.objects.create(
            event=cls.event, member=cls.member
        )

    def test_assignment_links_event_and_member(self):
        assignment = self.assignment
        self.assertEqual(assignment.event, self.event)
        self.assertEqual(assignment.member, self.member)
        self.assertIsNone(assignment.revoked_at)
        self.assertQuerySetEqual(
            self.event.organizer_assignments.all(),
            [assignment],
        )
        self.assertQuerySetEqual(
            self.member.organizer_assignments.all(),
            [assignment],
        )

    def test_assigned_event_and_member_are_kept(self):
        for row in (self.event, self.member):
            model = type(row)
            with self.subTest(model=model.__name__):
                with self.assertRaises(ProtectedError):
                    row.delete()
                kept = model.objects.filter(pk=row.pk)
                self.assertTrue(kept.exists())

    def test_unlinked_event_can_be_deleted(self):
        spare = save_event(title='Spare event')
        self.assertEqual(
            spare.delete(), (1, {'events.Event': 1})
        )

save_event() is Chapter 19’s helper, near the top of the same file. The test database is separate from yours, so sam@example.org here is a new, test-only member. In this class, the event and the member are linked only by the assignment, with no registration. That matters: if the event also had a registration, the registration’s PROTECT would refuse the delete on its own, and a wrong rule on the assignment would go unnoticed. type(row) is the row’s model, Event or User, so one loop checks both. The last test proves that the rule is “keep what history needs”, not “never delete”: an event that nothing points at can still be deleted, and delete() reports one Event.

Step 4: Write the two models

Replace the contents of registrations/models.py with this:

registrations/models.py

from django.conf import settings
from django.db import models
from django.utils import timezone


class Registration(models.Model):
    """A member's place in an event, from the ERD."""

    class Status(models.TextChoices):
        ACTIVE = 'active', 'Active'
        CANCELLED = 'cancelled', 'Cancelled'

    event = models.ForeignKey(
        'events.Event',
        on_delete=models.PROTECT,
        related_name='registrations',
    )
    member = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.PROTECT,
        related_name='registrations',
    )
    status = models.CharField(
        max_length=20,
        choices=Status,
        default=Status.ACTIVE,
    )
    registered_at = models.DateTimeField(
        default=timezone.now
    )
    cancelled_at = models.DateTimeField(
        null=True, blank=True
    )

    class Meta:
        ordering = ['registered_at']

    def __str__(self):
        return f'{self.member} at {self.event}'

Each part comes from the ERD or from an earlier chapter. The two foreign keys name their targets three ways you now know: 'events.Event' as a string, and the user model through the setting. related_name='registrations' on both is not a clash, because the names live on different models: Event gets registrations, and so does User. Status is a TextChoices class like the event’s, with active as the default. registered_at uses default=timezone.now, as Chapter 17’s date_joined does: the function itself, without brackets, so Django calls it for each new row. auto_now_add=True would also fill it, but would make the field impossible to set, which Chapter 41 needs when it imports registrations with their original times. cancelled_at may be empty, in Python as None and in the database as NULL, because a registration that has not been cancelled has no cancellation time; blank=True tells forms, from Chapter 24, that it is optional. Registrations are listed in the order they were made, and __str__() describes one for the shell and error messages.

class OrganizerAssignment(models.Model):
    """Which member organizes which event, from the ERD."""

    event = models.ForeignKey(
        Event,
        on_delete=models.PROTECT,
        related_name='organizer_assignments',
    )
    member = models.ForeignKey(
        settings.AUTH_USER_MODEL,
        on_delete=models.PROTECT,
        related_name='organizer_assignments',
    )
    assigned_at = models.DateTimeField(
        default=timezone.now
    )
    revoked_at = models.DateTimeField(
        null=True, blank=True
    )

    class Meta:
        ordering = ['assigned_at']

    def __str__(self):
        return f'{self.member} organizes {self.event}'

Event is named directly, because it is defined above in the same file. An assignment is current while revoked_at is empty; revoking one fills it in and keeps the row, the same idea as a cancelled registration. Who may assign and revoke organizers is Chapter 30’s question. Check the project:

Common Error: two reverse names that clash

If OrganizerAssignment.member also had related_name='registrations', User would be given two attributes with one name. check refuses with four messages, two for each field. The first begins events.OrganizerAssignment.member: (fields.E304) Reverse accessor 'User.registrations' for 'events.OrganizerAssignment.member' clashes with reverse accessor for 'registrations.Registration.member'. The others, fields.E305, say the same of the names used in lookups. Give each relationship to the same model its own related_name, as in the listings.

Two smaller mistakes stop the project before check can report anything. A foreign key without on_delete fails with TypeError: ForeignKey.__init__() missing 1 required positional argument: 'on_delete'. A model file that uses settings without importing it fails with NameError: name 'settings' is not defined. A misspelled string, such as 'event.Event', gives two check errors, fields.E300 and fields.E307, the second saying that app 'event' isn't installed. In each case, compare the file with the listing.

The meetup has two active registrations, so the join produces two meetup rows. distinct() asks the database for each event once. Use it whenever a filter across a reverse relationship could match several rows for one result.

This step is an experiment, like Chapter 18’s slug lab. Otahque’s first release has no topics, as Chapter 15’s ERD records, so you build them in a copy of the project and discard the copy afterwards. In the lab’s events/models.py, add a field to Event, directly after status:

events/models.py (lab only, in Event, after status)

    topics = models.ManyToManyField(
        'Topic', blank=True, related_name='events'
    )

Then add a model at the end of the file:

events/models.py (lab only, end of the file)

class Topic(models.Model):
    """A subject an event covers; lab only."""

    name = models.CharField(max_length=50, unique=True)

    class Meta:
        ordering = ['name']

    def __str__(self):
        return self.name

'Topic' is a string because the class is defined further down the file, the same lazy reference you used for 'events.Event'. blank=True lets an event have no topics; a many-to-many field never needs null=True, because it adds no column to the event table. related_name='events' names the reverse side, so a topic lists its events with python.events. There is no on_delete: you will see why at the end of the lab.

Python

<QuerySet [<Event: Python meetup>, <Event: Django sprint>]>

add() writes rows into the link table, one for each pair, and adding web a second time changes nothing, because the pair is already there. meetup.topics and python.events are related managers, like meetup.registrations, but here both sides are plural. Filters cross the link table with the double underscore, and repeat rows as reverse filters did in Step 6:

Python

>>> both = Event.objects.filter(
...     topics__name__in=['Python', 'Web']
... )
>>> [event.title for event in both]
['Python meetup', 'Django sprint', 'Django sprint']
>>> [event.title for event in both.distinct()]
['Python meetup', 'Django sprint']
>>> Event.topics.through
<class 'events.models.Event_topics'>
>>> Event.topics.through.objects.count()
3

The sprint matches both topics, so it appears twice until distinct(). through is the model Django made for the link table; it has no fields of its own beyond the two keys, which is exactly why a registration, with its status and times, could not be one. Reading each event’s topics in a loop is a query per row again, and prefetch_related() fixes it, as in Step 7:

Python

>>> from django.test.utils import CaptureQueriesContext
>>> with CaptureQueriesContext(connection) as queries:
...     events = Event.objects.prefetch_related('topics')
...     for e in events:
...         print(e, [t.name for t in e.topics.all()])
...     print('queries:', len(queries))
...
Python meetup ['Python']
Django sprint ['Python', 'Web']
Python meetup []
queries: 2

Without prefetch_related(), the same loop runs four queries: one for the events and one for each event’s topics. Finally, remove a link and delete a topic:

Python

>>> sprint.topics.remove(web)
>>> web.events.all()
<QuerySet []>
>>> python.delete()
(3, {'events.Event_topics': 2, 'events.Topic': 1})
>>> meetup.topics.all()
<QuerySet []>

remove() deletes one link row and leaves both the event and the topic. Deleting the Python topic deleted it and its two link rows, and the events are untouched. That answers the on_delete question: the link table Django makes always cascades, because a link row means nothing without both ends, and you cannot choose otherwise. When a link needs a rule of its own, or facts of its own, it becomes a model with two foreign keys, as Registration is. Leave the shell with exit().
