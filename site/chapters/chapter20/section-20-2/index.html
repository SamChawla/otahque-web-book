What You Need to Know

Relationship fields

Chapter 15 read relationships aloud: “one event has zero or more registrations; each registration belongs to exactly one event.” It drew the key on the many side, the registration, pointing at the one side, the event. Django turns that sentence into one field.

New Concept: relationship fields

What problem exists? A registration must refer to one event and one member. Storing the event’s title or the member’s email in the registration would copy facts that can change, and nothing would stop a registration from naming an event that does not exist.

What did people do before? They added an integer column, such as event_id, wrote the SQL FOREIGN KEY clause by hand, as you did in Chapter 15, and fetched the related row with a second query whenever they needed it.

What is a relationship field? A field on a model whose value is another model’s row. ForeignKey is the many-to-one kind: many registrations, one event. It becomes a column named after the field plus _id, such as event_id, holding the other row’s primary key, with a database foreign-key constraint and an index. OneToOneField is a foreign key that is also unique, so each row on the other side has at most one partner. ManyToManyField connects many rows to many rows through a third table that Django creates for you.

Why use one? The database refuses a key that points at nothing, the index makes lookups by event fast, and Python gets objects instead of numbers: booking.event is an Event, loaded when you ask for it.

Now let’s use it. Steps 3 and 4 write two models with two foreign keys each.

Table 20.1 compares the three fields. Otahque uses only ForeignKey in this chapter, because both new entities are rows with their own facts that point at two others.

You already have two many-to-many relationships, though you have not written one. Chapter 17’s user model inherits groups and user_permissions from PermissionsMixin, and Chapter 18’s sqlmigrate showed their link tables, such as accounts_user_groups, each row one pair of keys. A many-to-many field suits a link with no facts of its own. A registration has facts of its own, its status and its times, so Chapter 15 made it an entity, and here it becomes a model with two foreign keys. Django can treat such a model as the link table of a many-to-many field, through an option called through, but nothing in this chapter needs it.

A one-to-one field suits extra facts about exactly one row, such as a member profile beside the account. Otahque has no profile entity: the display name lives on the user model itself, and Chapter 27 decides whether a profile is needed. If it were, it would look like this, as an illustration only:

illustration only (not part of the project)

class Profile(models.Model):
    member = models.OneToOneField(
        settings.AUTH_USER_MODEL,
        on_delete=models.CASCADE,
    )
    bio = models.TextField(blank=True)

From the member’s side, sam.profile would be his profile. For a member with none, it raises RelatedObjectDoesNotExist, a kind of Profile.DoesNotExist, with the message User has no profile.

What happens on delete

Every foreign key forces a decision before Django accepts it: what should happen to the registrations when someone deletes the event they point at?

New Concept: the on_delete rule

What problem exists? Deleting an event that registrations point at would leave rows whose event_id names nothing. The database refuses that, so something must happen to them first.

What did people do before? They wrote ON DELETE clauses in their SQL, or deleted the dependent rows by hand before the parent, or forgot, and found orphaned rows later.

What is on_delete? A required argument of ForeignKey and OneToOneField that names the rule. models.CASCADE deletes the dependent rows too. models.PROTECT refuses the whole delete with a ProtectedError. models.SET_NULL empties the key, which the column must allow with null=True. Table 20.2 lists the common rules.

Why does it matter? The rule is a statement about what the data means. A registration records that Sai registered; deleting it erases history that Chapter 2’s cancellation rules and Chapter 15’s ERD both keep. So Otahque protects it.

Now let’s use it. Step 4 writes on_delete=models.PROTECT on all four keys, and Step 6 tries to delete the meetup.

Many tutorials use CASCADE everywhere. For Otahque’s registrations it would be wrong: deleting a cancelled event would silently erase every record that anyone registered for it. PROTECT has a cost too: a member who has registrations cannot be deleted either. How a member closes their account while history is kept is a question for Chapters 27 and 65, and this chapter’s L5 interview question looks ahead to it.

What Step 6 will see when it tries to delete the meetup is drawn in Figure 20.1.

Under the Hood: what a relationship becomes

In the database, event = models.ForeignKey(...) becomes a column, event_id bigint NOT NULL, with REFERENCES "events_event" ("id") and a CREATE INDEX on it; Step 5 reads both in the SQL. On SQLite, Django declares the constraint DEFERRABLE INITIALLY DEFERRED: the database checks it when the transaction commits, not on each statement. So Registration.objects.create(event_id=999, ...) inside a transaction appears to succeed, and the IntegrityError arrives at the commit. In the shell, each line commits at once, so you see the error immediately; inside a test or an atomic block, it arrives at the end. The on_delete rules in Table 20.2 other than the DB_ ones are not SQL at all. When you call delete(), Django’s deletion collector first queries every model with a foreign key to the row, applies each rule in Python, and only then sends DELETE statements, wrapped in one transaction. PROTECT raises its error during collection, before any DELETE is sent. Django 6.1’s DB_CASCADE, DB_SET_NULL, and DB_SET_DEFAULT instead write the rule into the table as SQL ON DELETE, so the database does the work without loading the rows; the price is that Django sends no pre_delete or post_delete signals for those rows.

Two directions

A foreign key is declared on one model, but you can follow it from both ends.

New Concept: forward access, reverse access, and related_name

What problem exists? Given a registration, you need its event. Given an event, you need its registrations. The key is stored only on the registration.

What did people do before? One direction read the key and fetched one row; the other ran a query for every row whose key matched, written by hand.

What are they? Forward access follows the field: booking.event is the event, and booking.event_id is the raw number, with no query. Reverse access starts from the other side: Django adds a related manager to Event, a manager limited to one event’s registrations, so meetup.registrations.all() and meetup.registrations.count() work like Event.objects, for this event only. The manager’s name comes from the field’s related_name argument. Without it, Django names it after the model, lowercased, plus _set: registration_set.

Why name it? meetup.registrations reads better than meetup.registration_set, and when two models point at the same model, as both new models point at the user, each needs its own clear name: sai.registrations and sam.organizer_assignments.

Now let’s use it. Step 6 follows both directions in the shell.

The four tables, the app that owns each model, and the reverse name on each relationship are drawn in Figure 20.2.

The double underscore from Chapter 19’s lookups also follows relationships. Registration.objects.filter(event__location='Virtual') follows the foreign key forwards and compares the event’s location. Event.objects.filter(registrations__member=sai) follows it backwards, using the related_name, and finds every event Sai has registered for. Django writes the SQL JOIN for you.

A reverse filter has one surprise. It joins each event to its registrations, so an event with two matching registrations appears twice in the result. distinct() removes the repeats. Step 6 shows both.

Prefer the setting, or get_user_model()?

Chapter 17 said that other code should not import accounts.User directly, so that the project can name its user model in one place. In a relationship field, use the setting: models.ForeignKey(settings.AUTH_USER_MODEL, ...). It is a string, 'accounts.User', which Django resolves after every model is loaded, so the import order of apps does not matter. In code that runs later, such as tests, views, and scripts, use get_user_model(), from django.contrib.auth, which returns the class itself. Both follow AUTH_USER_MODEL, and Django’s documentation recommends exactly this split.

Where the new models live

Chapter 7 created the events app with startapp and said that an app groups one area of the product. Registration is about to become a large area: Chapter 31 adds the pages where members register and cancel, and Chapter 46 a waitlist. This is the app that Chapter 7’s boundary record, Table 7.3, planned for this chapter. It gets its own app now, registrations, so that its model never has to move between apps after its table holds data, which needs careful migrations. Organizer assignment stays in events: it records who runs an event, and Chapter 30’s organizer access reads it from the event’s side.

A model can name a model in another app with a string, 'events.Event': the app label, a dot, and the class name. Like the user setting, the string is resolved after all models load, so registrations/models.py does not need to import events.models. Inside the events app, OrganizerAssignment can name Event directly, because the class is defined above it in the same file.

Try it yourself

Answer. ManyToManyField, because many events relate to many topics and the link holds nothing but the pair. Django would create a third table holding one row per pair of keys, like accounts_user_groups. If the link later needed its own facts, such as who added the topic, it would become a model with two foreign keys, as Registration is. Topics are not in Otahque’s first release, so the project has none; the optional lab in Step 9 builds them in a copy, so that you can see the third table.

One query per row

Following a relationship is so easy that it hides its cost. The queries one loop over three registrations runs, and the single query that replaces them, are drawn in Figure 20.3.

Under the Hood: lazy related objects and select_related()

A registration loaded from the database holds event_id and member_id, not the event or the member. The first time code reads booking.event, Django runs a query for that one event and caches it on that registration object; reading it again costs nothing. In a loop over many registrations, each one fetches its own event and its own member, so three registrations cost one query for the list and two for each row: seven. With a hundred rows it is two hundred and one. This pattern is called N+1: one query plus one more for each of N rows. select_related('event', 'member') tells the QuerySet to fetch the event and the member in the same query, with SQL INNER JOINs, and to build all three objects from each joined row: one query, however many rows. It follows forward foreign keys and one-to-one fields. For the reverse direction, such as every event with its registrations, prefetch_related('registrations') runs one more query for all the registrations at once and hands each event its own. Django 6.1 also adds fetch modes: fetch_mode(FETCH_PEERS) fetches a related object for every row of the QuerySet the first time any row asks, and fetch_mode(FETCH_RAISE) raises FieldFetchBlocked instead of querying, which makes an N+1 fail loudly. This book uses them only as a reference until Chapter 57 sets a policy.

Step 7 counts both versions on your own rows, and adds prefetch_related() for the reverse direction.

In practice: refusing to delete history

Situation. An organizer tidies up and deletes an old event that had forty registrations. Months later, a member asks for confirmation that they were registered, or the community wants to know how many people registered for its first year of events.

Application. With PROTECT on the registrations’ event key, the delete is refused, and the error names the rows that hold it. The organizer cancels the event instead, which changes its status and keeps every registration, as Chapter 2’s rules intend.

Consideration. Refusing deletes moves the decision to the people who own the data. Some rows should eventually go, such as personal details after an agreed time. That needs a stated retention rule and a deliberate process, Chapters 41 and 65, not a cascade that runs whenever someone deletes a parent row.
