Test Your Knowledge: Interview Questions

These five questions rehearse the chapter at interview level, one at each of five levels from junior to lead. L1 to L3 check what you have just done. L4 and L5 look ahead to a larger application with a team: attempt them now, and return to them after Chapters 27, 57, and 65. They are extension questions, not a gate to the next chapter. Each code proof except L5’s is a short file in the practice folder that starts by importing Chapter 16’s setup_django.py; run it from the folder that holds manage.py with uv run python ../practice/ followed by the file name. The proofs read your rows and leave them as they are.

L1 (Junior): What are ForeignKey, OneToOneField, and ManyToManyField, and where is the key stored for each?

What the interviewer is testing: Can you match a relationship described in words to a field, and say what it becomes in the database?

Flip to check your answerFold answer back

Perfect answer: All three connect one model’s rows to another’s. ForeignKey is many-to-one: many registrations belong to one event. It is declared on the many side and becomes a column such as event_id, holding the other row’s primary key, with a foreign-key constraint and an index. OneToOneField is a foreign key with a unique constraint, for at most one row on each side, such as a profile beside an account. ManyToManyField is many-to-many, such as members and groups; no column is added to either table, because Django creates a third table that holds one row per pair of keys. I choose by reading the relationship aloud, and when a link has facts of its own, such as a registration’s status, I make it a model with two foreign keys instead of a plain many-to-many field. Foreign keys and one-to-one fields also need an on_delete rule.

Behind the scenes:

relationship fields (summary)

ForeignKey      -> event_id column, constraint, index
OneToOneField   -> the same, plus UNIQUE
ManyToManyField -> a third table: (left_id, right_id)
link with facts -> a model with two ForeignKeys

Code proof: two fields from your project, asked what they are:

../practice/l1_fields.py

import setup_django
from django.contrib.auth import get_user_model

from registrations.models import Registration

User = get_user_model()
key = Registration._meta.get_field('event')
print(type(key).__name__, key.many_to_one, key.column)
groups = User._meta.get_field('groups')
print(type(groups).__name__, groups.many_to_many,
      groups.remote_field.through._meta.db_table)

Output

ForeignKey True event_id
ManyToManyField True accounts_user_groups

_meta is Django’s documented description of a model. The registration’s event is a many-to-one field stored in the column event_id; the user’s groups, from Chapter 17’s PermissionsMixin, is many-to-many, stored in the table accounts_user_groups.

Common mistakes:

  • Putting the foreign key on the one side, such as a registration field on Event.
  • Using ManyToManyField for a link that needs its own status or times.
  • Forgetting that OneToOneField is unique, so a second profile for the same member is refused.

Follow-up the interviewer might ask:

  • “How would you add a status to an existing many-to-many link?”
  • “Why does ManyToManyField need no on_delete?”

L2 (Mid-Level): What does related_name do, and why can a filter across a reverse relationship return the same row twice?

What the interviewer is testing: Do you understand the reverse side of a relationship, in Python and in the SQL it produces?

Flip to check your answerFold answer back

Perfect answer: A foreign key is declared on one model, but Django adds the reverse direction to the other model. related_name names it. On an object it is a related manager: meetup.registrations.all() and .count() query only that event’s registrations. Without related_name the manager is called registration_set, and the name used in lookups is the lowercase model name. Two relations from different models to the same model need different names, or check reports fields.E304 and E305. In a filter, Event.objects.filter(registrations__status='active') becomes a JOIN from events to registrations with a WHERE on the registration’s status. The join produces one row per matching registration, so an event with two active registrations appears twice. distinct() asks the database to return each event once. Conditions in one filter() call must hold for the same related row; conditions in chained filter() calls may match different ones.

Behind the scenes:

related_name (summary)

related_name='registrations'
  meetup.registrations    -> manager, this event only
  filter(registrations__) -> JOIN registrations
two matches               -> the event twice
.distinct()               -> each event once

Code proof: Sai’s reverse manager, and the same filter counted with and without distinct():

../practice/l2_reverse.py

import setup_django
from django.contrib.auth import get_user_model

from events.models import Event

User = get_user_model()
sai = User.objects.get(email='sai@example.org')
print(type(sai.registrations).__name__)
print(sai.registrations.count())
active = 'active'
matching = Event.objects.filter(registrations__status=active)
print(matching.count(), matching.distinct().count())

Output

RelatedManager
2
3 2

Common mistakes:

  • Looping over meetup.registrations instead of meetup.registrations.all().
  • Giving two relations to the user model the same related_name.
  • Counting results of a reverse filter without distinct(), and reporting too many events.

Follow-up the interviewer might ask:

  • “When would you set related_name='+'?”
  • “What is the difference between filter(a, b) and filter(a).filter(b) across a many-valued relation?”

L3 (Senior): How do you choose an on_delete rule, and what is the difference between Django’s CASCADE and Django 6.1’s DB_CASCADE?

What the interviewer is testing: Can you treat a deletion rule as a statement about data, and do you know where the rule actually runs?

Flip to check your answerFold answer back

Perfect answer: I ask what a dependent row means once its parent is gone. If it is history that the business needs, such as a registration or an organizer assignment, I use PROTECT, and accept that deleting the parent becomes a deliberate process, such as cancelling or anonymizing. If the row is part of its parent and meaningless alone, such as a line in a draft that is being discarded, CASCADE fits. If the link is optional, SET_NULL, with null=True. Where the rule runs matters too. CASCADE, PROTECT, and SET_NULL are applied in Python by Django’s deletion collector: it queries the dependent rows, sends pre_delete and post_delete signals for each, and deletes inside one transaction. DB_CASCADE, new in Django 6.1, writes ON DELETE CASCADE into the table, so the database deletes the rows itself: faster for many rows, but without loading them and without signals, so code that relies on those signals will not run. Whatever I choose, a test that tries the delete proves the rule.

Behind the scenes:

on_delete (summary)

PROTECT    -> collector refuses: ProtectedError
CASCADE    -> collector deletes, sends signals
SET_NULL   -> collector empties the key
DB_CASCADE -> SQL ON DELETE CASCADE, no signals

Code proof: inside a transaction that is rolled back, a temporary member in a group is deleted, and the group link goes with them, because Django’s own link table uses CASCADE; then Sai’s delete is refused:

../practice/l3_on_delete.py

import setup_django
from django.contrib.auth import get_user_model
from django.contrib.auth.models import Group
from django.db import transaction
from django.db.models import ProtectedError

User = get_user_model()
with transaction.atomic():
    temp = User.objects.create_user(
        'temp@example.org', display_name='Temp'
    )
    temp.groups.add(Group.objects.create(name='Helpers'))
    print('CASCADE:', temp.delete())
    sai = User.objects.get(email='sai@example.org')
    try:
        sai.delete()
    except ProtectedError as error:
        print('PROTECT:', len(error.protected_objects),
              'registrations keep Sai')
    transaction.set_rollback(True)
print(User.objects.filter(email='sai@example.org').exists())

Output

CASCADE: (2, {'accounts.User_groups': 1, 'accounts.User': 1})
PROTECT: 2 registrations keep Sai
True

delete() reported two rows: the member and the link row in accounts_user_groups. protected_objects holds the rows that refused Sai’s delete: her two registrations. The rollback undoes the temporary member and group.

Common mistakes:

  • Using CASCADE by habit for records that history needs.
  • Choosing SET_NULL without null=True, which check reports as fields.E320.
  • Switching to DB_CASCADE for speed when signal receivers clean up files or caches.

Follow-up the interviewer might ask:

  • “An event is cancelled. Should its registrations be deleted, cancelled, or left alone?”
  • “Where else can deletes bypass your Python rules?”

L4 (Staff): A page that lists registrations with member names and event titles runs 201 queries. How do you find the cause, fix it, and keep it fixed?

What the interviewer is testing: Looking ahead: can you diagnose N+1 with related objects, choose the right tool for each relationship, and stop it returning?

Flip to check your answerFold answer back

Perfect answer: 201 for 100 rows is 1 + 2N: one query for the registrations, then one for each row’s member and one for its event, because each related object is loaded the first time the template reads it. I confirm it with assertNumQueries, CaptureQueriesContext, or a tool such as Django Debug Toolbar, and look for the repeated query. Both relations are forward foreign keys, so select_related('member', 'event') fetches them in the same query with joins, and the page runs one query. For reverse or many-to-many relations, such as each event’s registrations, prefetch_related() adds one query per relation instead of one per row. To keep it fixed, the page’s test asserts the query count with several rows, so N+1 cannot hide behind one row. Django 6.1 adds another fence: fetch_mode(FETCH_RAISE) makes any unplanned related fetch raise FieldFetchBlocked, so a missing select_related() fails in development instead of slowing production. In Otahque, Chapter 22 composes these queries into named methods, and Chapter 57 measures them and sets the project’s policy.

Behind the scenes:

N+1 (summary)

1 query       -> the registrations
+2 per row    -> member and event, on first access
select_related('member', 'event') -> 1 query
FETCH_RAISE   -> unplanned fetch raises at once

Code proof: with FETCH_RAISE, the first related access stops the loop; with select_related(), the same loop runs:

../practice/l4_fetch_raise.py

import setup_django
from django.core.exceptions import FieldFetchBlocked
from django.db.models import FETCH_RAISE

from registrations.models import Registration

strict = Registration.objects.fetch_mode(FETCH_RAISE)
try:
    for booking in strict:
        print(booking.event.title)
except FieldFetchBlocked as error:
    print('blocked:', error)
for booking in strict.select_related('event'):
    print(booking.event.title)

Output

blocked: Fetching of Registration.event blocked.
Python meetup
Python meetup
Django workshop

Common mistakes:

  • Using prefetch_related() for a forward foreign key, where a join needs no extra query.
  • Calling select_related() with no arguments, which follows every non-null foreign key; Django 6.1 deprecates that form and warns.
  • Testing the query count with one row, where N+1 cannot show.

Follow-up the interviewer might ask:

  • “When is a second query from prefetch_related() better than a join?”
  • “How would you list each event with only its active registrations, without N+1?”

L5 (Lead): A member asks to close their account, but PROTECT keeps their registrations. How do you design for privacy and history together?

What the interviewer is testing: Looking ahead: can you turn a database rule into a product and data-protection design, with owners and evidence?

Flip to check your answerFold answer back

Perfect answer: PROTECT did its job: it stopped a delete that would have broken history, and it moved the decision to the people who own the data. The design starts with a written policy, agreed with whoever is responsible for data protection: what Otahque must keep, such as registration counts for past events, what it must remove, such as the email address and display name, and for how long anything is kept. Closing an account then becomes a deliberate workflow rather than delete(): deactivate the account so it cannot sign in, cancel future registrations so places are released, and replace personal details with an anonymous placeholder, so that past registrations still count but no longer identify the member. A retention job, from Chapter 41’s management commands, removes what the policy says to remove when its time comes, and audit records, in Chapter 65, show who closed what and when. I would give the member a way to export their data first, and test each part: closure, export, released places, and the retention rule. Chapter 27 builds account workflows, and Chapter 65 audit and retention; the policy itself is a product decision, not something the database chooses.

Behind the scenes:

account closure (summary)

request -> deactivate, cancel future places
personal details -> replaced, anonymous
past registrations -> kept, counted
retention job -> removes data on schedule
evidence -> tests and audit records

Common mistakes:

  • Switching the rule to CASCADE to make a deletion request “work”, and erasing other people’s history.
  • Treating deactivation alone as closure, while personal details stay.
  • Deciding retention periods in code review instead of in a written, owned policy.

Follow-up the interviewer might ask:

  • “Which data would you keep for an event that has already happened, and why?”
  • “How would you prove to a member that their details were removed?”
