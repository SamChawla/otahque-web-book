2.3 Stories and acceptance criteria

Sai returns to Otahque after requesting a workshop place. The registration page looked reassuring, but she still wants to know: “Am I on the list?” Our journey identifies that moment. We now need a short description of the need and clear conditions for deciding whether the product meets it.

Write the need from the person’s point of view

A user story describes a capability someone needs and the reason it matters. A useful starting pattern is “As a [person or role], I want [capability], so that [benefit].” The pattern helps us ask who, what, and why. Filling in its blanks does not make an unclear requirement useful.

For Sai: “As a member, I want to see the current status of my registration, so that I know whether I have a place.” This keeps the benefit visible. “As a user, I want a green message” chooses a display detail without saying what the person must learn.

For Raj: “As a member, I want to cancel my own registration, so that my decision is reflected in the event record.” For Sam: “As an organizer, I want to see current registrations for my assigned event, so that I can prepare for the people who have places.” These stories describe related needs without combining every action into one oversized story.

Stories are not only about registration. For Sam: “As an organizer, I want to preview my event before publishing it, so that visitors see correct details.” For Soni: “As a visitor, I want to read a published event’s date, time, place, and intended audience, so that I can decide whether to register.” Publication and browsing belong to the same first release as registration.

Describe observable conditions

Acceptance criteria are conditions a behaviour must satisfy before we accept it as meeting a requirement. Observable means that someone can inspect the result. “Registration works properly” is too vague. “After a successful registration, Sai sees a confirmed status and appears once in Sam’s active registration list” gives us something to check.

One way to write a concrete example is Given, When, Then. Given describes the starting situation. When describes an action or event. Then describes the expected result. This is a writing aid, not a requirement to use a particular testing tool.

Given: the event is published, registration is open, Sai is signed in, she has no active registration for it, and a place remains. When: Sai requests a place. Then: she receives confirmation, can find that registration later, and appears once in the assigned organizer’s current list. The active count increases by one.

Given: Sai already has an active registration for that event. When: she submits another registration request. Then: the product shows her existing registration; it does not create another active place or increase the active count. Repeating an action is common, even without anyone trying to cause harm.

Criteria for publishing an event

Publication needs criteria too, because visitors rely on the details Sam publishes.

Given: Sam is assigned to a draft event with a title, description, start time, timezone, place, capacity, and registration times. When: he previews it. Then: he sees the details as visitors will see them, and the event is still not visible to visitors.

Given: the same draft is complete and valid. When: Sam publishes it. Then: visitors can find and read it, and members can request places once registration opens.

Given: a draft is missing its timezone, or its registration would close after the event starts. When: Sam tries to publish it. Then: publication is refused, the event stays a draft, and the message names each detail he must correct without discarding the details he has already entered. Section 2.4 explains the timing rule behind this example.

Given: an event is still a draft. When: Soni, or any other visitor, looks for it. Then: it does not appear, and nobody can request a place for it.

Describe unsuccessful and forbidden actions

Given: all places are taken. When: Soni requests a place. Then: no new active registration is created, the active count stays unchanged, and she receives an explanation that no place was confirmed. The first release does not offer an unplanned waiting list.

Given: Raj has an active registration and cancellation is allowed. When: he cancels it. Then: Raj sees a cancelled status, the registration no longer consumes capacity, and Sam’s active list excludes it. Raj’s history can still show the cancelled registration. Removing a place from the active count need not erase its history.

An abuse case describes an attempt to use the product in a harmful or unauthorized way. Suppose Sai tries to cancel Raj’s registration by changing a reference in a request. The expected result is rejection: his registration and the count remain unchanged, and she receives no private registration details. Hiding a button does not define this boundary; every attempt must respect ownership.

Given: Sam is assigned to one event but not another. When: he attempts to open the other event’s registration list or change its details. Then: access is denied, and nothing is changed. A role name alone does not explain which records a person may manage.

Keep criteria separate from implementation

These criteria say what must be true. They do not select database tables, page layouts, or Python functions. Later we will implement checks and write executable tests. For now, we can review examples on paper and find contradictions before they spread into code.

Que. 1 Is “show a green success message” enough to accept registration?

Show answerHide answer

Answer. No. The message must agree with the saved registration and the organizer’s list. A colour or message alone cannot establish that a place exists.

Que. 2 Why include a request that should be rejected?

Show answerHide answer

Answer. A useful requirement defines its boundaries. Full events, duplicate requests, invalid publication, and attempts to alter another person’s registration reveal whether the product protects capacity, accuracy, and ownership.

Try it yourself

Write a Given/When/Then example for a visitor who tries to register without signing in. State what must not happen as well as what the visitor should see.

Que. 3 What is one suitable answer?

Show answerHide answer

Answer. Given a visitor who is not signed in, when the visitor requests a place, then the product asks the visitor to create an account or sign in and does not create a registration yet. Returning from sign-in must still allow the person to continue with the intended event.
